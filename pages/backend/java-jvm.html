一、JVM 内存结构篇 ​

1.1 JVM 由那些部分组成，运行流程是什么？ ​

（1）类加载器（ClassLoader）：负责读取、加载 class 字节码

理解：它就像一个文件搬运工。它不是去翻译 Java 源码，而是去磁盘 / 网络找到编译好的 class 字节码文件，校验、解析这个类的信息，准备送入 JVM 内存。 内部三步：加载 → 链接 → 初始化（就是我们说的类加载全过程，双亲委派就是它里面的规则）

（2）运行时数据区（Runtime Data Area）：存放程序运行时所有数据的内存空间

理解：相当于 JVM 的 "内存工作台"。ClassLoader 把字节码里的类信息、后面创建的对象、方法调用信息，全部放到这片内存里。 字节码本身只是一套 JVM 定义的指令，CPU 不认，不能直接跑，必须等执行引擎来读取、翻译执行。 分区小提示（辅助记忆）：这块内存分成 5 块：程序计数器、虚拟机栈、本地方法栈（线程私有）；堆、方法区（线程共享）。

（3）执行引擎（Execution Engine）：读取内存里的字节码，翻译成 CPU 可以识别的机器指令，交给 CPU 执行

理解：它是 JVM 里真正干活 "跑代码" 的角色。有两种翻译模式：解释器逐行翻译、JIT 把高频热点代码提前编译缓存，提升速度；GC 垃圾回收器也属于执行引擎这一块。

（4）本地库接口（Native Method Library）：兜底调用操作系统底层能力

理解：Java 有些功能自己实现不了（比如获取系统时间、线程阻塞、操作系统底层操作），这类方法会标记 native，没有 Java 实现。执行引擎遇到 native 方法时，就通过这个接口，调用 C/C++ 写好的本地函数库，借助操作系统能力完成功能。

1.2 什么是程序计数器？ ​

程序计数器：线程私有的，里面保存字节码的行号，用来记录当前正在执行的字节码指令地址。

Java 虚拟机实现多线程，是靠线程轮流切换、分配时间片执行。在任意时刻，一个 CPU 处理器同一时间只能执行一个线程。如果正在运行的线程分配的时间片耗尽，线程就会被挂起，处理器切换去执行别的线程。等后面再次调度回这个被挂起的线程时，处理器需要知道这个线程上次执行到哪个位置。

程序计数器就是用来解决这个问题的：读取它保存的字节码行号，从上一次中断的位置继续往下执行。

程序计数器是 JVM 规范里唯一一个没有规定会发生 OOM 的内存区域，这块空间也不需要 GC。

1.3 你能给我详细的介绍 Java 堆吗？ ​

Java 堆是线程共享的内存区域，主要存放对象实例、数组。如果堆内存空间耗尽，并且无法继续扩容，就会抛出 OutOfMemoryError 异常，它也是 GC 垃圾回收最主要的区域。

堆一般分为年轻代和老年代：

  • 年轻代分为三块：Eden 区 + 两个大小相等的 Survivor 区（form、to）。新创建的对象优先分配在 Eden 区；经过多次 GC 后还存活的对象，会晋升到老年代。
  • 老年代：存放生命周期长、存活时间久的对象。

补充：元空间不属于堆！ 元空间是 JVM 规范里方法区的实现，存放类元信息、字段、方法、静态变量、常量等。

元空间（MetaSpace）介绍 ​

在 JDK8 之前，HotSpot 使用**永久代（PermGen）**实现方法区，类元数据、常量信息都放在永久代，永久代是在 JVM 堆里面的，有固定上限。加载大量类的时候很容易出现 OOM，需要手动配置永久代大小。

JDK8 彻底移除永久代，换成元空间，原因两点：

  1. 永久代容易 OOM，内存管理不灵活；
  2. 为了统一 HotSpot 和 JRockit 虚拟机（JRockit 本身就没有永久代）。

版本变化重点：

  • JDK7：字符串常量池从永久代移到堆中
  • JDK8：永久代彻底删除，类元信息、方法、字段、静态属性等全部迁移到元空间

元空间和永久代最大区别： 永久代占用 JVM 堆内存；元空间使用操作系统本地内存，默认上限是机器可用内存。

注意：元空间只是不容易 OOM，加载海量类时依然会 OOM。

1.4 什么是虚拟机栈 ​

  • 每个线程运行时所需要的内存，称为虚拟机栈，遵循先进后出的特点
  • 每个栈由多个**栈帧（frame）**组成，对应着每次方法调用时所占用的内存
  • 每个线程只能有一个活动栈帧，对应着当前正在执行的那个方法

  1. 垃圾回收是否涉及栈内存？ 垃圾回收主要针对堆内存；栈帧弹栈之后，内存就直接释放，不需要 GC。

  2. 栈内存分配越大越好吗？ 未必，默认的栈内存通常为 1024k。 栈内存设置越大，能开启的线程数量就越少。举个例子：机器总内存为 512m，栈大小 1024k 时最多支持 512 个线程；如果改成 2048k，可支持的线程数就减半。

  3. 方法内的局部变量是否线程安全？

  • 如果方法内局部变量没有逃离方法的作用范围，它是线程安全的
  • 如果是局部变量引用了对象，并逃离方法的作用范围，就需要考虑线程安全问题

栈内存溢出情况

  • 栈帧过多导致栈内存溢出，典型场景：无限递归调用
  • 栈帧过大导致栈内存溢出

1.5 能不能解释一下方法区？ ​

方法区是 JVM 中一块线程共享的内存区域，属于逻辑分区。主要存放加载进来的类元信息、运行时常量池、静态变量、方法字节码以及 JIT 编译后的代码缓存。

JDK8 是一个重要分水岭： JDK7 及之前，方法区的实现是永久代（PermGen），放在堆里面； JDK8 彻底移除永久代，改用元空间 Metaspace 实现方法区，元空间使用本地内存，不再占用堆空间。

这里有个高频考点：JDK7 的时候字符串常量池就已经从方法区移到堆中了。

方法区也会发生 GC，GC 目标主要是卸载不再使用的类。 一个类要被卸载，需要同时满足三个条件：

  1. 类的所有实例都被回收
  2. 加载该类的类加载器被回收
  3. 该类对应的 Class 对象没有引用

如果元空间内存耗尽，会抛出 java.lang.OutOfMemoryError: Metaspace。

为什么废弃永久代，改用元空间？ ​

永久代固定上限、容易 OOM、和堆 GC 绑定 STW 长；元空间使用本地内存，容量更灵活，降低 OOM 概率，同时统一不同虚拟机实现。

1.6 你听过直接内存吗？ ​

直接内存（Direct Memory），不属于 JVM 运行时数据区，是操作系统本地内存，不在堆、也不在方法区。 它不受 JVM 垃圾回收直接管理，主要在 NIO 中使用 ByteBuffer.allocateDirect() 分配，作为数据缓冲区。

✅ 优点：少一次内存拷贝，读写速度快； ❌ 缺点：分配、回收成本高；大小不受 -Xmx 堆参数限制，但受整机物理内存限制，使用不当也会 OOM。

原理对比 ​

  • 传统 BIO：磁盘 → 内核缓冲区 → JVM 堆缓冲区 → 内核缓冲区 → 磁盘。存在两次拷贝。
  • NIO 直接内存：磁盘 → 直接内存（内核与用户空间共享） → 磁盘。省去堆内存这一次拷贝，所以大文件传输性能更好。

注意：直接内存不是完全不 GC。DirectByteBuffer 对象在堆里，它是直接内存的引用；当这个堆内对象被 GC 时，会触发底层系统调用去释放对应的直接内存。如果大量分配直接内存又不释放，会抛出 OutOfMemoryError: Direct buffer memory。

1.7 堆栈的区别是什么？ ​

1、栈内存一般会用来存储局部变量和方法调用，但堆内存是用来存储 Java 对象和数组的。堆会 GC 垃圾回收，而栈不会。

2、栈内存是线程私有的，而堆内存是线程共有的。

3、两者异常错误不同，但如果栈内存或者堆内存不足都会抛出异常。

栈空间不足：java.lang.StackOverFlowError。

堆空间不足：java.lang.OutOfMemoryError。

二、类加载机制篇 ​

2.1 什么是类加载器，类加载器有哪些？ ​

类加载器（ClassLoader）：作用是把字节码文件加载进 JVM，生成对应的 Class 对象。它负责查找、读取字节码，也可以加载资源文件。

一共四层：

  1. 启动类加载器（Bootstrap ClassLoader） 由 C++ 实现，不继承 ClassLoader；负责加载 JAVA_HOME/jre/lib 下核心类库，比如 java.lang.*。

  2. 扩展类加载器（ExtClassLoader） ClassLoader 的子类；加载 JAVA_HOME/jre/lib/ext 扩展目录下的 jar 包。

  3. 应用类加载器（AppClassLoader / 系统类加载器） ClassLoader 的子类；加载 classpath 路径下的类，也就是我们自己写的业务代码、项目引入依赖。

  4. 自定义类加载器 自己继承 ClassLoader 重写方法，自定义加载逻辑；常见场景：加密字节码、从网络/数据库加载 class、热部署。

⚠️ 重点：它们之间不是继承关系，是双亲委派的委派关系（parent 委派）。 加载类时，先交给父加载器去尝试加载；父加载器加载不了，自己才加载。 目的：防止同一个类被重复加载，保证核心类安全（防止篡改 JDK 核心类）。

2.2 什么是双亲委派模型？ ​

双亲委派模型是类加载器的一种委派机制。 当一个类加载器收到加载类的请求时，它首先不会自己尝试加载这个类，而是把加载请求委托给父加载器去处理，这个过程会一直向上递归，直到启动类加载器。

如果父加载器在自己的加载范围内能够加载成功，就直接返回 Class 对象； 只有所有父加载器都加载失败的时候，当前类加载器才会尝试自己去加载这个类。

2.3 JVM 为什么采用双亲委派机制 ​

（1）通过双亲委派机制可以避免某一个类被重复加载，当父类已经加载后则无需重复加载，保证唯一性。

（2）为了安全，保证类库 API 不会被修改

在工程中新建 java.lang 包，接着在该包下新建 String 类，并定义 main 函数

java
public class String {

    public static void main(String[] args) {

        System.out.println("demo info");
    }
}

此时执行 main 函数，会出现异常，在类 java.lang.String 中找不到 main 方法。

出现该信息是因为由双亲委派的机制，java.lang.String 在启动类加载器（Bootstrap ClassLoader）得到加载，因为在核心 jre 库中有其相同名字的类文件，但该类中并没有 main 方法。这样就能防止恶意篡改核心 API 库。

2.4 说一下类装载的执行过程？ ​

加载一共分为五个阶段：加载、验证、准备、解析、初始化。

注意：加载到初始化是按顺序开始，但不一定按顺序结束，解析阶段有可能在初始化之后（支持动态绑定）。

  1. 加载（Loading） 通过类加载器，根据全类名查找字节码，把 class 文件的二进制数据读入 JVM，在方法区生成类元数据，同时在堆中创建这个类对应的 Class 对象，作为访问方法区元数据的入口。
  2. 验证（Verification） 校验字节码是否合法、安全，防止恶意字节码破坏 JVM。包含：文件格式验证、元数据验证、字节码验证、符号引用验证。
  3. 准备（Preparation） 为类中静态变量（static）分配内存，并且赋默认初始值（零值）。 ⚠️ 重点：这一步不是赋代码里写的初始值； 比如 public static int a = 100;，准备阶段 a = 0，等到初始化阶段才赋值 100。static final 常量比较特殊，编译期就放入常量池，准备阶段直接赋值。
  4. 解析（Resolution） 把常量池里的符号引用替换成直接引用。 符号引用：字符串形式，不知道实际内存地址； 直接引用：指向内存地址、指针。 👉 静态绑定：解析在初始化之前；动态绑定（多态方法）可以推迟到运行时。
  5. 初始化（Initialization） 真正执行类的静态代码块、静态变量显式赋值，执行 <clinit>() 方法。<clinit>() 由编译器自动收集静态变量赋值语句和静态代码块合并生成。初始化是懒加载，只有主动引用的时候才触发。

三、垃圾回收篇 ​

3.1 简述 Java 垃圾回收机制？（GC 是什么？为什么要 GC） ​

GC 是 JVM 自动回收堆中无引用对象、释放内存的机制。目的：避免手动管理内存，防止内存泄漏、野指针，减轻程序员负担；GC 主要作用在堆，不同引用类型回收时机不一样。

3.2 对象什么时候可以被垃圾器回收 ​

当对象没有任何有效引用指向它时，该对象就成为垃圾，具备被 GC 回收的条件，但不一定马上回收，要等 GC 触发时才可能回收。

  1. 引用计数法 给对象维护一个引用计数器，有引用指向它，计数器 +1；引用失效，计数器 -1。计数器为 0 代表是垃圾。缺点：无法解决循环引用问题，JVM 没有采用这个算法。
  2. 可达性分析算法（JVM 使用） 以 GC Roots 作为起始根节点，向下搜索引用链；一个对象和 GC Roots 之间没有引用链相连，就判定为垃圾。

3.2.1 引用计数法 ​

引用计数法：每个对象头部维护一个引用计数器。每当有引用指向该对象，计数器 +1；引用断开，计数器 -1；计数器等于 0，代表对象可以被回收。

✅ 优点

  1. 实时性高：不需要等到内存不足才触发回收，计数归 0 就可以立刻回收。
  2. GC 时不需要挂起用户线程，没有 STW。
  3. 区域性好：只更新当前对象的计数器，不需要扫描整个堆。

❌ 缺点

  1. 赋值、断开引用时都要更新计数器，存在额外开销。
  2. 内存充足的时候，依然持续统计计数，浪费 CPU 资源。
  3. 无法解决循环引用问题（致命缺陷），会造成内存泄漏，这也是 HotSpot JVM 没有选用它的核心原因。

循环引用示例代码 ​

java
class TestObj {
    TestObj instance;
}

public class RefCountDemo {
    public static void main(String[] args) {
        TestObj a = new TestObj();
        TestObj b = new TestObj();

        // 互相引用，形成循环引用
        a.instance = b;
        b.instance = a;

        // 切断外部引用
        a = null;
        b = null;

        // 此时 a、b 两个对象互相持有对方引用，计数器都不为 0
        // 引用计数法识别不出垃圾，无法回收，内存泄漏
        System.gc();
    }
}

解释： a、b 外部引用置为 null 之后，a.instance 指向 b，b.instance 指向 a，两个对象的引用计数器都等于 1，引用计数法判定对象还在被使用，不会回收。但实际上这两个对象已经没有外部通路访问，属于垃圾，造成内存泄漏。

3.2.2 可达性分析算法 ​

可达性分析是 HotSpot 虚拟机判断对象是否为垃圾的核心算法。以 GC Roots 作为起始节点，沿着引用链进行遍历，能够遍历到达的对象判定为存活；无法到达的对象标记为可回收对象。该方案解决了引用计数法无法处理循环引用的缺陷。

3.3 JVM 垃圾回收算法有哪些？ ​

标记清除（Mark-Sweep） ​

流程：先标记不可达的垃圾对象 → 再清除标记对象 优点：实现简单，不需要移动对象 缺点：

  1. 标记、清除阶段都要遍历全部对象，效率一般；
  2. 产生大量内存碎片；
  3. GC 会 STW（暂停用户线程）

记忆点：只标记、只清掉，不挪对象 → 碎片多

复制算法（Copying） ​

流程：内存对半划分成两块，一块是使用区（From）、一块空闲区（To）；GC 时把 From 里所有存活对象复制到 To，复制完成后直接清空 From，交换 From/To 身份。 优点：存活对象连续，没有内存碎片；垃圾多的时候复制量小，速度快 缺点：同一时间只能用一半内存，内存利用率低；存活对象很多时，复制开销很大

记忆点：对半分，活的搬走，整块清空 → 无碎片，浪费一半空间

标记整理 / 标记压缩（Mark-Compact） ​

流程：第一步和标记清除一样，标记存活对象；不直接删垃圾，而是把所有存活对象往内存一端紧凑移动，移动完成后，一次性清理边界之外全部垃圾。 优点：无内存碎片，不需要预留额外空间，内存利用率高 缺点：需要移动对象、更新引用地址，开销比标记清除更大，STW 时间更长

记忆点：先标记，存活对象挤到一边，尾部垃圾一次性清除 → 无碎片，移动对象成本高

三者横向对比速记 ​

  • 标记清除：不移动对象，有碎片
  • 复制算法：复制存活对象，无碎片，浪费一半内存
  • 标记整理：移动存活对象做压缩，无碎片，开销大

3.4 分代收集算法 ​

3.4.1 堆分代概述（JDK8） ​

堆划分为 新生代 : 老年代 = 1 : 2

  • JDK7 及之前：还有永久代（方法区实现）；JDK8 永久代移除，替换为元空间（直接使用本地内存，不在堆内）
  • 新生代内部三块：Eden : S0(From) : S1(To) = 8 : 1 : 1

    S0、S1 也叫 Survivor 幸存区，同一时间只有一块是 From（在用），另一块是 To（空闲）

GC 类型区分：

  1. Minor GC（Young GC）：只回收新生代
  2. Major GC：只回收老年代（出现较少）
  3. Full GC：回收新生代 + 老年代，STW 耗时很长，开发中尽量规避
  4. Mixed GC：G1 收集器特有，回收全部新生代 + 部分老年代区域

STW(Stop-The-World)：GC 执行时，暂停全部用户业务线程，GC 结束后恢复。

3.4.2 新生代工作流程（复制算法） ​

  1. 新建对象优先分配到 Eden 区。
  2. Eden 空间填满，触发 Minor GC：标记 Eden + From 幸存区中的存活对象，复制到 To 幸存区。
  3. 复制完成，清空 Eden 和 From；交换 From、To 的身份（原来 To 变成下一轮 From，原来 From 变成 To）。
  4. 循环往复，每次 Minor GC，存活对象在两个 Survivor 之间来回拷贝，对象年龄 +1。
  5. 对象年龄达到阈值（默认最大 15 岁），晋升到老年代； 触发提前晋升场景：Survivor 空间放不下存活对象、大对象直接分配到老年代。

3.5 说一下 JVM 有哪些垃圾回收器？ ​

在 jvm 中，实现了多种垃圾收集器，包括：

  • 串行垃圾收集器
  • 并行垃圾收集器
  • CMS（并发）垃圾收集器
  • G1 垃圾收集器

3.5.1 串行垃圾收集器 ​

  • Serial：新生代，复制算法；Serial Old：老年代，标记整理
  • GC 线程：单线程回收
  • STW：整个 GC 全过程，所有业务线程全部暂停阻塞
  • 适用：小堆、客户端程序

3.5.2 并行垃圾收集器 JDK8 默认使用此垃圾回收器 ​

  • ParNew：新生代，复制算法；Parallel Old：老年代，标记整理
  • GC 线程：多条 GC 线程同时回收
  • STW：整个 GC 全过程，所有业务线程也全部暂停阻塞

✅ 串行、并行共同点：GC 全程 STW，业务线程全卡住 ✅ 差别只在于：串行只有 1 个 GC 干活；并行开多个 GC 线程一起干活，回收更快，追求吞吐量

3.5.3 CMS（并发）垃圾收集器 ​

  • 算法：标记 - 清除（会产生内存碎片）
  • GC 线程：分阶段执行
  • STW：不是全程阻塞业务线程
    • 初始标记、重新标记：短暂 STW，业务线程阻塞
    • 并发标记、并发清除：GC 线程和业务线程一起跑，应用正常运行，不阻塞
  • 目标：压低 STW 停顿时间，追求低延迟。

一句话区分重点 ​

  • 串行：业务全停，1 个 GC 线程回收
  • 并行：业务全停，多个 GC 线程回收
  • CMS：大部分阶段业务不停，只有少量短时间 STW

3.6 G1 垃圾回收器 ​

3.7 强引用、软引用、弱引用、虚引用的区别？ ​

3.7.1 强引用 ​

强引用：只要 GC Roots 能通过强引用到达对象，就不会被回收；断开所有强引用，对象才可以被垃圾回收。

java
// 强引用，日常 new 对象默认就是强引用
User user = new User();
// user = null; // 只有把强引用置空，GC Roots 不可达，对象才会被回收

3.7.2 软引用 ​

软引用：仅有软引用引用该对象时，内存充足 GC 不回收；内存不足即将 OOM 时，GC 回收该对象。适合做缓存。

java
User user = new User();
// 使用软引用包裹对象
SoftReference<User> softReference = new SoftReference<>(user);
user = null; // 重点：切断原强引用，此时对象只剩下软引用

3.7.3 弱引用 ​

弱引用：仅有弱引用引用该对象时，只要发生 GC，无论内存是否充足，都会回收该对象。典型场景：WeakHashMap、ThreadLocal 的 key。

java
User user = new User();
// 使用弱引用包裹对象
WeakReference<User> weakReference = new WeakReference<>(user);
user = null; // 重点：切断原强引用，此时对象只剩下弱引用

3.7.4 虚引用 ​

虚引用：无法通过 get() 获取对象；对象被回收时，虚引用会被加入引用队列，仅用来监听对象回收事件，一般用于堆外内存清理。

java
ReferenceQueue<User> queue = new ReferenceQueue<>();
User user = new User();
// 虚引用必须绑定引用队列
PhantomReference<User> phantomReference = new PhantomReference<>(user, queue);
user = null;

延伸话题：ThreadLocal 内存泄漏问题

ThreadLocal 用的就是弱引用，看以下源码：

java
static class Entry extends WeakReference<ThreadLocal<?>> {
    Object value;

    Entry(ThreadLocal<?> k, Object v) {
         super(k);
        value = v; //强引用，不会被回收
     }
}

Entry 的 key 是当前 ThreadLocal，value 值是我们要设置的数据。

WeakReference 表示的是弱引用，当 JVM 进行 GC 时，一旦发现了只具有弱引用的对象，不管当前内存空间是否足够，都会回收它的内存。但是 value 是强引用，它不会被回收掉。

ThreadLocal 使用建议：使用完毕后注意调用清理方法。

4.2 用的 JVM 调优的参数都有哪些？ ​

对于 JVM 调优，主要就是调整年轻代、年老大、元空间的内存空间大小及使用的垃圾回收器类型。

https://www.oracle.com/java/technologies/javase/vmoptions-jsp.html

1）设置堆的初始大小和最大大小，为了防止垃圾收集器在初始大小、最大大小之间收缩堆而产生额外的时间，通常把最大、初始大小设置为相同的值。

-Xms：设置堆的初始化大小

-Xmx：设置堆的最大大小

2）设置年轻代中 Eden 区和两个 Survivor 区的大小比例。该值如果不设置，则默认比例为 8:1:1。Java 官方通过增大 Eden 区的大小，来减少 YGC 发生的次数，但有时我们发现，虽然次数减少了，但 Eden 区满的时候，由于占用的空间较大，导致释放缓慢，此时 STW 的时间较长，因此需要按照程序情况去调优。

-XXSurvivorRatio=3，表示年轻代中的分配比率：survivor:eden = 2:3

3）年轻代和老年代默认比例为 1:2。可以通过调整二者空间大小比率来设置两者的大小。

-XX:newSize   设置年轻代的初始大小
-XX:MaxNewSize   设置年轻代的最大大小，  初始大小和最大大小两个值通常相同

4）线程堆栈的设置：每个线程默认会开启 1M 的堆栈，用于存放栈帧、调用参数、局部变量等，但一般 256K 就够用。通常减少每个线程的堆栈，可以产生更多的线程，但这实际上还受限于操作系统。

-Xss   对每个线程 stack 大小的调整,-Xss128k

5）一般来说，当 survivor 区不够大或者占用量达到 50%，就会把一些对象放到老年区。通过设置合理的 eden 区，survivor 区及使用率，可以将年轻对象保存在年轻代，从而避免 full GC，使用 -Xmn 设置年轻代的大小

6）系统 CPU 持续飙高的话，首先先排查代码问题，如果代码没问题，则咨询运维或者云服务器供应商，通常服务器重启或者服务器迁移即可解决。

7）对于占用内存比较多的大对象，一般会选择在老年代分配内存。如果在年轻代给大对象分配内存，年轻代内存不够了，就要在 eden 区移动大量对象到老年代，然后这些移动的对象可能很快消亡，因此导致 full GC。通过设置参数：-XX:PetenureSizeThreshold=1000000，单位为 B，标明对象大小超过 1M 时，在老年代（tenured）分配内存空间。

8）一般情况下，年轻对象放在 eden 区，当第一次 GC 后，如果对象还存活，放到 survivor 区，此后，每 GC 一次，年龄增加 1，当对象的年龄达到阈值，就被放到 tenured 老年区。这个阈值可以同构 -XX:MaxTenuringThreshold 设置。如果想让对象留在年轻代，可以设置比较大的阈值。

（1）-XX:+UseParallelGC:年轻代使用并行垃圾回收收集器。这是一个关注吞吐量的收集器，可以尽可能的减少垃圾回收时间。

（2）-XX:+UseParallelOldGC:设置老年代使用并行垃圾回收收集器。

9）尝试使用大的内存分页：使用大的内存分页增加 CPU 的内存寻址能力，从而系统的性能。

-XX:+LargePageSizeInBytes 设置内存页的大小

10）使用非占用的垃圾收集器。

-XX:+UseConcMarkSweepGC老年代使用 CMS 收集器降低停顿。

JDK 自带，功能更强 启动：bin/jvisualvm.exe 能力：实时监控内存、线程、CPU；加载 dump 堆快照；查看对象、查看 GC；可以安装插件。

线上 dump 下载到本地，用 VisualVM 或者 MAT 分析。

4.4 Java 内存泄漏/内存溢出排查思路 ​

区分： StackOverflowError：栈深度超过栈最大容量（递归太深） OOM：内存不足；分：堆 OOM、元空间 Metaspace OOM、创建线程时栈内存不足 OOM

排查步骤：

  1. 优先配置 OOM 自动 dump（推荐） 程序 OOM 崩溃时自动导出堆快照，避免程序挂了 jmap 抓不到：
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/home/app/dumps/heap.hprof

如果程序还活着，也可以手动 jmap -dump:format=b,file=heap.hprof pid

  1. 下载 dump 文件，使用 MAT / VisualVM 加载分析 Linux 服务器生成的 hprof，下载到本地，VisualVM：文件 → 装入，选中 dump 文件

  2. 重点查看：

  • 大对象、实例数量异常多的类
  • 谁持有这些对象引用，找到 GC Roots，定位泄漏点（集合没有清理、静态集合、ThreadLocal 未 remove 等）
  1. 定位代码位置，修改代码验证

常见内存泄漏场景：静态集合、未关闭流、ThreadLocal 不 remove、监听器/回调未移除、内部类长生命周期持有外部引用

4.5 CPU 飙高排查思路 ​

场景：服务器 Java 进程 CPU 占用很高

  1. top 命令，找到 CPU 高的进程 pid
shell
top
  1. 查看该进程下所有线程 CPU 占用（十进制 tid）
shell
ps H -eo pid,tid,%cpu | grep pid

pid：进程 ID；tid：线程 ID；%cpu：线程 CPU 使用率

  1. 把占用 CPU 最高的十进制 tid，转为十六进制（jstack 里面线程栈是 16 进制）
shell
printf "%x\n tid值"
  1. 导出该进程线程栈
shell
jstack pid
  1. 在 jstack 输出里搜索十六进制 tid，找到对应线程栈，定位代码：
  • 如果是 RUNNABLE：大概率死循环、复杂计算、大量序列化
  • 如果频繁锁竞争：看 BLOCKED，死锁

✅ 一句话背流程：top 找进程 → ps 找高 CPU 线程 tid → 转 16 进制 → jstack 打印栈 → 搜索 tid 定位代码
