一、认知与定位篇 ​

1.1 为什么需要消息队列：解耦、异步、削峰的真实边界 ​

概念

消息队列（Message Queue）是一个独立于业务服务之外的中间存储。生产者把消息写进去就返回，消费者按自己的节奏取出来处理。它把「调用」变成了「投递」，把「同步依赖」变成了「异步契约」。

没有 MQ 的下单流程 ​

text
用户点击「提交订单」
      |
      v
+---------------------------+
| OrderService.createOrder  |
|  1. 写订单表      50ms    |
|  2. 调用短信服务  200ms   |  <-- 短信服务挂了，下单也失败
|  3. 调用积分服务  150ms   |  <-- 积分服务慢，下单跟着慢
|  4. 调用物流服务  300ms   |
+---------------------------+
      |
      v
返回成功（总耗时 700ms，可用性 = 四个服务可用性相乘）

四个服务各自可用性 99.9%，串起来就是 0.999^4 ≈ 99.6%，一年多出约 14 小时不可用。

引入 MQ 之后 ​

text
用户点击「提交订单」
      |
      v
+---------------------------+
| OrderService.createOrder  |
|  1. 写订单表      50ms    |
|  2. 发一条 MQ 消息 5ms    |
+---------------------------+
      |
      v
返回成功（总耗时 55ms）

        RabbitMQ
           |
   +-------+-------+-------+
   v       v       v
 短信消费  积分消费  物流消费   <-- 各自异步处理，挂了可重试

三大价值的真实边界 ​

价值它真正解决的问题它解决不了的问题
解耦上游不再需要知道下游有几个、是谁、在哪下游必须容忍延迟；强依赖返回值的调用不能用 MQ
异步把非核心链路移出主流程，缩短响应时间用户需要立即看到结果的场景不能异步
削峰流量洪峰先入队，消费端按能力平滑消费只能削瞬时峰；平均流量超过消费能力只会无限堆积

关于削峰最常见的误解

削峰不是「让系统能处理更多请求」，而是「把短时间的高并发摊平到更长时间」。

  • ✅ 适合：秒杀 10 秒内来 10 万请求，后台 5 分钟处理完
  • ❌ 不适合：日常每秒 5000 请求，消费端每秒只能处理 1000 —— 这叫容量不足，加 MQ 只会让堆积从「用户超时」变成「队列爆炸」

✅ / ❌ 什么场景该用 MQ ​

java
// ❌ 错误：需要同步拿到结果的调用，硬改成 MQ
// 前端点「查询余额」，结果塞进 MQ，前端只能轮询 —— 复杂度爆炸
rabbitTemplate.convertAndSend("balance.query", userId);
return "请稍后刷新"; // 用户体验灾难

// ❌ 错误：用 MQ 做强一致的转账
rabbitTemplate.convertAndSend("account.ex", "deduct", new Deduct(from, 100));
rabbitTemplate.convertAndSend("account.ex", "add", new Add(to, 100));
// 两条消息无事务关系，一条成功一条失败就是资金错账

// ✅ 正确：下单后的通知类、统计类、可补偿的副作用
@Transactional
public void createOrder(OrderDTO dto) {
    Order order = orderService.save(dto);           // 核心链路同步
    rabbitTemplate.convertAndSend("order.event.ex",
            "order.created", OrderEvent.of(order)); // 副作用异步
}

// ✅ 正确：削峰 —— 秒杀请求先入队，后台按库存能力扣减
@PostMapping("/seckill")
public Result seckill(Long skuId, Long userId) {
    rabbitTemplate.convertAndSend("seckill.ex", "seckill",
            new SeckillMsg(skuId, userId));
    return Result.ok("排队中，请稍后查看结果"); // 用户预期已对齐
}

判断口诀

上游要不要等结果？要等就别用 MQ。

下游失败能不能重试补偿？不能就别用 MQ。

流量是「瞬时尖峰」还是「长期超载」？长期超载先扩容，不是加 MQ。

📌 单独澄清：「异步」和「解耦」不是同一件事。

  • 异步指的是时间维度：调用方不等结果立刻返回，用线程池也能做到。
  • 解耦指的是依赖维度：调用方代码里不再出现下游服务的名字。线程池做不到解耦，因为下游的类还在你的代码里。
  • 结论：线程池 = 异步但不解耦；MQ = 异步 + 解耦 + 跨进程持久化。

1.2 MQ 不是免费的：引入 MQ 要付出的三份代价 ​

很多团队把引入 MQ 当成「架构升级」的标志，但真正的工程判断是：先算清代价，再决定要不要付。

代价一：系统可用性下降 ​

text
加 MQ 前：  App ----> DB
加 MQ 后：  App ----> RabbitMQ ----> Consumer ----> DB
                        ^
                        |
                 新增的单点依赖

MQ 一挂，所有依赖它的链路全断。所以生产环境的 MQ 必须集群化，并且生产端必须准备「MQ 不可用时的降级方案」（见 5.5 本地消息表）。

代价二：系统复杂度上升 ​

原来不需要考虑的问题加了 MQ 之后必须考虑
消息会不会丢生产确认、持久化、消费确认，三处都要配
消息会不会重复消费端必须做幂等
消息顺序多消费者并发时顺序会乱
消息堆积需要监控队列深度 + 应急扩容方案
消息格式演进生产者改了字段，老消费者会反序列化失败

代价三：一致性从「强」降级为「最终」 ​

java
// ❌ 典型错误：以为加了 @Transactional 就有事务保证
@Transactional
public void createOrder(OrderDTO dto) {
    orderMapper.insert(order);                              // 本地事务
    rabbitTemplate.convertAndSend("order.ex", "created", m); // 不在事务内！
    int i = 1 / 0;  // 这里抛异常 -> 订单回滚了，但消息已经发出去了
}

// ✅ 正确做法一：把发消息推迟到事务提交之后
@Transactional
public void createOrder(OrderDTO dto) {
    orderMapper.insert(order);
    TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                rabbitTemplate.convertAndSend("order.ex", "created", m);
            }
        });
}

// ✅ 正确做法二：本地消息表 + 定时补偿（见 5.5，最可靠）
@Transactional
public void createOrder(OrderDTO dto) {
    orderMapper.insert(order);
    msgMapper.insert(new LocalMsg("order.ex", "created", json, "NEW"));
    // 同一个事务，要么都成功要么都回滚；后台任务扫 NEW 状态的消息去投递
}

事务消息的真相

RabbitMQ 自带的 channel.txSelect() / txCommit() 是 AMQP 信道事务，只保证「多条消息要么都进 Broker 要么都不进」，它和你的数据库事务没有任何关系，而且性能极差（吞吐下降一个数量级）。

想要「数据库操作 + 发消息」原子化，RabbitMQ 没有 RocketMQ 那样的半消息机制，只能用本地消息表自己实现。

📌 单独澄清：「AMQP 事务」「Publisher Confirm」「本地消息表」解决的是三个不同问题。

机制解决的问题不解决的问题
AMQP 事务 txSelect多条消息进 Broker 的原子性与 DB 事务的一致性；性能差，生产基本不用
Publisher Confirm单条消息是否真的到了 BrokerDB 回滚了但消息已发出的问题
本地消息表DB 操作与消息投递的最终一致消费端的重复消费（仍需幂等）

判断口诀

MQ 带来的是「吞吐」和「解耦」，拿走的是「实时性」和「强一致」。

换不换，看业务能不能接受「最终一致 + 可能重复」。

1.3 RabbitMQ / Kafka / RocketMQ 选型对照 ​

概念

三者都叫「消息队列」，但设计目标完全不同：RabbitMQ 是消息路由器，Kafka 是分布式日志，RocketMQ 是面向业务的消息平台。选型选错，后面每一天都在为架构不匹配付出代价。

维度RabbitMQKafkaRocketMQ
开发语言ErlangScala / JavaJava
协议AMQP 0-9-1（标准协议）自定义 TCP 协议自定义协议
核心抽象Exchange + Queue + BindingTopic + Partition + OffsetTopic + Queue + Tag
单机吞吐万级（1~5 万 TPS）百万级十万级
消息延迟微秒级（最低）毫秒级毫秒级
路由能力极强（四种交换机 + 通配符）弱（只能按 Topic/Partition）中（Topic + Tag 过滤）
延迟消息插件 / TTL+DLX（需自建）不支持（需自己实现）原生支持（18 个固定级别）
事务消息无（只有信道事务）有（流处理场景）原生半消息事务
消息回溯不支持（消费即删）支持（按 offset 任意重放）支持（按时间戳）
消息堆积能力较弱（堆积影响性能）极强（磁盘顺序写）强
运维难度低（控制台好用）中高（需管 ZK/KRaft）中

用一句话区分三者 ​

text
RabbitMQ：我要把这条消息，按复杂规则，精准送到某几个消费者手上
          -> 业务解耦、任务分发、延迟取消、路由规则多变的场景

Kafka：   我要把海量数据流，顺序持久化，让多个下游各自按进度消费
          -> 日志采集、埋点、大数据管道、流式计算

RocketMQ：我要在电商/金融业务里，用事务消息和定时消息保证一致性
          -> 订单、交易、分布式事务，阿里系技术栈

✅ / ❌ 选型实例 ​

text
✅ 用 RabbitMQ：
   - 下单后要同时通知短信、积分、物流，且规则经常变（Topic 交换机一改绑定就行）
   - 订单 30 分钟未支付自动取消（TTL + 死信 / 延迟插件）
   - 日均消息量百万级以内，但要求路由灵活、延迟极低

❌ 不要用 RabbitMQ：
   - 每天 TB 级的用户行为埋点日志（吞吐不够，堆积会拖垮 Broker）
   - 需要把上周的消息重新消费一遍做数据修复（RabbitMQ 消费完就删了）
   - 需要「扣库存 + 发消息」严格原子（没有事务消息，要自己做本地消息表）

RabbitMQ 的最大短板：不擅长堆积

RabbitMQ 的队列设计是「消息尽量在内存中流转」。一旦堆积到几百万条，内存压力会触发内存告警 -> 阻塞生产者（flow control），整个集群性能断崖下跌。

Kafka 则是把消息顺序写磁盘，堆积 1 亿条和堆积 0 条的写入性能几乎一样。

所以 RabbitMQ 的队列应该是「流动的水管」，而不是「蓄水的池子」。

判断口诀

要路由灵活、延迟低、量不大 → RabbitMQ。

要吞吐高、能回溯、做数据管道 → Kafka。

要事务消息、定时消息、电商交易 → RocketMQ。

📌 单独澄清：「消息堆积能力」和「消息持久化」不是一回事。

  • 持久化：Broker 重启后消息还在不在。RabbitMQ 配了 durable 就有。
  • 堆积能力：队列里积压上千万条消息时，系统还能不能正常工作。RabbitMQ 即使持久化了，堆积仍会严重影响性能，因为它的索引结构和内存模型不是为海量堆积设计的。

1.4 AMQP 协议模型：一条消息的完整旅程 ​

概念

AMQP（Advanced Message Queuing Protocol）是一个开放的应用层协议，RabbitMQ 是它最标准的实现。AMQP 最核心的设计是：生产者永远不直接把消息发给队列，而是发给交换机（Exchange），由交换机根据规则路由到队列。 这一层间接，就是 RabbitMQ 路由能力强大的全部来源。

完整模型全景图 ​

  |                  Virtual Host: /mall                       |
  |                                                            |
  |  Exchange (order.event.ex)  type = topic                   |
  |       |                                                    |
  |       |  Binding(bindingKey = order.created)               |
  |       +--------------------------> Queue: sms.queue        |
  |       |                                                    |
  |       |  Binding(bindingKey = order.#)                     |

一条消息的七个阶段 ​

阶段发生了什么可能丢消息的点
1. 建立 Connection客户端与 Broker 建立 TCP 连接网络不通直接报错
2. 创建 Channel在 TCP 上复用出逻辑信道——
3. 声明拓扑declare Exchange / Queue / Binding参数不一致会报 PRECONDITION_FAILED
4. publish消息带 routingKey 发给 Exchange网络抖动，需 Publisher Confirm
5. routeExchange 按类型匹配 Binding匹配不到队列，消息被直接丢弃，需 mandatory + Return
6. 入队存储消息写入 Queue（内存或磁盘）Broker 宕机，需三重持久化
7. deliver + ack推给消费者，消费者确认自动 ack 下消费者异常，消息已删

核心组件职责速查 ​

组件一句话职责常见误解
BrokerRabbitMQ 服务实例本身——
Virtual Host逻辑隔离单元，拥有独立的交换机、队列、权限以为是物理隔离，其实共享同一进程和内存
Connection一条 TCP 长连接以为每次发消息都要新建，其实应复用
Channel建立在 Connection 上的轻量逻辑信道以为线程安全，其实一个 Channel 不能被多线程共享
Exchange按类型和 Binding 规则路由消息以为交换机会存消息，其实交换机不存储任何消息
Queue真正存储消息的地方——
BindingExchange 与 Queue 的绑定关系，携带 bindingKey以为绑定是一对一，其实是多对多
MessageBody（字节数组）+ Properties（头信息）以为能直接发对象，其实必须序列化

为什么要有 Channel 这一层 ​

java
// ❌ 错误：每发一条消息建一个 Connection
for (int i = 0; i < 1000; i++) {
    Connection conn = factory.newConnection();  // TCP 三次握手 x 1000
    Channel channel = conn.createChannel();
    channel.basicPublish("", "queue", null, msg.getBytes());
    conn.close();
}
// 结果：TCP 连接耗尽，Broker 的文件句柄被打满

// ✅ 正确：一个 Connection 复用，多个 Channel 并发
Connection conn = factory.newConnection();      // 整个应用共享
for (int i = 0; i < 10; i++) {
    new Thread(() -> {
        Channel channel = conn.createChannel(); // 每个线程独占一个 Channel
        channel.basicPublish("", "queue", null, msg.getBytes());
    }).start();
}
// Spring Boot 中 CachingConnectionFactory 已经帮你做好了这件事

Channel 绝对不能跨线程共享

AMQP 协议在同一个 Channel 上是串行的。多线程共用一个 Channel 会导致帧交错、unexpected frame 错误、confirm 回调错乱。

Spring 的 RabbitTemplate 默认从连接工厂缓存中为每次操作取一个 Channel，所以它是线程安全的；但如果你直接用原生 API，必须做到「一线程一 Channel」。

判断口诀

Connection 是「电缆」，Channel 是「电缆里的一根芯线」。

电缆很贵要复用，芯线很便宜但不能两个人同时用。

📌 单独澄清：Exchange 不存消息，这句话有三个推论。

  • 推论一：消息到了交换机但没有任何队列匹配，会被静默丢弃（除非开启 mandatory）。
  • 推论二：应先让消费者声明好队列和绑定，再发消息；否则「发早了」的消息找不到队列就没了。
  • 推论三：管理控制台的 Exchange 页面永远看不到「消息数量」，只有 Queue 页面才有 Ready / Unacked 计数。

2.2 Broker / VirtualHost / Connection / Channel 的层级边界 ​

概念

这四个概念是一条从粗到细的嵌套链：一个 Broker 里有多个 VirtualHost，一个应用对一个 VirtualHost 建立若干 Connection，一个 Connection 上复用成百上千个 Channel。搞清楚谁包含谁，连接数、权限、隔离三类问题就都能自己判断。

text
Broker（一个 RabbitMQ 服务实例 / 集群）
  |
  +-- Virtual Host  "/"        <- 默认，建议别用于业务
  +-- Virtual Host  "/mall"    <- 电商业务：独立的 exchange/queue/权限
  |        |
  |        +-- Exchange / Queue / Binding / User 权限
  |
  +-- Virtual Host  "/log"     <- 日志业务，与 /mall 完全隔离

应用侧：
  Application
     |
     +-- Connection #1 (TCP, 指向某个 vhost)
     |        +-- Channel 1   <- 线程 A 独占
     |        +-- Channel 2   <- 线程 B 独占
     |        +-- Channel N
     |
     +-- Connection #2 (消费者专用，与生产者隔离)

四者关键差异 ​

维度BrokerVirtual HostConnectionChannel
本质服务进程逻辑命名空间TCP 长连接逻辑子通道
创建成本极高低（一条命令）高（三次握手 + 认证）极低

VirtualHost 的隔离是「逻辑」不是「物理」

两个 vhost 里可以有同名队列 order.queue，互不影响，权限也能分开配置 —— 这是逻辑隔离。

但它们共享同一个 Erlang 进程、同一份内存、同一块磁盘。/log 里堆积几百万条消息触发内存告警时，/mall 的生产者同样会被流控阻塞。

需要真正的故障隔离，必须用独立集群，而不是多开 vhost。

list_queues 输出的关键列怎么读 ​

列名含义异常信号
messages_ready等待投递的消息数持续上涨 = 消费能力不足
messages_unacknowledged已投递但未 ack 的消息数居高不下 = 消费者卡死或忘了 ack
messages上面两者之和队列总深度
consumers当前消费者数量等于 0 = 消费者全掉线，最常见事故
memory该队列占用的内存单队列吃掉大量内存需警惕

Ready 不涨但 Unacked 很高，是什么问题

这说明消息已经推给消费者了，但消费者迟迟不 ack。常见原因：

  • 消费逻辑里有慢 SQL、死循环或远程调用超时
  • 手动 ack 模式下代码漏写了 basicAck
  • prefetch 设得过大，消费者一次性抓了几千条

此时队列不会继续投递新消息（受 prefetch 限制），表现为「消息卡住不动了」。

管理控制台最该用的四个页面 ​

2.4 Exchange、Queue、Binding 的三种声明方式 ​

概念

RabbitMQ 的拓扑（交换机、队列、绑定）必须先声明后使用。声明是幂等的：同样的参数重复声明不报错，但参数不一致时会直接报错并关闭 Channel。这个特性既是便利，也是最大的坑源。

方式一：管理控制台手动创建 ​

适合学习和临时验证，不适合生产：没有版本管理，换个环境就要重建一遍，容易漏。

方式二：Spring 配置类声明（推荐） ​

java
@Configuration
public class RabbitTopologyConfig {

    public static final String ORDER_EXCHANGE = "order.event.ex";
    public static final String SMS_QUEUE      = "order.sms.queue";

    @Bean
    public TopicExchange orderExchange() {
        return ExchangeBuilder.topicExchange(ORDER_EXCHANGE)
                .durable(true)   // 持久化：Broker 重启后交换机还在
                .build();
    }

    @Bean
    public Queue smsQueue() {
        return QueueBuilder.durable(SMS_QUEUE)
                .withArgument("x-message-ttl", 600000)            // 消息 10 分钟过期
                .withArgument("x-dead-letter-exchange", "dlx.ex") // 死信交换机
                .withArgument("x-max-length", 100000)             // 队列最大长度
                .build();
    }

    @Bean
    public Binding smsBinding(Queue smsQueue, TopicExchange orderExchange) {
        return BindingBuilder.bind(smsQueue)
                .to(orderExchange)
                .with("order.created");   // bindingKey
    }
}

方式三：注解内联声明（最简洁） ​

java

public class SmsConsumer {

    @RabbitListener(bindings = @QueueBinding(
            value = @Queue(name = "order.sms.queue", durable = "true",
                    arguments = @Argument(name = "x-message-ttl",
                            value = "600000", type = "java.lang.Integer")),
            exchange = @Exchange(name = "order.event.ex", type = ExchangeTypes.TOPIC),
            key = "order.created"

    public void onOrderCreated(OrderEvent event) {
        smsService.send(event.getPhone(), "您的订单已创建");

}

三种方式对照 ​

方式优点缺点适用场景
控制台手建直观、零代码无法版本化，环境迁移易漏临时验证
配置类 Bean集中管理、可复用常量、支持复杂参数拓扑与消费逻辑分离在两个文件生产推荐
注解内联队列、绑定、消费逻辑写在一起，一目了然参数只能写字符串，复杂拓扑难维护简单队列、小项目

最高频报错：PRECONDITION_FAILED

text
Channel shutdown: channel error; protocol method:
#method<channel.close>(reply-code=406, reply-text=PRECONDITION_FAILED -
inequivalent arg 'x-message-ttl' for queue 'order.sms.queue' in vhost '/mall':
received '600000' but current is '300000')

原因：队列已经存在，但你这次声明的参数和已存在的不一样。RabbitMQ 不会帮你修改已有队列。

解决办法只有两条：

  • 把代码里的参数改回和线上一致
  • 或者删掉旧队列重建（会丢掉队列里的消息，生产环境需谨慎，先确认队列为空）

所以：队列参数一旦上线，就当作不可变；要改参数，就新建一个带版本号的队列名，如 order.sms.queue.v2。

✅ / ❌ 队列声明实践对照 ​

java
// ❌ 错误：用 new Queue("xx") 这种默认构造
new Queue("order.queue");
// 默认 durable=true, exclusive=false, autoDelete=false，看起来没问题
// 但你无法表达 TTL、死信、最大长度等参数，后续想加就会踩 PRECONDITION_FAILED

// ❌ 错误：生产队列用了 autoDelete 或 exclusive
new Queue("order.queue", true, true, true);
// exclusive=true：只对声明它的连接可见，连接断开就删除
// autoDelete=true：最后一个消费者断开后队列自动删除
// 结果：消费者重启的瞬间队列没了，期间的消息全部丢失

// ✅ 正确：一次性把可能用到的参数规划好
@Bean
public Queue orderQueue() {
    return QueueBuilder.durable("order.queue")
            .deadLetterExchange("order.dlx.ex")   // 预留死信出口
            .deadLetterRoutingKey("order.dead")
            .maxLength(500000)                    // 兜底，防止无限堆积
            .build();
}

判断口诀

声明是幂等的，但「参数不同」不叫幂等，叫冲突。

队列参数要在上线前想清楚，改参数等于建新队列。

📌 单独澄清：durable、exclusive、autoDelete 三个布尔值的区别。

参数含义生产环境取值
durableBroker 重启后队列定义是否保留true
exclusive是否只允许声明它的连接使用，连接关闭即删除false（临时回调队列才用 true）
autoDelete最后一个消费者解绑后是否自动删除false

注意：durable=true 只保证队列本身不丢，队列里的消息是否持久化由消息自己的 deliveryMode 决定（见 5.3）。

三、交换机与路由篇 ​

3.1 Direct 交换机：精确匹配 ​

概念

Direct 交换机的路由规则是字符串完全相等：消息的 routingKey 必须和绑定的 bindingKey 一模一样，才会被投递到对应队列。它是最简单、也是最容易预测的交换机类型。

text
                 Exchange: order.direct.ex (direct)
 publish(rk="create") ----+
                          |  bindingKey = "create"  -> order.create.queue  ✅
                          |  bindingKey = "pay"     -> order.pay.queue     ❌
                          |  bindingKey = "create"  -> log.queue           ✅ (同 key 可多绑)
                          +-------------------------------------------

配置与收发 ​

默认交换机：一个特殊的 Direct ​

java
// 交换机名传空字符串，这就是 RabbitMQ 内置的「默认交换机」(AMQP default)
rabbitTemplate.convertAndSend("", "order.create.queue", order);

默认交换机的隐藏规则

每个队列被创建时，RabbitMQ 都会自动把它绑定到默认交换机上，bindingKey 就是队列名本身。

所以 convertAndSend("", "order.create.queue", msg) 看起来像「直接发给队列」，本质仍是走了一次 Direct 路由。

它很方便，但不要在生产代码里用：一旦这么写，生产者就和队列名强耦合了，等于放弃了 MQ 最核心的解耦能力。

✅ / ❌ Direct 使用对照 ​

java
// ❌ 错误：routingKey 大小写或空格不一致
rabbitTemplate.convertAndSend("order.direct.ex", "Create", order);
// bindingKey 是 "create"，这里是 "Create" -> 完全不匹配，消息被静默丢弃

// ❌ 错误：想「一条消息同时给多个不同业务」，却用了多个 key 发多次
rabbitTemplate.convertAndSend("order.direct.ex", "sms", order);
rabbitTemplate.convertAndSend("order.direct.ex", "point", order);
// 发了两次，网络开销翻倍，而且无法保证原子性 -> 这种场景该用 Fanout 或 Topic

// ✅ 正确：一次发送，靠多个队列绑定同一个 key 实现一对多
// sms.queue 和 point.queue 都 bind 到 "order.created"
rabbitTemplate.convertAndSend("order.direct.ex", "order.created", order);

判断口诀

Direct = equals()。key 写错一个字符，消息就消失得无影无踪。

📌 单独澄清：Direct 也能实现「一对多」。

很多人以为 Direct 是一对一、Fanout 才是一对多，这是错的。

Direct 的一对多方式是：多个队列用同一个 bindingKey 绑定到同一个交换机，消息会被复制投递到每个队列。它和 Fanout 的真正区别是 Fanout 「无条件给所有队列」，Direct 「只给 key 相等的队列」。

3.2 Fanout 交换机：广播 ​

概念

Fanout 交换机完全忽略 routingKey，把收到的每条消息复制投递到所有与它绑定的队列。它是四种交换机里路由最快的，因为根本不需要做任何匹配计算。

text
                     Exchange: order.fanout.ex (fanout)
 publish(rk="随便写") ----+---> sms.queue        ✅
                          +---> point.queue      ✅
                          +---> logistics.queue  ✅
                          +---> bigdata.queue    ✅
          routingKey 被完全忽略，所有绑定队列都收到一份副本

配置示例 ​

java
@Configuration
public class FanoutConfig {

    @Bean
    public FanoutExchange orderFanoutExchange() {
        return ExchangeBuilder.fanoutExchange("order.fanout.ex").durable(true).build();
    }

    @Bean
    public Queue smsQueue()  { return QueueBuilder.durable("order.sms.queue").build(); }

    @Bean
    public Queue pointQueue(){ return QueueBuilder.durable("order.point.queue").build(); }

    // Fanout 绑定不需要 with(key)
    @Bean
    public Binding smsFanoutBinding() {
        return BindingBuilder.bind(smsQueue()).to(orderFanoutExchange());
    }

    @Bean
    public Binding pointFanoutBinding() {
        return BindingBuilder.bind(pointQueue()).to(orderFanoutExchange());
    }
}

Fanout 的典型使用场景 ​

场景为什么适合 Fanout
订单创建后的多方通知短信、积分、风控、大数据都要同一份完整事件
配置变更广播所有应用实例都要刷新本地缓存
缓存失效通知集群中每个节点都要清掉自己的本地缓存

Fanout 做「集群内广播」的正确姿势

配置刷新这类场景，需要每个实例各自收到一份，而不是集群里只有一台收到。

如果多个实例共用一个队列，消息会被轮询分给其中一台 —— 这是错的。正确做法是每个实例声明自己独立的临时队列：

java
@RabbitListener(bindings = @QueueBinding(
        value = @Queue(autoDelete = "true", exclusive = "true"), // 匿名临时队列
        exchange = @Exchange(name = "config.refresh.ex", type = ExchangeTypes.FANOUT)
))
public void onConfigRefresh(String payload) {
    localCache.reload();
}

这里的 exclusive + autoDelete 是极少数该用临时队列的正当场景：实例下线队列就该消失，消息也不需要保留。

✅ / ❌ Fanout 使用对照 ​

java
// ❌ 错误：以为 Fanout 也能按 key 过滤
rabbitTemplate.convertAndSend("order.fanout.ex", "only.sms", event);
// 幻想只有 sms 队列收到，实际上所有绑定队列都收到了
// 后果：积分服务也加了一次积分，数据错乱

// ❌ 错误：所有业务共用一个 Fanout，靠消费端 if 判断过滤
@RabbitListener(queues = "biz.queue")
public void handle(Event e) {
    if (!"ORDER_CREATED".equals(e.getType())) return;  // 白白消费 + 丢弃
    ...
}
// 后果：网络、序列化、消费线程全部浪费；该用 Topic 在 Broker 侧过滤

// ✅ 正确：所有下游确实都需要这条消息时，才用 Fanout

判断口诀

Fanout = 群发，不认 key，只认绑定。

要过滤就别用 Fanout，过滤这件事应该交给 Broker，而不是消费端的 if。

📌 单独澄清：「多个队列」和「一个队列多个消费者」是完全不同的两种模型。

模型结构结果适用场景
发布订阅一个交换机 → 多个队列，各队列一个消费者每个队列都收到完整副本一个事件通知多个不同业务
工作队列一个队列 → 多个消费者实例消息在消费者间轮询分配，每条只被处理一次同一业务横向扩容

同一个服务部署 3 个实例，它们共用一个队列，属于第二种 —— 一条消息只会被其中一个实例处理，这正是我们想要的。

3.3 Topic 交换机：通配符匹配 ​

概念

Topic 交换机把 routingKey 当作用点号分隔的单词序列（如 order.cn.vip.created），绑定时可以使用两个通配符：

  • *（星号）匹配恰好一个单词
  • #（井号）匹配零个或多个单词

它是功能最强的交换机，Direct 和 Fanout 的能力它都能覆盖。

text
            Exchange: order.topic.ex (topic)

bindingKey          匹配 "order.cn.created"   匹配 "order.created"   匹配 "order.cn.vip.created"
--------------------------------------------------------------------------------------------
order.#                     ✅                        ✅                      ✅
order.*                     ❌（两个单词）             ✅                      ❌
order.*.created             ✅                        ❌                      ❌
order.#.created             ✅                        ✅                   ✅
#                           ✅                        ✅                      ✅  (等价于 Fanout)
*.cn.#                      ✅                        ❌                      ✅

实战：按「业务 + 地区 + 用户等级」路由 ​

java
@Configuration
public class TopicConfig {

    @Bean
    public TopicExchange orderTopicExchange() {
        return ExchangeBuilder.topicExchange("order.topic.ex").durable(true).build();
    }

    // 所有订单事件都要进大数据
    @Bean
    public Binding bigdataBinding() {
        return BindingBuilder.bind(QueueBuilder.durable("order.bigdata.queue").build())
                .to(orderTopicExchange()).with("order.#");
    }

    // 只关心「已创建」事件，不分地区
    @Bean
    public Binding smsBinding() {
        return BindingBuilder.bind(QueueBuilder.durable("order.sms.queue").build())
                .to(orderTopicExchange()).with("order.*.created");
    }

    // VIP 专属客服队列：任意地区的 vip 订单
    @Bean
    public Binding vipBinding() {
        return BindingBuilder.bind(QueueBuilder.durable("order.vip.queue").build())
                .to(orderTopicExchange()).with("order.*.vip.#");
    }
}
java
@Service
@RequiredArgsConstructor
public class OrderTopicPublisher {

    private final RabbitTemplate rabbitTemplate;

    /**
     * routingKey 的设计是 Topic 用好的关键：
     * 格式约定为 业务.地区.等级.动作，从粗到细、从稳定到易变
     */
    public void publish(Order order, String action) {
        String routingKey = String.join(".",
                "order",
                order.getRegion(),      // cn / us
                order.getUserLevel(),   // normal / vip
                action);                // created / paid / cancelled
        rabbitTemplate.convertAndSend("order.topic.ex", routingKey, order);
    }
}

routingKey 命名规范建议 ​

text
推荐：  <领域>.<子域>.<动作>        order.payment.succeeded
       <领域>.<地区>.<动作>        order.cn.created
       <系统>.<服务>.<级别>        log.gateway.error

原则：
  1. 从左到右，粒度由粗到细、由稳定到易变
  2. 全小写 + 点号分隔，不要用下划线或驼峰
  3. 单词数量尽量固定，便于使用 * 精确匹配
  4. 动作用过去式（created / paid），强调「已发生的事实」

* 和 # 的两个高频误解

误解一：* 能匹配空单词。order.* 匹配 order.created，但不匹配 order（单词数不够）。想包含自身，用 order.#。

误解二：# 只能放在末尾。# 可以在任何位置，*.cn.#、order.#.created 都是合法的。但 # 放中间时匹配范围极大，容易误收消息。

✅ / ❌ Topic 使用对照 ​

java
// ❌ 错误：routingKey 用下划线或驼峰
rabbitTemplate.convertAndSend("order.topic.ex", "order_created", event);
// 整个字符串被当成一个单词，"order.*" 和 "order.#" 全都匹配不上

// ❌ 错误：单词数量忽多忽少
publish("order.created");            // 2 个单词
publish("order.cn.vip.created");     // 4 个单词
// bindingKey 很难写，要么漏消息要么多收消息

// ❌ 错误：所有队列都绑 "#" 图省事
BindingBuilder.bind(smsQueue).to(topicEx).with("#");
// 等于把 Topic 退化成 Fanout，还白白付出了匹配开销

// ✅ 正确：固定 4 段式结构，bindingKey 精确表达意图
publish("order.cn.vip.created");
BindingBuilder.bind(vipQueue).to(topicEx).with("order.*.vip.*");

判断口诀

* 是「一个单词」，# 是「任意多个单词（含 0 个）」。

routingKey 的结构在上线前定好，它是消息系统的「接口契约」，改一次全链路都要动。

📌 单独澄清：Topic 的性能真的比 Direct 差吗？

理论上 Topic 需要做通配符树匹配，确实比 Direct 的哈希查找慢。但 RabbitMQ 内部用 Trie 树实现 Topic 匹配，实测在绑定数量不超过几千时，两者差距在同一数量级内，远不是系统瓶颈。

真正的瓶颈在于：持久化刷盘、网络带宽、消费者处理速度。

所以选交换机应该按「表达能力」而不是「性能」来选。 实际项目中，绝大多数场景直接用 Topic，它能覆盖 Direct 和 Fanout，还为未来的路由规则变化留了余地。

3.4 Headers 交换机与四种交换机终极对照 ​

概念

Headers 交换机（BuiltinExchangeType.HEADERS）完全忽略 routingKey，改用消息头 headers 里的键值对，与 Binding 声明时携带的参数做匹配。

匹配规则由绑定参数 x-match 决定：

  • x-match = all：Binding 上声明的每一个键值对都必须在消息头中出现且值相等（AND 语义）
  • x-match = any：只要命中任意一个键值对即可（OR 语义）

代码示例 ​

java
@Configuration
public class HeadersConfig {

    @Bean
    public HeadersExchange orderHeadersEx() {
        return ExchangeBuilder.headersExchange("order.headers.ex").durable(true).build();
    }

    @Bean
    public Queue orderVipQueue() {
        return QueueBuilder.durable("order.vip.queue").build();
    }

    /** x-match=all：必须同时满足 level=vip 且 region=cn */
    @Bean
    public Binding vipAllBinding() {
        return BindingBuilder.bind(orderVipQueue())
                .to(orderHeadersEx())
                .whereAll(Map.of("level", "vip", "region", "cn"))
                .match();   // match() = all
    }

    /** x-match=any：level=vip 或 region=cn 命中一个即可 */
    @Bean
    public Binding vipAnyBinding() {
        return BindingBuilder.bind(orderVipQueue())
                .to(orderHeadersEx())
                .whereAny(Map.of("level", "vip", "region", "cn"))
                .match();
    }
}
java
@Service
@RequiredArgsConstructor
public class HeadersSender {

    private final RabbitTemplate rabbitTemplate;

    public void send(OrderDTO order) {
        MessageProperties props = new MessageProperties();
        props.setHeader("level", "vip");
        props.setHeader("region", "cn");
        props.setContentType(MessageProperties.CONTENT_TYPE_JSON);

        Message msg = new Message(JSON.toJSONBytes(order), props);
        // 第二个参数 routingKey 必须传，但 Headers 交换机根本不看它
        rabbitTemplate.send("order.headers.ex", "", msg);
    }
}

典型场景日志等级、固定业务码广播通知、缓存刷新多维度事件路由跨语言元数据路由（极少用）

📌 单独澄清：为什么 Headers 几乎没人用？

三个原因叠加，让它在工程上几乎被淘汰：

  1. 性能最差：Direct 用 routingKey 做哈希查找是 O(1)，Headers 必须遍历该交换机下所有 Binding，逐个比对 Map，是 O(n×m)。
  2. 可读性差：控制台上看 Binding 只能看到一串参数，排障时无法像 order.cn.vip.created 那样一眼看懂业务含义。
  3. Topic 能覆盖它 95% 的场景：把"多维度"编码进 routingKey 的分段里（order.cn.vip.created），就等价于多个 header 的 AND 匹配，而且更快更直观。

唯一还算合理的场景是：消息头由上游系统/网关自动注入（如链路追踪的 tenant、租户 ID），业务方无权改 routingKey，才退而求其次用 Headers。

判断口诀

routingKey 固定几个值 → Direct。

所有订阅者都要收 → Fanout。

路由条件会随业务增长 → Topic（默认选它）。

路由依据不在 routingKey 而在消息头 → 才考虑 Headers。

3.5 RoutingKey 与 BindingKey：最容易混淆的一对概念 ​

概念

这两个词长得像，但属于完全不同的生命周期，由完全不同的角色设置：

  • BindingKey：绑定键。在声明拓扑时由运维/配置类设置，描述"这个队列想收哪一类消息"，是规则/模式，可以带 * # 通配符。
  • RoutingKey：路由键。在发送每一条消息时由生产者设置，描述"这条消息是什么",是具体值，永远不能带通配符。

交换机做的事就一句话：拿消息的 RoutingKey，去和自己身上所有 Binding 的 BindingKey 做匹配。

一张图看清两者的位置 ​

text

      |                           |                            |
      |  发送消息                  |                            |
      |  RoutingKey =             |   Binding 1                |
      |  "order.cn.vip.created"   |   BindingKey="order.#"  ---+--> order.bigdata.queue
      |-------------------------->|                            |
      |      (具体值，无通配符)      |   Binding 2                |
      |                           |   BindingKey="order.*.vip.*"--> order.vip.queue
      |                           |                            |
      |                           |   Binding 3                |
      |                           |   BindingKey="order.cn.normal.created" --> （不匹配，丢弃）
      |                           |                            |
                                  ↑                            ↑
                           运行期每条消息都变          声明期设置一次，长期不变

存放位置消息属性中，随消息传输Broker 的 Binding 元数据中
变更频率每条消息都可能不同几乎不变，变更需重新声明
在 Direct 中具体值也是具体值（二者需完全相等）

📌 单独澄清：Fanout 交换机下这两个还有意义吗？

没有。Fanout 既不看 RoutingKey 也不看 BindingKey，发送时第二个参数传 "" 即可，绑定时也不需要 .with(...)。但注意：API 签名仍然要求你传 routingKey 参数，这是协议层的统一格式，不是逻辑需要——很多人在这里误以为"传了就会生效"，于是在 Fanout 上写了一堆 routingKey，排障时反而误导自己。

判断口诀

带通配符的一定是 BindingKey，声明期才出现。

发消息时传的一定是 RoutingKey，必须是具体值。

匹配永远是"RoutingKey 去撞 BindingKey"，方向不可逆。

3.6 官方五种工作模式与交换机的真实映射 ​

概念

RabbitMQ 官方教程列了"五种（含 RPC 共六种）工作模式"，很多人把它们背成了六种独立技术。

真相是：它们不是六种技术，而是"交换机类型 × 消费者数量 × 是否需要回复"的六种排列组合。底层只有一套 AMQP 模型，没有任何一种模式是特殊实现。

六种模式的真实构成 ​

模式交换机类型队列数消费者数本质
1. 简单队列 Simple默认交换机（""）11Direct 的退化形态
2. 工作队列 Work Queue默认交换机（""）1N多消费者抢同一个队列
3. 发布订阅 Pub/SubFanoutN每队列各 1+广播
4. 路由 RoutingDirectN每队列各 1+精确键匹配
5. 主题 TopicTopicN每队列各 1+通配符匹配
6. RPC默认交换机 + 回调队列21+请求/响应，靠 replyTo + correlationId

📌 单独澄清：模式 1、2 用的"默认交换机"是什么？

每个 vhost 都自带一个名字为空字符串 "" 的 Direct 交换机，叫 default exchange。它有一条隐藏规则：vhost 下每个队列都自动以"队列名"为 BindingKey 绑定到它上面。

所以 rabbitTemplate.convertAndSend("order.sms.queue", msg)（只传两个参数）本质是：发到默认交换机，routingKey = 队列名，于是直达该队列。这就是"简单队列模式看起来没有交换机"的原因——不是没有，是你没看见。

Work Queue：轮询分发 vs 公平分发 ​

这是六种模式里唯一有"真知识点"的地方。

yaml
# 不配置 prefetch 时，Broker 把消息平均轮流发给每个消费者
# 后果：消费者 A 处理慢（5s/条），消费者 B 处理快（0.1s/条）
#      Broker 仍 1:1 轮流发 → A 堆积一大串，B 空转摸鱼
spring:
  rabbitmq:
    listener:
      simple:
        prefetch: 0 # 0 表示不限制，等价于无脑轮询
yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: manual
        prefetch: 1 # 每个消费者手里最多 1 条未 ack 的消息
        # 处理完 ack 后才会拿下一条 → 快的消费者自然拿得多

注意

prefetch: 1 只有在 手动 ack 或 auto ack 之后才生效的语义下才有"能者多劳"效果。如果用 acknowledge-mode: none（自动确认且不等待），Broker 发出去就认为完成，prefetch 形同虚设，又退化成轮询。

prefetch 的取值不是越小越好，1 会带来频繁的网络往返，吞吐下降明显。调优方法见 8.3 Prefetch 调优。

为什么说"记模式不如记交换机" ​

  • 面试官问"RabbitMQ 有几种工作模式"，答六种并说清它们只是交换机组合，比死背更能加分；
  • 实际写代码时，你选择的从来不是"模式"，而是交换机类型和消费者数量；
  • 官方教程把 Pub/Sub、Routing、Topic 分成三节，只是为了循序渐进讲解 Fanout、Direct、Topic 三种交换机。

判断口诀

没写交换机名 → 走的是默认交换机，routingKey 就是队列名。

一个队列多个消费者 → Work Queue，必须考虑 prefetch。

多个队列各收一份 → 看交换机类型决定是 Fanout / Direct / Topic。

需要同步拿返回值 → RPC 模式，但优先考虑用 HTTP/RPC 框架替代。

📌 单独澄清：default-requeue-rejected: false 为什么是生产必配？

它的默认值是 true，含义是"消费抛异常时把消息重新放回队列头部"。听起来很合理，实际是线上事故高发点：如果异常是由消息内容本身引起的（比如 JSON 格式错误），重回队列后会被立刻重新消费、再次抛异常、再次重回……形成无限死循环，CPU 打满、日志刷爆。

正确做法是设为 false，让失败消息进入死信队列（见 6.1）人工介入，而不是在队列里反复打转。

判断口诀

5672 是程序连的，15672 是人看的，配错了连不上还查不出。

mandatory: true 没开，Return 回调写了也白写。

default-requeue-rejected 不改成 false，线上迟早刷爆日志。

4.2 用配置类声明拓扑：让队列随应用自动创建 ​

概念

在 Spring Boot 中声明交换机、队列、绑定，推荐用 @Bean 配置类。RabbitAdmin 会在应用启动时扫描容器里所有 Exchange、Queue、Binding 类型的 Bean，自动在 Broker 上执行 declare。

这带来一个关键能力：拓扑随代码走。新环境只要启动应用，队列就自动建好，不需要运维手动点控制台。

完整示例：订单业务拓扑 ​

java
@Configuration
public class OrderRabbitConfig {

    public static final String ORDER_TOPIC_EX = "order.topic.ex";
    public static final String ORDER_SMS_QUEUE = "order.sms.queue";
    public static final String ORDER_POINT_QUEUE = "order.point.queue";

    /** 交换机：durable=true 持久化，autoDelete=false 不自动删除 */
    @Bean
    public TopicExchange orderTopicEx() {
        return ExchangeBuilder.topicExchange(ORDER_TOPIC_EX)
                .durable(true)
                .build();
    }

    /** 队列：绑定死信交换机，为第六篇做准备 */
    @Bean
    public Queue orderSmsQueue() {
        return QueueBuilder.durable(ORDER_SMS_QUEUE)
                .deadLetterExchange("dlx.ex")
                .deadLetterRoutingKey("dlx.order.sms")
                .build();
    }

    @Bean
    public Queue orderPointQueue() {
        return QueueBuilder.durable(ORDER_POINT_QUEUE).build();
    }

    @Bean
    public Binding smsBinding() {
        return BindingBuilder.bind(orderSmsQueue())
                .to(orderTopicEx())
                .with("order.*.*.created");
    }

    @Bean
    public Binding pointBinding() {
        return BindingBuilder.bind(orderPointQueue())
                .to(orderTopicEx())
                .with("order.#");
    }
}

三种声明方式对照（承接 2.4） ​

方式适用阶段优点缺点
控制台手动创建本地调试、临时验证直观、改参数快无版本管理，换环境要重做
@Bean 配置类生产推荐随代码进 Git，自动同步参数变更需重启应用
@RabbitListener 上的 @QueueBinding小型项目、单消费者声明与消费写在一起拓扑分散在各处，不易全局审视

最容易踩的坑：参数不一致导致 PRECONDITION_FAILED

RabbitMQ 的 declare 操作是幂等但不可变更的：如果 Broker 上已存在同名队列，而你新声明的参数（durable、ttl、死信配置等）与现存的不一致，Broker 会直接报错：

text
Channel shutdown: channel error; protocol method: #method<channel.close>(
  reply-code=406, reply-text=PRECONDITION_FAILED -
  inequivalent arg 'x-message-ttl' for queue 'order.sms.queue' in vhost '/mall':
  received '60000' but current is none, class-id=50, method-id=10)

无解，必须二选一：

  1. 删除旧队列后重启应用（会丢失队列中未消费的消息，生产慎用）；
  2. 用新队列名（如 order.sms.queue.v2），新旧并行一段时间后下线旧队列（生产推荐）。

📌 单独澄清：队列必须先于消费者存在吗？

是的，但顺序由 Spring 自动保证。RabbitAdmin 的初始化优先级高于监听容器启动，所以配置类里声明的队列一定先被创建。

但有两个例外会出问题：

  • 队列不是由本应用声明的（比如由上游服务声明），而上游还没启动 → 消费者启动时报 NOT_FOUND - no queue，需开启 missing-queues-fatal: false 让它重试等待；
  • 用了 @RabbitListener(queues = "xxx") 但没有对应 Queue Bean → 同样是 NOT_FOUND。这时应改用 @QueueBinding 让监听注解自身去声明。

判断口诀

拓扑要进 Git、要跨环境 → 配置类 @Bean。

报 406 PRECONDITION_FAILED → 一定是参数和已存在的队列不一致，改名或删队列，没有第三条路。

报 404 NOT_FOUND → 队列根本没被任何人声明，检查声明方是否启动。

4.3 RabbitTemplate 发送消息的四种姿势 ​

概念

RabbitTemplate 是发送端唯一入口，它的方法看似很多，本质只有四类：

  1. convertAndSend：传 Java 对象，由消息转换器自动序列化——99% 的场景用这个；
  2. convertAndSend + MessagePostProcessor：在序列化之后、发送之前，插手修改消息属性（加 header、设 TTL、设 expiration）；
  3. send：自己构造 Message 对象（byte[] + MessageProperties），完全手动控制；
  4. convertSendAndReceive：同步等待消费者返回结果（RPC 模式），会阻塞当前线程。

四种姿势代码 ​

java
@Service
@RequiredArgsConstructor
public class OrderSender {

    private final RabbitTemplate rabbitTemplate;

    public void sendCreated(OrderDTO order) {
        // 参数：交换机、routingKey、消息体对象
        rabbitTemplate.convertAndSend(
                "order.topic.ex",
                "order.cn.vip.created",
                order);
    }
}
java
public void sendWithTtl(OrderDTO order) {
    rabbitTemplate.convertAndSend("order.topic.ex", "order.cn.vip.created", order,
            message -> {
                MessageProperties props = message.getMessageProperties();
                props.setExpiration("60000");                    // 单条消息 TTL，见 6.2
                props.setHeader("traceId", MDC.get("traceId"));  // 透传链路 ID
                props.setDeliveryMode(MessageDeliveryMode.PERSISTENT); // 持久化，见 5.3
                props.setMessageId(order.getOrderNo());          // 幂等用，见 7.2
                return message;
            });
}
java
public void sendRaw(OrderDTO order) {
    MessageProperties props = MessagePropertiesBuilder.newInstance()
            .setContentType(MessageProperties.CONTENT_TYPE_JSON)
            .setContentEncoding("UTF-8")
            .setHeader("source", "mall-order-service")
            .build();

    Message message = new Message(JSON.toJSONBytes(order), props);
    rabbitTemplate.send("order.topic.ex", "order.cn.vip.created", message);
}
java
public StockResult checkStock(Long skuId) {
    // 阻塞等待消费者回包，默认超时 5 秒
    Object result = rabbitTemplate.convertSendAndReceive(
            "stock.direct.ex", "stock.check", skuId);
    return (StockResult) result;   // 超时返回 null，必须判空
}

对照表 ​

姿势序列化可改消息属性是否阻塞使用占比
convertAndSend(ex, rk, obj)自动❌否约 70%
convertAndSend + MPP自动✅否约 25%
send(ex, rk, Message)手动✅否约 5%
convertSendAndReceive自动可配是近乎 0%

慎用 convertSendAndReceive

它把异步的 MQ 强行用成了同步 RPC，同时丢掉了 MQ 的三大价值（解耦、削峰、异步），还额外引入了超时、回调队列、线程阻塞三类问题。

需要同步拿返回值，就该用 OpenFeign / gRPC，而不是 MQ。 面试时能主动说出这一点，是很明显的加分项。

📌 单独澄清：convertAndSend 的"convert"到底转了什么？

转的是 Java 对象 → byte[] + contentType，由容器里的 MessageConverter 完成。

默认实现是 SimpleMessageConverter，它对 String、byte[]、Serializable 有特殊处理：普通 POJO 会走 JDK 原生序列化，产出一串二进制，控制台上看到的是乱码，跨语言也无法解析。

这就是为什么几乎所有项目都必须手动换成 JSON 转换器——详见 4.5 消息转换器与序列化坑。

判断口诀

只发对象 → convertAndSend 三参数版。

要加 header / TTL / messageId → 加 MessagePostProcessor。

要完全控制字节 → 用 send 自己构造 Message。

想拿返回值 → 先问自己："为什么不用 Feign？"

4.4 @RabbitListener 的参数绑定与多种写法 ​

概念

@RabbitListener 是消费端的核心注解。它的方法参数是按类型自动绑定的，你可以只声明自己关心的那几个，顺序也不限：

  • 业务对象（OrderDTO）：由消息转换器反序列化而来
  • Message：原始消息，可取 body 和全部属性
  • Channel：手动 ack / nack 时必须要
  • @Header(...)：取单个消息头
  • @Headers Map<String,Object>：取全部消息头
  • @Payload：显式标注哪个参数是消息体

三种常见写法 ​

java
@Component
@Slf4j
public class OrderSmsListener {

    @RabbitListener(queues = "order.sms.queue")
    public void onMessage(OrderDTO order) {
        log.info("发短信，订单号={}", order.getOrderNo());
    }
}
java
@RabbitListener(queues = "order.sms.queue", concurrency = "3-10")
public void onMessage(OrderDTO order,
                      Message message,
                      Channel channel,
                      @Header(AmqpHeaders.DELIVERY_TAG) long deliveryTag,
                      @Header(required = false, name = "traceId") String traceId) throws IOException {
    try {
        MDC.put("traceId", traceId);
        smsService.send(order);
        // 手动确认：第二个参数 multiple=false 表示只确认当前这一条
        channel.basicAck(deliveryTag, false);
    } catch (Exception e) {
        log.error("短信发送失败, msgId={}", message.getMessageProperties().getMessageId(), e);
        // requeue=false → 进死信队列，不要无限重投（见 6.1）
        channel.basicNack(deliveryTag, false, false);
    } finally {
        MDC.clear();
    }
}

📌 单独澄清：@RabbitListener 加在类上和加在方法上有什么区别？

  • 加在方法上：这个方法就是消费入口，最常用；
  • 加在类上：表示"这个类负责监听该队列"，但必须配合 @RabbitHandler 标注具体方法，用于同一个队列里混着多种消息类型时按参数类型分发：
java
@Component
@RabbitListener(queues = "order.event.queue")
public class OrderEventListener {

    @RabbitHandler
    public void onCreated(OrderCreatedEvent event) { /* ... */ }

    @RabbitHandler
    public void onPaid(OrderPaidEvent event) { /* ... */ }

    @RabbitHandler(isDefault = true)
    public void onOther(Object msg) { /* 兜底，防止类型不匹配直接报错 */ }
}

注意

类级 @RabbitListener + @RabbitHandler 的类型分发依赖 JSON 转换器写入的 __TypeId__ 消息头。如果生产者和消费者不在同一套序列化配置下，会抛 AmqpException: No method found for class [B。强烈建议加一个 isDefault = true 的兜底方法。

判断口诀

只有一种消息类型 → 方法级 @RabbitListener。

一个队列混多种事件 → 类级 @RabbitListener + @RabbitHandler。

要手动 ack → 参数里必须同时有 Channel 和 deliveryTag。

队列由别人声明 → 用 queues；由自己声明 → 用 bindings。

4.5 消息转换器与序列化的那些坑 ​

概念

消息在网络上传输的永远是 byte[]。把 Java 对象变成 byte[]（发送端）、把 byte[] 变回 Java 对象（消费端），这个双向工作由 MessageConverter 完成。

Spring AMQP 默认用 SimpleMessageConverter，它的行为是：

  • String → UTF-8 字节
  • byte[] → 原样
  • 其他 Serializable 对象 → JDK 原生序列化（问题就出在这里）

❌ 默认转换器的三个致命问题 ​

│    Get Message 看到的是 \xAC\xED\x00\x05sr... 二进制乱码  │

✅ 正确做法：全局替换为 JSON 转换器 ​

java
@Configuration
public class RabbitMessageConverterConfig {

    @Bean
    public MessageConverter jackson2MessageConverter() {
        ObjectMapper mapper = new ObjectMapper();
        // 1. 忽略未知字段：生产者加字段时消费者不会炸（向后兼容的关键）
        mapper.configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, false);
        // 2. 支持 LocalDateTime 等 JSR-310 类型，并禁用时间戳数字格式
        mapper.registerModule(new JavaTimeModule());
        mapper.disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS);
        return new Jackson2JsonMessageConverter(mapper);
    }
}

只要容器里存在一个 MessageConverter 类型的 Bean，RabbitTemplate 和所有 @RabbitListener 的容器工厂都会自动使用它，发送端和消费端同时生效，不需要额外配置。

📌 单独澄清：__TypeId__ 这个消息头是干什么的，能不能去掉？

Jackson2JsonMessageConverter 发送时会在消息头写入 __TypeId__ = com.mall.dto.OrderDTO，消费端据此决定反序列化成哪个类。

它带来一个隐蔽的强耦合：如果消费端没有完全相同的全限定类名（比如包名不同、或者是其他语言的服务），就会抛 ClassNotFoundException。

解决方式有两种：

  1. 消费端方法签名已指明类型（如 public void on(OrderDTO o)），可以配置 DefaultJackson2JavaTypeMapper 的 setTypePrecedence(TypePrecedence.INFERRED)，让它优先信任方法签名而不是 __TypeId__；
  2. 跨服务/跨语言场景：消费端统一接收 String 再自己 JSON.parseObject，彻底不依赖这个头。

升级陷阱

给已上线的服务换转换器时，队列里可能还积压着旧格式（JDK 序列化）的消息。新转换器读到它们会直接抛异常并进入死信。

安全做法：先停止生产者 → 等待队列消费见底（控制台 Ready=0）→ 再发布新版本消费者 → 最后恢复生产者。

判断口诀

控制台看消息是乱码 → 没换 JSON 转换器。

报 ClassNotFoundException → __TypeId__ 和消费端类名对不上。

生产者加字段后消费端炸了 → 没关 FAIL_ON_UNKNOWN_PROPERTIES。

LocalDateTime 报错 → 没注册 JavaTimeModule。

5.1 消息丢失的三个环节：先定位，再治理 ​

概念

"消息丢了"不是一个问题，而是三个完全不同的问题。它们发生在不同环节、由不同机制负责、用不同手段解决。不先把环节分清楚，就会陷入"开了持久化为什么还丢"这类死胡同。

全链路丢失点 ​

text
  [生产者]            [Broker]                      [消费者]
     |                   |                              |
     |---① 发送 ------->|                              |
     |                   |                              |
     |            ② 存储（内存/磁盘）                    |
     |                   |                              |
     |                   |--- ③ 投递 ------------------>|
     |                   |                              |
     |                   |<-- ack ----------------------|

  ① 生产端丢失：网络抖动、Broker 宕机、routingKey 写错路由不到队列
     → 解决：Publisher Confirm + Return 回调（5.2）

  ② Broker 丢失：消息只在内存中，Broker 重启或宕机后消失
     → 解决：交换机 + 队列 + 消息 三者同时持久化（5.3）

  ③ 消费端丢失：自动 ack 下消息刚投递就被确认，业务还没执行完消费者就挂了
     → 解决：手动 ack，业务成功后再确认（5.4）

三环节对照表 ​

环节典型场景负责机制是否默认开启本文章节
① 生产端 → Broker网络断开、交换机不存在Publisher Confirm❌ 需配置5.2
① 交换机 → 队列routingKey 写错、无绑定Return 回调 + mandatory❌ 需配置5.2
② Broker 内部Broker 宕机重启三要素持久化部分默认5.3
③ Broker → 消费者消费者处理中崩溃手动 ack❌ 默认自动5.4

📌 单独澄清：为什么"开了持久化还会丢消息"？

这是最常见的认知误区。持久化只解决环节 ②，而且它本身也不是 100% 可靠的：

RabbitMQ 为了性能，消息落盘采用异步刷盘。消息被标记为持久化后，会先进入操作系统的 page cache，再由内核择机写入磁盘（通常几百毫秒内）。如果恰好在这个窗口期服务器断电，这批消息就真的没了。

所以严格来说：

  • 持久化 = 大幅降低丢失概率，不等于绝不丢失；
  • 要做到真正不丢，必须叠加 Confirm 回调 + 发送方重试 + 本地消息表对账（见 5.5），用"最终一致"而不是"绝对可靠"来兜底。

不要过度设计

全套可靠性方案（Confirm + 持久化 + 手动 ack + 本地消息表）会让吞吐下降 30%~50%，代码复杂度翻倍。

正确做法是按业务分级：

  • 资金、订单、库存类 → 全套上
  • 短信、推送、埋点类 → 持久化 + 手动 ack 即可
  • 日志、监控数据类 → 什么都不开，丢几条无所谓，优先要吞吐

判断口诀

消息根本没到 Broker → 看 Confirm 回调。

到了 Broker 但没进队列 → 看 Return 回调（八成 routingKey 写错）。

进了队列但重启后没了 → 看三要素持久化。

消费者"收到了"却没处理完就没了 → 看 ack 模式。

5.2 Publisher Confirm 与 Return：生产端的两道关卡 ​

概念

这两个回调管的是不同的两段路，必须一起理解：

  • Confirm 确认回调：回答"消息有没有到达交换机"。无论成功失败都会触发。
  • Return 退回回调：回答"消息有没有从交换机路由到队列"。只有路由失败时才触发。

两段路示意 ​

text
  生产者 ──①──> 交换机 ──②──> 队列
           ↑              ↑
     Confirm 管这段    Return 管这段

  ① 成功 + ② 成功 → 只触发 Confirm(ack=true)，不触发 Return
  ① 成功 + ② 失败 → 先触发 Return，再触发 Confirm(ack=true)   ← 最反直觉的一点
  ① 失败           → 只触发 Confirm(ack=false)，带失败原因

最反直觉的一点

路由失败时，Confirm 的 ack 仍然是 true！

因为 Confirm 的语义是"交换机收到了消息"，交换机确实收到了，只是没找到匹配的队列。所以不能只靠 Confirm 判断消息是否安全，必须同时监听 Return。

完整配置与回调实现 ​

yaml
spring:
  rabbitmq:
    publisher-confirm-type: correlated # simple/correlated/none，必须选 correlated
    publisher-returns: true
    template:
      mandatory: true # 不开则路由失败直接丢弃，Return 永不触发
java
@Configuration
@Slf4j
@RequiredArgsConstructor
public class RabbitCallbackConfig {

    private final RabbitTemplate rabbitTemplate;

    @PostConstruct
    public void init() {
        // ① Confirm：消息是否到达交换机
        rabbitTemplate.setConfirmCallback((correlationData, ack, cause) -> {
            String msgId = correlationData == null ? "unknown" : correlationData.getId();
            if (ack) {
                log.info("[Confirm] 已到达交换机, msgId={}", msgId);
                // 可在此把本地消息表状态置为「已投递」，见 5.5
            } else {
                log.error("[Confirm] 未到达交换机, msgId={}, cause={}", msgId, cause);
                // 必须落库或告警，等待定时任务补偿重发
            }
        });

        // ② Return：消息是否路由到队列（Spring Boot 2.2+ 用 ReturnsCallback）
        rabbitTemplate.setReturnsCallback(returned -> {
            log.error("[Return] 路由失败! exchange={}, routingKey={}, replyCode={}, replyText={}, body={}",
                    returned.getExchange(),
                    returned.getRoutingKey(),
                    returned.getReplyCode(),     // 312
                    returned.getReplyText(),     // NO_ROUTE
                    new String(returned.getMessage().getBody(), StandardCharsets.UTF_8));
            // 路由失败是配置问题，不是网络问题，重发无意义 → 直接告警人工介入
        });
    }
}

📌 单独澄清：mandatory: true 不开会怎样？

交换机找不到匹配队列时，会静默丢弃该消息——没有异常、没有日志、控制台也看不到任何痕迹。

这是线上最难排查的一类问题：生产者日志显示"发送成功"，消费者却一条都收不到，而 Confirm 回调还告诉你 ack=true。只有开了 mandatory 并监听 Return，才能看到那句关键的 312 NO_ROUTE。

判断口诀

Confirm 管"到没到交换机"，Return 管"进没进队列"，两者都要开。

路由失败时 Confirm 依然 ack=true，别被它骗了。

mandatory: true 没开 → Return 回调写了也不会触发。

Confirm 失败可重发，Return 失败是配置错，重发没用。

5.3 持久化三要素：少一个都等于白做 ​

概念

"持久化"不是一个开关，而是三个独立的开关必须同时打开：

  1. 交换机持久化（durable = true）
  2. 队列持久化（durable = true）
  3. 消息持久化（deliveryMode = PERSISTENT）

任何一个没开，Broker 重启后链路就会断在那一环。

三要素缺失后果对照 ​

缺失项Broker 重启后的后果
交换机未持久化交换机消失，生产者发消息报 404 NOT_FOUND，整条链路不通
队列未持久化队列消失，连带队列里所有消息一起没了，绑定关系也没了
消息未持久化交换机、队列都在，但队列里空空如也，消息全丢

📌 单独澄清：Spring Boot 下这三项哪些需要你操心？

好消息是 Spring AMQP 的默认值已经很安全了：

  • ExchangeBuilder / QueueBuilder.durable() → 默认持久化
  • RabbitTemplate 发送的消息 → 默认 deliveryMode = PERSISTENT

真正容易出问题的是这两种情况：

  1. 在控制台手动建队列时忘了勾 Durable（控制台默认值其实也是 Durable，但有人会手滑改成 Transient）；
  2. 用原生 amqp-client 或其他语言客户端，它们的默认值是非持久化，必须显式指定。

持久化的代价 ​

text
  非持久化：消息 → 内存 → 投递            （微秒级）
  持久化  ：消息 → 内存 → page cache → 磁盘 → 投递  （毫秒级）

  吞吐对比（单机 4C8G 参考值，仅示意量级）：
    非持久化：约 5~8 万条/秒
    持久化  ：约 1~2 万条/秒     ← 下降 60%~75%

注意

持久化会让消息写入磁盘，因此磁盘空间和磁盘 IO 成为新的瓶颈。当磁盘剩余空间低于 disk_free_limit（默认 50MB）时，RabbitMQ 会阻塞所有生产者，表现为发送端卡死无响应——这是 8.2 节要讲的流控机制。

判断口诀

三要素少一个，持久化就等于零。

Spring Boot 下三项默认都已开启，重点检查手动建的队列和非 Java 客户端。

持久化换来的是可靠，付出的是约 60% 的吞吐。

持久化只防"进程重启"，不防"断电瞬间丢 page cache"。

5.4 三种 ack 模式：消费端可靠性的总开关 ​

概念

ack（acknowledge）是消费者告诉 Broker"这条消息我处理完了，可以删了"的信号。在它到来之前，消息在 Broker 里处于 Unacked（未确认） 状态，既不会被删除，也不会投给别人。

Spring AMQP 提供三种模式：NONE、AUTO（默认）、MANUAL。

三种模式对照 ​

模式何时确认消费抛异常时丢消息风险适用场景
NONEBroker 投递出去立即删除消息已丢，无感知极高日志、埋点
AUTO（默认）方法正常返回后由框架 ack框架自动 nack，按 default-requeue-rejected 决定重回或进死信中一般业务
MANUAL你调 channel.basicAck 才确认由你决定 ack / nack / reject最低资金、订单

                      @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
    try {
        payService.handle(pay);
        channel.basicAck(tag, false);          // 确认当前这一条
    } catch (BizException e) {
        // 业务异常：消息本身有问题，重试多少次都没用 → 直接进死信
        channel.basicNack(tag, false, false);
    } catch (Exception e) {
        // 系统异常（如数据库瞬时不可用）：值得重试 → 重回队列
        channel.basicNack(tag, false, true);
    }
}

📌 单独澄清：basicNack 的三个参数到底什么意思？

channel.basicNack(deliveryTag, multiple, requeue)：

  • deliveryTag：消息在当前 Channel 内的递增序号。注意它不是全局唯一 ID，不同 Channel 的 tag 会重复，所以不能用它做幂等。
  • multiple：false 只操作当前这条；true 批量操作 tag ≤ 当前值的所有未确认消息。生产一律传 false，传 true 很容易误确认掉还在处理中的消息。
  • requeue：true 重回队列头部（可能无限循环，危险）；false 进死信队列（推荐）。

📌 单独澄清：basicNack 和 basicReject 有什么区别？

功能几乎一样，唯一区别是 basicReject 没有 multiple 参数，只能一条条拒绝。basicNack 是 RabbitMQ 对 AMQP 标准的扩展，功能是 basicReject 的超集。统一用 basicNack 即可。

Unacked 消息堆积陷阱

如果消费者忘了 ack（比如某个异常分支没调 basicAck），消息会永远停在 Unacked 状态：

  • 控制台上 Unacked 数量只增不减
  • 这些消息占用 prefetch 配额，达到上限后该消费者再也收不到新消息，表现为"消费者假死"
  • 只有当连接断开时，Broker 才会把它们重新投递给别人

排查方法：控制台 Queues 页签看 Unacked 列，若持续增长且不归零，一定是某条代码路径漏了 ack。

判断口诀

消费者假死、Unacked 只涨不降 → 一定是漏了 basicAck。

业务异常不值得重试 → basicNack(tag, false, false) 进死信。

系统异常值得重试 → 交给 Spring 的重试机制（5.5），别直接 requeue=true。

multiple 永远传 false，别省那点网络往返。

5.5 消费重试与本地消息表：最终一致的兜底方案 ​

概念

前四节解决的是"尽量不丢"。但分布式系统里永远存在极端情况：Confirm 回调本身丢了、应用在发送后宕机、网络分区……

要做到真正的可靠，必须换一种思路：不追求"一次成功"，而是保证"最终一定成功"。实现手段有两层：

  1. 消费端重试：失败后自动重试几次，解决瞬时故障；
  2. 本地消息表：把"发消息"和"业务数据"放进同一个数据库事务，再由定时任务补偿，解决"业务成功但消息没发出去"。

第一层：Spring Retry 消费重试 ​

yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: auto # 重试机制依赖 auto 模式，manual 下需自己实现
        default-requeue-rejected: false
        retry:
          enabled: true
          max-attempts: 4 # 含首次，即首次 + 3 次重试
          initial-interval: 1000ms
          multiplier: 3 # 退避：1s → 3s → 9s
          max-interval: 10000ms

这是「本地重试」，不是「重回队列」

开启后，重试全部发生在消费者进程内存中，消息始终处于 Unacked 状态，不会回到 Broker。

这意味着：重试期间消费者进程挂了，这条消息会被 Broker 重新投递给其他消费者（因为连接断开，Unacked 消息自动 requeue）。这点反而是好事。

但也意味着：initial-interval 设太大 + max-attempts 设太多，会长时间占用 prefetch 配额，拖垮消费速度。建议总重试时长控制在 30 秒内。

重试耗尽后的处理由 MessageRecoverer 决定：

java
@Bean
public MessageRecoverer messageRecoverer(RabbitTemplate rabbitTemplate) {
    // 重试全部失败后，把消息投递到专门的失败交换机，而不是简单丢弃
    return new RepublishMessageRecoverer(rabbitTemplate, "error.ex", "error.order");
}

ImmediateRequeueMessageRecoverer重回原队列 → 慎用，易死循环

📌 单独澄清：为什么不能"先发消息再写数据库"或"写完数据库再发消息"？

这是本地消息表要解决的核心问题：

  • 先发消息，后写库：消息发出去了，但数据库事务回滚了 → 下游处理了一笔根本不存在的订单（数据凭空出现）；
  • 先写库，后发消息：数据库提交成功，但发消息时应用崩溃 → 订单存在，下游永远收不到通知（数据不一致）。

本地消息表的巧妙之处在于：把"要发消息"这件事也变成一条数据库记录，和业务数据同生共死。只要业务成功，这条待发记录就一定存在；只要它存在，定时任务就一定会把它发出去。

代价是：下游必须做幂等（补偿重发会产生重复消息），这正是 7.2 幂等三板斧 的内容。

判断口诀

瞬时故障（网络抖动、DB 超时）→ 本地重试能救。

永久故障（数据格式错、业务规则不满足）→ 重试无意义，直接进死信。

业务与消息必须同成功同失败 → 本地消息表。

用了补偿重发，消费端就必须幂等，没有例外。

六、死信与延迟消息篇 ​

6.1 死信的三个触发条件与死信交换机 ​

概念

死信（Dead Letter） 不是一种特殊消息，而是一种状态：普通消息因为某些原因无法被正常消费，就"变成"了死信。

Broker 对死信的处理很简单：如果该队列配置了 死信交换机（DLX, Dead Letter Exchange），就把消息重新投递到 DLX；没配置就直接丢弃。

三个触发条件（只有这三个，没有第四个） ​

触发条件典型场景注意点
① 消息被拒绝且不重回队列basicNack(tag, false, false) 或 basicReject(tag, false)requeue 必须为 false，为 true 不算死信
② 消息 TTL 过期队列 TTL 或单条消息 TTL 到期仍未被消费这是实现延迟队列的基础，见 6.2
③ 队列达到最大长度队列配了 x-max-length，新消息进来时挤掉队头最老的消息注意被挤掉的是最老的，不是新来的

死信拓扑配置 ​

java
@Configuration
public class DlxConfig {

    /** 业务队列：配置死信交换机和死信 routingKey */
    @Bean
    public Queue orderSmsQueue() {
        return QueueBuilder.durable("order.sms.queue")
                .deadLetterExchange("dlx.ex")            // x-dead-letter-exchange
                .deadLetterRoutingKey("dlx.order.sms")   // x-dead-letter-routing-key
                .maxLength(10000)                        // x-max-length，触发条件③
                .build();
    }

    /** 死信交换机：用 Direct 即可，死信不需要复杂路由 */
    @Bean
    public DirectExchange dlxEx() {
        return ExchangeBuilder.directExchange("dlx.ex").durable(true).build();
    }

    /** 死信队列：⚠️ 它自己不要再配死信，否则可能形成循环 */
    @Bean
    public Queue dlxQueue() {
        return QueueBuilder.durable("dlx.order.sms.queue").build();
    }

    @Bean
    public Binding dlxBinding() {
        return BindingBuilder.bind(dlxQueue()).to(dlxEx()).with("dlx.order.sms");
    }
}

@RabbitListener(queues = "dlx.order.sms.queue")
public void onDeadLetter(Message message, Channel channel,
                         @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
    Map<String, Object> props = message.getMessageProperties().getHeaders();
    // Broker 自动注入的 x-death 头，记录了完整的死信轨迹
    List<Map<String, Object>> xDeath = (List<Map<String, Object>>) props.get("x-death");

    if (xDeath != null && !xDeath.isEmpty()) {
        Map<String, Object> first = xDeath.get(0);
        log.error("死信! 原队列={}, 原因={}, 死信次数={}, 原 routingKey={}",
                first.get("queue"),
                first.get("reason"),   // rejected / expired / maxlen
                first.get("count"),
                first.get("routing-keys"));
    }
    alarmService.send("订单短信进入死信队列");
    channel.basicAck(tag, false);
}

📌 单独澄清：x-death 头里的 reason 对应哪个触发条件？

reason 取值对应触发条件
rejected① 被 nack/reject 且 requeue=false
expired② TTL 过期
maxlen③ 队列超长被挤出

排障时先看这个字段，能瞬间锁定问题方向——是代码主动拒绝的，还是消费太慢超时的，还是队列爆了。

死信队列不是垃圾桶

很多团队配了 DLX 就不管了，结果死信队列积压几十万条消息，占满磁盘触发流控，反而拖垮整个 Broker。

死信队列必须有消费者，至少做三件事：记录日志、发送告警、支持人工重投。

判断口诀

消息莫名消失 → 先查有没有配 DLX，没配就是被直接丢弃了。

requeue=true 不产生死信，只会无限重投。

队列超长挤掉的是最老的消息，不是刚来的。

配了死信就必须配死信消费者，否则只是换个地方堆积。

6.2 TTL 的两种设置方式与队头阻塞陷阱 ​

概念

TTL（Time To Live）是消息的存活时间，到期未被消费就变成死信。设置方式有两种，行为差异巨大：

  • 队列 TTL（x-message-ttl）：作用于队列，该队列里所有消息统一时长；
  • 消息 TTL（expiration）：作用于单条消息，每条可以不同。

两者同时存在时，取较小值生效。

两种方式代码 ​

java
@Bean
public Queue ttlQueue() {
    return QueueBuilder.durable("order.delay.queue")
            .ttl(30 * 60 * 1000)                   // x-message-ttl，30 分钟
            .deadLetterExchange("dlx.ex")
            .deadLetterRoutingKey("dlx.order.timeout")
            .build();
}
java
public void sendWithTtl(OrderDTO order, long ttlMillis) {
    rabbitTemplate.convertAndSend("order.delay.ex", "order.delay", order,
            message -> {
                // 注意：必须是字符串类型的毫秒数
                message.getMessageProperties().setExpiration(String.valueOf(ttlMillis));
                return message;
            });
}

❗ 核心陷阱：消息 TTL 的队头阻塞 ​

text
  队列（FIFO，只检查队头）：

  [队头] msg1(TTL=30min) ← msg2(TTL=10s) ← msg3(TTL=5s) [队尾]
           ↑
       Broker 只盯着队头这一条

  时间线：
    t=5s   msg3 实际已过期，但它在队尾 → Broker 根本不看它
    t=10s  msg2 实际已过期，同样不被处理
    t=30min msg1 过期 → 出队进死信
           → 此时才轮到 msg2 到队头，立刻判定过期 → 进死信（迟到 30 分钟！）
           → msg3 同理

  结果：本该 5 秒后触发的业务，30 分钟后才触发。

这是 RabbitMQ 的设计使然，不是 bug

RabbitMQ 的队列是严格 FIFO 的，只会检查队头消息是否过期，因为逐条扫描全队列的开销太大。

因此：

  • 队列 TTL 下所有消息时长相同，天然不会出现这个问题；
  • 消息 TTL 下只要存在不同时长的消息，就必然出现队头阻塞。

这就是为什么不能用消息 TTL 实现"每单延迟时间不同"的延迟队列，必须用 6.3 的延迟插件。

对照表 ​

维度队列 TTL（x-message-ttl）消息 TTL（expiration）
作用范围整个队列所有消息单条消息
时长是否可变固定，改需重建队列每条可不同
队头阻塞❌ 不会✅ 时长不一致时必然发生
过期判定时机入队即可计算，可提前移除仅在到达队头时判定
典型用法固定 30 分钟订单超时几乎不该单独使用

📌 单独澄清：那"死信队列实现延迟"到底还能不能用？

能用，但有严格前提：必须用队列 TTL，并且为每种延迟时长建一个独立队列。

常见做法是建一组「延迟梯度队列」：

text
  order.delay.5s.queue    (x-message-ttl=5000)     ──┐
  order.delay.1m.queue    (x-message-ttl=60000)    ──┼──> dlx.ex ──> 真正的业务队列
  order.delay.30m.queue   (x-message-ttl=1800000)  ──┘

生产者按需求选择投递到哪个队列。缺点是延迟时长只能是预设的几档，不够灵活——需要任意时长就只能上插件。

判断口诀

所有消息延迟时长一样 → 队列 TTL，安全。

每条消息延迟时长不同 → 别用消息 TTL，会队头阻塞，直接上延迟插件。

两个 TTL 都设了 → 取小的那个生效。

setExpiration 的参数是字符串，传 long 编译不过。

6.3 延迟消息插件 rabbitmq_delayed_message_exchange ​

概念

官方插件 rabbitmq_delayed_message_exchange 提供了一种新的交换机类型 x-delayed-message。

它的核心区别在于：消息不是先进队列再等过期，而是先被扣在交换机里，由插件用 Erlang 的定时器（底层是 Mnesia 数据库 + timer）管理，到点后才路由到队列。

因此不存在队头阻塞，每条消息的延迟时间可以完全不同。

两种延迟方案对照 ​

维度死信 + 队列 TTL延迟插件
延迟时长只能是预设的几档任意时长，每条不同
队头阻塞需按时长分队列才能规避❌ 不存在
拓扑复杂度高（每档要 2 个队列 + 1 个交换机）低（1 个交换机 + 1 个队列）
额外依赖无，原生能力需安装插件、重启 Broker
集群支持✅ 完善⚠️ 延迟消息不会在节点间复制

插件的两个生产级限制

  1. 不支持集群高可用：延迟中的消息只保存在接收它的那个节点上，该节点宕机，这批未到期的消息就丢了（即使队列是镜像的也救不回来）。
  2. 延迟消息量不宜过大：待触发消息常驻内存（Mnesia），建议单节点不超过 10 万条，超过会明显推高内存占用并拖慢 Broker。

量大且要求高可用的场景，应改用 Redis ZSet 扫描 或 RocketMQ 定时消息。

判断口诀

延迟时长固定 + 不想装插件 → 死信 + 队列 TTL。

延迟时长任意 + 量不大 → 延迟插件。

延迟量大 + 要求高可用 → 别用 RabbitMQ，上 Redis ZSet 或 RocketMQ。

x-delayed-type 忘了设 → 交换机创建直接失败。

6.4 实战：订单超时 30 分钟自动取消 ​

场景

用户下单后 30 分钟内未支付，系统自动取消订单并回滚库存。这是延迟消息最经典的落地场景，也是面试高频追问。

整体链路 ​

text
  ① 用户下单
       │ 同一个本地事务：写 t_order(status=UNPAID) + 写 t_mq_message
       ▼
  ② 发送延迟消息（x-delay = 30min, messageId = orderNo）
       │
       ▼
  ③ order.delayed.ex（消息被扣住 30 分钟）
       │
       ▼
  ④ order.timeout.queue
       │
       ▼
  ⑤ 消费者处理
       ├─ 查库：订单当前状态是什么？
       │    ├─ UNPAID   → 执行取消：改状态 + 回滚库存 + 退优惠券
       │    ├─ PAID     → 用户已支付，直接 ack 忽略        ← 关键分支
       │    └─ CANCELED → 已取消过，直接 ack（幂等）       ← 关键分支
       └─ basicAck

核心代码 ​

java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderMapper orderMapper;
    private final RabbitTemplate rabbitTemplate;

    private static final int TIMEOUT_MILLIS = 30 * 60 * 1000;

    @Transactional(rollbackFor = Exception.class)
    public String createOrder(OrderDTO dto) {
        dto.setOrderNo(IdUtil.getSnowflakeNextIdStr());
        dto.setStatus(OrderStatus.UNPAID);
        orderMapper.insert(dto);

        // 事务提交后再发消息，避免「消息已发但事务回滚」
        TransactionSynchronizationManager.registerSynchronization(
            new TransactionSynchronization() {
                @Override
                public void afterCommit() {
                    sendTimeoutMessage(dto);
                }
            });
        return dto.getOrderNo();
    }

    private void sendTimeoutMessage(OrderDTO dto) {
        rabbitTemplate.convertAndSend("order.delayed.ex", "order.timeout", dto,
                msg -> {
                    msg.getMessageProperties().setHeader("x-delay", TIMEOUT_MILLIS);
                    msg.getMessageProperties().setMessageId(dto.getOrderNo());
                    return msg;
                },
                new CorrelationData(dto.getOrderNo()));
    }
}
java
@Component
@Slf4j
@RequiredArgsConstructor
public class OrderTimeoutListener {

    private final OrderMapper orderMapper;
    private final StockService stockService;

    @RabbitListener(queues = "order.timeout.queue", concurrency = "3-10")
    public void onTimeout(OrderDTO dto, Channel channel,
                          @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
        try {
            Order order = orderMapper.selectByOrderNo(dto.getOrderNo());
            if (order == null) {
                log.warn("订单不存在, orderNo={}", dto.getOrderNo());
                channel.basicAck(tag, false);
                return;
            }
            if (order.getStatus() != OrderStatus.UNPAID) {
                // 已支付或已取消，什么都不做 —— 这就是天然的幂等
                log.info("订单状态={}, 无需超时取消", order.getStatus());
                channel.basicAck(tag, false);
                return;
            }
            // 乐观锁：仅当状态仍是 UNPAID 时才更新，防止与支付回调并发
            int rows = orderMapper.cancelIfUnpaid(dto.getOrderNo());
            if (rows > 0) {
                stockService.rollback(dto.getOrderNo());
                log.info("订单超时取消成功, orderNo={}", dto.getOrderNo());
            }
            channel.basicAck(tag, false);
        } catch (Exception e) {
            log.error("超时取消失败, orderNo={}", dto.getOrderNo(), e);
            channel.basicNack(tag, false, false);   // 进死信，人工介入
        }
    }
}

    SET status = 'CANCELED', update_time = NOW()

📌 单独澄清：为什么一定要在消费时再查一次数据库状态？

因为延迟消息是"无条件"投递的：无论这 30 分钟里用户做了什么，到点消息一定会来。

典型并发场景：用户在第 29 分 59 秒完成支付，支付回调把状态改成 PAID，1 秒后超时消息到达。如果消费者不查状态就直接取消，就会把一笔已付款的订单取消掉——这是真实发生过的线上资损事故。

所以记住：延迟消息只负责"到点提醒"，绝不能替代"状态判断"。真正的业务决策永远要以数据库当前状态为准。

为什么不用定时任务轮询？

定时任务（如每分钟扫一次 status=UNPAID AND create_time < now()-30min）也能实现，但有三个问题：

  1. 精度差：扫描间隔决定精度，1 分钟扫一次就有最多 1 分钟误差；
  2. 压力大：订单表数据量上千万后，这条扫描 SQL 会成为慢查询；
  3. 难扩展：改成"VIP 用户 60 分钟超时"就得改 SQL 和索引。

延迟消息把时间调度交给 Broker，数据库零压力，精度到秒级。数据量小用定时任务，数据量大用延迟消息。

判断口诀

延迟消息到点必达，但业务做不做要看数据库当前状态。

取消操作必须带 WHERE status = 'UNPAID'，靠乐观锁防并发。

消息要在事务提交后再发，用 afterCommit 回调。

消费失败进死信，别重回队列反复取消订单。

七、幂等顺序与堆积篇 ​

7.1 消息重复消费的三大根因 ​

概念

重复消费：同一条业务消息被消费者的业务逻辑成功执行了两次及以上。

注意这句话的落点是业务逻辑执行了两次，而不是"消息投递了两次"。投递两次但业务只生效一次，叫做幂等成功；投递一次但业务执行了两次（比如重试逻辑写错），同样算重复消费。

📌 单独澄清：RabbitMQ 承诺的是 at-least-once，不是 exactly-once

很多人以为开了 Confirm + 手动 ack 就能做到"消息只消费一次"。不可能。分布式系统里 exactly-once 需要消息中间件与业务数据库处于同一个事务，而 RabbitMQ 与 MySQL 是两套独立系统，网络可能在任意时刻断开。

RabbitMQ 的设计取舍是：宁可重复，不可丢失。所以它只保证 at-least-once（至少一次），剩下的"一次"由消费端自己做幂等来兜底。

根因一：生产者重复投递 ​

生产者发完消息后没收到 Broker 的 confirm 回调（网络抖动把 ack 包吞了），于是触发重试再发一次。但实际上 Broker 第一次就已经收下了。

text
生产者                      Broker
  │  ──── 消息 M ────────▶   │  收下了，落盘成功
  │                          │
  │  ◀─ ─ ack(丢包) ─ ─ ─ ─  │
  │                          │
  │  (超时未收到 ack)          │
  │  ──── 消息 M(重发) ───▶   │  又收下一条,队列里现在有 2 条

根因二：消费者 ack 丢失或超时 ​

消费者业务已经执行完了，正准备 basicAck，这时候连接断了 / 应用被 kill / ack 包丢了。Broker 没收到 ack，认为这条消息没被处理，于是 requeue 重新投递给其他消费者。

text
消费者                      Broker
  │  ◀──── 投递 M ────────   │  unacked +1
  │  执行业务: 扣库存成功 ✅    │
  │  ──── ack ──X 断线        │
  │                          │检测到 channel 关闭
  │  ◀──── 重新投递 M ─────   │  requeue
  │  执行业务: 又扣了一次 ❌    │

这是最高频的重复场景，也是生产上必须做幂等的核心原因。

根因三：消费者主动 nack 重回队列 ​

业务抛异常后调用 basicNack(deliveryTag, false, true)，消息回到队列重新投递。如果异常发生在业务部分执行完之后（比如扣了库存但加积分失败），那么重投后扣库存的逻辑又会跑一遍。

java
@RabbitListener(queues = "order.point.queue")
public void handle(OrderMsg msg, Channel channel, Message message) throws IOException {
    long tag = message.getMessageProperties().getDeliveryTag();
    try {
        stockService.deduct(msg.getSkuId());   // ① 执行成功
        pointService.addPoint(msg.getUserId()); // ② 抛异常
        channel.basicAck(tag, false);
    } catch (Exception e) {
        // ❌ 重回队列后 ① 会再执行一次,库存被扣两次
        channel.basicNack(tag, false, true);
    }
}

三大根因对照表 ​

根因发生位置触发条件能否靠配置规避实际概率
生产者重复投递生产端confirm 回调丢失后重试否（重试是必要的）中
ack 丢失/超时消费端消费者宕机、网络断、处理超时否（ack 本身不可靠）高
主动 nack 重投消费端业务异常 + requeue=true可（改成进死信）中

不要试图用"关闭重试"来解决重复

把生产者重试关掉、把 nack 的 requeue 改成 false，确实能降低重复率，但代价是消息丢失。两害相权，重复可以靠幂等消除，丢失只能靠人工对账。所以正确路线永远是：允许重复 + 消费端幂等。

判断口诀

没收到 ack 就重发 → 生产者重复。

ack 没送到就重投 → 消费者重复。

nack 带 requeue → 自己给自己重复。

7.2 幂等三板斧：唯一索引、Redis 去重、状态机 ​

概念

幂等（Idempotent）：同一个操作执行一次和执行 N 次，对系统状态产生的影响完全相同。

数学里 f(f(x)) = f(x) 就是幂等。放到业务上：扣库存(订单A) 执行 10 次，库存也只应该少 1 件。

📌 单独澄清：幂等 ≠ 去重，两者解决问题的层次不同

  • 去重：在消息层面拦截，"这条消息我见过，直接丢弃"。
  • 幂等：在业务层面兜底，"这个业务已经做过了，再做一次也不改变结果"。

去重是性能优化（省掉一次业务执行），幂等是正确性保障（即使去重失效也不出错）。只做去重不做幂等是危险的，因为 Redis 可能宕机、key 可能过期。

前提：消息必须携带全局唯一业务 ID ​

幂等的一切前提是"能判断两条消息是不是同一个业务操作"。不要用 RabbitMQ 的 deliveryTag（每次投递都不同），也不要用消息体哈希（业务字段可能相同但确实是两笔）。正确的做法是生产端生成全局唯一 ID 并塞进 messageId。

java
@Service
public class OrderMqSender {

    @Resource
    private RabbitTemplate rabbitTemplate;

    public void sendOrderCreated(OrderMsg msg) {
        // 业务唯一键:订单号,天然全局唯一
        String bizId = msg.getOrderNo();
        rabbitTemplate.convertAndSend("order.direct.ex", "order.sms", msg, message -> {
            message.getMessageProperties().setMessageId(bizId);
            return message;
        }, new CorrelationData(bizId));
    }
}

不要用 UUID.randomUUID() 当幂等键

UUID 每次调用都不同，生产者重试时会生成一个新的 UUID，消费端根本认不出这是同一条消息。幂等键必须是业务维度稳定的值：订单号、支付流水号、订单号 + 操作类型 组合键。

第一板斧：数据库唯一索引（最可靠） ​

利用数据库的唯一约束天然排他，重复插入直接抛 DuplicateKeyException。

sql
CREATE TABLE mq_consume_log (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    biz_id      VARCHAR(64)  NOT NULL COMMENT '业务唯一键',
    consumer    VARCHAR(128) NOT NULL COMMENT '消费者标识',
    create_time DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_biz_consumer (biz_id, consumer)
) COMMENT 'MQ 消费幂等表';
java
@RabbitListener(queues = "order.point.queue")
@Transactional(rollbackFor = Exception.class)
public void handle(OrderMsg msg, Message message) {
    String bizId = message.getMessageProperties().getMessageId();
    try {
        consumeLogMapper.insert(new ConsumeLog(bizId, "order.point.queue"));
    } catch (DuplicateKeyException e) {
        log.info("消息已消费过,跳过: {}", bizId);
        return; // 直接 return,外层自动 ack
    }
    pointService.addPoint(msg.getUserId(), msg.getAmount());
}

关键点：插入幂等记录和业务操作必须在同一个事务里。否则插入成功但业务失败，事务回滚后幂等记录没了（或者业务成功但幂等记录没写进去），下次重投会重复执行。

组合方式结果
✅ 幂等插入 + 业务操作同事务要么都成功要么都回滚，安全
❌ 先插幂等记录再单独提交业务业务失败后幂等记录残留，消息永久丢失
❌ 先做业务再插幂等记录业务成功后宕机，幂等记录丢失，重投会重复

为什么 unique key 要带 consumer 字段

同一条消息可能被 fanout 扇出到多个队列，被不同的消费者处理。只用 biz_id 做唯一键，第二个消费者会误判为"已消费"。加上消费者标识后，每个消费者各自独立幂等。

第二板斧：Redis 去重（最高性能） ​

用 Redis 的 SET key value NX EX seconds 原子命令抢占"消费权"，抢到的才执行业务。

java
@Component
@Slf4j
public class IdempotentConsumer {

    @Resource
    private StringRedisTemplate redisTemplate;

    private static final String PREFIX = "mq:idem:order.point.queue:";

    @RabbitListener(queues = "order.point.queue")
    public void handle(OrderMsg msg, Message message) {
        String key = PREFIX + message.getMessageProperties().getMessageId();
        // NX: key 不存在才设置;EX: 7 天后自动过期
        Boolean first = redisTemplate.opsForValue()
                .setIfAbsent(key, "1", Duration.ofDays(7));
        if (!Boolean.TRUE.equals(first)) {
            log.info("重复消息,跳过: {}", key);
            return;
        }
        try {
            pointService.addPoint(msg.getUserId(), msg.getAmount());
        } catch (Exception e) {
            // ⚠️ 业务失败必须删除 key,否则这条消息永远没机会重试
            redisTemplate.delete(key);
            throw e;
        }
    }
}

Redis 去重的两个致命坑

坑一：业务异常后忘记删 key。 第一次消费抢到锁但业务抛异常，消息重投后发现 key 已存在直接跳过 —— 这条消息就彻底丢了。必须在 catch 里删除。

坑二：过期时间设太短。 设 5 分钟，但消息在死信队列里躺了 1 小时才被重新投递，这时 key 早过期了，业务又跑一遍。过期时间要 大于消息在系统里可能存活的最长时间，一般设 3~7 天。

📌 单独澄清：setIfAbsent 不是万能的，它不能跨越"业务执行"这个时间窗

Redis 占位和业务执行之间不是原子的。如果消费者在"占位成功 → 业务执行中"时宕机，key 留在 Redis 但业务只做了一半，重投后会被跳过，数据永久不一致。所以 Redis 去重只适合"允许极小概率不一致"的弱一致场景（发短信、加积分、推消息），强一致场景（扣款、扣库存）必须用数据库唯一索引。

第三板斧：业务状态机（最优雅） ​

不额外建表、不依赖 Redis，直接利用业务自身的状态流转天然排重。核心是带条件的 UPDATE。

java
// ❌ 错误:无条件更新,执行两次就扣两次钱
@Update("UPDATE t_account SET balance = balance - #{amt} WHERE user_id = #{uid}")
int deduct(Long uid, BigDecimal amt);

// ✅ 正确:状态机 + 乐观锁,第二次执行 affected = 0
@Update("UPDATE t_order SET status = 'PAID', pay_time = NOW() " +
        "WHERE order_no = #{orderNo} AND status = 'UNPAID'")
int markPaid(String orderNo);
java
@RabbitListener(queues = "order.pay.queue")
public void handlePaid(OrderMsg msg) {
    int affected = orderMapper.markPaid(msg.getOrderNo());
    if (affected == 0) {
        log.info("订单已是终态,无需重复处理: {}", msg.getOrderNo());
        return;
    }
    // 只有真正改变了状态的那一次才会走到这里
    pointService.addPoint(msg.getUserId(), msg.getAmount());
}

状态机的精髓在于：把"是否已处理"的判断，交给数据库的行锁 + WHERE 条件去做，天然原子，不需要任何额外存储。

三板斧选型对照 ​

方案存储依赖性能一致性强度适用场景
数据库唯一索引MySQL（需建幂等表）中（一次 insert）强扣款、扣库存、开票等金额相关
Redis 去重Redis高弱（宕机有窗口）发短信、推送、加积分、日志上报
业务状态机无（复用业务表）高强有明确状态流转的订单、工单、审批

判断口诀

有状态流转 → 优先状态机，零成本。

无状态但要强一致 → 唯一索引幂等表。

只求快且能容忍极小概率重复 → Redis 去重。

生产最稳方案 = Redis 前置拦截 + 数据库唯一索引兜底。

7.3 顺序消费：为什么会乱序，怎么保证有序 ​

概念

顺序消费：业务上存在先后依赖的一组消息，必须按生产顺序被处理。

典型场景：订单的"创建 → 支付 → 发货 → 完成"四条状态变更消息，如果"发货"先于"支付"被处理，订单状态机就会错乱。

📌 单独澄清：RabbitMQ 的"队列有序"和"消费有序"是两回事

  • 队列内部有序：RabbitMQ 保证单个队列中的消息按入队顺序排列，这是 FIFO 数据结构的天然属性，永远成立。
  • 消费端有序：消息被业务逻辑处理完成的顺序，不保证。

队列是有序的，但只要多个消费者同时从队列里取消息，各自处理耗时不同，完成顺序就会乱。所以"RabbitMQ 是有序的吗"这个问题的正确答案是：队列有序，但多消费者场景下消费无序。

乱序的两种成因 ​

成因一：一个队列挂了多个消费者

text
                   ┌──▶ 消费者A  处理「支付」耗时 500ms ──▶ 完成(t=500)
order.queue        │
[创建][支付][发货]  ┤
                   └──▶ 消费者B  处理「发货」耗时 50ms  ──▶ 完成(t=50)

结果:发货(t=50) 比 支付(t=500) 先完成 ❌

成因二：单消费者但开了多线程（并发消费）

yaml
spring:
  rabbitmq:
    listener:
      simple:
        concurrency: 5 # ⚠️ 同一个队列起 5 个消费线程
        max-concurrency: 10

即使只有一个应用实例，concurrency > 1 也会起多个线程并行消费同一队列，效果等同于多消费者，照样乱序。

还有一个隐蔽成因：nack 重回队列

消息 A、B 顺序投递，A 消费失败 nack 并 requeue，A 会被塞回队列尾部（不是头部）。等 A 再被消费时，B 早就处理完了，顺序彻底颠倒。

所以要求顺序的队列，绝不能用 requeue=true 做重试，失败必须进死信或原地阻塞重试。

方案一：单队列 + 单消费者 + 单线程（最简单） ​

java
@RabbitListener(queues = "order.status.queue", concurrency = "1")
public void handle(OrderStatusMsg msg) {
    orderService.changeStatus(msg);
}
yaml
spring:
  rabbitmq:
    listener:
      simple:
        concurrency: 1
        max-concurrency: 1
        prefetch: 1

代价是吞吐量被锁死在单线程水平，而且只能部署一个实例（多实例还是多消费者）。只适合消息量极低的场景。

方案二：哈希分片 —— 按业务键把同一组消息路由到同一队列（生产首选） ​

顺序的要求其实是局部有序：订单 A 的四条消息要有序，订单 B 的四条消息要有序，但 A 和 B 之间互不相干。那就按订单号哈希，把同一订单的消息永远投到同一个队列。

java
@Service
public class OrderStatusSender {

    private static final int QUEUE_COUNT = 4;

    @Resource
    private RabbitTemplate rabbitTemplate;

    public void send(OrderStatusMsg msg) {
        // 同一个 orderNo 恒定落到同一个 index
        int index = Math.abs(msg.getOrderNo().hashCode() % QUEUE_COUNT);
        String routingKey = "order.status." + index;
        rabbitTemplate.convertAndSend("order.direct.ex", routingKey, msg);
    }
}
java
@Configuration
public class OrderStatusMqConfig {

    @Bean
    public Declarables orderStatusQueues() {
        DirectExchange ex = new DirectExchange("order.direct.ex", true, false);
        List<Declarable> list = new ArrayList<>();
        list.add(ex);
        for (int i = 0; i < 4; i++) {
            Queue q = QueueBuilder.durable("order.status.queue." + i).build();
            list.add(q);
            list.add(BindingBuilder.bind(q).to(ex).with("order.status." + i));
        }
        return new Declarables(list);
    }
}

每个分片队列各自单线程消费，分片之间并行 —— 既保证了局部有序，又把吞吐量提升到了 4 倍。

分片数一旦确定就不能随便改

队列数从 4 改成 8，hashCode % N 的结果会变，同一个订单的历史消息在队列 1、新消息在队列 5，顺序立刻被打破。扩容必须在业务低峰期、确认旧队列已消费干净后再做。

方案三：消费端排序兜底（有状态流转时最实用） ​

不强求消息到达顺序，而是让业务逻辑自己拒绝乱序。给消息加版本号或利用状态机，发现是"过期的"或"跳步的"消息就延后处理。

java
@RabbitListener(queues = "order.status.queue")
public void handle(OrderStatusMsg msg, Channel channel, Message message) throws IOException {
    Order order = orderMapper.selectByNo(msg.getOrderNo());
    long tag = message.getMessageProperties().getDeliveryTag();
    if (msg.getVersion() <= order.getVersion()) {
        // 过期消息,直接丢弃
        channel.basicAck(tag, false);
        return;
    }
    if (msg.getVersion() > order.getVersion() + 1) {
        // 跳步消息,前一条还没到,延后重试(进延迟队列而不是 requeue)
        delaySender.retryLater(msg, 3000);
        channel.basicAck(tag, false);
        return;
    }
    orderService.changeStatus(msg);
    channel.basicAck(tag, false);
}

三种方案对照 ​

方案吞吐量实现成本可水平扩展适用场景
单队列单消费者最低极低否消息量 < 100/s 的配置同步类
哈希分片高中是（分片数内）生产首选，订单/用户维度有序
消费端排序兜底高高是已有版本号/状态机的业务

判断口诀

问"要不要全局有序"：几乎永远不要，业务只需要局部有序。

局部有序 → 按业务键哈希分片，每片单线程。

顺序队列禁止 requeue 重试，失败只能进死信或原地阻塞。

7.4 消息堆积：定位、应急扩容与临时转存 ​

概念

消息堆积（Backlog）：队列中 Ready 状态的消息数量持续增长，生产速率长期大于消费速率。

管理台队列列表的 Ready 列就是堆积量，Unacked 是已投递未确认的量，Total = Ready + Unacked。

📌 单独澄清：Ready 高和 Unacked 高是完全不同的两种故障

现象含义根因方向
Ready 高、Unacked 低消息投不出去，消费者吃不下消费者数量不足 / 消费者全挂了 / 消费逻辑太慢
Ready 低、Unacked 高消息都发出去了，但没人 ack消费者卡死（死锁、慢 SQL、外部接口超时）/ 忘记 ack
两者都高消费能力彻底崩溃下游依赖故障，先查下游

看错这一点会把排查方向完全带偏：Unacked 高的时候盲目加消费者实例，只会让更多消息卡在 unacked 状态。

第一步：定位堆积根因 ​

bash
# 查看所有队列的堆积情况(按 Ready 排序)
docker exec -it rabbitmq rabbitmqctl list_queues \
  name messages_ready messages_unacknowledged consumers

# 查看消费者详情:确认消费者是否还活着、prefetch 是多少
docker exec -it rabbitmq rabbitmqctl list_consumers

典型输出与诊断：

text
name                  ready    unacked  consumers
order.sms.queue       128000   0        0          ← 消费者全挂了,0 consumer
order.point.queue     95000    10       2          ← 消费太慢,prefetch 可能是 1
order.pay.queue       20       5000     5          ← 消费者卡死,unacked 居高不下
观察到的现象判断结论与动作
consumers = 0消费者进程挂了 / 连接断了 / 没启动 → 先把应用拉起来
consumers > 0 但 ready 持续涨消费能力不足 → 看是并发低还是单条处理慢
unacked 长期不降消费者线程卡住 → 用 jstack 抓线程栈查阻塞点

堆积不只是"慢"，还会反噬整个 Broker

队列堆积到一定量后，RabbitMQ 会把消息换页（page out）到磁盘，导致磁盘 IO 飙升；内存继续涨会触发内存告警，Broker 会阻塞所有生产者连接，整个系统的写入链路全部卡死。详见 8.2 流控与内存磁盘告警。

所以堆积是必须分钟级响应的线上故障，不能放着不管。

第二步：应急处理（已经堆了几十万条怎么办） ​

手段一：提高并发度（最快，改配置重启即可）

yaml
spring:
  rabbitmq:
    listener:
      simple:
        concurrency: 10 # 从 1 提到 10
        max-concurrency: 20
        prefetch: 50 # 从默认 250 调到合适值,别设 1

手段二：水平扩容消费者实例

多部署几个消费者 Pod，RabbitMQ 会把消息轮询投给所有消费者。注意：队列数量不变的情况下，消费者数量超过分片数就没有收益了（顺序分片场景尤其如此）。

手段三：临时转存（终极方案，适用于堆积量巨大且来不及处理）

写一个"搬运工"消费者，它不执行业务逻辑，只负责把消息极速捞出来落到数据库 / Kafka / 文件，先把队列清空，解除 Broker 压力，之后再离线慢慢消费。

java
@Component
@Slf4j
public class BacklogRescueConsumer {

    @Resource
    private BacklogMsgMapper backlogMapper;

    /**
     * 应急开关:只在堆积故障时开启
     * 不做任何业务处理,纯搬运,单条耗时 < 1ms
     */
    @RabbitListener(queues = "order.point.queue",
                    concurrency = "20",
                    autoStartup = "${mq.rescue.enabled:false}")
    public void rescue(Message message) {
        BacklogMsg record = new BacklogMsg();
        record.setQueueName("order.point.queue");
        record.setMsgId(message.getMessageProperties().getMessageId());
        record.setBody(new String(message.getBody(), StandardCharsets.UTF_8));
        record.setStatus("PENDING");
        backlogMapper.insert(record);
    }
}

落库后，用定时任务分批捞出来按正常业务逻辑处理，或者在业务低峰期重新打回 MQ。

为什么转存比"直接扩容消费者"更可靠

扩容消费者的前提是下游扛得住。如果堆积根因就是下游数据库/第三方接口慢，加 10 倍消费者只会把下游彻底打垮，故障范围从 MQ 扩散到整个系统。

转存方案把"接收"和"处理"解耦：接收侧极速清空队列解除 Broker 风险，处理侧用可控速率慢慢消化，不会把故障传导给下游。

第三步：事后防堆积 ​

措施做法作用
队列长度上限x-max-length + x-overflow: reject-publish堆积到阈值直接拒绝生产，保护 Broker
惰性队列x-queue-mode: lazy消息直接落盘不占内存，扛得住百万级堆积
监控告警Ready > 1 万持续 5 分钟告警分钟级发现，不等到故障
消费耗时监控单条处理 P99 埋点提前发现消费端变慢
java
// 声明惰性队列:专门用于可能大量堆积的场景
@Bean
public Queue orderPointQueue() {
    return QueueBuilder.durable("order.point.queue")
            .withArgument("x-queue-mode", "lazy")      // 惰性队列
            .withArgument("x-max-length", 500000)      // 最多 50 万条
            .withArgument("x-overflow", "reject-publish")
            .build();
}

x-overflow 的两个值差别巨大

  • drop-head（默认）：超限时丢弃队头最老的消息，生产者无感知 —— 悄悄丢消息。
  • reject-publish：超限时拒绝新消息，生产者会收到 nack，可以感知并落库补偿。

要求不丢消息的业务，必须显式设成 reject-publish。

判断口诀

Ready 高 → 消费不动，加并发或加实例。

Unacked 高 → 消费者卡死，抓线程栈查阻塞。

堆积百万级 → 先转存清空队列，再离线消化。

事后必加惰性队列 + 长度上限 + 告警，三件套缺一不可。

八、集群与运维篇 ​

8.1 普通集群、镜像队列与 Quorum Queue ​

概念

RabbitMQ 的集群能力经历了三代演进：

  • 普通集群（Classic Cluster）：节点间只同步元数据，队列数据只在一个节点上。
  • 镜像队列（Mirrored Queue）：队列数据在多个节点间复制，3.8 之后官方已不推荐，4.0 彻底移除。
  • Quorum Queue（仲裁队列）：基于 Raft 共识算法的新一代高可用队列，3.8+ 官方推荐方案。

📌 单独澄清：RabbitMQ 集群默认不等于高可用

很多人搭了三节点集群就以为万事大吉。普通集群模式下，队列的实际数据只存在于创建它的那个节点上，其他节点只是存了"这个队列在节点 A 上"这条元数据。节点 A 一挂，队列和里面的消息全部不可用 —— 集群还在，但业务已经崩了。

集群解决的是扩展连接数和吞吐量，高可用必须靠镜像队列或 Quorum Queue 额外实现。

普通集群：元数据同步，数据不同步 ​

text
          Client 连 node2,但队列在 node1
                      │
      ┌───────────────┼───────────────┐
      ▼               ▼               ▼
  ┌────────┐     ┌────────┐     ┌────────┐
  │ node1  │     │ node2  │     │ node3  │
  │ ✅实际  │◀────│ 仅元数据│     │ 仅元数据│
  │  队列  │ 转发 │(知道在  │     │(知道在  │
  │  数据  │      │ node1) │     │ node1) │
  └────────┘     └────────┘     └────────┘
       │
       ✖ node1 宕机 → 队列彻底不可用,消息全部无法访问
同步内容是否跨节点同步
交换机、绑定关系、vhost、用户权限✅ 全量同步到所有节点
队列的定义（名字、参数）✅ 同步
队列里的消息实体❌ 只在宿主节点

镜像队列：数据复制，但有脑裂隐患 ​

镜像队列给队列指定了 master + 若干 mirror，消息写入 master 后同步到 mirror。master 挂了，某个 mirror 提升为新 master。

bash
# 通过 policy 开启镜像:所有 order. 开头的队列,镜像到 2 个节点
docker exec -it rabbitmq rabbitmqctl set_policy ha-order "^order\." \
  '{"ha-mode":"exactly","ha-params":2,"ha-sync-mode":"automatic"}' \
  --apply-to queues

镜像队列为什么被官方废弃

同步是"尽力而为"，没有共识算法保证。 网络分区时两边各自选出 master，分区恢复后 RabbitMQ 会直接丢弃其中一侧的全部消息（取决于 cluster_partition_handling 策略），这是设计上的硬伤。

此外 ha-sync-mode: automatic 在队列很大时会导致新 mirror 全量同步，期间整个队列阻塞不可用，生产上经常引发雪崩。

RabbitMQ 3.8 引入 Quorum Queue 后就不再推荐镜像队列，4.0 版本已完全移除。新项目不要再用。

Quorum Queue：基于 Raft 的强一致方案 ​

Quorum Queue 用 Raft 共识算法管理副本，写入需要超过半数副本确认才算成功，天然避免脑裂。

java
@Bean
public Queue orderPayQueue() {
    return QueueBuilder.durable("order.pay.queue")
            .quorum()                              // 声明为 Quorum Queue
            .withArgument("x-quorum-initial-group-size", 3)  // 3 副本
            .withArgument("x-delivery-limit", 5)   // 重投 5 次后自动进死信
            .build();
}
text
   写入 M ──▶ Leader(node1)
                 │ 复制
        ┌────────┴────────┐
        ▼                 ▼
   Follower(node2)   Follower(node3)
        │                 │
        └──── 2/3 确认 ───┘  ──▶ 回 confirm 给生产者

   node1 挂掉 → node2/node3 发起选举,数据零丢失

x-delivery-limit 是 Quorum Queue 独有的宝藏参数

经典队列遇到"毒消息"（反复消费失败反复 requeue）会无限循环，把 CPU 跑满。Quorum Queue 的 x-delivery-limit 会记录每条消息的投递次数，超限后自动投进死信队列，不需要业务代码自己计数。

这是从镜像队列迁移到 Quorum Queue 最直接的收益之一。

三种模式全面对照 ​

维度普通集群镜像队列Quorum Queue
数据冗余无有（异步复制）有（Raft 多数派）
节点宕机队列不可用mirror 提升为 master自动选举新 Leader
脑裂安全不涉及❌ 可能丢消息✅ Raft 保证
消息零丢失❌⚠️ 不保证✅ 保证（多数派确认）
性能最高中略低于镜像（Raft 开销）
支持 TTL / 优先级✅✅⚠️ 不支持消息优先级，TTL 支持有限
官方状态保留4.0 已移除推荐

Quorum Queue 的限制：不支持消息优先级，不支持惰性队列模式

如果业务强依赖 x-max-priority（优先级队列），目前只能继续用 Classic Queue。另外 Quorum Queue 本身就是磁盘优先的设计，不需要也不支持 x-queue-mode: lazy。

副本数建议设奇数（3 或 5），偶数副本在 Raft 里无法提升容错能力还浪费资源。

判断口诀

只要高吞吐不要高可用 → 普通集群。

新项目做高可用 → 一律 Quorum Queue，副本数设 3。

老项目还在用镜像队列 → 排期迁移，4.0 升级前必须换掉。

需要消息优先级 → 只能 Classic Queue，另想高可用办法。

8.2 流控、内存告警与磁盘告警 ​

概念

流控（Flow Control）：当 RabbitMQ 发现某个环节处理不过来时，主动降低上游的发送速率，是一种反压（back-pressure）机制。

RabbitMQ 有三层保护，从轻到重依次是：Credit Flow（内部通道级限速）→ 内存告警 → 磁盘告警。触发后的共同表现是：生产者的 basicPublish 被阻塞，连接进入 blocked 状态。

📌 单独澄清：生产者"卡住"不是网络问题，是 Broker 在保护自己

线上最常见的误判：生产者发消息时线程 hang 住几十秒，运维去查网络、查 DNS、查连接池，查了半天没问题。实际上是 Broker 内存或磁盘触发了告警，主动把所有生产者连接 block 了。

判断方法只需一条命令：

bash
# 如果有输出,说明这些连接正在被 Broker 阻塞
docker exec -it rabbitmq rabbitmqctl list_connections name state
# state 为 blocked / blocking 即为流控中
state 值含义
running正常
blocking告警已触发，连接即将被阻塞（还能发完手头这条）
blocked已被阻塞，basicPublish 调用会一直挂起

内存告警：默认内存超 40% 就触发 ​

bash
# 查看当前内存水位和阈值
docker exec -it rabbitmq rabbitmqctl status | grep -A 5 memory

# 查看当前阈值设置
docker exec -it rabbitmq rabbitmqctl environment | grep vm_memory

# 临时调整为物理内存的 60%(重启失效)
docker exec -it rabbitmq rabbitmqctl set_vm_memory_high_watermark 0.6

# 也可以设绝对值,比如 4GB
docker exec -it rabbitmq rabbitmqctl set_vm_memory_high_watermark absolute 4GB

永久配置写进 rabbitmq.conf：

ini
# 内存高水位:物理内存的 60%
vm_memory_high_watermark.relative = 0.6

# 分页阈值:到达高水位的 50% 时开始把消息换页到磁盘
vm_memory_high_watermark_paging_ratio = 0.5

# 磁盘可用空间低于 5GB 触发磁盘告警
disk_free_limit.absolute = 5GB

容器环境下内存阈值的大坑

RabbitMQ 默认读取的是宿主机的物理内存，不是容器的 memory limit。容器限制 2GB，宿主机 64GB，那么 40% 水位 = 25.6GB —— 永远不会触发内存告警，而是直接被 OOMKilled。

Docker 部署时必须显式设置绝对值：

yaml
environment:
  RABBITMQ_VM_MEMORY_HIGH_WATERMARK: "1GB" # 容器限制 2GB 时设 1GB
deploy:
  resources:
    limits:
      memory: 2G

磁盘告警：比内存告警更凶险 ​

磁盘可用空间低于 disk_free_limit 时，RabbitMQ 会阻塞所有生产者，且这个阻塞会持续到磁盘空间恢复为止。

text
磁盘剩余 < 50MB(默认阈值)
        │
        ▼
  所有 publisher 被 block
        │
        ▼
  业务线程池被 publish 调用耗尽
        │
        ▼
  整个应用无响应 ← 故障从 MQ 扩散到业务系统

磁盘被占满的常见原因：

原因排查方式
消息大量堆积落盘rabbitmqctl list_queues name messages 找最大的队列
日志文件无限增长检查 /var/log/rabbitmq/，配置 logrotate
死信队列没人消费死信队列也会持续堆积，必须有兜底消费者
容器 overlay 层撑爆docker system df 看镜像/容器占用

Credit Flow：最轻量的内部限速 ​

即使没触发内存磁盘告警，RabbitMQ 内部也会做通道级限速。当某个队列的写入进程处理不过来时，会向上游 channel 进程"收回信用额度"，层层传导到生产者连接。

bash
# 查看某个连接是否处于 credit flow 状态
docker exec -it rabbitmq rabbitmqctl list_connections name state channels

Credit Flow 的表现是发送速率明显下降但不完全卡死，通常意味着：单队列写入成为瓶颈，应该考虑拆分队列（参见 7.3 顺序消费 的分片思路）。

三层保护对照 ​

保护层触发条件影响范围恢复方式
Credit Flow内部进程处理不过来单个连接降速下游跟上后自动恢复
内存告警内存 > vm_memory_high_watermark全部生产者阻塞消费掉消息 / 调高阈值
磁盘告警磁盘可用 < disk_free_limit全部生产者阻塞清理磁盘 / 扩容

生产者侧必须做的防护：设置发送超时

Broker block 住之后，convertAndSend 会无限期挂起，直接拖垮业务线程池。必须给 RabbitTemplate 设超时：

java
@Bean
public RabbitTemplate rabbitTemplate(ConnectionFactory cf) {
    RabbitTemplate template = new RabbitTemplate(cf);
    // 等待 confirm 的超时时间
    template.setReplyTimeout(5000);
    // 开启 Publisher Confirm 后,配合超时快速失败
    template.setMandatory(true);
    return template;
}

更彻底的做法是监听 ConnectionBlockedListener，感知到 blocked 后直接降级（消息落库走补偿），不要硬等。

判断口诀

生产者卡住先查 list_connections state，blocked 就是流控。

容器部署必须设 RABBITMQ_VM_MEMORY_HIGH_WATERMARK 绝对值。

磁盘告警比内存告警更难恢复，监控必须提前到 20% 余量。

调高阈值只是应急，根因永远是消息堆积，回去看 7.4。

8.3 Prefetch 调优：决定消费吞吐量的关键一环 ​

概念

Prefetch（预取数量）：Broker 一次性推送给单个消费者、但尚未收到 ack 的消息上限。对应 AMQP 的 basic.qos(prefetchCount)。

prefetch = N 的含义是：这个消费者的 unacked 消息数达到 N 之后，Broker 就不再给它推新消息，直到它 ack 掉一些。

📌 单独澄清：prefetch 只在手动 ack 模式下生效

acknowledge-mode: none（自动确认）下，消息一推出去就视为已确认，unacked 恒为 0，prefetch 永远不会触发限制 —— 设了也等于没设，Broker 会把消息无限推给消费者，直接把内存撑爆。

prefetch 是手动 ack 模式的专属参数，这也是生产上必须用 manual 或 auto（Spring 的容器级确认）而不是 none 的原因之一。

prefetch 过大和过小分别是什么后果 ​

text
prefetch = 1（过小）
消费者: [处理M1]      ──ack──▶ Broker ──推M2──▶ [处理M2]
             ↑                              ↑
          等待网络往返                  每条都要一个 RTT
结果:吞吐量被网络延迟锁死,CPU 大量空转

prefetch = 1000（过大）
消费者A: 一口气拿走 1000 条 ──▶ 内存占用飙升
消费者B: 队列空了,无消息可消费 ──▶ 负载严重倾斜
A 宕机 ──▶ 1000 条消息全部 requeue,延迟毛刺
设置吞吐量内存占用负载均衡宕机影响面
prefetch = 1很低最低最均衡最小（只影响 1 条）
prefetch 适中（20~100）高可控良好可控
prefetch 过大（> 500）高高倾斜大
prefetch = 0（无限制）高可能 OOM极度倾斜极大

Spring Boot 的默认 prefetch 是 250，不是 1

spring.rabbitmq.listener.simple.prefetch 默认值为 250。如果你的单条消息体积很大（比如几百 KB 的报文），250 条就是几十 MB 常驻内存，再乘以 concurrency 的线程数，很容易把堆打满。

大消息场景必须手动调低到 10~20。

怎么算出合理的 prefetch 值 ​

经验公式：

text
prefetch ≈ (单条消息处理耗时 + 网络 RTT) / 单条消息处理耗时 × 安全系数

举例:处理耗时 50ms,RTT 2ms
prefetch ≈ (50 + 2) / 50 × 2 ≈ 2 ~ 5 就够了

举例:处理耗时 1ms(纯内存操作),RTT 2ms
prefetch ≈ (1 + 2) / 1 × 2 ≈ 6 ~ 20

核心直觉：处理越快、prefetch 要越大（否则网络往返成为瓶颈）；处理越慢、prefetch 要越小（否则消息白白堆在消费者本地，别的消费者却闲着）。

业务类型单条耗时推荐 prefetch
纯内存计算、日志上报< 1ms100 ~ 250
普通数据库写入5 ~ 50ms20 ~ 50
调用第三方接口、发短信100ms ~ 1s1 ~ 5
大文件处理、报表生成> 5s1

prefetch 与 concurrency 的乘积关系 ​

真正决定内存占用的不是 prefetch 本身，而是 prefetch × concurrency × 单条消息大小。

text
prefetch=250, concurrency=10, 单条 100KB
→ 250 × 10 × 100KB = 250MB 常驻堆内存 ❌

prefetch=20, concurrency=10, 单条 100KB
→ 20 × 10 × 100KB = 20MB ✅

concurrency 的两个值不要设成一样

concurrency 是初始线程数，max-concurrency 是弹性上限。设成一样等于关闭了弹性伸缩，低峰期白白占着线程。

合理做法是 concurrency 设日常负载够用的值，max-concurrency 设峰值值，让容器自动扩缩。

判断口诀

处理慢（调外部接口）→ prefetch 设 1~5。

处理快（纯内存）→ prefetch 设 100~250。

消息体积大 → 无条件调低，看 prefetch × concurrency × 消息大小。

自动 ack 模式下 prefetch 无效，生产永远用 manual 或 auto。

8.4 核心监控指标与告警阈值 ​

概念

RabbitMQ 的监控不是"看 CPU 和内存"那么简单。真正有价值的指标分三层：

  • 队列层：堆积量、消费速率、消费者数 —— 发现业务侧问题
  • 节点层：内存、磁盘、文件句柄、Erlang 进程数 —— 发现 Broker 侧问题
  • 连接层：连接数、channel 数、blocked 状态 —— 发现客户端侧问题

📌 单独澄清：messages_ready 和 message_stats.publish_details.rate 要配合看

单看 Ready 数量会误判。双十一期间 Ready 涨到 5 万可能完全正常（消费速率同样很高，队列在快速流转）；而平时 Ready 稳定在 3000 不动，反而说明消费者可能已经卡死了。

真正的健康标志是：消费速率 (ack rate) ≈ 生产速率 (publish rate)，且 Ready 在波动中回落。只有 Ready 单调递增且 ack rate 趋近 0 时才是真故障。

9.1 高频报错速查手册 ​

概念

RabbitMQ 的报错有一个显著特点：异常信息往往出现在 channel 关闭的回调里，而不是你调用的那一行。因为 AMQP 协议大量操作是异步的，Broker 发现问题后会主动关闭 channel 并带上 reply-code 和 reply-text。

所以排查第一步永远是：把完整的 channel 关闭日志翻出来，找 reply-code。

报错一：PRECONDITION_FAILED - inequivalent arg ​

text
Channel shutdown: channel error; protocol method:
#method<channel.close>(reply-code=406, reply-text=PRECONDITION_FAILED -
inequivalent arg 'x-message-ttl' for queue 'order.timeout.queue' in vhost '/mall':
received '60000' but current is '30000')
项说明
根因代码里声明的队列参数，与 Broker 上已存在的队列参数不一致
常见触发改了 TTL / 死信交换机 / durable 后重启应用
错误做法改回原参数绕过去（技术债越滚越大）
正确做法停掉消费者 → 确认队列已消费完 → 删除旧队列 → 重启应用重建
bash
# 确认队列当前的真实参数
docker exec -it rabbitmq rabbitmqctl list_queues name arguments

# 确认没有消息后删除(有消息时会报错,防误删)
docker exec -it rabbitmq rabbitmqctl delete_queue order.timeout.queue --if-empty

队列参数是不可变的，这是 RabbitMQ 的设计

队列一旦创建，x-message-ttl、x-dead-letter-exchange、durable 等参数就永久固定，没有任何"修改队列参数"的 API。想改只能删了重建。

所以生产环境上线前必须把队列参数定稿，否则后续每次改动都要走删队列流程，有消息丢失风险。更稳妥的做法是用版本后缀：order.timeout.queue.v2。

vhost 写错了spring.rabbitmq.virtual-host 是不是 /mall

报错四：消息发出去了但队列里没有 ​

这不是报错，是最难排查的静默丢失。按以下顺序排查：

text

② 绑定关系对吗?          → list_bindings

④ 开 mandatory + ReturnCallback 了吗?  → 没开就是静默丢弃
⑤ 队列有 TTL 吗?         → 消息可能已过期进死信
⑥ 队列有 x-max-length 吗? → 可能被 drop-head 丢了

  source_name destination_name routing_key

排查静默丢失的终极手段：加一个兜底队列

给交换机额外绑一个 # 通配的兜底队列（Topic 交换机），或者配置 alternate-exchange 备用交换机。所有路由不到的消息会进到兜底队列，打开管理台一看就知道 routingKey 到底是什么。

java
@Bean
public DirectExchange orderDirectExchange() {
    return ExchangeBuilder.directExchange("order.direct.ex")
            .durable(true)
            .alternate("unrouted.ex")   // 路由不到就进备用交换机
            .build();
}

报错六：消息体反序列化失败 ​

text
org.springframework.amqp.support.converter.MessageConversionException:
failed to resolve class name. Class not found [com.old.pkg.OrderMsg]

生产者和消费者的实体类包路径不一致，而 Jackson2JsonMessageConverter 默认会把类全限定名写进 header 的 __TypeId__。解决方式是配置类型映射或消费端显式指定目标类型：

java
@Bean
public Jackson2JsonMessageConverter messageConverter() {
    Jackson2JsonMessageConverter converter = new Jackson2JsonMessageConverter();
    DefaultJackson2JavaTypeMapper mapper = new DefaultJackson2JavaTypeMapper();
    // 忽略生产端写入的 __TypeId__,强制用消费端的类
    mapper.setTypePrecedence(Jackson2JavaTypeMapper.TypePrecedence.INFERRED);
    converter.setJavaTypeMapper(mapper);
    return converter;
}

判断口诀

406 PRECONDITION_FAILED → 队列参数冲突，删队列重建。

404 NOT_FOUND → 交换机/队列不存在，先确认 vhost。

403 ACCESS_REFUSED → vhost 权限没授，权限按 vhost 独立。

消息没进队列 → 查绑定、查 routingKey、开 mandatory。

反序列化失败 → 配 TypePrecedence.INFERRED。

9.2 面试问答与加分点 ​

Q5：为什么不推荐镜像队列了？ ​

加分答法：镜像队列的同步是"尽力而为"，没有共识算法，网络分区时两侧各自选 master，恢复后会直接丢弃一侧的全部消息；而 Quorum Queue 基于 Raft，写入需多数派确认，天然防脑裂。而且镜像队列的 ha-sync-mode: automatic 在大队列全量同步时会阻塞整个队列，生产上常引发雪崩。RabbitMQ 4.0 已彻底移除镜像队列。

容易答错的细节题 ​

问题容易答错的点正确答案
死信队列需要手动创建吗？以为会自动创建需要，DLX 和死信队列必须显式声明并绑定
搭了集群就高可用了吗？以为是不是，普通集群只同步元数据，队列数据在单节点
routingKey 和 bindingKey 一样吗？以为是同一个东西发送时用 routingKey，绑定时用 bindingKey，只有 Topic 的 bindingKey 支持通配
prefetch 自动 ack 下生效吗？以为生效不生效，unacked 恒为 0
消息持久化后就一定不丢吗？以为一定不丢不一定，落盘有缓冲窗口，宕机仍可能丢
Quorum Queue 支持优先级吗？以为支持不支持 x-max-priority

问"怎么保证不丢" → 答三环节 + 本地消息表兜底。

问"选哪个 MQ" → 答设计定位差异 + 举一个用错的例子。

十一、面试问答 ​

为什么要用 MQ？它解决了什么问题？ ​

三个主要好处：

  • 异步：用户点下单，我只要把"下单成功"这件事记下来就能返回，发短信、加积分、推报表这些慢活交给 MQ 后面慢慢干。接口响应从几百毫秒降到几十毫秒，用户体验直接不一样。
  • 解耦：以前新增一个下游（比如加个风控、加个推荐），得回头改下单代码。现在上游只管喊一声"订单创建了"，谁想听谁订阅，上游完全不用管有几个听众。
  • 削峰填谷：秒杀一瞬间进来十万请求，数据库扛不住。请求先堆在队列里，下游按自己的节奏一秒处理一千条，慢慢消化，数据库不会被打挂。用户看到的是"排队中"，而不是"系统繁忙"。

另外还有些顺带的好处：同一份数据多方消费（广播），做分布式事务的最终一致（本地消息表 ＋ MQ），以及延迟任务（订单 30 分钟不付款自动关单）。

但引入 MQ 不是白拿的：

  • 多了一个可能挂的环节：MQ 挂了，整条链路就跟着瘫，所以必须做集群、做高可用。
  • 麻烦事变多了：丢消息、重复消费、顺序乱了、积压、幂等、对账、补偿，全都要自己处理。
  • 一致性从"立刻一致"变成"最终一致"：中间那几秒数据是不一致的，业务上必须能接受。

所以别什么都往 MQ 里塞。像"下单成功必须代表库存已扣"，这种强一致的逻辑就老老实实同步做，或者先预占库存；硬丢给 MQ 只会让问题从"慢"变成"错"。

RabbitMQ 的工作模型是怎样的？ ​

AMQP 模型：Producer → Exchange →（Binding ＋ RoutingKey）→ Queue → Consumer。

生产者只发给交换机，不直接发给队列；交换机根据绑定关系和路由键决定投递到哪些队列；队列才是消息真正的存储单元。

组件作用
Connection客户端与 Broker 之间的 TCP 长连接，创建成本高，应复用
Channel建立在 Connection 上的逻辑信道，真正的操作单位，轻量、可多路复用
Exchange消息路由器，不存储消息
Binding交换机与队列的绑定关系，可带路由键
Queue消息存储单元，消费者从队列拉/收消息
Virtual Host逻辑隔离单位，不同 vhost 的交换机、队列互不可见，常用于多环境/多业务隔离

为什么要有 Channel？ TCP 连接的创建和销毁开销大，高并发下不能一个线程一个连接。RabbitMQ 用 Channel 做多路复用：一个 Connection 上开多个 Channel，每个线程用自己的 Channel（Channel 非线程安全，不能多线程共享）。

交换机有哪几种类型？分别什么场景？ ​

类型路由规则场景
direct路由键完全匹配按类型精准分发，如 order.create
topic路由键模糊匹配，* 匹配一个单词，# 匹配零或多个单词按业务域订阅，如 order.#
fanout忽略路由键，广播给所有绑定队列一份消息多方消费，性能最好
headers按消息 headers 属性匹配（x-match=all/any），性能差很少用

补充：

  • 默认交换机（空名 direct）：所有队列都会以队列名作为路由键自动绑定到它，所以 channel.basicPublish("", "queueName", ...) 能直投队列。
  • 交换机不存储消息：找不到匹配队列时消息被静默丢弃，除非开启 mandatory 并处理 Return 回退。
  • 同一队列的多个消费者是竞争消费，不是广播；要让多个服务都收到，必须建多个队列绑定同一交换机。

常用的工作模式有哪些？ ​

  • 简单模式：一个生产者一个消费者，走默认交换机。
  • Work Queue（工作队列）：多个消费者竞争消费同一队列，实现负载分担；配合 prefetch 实现"能者多劳"，否则默认轮询会让慢消费者积压。
  • Publish/Subscribe：fanout 交换机广播给多个队列。
  • Routing（路由）：direct 交换机按路由键精准投递。
  • Topics（主题）：topic 交换机按通配符订阅。
  • RPC 模式：请求带 replyTo 回调队列和 correlationId，服务端处理后回写结果队列。
  • Publisher Confirms：发布确认模式，保证消息到达 Broker。

消费者是推模式还是拉模式？prefetch 有什么用？ ​

  • RabbitMQ 默认是 Broker 主动推送（basic.consume），实时性好；也支持 basic.get 主动拉取，但每次一个请求、性能差，不推荐在生产循环使用。
  • 推模式的风险是压垮消费者，所以用 prefetch（basic.qos，预取数量） 做流控：限制每个消费者未确认消息的上限，达到上限就不再推送。

举个例子：设置 prefetch=5，表示"手里最多攥 5 条没确认的消息"。

  1. 消费者启动，Broker 一次推 5 条过来（unacked = 5）。
  2. 这时即使队列里还有 1000 条，Broker 也不再推第 6 条。
  3. 消费者处理完第 1 条、basicAck 确认（unacked 变成 4），Broker 立刻补推 1 条，又回到 5。
  4. 如果消费者卡住了（慢 SQL、下游超时），一条都不确认，unacked 一直是 5，Broker 就彻底停推 —— 消息全留在队列里，等它恢复或者被其他消费者分走。

所以 prefetch 本质是"确认一条，才发一条"的滑动窗口。它还顺带实现了能者多劳：处理快的消费者确认得快、拿到的消息就多；处理慢的消费者窗口一直占满，Broker 自然不给它派活，比默认的轮询分发合理得多。

另外要注意：忘记 ACK 的话 unacked 会一直攒到 prefetch 上限，然后这个消费者就彻底不收消息了，线上表现就是"消费者在线但完全不消费"。

  • prefetch 取值权衡：
    • 太大：消息都囤在一个消费者本地，负载不均，宕机后大量消息重投，内存压力大。
    • 太小（如 1）：吞吐下降（等确认的网络往返），但顺序性和公平分发最好。
    • 一般：处理快、消息小 → 取大一些（几十到几百）；处理慢、消息大 → 取小（1~10）。

RabbitMQ 有哪几种队列类型？怎么选？ ​

  1. 经典队列 Classic

    • 集群节点之间只同步元数据（队列名称、参数），消息本体不同步。
    • 消息只存在队列所在的那一个节点。
    • 节点宕机 → 消息丢失。
    • 适合：临时队列、需要优先级/lazy 队列的场景。

  2. 仲裁队列 Quorum（Raft）

    • 元数据、消息都会同步到所有副本节点。
    • 写入规则：严格大于一半的副本落盘成功，才算写入成功（多数派）
      • 3 副本：≥2 成功
      • 5 副本：≥3 成功
    • 👉 推荐奇数副本；偶数副本不会提升容错，浪费机器。
    • Leader 负责读写，Leader 挂了，剩余副本自动选新 Leader，消息不丢。
    • 适合：订单、支付等核心业务，要求消息不丢。

  3. Stream 流队列

    • 同样 Raft 多副本、消息同步、多数派写入。
    • 区别：ack 不会删除消息，只是记录 offset 消费进度，支持历史消息回放。
    • 适合：埋点、事件日志、需要重放的场景。

消息优先级怎么实现？ ​

声明队列时加 x-max-priority（如 10），发送消息时设置 priority，优先级高的消息先被消费。

注意点：

  • 优先级只在队列堆积时才有意义，队列是空的、消息来了就被消费，先发的照样先走。
  • 已被 prefetch 到消费者本地的消息不会再重排，所以要配合较小的 prefetch。
  • 优先级范围不要设太大（官方建议 1~10），每个优先级在内部是一个独立的子队列，太多会吃内存。
  • 仲裁队列不支持优先级，需要优先级时只能用经典队列，或者干脆按优先级拆成"高优队列 / 普通队列"两条链路——这也是生产里更常见的做法。

如何保证消息不丢失？ ​

消息有三个可能丢失的环节，要分别加固，再用重试、告警、补偿兜底。

环节措施注意事项
生产者 → Broker开启发布确认（Publisher Confirm）确认只代表 Broker 接管了消息，不代表消费成功；确认超时结果未知，重试要幂等
Exchange → Queue开启 mandatory 并处理 Return 回退Confirm 成功不代表进了目标队列；无法路由的消息要落库单独处理
Broker 存储交换机、队列、消息都持久化；关键业务用仲裁队列多副本队列持久化 ≠ 消息持久化；单机持久化挡不住磁盘损坏
Broker → 消费者业务处理成功后手动 ACK失败要有限重试，超限转死信队列并告警，不能无限 requeue

如果还涉及数据库和消息的一致性，就用本地消息表；消费者必须幂等，因为重投一定会带来重复。

发布确认（Confirm）和事务（Transaction）有什么区别？ ​

  • AMQP 事务（txSelect/txCommit/txRollback）：同步阻塞，每条消息都要等 commit 往返，吞吐下降明显（能降一个数量级），基本不用。
  • 发布确认（Publisher Confirm）：Broker 收下消息后异步回 ack/nack，支持三种用法：
    • 单条同步确认（waitForConfirms）：简单但阻塞，吞吐低。
    • 批量确认：攒一批再等确认，吞吐高，但 nack 时要整批重发，不知道具体哪条失败。
    • 异步确认（推荐）：注册 ConfirmCallback，用 deliveryTag 关联未确认消息表，收到 ack 删除、nack 重发；Spring 中用 CorrelationData 关联业务 ID。

发布确认的坑：

  • ack=true 只代表 Broker 接管了消息，持久化消息还可能在刷盘前丢（所以关键业务要仲裁队列）。
  • ack=false（nack）表示 Broker 内部出错，需要重发。
  • 超时/连接断开 = 结果未知，不能当成失败直接重发，否则会产生重复，必须让消费端幂等。

mandatory 和备份交换机（Alternate Exchange）是干什么的？ ​

两者都用来处理"消息无法路由到任何队列"的情况：

  • mandatory=true：路由失败时 Broker 把消息通过 Return 回退给生产者，生产者注册 ReturnCallback 落库 / 告警 / 修复后重发。

  • 备份交换机：在声明交换机时指定 alternate-exchange，路由失败的消息自动转到备份交换机（通常是 fanout ＋ 一个兜底队列）。无需生产者处理，运维更省事。

  • 二者同时配置时，消息会进备份交换机，不会再触发 Return 回调。

  • 注意：mandatory 只能发现"完全没有队列可路由"，不能发现"某个预期订阅的队列不存在"。所以队列和绑定必须提前部署并校验。

消息持久化了就一定不丢吗？ ​

不一定：

  • 三件套都要开：交换机 durable、队列 durable、消息 deliveryMode=2（持久化）。队列持久化只保证队列元数据不丢，不等于消息持久化。
  • 持久化是异步刷盘：消息先进 page cache，还没落盘时断电仍会丢。
  • 真正的解决办法是用仲裁队列：消息复制并持久化到多数副本后才返回确认，容忍单节点宕机/磁盘损坏。
  • 仲裁队列本身就持久化消息，不依赖消息持久化标记（但建议仍设置，便于兼容经典队列）。

**一致的权衡：越可靠越慢。**金融类业务用仲裁队列＋发布确认，日志类可以牺牲可靠性换吞吐。

消费者确认（ACK）有哪几种模式？ ​

模式行为风险
RabbitMQ 原生 autoAck=true投递即确认，不等业务处理业务失败/宕机直接丢消息
Spring AMQP AUTO监听方法正常返回后由容器确认，抛异常则按重试/拒绝配置处理与原生 autoAck 完全不同，别混淆
Spring AMQP MANUAL业务代码处理成功后调用 basicAck忘记 ACK 会导致 unacked 堆积、消费者被堵死
NONE不确认等同于原生自动确认

拒绝消息的两个方法：

  • basicNack(tag, multiple, requeue)：支持批量拒绝。

  • basicReject(tag, requeue)：只能拒绝一条。

  • requeue=true 会重新入队（失败消息立刻重投容易形成忙循环），requeue=false 则丢弃或进入死信队列。

  • 异步处理不能提前确认：如果监听方法内部把任务丢给线程池就返回，容器会立刻确认消息，异步任务失败/宕机就丢了。要么同步处理，要么先把任务可靠落库再确认。

三、重复消费与幂等 ​

消息为什么会重复消费？ ​

  • 消费者业务已执行完，ACK 之前宕机/连接断开，Broker 把 unacked 消息重新投递。
  • 生产者发送成功但没收到确认（网络超时），重试产生两条消息。
  • 消费失败后 requeue 重投、死信重放、人工补偿投递。

结论：RabbitMQ 只能保证 at-least-once（至少一次），"恰好一次"必须靠消费端幂等实现。

如何保证消费幂等？ ​

  1. 业务唯一标识 ＋ 数据库唯一约束（首选）
    • 选稳定的业务标识：支付流水号，或"订单号＋事件类型＋业务版本"。同一订单的创建、支付、退款不能共用一个去重键；生产者重试要保持事件 ID 不变。
    • 多服务共用消费记录表时，唯一键要带消费者业务标识，否则 A 服务的消费记录会误拦 B 服务。
    • 消费记录和业务更新要放在同一个事务里，避免"已标记消费但业务没做完"。
  2. 状态机 / 条件更新
    • 例如 update order set status='已支付' where id=? and status='待支付'，用受影响行数判断是否首次处理。
    • 同库操作放一个事务；外部扣款、发短信不受本地事务保护，要靠下游幂等键＋结果核实，超时不能直接当失败。
  3. Redis 去重 / 分布式锁（辅助）
    • 能挡掉大部分重复、控制并发，但要考虑 key 过期、Redis 宕机，以及"打标记"和"业务操作"无法原子提交。
    • 分布式锁不等于幂等：锁释放后重复消息照样能再执行一次，关键业务必须有数据库兜底。

常见误区："先查询，不存在再插入"不安全：两个消费者可能同时查到不存在然后都插入。必须靠唯一约束或原子条件更新兜底。

消息的三种投递语义是什么？ ​

语义含义实现方式代价
at-most-once最多一次，可能丢自动确认、发送不重试会丢消息，只适合日志、埋点
at-least-once至少一次，可能重发布确认＋手动 ACK ＋重试必须幂等，生产最常用
exactly-once恰好一次at-least-once ＋ 消费端业务去重RabbitMQ 本身不提供，靠业务实现

四、死信队列与延迟消息 ​

什么是死信？消息在什么情况下会变成死信？ ​

死信（Dead Letter）是无法被正常消费的消息。队列通过 x-dead-letter-exchange（必填）和 x-dead-letter-routing-key（选填，不填则沿用原路由键）指定死信交换机，消息成为死信后由原队列自动转发到死信交换机。

三种进入死信的情况：

  • 被拒绝：basicNack / basicReject 且 requeue=false。
  • 消息过期：消息 TTL 或队列 TTL 到期且未被消费。
  • 队列满：队列达到 x-max-length / x-max-length-bytes，默认从队头丢弃最老的消息成为死信。

死信队列的典型用途：

  • 异常兜底：重试超限的消息进死信队列，落库＋告警，人工或定时任务补偿重放。
  • 延迟队列：TTL ＋ 死信实现延时投递。

死信队列的坑：

  • 死信队列也可能堆积，必须配监控告警，否则等于把问题藏起来。
  • 死信队列不要再配死信，容易形成循环。
  • 重放死信前要确认消费端幂等，否则补偿会造成重复扣款这类事故。

RabbitMQ 怎么实现延迟队列？ ​

方案一：TTL ＋ 死信队列（DLX）

消息进入一个没有消费者的"延迟队列"，设置 TTL；到期成为死信，转发到死信交换机，真正的消费者监听死信队列。

缺点（队头阻塞）：队列 TTL 是统一的；如果给单条消息设置不同 TTL，RabbitMQ 只检查队头消息是否过期。前面一条 30 分钟的消息没过期，后面 5 秒的消息也不会被投递。所以这种方案只适合固定延迟时长（如统一 30 分钟超时关单），每种时长建一个队列。

方案二：延迟消息插件（推荐）

安装 rabbitmq_delayed_message_exchange 插件，声明 x-delayed-message 类型交换机，发消息时在 header 里设置 x-delay（毫秒）。消息先存在交换机里，到期才路由到队列，支持任意延迟时间、不存在队头阻塞。

缺点：延迟中的消息存放在交换机的内部存储里，延迟消息量很大时有内存和性能压力，且插件版本要与 Broker 版本匹配。

方案三：业务层方案

对于超长延迟（几天、几个月）或海量定时任务，更稳妥的做法是任务落库 ＋ 定时扫描到期任务，或用 Redis ZSet 按到期时间排序轮询，MQ 只负责投递。

延迟队列常见的业务场景有哪些？ ​

订单超时未支付自动关闭并释放库存、下单后 N 分钟未支付发提醒、预约提醒、支付结果延时对账补偿（第一次查不到结果就延迟 5s/30s/5min 重试）、任务超时检测。

五、顺序消费、积压与重试 ​

如何保证消息的顺序消费？ ​

消息乱序有两个来源：一个队列被多个消费者并发消费，以及同一消费者多线程处理 / 失败重投。

  • 单队列单消费者单线程：最简单，但吞吐低，只适合顺序要求强、量小的场景；prefetch=1 可以减少重投造成的乱序。
  • 按业务键拆队列（推荐）：按订单号 / 用户 ID 哈希路由到不同队列（routingKey = "order." + hash(orderId) % N），每个队列一个消费者。保证局部有序，整体仍能并发，和 Kafka 按 key 分区思路一致。
  • 消费端排序兜底：消息里带版本号或时间戳，用条件更新丢弃旧消息（update ... where version < #{version}），或状态机只接受合法流转，这样即使乱序也不会把数据改错。
  • 单活消费者（Single Active Consumer）：队列声明 x-single-active-consumer=true，同一时刻只有一个消费者在消费，其余作为备份；消费者宕机后自动切换到下一个。既保证顺序，又不丢高可用，比"只部署一个消费者实例"更可靠。

注意失败重试会破坏顺序：一条消息 nack 重入队后会排到队尾，顺序就断了。顺序敏感的场景，重试要在消费者内部有限重试（不 requeue），失败后让该业务键的后续消息暂停或直接进死信人工介入，不能简单重投。

消息积压怎么处理？ ​

先定位原因：生产端突增流量，还是消费端变慢（慢 SQL、下游超时、死锁、线程阻塞），还是消费者挂了/一直报错 requeue 形成忙循环。看管理台的 Ready、Unacked 和 ack 速率：Unacked 很高说明消费慢或忘了 ACK；Ready 很高、消费者为 0 说明消费端挂了。

紧急处理（临时扩容）

  1. 消费端能力不足：水平扩容消费者（队列消费者数 ≤ 队列分片数才有效，单队列加消费者有效；若受顺序约束则受限）。
  2. 原队列分片不够：临时写一个"搬运"消费者，只做不处理业务、快速转发，把消息分发到新建的多个队列，再用多组消费者并行处理。
  3. 可降级的场景：先把积压消息快速落库（或转存到新队列），恢复链路后离线慢慢消费。
  4. 允许丢弃的消息（如过期的推送、日志）：直接设置 TTL 或清空队列，先保链路可用。

根治

  • 优化消费逻辑：批量处理、去掉慢 SQL、下游调用加超时和熔断。
  • 调大 prefetch 与消费并发（concurrency），但要和下游承载能力匹配。
  • 生产端限流、把非核心消息降级。
  • 配置队列长度上限 ＋ 死信兜底，避免无限堆积把 Broker 内存/磁盘打满。
  • 加监控告警：队列深度、消费速率、unacked 数、消费耗时 P99。

消费失败应该怎么重试？ ​

  • 不要用 requeue=true 无限重投：消息立刻回到队列又马上被消费，形成 CPU 忙循环，还会拖垮整个队列。
  • 区分异常类型：参数错误、反序列化失败这类不可恢复异常直接进死信，重试没有意义；网络抖动、下游超时这类可恢复异常才重试。
  • 本地有限重试 ＋ 退避：Spring AMQP 用 RetryTemplate 做 3 次指数退避；超限后由 RepublishMessageRecoverer 把消息转发到异常交换机 / 死信队列，并带上失败原因。
  • 延迟重试：用延迟队列实现 1min → 5min → 30min 的阶梯重试，比立即重试更容易成功。
  • 死信队列的消息要落库 ＋ 告警，提供后台重放入口，重放前确保幂等。

怎么提升 RabbitMQ 的吞吐？ ​

  • 复用连接、一线程一 Channel，不要每次发送都新建连接。
  • 发布确认用异步模式，不要用 waitForConfirms 逐条阻塞，更不要用 AMQP 事务。
  • 批量消费 / 批量入库：攒一批消息一次写库，再批量 ACK（multiple=true），显著降低网络往返。
  • 合理调大 prefetch 和消费者并发数（Spring 的 concurrency / max-concurrency），上限取决于下游承载能力。
  • 消息体精简：只传业务 ID 和必要字段，用 JSON 而不是 Java 原生序列化。
  • 减少不必要的持久化：非关键消息可以不持久化换吞吐；关键消息该持久化就持久化，别为性能牺牲可靠性。
  • 拆队列：按业务/分片拆成多个队列，避免单队列成为瓶颈（单队列由单个 Erlang 进程处理，有天花板）。

RabbitMQ 消息会过期丢失吗？TTL 怎么设置？ ​

  • 队列 TTL（x-message-ttl）：队列里所有消息统一过期时间。

  • 消息 TTL（发送时设置 expiration）：单条消息的过期时间，二者同时存在取较小值。

  • 队列空闲过期（x-expires）：队列在指定时间内没有消费者、未被使用就自动删除。

  • 过期消息如果配了死信交换机就进死信队列，没配就直接丢弃。

  • 生产建议：核心业务消息不要设置 TTL（或设得足够长），否则一次积压就会把消息全部过期丢掉。只对本身有时效性的消息（验证码推送、实时行情）设置 TTL。

六、集群与高可用 ​

RabbitMQ 集群有哪几种模式？ ​

  • 普通集群（默认）：节点间同步元数据（交换机、队列、绑定、vhost），但队列的消息只存在创建它的那个节点。连到其他节点时请求会被转发到宿主节点。优点是可以水平扩展连接和吞吐，缺点是宿主节点宕机，该队列的消息不可用（未持久化则丢失）。
  • 镜像队列（Mirrored，经典队列高可用）：主队列 ＋ 从队列副本，消息同步到镜像节点，主节点挂了从节点升主。缺点是全量同步、网络开销大，极端网络分区下可能丢消息；RabbitMQ 3.8 后被仲裁队列取代，4.0 已移除。
  • 仲裁队列（Quorum，推荐）：基于 Raft 协议，写入多数副本成功才算成功，Leader 挂了自动选举新 Leader，数据一致性和可用性都更好。要求副本数为奇数（一般 3 或 5），只能容忍少数节点故障。
  • 流队列（Stream）：也有多副本复制，适合超大吞吐和消息回溯。

前面接 HAProxy / Nginx / VIP 做负载均衡和故障转移，客户端配置多个地址实现自动重连。

脑裂（网络分区）怎么处理？ ​

网络分区是节点之间失去通信，不等于节点已经宕机。处理的核心是：失去多数派时，宁可暂时停止服务，也不要让两侧分别写入后再强行合并。

RabbitMQ 的 cluster_partition_handling 配置用于处理集群网络分区：

  • ignore：不主动处理分区，分区可能长期存在，恢复后通常需要人工介入；不应把它理解为“继续服务且数据一定安全”。
  • pause_minority：处于少数派的节点暂停服务，恢复通信后再恢复。适合至少三个节点的部署；两节点集群失联时双方都不是多数派，可能同时暂停。
  • pause_if_all_down：指定一组参考节点，无法联系任何参考节点时暂停。适用于特定拓扑，需要明确参考节点故障时的行为，不能随意照抄配置。
  • autoheal：检测到分区恢复后选择一个分区作为胜出方，重启另一侧节点。它不是无损合并，两侧独立产生的数据可能丢失，不适合把数据正确性放在第一位的业务。

生产建议：关键业务优先使用仲裁队列，跨故障域部署副本，确保多数副本可互通。仲裁队列通过 Raft 决定哪一侧能写入，失去多数副本时停止可用；集群分区策略不能替代队列的多数派复制保证。

RabbitMQ 的流控和内存、磁盘告警有什么区别？ ​

三者都会让生产端变慢，但触发原因和处理范围不同：

  • 流控（flow）：Broker 内部处理速度跟不上上游，逐级施加背压，连接可能在 flow 与正常状态之间切换。先检查队列写入、磁盘性能和消费能力，不要只盯着网络。
  • 内存告警：内存使用超过配置水位，发布连接被阻塞，防止继续占用资源。水位是告警阈值，不是严格的内存上限。
  • 磁盘告警：可用磁盘低于安全阈值，阻塞发布，避免磁盘耗尽。即使主要使用非持久化消息，也不能忽视磁盘，因为 Broker 仍可能进行磁盘操作。

资源告警在集群范围传播，一个节点告警就可能影响整个集群的发布。通常消费仍可继续，用于释放积压；生产和消费尽量使用不同连接，避免发布连接阻塞拖住消费确认。

处理顺序：看告警类型 → 查队列 Ready / Unacked 和增长速率 → 排查慢消费者、磁盘与容量 → 限流或扩容。不要仅靠调高水位掩盖资源不足。

七、工程实践与选型 ​

RabbitMQ、Kafka、RocketMQ 怎么选？ ​

产品更擅长的场景选型时要考虑的代价
RabbitMQ业务异步解耦、任务分发、复杂路由、低延迟消费副本与队列规模影响资源开销，历史回放需明确使用 Stream 等方案
Kafka日志采集、事件流、数据管道、大吞吐与回放顺序通常限定在分区内，复杂业务路由和失败重试需额外设计
RocketMQ业务消息、事务消息、顺序消息与延时消息功能与限制依赖具体版本，仍需做好幂等、补偿和运维

不能只背“哪个更快”。先明确峰值吞吐、延迟、是否需要回放、顺序范围、延时时长，以及团队已有的运维能力，再做压测。事务消息也不意味着 MQ 替你完成数据库与所有下游的原子事务。

数据库事务与发消息怎么保持一致？ ​

两个操作不在同一个事务里：先提交数据库再发消息，可能提交后发送失败；先发消息再提交数据库，可能消费者已经执行但数据库回滚。

常用方案：本地消息表（Outbox） ＋ 可靠投递 ＋ 消费幂等。

  1. 在同一个数据库事务内写业务数据和待发送消息，保证一起提交或一起回滚。
  2. 后台任务或 CDC 读取待发送记录，发布到 MQ；使用 Confirm，并处理无法路由的 Return。
  3. 明确确认成功后更新投递状态；失败则记录原因，有限重试并告警。
  4. 消费端用业务唯一键去重，最好把“去重记录”和“业务更新”放在同一个数据库事务里。
  5. 用定时对账发现长时间未投递或业务状态不一致的记录，提供补偿入口。

确认成功后、更新消息表前宕机，仍可能重复发送，因此 Outbox 保证的是最终可靠投递，不是天然 exactly-once。HTTP 发货、扣款等外部副作用还需要对方支持幂等键，不能仅靠本地去重表保证。

生产中 RabbitMQ 有哪些容易踩的坑？ ​

  1. 只开持久化就认为绝不会丢：关键消息要组合持久化、Confirm、正确路由、手动 ACK 和业务补偿；副本可靠性还取决于队列类型。
  2. 失败就无限 requeue：毒消息形成忙循环。区分可恢复异常，有限退避重试，超限进死信并告警。
  3. ACK 时机不对：业务提交前 ACK 会丢业务；ACK 丢失则可能重投，必须幂等。批量 ACK 不能确认尚未处理完成的消息。
  4. 连接与 Channel 使用混乱：不要每条消息建连接，也不要随意跨线程共享 Channel；使用连接池或框架提供的通道管理，监控资源泄漏。
  5. prefetch 和并发盲目拉满：消息大量变成 Unacked，下游数据库先被打垮。按消费耗时、消息大小和下游容量压测调整。
  6. 把死信当作处理完成：死信只是隔离失败消息，必须落库、告警、补偿，并控制重放速度；同时检查死信转发的可靠性保证。
  7. 忽略版本与队列类型差异：镜像队列在 4.0 已移除；仲裁队列的优先级能力随版本演进，不能沿用“永远不支持”的结论。经典队列单条消息 TTL 的队头阻塞、重入队后的消息位置、插件存储与副本行为都要按实际版本核实，不能把经验当作所有版本的协议保证。
