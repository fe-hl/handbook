一、线程基础篇 ​

1.1 线程和进程的区别？ ​

  • 进程是操作系统分配资源的基本单位；线程是操作系统调度和执行的基本单位。一个进程可以包含多个线程。
  • 资源共享：进程拥有独立的地址空间；同一进程中的线程共享堆、全局变量等资源，但各自拥有独立的栈、程序计数器等。
  • 开销：进程创建、销毁和切换通常开销更大；线程通常更轻量。
  • 通信：进程间需要通过管道、共享内存、套接字等方式通信；线程可以直接访问共享数据，但需要同步机制保证线程安全。
  • 隔离性：进程之间隔离性较强；线程之间隔离性较弱，一个线程发生严重错误可能导致整个进程崩溃。

1.2 并行和并发有什么区别？ ​

  • 并发：多个任务在同一段时间内交替推进，不一定同时执行。例如单核 CPU 通过时间片切换执行多个线程。
  • 并行：多个任务在同一时刻真正同时执行，通常需要多个 CPU 核心。例如两个核心分别执行两个线程。

一句话总结：并发强调一段时间内处理多个任务，并行强调同一时刻执行多个任务。

1.3 创建线程的四种方式 ​

共有四种方式可以创建线程，分别是：继承 Thread 类、实现 Runnable 接口、实现 Callable 接口、线程池创建线程。

详细创建方式参考下面代码：

① 继承 Thread 类

java
public class MyThread extends Thread {
    @Override
    public void run() {
        System.out.println("MyThread...run...");
    }

    public static void main(String[] args) {
        // 创建 MyThread 对象
        MyThread t1 = new MyThread();
        MyThread t2 = new MyThread();

        // 调用 start 方法启动线程
        t1.start();
        t2.start();
    }
}

② 实现 Runnable 接口

java
public class MyRunnable implements Runnable {
    @Override
    public void run() {
        System.out.println("MyRunnable...run...");
    }

    public static void main(String[] args) {
        // 创建 MyRunnable 对象
        MyRunnable mr = new MyRunnable();

        // 创建 Thread 对象
        Thread t1 = new Thread(mr);
        Thread t2 = new Thread(mr);

        // 调用 start 方法启动线程
        t1.start();
        t2.start();
    }
}

③ 实现 Callable 接口

java
public class MyCallable implements Callable<String> {
    @Override
    public String call() throws Exception {
        System.out.println("MyCallable...call...");
        return "OK";
    }

    public static void main(String[] args) throws ExecutionException, InterruptedException {
        // 创建 MyCallable 对象
        MyCallable mc = new MyCallable();

        // 创建 FutureTask 对象
        FutureTask<String> ft = new FutureTask<>(mc);

        // 创建 Thread 对象
        Thread t1 = new Thread(ft);
        Thread t2 = new Thread(ft);

        // 调用 start 方法启动线程
        t1.start();

        // 调用 ft 的 get 方法获取执行结果
        String result = ft.get();

        // 输出
        System.out.println(result);
    }
}

④ 线程池创建线程

java
public class MyExecutors implements Runnable {
    @Override
    public void run() {
        System.out.println("MyRunnable...run...");
    }

    public static void main(String[] args) {
        // 创建线程池对象
        ExecutorService threadPool = Executors.newFixedThreadPool(3);
        threadPool.submit(new MyExecutors());

        // 关闭线程池
        threadPool.shutdown();
    }
}

1.4 Runnable 和 Callable 有什么区别？ ​

  1. Runnable 接口的 run 方法没有返回值；Callable 接口的 call 方法有返回值，是个泛型，和 Future、FutureTask 配合可以用来获取异步执行的结果。
  2. Callalbe 接口支持返回执行结果，需要调用 FutureTask.get() 得到。此方法会阻塞主进程的继续往下执行，如果不调用不会阻塞。
  3. Runnable 不能直接外抛受检异常，但可以外抛运行时异常；Callable 两者都可以外抛。通过 submit() 提交任务时，异常会保存到 Future，调用 get() 时再以 ExecutionException 抛出。

1.5 线程的 run() 和 start() 有什么区别？ ​

  • start：用来启动线程，通过该线程调用 run 方法执行，start 方法只能被调用一次。
  • run：封装了要被线程执行的代码，可以被调用多次，如果直接调用就是普通方法的调用。

1.6 线程包括哪些状态，状态之间是如何变化的？ ​

  1. 线程包括哪些状态

    新建（NEW）、可运行（RUNNABLE）、阻塞（BLOCKED）、等待（WAITING）、计时等待（TIMED_WAITING）、终止（TERMINATED）。

  2. 线程状态之间是如何变化的

    • 创建线程对象是新建状态。
    • 调用了 start() 方法转变为可执行状态。
    • 线程获取到了 CPU 的执行权，执行结束是终止状态。
    • 在可执行状态的过程中，如果没有获取 CPU 的执行权，可能会切换其他状态：
      • 如果没有获取锁（synchronized 或 lock）进入阻塞状态，获得锁再切换为可执行状态。
      • 如果线程调用了 wait() 方法进入等待状态，其他线程调用 notify() 唤醒后可切换为可执行状态。
      • 如果线程调用了 sleep(50) 方法，进入计时等待状态，到时间后可切换为可执行状态。

1.7 新建 T1、T2、T3 三个线程，如何保证它们按顺序执行？ ​

在多线程中有多种方法让线程按特定顺序执行，你可以用线程类的 join() 方法在一个线程中启动另一个线程，另外一个线程完成该线程继续执行。

代码举例：

为了确保三个线程的顺序你应该先启动最后一个（T3 调用 T2，T2 调用 T1），这样 T1 就会先完成而 T3 最后完成。

java
public class JoinTest {
    public static void main(String[] args) {
        // 创建线程对象
        Thread t1 = new Thread(() -> System.out.println("t1"));

        Thread t2 = new Thread(() -> {
            try {
                // 加入线程 t1，只有 t1 线程执行完毕以后，再次执行该线程
                t1.join();
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
            System.out.println("t2");
        });

        Thread t3 = new Thread(() -> {
            try {
                // 加入线程 t2，只有 t2 线程执行完毕以后，再次执行该线程
                t2.join();
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
            System.out.println("t3");
        });

        // 启动线程
        t1.start();
        t2.start();
        t3.start();
    }
}

1.8 notify() 和 notifyAll() 有什么区别？ ​

  • notifyAll：唤醒所有 wait 的线程。
  • notify：只随机唤醒一个 wait 线程。
java
public class WaitNotify {
    static boolean flag = false;
    static Object lock = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (lock) {
                while (!flag) {
                    System.out.println(Thread.currentThread().getName() + "...wating...");
                    try {
                        lock.wait();
                    } catch (InterruptedException e) {
                        e.printStackTrace();
                    }
                }
                System.out.println(Thread.currentThread().getName() + "...flag is true");
            }
        });

        Thread t2 = new Thread(() -> {
            synchronized (lock) {
                while (!flag) {
                    System.out.println(Thread.currentThread().getName() + "...wating...");
                    try {
                        lock.wait();
                    } catch (InterruptedException e) {
                        e.printStackTrace();
                    }
                }
                System.out.println(Thread.currentThread().getName() + "...flag is true");
            }
        });

        Thread t3 = new Thread(() -> {
            synchronized (lock) {
                System.out.println(Thread.currentThread().getName() + " hold lock");
                lock.notifyAll();
                flag = true;
                try {
                    Thread.sleep(2000);
                } catch (InterruptedException e) {
                    e.printStackTrace();
                }
            }
        });

        t1.start();
        t2.start();
        t3.start();
    }
}

1.9 Java 中 wait 和 sleep 方法的不同？ ​

✅ sleep ​

Thread.sleep(5000)

  1. 交出 CPU 执行权，线程进入阻塞。
  2. 不会释放持有的 synchronized 锁。
  3. 结果：想要竞争同一把锁的线程拿不到锁，被阻塞；不竞争这把锁的线程可以正常执行。

✅ wait ​

lock.wait()（必须在 synchronized 内调用）

  1. 交出 CPU 执行权，线程进入等待队列。
  2. 释放当前 lock 对象锁。
  3. 结果：其他线程可以竞争拿到这把 lock 锁。
  4. 补充：被 notify/notifyAll 唤醒后，不能立刻执行，需要重新竞争锁，拿到锁才继续运行。

代码示例：

java
public class WaitSleepCase {
    static final Object LOCK = new Object();

    public static void main(String[] args) throws InterruptedException {
        sleeping();
    }

    private static void illegalWait() throws InterruptedException {
        LOCK.wait();
    }

    private static void waiting() throws InterruptedException {
        Thread t1 = new Thread(() -> {
            synchronized (LOCK) {
                try {
                    get("t").debug("waiting...");
                    LOCK.wait(5000L);
                } catch (InterruptedException e) {
                    get("t").debug("interrupted...");
                    e.printStackTrace();
                }
            }
        }, "t1");
        t1.start();

        Thread.sleep(100);
        synchronized (LOCK) {
            main.debug("other...");
        }
    }

    private static void sleeping() throws InterruptedException {
        Thread t1 = new Thread(() -> {
            synchronized (LOCK) {
                try {
                    get("t").debug("sleeping...");
                    Thread.sleep(5000L);
                } catch (InterruptedException e) {
                    get("t").debug("interrupted...");
                    e.printStackTrace();
                }
            }
        }, "t1");
        t1.start();

        Thread.sleep(100);
        synchronized (LOCK) {
            main.debug("other...");
        }
    }
}

1.10 如何停止一个正在运行的线程？ ​

有三种方式可以停止线程：

  • 使用退出标志，使线程正常退出，也就是当 run 方法完成后线程终止。
  • 使用 stop 方法强行终止（不推荐，方法已作废）。
  • 使用 interrupt 方法中断线程。

代码参考如下：

① 使用退出标志，使线程正常退出。

java
public class MyInterrupt1 extends Thread {
    volatile boolean flag = false; // 线程执行的退出标记

    @Override
    public void run() {
        while (!flag) {
            System.out.println("MyThread...run...");
            try {
                Thread.sleep(3000);
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        }
    }

    public static void main(String[] args) throws InterruptedException {
        // 创建 MyThread 对象
        MyInterrupt1 t1 = new MyInterrupt1();
        t1.start();

        // 主线程休眠 6 秒
        Thread.sleep(6000);

        // 更改标记为 true
        t1.flag = true;
    }
}

② 使用 stop 方法强行终止

java
public class MyInterrupt2 extends Thread {
    volatile boolean flag = false; // 线程执行的退出标记

    @Override
    public void run() {
        while (!flag) {
            System.out.println("MyThread...run...");
            try {
                Thread.sleep(3000);
            } catch (InterruptedException e) {

            }
        }
    }

    public static void main(String[] args) throws InterruptedException {

        MyInterrupt2 t1 = new MyInterrupt2();
        t1.start();

        // 主线程休眠 2 秒
        Thread.sleep(6000);

        // 调用 stop 方法

    }
}

二、并发原理篇 ​

2.1 谈谈 synchronized 关键字的底层原理？ ​

synchronized 是 JVM 层面实现的锁，锁信息存在对象头里的 Mark Word，锁是单向升级的：无锁 → 偏向锁 → 轻量级锁 → 重量级锁，只能升级，不能降级。

偏向锁 ​

适合几乎没有竞争的场景。Mark Word 里面会记录第一个拿到锁的线程 ID。这个线程再来获取锁的时候，直接比对线程 ID，不需要 CAS，直接拿到锁，开销最小。当有第二个线程来抢锁的时候，偏向锁就会被撤销，升级成轻量级锁。

轻量级锁 ​

适合少量竞争、线程交替执行的情况。线程会在自己的栈帧里面创建 Lock Record 锁记录，然后用 CAS 尝试把对象的 Mark Word 指向自己栈里的锁记录，CAS 成功就代表拿到锁。如果 CAS 失败，线程会自旋，循环重试抢锁，不会被操作系统阻塞，省去用户态内核态切换的开销。如果自旋很多次还是抢不到锁，竞争变激烈，就升级成重量级锁。

重量级锁 ​

升级之后，Mark Word 里面存一个指针，指向 Monitor 监视器。Monitor 里面有三部分：Owner、EntryList、WaitSet。

  • Owner：就是当前持有锁的线程，同一时刻只能有一个。
  • EntryList：线程过来抢锁，如果锁已经被占用，抢不到，就进入 EntryList 排队阻塞。
  • WaitSet：如果已经拿到锁的线程调用了 wait()，就会释放锁，进到 WaitSet 里面休眠，等待唤醒。

当别的线程调用 notify 或者 notifyAll 的时候，会把 WaitSet 里的线程捞出来，放到 EntryList，重新参与锁竞争，不能直接拿到锁。等 Owner 执行完同步代码释放锁，再唤醒 EntryList 里的线程去抢锁。重量级锁会让线程在内核态阻塞，上下文切换开销比较大。

2.2 谈谈 JMM（Java 内存模型） ​

JMM 是 Java 虚拟机规范中所定义的一种内存模型，描述了 Java 程序中各种变量（线程共享变量）的访问规则，以及在 JVM 中将变量存储到内存和从内存中读取变量这样的底层细节。

特点：

  1. 所有的共享变量都存储于主内存（计算机的 RAM）。这里所说的变量指的是实例变量和类变量。不包含局部变量，因为局部变量是线程私有的，因此不存在竞争问题。
  2. 每一个线程还存在自己的工作内存，线程的工作内存保留了被线程使用的变量的工作副本。
  3. 线程对变量的所有操作（读、写）都必须在工作内存中完成，而不能直接读写主内存中的变量；不同线程之间也不能直接访问对方工作内存中的变量，线程间变量的值的传递需要通过主内存完成。

2.3 CAS 你知道吗？ ​

CAS 全称 Compare And Swap（比较并交换），属于乐观锁，无锁操作，底层依靠 CPU 硬件指令保证【比较+交换】原子性。

三个要素：内存当前值 V、预期值 A、新值 B。

逻辑：只有 V == A，才将 V 更新为 B；否则更新失败。

举例：初始 V=10。A 线程读到 A=10，想改成 20；B 线程抢先把 V 改成 15。A 执行 CAS 对比，10≠15，更新失败。失败不会阻塞线程，通常自旋重试。

经典问题：ABA 问题。V=10，A 读到预期 10 准备改 20；B 先改成 15，又改回 10。A 对比发现等于预期，正常更新，感知不到中间被修改过。

✅ 解决：追加版本号，值+版本一起校验（AtomicStampedReference）。

优缺点：

  • ✅ 优点：无阻塞、无上下文切换，低竞争场景性能高。
  • ❌ 缺点：存在 ABA 问题；自旋竞争激烈时耗 CPU；仅支持单个变量原子更新。

2.3.1 CAS 底层实现 ​

Java 中 CAS 调用 Unsafe 的 native 方法，底层是 CPU 的 cmpxchg 指令，硬件保证原子性；多核环境依靠 MESI 缓存一致性协议，自旋就是循环重试 CAS。

2.3.2 乐观锁和悲观锁 ​

  • 乐观锁（代表：CAS）：乐观认为并发冲突很少发生，不加锁。操作前先校验数据有没有被别人修改过，冲突了就重试。
  • 悲观锁（代表：synchronized）：悲观认为并发冲突大概率会发生，操作前直接上锁，锁住资源，其他线程阻塞等待，释放锁后别人才能操作。

对比一句话：

乐观锁：先干活，冲突了重试；悲观锁：先上锁，干完活再放行。

2.4 谈谈你对 volatile 的理解 ​

volatile 修饰共享变量，两大核心语义：保证可见性、禁止指令重排，不能保证原子性。

1. 保证可见性 ​

一个线程修改 volatile 变量，会立刻刷入主内存；其他线程读取时，会清空本地工作内存副本，从主内存读取最新值。

经典例子：循环标记 stop。不加 volatile，JIT 即时编译优化，把 while(!stop) 优化成 while(true)，循环永远停不下来；加上 volatile 就会禁用这个优化，感知到 stop 的变化。

2. 禁止指令重排 ​

通过内存屏障实现，限制 CPU、编译器乱序：

  • volatile 写：前面的读写不能重排到 volatile 写之后。
  • volatile 读：后面的读写不能重排到 volatile 读之前。

经典场景：DCL 双重检查锁，就是靠 volatile 防止指令重排，避免拿到半初始化对象。
小技巧：volatile 写尽量放在代码末尾；volatile 读尽量放在代码开头。

补充 ​

❌ 不保证原子性，像 i++ 这种读改写复合操作，volatile 解决不了，需要 CAS 或者 synchronized。

2.5 什么是 AQS？ ​

AQS 全称 AbstractQueuedSynchronizer，抽象队列同步器，是 Java 里构建锁、同步工具的基础框架，Java 代码实现。

和 synchronized 对比 ​

  • synchronized：关键字，C++ 底层实现，悲观锁，自动加锁释放锁。
  • AQS：Java 层框架，悲观锁，需要手动获取、释放锁；支持更多扩展能力。

AQS 核心三要素 ​

  1. volatile 修饰的 state：同步状态，用来记录资源。比如 ReentrantLock 里 0 代表无锁，大于 0 代表已占用（可重入时 state 会累加）。
  2. FIFO 双向等待队列：抢锁失败的线程进入队列排队，类似 Monitor 的 EntryList。
  3. 条件变量 Condition：支持多条件等待唤醒，类似 Monitor 的 WaitSet。

工作流程 ​

线程抢资源时，先通过 CAS 自旋修改 state：

  • CAS 成功：抢到锁，持有资源。
  • CAS 失败：进入双向队列阻塞排队。

公平锁 / 非公平锁（ReentrantLock） ​

  • 非公平锁（默认）：新来线程直接尝试抢锁，和队列里排队的线程一起竞争。
  • 公平锁：新来线程先入队，只有队列头部的线程才有资格获取锁。

常见实现类 ​

ReentrantLock、Semaphore、CountDownLatch。

2.6 ReentrantLock 的实现原理 ​

ReentrantLock 是可重入锁，底层基于 AQS + CAS 实现。

和 synchronized 对比优势 ​

  • ✅ 支持可中断：抢锁过程中可以被中断。
  • ✅ 支持超时获取锁：到时间拿不到就放弃。
  • ✅ 支持公平锁 / 非公平锁（默认非公平）。
  • ✅ 支持多个 Condition 条件变量。
  • ✅ 和 synchronized 一样，支持锁重入。

底层原理 ​

内部有 Sync 抽象类，继承 AQS；有两个子类：

  • NonfairSync：非公平锁（默认）。
  • FairSync：公平锁。

抢锁流程：

  1. 线程通过 CAS 修改 AQS 的 state；成功，state=1，把 exclusiveOwnerThread 设置为当前线程，拿到锁。
  2. 重入：同一个线程再次加锁，state ++。
  3. CAS 失败：线程进入 AQS 双向等待队列阻塞。
  4. 锁释放：state--，state 归 0 后，清空持有线程，唤醒队列里等待的线程。

公平锁 vs 非公平锁：

  • 非公平锁（默认）：新来线程直接 CAS 抢锁，和队列里线程竞争，吞吐量更高。
  • 公平锁：新来线程先入队，只有队首线程才有资格抢锁，性能低一点。

注意 ​

必须手动 lock()、unlock()，一般在 finally 里面释放锁，避免死锁。

2.7 synchronized 和 Lock 有什么区别？ ​

synchronized 是关键字，JVM 实现，自动释放；Lock 是接口，Java 实现，手动释放。二者都是悲观锁、可重入。Lock 支持公平锁、可中断、超时、多条件变量。低竞争下 synchronized 优化后性能不错，竞争激烈 Lock 性能更好。

2.8 如何进行死锁诊断？ ​

当程序出现了死锁现象，我们可以使用 jps 和 jstack、jconsole、VisualVM。

2.9 ConcurrentHashMap ​

ConcurrentHashMap 是线程安全、高性能的 Map。

JDK 1.7 ​

结构：Segment 数组 + HashEntry 数组 + 单向链表。

  • Segment 默认 16 个，长度固定不能扩容，每个 Segment 自带 ReentrantLock。
  • 先 hash 定位 Segment，再定位 HashEntry 数组下标。
  • 锁粒度：锁住整个 Segment，分段锁，并发度最高 16。

JDK 1.8（重点） ​

结构：数组 + 链表 / 红黑树，和 HashMap 1.8 一致。
并发安全方案：CAS + synchronized。

  • 新增节点：先用 CAS。
  • 链表/树修改：synchronized 只锁当前桶的头节点。

✅ 优点：锁粒度变小，hash 不冲突就不竞争，并发性能更高。

2.10 导致并发程序出现问题的根本原因是什么？ ​

并发程序出问题，根源就是三大特性被破坏：原子性、可见性、有序性。

  1. 原子性：一组操作不可拆分，要么全部执行成功，要么都不执行。i++ 是读-改-写三步，不是原子操作，多线程下会出错。解决：synchronized、Lock、CAS。
  2. 可见性：一个线程修改共享变量，其他线程不能及时看到最新值（工作内存副本问题）。解决：volatile、synchronized、Lock。
  3. 有序性：CPU、编译器会指令重排，单线程结果不变，但多线程逻辑错乱。解决：volatile（内存屏障）。

一句话总结：多线程并发 bug，就是原子性、可见性、有序性这三点没有保证。

三、线程池篇 ​

3.1 线程池的核心参数与执行流程 ​

ThreadPoolExecutor 7 个核心参数：

  1. corePoolSize：核心线程数。
  2. maximumPoolSize：最大线程数（核心+救急线程总和）。
  3. keepAliveTime：救急线程空闲存活时间。
  4. unit：存活时间单位。
  5. workQueue：阻塞任务队列，核心线程满了任务进队列排队。
  6. threadFactory：线程工厂，自定义线程名称、守护线程等。
  7. handler：拒绝策略。

执行流程（口诀：核心→队列→救急线程→拒绝） ​

  1. 新来任务，核心线程没满，新建核心线程执行。
  2. 核心线程已满，队列没满，任务放入阻塞队列。
  3. 队列已满，总线程数 < 最大线程数，创建救急线程执行。
  4. 队列满、线程也达到最大，触发拒绝策略。

举个例子 ​

corePoolSize = 2 核心线程
maximumPoolSize = 5 最大线程
队列容量 = 3 容量

  • 任务 1、2：开 2 个核心线程（核心满了）。
  • 任务 3、4、5：放进队列（队列放满）。

现在：核心线程 2 个都在忙，队列 3 个任务塞满。再来任务 6：

  • 不能开核心（核心已满）。
  • 不能入队（队列已满）。
  • 判断：当前线程数 (2) < 最大 (5) → 创建救急线程执行任务 6。

再来任务 7：当前线程数 3 < 5 → 再开救急线程。直到线程总数达到 5，再来任务就触发拒绝策略。

四种拒绝策略 ​

  • AbortPolicy（默认）：直接抛异常。
  • CallerRunsPolicy：交给提交任务的调用线程执行。
  • DiscardOldestPolicy：丢弃队列最老任务，加入当前新任务。
  • DiscardPolicy：直接丢弃当前任务，不抛异常。

补充：救急线程空闲超过 keepAliveTime，会被回收；核心线程默认不会回收。

3.2 线程池中有哪些常见的阻塞队列？ ​

  1. ArrayBlockingQueue：数组实现、有界，FIFO；读写共用一把锁。
  2. LinkedBlockingQueue：链表实现，默认无界（可指定容量变成有界），FIFO；读、写两把独立锁，并发性能更高。
  3. DelayedWorkQueue：延迟优先级队列，任务带时间，只有到期才能取出，ScheduledThreadPool 用它。
  4. SynchronousQueue：不存任务，插入必须等另一个线程来取，相当于直接交接。

ArrayBlockingQueue vs LinkedBlockingQueue ​

  • ArrayBlockingQueue：数组、强制有界、一把锁，读写互斥。
  • LinkedBlockingQueue：链表、默认无界、头尾两把锁，读写可以并行，并发更好。

面试坑点：LinkedBlockingQueue 默认无界，如果用它做线程池队列，任务会无限堆积，救急线程永远不会创建，容易 OOM。

3.3 如何确定核心线程数？ ​

先区分任务类型：

  • CPU 密集型：大量计算，CPU 一直忙碌，比如数据运算、序列化转换。
    公式：N + 1（N = CPU 核心数）。
    多出来的 1 个线程，用来应对偶尔的线程停顿，充分利用 CPU，减少上下文切换。
  • IO 密集型：大量等待，比如数据库查询、网络请求、文件读写。
    公式：2N + 1（N = CPU 核心数）。
    IO 时 CPU 空闲，多开线程可以充分利用 CPU。

分场景参考 ​

  1. 高并发、任务执行时间短：CPU 核数+1，降低上下文切换开销。
  2. 并发不高、任务执行时间长：
    • IO 密集：2*CPU 核数+1。
    • CPU 密集：CPU 核数+1。
  3. 并发高、业务执行时间很长：重点不是调线程池，优先做缓存、拆分任务、扩容服务器；线程池参考上面 IO 密集配置。

3.4 线程池的种类有哪些？ ​

Executors 提供，底层基于 ThreadPoolExecutor。

线程池核心线程最大线程阻塞队列特点使用场景风险
newFixedThreadPool指定值和核心线程相等LinkedBlockingQueue（无界）线程数量固定，无救急线程，任务排队任务量已知、耗时稳定的任务无界队列，任务堆积 OOM
newSingleThreadExecutor11LinkedBlockingQueue（无界）只有一个工作线程，任务串行 FIFO 执行需要保证顺序执行的任务无界队列，任务堆积 OOM
newCachedThreadPool0Integer.MAX_VALUESynchronousQueue无核心线程，来任务就新建线程；空闲 60s 回收大量短耗时任务线程无限创建，突增流量导致 OOM、CPU 飙高
newScheduledThreadPool指定值Integer.MAX_VALUEDelayedWorkQueue支持延迟执行、周期定时执行定时任务、延迟任务最大线程无上限，大量定时任务会创建过多线程

口诀 ​

  • Fixed：固定线程，排队。
  • Single：单线程，串行。
  • Cached：来任务就开线程，空闲回收。
  • Scheduled：延迟、定时专用。

3.5 为什么不建议用 Executors 创建线程池？ ​

依据阿里 Java 开发手册：禁止使用 Executors 去创建线程池，推荐手动 new ThreadPoolExecutor()。

原因：Executors 封装好的线程池，隐藏了底层参数，存在 OOM 风险：

  1. newFixedThreadPool / newSingleThreadExecutor：底层队列是 LinkedBlockingQueue，默认容量 Integer.MAX_VALUE，属于无界队列。任务持续堆积，队列无限膨胀，占用大量内存，最终触发 OOM。
  2. newCachedThreadPool：maximumPoolSize = Integer.MAX_VALUE，线程上限几乎无限。短时间大量任务涌入，会疯狂新建线程，线程过多导致 CPU 耗尽、内存溢出 OOM。
  3. newScheduledThreadPool：maximumPoolSize = Integer.MAX_VALUE，同样线程上限无限制，大量定时任务时会创建大量线程，引发 OOM。

✅ 正确做法：手动实例化 ThreadPoolExecutor，自己指定 7 个核心参数，使用有界阻塞队列，设置合理拒绝策略，风险可控。

一句话口述：Executors 封装的线程池，要么队列无界，要么线程数量无上限，高并发下容易 OOM；所以阿里规范要求手动创建 ThreadPoolExecutor，使用有界队列。

3.6 线程使用场景问题 ​

场景 1：消息异步处理 ​

业务：订单创建成功之后，不要同步做一堆附属操作。
同步版本：下单 → 扣库存 → 生成订单 → 发短信、发微信模板消息、积分发放、日志记录、统计埋点 → 返回给前端。
问题：同步串行链路太长，接口 RT 高，其中一个附属操作失败还会影响下单主流程。
方案：下单主流程只做【创建订单、扣库存】，剩下通知、积分、埋点这些丢进线程池异步执行；也可以结合 MQ，消费者内部再用线程池并发消费。

适合：IO 密集型线程池，2N+1。

场景 2：批量导入/批量导出（Excel） ​

业务：后台运营批量导入上万条商品、会员数据；或者导出订单报表。
问题：单线程循环读解析 Excel，速度极慢，导出大文件容易超时。
方案：

  1. 先把 Excel 分片，拆成多个子任务；
  2. 线程池并行解析每一片数据、校验、入库；
  3. 全部分片执行完成后，汇总结果返回给前端。

⚠️ 注意：入库是数据库 IO，属于 IO 密集；还要控制并发，防止打垮 DB。

场景 3：多接口并行查询（接口聚合） ​

业务：一个首页/详情聚合接口，需要同时查用户信息、商品基础信息、库存、价格、营销券、评价。
同步：串行依次调用多个服务，总耗时 = 所有接口耗时相加。
方案：用线程池+CompletableFuture 并行调用多个 RPC/HTTP 接口，等全部结果返回再组装返回。
优势：总耗时≈最慢的那个接口耗时。

高频！面试最爱问 CompletableFuture 场景。

场景 4：定时任务 + 异步扫描（补偿任务） ​

业务：订单超时自动关闭、未支付订单回收库存、失效优惠券回收。
方案：ScheduledThreadPool 定时扫描待补偿数据；拿到一批待处理订单后，再丢普通线程池并发处理，避免单线程扫描处理太慢。
区分：定时调度是 ScheduledThreadPool，实际执行业务是普通线程池。

场景 5：文件处理、图片处理（异步） ​

业务：用户上传图片，需要同步压缩、水印、转格式、上传到 MinIO；或者视频切片、文档转 PDF。
问题：图片处理耗时久，同步上传会让前端等待超时。
方案：上传接口先返回成功，后台线程池异步做图片压缩、加水印、上传对象存储。

场景 6：日志、埋点上报（异步） ​

业务：用户行为埋点、操作日志。
不建议同步上报给日志服务，拖慢主接口；方案：线程池异步发送，或者用队列+线程池批量攒一批再上报，减少网络 IO 次数。

场景 7：大数据量统计、报表计算 ​

业务：夜间统计日订单、销售额、转化率，跑报表。
方案：分片读取历史数据，线程池并行计算，计算结果写入统计表；一般放在定时任务里执行，白天不跑，避免影响线上业务。

3.7 如何控制某个方法允许并发访问线程的数量？【面试背诵版】 ​

使用 JUC 的 Semaphore（信号量），用来控制同一时间访问资源/方法的线程数量，实现限流。

核心原理 ​

初始化时指定许可数量，代表最多允许多少线程同时执行：

  • acquire()：获取许可，许可数 -1；许可用完，线程阻塞等待。
  • release()：释放许可，许可数 +1；一般放在 finally，保证一定释放。

注意：许可一定要在 finally 里面释放，防止异常导致许可不释放、死锁。

示例代码 ​

java
public class SemaphoreCase {
    public static void main(String[] args) {
        // 最多允许 3 个线程同时执行
        Semaphore semaphore = new Semaphore(3);
        // 启动 10 个线程去竞争
        for (int i = 0; i < 10; i++) {
            new Thread(() -> {
                try {
                    semaphore.acquire(); // 获取许可
                } catch (InterruptedException e) {
                    e.printStackTrace();
                }
                try {
                    System.out.println("running...");
                    Thread.sleep(1000);
                    System.out.println("end...");
                } catch (InterruptedException e) {
                    e.printStackTrace();
                } finally {
                    semaphore.release(); // 释放许可，finally 保证一定会释放
                }
            }).start();
        }
    }
}

四、线程变量篇 ​

4.1 谈谈你对 ThreadLocal 的理解 ​

ThreadLocal 主要功能有两个，第一个是可以实现资源对象的线程隔离，让每个线程各用各的资源对象，避免争用引发的线程安全问题，第二个是实现了线程内的资源共享。

ThreadLocal 的底层原理实现吗？ ​

在 ThreadLocal 内部维护了一个一个 ThreadLocalMap 类型的成员变量。

当我们调用 set 方法，就是以 ThreadLocal 自己作为 key，资源对象作为 value，放入当前线程的 ThreadLocalMap 集合中。

当调用 get 方法，就是以 ThreadLocal 自己作为 key，到当前线程中查找关联的资源值。

当调用 remove 方法，就是以 ThreadLocal 自己作为 key，移除当前线程关联的资源值。

ThreadLocal 会导致内存溢出这个事情，了解吗？ ​

是应为 ThreadLocalMap 中的 key 被设计为弱引用，它是被动的被 GC 调用释放 key，不过关键的是只有 key 可以得到内存释放，而 value 不会，因为 value 是一个强引用。

在使用 ThreadLocal 时都把它作为静态变量（即强引用），因此无法被动依靠 GC 回收，建议主动的 remove 释放 key，这样就能避免内存溢出。

4.2 谈谈你对 volatile 的理解 ​

volatile 是一个关键字，可以修饰类的成员变量、类的静态成员变量，主要有两个功能。

第一：保证了不同线程对这个变量进行操作时的可见性，即一个线程修改了某个变量的值，这新值对其他线程来说是立即可见的，volatile 关键字会强制将修改的值立即写入主存。

第二：禁止进行指令重排序，可以保证代码执行有序性。底层实现原理是，添加了一个内存屏障，通过插入内存屏障禁止在内存屏障前后的指令执行重排序优化。
