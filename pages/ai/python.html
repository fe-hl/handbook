变量与常用类型 ​

python
name = "小明"             # str：文本
age = 18                  # int：整数
height = 1.75             # float：浮点数
is_student = True         # bool：布尔值
address = None            # None：尚无值
MAX_RETRIES = 3            # 常量命名约定，不会禁止重新赋值
print(type(age).__name__)  # int

名字区分大小写，用有含义的 snake_case，不要把变量命名为 list、str 或 sum 遮蔽内置名字。动态类型表示名字可以重新绑定到不同类型的对象，不表示程序没有类型规则：字符串与整数不能直接相加。

类型可变性典型用途
int、float、bool不可变计数、测量、条件
str、bytes不可变Unicode 文本、二进制数据
list、dict、set可变有序记录、键值映射、去重
tuple、frozenset不可变固定结构、不可变集合
NoneType不可变缺失值或无返回结果

“不可变”是对象本身不能原地改变，不代表绑定它的变量不能赋新值。元组不能替换成员引用，但其引用的列表仍可修改。

python
a = [1]
b = a
print(a == b, a is b)  # True True：值相等且是同一对象
c = [1]
print(a == c, a is c)  # True False：值相等但不是同一对象
value = None
print(value is None)  # True

== 比较值，is 比较身份；用 is None 检查缺失值，不用 is 比较数值或字符串。id() 仅保证对象存活期间的身份唯一，释放后可复用。地址、小整数缓存和字符串驻留是实现细节，不要依赖它们做业务判断；不可变运算也不保证总是创建新对象。

输入、转换与输出 ​

input() 返回字符串。转换成功只代表格式可转换，业务范围仍需检查。下面会等待输入：输入 18 输出 明年 19 岁；输入 abc 或负数会得到相应提示。

python
raw = input("请输入年龄：")
try:
    age = int(raw)
except ValueError:
    print("年龄必须是整数")
else:
    if age < 0:
        print("年龄不能为负数")
    else:
        print(f"明年 {age + 1} 岁")

这里的异常处理会在核心篇展开。输入结束可能抛出 EOFError，用户中断可能抛出 KeyboardInterrupt，不能假设输入永远可用。

python
print(int("12"), float("1.5"), str(42))  # 12 1.5 42
print(bool("False"), bool(""))         # True False
print("苹果", "香蕉", sep=" / ")       # 苹果 / 香蕉
print(f"单价：{12.345:.2f}")            # 单价：12.35

布尔转换不是解析文本中的真假；非空字符串都是真。空容器、零、None 通常是假，自定义对象还可以定义真假协议。bool 是 int 的子类，所以 isinstance(True, int) 为真；严格 JSON 数字字段校验有时需要 type(value) is int，避免把布尔值当 ID。

数值精度 ​

整数可随内存增长而扩大，没有固定的 32 位溢出规则，但计算和存储都不是免费。浮点数通常使用二进制近似表示，测量值比较应带业务容差。

python
import math
from decimal import Decimal, ROUND_HALF_UP

print(0.1 + 0.2 == 0.3)                # False
print(math.isclose(0.1 + 0.2, 0.3))    # True
print(math.isclose(1e-12, 0, abs_tol=1e-9))  # True
price = Decimal("0.10") + Decimal("0.20")
print(price)                           # 0.30
print(Decimal("2.345").quantize(Decimal("0.01"), rounding=ROUND_HALF_UP))
# 2.35

金额可以用最小货币单位的整数，或从字符串构造 Decimal 并明确舍入策略。Decimal(0.1) 会保留传入浮点数的误差；十进制运算同样有上下文精度。处理外部数值还要考虑无穷大和 NaN，必要时用 math.isfinite() 或 Decimal.is_finite() 校验。

核心概念

运算符与短路 ​

类别写法易错点
算术+ - * / // % **/ 真除法；// 向负无穷取整

python
print(7 / 2, 7 // 2, -7 // 2, -7 % 2)  # 3.5 3 -4 1

分支、循环与解包 ​

python
score = 85
if score >= 90:
    level = "优秀"
elif score >= 60:
    level = "合格"
else:
    level = "待提升"
print(level)  # 合格

for index, name in enumerate(["小明", "小红"], start=1):
    print(index, name)
# 1 小明
# 2 小红

remaining = 3

    remaining -= 1

range(start, stop, step) 不包含结束值，步长不能为零。for 遍历可迭代对象；break 退出当前循环，continue 跳过本轮剩余部分，pass 只是空语句。

python
for number in range(2, 8):
    if number % 3 == 0:
        print("找到：", number)  # 找到： 3
        break
else:
    print("没有找到")  # 仅循环未经过 break 才执行

names = ["小明", "小红"]
scores = [80, 90]
for name, score in zip(names, scores, strict=True):
    print(name, score)
# 小明 80
# 小红 90

默认 zip() 截断到最短输入；要求长度一致时用 3.10+ 的 strict=True。循环 else 不是“条件为假”的替代分支；发生异常中断时也不会执行。遍历容器时不要随意增删该容器，优先构造新容器。

字符串与容器 ​

核心概念

选择数据结构就是选择数据关系：列表表达顺序，字典表达映射，集合表达唯一性，元组表达固定结构。

字符串、索引与切片 ​

python
text = "Python"
print(text[0], text[-1])     # P n
print(text[1:4], text[::-1]) # yth nohtyP
parts = " alice, bob ".strip().split(",")
print(" / ".join(part.strip() for part in parts))  # alice / bob
print("任务".encode("utf-8").decode("utf-8"))       # 任务

索引越界抛出 IndexError，切片越界通常截断；切片右端不包含在结果中。字符串方法返回新字符串，不会修改原对象。strip("ab") 去掉的是两端属于字符集合的字符，不是指定前缀；移除前缀用 removeprefix()。文本先编码为字节才适合写入二进制通道，解码必须匹配编码。

列表与元组 ​

python
items = [3, 1, 2]
items.append(4)          # 追加单个对象
items.extend([5, 6])     # 逐项追加
last = items.pop()       # 删除并返回末项
print(last)             # 6
print(sorted(items))    # [1, 2, 3, 4, 5]，返回新列表
print(items.sort())     # None，原地排序
print(items)            # [1, 2, 3, 4, 5]
first, *middle, last = items
print(first, middle, last)  # 1 [2, 3, 4] 5
point = (10, 20)
x, y = point
single = (1,)           # 单元素元组必须有逗号
print(x + y, single)    # 30 (1,)

remove(value) 删除第一个相等的值，找不到时抛出 ValueError；pop(index) 按位置删除并返回，del items[index] 按位置删除但不返回。许多原地修改方法返回 None，不要写 items = items.sort()。

字典与集合 ​

python
user = {"name": "小明", "score": 80}
user["score"] = 90
print(user.get("city", "未知"))  # 未知，不会插入 city
for key, value in user.items():
    print(key, value)
# name 小明

left = {1, 2, 2, 3}
right = {3, 4}
print(sorted(left | right))  # [1, 2, 3, 4]：并集
print(sorted(left & right)) # [3]：交集
print(sorted(left - right)) # [1, 2]：差集
empty_set = set()           # {} 是空字典

Python 3.7+ 字典保留插入顺序，但不是按键自动排序；集合没有可依赖的迭代顺序。字典键和集合元素必须可哈希：哈希值在生命周期内应稳定，相等对象应具有相同哈希。列表、字典不能当键，元组只有所有成员都可哈希时才能当键。可哈希与不可变有关，但不是同义词。

需求优先选择复杂度直觉
按位置读取、尾部追加列表索引通常 O(1)，尾部追加均摊 O(1)
按键查询、唯一性检测字典、集合平均查找 O(1)，不是绝对保证
两端频繁入队出队collections.deque避免列表头部移除的 O(n) 搬移
少量固定字段元组或数据类数据类通常更自解释

函数、参数与作用域 ​

核心概念

函数把输入转换成输出；尽量将计算与输入输出分开。参数绑定到传入对象，不自动复制对象。

参数、返回值与文档 ​

python
def total_price(price: float, quantity: int = 1, *, discount: float = 1.0) -> float:
    """计算演示用总价；实际金额请考虑 Decimal。"""
    return price * quantity * discount

print(total_price(10, 2, discount=0.8))  # 16.0

def collect(*args, **kwargs):
    return args, kwargs

print(collect(1, 2, enabled=True))  # ((1, 2), {'enabled': True})
values = [10, 2]
options = {"discount": 0.8}
print(total_price(*values, **options))  # 16.0

位置参数按位置传递，关键字参数按名字传递；*args 收集额外位置参数为元组，**kwargs 收集额外关键字参数为字典。定义中的 / 之前只能位置传参，裸 * 之后只能关键字传参。调用时的 * 和 ** 则是解包，避免把定义和调用混淆。

return 立即退出函数；没有写返回值就返回 None。return a, b 返回的是元组，不是独立的多个返回通道。函数也属于对象，可以赋值、传参和返回；简单排序键可以使用 lambda，复杂逻辑用具名函数。

默认参数与对象共享 ​

python
def append_item(item, items=None):
    if items is None:
        items = []
    items.append(item)
    return items

print(append_item("a"))  # ['a']
print(append_item("b"))  # ['b']

def update(items, count):
    items.append("新增")  # 调用方能看到原地修改
    items = ["局部列表"]  # 只改变局部绑定
    count += 1
    return items, count

original = ["原始"]
number = 1
print(update(original, number))  # (['局部列表'], 2)
print(original, number)          # ['原始', '新增'] 1

默认值在执行函数定义时求值一次；def f(items=[]) 会让省略参数的调用共享同一个列表。用 None 在调用时创建新对象；如果 None 也是合法业务值，使用独立哨兵对象区别“未提供”。

LEGB 与作用域 ​

普通函数中的名字通常依次查找：局部 Local → 外层函数 Enclosing → 当前模块 Global → Builtins。属性查找不是 LEGB；类体也不是方法的外层函数作用域。

python
def make_counter():
    count = 0
    def increment():
        nonlocal count
        count += 1
        return count
    return increment

counter = make_counter()
print(counter(), counter())  # 1 2

函数内赋值通常使该名字在整个函数体中成为局部名字；赋值前读取会触发 UnboundLocalError。global 指向当前模块的绑定，nonlocal 指向最近的已有外层函数绑定。修改共享列表的元素不等于重新绑定列表名字。优先通过参数和返回值传递状态，避免隐式全局依赖。

引用与浅深复制 ​

核心概念

赋值建立绑定；浅复制只复制外层容器；深复制递归复制需要复制的成员。问“两个对象是否独立”时，要检查嵌套成员。

python
import copy

original = {"name": "小明", "scores": [80, 90]}
alias = original
shallow = original.copy()
deep = copy.deepcopy(original)
original["scores"][0] = 100
print(alias is original)       # True
print(shallow is original)     # False
print(shallow["scores"])      # [100, 90]
print(deep["scores"])         # [80, 90]

wrong = [[0] * 2] * 3
wrong[0][0] = 1
print(wrong)  # [[1, 0], [1, 0], [1, 0]]
right = [[0] * 2 for _ in range(3)]
right[0][0] = 1
print(right)  # [[1, 0], [0, 0], [0, 0]]

列表切片、list.copy()、字典 copy() 都是浅复制。deepcopy() 使用记忆表处理循环并保留副本内部的共享关系；不可变对象可能复用，文件、套接字等资源不能靠它获得独立副本。复制不是越深越好，应先明确哪些对象应该共享。

基础篇验收：不用运行，预测上例四种对象受到修改的范围，再运行对照。能解释默认列表参数和重复嵌套列表为什么共享，才算掌握引用。

模块、包与标准库 ​

核心概念

模块是代码组织和命名空间单位；包组织多个模块。先熟悉标准库，只有确有需求时才增加第三方依赖。

把脚本拆成模块 ​

在同一个练习目录创建两个文件。prices.py：

python
# file: prices.py
def subtotal(price, quantity):
    return price * quantity

if __name__ == "__main__":
    print(subtotal(10, 2))

app.py：

python
# file: app.py
from prices import subtotal

print(subtotal(12, 3))  # 36

运行 python app.py 输出 36。运行 python prices.py 输出 20，导入它时不会执行入口分支。模块顶层代码通常在首次导入时执行，结果缓存于 sys.modules；不要把请求、安装依赖或永久循环放在模块顶层。

常规包是含有 __init__.py 的目录；命名空间包可以没有该文件，这是进阶场景。包内优先使用清楚的绝对导入或显式相对导入，例如 from .models import Task，以 python -m tasker.cli 运行，而不是直接运行包内部文件。

常见陷阱：

  • 文件不要叫 json.py、typing.py 等，以免遮蔽标准库。
  • 避免 from module import *；名字来源不清晰，也容易冲突。
  • 导入找不到时检查解释器、工作目录和安装状态，不先修改 sys.path。
  • 循环导入通常提示职责耦合；把共享的数据结构移到低层模块，而不是到处延迟导入。
  • 安装分发包名与导入包名不一定相同；安装成功不等于当前解释器一定能导入。

异常与上下文管理器 ​

核心概念

异常负责报告无法正常完成的操作；上下文管理器负责建立和退出资源使用范围。处理能恢复的问题，让无法恢复的问题保留诊断信息。

捕获、转换与清理 ​

python
def parse_port(text):
    try:
        port = int(text)
    except ValueError as exc:
        raise ValueError("端口必须是整数") from exc
    if not 1 <= port <= 65535:
        raise ValueError("端口超出范围")
    return port

try:
    port = parse_port("8080")
except ValueError as exc:
    print(f"配置错误：{exc}")
else:
    print(f"使用端口 {port}")  # 使用端口 8080
finally:
    print("本次配置检查结束")
结构执行时机误区
try执行可能失败的最小范围包裹整个应用容易掩盖错误来源
except匹配指定异常从具体到一般排列；不要裸捕获后静默忽略
elsetry 正常结束时其中异常不由同组 except 捕获
finally正常离开或异常展开时清理不写 return，否则可能覆盖返回值或异常
raise ... from exc转换为上层领域异常保留原始原因，不只留下“失败”

通常自定义异常继承 Exception。KeyboardInterrupt、SystemExit 不属于 Exception；不要随意拦截用户中断和退出。进程被强制终止、掉电等情况下不保证运行清理代码。assert 是开发期不变量检查，优化模式可能移除它，不能用来做外部输入校验。

读 Traceback 时先看最后一行的异常类型和消息，再向上找到自己的调用位置；有异常链时连同原始原因一起看。报错位置是错误暴露点，不一定是最早的原因。

用 with 管理资源 ​

with 调用上下文管理器的进入与退出协议，常用于文件、锁和事务。退出方法返回真值可以抑制异常；不需要抑制时不要返回真值。

python
from contextlib import contextmanager

@contextmanager
def operation(name):
    print("开始", name)
    try:
        yield
    finally:
        print("结束", name)

with operation("统计"):
    print(sum([1, 2, 3]))
# 开始 统计
# 6
# 结束 统计

这里的生成器应当恰好 yield 一次。块内异常会在该挂起点抛回生成器；只有确实处理成功才抑制它。装饰器与生成器的机制将在后面展开，初学时先会使用 with 即可。

文件、路径与 JSON ​

核心概念

路径描述位置，文件对象管理访问，编码连接文本与字节，JSON 只是一种数据格式。读到了数据不等于读到了合法业务对象。

文件模式与路径 ​

模式用途风险
r读取文本不存在会报错
w写入文本打开时就截断旧内容
a末尾追加重复运行会重复追加
x仅创建新文件已存在会报错，适合防止覆盖
rb、wb读写字节不传文本编码参数

相对路径基于 Path.cwd()；脚本相邻资源可基于 Path(__file__).resolve().parent 定位，但交互环境未必有 __file__。用户数据不宜写进安装包目录。拼接路径使用 / 运算，不手工拼平台分隔符。

以下示例只在自动清理的临时目录写入，不覆盖已有项目数据：

python
import json
from pathlib import Path
from tempfile import TemporaryDirectory

with TemporaryDirectory() as directory:
    path = Path(directory) / "tasks.json"
    records = [{"id": 1, "title": "学习文件", "done": False}]
    with path.open("w", encoding="utf-8") as stream:
        json.dump(records, stream, ensure_ascii=False, indent=2, allow_nan=False)
    with path.open("r", encoding="utf-8") as stream:
        loaded = json.load(stream)
    print(loaded[0]["title"])  # 学习文件
    print(path.exists())       # True

json.dumps() / loads() 操作字符串，dump() / load() 操作文件对象。JSON 对象键是字符串；元组往返后变成列表，日期、集合、数据类不能默认直接序列化。跨系统交换时避免 NaN 等非标准值。

从演示升级为可靠持久化 ​

  • 读取失败时区分“不存在”“没有权限”“编码不正确”“JSON 损坏”，不要全部当成空列表后覆盖原文件。
  • 解析后检查顶层类型、必需字段、取值范围和重复 ID。文件体积和嵌套深度也需要按风险限制。
  • 大文件逐行或分块处理，不无条件 read()；注意一行本身也可能很长。
  • 保存前先完整序列化，再写同目录临时文件并替换目标，降低半写入风险。综合项目会演示基础版本。
  • 文件替换不等于事务隔离，不防多进程丢失更新，也不自动保证掉电持久性。复杂并发写入优先使用数据库事务。

类与对象 ​

核心概念

对象把状态与相关行为组织起来。函数足够时不必引入类；需要多个独立状态实例或稳定接口时，类才有明显价值。

python
class Task:
    category = "学习"  # 类属性：实例之间共享的默认信息

    def __init__(self, title):
        self.title = title  # 实例属性
        self.done = False
        self.tags = []     # 每次初始化分别创建列表

    def complete(self):
        self.done = True

    def __repr__(self):
        return f"Task(title={self.title!r}, done={self.done!r})"

first = Task("阅读")
second = Task("练习")
first.complete()
first.tags.append("Python")
print(first)        # Task(title='阅读', done=True)
print(second.done, second.tags)  # False []

self 是实例方法约定的第一个参数，调用 first.complete() 时绑定实例；不是特殊关键字。__init__ 初始化已创建的实例，应返回 None；对象创建更底层涉及 __new__，初学不必自定义。

不要把每个实例独立的列表放在类属性上，否则所有实例可能共享它。读取属性可能回退到类属性；给实例同名属性赋值一般会建立实例属性，不会改写整个类的属性。

方法第一参数典型用途
实例方法self读取或改变实例状态
@classmethodcls替代构造入口，例如从字典构造实例
@staticmethod无自动绑定参数放在类命名空间中的辅助函数；也可写为模块函数

__repr__ 面向调试，__str__ 面向用户；__len__、__iter__ 等特殊方法让对象接入语言协议。不要为了“面向对象”把简单工具函数包装成无状态类。

封装、继承与多态 ​

核心概念

封装维护对象的不变量，多态依靠相同接口，继承表达真正的“是一种”关系。复用实现时优先考虑组合。

用属性维护规则 ​

python
class Counter:
    def __init__(self, value=0):
        self.value = value

    @property
    def value(self):
        return self._value

    @value.setter
    def value(self, value):
        if type(value) is not int or value < 0:
            raise ValueError("计数必须是非负整数")
        self._value = value

counter = Counter(2)
print(counter.value)  # 2
try:
    counter.value = -1
except ValueError as exc:
    print(exc)  # 计数必须是非负整数

单下划线表示内部使用约定，不构成访问限制；双下划线触发名字改写，主要防子类意外冲突，也不是真正的权限控制。属性适合轻量访问，不要悄悄进行耗时网络请求。

继承与鸭子类型 ​

python
class Notifier:
    def send(self, message):
        return f"通知：{message}"

class UrgentNotifier(Notifier):
    def send(self, message):
        return super().send(f"紧急 {message}")

def report(notifier):
    print(notifier.send("任务完成"))

report(Notifier())        # 通知：任务完成
report(UrgentNotifier())  # 通知：紧急 任务完成

report() 只关心对象是否支持 send()，不要求其一定继承某个父类，这就是鸭子类型。需要强制子类实现接口时可用 abc.ABC 与 abstractmethod；需要静态结构约束时可用 typing.Protocol。

super() 按方法解析顺序 MRO 寻找下一个实现，不等于永远调用某个固定父类。多重继承要协作调用并统一参数约定，具体原理放在选学部分。一个任务管理器“拥有存储器”，通常应传入存储对象进行组合，而不是继承一个存储器。

推导式、迭代器与生成器 ​

核心概念

可迭代对象提供迭代入口，迭代器保存遍历进度，生成器用暂停与恢复实现惰性计算。惰性意味着需要时才执行，也意味着错误可能延迟出现。

先写循环，再用推导式简化 ​

python
numbers = [1, 2, 3, 4]
squares = [n * n for n in numbers if n % 2 == 0]
lookup = {str(n): n * n for n in numbers}
unique = {n % 2 for n in numbers}
print(squares)                 # [4, 16]
print(lookup["3"], sorted(unique))  # 9 [0, 1]
print(sum(n * n for n in numbers)) # 30，生成器表达式

列表、字典、集合推导式立即构造结果；生成器表达式按需计算。不用推导式执行纯副作用，不写多层难读嵌套；清晰的循环比压成一行更 Pythonic。

迭代协议与耗尽 ​

python
items = [10, 20]
iterator = iter(items)
print(next(iterator))          # 10
print(next(iterator))          # 20
print(next(iterator, "结束"))  # 结束
print(list(iterator))          # []，已经耗尽
print(list(items))             # [10, 20]，列表可重新创建迭代器

iter(obj) 通常调用 __iter__()，next(it) 调用 __next__()；耗尽时抛出 StopIteration，for 自动处理它。迭代器通常返回自身作为迭代入口，不会自动重置。

python
def countdown(start):
    while start > 0:
        yield start
        start -= 1

stream = countdown(3)
print(next(stream))  # 3
print(list(stream)) # [2, 1]
print(list(stream)) # []

含 yield 的函数调用后返回生成器对象，不立即执行函数体。yield from 可委托子迭代器；return 结束生成器，不要手动抛 StopIteration。生成器节省的是未物化结果的内存，并非一定更快。跨 yield 持有文件等资源时，提前停止迭代也应显式关闭资源，不能只依赖垃圾回收。

闭包与装饰器 ​

核心概念

闭包保留外层函数绑定，装饰器在定义时接收并替换函数。先理解普通高阶函数，再理解 @ 语法。

闭包的迟绑定 ​

python
late = [lambda: i for i in range(3)]
fixed = [lambda i=i: i for i in range(3)]
print([fn() for fn in late])   # [2, 2, 2]
print([fn() for fn in fixed])  # [0, 1, 2]

闭包读取绑定，不是自动保存每一轮的值；默认参数可以在定义时捕获当时的值。捕获可变对象仍会共享对象，不能把此技巧当作深复制。

一个保留元信息的装饰器 ​

python
from functools import wraps

def announce(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        print(f"调用 {func.__name__}")
        return func(*args, **kwargs)
    return wrapper

@announce
def add(a, b):
    """返回两个数的和。"""
    return a + b

print(add(2, 3))       # 先输出 调用 add，再输出 5
print(add.__name__)    # add

@announce 相当于定义之后执行 add = announce(add)；调用时才进入包装器。多层装饰器由下向上应用。要透传参数、返回值和异常，并用 wraps() 保留常用元信息。同步包装器不自动适配异步函数；异步装饰器通常需要自己的 async def 包装层。

类型注解、数据类与 Pythonic ​

核心概念

类型注解帮助人和工具理解契约，数据类减少数据对象样板代码。它们都不自动完成输入校验。

注解表达意图 ​

python
from collections.abc import Iterable

def average(values: Iterable[float]) -> float | None:
    total = 0.0
    count = 0
    for value in values:
        total += value
        count += 1
    return total / count if count else None

scores: list[float] = [80.0, 90.0]
result = average(scores)
if result is not None:
    print(f"{result:.1f}")  # 85.0
print(average([]))         # None
  • 参数只要求遍历时，标注 Iterable，不要无必要地要求列表。
  • float | None 表示可能缺失，使用前缩小类型范围；Optional[T] 表示可为 None，不表示参数可以省略。
  • Any 会绕开许多静态检查，应尽量限制在外部边界，并及时校验转换。
  • 注解通常不会阻止运行时传入错误类型；typing.cast() 也不执行数据转换或验证。
  • 不同版本的注解求值机制有差异，尤其 Python 3.14 的延迟求值变化。需要反射时优先使用官方类型工具并阅读目标版本文档，不假设所有注解都是立即求值或字符串。

数据类与独立默认值 ​

python
from dataclasses import dataclass, field, asdict

@dataclass
class Task:
    id: int
    title: str
    done: bool = False
    tags: list[str] = field(default_factory=list)

first = Task(1, "阅读")
second = Task(2, "练习")
first.tags.append("Python")
print(second.tags)  # []
print(asdict(first))
# {'id': 1, 'title': '阅读', 'done': False, 'tags': ['Python']}

dataclass 默认生成初始化、表示和值比较等方法。default_factory 每个实例调用一次；frozen=True 限制常规字段赋值，不会递归冻结内部列表。asdict() 会递归转换数据类并处理成员，不等于自动获得适合业务协议的 JSON。slots=True 可减少部分实例开销，但限制动态属性等行为，先按需要选择。

Pythonic 是清晰，而不是炫技 ​

常见写法更清晰的方向
手动维护索引enumerate()
同时遍历两个序列zip()，需要时检查长度
先造完整列表再求和sum() 配合生成器表达式
为真假结果编写循环any()、all()，注意短路和空输入
大量分支只为取默认值合适地使用 dict.get()，区别缺失与 None
到处传多个相关字段数据类或明确的结构
把一切压成一行小函数、早返回、表达意图的变量名

any([]) 为假，all([]) 为真。使用 EAFP（先尝试再处理异常）时捕获具体错误；使用 LBYL（先检查再执行）时不要忽略检查与执行之间状态可能改变。可读性、正确性和可测试性比风格口号更重要。

核心篇验收

把成绩统计拆成解析、计算、展示三个函数；用数据类表示学生；从 JSON 读取输入并检查字段；用生成器逐条输出结果。确认导入模块不会触发输入或文件写入。

核心概念

名字、对象与生命周期 ​

名字绑定对象，容器也保存对象引用。对象有身份、类型和值；对象存活期间身份稳定，但释放后的身份值可以复用。id() 不应当作业务主键，语言也不保证它是内存地址。小整数缓存、字符串驻留等优化不是用 is 比较值的理由。

del name 删除绑定，不是命令对象立刻释放。对象是否仍可达取决于其他引用；文件、锁等外部资源应显式关闭或使用上下文管理器，不依赖垃圾回收时机。

CPython 的回收策略与观测限制 ​

常规 CPython 主要结合引用计数和循环垃圾收集。引用计数能及时处理许多不再引用的对象；循环引用则需要额外机制。自由线程构建等实现路径可能采用不同细节，不应依赖引用计数归零后的精确清理时机。

  • gc 用于观察、调试与控制循环收集；代际布局和阈值可能随版本变化，不把某个版本的“几代”当成语言保证。
  • sys.getsizeof() 主要报告对象本身的大小，不自动递归计算整个对象图。
  • 进程 RSS 不一定随对象释放立即下降，分配器可能保留内存以复用。
  • __del__() 的执行环境和时机不适合承担关键资源协议；优先 with，必要时了解 weakref.finalize()。
  • 缓存、全局容器、闭包、未结束任务等可能长期持有引用，这不是收集器“忘了回收”。
python
import gc
import weakref

class Node:
    pass

node = Node()
node.peer = node
reference = weakref.ref(node)
del node
gc.collect()
print(reference() is None)  # 常规 CPython 独立脚本中：True

手动收集返回的数量取决于进程状态，不应写成固定预期值。生产环境先测量再调整 GC，不要把关闭 GC 作为通用加速技巧。

多线程入门：先启动，再等待 ​

进程可以理解为一个运行中的程序及其资源容器；线程是进程内的一条执行路径。同一进程中的线程共享许多对象和资源，所以传递数据方便，但同时修改状态时需要协调。主线程负责启动程序，也可以创建工作线程处理其他任务。

多线程不是让函数自动变快，而是允许多条执行路径在时间上重叠。 例如一个线程等待网络响应时，另一个线程可以处理其他请求。纯 Python 的大量计算是否能并行，还取决于解释器及 GIL，不能只看线程数量。

下面先不引入锁和线程池，用两个原生线程模拟等待型任务。保存为独立脚本运行，无网络或文件操作：

python
from threading import Thread
from time import sleep


def download(name: str) -> None:
    print(f"开始：{name}")
    sleep(0.05)  # 模拟阻塞等待，不是真实下载。
    print(f"完成：{name}")


def main() -> None:
    threads = [
        Thread(target=download, args=("文件 A",), name="download-a"),
        Thread(target=download, args=("文件 B",), name="download-b"),
    ]
    for thread in threads:
        thread.start()
    for thread in threads:
        thread.join()
    print("全部工作线程已结束")


if __name__ == "__main__":
    main()

逐步理解执行过程：

  1. 创建线程对象时传入函数本身，不能写成 target=download("文件 A")，否则会先在当前线程调用函数。
  2. args=("文件 A",) 是单元素元组，末尾逗号不可省略；参数在工作线程执行目标函数时使用。
  3. start() 请求启动新线程；直接调用线程的 run() 方法不会为这次调用创建新线程。
  4. 第一个循环启动全部线程，第二个循环等待它们结束。如果每启动一个就立刻等待结束，任务将失去这种并发重叠。
  5. join() 阻塞调用它的线程。它确认目标线程结束，不返回目标函数的业务结果，也不自动向调用者重新抛出工作线程异常。

预期两项任务各打印一次开始与完成，最后才打印“全部工作线程已结束”。每项任务内部先开始后完成，但两项任务之间的交错顺序不固定；不要根据一次打印结果推断调度规则。这里的睡眠仅模拟等待，不用它证明加速比例或线程同步正确性。

初学时的问题正确处理方式
如何获得线程计算结果？使用队列传递，或采用线程池并读取 Future 结果
多个线程修改同一个对象怎么办？先明确共享状态，再用锁或单消费者协议保护整个操作
主线程不想等了，工作线程就停止了吗？不会；需要停止信号和可退出的底层操作
工作线程越多越快吗？不一定；连接、内存和调度都有成本，应限制数量

GIL 的准确边界 ​

在启用 GIL 的 CPython 中，同一解释器里的线程通常不能同时执行 Python 字节码。因此纯 Python CPU 密集循环通常不能靠线程数获得多核加速；线程仍可在阻塞 I/O 等待期间推进其他任务，部分原生扩展会释放 GIL 并并行计算。

Python 3.13 起提供可选的自由线程构建，它不同于“所有 Python 都没有 GIL”。扩展兼容性、是否重新启用 GIL、运行方式与版本都会影响行为；先检查实际解释器和依赖。其他 Python 实现也不能直接套用 CPython 结论。即使有 GIL，复合业务操作依然需要同步；不能把某次字节码实验中“似乎原子”当成承诺。

线程与锁：保护不变量 ​

以下示例启动四个线程，每次递增都在同一把锁中完成，无文件或网络副作用：

python
from concurrent.futures import ThreadPoolExecutor
from threading import Lock

counter = 0
lock = Lock()

def increment(times: int) -> None:
    global counter
    for _ in range(times):
        with lock:
            counter += 1

if __name__ == "__main__":
    with ThreadPoolExecutor(max_workers=4) as pool:
        list(pool.map(increment, [1000] * 4))
    print(counter)  # 4000

counter += 1 包含读、计算、写。去掉锁以后不能保证一定得到错误结果，也不能保证正确。需要保护的是整个状态转换，不只是最终赋值。multiprocessing.Value 的读写即使各自有锁，复合更新仍应在 with value.get_lock(): 中保护整个读改写过程。

  • 生产者/消费者优先使用 queue.Queue，设置合理容量形成背压；跨进程使用相应的进程队列。
  • 多把锁需要一致的获取顺序，锁内避免长时间 I/O，防止死锁和吞吐下降。
  • 线程无法被安全地随意强杀；使用 Event 等发出停止信号，让任务协作退出。
  • Future.result() 会等待并传播任务异常；as_completed() 按完成顺序产出，顺序不固定；map() 按输入顺序提供结果。

原生线程的生命周期与协作停止 ​

线程对象创建后不会立刻执行目标函数。调用启动方法之后，由操作系统调度线程；同一个线程对象只能启动一次。等待线程结束只是回收生命周期，并不会替你检查它是否成功。

text
创建 Thread --> start() --> 就绪 / 运行 / 等待 --> 目标函数返回或抛异常
                               ^                         |
                               |                         +--> join() 返回
                               +---- Event / Queue / I/O

下面通过事件协调启动与停止，不通过猜测睡眠时间判断线程是否已经运行：

python
from queue import Empty, Queue
from threading import Event, Thread


def main() -> None:
    ready = Event()
    stop = Event()
    errors: Queue[Exception] = Queue()

    def worker() -> None:
        try:
            ready.set()
            while not stop.wait(timeout=0.05):
                # 实际项目在此执行一小段有超时的工作。
                pass
        except Exception as exc:
            errors.put(exc)
        finally:
            print("工作线程已清理")

    thread = Thread(target=worker, name="poller")
    thread.start()
    try:
        if not ready.wait(timeout=2):
            raise TimeoutError("线程没有就绪")
    finally:
        stop.set()
        thread.join(timeout=2)
    if thread.is_alive():
        raise RuntimeError("线程没有按协议退出")
    try:
        error = errors.get_nowait()
    except Empty:
        pass
    else:
        raise RuntimeError("工作线程失败") from error
    print("主线程结束")


if __name__ == "__main__":
    main()

预期先输出“工作线程已清理”，再输出“主线程结束”。事件保存的是状态，不是通知次数；连续两次设置事件不会形成两个待消费消息。需要逐条处理的数据应进入队列。

  • 等待线程时传入超时只限制调用方的等待；超时后必须检查线程是否仍存活。
  • 普通线程的未捕获异常交给线程异常钩子处理，不会通过等待方法重新抛给主线程；示例用错误队列显式传递。
  • 守护线程不是可靠的后台任务方案。解释器关闭时其资源清理可能来不及执行，不适合保存文件、提交事务或发送重要消息。
  • 停止事件不能打断一个永不返回的阻塞调用。底层网络、锁等待和轮询都需要可退出的边界；不能靠主线程设置事件来保证一切停止。

同步原语不是只有一把锁 ​

原语解决什么问题易错点
Lock同一时刻只有一个执行者进入临界区同线程重复获取也可能死锁
RLock同线程需要递归进入同一保护区域必须对应释放，不是无死锁保证
Event共享“已启动”“应停止”等状态不计数，不替代消息队列
Condition在同一把锁下等待共享状态满足条件唤醒不代表条件一定满足，必须重新检查
Semaphore同时占用某资源的执行者不超过配额不保证每秒请求数，也不限定总任务数
BoundedSemaphore在信号量基础上检测部分过量释放错误仍需确保异常时正确释放
Barrier固定参与者在阶段边界会合某参与者失败可能破坏屏障，需处理超时
Queue安全传递消息、阻塞等待、任务计数每次取出必须对应一次完成确认

条件变量适合“状态 + 等待者”的协议。下面只有发布者能将状态从未发布改为已发布，消费者在持锁状态检查条件：

python
from threading import Condition, Thread


def main() -> None:
    condition = Condition()
    state = {"published": False, "value": 0}

    def publish() -> None:
        with condition:
            state["value"] = 42
            state["published"] = True
            condition.notify_all()

    thread = Thread(target=publish)
    thread.start()
    try:
        with condition:
            ok = condition.wait_for(lambda: state["published"], timeout=2)
            if not ok:
                raise TimeoutError("没有收到状态更新")
            value = state["value"]
    finally:
        thread.join()
    print(value)  # 42


if __name__ == "__main__":
    main()

条件等待会释放关联锁，恢复时重新获取锁；通知本身不会释放锁。即使发布发生在消费者开始等待之前，消费者也会通过状态谓词直接发现结果，不会丢失这一状态变化。

锁应保护明确的不变量，例如“库存非负，并且扣减与订单登记一致”。不要只给每次属性读写分别加锁，却把检查和更新拆开。锁也不提供数据库事务：已经发出的网络请求不会因为释放锁而撤销。

死锁排查优先检查四类问题：不同路径以相反顺序拿锁；持锁等待需要同一把锁的线程；在线程池工作者内等待同池子任务；持锁进行无限期网络 I/O。统一锁顺序、缩小临界区、拆分依赖图，比事后增加超时更可靠。

有界线程队列：通信、背压与收尾 ​

下面使用两个消费者处理六个任务，队列只能缓存两个未取出的任务。生产速度超过消费速度时，放入操作等待空位；这就是背压。示例故意让一个任务失败，但继续处理其他任务，把失败当作业务结果收集。

python
from queue import Queue
from threading import Thread


def main() -> None:
    jobs: Queue[int | None] = Queue(maxsize=2)
    outcomes: Queue[tuple[int, int | str]] = Queue()

    def consume() -> None:
        while True:
            item = jobs.get()
            try:
                if item is None:
                    return
                try:
                    if item == 3:
                        raise ValueError("模拟坏任务")
                    outcomes.put((item, item * item))
                except Exception as exc:
                    outcomes.put((item, f"失败: {exc}"))
            finally:
                jobs.task_done()

    workers = [Thread(target=consume) for _ in range(2)]
    for worker in workers:
        worker.start()
    try:
        for number in range(6):
            jobs.put(number)
    finally:
        for _ in workers:
            jobs.put(None)
        jobs.join()
        for worker in workers:
            worker.join()
    results = [outcomes.get_nowait() for _ in range(6)]
    print(sorted(results))


if __name__ == "__main__":
    main()

预期得到按编号排序的平方结果，其中编号 3 对应失败字符串。实际消费顺序没有承诺。停止标记与合法任务类型不冲突，并且每个消费者需要一份标记。

三个不同的“完成”必须区分：

  1. 取出消息只说明队列中不再有这条消息，不代表处理完成。
  2. 完成确认减少未完成计数。它应放在清理分支中，停止标记也要确认；重复确认会抛错。
  3. 队列等待方法等待所有入队任务被确认；线程等待方法等待工作线程退出，两者不互相替代。

不要用空队列检测或队列长度决定下一步取出是否一定成功：检查和操作之间，其他消费者可能已经改变状态。直接使用阻塞取出，或使用非阻塞取出并捕获空队列异常。

本例的结果集合是固定且很小的，因此结果队列无界。无限数据流中，结果侧也需要并行消费者、有限缓存或直接落盘；不能让主线程先等待所有任务，再消费有界结果队列，否则消费者可能卡在输出上，导致全链路死锁。

这个收尾协议处理普通任务异常，但不能处理消费者进程被杀死、线程卡死等所有故障。真实服务还需要健康检查、底层 I/O 超时和停止时限；如果改成“首错即停”，必须同步定义尚未取出消息的处置和完成计数，不能直接让消费者抛错后遗留队列等待。

线程池、Future 与任务所有权 ​

线程池复用工作线程，Future 表示某次提交的计算状态；它不是执行线程本身。多个 Future 会轮流占用同一组线程。

操作语义不保证的事情
submit提交一次调用并返回 Future不保证马上开始，也不保证提交队列有界
result等待结果或重新抛出任务异常等待超时不会终止任务
exception等待并读取异常对象不能代替业务失败处理
cancel尝试取消尚未运行的任务不能强制终止已运行线程
as_completed按完成情况迭代 Future不保证输入顺序或固定完成顺序
map按输入顺序读取结果前面慢任务可能阻塞后面结果的交付
shutdown停止提交并按参数回收线程池不会安全强杀运行中的工作

下面通过单工作者和事件让第二个任务保持排队，从而确定性验证取消行为：

python
from concurrent.futures import CancelledError, ThreadPoolExecutor
from threading import Event


def main() -> None:
    started = Event()
    release = Event()

    def hold() -> int:
        started.set()
        if not release.wait(timeout=5):
            raise TimeoutError("未释放工作者")
        return 42

    with ThreadPoolExecutor(max_workers=1) as pool:
        first = pool.submit(hold)
        try:
            if not started.wait(timeout=2):
                raise TimeoutError("任务未启动")
            second = pool.submit(lambda: 99)
            assert second.cancel()
            assert not first.cancel()
            try:
                second.result()
            except CancelledError:
                print("排队任务已取消")
        finally:
            release.set()
        print(first.result(timeout=2))  # 42


if __name__ == "__main__":
    main()

使用上下文管理器离开线程池时，默认等待已提交任务结束，包括因异常离开代码块的情况。因此结果等待超时并不保证整个代码块立即结束。关闭时取消待执行任务也不会停止正在运行的任务；非等待关闭同样不代表解释器可以忽略尚未结束的线程。

不要提交一百万个任务后才考虑限并发。工作线程数限制执行中的任务，不限制待执行任务和 Future 占用的内存。Python 3.11 中可用有界队列，或维护固定窗口：只提交有限批任务，每完成一个再补一个。Python 3.14 的 Executor.map 新增缓冲参数，使用前需要核对实际版本；进程池分块参数不是线程池的限流开关。

进程池与入口保护 ​

将以下代码保存为普通脚本运行，不要直接粘贴进交互解释器。函数放模块顶层，参数和返回值可序列化，显式使用 spawn 以展示跨平台要求：

python
import multiprocessing as mp
from concurrent.futures import ProcessPoolExecutor

def square(number: int) -> int:
    return number * number

if __name__ == "__main__":
    context = mp.get_context("spawn")
    with ProcessPoolExecutor(max_workers=2, mp_context=context) as pool:
        results = list(pool.map(square, [1, 2, 3, 4]))
    print(results)  # [1, 4, 9, 16]

入口保护避免子进程导入时再次创建进程。不同平台、Python 版本的默认启动方式不同，例如 Python 3.14 在支持的平台上调整了 POSIX 默认行为，不能假设永远是 fork。进程间不直接共享普通列表；使用消息传递、受控共享内存或数据库。细粒度任务可能被启动和传输成本吞没，先分块并测量。

进程启动、数据传递与隔离边界 ​

线程共享同一进程地址空间；进程拥有独立地址空间。把一个列表传给子进程，不等于共享主进程的列表。子进程修改自己的副本不会自动反馈给父进程，必须显式返回结果、发送消息或使用共享机制。

启动方式基本机制主要边界
spawn启动新解释器，重新导入主模块跨平台清晰；启动较慢；要求安全导入和可序列化参数
fork复制父进程状态，通常利用写时复制POSIX 特有；多线程父进程中的锁和运行库状态有风险
forkserver由专用服务进程创建子进程只在支持的平台可用；仍需考虑导入和序列化要求

入口保护不是只给 Windows 用的语法习惯，而是在“子进程导入模块”时避免重复执行启动逻辑。模块顶层可以定义函数和常量，不应启动进程池、读用户输入或连接生产数据库。可移植示例显式选择启动上下文，不依赖随版本变化的默认值。

进程池会通过序列化传递任务和结果，因此有几项常见限制：

  • 目标函数优先放在可导入模块顶层；局部函数和匿名函数通常不适合标准进程池。
  • 文件句柄、线程锁、数据库连接、事件循环不能当成普通业务参数随意传过去。
  • 大数组反复传输可能比计算更贵；优先批处理、初始化时加载只读数据，或在确有必要时使用共享内存。
  • 序列化数据不是可信协议。不要反序列化来自不可信来源的 pickle；进程隔离也不意味着允许执行不可信代码。

普通队列适合所有权转移，Manager 代理适合低频共享状态，但每次代理调用可能涉及跨进程通信。共享内存减少复制成本，却要求你自己管理同步、布局、关闭与释放。共享计数器的读改写仍需把完整操作放入它的锁中，不要误以为“共享”意味着“原子”。

批处理、结果顺序与失败传播 ​

下面统计分块中的质数个数，故意加入一个非法任务来展示失败隔离。保存成脚本运行；仅使用 CPU，不访问网络或文件。规模很小是为了演示协议，不用于证明性能提升。

python
import multiprocessing as mp
from concurrent.futures import ProcessPoolExecutor, as_completed
from math import isqrt


def count_primes(bounds: tuple[int, int]) -> int:
    start, stop = bounds
    if start > stop:
        raise ValueError("范围倒置")
    total = 0
    for number in range(max(start, 2), stop):
        if all(number % divisor for divisor in range(2, isqrt(number) + 1)):
            total += 1
    return total


def main() -> None:
    ranges = [(0, 10), (10, 20), (20, 10)]
    answers: dict[int, int | str] = {}
    context = mp.get_context("spawn")
    with ProcessPoolExecutor(max_workers=2, mp_context=context) as pool:
        pending = {
            pool.submit(count_primes, bounds): index
            for index, bounds in enumerate(ranges)
        }
        for future in as_completed(pending):
            index = pending[future]
            try:
                answers[index] = future.result()
            except ValueError as exc:
                answers[index] = f"失败: {exc}"
    print([answers[index] for index in range(len(ranges))])
    # [4, 4, '失败: 范围倒置']


if __name__ == "__main__":
    main()

普通任务异常可在对应结果处捕获，并不必然破坏整个池。若工作进程意外退出，可能收到进程池损坏异常，这属于执行基础设施故障；不应只把它当成某个数据项的普通校验失败并继续往损坏的池中提交。

任务粒度决定调度效率。把每个整数作为一个跨进程任务通常太细；分块降低序列化和调度次数，但块过大会增加负载不均衡和取消延迟。工作者数量还要受容器 CPU 配额、内存和原生库内部线程数约束，不能只根据机器报告的 CPU 数量无限放大。

进程池的结果等待超时也不是杀进程指令，取消通常只对尚未进入运行状态的任务有效。硬终止可能留下半写入文件、锁或损坏的通信通道；需要强隔离和硬时间限制时，应设计独立子进程监督、幂等写入与故障恢复，而不是假设普通池自动提供这些保证。

并发不是事务：提交与副作用 ​

不管使用线程、进程还是协程，都要分别定义“任务算完”“结果收到”“外部提交完成”。调用方超时可能发生在服务端提交之后；盲目重试会重复扣款、发消息或创建资源。

工程实践中通常需要：请求幂等键、可查询的最终状态、数据库唯一约束或事务、有限重试及故障记录。同步锁只保护参与同一协议的执行者；单机线程锁不能保护多个服务实例共同写入的数据库记录。

异步编程：从同步等待到协作执行 ​

核心概念

多线程是一种执行机制，异步是一种组织发起操作与处理完成结果的方式，协程是一种可以暂停和恢复的执行单元。三者不是互斥选项：异步接口可以使用线程实现，协程也可以把阻塞工作交给线程。

同步、异步、阻塞与非阻塞 ​

这些词描述的角度不同，不能直接互相替换：

概念关注的问题常见表现
同步调用流程如何取得最终结果？当前流程等本次操作完成，再继续后续步骤
异步操作完成后如何通知或恢复处理？先获得任务或结果占位对象，完成后通过回调或等待点继续
阻塞等待时当前线程能否继续处理其他工作？同步网络读取、普通睡眠使当前线程等待
非阻塞操作暂时无法完成时是否立即返回？非阻塞套接字告知暂不可读，由调度器等待后续就绪

同步与异步主要描述接口和控制流程；阻塞与非阻塞主要描述调用对当前线程的影响。在 asyncio 中，等待未完成的异步 I/O 会暂停当前协程，让循环处理其他任务，并不是让当前协程越过依赖、提前得到结果。

举例：查询用户资料后才能生成问候语，两步有依赖，必须按顺序等待；查询两个互不依赖的用户资料，才适合先启动两项任务，再统一收集结果。异步不会消除业务依赖，声明异步函数也不会自动制造并发。

第一个协程：定义、调用与运行 ​

Python 原生协程通常由 async def 定义。调用这类函数得到协程对象，而不是最终业务结果；普通脚本用 asyncio.run() 启动入口，在异步函数内部通过 await 等待可等待对象。

以下示例要求 Python 3.11+，可独立运行：

python
import asyncio


async def make_message(name: str) -> str:
    print("进入协程")
    await asyncio.sleep(0.01)
    return f"你好，{name}"


async def main() -> None:
    pending = make_message("Python")
    print("已创建协程，函数体尚未运行")
    message = await pending
    print(message)


if __name__ == "__main__":
    asyncio.run(main())

输出顺序固定为“已创建协程，函数体尚未运行”“进入协程”“你好，Python”。创建协程本身不运行函数体；等待时才开始推进它。这里只存在一条业务执行链，所以它是异步写法，但没有同时启动多个业务任务。

  • async def 声明原生协程函数，不会把内部的普通函数调用变成非阻塞调用。
  • await 取得可等待对象的结果；异常也会沿等待链传播。它不是通用的“异步转换器”，不能等待普通字符串或同步请求返回值。
  • asyncio.sleep() 通过循环计时器等待；time.sleep() 会阻塞所在的线程。二者在事件循环中不可随意互换。
  • asyncio.run() 管理脚本入口的循环生命周期。在已有循环的 Notebook 或 Web 框架中使用其异步入口，不要在同一线程嵌套调用。
  • 创建后既不等待也不调度的协程不会完成工作，还可能产生“协程从未被等待”的警告。

多线程与协程怎样选择 ​

工作形态优先考虑注意边界
现成的同步 HTTP、文件或数据库接口有界线程池，或异步程序中的线程桥接底层调用仍需要超时，取消等待不等于停止线程
已提供原生异步驱动的大量 I/O 等待asyncio 与协程不要在循环线程中执行阻塞调用，限制并发和排队
纯 Python CPU 密集计算进程池，或经验证适用的其他并行机制考虑启动、序列化、内存以及解释器配置
少量顺序操作、任务之间有强依赖普通同步代码简单直接通常比引入并发框架更易维护

协程通常比操作系统线程轻量，但并不免费。大量创建任务仍会消耗内存，也可能让下游连接池或服务过载。选择机制之后还要设置队列容量、并发上限、超时和退出协议。

把阻塞接口接入异步程序 ​

遇到没有异步版本的第三方接口，可以将阻塞操作交给线程，让循环继续处理其他协程。下面只模拟有限时长的阻塞等待：

python
import asyncio
import time


def blocking_lookup(user_id: int) -> str:
    time.sleep(0.02)
    return f"user-{user_id}"


async def main() -> None:
    async with asyncio.TaskGroup() as group:
        first = group.create_task(asyncio.to_thread(blocking_lookup, 1))
        second = group.create_task(asyncio.to_thread(blocking_lookup, 2))
    print(first.result(), second.result())  # user-1 user-2


if __name__ == "__main__":
    asyncio.run(main())

这里组合了三层机制：协程表达业务流程，事件循环管理异步任务，线程执行阻塞函数。线程桥接不会改写阻塞函数内部逻辑，也不能保证纯 Python 计算获得多核加速。不要把成千上万次调用一次性全部创建为任务；后文用队列和固定工作者限制任务总量。

等待取消，不代表外部工作停止

取消等待线程结果的异步任务，通常不会终止已经运行的线程函数。涉及写入、付款或发消息时，还需要底层超时、幂等设计、状态查询与协作停止；异步超时不是事务回滚。

从基础走向完整的协程程序 ​

学习时按以下顺序推进，而不是只记语法：

  1. 理解函数、协程对象与任务的区别，能解释为什么调用不等于执行。
  2. 区分有依赖的串行等待与独立任务的并发调度。
  3. 用结构化并发明确谁创建任务、谁等待结束、谁处理异常。
  4. 为超时和取消编写清理逻辑，再学习异步锁、数据流和队列。
  5. 在负载增长之前定义并发、排队和重试预算，并验证失败路径。

从生成器到原生协程 ​

理解协程的关键不是“写了异步关键字”，而是函数执行可以暂停，保存局部状态，之后从暂停处恢复。生成器已经具备暂停能力，但生成器与原生协程服务于不同协议。

对象如何创建如何推进主要用途
普通函数调用结果调用普通函数调用过程中执行完毕同步计算
生成器调用包含 yield 的普通函数next、send、迭代惰性产生数据
原生协程调用 async def 函数（不含 yield）await，通常由任务驱动可暂停的异步工作
异步生成器调用同时包含 async def 和 yield 的函数异步迭代异步按需产生数据
Task将协程交给事件循环调度循环在就绪时推进并发任务的生命周期与结果
asyncio.Future在循环中创建结果占位对象底层回调设置结果或异常桥接回调式接口

生成器可以接收外部值：首次推进执行到第一个暂停点，后续发送的值成为暂停表达式的结果。下面只是展示双向交互，不会自动产生异步 I/O 或并发：

python
from collections.abc import Generator


def accumulator() -> Generator[int, int, None]:
    total = 0
    while True:
        received = yield total
        total += received


generator = accumulator()
try:
    print(next(generator))      # 0：预激到第一个 yield
    print(generator.send(3))   # 3
    print(generator.send(5))   # 8
finally:
    generator.close()

历史上可以借助生成器和调度器实现协程，但现代 asyncio 业务代码优先使用原生协程，不需要手工调用发送方法来调度。一个普通生成器不能仅因为“会暂停”就被原生等待表达式直接等待。

可等待对象是一类协议对象：原生协程、Task、asyncio.Future，以及正确实现等待协议的对象。线程池返回的 concurrent.futures.Future 与 asyncio.Future 不是同一类型；前者的结果读取可能阻塞线程，不能直接当作事件循环中的等待操作。桥接时用循环执行器接口或包装方法。

协程对象通常是一次性的。同一个原生协程对象不能被执行完成后再次等待，也不能交给多个任务同时驱动。若多个消费者需要同一次计算的结果，应先创建一个 Task，再等待该 Task；已经完成的 Task 可以重复读取结果。

事件循环如何推进工作 ​

可以把事件循环理解为一个在所属线程内执行的调度器，它管理就绪回调、计时器和 I/O 就绪通知。下面是帮助理解的抽象过程，不代表各平台实现细节完全相同：

text
取出就绪回调 / 推进任务
          |
          +--> 普通计算：继续占用当前线程
         |
          +--> 等待未完成对象：登记恢复条件，暂停当前任务
          |
          +--> 返回 / 抛错：记录最终结果，唤醒等待者
          |
检查计时器和 I/O 事件 --> 将可以继续的工作加入就绪队列

单个循环线程不会像操作系统调度线程那样，随意在两条普通 Python 语句之间切换到另一个 asyncio 任务。任务要到真正挂起时才让出执行机会。但同一进程内其他线程、原生扩展以及外部服务仍可能并发修改状态，不能把“单循环”推广成“所有资源都安全”。

三个容易混淆的事实：

  1. 声明异步函数不改变函数内部调用的性质；同步 HTTP 请求放进去仍然阻塞。
  2. 等待一个已经完成的 Future 可能立即继续，不一定给其他任务运行机会。
  3. 零延迟异步睡眠可用于主动让出执行机会，但不保证公平调度，也不能把长 CPU 计算变成多核并行。

运行入口负责建立循环、运行主协程并回收相关资源。普通脚本通常使用一次运行入口；已经存在事件循环的框架或 Notebook 中，应使用框架提供的生命周期或顶层等待，不要嵌套启动循环。异步锁、队列、连接池等最好在所属异步入口中创建和使用，不要随意跨循环复用。

直接等待与并发调度 ​

调用 async def 函数获得协程对象，不会自动运行其函数体。直接 await coroutine() 在当前任务中等待它，不自动创建新任务；使用 create_task() 或 TaskGroup 才显式安排独立任务。await 不保证挂起，也不一定等待 I/O；如果结果已经就绪，它可能立即返回。

以下脚本仅使用异步计时器，不访问网络，Python 3.11+ 可运行：

python
import asyncio

async def fetch(name: str, delay: float) -> str:
    await asyncio.sleep(delay)
    return f"{name}:ok"

async def main() -> None:
    async with asyncio.TaskGroup() as group:
        first = group.create_task(fetch("A", 0.02))
        second = group.create_task(fetch("B", 0.01))
    print(first.result(), second.result())  # A:ok B:ok

if __name__ == "__main__":
    asyncio.run(main())

输出按显式读取结果的顺序排列，不代表任务完成顺序。TaskGroup 离开时会等待组内任务；一个任务因普通异常失败时会取消其他任务，并通常用异常组传播错误。取消、KeyboardInterrupt、SystemExit 有专门规则；异常组可用 Python 3.11 的 except* 分类型处理。

asyncio.gather() 默认按输入顺序提供成功结果，但首个异常可能提前传播，其他任务并不因此自动全部取消。使用 return_exceptions=True 时异常作为结果返回，需要逐项检查，不能悄悄忽略。不要把 gather 和 TaskGroup 当成完全相同的错误管理策略。

串行等待、并发启动与结果顺序 ​

下面通过事件记录区分两个模型，不靠“运行时间大概减半”的脆弱断言。两个任务都启动后，协调者才释放它们：

python
import asyncio


async def main() -> None:
    trace: list[str] = []

    async def sequential_job(name: str) -> str:
        trace.append(f"start:{name}")
        await asyncio.sleep(0)
        trace.append(f"end:{name}")
        return name

    await sequential_job("A")
    await sequential_job("B")
    assert trace == ["start:A", "end:A", "start:B", "end:B"]
    print("串行:", trace)

    trace.clear()
    ready = {name: asyncio.Event() for name in ("A", "B")}
    release = asyncio.Event()

    async def concurrent_job(name: str) -> str:
        trace.append(f"start:{name}")
        ready[name].set()
        await release.wait()
        trace.append(f"end:{name}")
        return name

    async with asyncio.timeout(2):
        async with asyncio.TaskGroup() as group:
            first = group.create_task(concurrent_job("A"))
            second = group.create_task(concurrent_job("B"))
            await ready["A"].wait()
            await ready["B"].wait()
            assert set(trace) == {"start:A", "start:B"}
            release.set()
    print("并发结果:", first.result(), second.result())  # A B


if __name__ == "__main__":
    asyncio.run(main())

循环里逐个等待每次请求，通常就是串行；先创建多个任务再等待，才允许它们的等待阶段重叠。输出结果可以按输入顺序整理，也可以按完成顺序处理，两者是调用方的选择，而不是“并发”一词自动规定的顺序。

默认任务创建通常安排后续执行，但 Python 3.12 起支持立即执行任务工厂，较新版本还提供相关选项；启用这类机制可能改变协程开始执行的时机。不要把“创建任务后的下一行一定先于协程函数体执行”作为跨配置不变量。

任务状态、引用与异常所有权 ​

text
创建任务 --> 待运行 / 运行 / 挂起 --> 正常完成：保存结果
                      |          --> 异常完成：保存异常
                      +--> 收到取消请求 --> 清理 --> 取消完成
                                            |
                                            +--> 抑制取消：可能继续运行

待完成状态覆盖运行和等待，不能通过一个状态查询精确推断任务正在执行哪一行。取消请求被提出与最终进入取消状态是两个阶段；只有取消异常实际传播到任务边界，任务才以取消结束。

尚未完成时读取 asyncio.Task 的结果会抛状态错误，而不是像线程池 Future 那样阻塞。任务已失败时读取结果会重新抛出异常；已取消时会抛取消异常。因此必须先等待，或确认已结束，再读取结果。

每个任务都需要一个明确的所有者，负责：保存引用、等待结果、处理异常、发出取消并等待清理。把任务创建后完全丢弃可能产生未观察异常或生命周期问题。对于后台服务任务，优先把它们纳入服务级任务组；确实独立的任务也应保存在集合中，在完成回调中回收并记录异常，在服务停止时统一取消并等待。

结构化并发与异常组 ​

结构化并发的目标是让子任务的生存范围受父作用域管理。离开任务组时，子任务不会仍然毫无归属地运行。一个子任务发生非取消异常后，组会请求取消其余子任务，等待它们完成清理，再传播收集到的错误。

下面故意失败一个子任务，验证兄弟任务先进入等待，再被取消并清理：

python
import asyncio


async def main() -> None:
    started = asyncio.Event()
    cleaned = asyncio.Event()

    async def sibling() -> None:
        started.set()
        try:
            await asyncio.Event().wait()
        finally:
            cleaned.set()

    async def fail() -> None:
        await started.wait()
        raise ValueError("模拟子任务失败")

    try:
        async with asyncio.TaskGroup() as group:
            other = group.create_task(sibling())
            group.create_task(fail())
    except* ValueError as errors:
        assert cleaned.is_set()
        assert other.cancelled()
        print("已处理校验错误数量:", len(errors.exceptions))  # 1


if __name__ == "__main__":
    asyncio.run(main())

异常组可能保留多个任务甚至嵌套任务组的错误。按类型处理只消费匹配部分，未匹配错误继续传播，不要把整个异常组简单转换为一条“请求失败”后丢掉其余信息。同一 try 语句不能混用普通异常处理子句与异常组处理子句。

需求常用方式异常与取消策略
一组任务共同成功或失败TaskGroup普通失败取消兄弟任务，等待清理，再传播错误组
独立任务全部尝试并收集结果gather，显式接收异常结果调用方逐项判定成功、失败和取消
保留原始 Future 并等待一部分完成wait返回已完成/未完成集合；超时不自动取消剩余项
尽快消费已完成结果as_completed适合流式交付；仍需管理剩余任务
某个操作必须先完成再继续直接 await不新增独立任务作用域

单个子任务被取消通常不会触发任务组把所有兄弟都作为失败取消；任务组也不是回滚事务。成功写出的文件或外部请求需要业务补偿。对收集异常的聚合结果，取消异常属于 BaseException 分支，不应只检查普通 Exception 后把取消结果当作成功数据。

取消、超时和清理 ​

python
import asyncio

async def work() -> None:
    try:
        await asyncio.sleep(10)
    finally:
        print("清理完成")

async def main() -> None:
    try:
        async with asyncio.timeout(0.01):
            await work()
    except TimeoutError:
        print("等待超时")

if __name__ == "__main__":
    asyncio.run(main())
# 顺序：清理完成；等待超时

取消是协作式请求，通常在后续可取消的挂起点被接收。CancelledError 不是普通 Exception 的子类；如必须捕获，应完成清理后重新抛出。超时不等于操作系统级硬截止：阻塞代码、取消清理、吞掉取消都可能延长耗时；已发生的外部副作用也不会自动撤销。

主动取消：请求之后还要等待 ​

取消常见于用户断开、服务停止、超时或上层任务失败。正确步骤是“请求取消 → 等待任务响应 → 确认资源清理完成”，而不是调用取消方法后就丢掉引用。

python
import asyncio


async def main() -> None:
    started = asyncio.Event()
    cleaned = asyncio.Event()

    async def worker() -> None:
        try:
            started.set()
            await asyncio.Event().wait()
        except asyncio.CancelledError:
            print("收到取消请求")
            raise
        finally:
            cleaned.set()
            print("资源已释放")

    task = asyncio.create_task(worker(), name="cancellable-worker")
    await started.wait()
    task.cancel()
    try:
        await task
    except asyncio.CancelledError:
        assert task.cancelled()
        assert cleaned.is_set()
        print("调用方确认取消完成")


if __name__ == "__main__":
    asyncio.run(main())

预期依次输出收到请求、资源释放、调用方确认。清理可能包含异步操作，但再次取消仍可能打断清理中的等待；重要资源应使用成熟上下文管理器，并为关闭操作设置合理预算。不要在清理阶段无限重试。

若协程在接收取消前根本没有运行过，其函数体中的清理分支也未必执行。因此资源最好在协程自己的作用域内获取，避免父任务提前创建资源后，只指望尚未启动的子协程负责释放。

普通业务代码很少需要清除任务取消计数。吞掉取消后伪装成功会破坏上层超时和任务组协议；确实要把取消转换为业务结果时，应明确这一协议，并核对当前版本的取消计数规则。

超时预算、截止时间与屏蔽取消 ​

工具主要作用需要注意
timeout限制一个异步作用域到期取消当前任务，在作用域外转换成超时异常
timeout_at使用循环单调时钟的绝对截止时间不能传日历时间戳；适合共享总预算
wait_for等待单个可等待对象并设置超时通常会请求取消目标并等待其响应
wait等待集合中的完成条件超时返回尚未完成集合，不自动清理这些任务
shield阻止某次外层取消传播给内层任务外层仍被取消；内层仍需要所有者等待与回收

总预算和每次尝试的超时不同。若每次重试都重新获得完整的十秒预算，加上退避，用户实际等待可能远超十秒。可在外层设置整体截止时间，在内部为单次操作设置更短预算，重试和清理也要计入总耗时设计。

下面演示屏蔽只保护内层任务，不会让调用方免于超时。示例结束前显式等待内层任务，不留下后台工作：

python
import asyncio


async def main() -> None:
    gate = asyncio.Event()

    async def finish_later() -> str:
        await gate.wait()
        return "内层完成"

    task = asyncio.create_task(finish_later())
    try:
        async with asyncio.timeout(0.01):
            await asyncio.shield(task)
    except TimeoutError:
        assert not task.done()
        print("外层已超时，内层仍等待")
    finally:
        gate.set()
        print(await task)


if __name__ == "__main__":
    asyncio.run(main())

这里的小超时用于主动触发协议分支，没有用实际耗时作断言。屏蔽不是通用的“确保提交成功”：外部进程退出、内层主动取消、任务自身失败仍会发生。事务提交和支付类业务应依靠幂等键与最终状态查询，不应只依赖屏蔽取消。

异步不自动消除竞争 ​

单个事件循环线程内，协程通常在挂起点交接执行。若“检查状态 → await → 修改状态”，其他协程可能在中间改变状态，因此仍需 asyncio.Lock、队列或重新设计协议。异步锁只协调相应事件循环中的任务，不用于线程或进程同步。

阻塞网络库、time.sleep() 和耗时 CPU 循环会阻塞事件循环。阻塞 I/O 可用 asyncio.to_thread() 转移到线程；取消等待它的任务不等于停止已在运行的线程。CPU 工作考虑进程池或释放 GIL 的原生库。Notebook 已有事件循环时通常直接使用顶层 await，不要在运行中的循环里嵌套 asyncio.run()。

大量请求还需要限并发、连接复用、限速与背压。信号量限制正在工作的数量，却不阻止一次创建海量任务占用内存；需要有界队列和固定工作者。无穷重试会放大故障，只对可重试、可幂等的操作设置次数、退避和总预算。

异步锁：保护跨等待的不变量 ​

下面故意在读与写之间让出执行机会，让无锁丢更新稳定复现，不依赖随机的线程调度：

python
import asyncio


async def experiment(protected: bool) -> int:
    counter = 0
    lock = asyncio.Lock()

    async def update() -> None:
        nonlocal counter
        old = counter
        await asyncio.sleep(0)
        counter = old + 1

    async def worker() -> None:
        if protected:
            async with lock:
                await update()
        else:
            await update()

    async with asyncio.TaskGroup() as group:
        group.create_task(worker())
        group.create_task(worker())
    return counter


async def main() -> None:
    print(await experiment(False))  # 1：两个任务读取了同一个旧值
    print(await experiment(True))   # 2：完整读改写被保护


if __name__ == "__main__":
    asyncio.run(main())

异步锁等待不会阻塞整个事件循环线程，但持锁任务仍可能因等待外部 I/O 长时间不释放资源。示例为了显示竞态才在临界区内主动挂起；生产代码应尽量缩小保护范围，或使用单个消费者拥有状态。

不要用线程可重入锁保护协程临界区：同一事件循环内的协程往往属于同一个操作系统线程，这类锁可能允许多个协程进入。普通线程锁在竞争时又可能直接阻塞循环。同步工具必须匹配线程、进程或任务的实际执行模型。

异步事件、条件变量与信号量遵循类似线程原语的用途，但只能用于相应事件循环中的协作。若同时有线程访问共享数据，要明确所有权边界，通过线程安全的调度接口传消息，或另外设计线程同步层。

异步迭代、生成器与上下文清理 ​

异步迭代适合分页读取、游标、消息流等“下一条数据可能需要等待”的场景。消费者按需获取下一项形成拉取式节奏，但底层驱动是否预取、缓存多少数据，仍由其实现决定。

异步上下文管理器把获取和释放资源放在同一个作用域。异步生成器提前退出时，显式关闭可以让清理及时在当前任务中执行，而不必依赖垃圾回收或循环关闭。

python
import asyncio
from collections.abc import AsyncIterator
from contextlib import aclosing, asynccontextmanager


@asynccontextmanager
async def connection() -> AsyncIterator[dict[str, bool]]:
    resource = {"open": True}
    print("连接打开")
    try:
        yield resource
    finally:
        resource["open"] = False
        print("连接关闭")


async def rows() -> AsyncIterator[int]:
    try:
        for number in range(3):
            await asyncio.sleep(0)
            yield number
    finally:
        print("数据流关闭")


async def main() -> None:
    async with connection() as resource:
        async with aclosing(rows()) as stream:
            async for row in stream:
                assert resource["open"]
                print(row)
                if row == 1:
                    break
    assert not resource["open"]


if __name__ == "__main__":
    asyncio.run(main())

预期依次输出连接打开、0、1、数据流关闭、连接关闭。这个例子模拟资源协议，不实际建立网络连接。提前结束迭代不应被解释成“生产端一定已释放所有资源”；明确关闭是调用方与生成器之间的生命周期约定。

异步迭代协议中，获取迭代器的方法返回异步迭代器；获取下一项的方法返回可等待对象，并用异步迭代结束异常标记耗尽。它不是把一个普通列表放进异步循环就能工作，也不意味着多条数据自动并发处理。

固定工作者、有界队列与背压 ​

以下流水线使用一个生产者、三个消费者和容量为二的队列。异常策略是首个普通失败使任务组取消其余工作，属于共同成功或失败的批处理协议。

python
import asyncio


async def transform(number: int) -> int:
    await asyncio.sleep(0)
    return number * number


async def pipeline(count: int, fail_on: int | None = None) -> dict[int, int]:
    jobs: asyncio.Queue[int | None] = asyncio.Queue(maxsize=2)
    results: dict[int, int] = {}
    worker_count = 3

    async def produce() -> None:
        for number in range(count):
            await jobs.put(number)
        for _ in range(worker_count):
            await jobs.put(None)

    async def consume() -> None:
        while True:
            item = await jobs.get()
            try:
                if item is None:
                    return
                if item == fail_on:
                    raise ValueError("模拟流水线失败")
                results[item] = await transform(item)
            finally:
                jobs.task_done()

    async with asyncio.TaskGroup() as group:
        producer = group.create_task(produce())
        for _ in range(worker_count):
            group.create_task(consume())
        await producer
        await jobs.join()
    return results


async def main() -> None:
    async with asyncio.timeout(2):
        results = await pipeline(6)
        print(sorted(results.items()))
        try:
            await pipeline(6, fail_on=3)
        except* ValueError:
            print("失败已传播，其余工作已回收")


if __name__ == "__main__":
    asyncio.run(main())

成功时输出 0 到 5 的平方结果；失败测试不要求固定数量的任务已经完成，因为失败发生前其他任务可能已经推进。任务组退出保证相关任务已结束，但不保证已经产生的业务副作用回滚。

这里先等待生产者结束，再等待队列确认。如果在生产者尚未放入第一项时直接等待空队列，其完成计数可能本来就是零，会提前返回。消费者对每一条取出的消息执行一次确认，包括停止标记。

失败时，任务组取消生产者、消费者以及作用域中正在等待的父任务；不在外部强行等待未消费队列归零，否则可能永远等不到。若要继续处理其他数据项，应像线程示例那样把业务错误记录为结果；这是另一种协议，不要混用。

有界的是任务队列，不是结果字典。无限流需要输出消费者、分批提交或落盘，并对输出端设置背压。总内存预算要计算输入缓存、运行中数据、输出缓存、连接池内部缓存，而不仅是队列的容量。

限并发、限速、连接池与重试预算 ​

这四个概念经常被混成“加个信号量”，实际上约束不同：

机制约束的量典型目的
并发限制同时执行或占用资源的任务数防止连接、文件描述符和内存耗尽
速率限制单位时间内允许启动或完成的操作数满足 API 配额，平滑请求流量
连接池可复用连接及等待队列减少建连成本，约束下游连接数量
有界任务队列尚未被工作者取出的数据量防止入口生产速度无限超过处理速度
重试预算重试次数、总时间或重试比例避免故障时额外流量压垮下游

两个并发请求每次只需一毫秒，仍可能在一秒内发出大量请求；信号量不是每秒两次的限制器。真实限速常用令牌桶或漏桶，还需决定突发配额、跨实例共享和被限流时的响应。

下面只演示“并发配额 + 有上限的退避重试 + 整体超时”。任务数固定为三个，不是无限入口方案；没有真实网络请求。

python
import asyncio


class TransientError(Exception):
    pass


async def main() -> None:
    semaphore = asyncio.Semaphore(2)
    attempts: dict[str, int] = {}

    async def request(key: str) -> str:
        attempts[key] = attempts.get(key, 0) + 1
        await asyncio.sleep(0)
        if key == "B" and attempts[key] == 1:
            raise TransientError("临时不可用")
        return f"{key}:ok"

    async def request_with_retry(key: str) -> str:
        for attempt in range(3):
            try:
                async with semaphore:
                    return await request(key)
            except TransientError:
                if attempt == 2:
                    raise
                # 在配额外退避，让其他请求有机会执行。
                await asyncio.sleep(0.01 * (2 ** attempt))
        raise AssertionError("不可达")

    async with asyncio.timeout(2):
        async with asyncio.TaskGroup() as group:
            tasks = [group.create_task(request_with_retry(key)) for key in "ABC"]
    print([task.result() for task in tasks])  # ['A:ok', 'B:ok', 'C:ok']
    assert attempts == {"A": 1, "B": 2, "C": 1}


if __name__ == "__main__":
    asyncio.run(main())

实际网络重试还需要随机抖动、服务端重试提示和错误分类。身份认证失败、参数错误、程序缺陷通常不应重试；写操作只有在具备幂等保障或能确认未提交时才适合自动重试。不要捕获所有异常后无限循环，这会隐藏故障并吞掉停止协议。

异步 HTTP 客户端一般应在应用生命周期内复用会话和连接池，并显式关闭响应或完整消费响应体。每次请求重新创建连接池会失去复用价值。还应区分等待池连接、建立连接、读取数据和整体请求预算，避免只设置一个模糊超时。

同步代码与事件循环的桥接 ​

已有同步库不必全部重写，但必须明确把阻塞调用放在哪里执行。线程桥接适合阻塞 I/O；启用 GIL 的 CPython 中，纯 Python CPU 密集计算通常应使用进程池，而不是指望更多线程。

python
import asyncio
from contextvars import ContextVar
from threading import Event


request_id: ContextVar[str] = ContextVar("request_id", default="unset")


def blocking_io(release: Event) -> str:
    if not release.wait(timeout=2):
        raise TimeoutError("模拟 I/O 未释放")
    return request_id.get()


async def main() -> None:
    release = Event()
    token = request_id.set("request-42")
    try:
        async with asyncio.TaskGroup() as group:
            result = group.create_task(asyncio.to_thread(blocking_io, release))
            await asyncio.sleep(0)
            release.set()
        print(result.result())  # request-42
    finally:
        release.set()
        request_id.reset(token)


if __name__ == "__main__":
    asyncio.run(main())

线程桥接会传播当前上下文变量的上下文，适合请求标识、追踪信息等；它不是业务数据自动同步机制。子任务通常继承创建时的上下文副本，线程里的修改不会自动成为调用方的新值；上下文变量中保存的可变对象仍可能被共享。

取消正在等待线程桥接的任务，不会强制终止已经开始的同步函数。同步函数必须自己拥有超时或停止信号；事件循环关闭时对执行器的收尾仍可能等待这些线程。不要通过反复取消和重新发起操作，悄悄堆积越来越多的阻塞线程。

循环执行器接口可以显式接入线程池或进程池。使用进程池时仍然遵循函数顶层定义、参数可序列化及入口保护；请求上下文也不会自然跨进程传播，应该把必要字段作为普通数据传递。

从其他线程向事件循环发送消息 ​

大部分 asyncio 对象不是线程安全的。外部线程不要直接修改异步队列、设置异步 Future 结果或操作异步事件，应让事件循环在线程安全调度入口安排回调。

python
import asyncio
from threading import Thread


async def main() -> None:
    loop = asyncio.get_running_loop()
    message = loop.create_future()

    def deliver(value: str) -> None:
        # 回调在循环线程执行；结果可能已因取消而失效。
        if not message.done():
            message.set_result(value)

    def worker() -> None:
        loop.call_soon_threadsafe(deliver, "来自工作线程")

    thread = Thread(target=worker)
    thread.start()
    try:
        async with asyncio.timeout(2):
            print(await message)
    finally:
        await asyncio.to_thread(thread.join)


if __name__ == "__main__":
    asyncio.run(main())

在外部线程提交整个协程可使用线程安全的协程提交接口，它返回 concurrent.futures.Future。只应在外部线程用其阻塞结果方法；在事件循环线程内阻塞等待同一个循环才能完成的工作会死锁。提交之前还要确定循环仍存活，应用停止时先关闭入口，再回收线程与任务。

并发代码如何测试与调试 ​

并发测试应验证协议，而不是猜测线程或任务的执行顺序。用事件证明“已经进入某个阶段”，用受控释放证明“正在等待资源”，最终检查计数、结果和清理状态。短暂休眠不应成为“另一个任务一定已经启动”的证据。

下面是一个可独立运行的标准库测试脚本。五项测试分别覆盖线程共享状态、取消清理、超时清理、信号量上限和队列背压。异步测试类为每个测试创建独立事件循环；两秒超时只是防挂保护，不是性能指标，也不表示生产系统适合使用相同预算。

python
import asyncio
import unittest
from concurrent.futures import ThreadPoolExecutor
from threading import Lock


class ThreadTests(unittest.TestCase):
    def test_shared_counter(self) -> None:
        lock = Lock()
        counter = 0

        def increment() -> None:
            nonlocal counter
            for _ in range(100):
                with lock:
                    counter += 1

        with ThreadPoolExecutor(max_workers=4) as pool:
            futures = [pool.submit(increment) for _ in range(4)]
            for future in futures:
                future.result(timeout=2)
        self.assertEqual(counter, 400)


class AsyncTests(unittest.IsolatedAsyncioTestCase):
    async def test_cancel_runs_cleanup(self) -> None:
        started = asyncio.Event()
        cleaned = asyncio.Event()

        async def worker() -> None:
            try:
                started.set()
                await asyncio.Event().wait()
            finally:
                cleaned.set()

        task = asyncio.create_task(worker())
        try:
            async with asyncio.timeout(2):
                await started.wait()
                task.cancel()
                with self.assertRaises(asyncio.CancelledError):
                    await task
            self.assertTrue(cleaned.is_set())
            self.assertTrue(task.cancelled())
        finally:
            task.cancel()
            await asyncio.gather(task, return_exceptions=True)

    async def test_timeout_runs_cleanup(self) -> None:
        cleaned = asyncio.Event()
        with self.assertRaises(TimeoutError):
            async with asyncio.timeout(0.01):
                try:
                    await asyncio.Event().wait()
                finally:
                    cleaned.set()
        self.assertTrue(cleaned.is_set())

    async def test_semaphore_limit(self) -> None:
        semaphore = asyncio.Semaphore(2)
        full = asyncio.Event()
        release = asyncio.Event()
        active = peak = completed = 0

        async def worker() -> None:
            nonlocal active, peak, completed
            async with semaphore:
                active += 1
                peak = max(peak, active)
                try:
                    if active == 2:
                        full.set()
                    await release.wait()
                    completed += 1
                finally:
                    active -= 1

        async with asyncio.timeout(2):
            async with asyncio.TaskGroup() as group:
                for _ in range(5):
                    group.create_task(worker())
                await full.wait()
                self.assertEqual(active, 2)
                release.set()
        self.assertEqual(peak, 2)
        self.assertEqual(active, 0)
        self.assertEqual(completed, 5)

    async def test_queue_backpressure(self) -> None:
        queue: asyncio.Queue[int] = asyncio.Queue(maxsize=1)
        started = asyncio.Event()
        await queue.put(1)

        async def produce() -> None:
            started.set()
            await queue.put(2)

        async with asyncio.timeout(2):
            async with asyncio.TaskGroup() as group:
                producer = group.create_task(produce())
                await started.wait()
                # set 与 put 之间没有挂起点；满队列使生产者停在 put。
                self.assertFalse(producer.done())
                self.assertEqual(await queue.get(), 1)
                queue.task_done()
                await producer
                self.assertEqual(await queue.get(), 2)
                queue.task_done()
                await queue.join()


if __name__ == "__main__":
    unittest.main(verbosity=2)

线程池的退出仍会等待已启动任务，结果等待的超时不能强杀线程；上述递增操作是有限且不阻塞的。若测试可能调用失控的外部库，应使用独立子进程作为测试隔离边界，由测试运行器限制总运行时间，而不是只依赖单次结果等待超时。

还应扩展哪些失败用例？

  • 工作者在拿到任务之前、处理途中、写出结果之后分别失败，确认任务是否重试、丢弃或重复提交。
  • 消费者失败时生产者正等待满队列，确认停止路径不会卡死。
  • 取消发生在启动前、等待连接时、收到结果后，确认资源所有权不含糊。
  • 同时出现多个普通异常，确认异常组被正确分流，而不是只记录第一条。
  • 慢下游、输出端阻塞和大量输入下，检查内存是否稳定，而不只观察吞吐量。

调试异步程序时，可在启动入口开启调试模式，或设置 PYTHONASYNCIODEBUG 环境变量。结合警告检查未等待的协程、未读取的任务异常、慢回调和未关闭资源；给长生命周期任务命名，并在必要时枚举存活任务及其等待栈。

监控至少区分排队时间、执行时间、端到端延迟、当前并发数、队列深度、重试次数与取消原因。线程安全的日志处理器也可能阻塞事件循环；高吞吐场景可把日志 I/O 交给队列和专门的处理线程，同时定义日志队列满时的策略。

性能分析与优化 ​

核心概念

先建立正确性基线，再测量真实工作负载，最后优化最昂贵的部分，并重新验证结果。

工具回答的问题注意事项

优化顺序一般是：减少重复工作和 I/O → 改进算法/数据结构 → 分批处理和有界缓存 → 合适的并发 → 必要时原生扩展。列表成员查询通常是线性的，集合平均常数级但需额外内存且元素可哈希。生成器降低部分中间存储开销，不保证更快，也不保证下游不会把所有数据重新物化。

functools.lru_cache 适合相同可哈希参数产生稳定结果的计算；考虑内存上限、失效、可变返回值和并发重复计算，不能直接缓存依赖外部变化而无失效策略的结果。测量时记录解释器、平台、输入规模、重复次数与分位数，避免把一次最快结果包装成生产承诺。

描述符、属性查找与 MRO（选学） ​

核心概念

属性访问是一个协议，不只是查字典。理解描述符与方法解析顺序，才能解释方法绑定、属性和多重继承。

在常规属性访问下，可粗略理解为：沿类型的 MRO 找数据描述符 → 查实例字典 → 找非数据描述符或类属性 → 必要时调用 __getattr__()。自定义 __getattribute__() 可以改变行为，带槽实例也不一定有实例字典。

实现 __get__ 且提供 __set__ 或 __delete__ 的描述符通常作为数据描述符；普通函数是非数据描述符，访问实例方法时产生绑定方法。property 是数据描述符，不是“把方法结果存进实例”。

以下示例用描述符复用非空字段校验，输出“阅读”：

python
class NonEmpty:
    def __set_name__(self, owner, name):
        self.storage_name = "_" + name

    def __get__(self, instance, owner=None):
        if instance is None:
            return self
        return getattr(instance, self.storage_name)

    def __set__(self, instance, value):
        if not isinstance(value, str) or not value.strip():
            raise ValueError("字段必须是非空字符串")
        setattr(instance, self.storage_name, value.strip())

class Book:
    title = NonEmpty()

    def __init__(self, title):
        self.title = title

print(Book(" 阅读 ").title)

super() 根据当前类型的 MRO 继续查找，不是简单地“调用写在括号里的父类”。协作式多继承需要参与类一致地调用 super() 并设计兼容参数；MRO 使用 C3 线性化，不一致的继承关系会在类创建时失败。

python
class Root:
    def names(self):
        return ["Root"]

class Left(Root):
    def names(self):
        return ["Left"] + super().names()

class Right(Root):
    def names(self):
        return ["Right"] + super().names()

class Leaf(Left, Right):
    pass

print(Leaf().names())  # ['Left', 'Right', 'Root']
print([cls.__name__ for cls in Leaf.__mro__])
# ['Leaf', 'Left', 'Right', 'Root', 'object']

类本身也是对象，通常由 type 创建。元类可以干预类的创建，但日常项目优先函数、组合、类装饰器和 __init_subclass__()；不要仅为了“高级”引入难以调试的元编程。

    """可向终端用户展示的业务或存储错误。"""


def clean_title(value: object) -> str:

        raise TaskError("任务标题必须是字符串")
    title = value.strip()
    if not title or len(title) > 200 or not title.isprintable():
        raise TaskError("标题必须为 1～200 个可打印字符")
    return title

JSON 存储与失败保护 ​

tasker/storage.py：

python
# file: tasker/storage.py
import json
import logging
import os
import tempfile
from dataclasses import asdict
from pathlib import Path

from .models import State, Task, TaskError, clean_title

logger = logging.getLogger(__name__)
MAX_BYTES = 1_000_000


def decode_state(raw: object) -> State:
    if not isinstance(raw, dict) or set(raw) != {"version", "next_id", "tasks"}:
        raise TaskError("数据文件顶层结构无效")
    if type(raw["version"]) is not int or raw["version"] != 1:
        raise TaskError("不支持的数据版本")
    next_id = raw["next_id"]
    rows = raw["tasks"]
    if type(next_id) is not int or next_id < 1 or not isinstance(rows, list):
        raise TaskError("任务列表或下一个编号无效")
    tasks: list[Task] = []
    seen: set[int] = set()
    for row in rows:
        if not isinstance(row, dict) or set(row) != {"id", "title", "done"}:
            raise TaskError("任务字段无效")
        number = row["id"]
        if type(number) is not int or not 1 <= number < next_id or number in seen:
            raise TaskError("任务编号无效或重复")
        if type(row["done"]) is not bool:
            raise TaskError("完成状态必须是布尔值")
        title = clean_title(row["title"])
        if title != row["title"]:
            raise TaskError("存储的标题不应有首尾空白")
        seen.add(number)
        tasks.append(Task(number, title, row["done"]))
    return State(next_id, tasks)


def unique_object(pairs: list[tuple[str, object]]) -> dict[str, object]:
    result: dict[str, object] = {}
    for key, value in pairs:
        if key in result:
            raise TaskError(f"JSON 包含重复字段：{key!r}")
        result[key] = value
    return result


def load(path: Path) -> State:
    try:
        with path.open("rb") as stream:
            content = stream.read(MAX_BYTES + 1)
    except FileNotFoundError:
        return State()
    except OSError as exc:
        raise TaskError(f"无法读取数据文件：{exc}") from exc
    if len(content) > MAX_BYTES:
        raise TaskError("数据文件超过大小上限")
    try:
        raw = json.loads(content.decode("utf-8"), object_pairs_hook=unique_object)
    except (UnicodeError, ValueError, RecursionError) as exc:
        raise TaskError("数据文件不是有效的 UTF-8 JSON") from exc
    return decode_state(raw)


def save(path: Path, state: State) -> None:
    raw = {"version": 1, "next_id": state.next_id, "tasks": [asdict(t) for t in state.tasks]}
    decode_state(raw)  # 写入前验证，不把错误状态落盘
    content = (json.dumps(raw, ensure_ascii=False, indent=2) + "\n").encode("utf-8")
    if len(content) > MAX_BYTES:
        raise TaskError("保存结果超过大小上限")
    temporary: Path | None = None
    try:
        # 不自动创建父目录，路径拼错时明确失败。
        with tempfile.NamedTemporaryFile(
            mode="wb", dir=path.parent, prefix=".tasker-", delete=False
        ) as stream:
            temporary = Path(stream.name)
            stream.write(content)
            stream.flush()
            os.fsync(stream.fileno())
        # Windows 上先关闭临时文件，再替换目标文件。
        os.replace(temporary, path)
        temporary = None
    except OSError as exc:
        raise TaskError(f"无法保存数据文件：{exc}") from exc
    finally:
        if temporary is not None:
            try:
                temporary.unlink(missing_ok=True)
            except OSError:
                logger.warning("清理临时文件失败：%s", temporary)

解释几个刻意的设计：

  • 只有文件不存在才视作新数据库；空文件、乱码、结构错误、未知版本都会失败。
  • bool 是 int 的子类，因此编号使用精确整数类型判断，拒绝 true 冒充编号。
  • 从文件读取最多上限加一个字节，超限立即拒绝；这不是通用的不可信 JSON 沙箱，生产仍需更强资源隔离和深度限制。
  • 编号不使用“列表长度加一”，删除任务后也不会立即复用编号。
  • 先验证和序列化，再写临时文件；写入或替换失败时保留原文件并尽量清理临时文件。
  • fsync 文件后再替换仍不等于完全的掉电保障，父目录同步和文件系统语义等问题需单独设计。替换也不保证保留原文件全部权限或元数据。

# file: tasker/service.py
from .models import State, Task, TaskError, clean_title


def add_task(state: State, title: str) -> Task:
    task = Task(state.next_id, clean_title(title))
    state.tasks.append(task)
    state.next_id += 1
    return task


def find_task(state: State, number: int) -> Task:
    for task in state.tasks:
        if task.id == number:
            return task
    raise TaskError(f"任务不存在：{number}")


def complete_task(state: State, number: int) -> Task:
    task = find_task(state, number)
    task.done = True  # 重复完成同一任务仍然成功，操作幂等。
    return task


def delete_task(state: State, number: int) -> Task:
    task = find_task(state, number)
    state.tasks.remove(task)
    return task

业务层没有命令行解析、文件路径或日志配置，可以直接在内存里测试。此处线性查找足够；是否引入编号索引应由数据规模和测量决定。

# file: tasker/cli.py
import argparse
import logging
from pathlib import Path

from .models import TaskError
from .service import add_task, complete_task, delete_task
from .storage import load, save

logger = logging.getLogger(__name__)


def make_parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser(description="本地任务管理器")
    parser.add_argument("--db", type=Path, default=Path("tasks.json"), help="数据文件路径")
    parser.add_argument("--verbose", action="store_true", help="显示调试日志")
    commands = parser.add_subparsers(dest="command", required=True)
    add = commands.add_parser("add", help="新增任务")
    add.add_argument("title")
    listing = commands.add_parser("list", help="列出任务")
    listing.add_argument("--pending", action="store_true", help="仅未完成任务")
    for command in ("done", "delete"):
        sub = commands.add_parser(command)
        sub.add_argument("id", type=int)
    return parser


def main(argv: list[str] | None = None) -> int:
    args = make_parser().parse_args(argv)
    logging.basicConfig(
        level=logging.DEBUG if args.verbose else logging.WARNING,
        format="%(levelname)s %(message)s",
    )
    try:
        state = load(args.db)
        logger.debug("读取到 %d 个任务", len(state.tasks))
        if args.command == "list":
            tasks = [task for task in state.tasks if not args.pending or not task.done]
            if not tasks:
                print("暂无任务")
            for task in tasks:
                mark = "x" if task.done else " "
                print(f"{task.id} [{mark}] {task.title}")
            return 0
        if args.command == "add":
            task = add_task(state, args.title)
            message = f"已新增 #{task.id}: {task.title}"
        elif args.command == "done":
            task = complete_task(state, args.id)
            message = f"已完成 #{task.id}"
        else:
            task = delete_task(state, args.id)
            message = f"已删除 #{task.id}"
        save(args.db, state)
        print(message)  # 保存成功之后才报告成功。
        return 0
    except TaskError as exc:
        logger.error("%s", exc)
        return 1

附录：正则表达式 ​

正则适合模式匹配、提取和简单清洗，不适合独自解析任意嵌套语法。字符串转义与正则转义是两层规则，模式通常用原始字符串书写。

python
import re

pattern = re.compile(r"(?P<year>\d{4})-(?P<month>\d{2})-(?P<day>\d{2})")
match = pattern.fullmatch("2026-09-20")
if match:
    print(match.groupdict())
# {'year': '2026', 'month': '09', 'day': '20'}
print(re.sub(r"\s+", " ", "hello   python"))  # hello python
print(re.findall(r"[A-Za-z]+", "Python 3.11"))  # ['Python']
构造 / API含义
.、\d、\w、\s任意非换行字符、数字、单词字符、空白，受标志影响
[]、[^]字符集合、集合取反；取反方括号内仍需具体字符
*、+、?、{m,n}重复次数；后接 ? 通常改为非贪婪
^、$行/字符串位置锚点，受多行标志等影响
()、(?:...)捕获组、非捕获组
search()找第一个匹配
match()从起点匹配，不等于匹配全部
fullmatch()要求完整匹配
finditer()逐个产生匹配对象

上例只检查日期形状，不保证月份或日期真实存在；需要再交给 datetime.date 等校验。Python 的 \d 默认匹配 Unicode 十进制数字，只接受 ASCII 数字时使用 [0-9] 或适当标志。恶意输入可能触发灾难性回溯，限制输入长度，避免含糊嵌套量词；标准库 re 没有通用的单次匹配超时参数。

可在 regex101 选择 Python 模式辅助理解，但最终用目标 Python 版本的 re 验证，且不要上传敏感内容。

except (urllib.error.URLError, TimeoutError, OSError) as exc:
    print("请求失败：", exc)

这里的 timeout 不是完整请求的严格总预算；DNS、分段读取等阶段的行为需结合客户端和平台理解。响应头的编码、内容类型和正文都不能盲目信任。解析 JSON 后仍需字段验证。面向外部输入的 URL 必须考虑 SSRF、重定向与内网访问，不要把这个固定网址示例改成无约束的代理接口。

选择 requests 或 httpx 时先在虚拟环境安装并声明依赖，配置连接/读取等超时与连接池；异步代码使用真正的异步客户端。仅对允许重试的错误重试，并考虑操作幂等性、速率限制、总预算和取消。

Socket 是字节流，不是消息队列 ​

TCP 提供有序字节流，不保留应用消息边界。一次 send() 不保证发送全部，一次 recv() 不保证收到一条完整消息；采用 sendall() 并设计长度前缀、分隔符或固定长度协议。recv() 返回空字节串通常表示对端有序关闭，不能当成“暂时没数据”。

下面示例只使用本机 socket 对，不打开公网端口；通过长度前缀和循环读取展示分帧，Python 3.11 的常见 Windows/macOS/Linux 环境可运行：

python
import socket
import struct

def receive_exact(sock: socket.socket, size: int) -> bytes:
    chunks = bytearray()
    while len(chunks) < size:
        piece = sock.recv(size - len(chunks))
        if not piece:
            raise EOFError("消息尚未完整接收，连接已关闭")
        chunks.extend(piece)
    return bytes(chunks)

left, right = socket.socketpair()
with left, right:
    left.settimeout(2)
    right.settimeout(2)
    payload = "你好".encode("utf-8")
    left.sendall(struct.pack("!I", len(payload)) + payload)
    size = struct.unpack("!I", receive_exact(right, 4))[0]
    if size > 1024:
        raise ValueError("消息过大")
    print(receive_exact(right, size).decode("utf-8"))  # 你好

这里只发送很小的消息；同线程先发送全部大数据再读取可能填满缓冲区并阻塞，不是服务架构模板。真实服务还需处理连接生命周期、认证、TLS、读写总预算、并发上限、消息大小和半连接等问题。UDP 保留数据报边界，但不保证可靠交付、顺序或不重复，应按应用需求设计协议。

问题答案要点
为什么值比较通常用 ==，判断 None 用 is？值相等与对象身份不同；None 是单例，缓存优化不是比较值的依据
为什么函数内部修改列表会影响调用方，重新赋值未必会？共享的是对象，重新赋值只改变局部绑定
浅复制后的外层列表不同，为什么内部仍联动？内层引用没有被递归复制；深复制也不是任意资源克隆
为什么可变默认参数会“记住”前一次调用？默认值在函数定义时创建，多次调用复用同一对象
sort() 与 sorted() 的返回值有什么区别？前者原地修改并返回 None，后者生成新列表
finally 能否在所有情况下执行？正常异常展开一般执行，进程被强杀、崩溃等不能保证
类型注解和数据类能否验证外部 JSON？不能自动验证，仍需边界校验和明确转换
为什么第二次遍历生成器可能没有内容？迭代器有状态且可能已经耗尽，不是可自动重放的数据源
super() 一定调用直接父类吗？按 MRO 继续查找，协作式多继承中可能到兄弟分支
有 GIL 为什么仍然需要锁？复合操作与业务不变量不自动原子化，I/O 和扩展还可能释放 GIL
