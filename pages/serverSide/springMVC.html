一、MVC 认知篇 ​

1.1 从 Servlet 到 Spring MVC ​

概念

Spring MVC（全称 Spring Web MVC）是 Spring 家族中专门负责表述层（Web 层）的模块。它本质上是对 Servlet 规范的一层封装：整个框架对外只向 Servlet 容器注册了一个 DispatcherServlet，再由它把请求分发给成百上千个 Controller 方法。

先看没有框架时，一个原始 Servlet 要自己做多少事：

java
// ❌ 原生 Servlet：业务逻辑只有 1 行，其余全是重复的"体力活"
public class UserServlet extends HttpServlet {
    protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        // 1. 手动解决请求编码
        req.setCharacterEncoding("UTF-8");
        // 2. 手动按名字取参数，全都是 String
        String idStr = req.getParameter("id");
        String name  = req.getParameter("name");
        // 3. 手动做类型转换 + 判空 + 异常处理
        Integer id;
        try {
            id = Integer.valueOf(idStr);
        } catch (NumberFormatException e) {
            resp.setStatus(400);
            return;
        }
        // 4. 手动封装成对象
        User user = new User(id, name);
        // ====== 真正的业务只有这一行 ======
        userService.save(user);
        // 5. 手动序列化 JSON、手动设响应头
        resp.setContentType("application/json;charset=UTF-8");
        resp.getWriter().write("{\"code\":200,\"msg\":\"ok\"}");
    }
}

同样的功能，用 Spring MVC 写：

java
// ✅ Spring MVC：只剩业务语义，1~5 全部交给框架
@RestController
@RequestMapping("/users")
public class UserController {

    @PostMapping
    public Result save(@RequestBody @Valid User user) {
        userService.save(user);
        return Result.success(null);
    }
}

两段代码的差异，正是 Spring MVC 帮你接管的五件事：

原生 Servlet 要手写Spring MVC 的对应机制
一个 URL 配一个 ServletHandlerMapping 统一路由到方法
getParameter 逐个取、全是 StringHandlerMethodArgumentResolver 自动绑定
手写 Integer.valueOf、日期解析Converter / Formatter 类型转换体系
手写 JSON 拼串HttpMessageConverter 自动序列化
每个 Servlet 自己 try-catchHandlerExceptionResolver 全局异常处理

TIP

一句话定位：Spring MVC = 一个总调度的 Servlet（DispatcherServlet） + 一套可插拔的组件（九大组件）。 后面所有看起来零散的注解（@RequestParam、@ResponseBody、@ExceptionHandler……），本质上都是在给这九大组件喂配置。把这句话记住，整篇文档就有了主干。

1.2 MVC 模式与三层架构辨析 ​

这是初学者最容易混为一谈的两个概念，必须先拆清楚：它们切的不是同一刀。

概念

  • MVC：是表述层内部的职责划分模式，解决的是"一次 HTTP 请求如何在 Web 层流转"。
  • 三层架构：是整个应用的纵向分层（表述层 / 业务层 / 持久层），解决的是"代码按职责放在哪一层"。
text
                     三层架构（纵向切整个应用）
  ┌──────────────────────────────────────────────────────┐
  │  表述层 Controller        ← MVC 只作用在这一层内部！  │
  │   ┌────────────────────────────────────────────────┐ │
  │   │  MVC：  C(Controller) ──► M(Model) ──► V(View) │ │
  │   └────────────────────────────────────────────────┘ │
  ├──────────────────────────────────────────────────────┤
  │  业务层 Service           事务边界、业务编排          │
  ├──────────────────────────────────────────────────────┤
  │  持久层 Dao/Mapper        SQL、ORM 映射               │
  └──────────────────────────────────────────────────────┘
维度MVC三层架构
作用范围仅表述层内部整个应用
划分依据一次请求中的角色（控制/数据/展现）代码的职责归属
典型产物Controller、ModelAndView、ViewController、Service、Dao
对应框架Spring MVCSpring（IoC 把三层粘起来）

TIP

判断口诀：问"这个类放哪一层"，答案来自三层架构；问"这次请求下一步走到谁"，答案来自 MVC。 Service 和 Dao 不属于 MVC 里的任何一个字母——它们整体被 MVC 看作"Model 的数据来源"。

WARNING

📌 单独澄清：MVC 里的 M 到底是什么？

很多人以为 Model = Service 或 = 数据库实体，这是错的。

  • MVC 的 M 指"本次请求要渲染/返回的数据"，在 Spring MVC 里具体就是 Model、ModelMap、ModelAndView 里装的那些键值对，或者前后端分离下 @ResponseBody 返回的那个对象。
  • Service 是业务层的概念，它负责生产这些数据，但它自己不是 M。
java
@GetMapping("/detail")
public String detail(Integer id, Model model) {   // ← Model 才是 MVC 的 M
    User user = userService.getById(id);          // ← Service 是三层架构的业务层
    model.addAttribute("user", user);             // ← 往 M 里塞数据
    return "user/detail";                         // ← 返回逻辑视图名，交给 V
}

Spring MVC 的能力可以归到四条主线，后面六篇正文分别展开其中一条或几条：

text
   ① 路由           ② 入参              ③ 出参            ④ 横切

特点具体体现
Spring 原生与 IoC 容器无缝对接，Controller 就是一个普通 Bean，可直接注入 Service
组件可插拔九大组件全部面向接口，任何一个都能换成自定义实现

1.4 第一个 HelloWorld ​

① 引入依赖（Spring Boot 环境，spring-boot-starter-web 已内置 Tomcat + Spring MVC + Jackson）：

xml
<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>

    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-test</artifactId>
        <scope>test</scope>
    </dependency>
</dependencies>

② 编写 Controller：

java
package com.at.controller;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController                      // = @Controller + @ResponseBody
public class HelloController {

    @GetMapping("/hello")
    public String hello() {
        return "hello springMVC!!!";  // 直接作为响应体写回，不走视图解析
    }
}

③ 启动并验证：运行主启动类后访问 http://localhost:8080/hello，页面显示 hello springMVC!!!。

WARNING

最常见的"404 为什么"：@RestController 所在的包必须在主启动类所在包或其子包下。 Spring Boot 的组件扫描默认以 @SpringBootApplication 标注的类所在包为根，写在根包之外（例如启动类在 com.at.app，Controller 在 com.other.web）时，Controller 根本不会被注册成 Bean，自然也不会生成路由，表现就是干净利落的 404。

TIP

启动后立刻做一件事：在 application.properties 里加上这行，启动日志会打印出所有已注册的 URL 映射表，是排查 404 的第一手段。

properties
logging.level.org.springframework.web.servlet.mvc.method.annotation.RequestMappingHandlerMapping=TRACE

2.1 DispatcherServlet：前端控制器 ​

概念

DispatcherServlet（前端控制器） 是 Spring MVC 的唯一入口 Servlet。它本身不处理任何业务，只负责「接收请求 → 找到合适的组件 → 按顺序调用它们 → 把结果写回响应」，是典型的 Front Controller 模式。

没有它会怎样？ 回到 Servlet 时代：每个 URL 一个 Servlet，web.xml 里堆几十个 <servlet-mapping>，而且鉴权、日志、编码、异常处理这些横切逻辑要在每个 Servlet 里重写一遍。前端控制器把这些公共动作收敛到唯一入口，于是横切能力（拦截器、全局异常、内容协商）才有了统一的挂载点。

text
                         ┌──────────────────────────────┐
  浏览器 ──── 请求 ─────▶ │     DispatcherServlet        │
                         │  （唯一入口 / 不写业务代码）   │
                         └───┬────────┬────────┬────────┘
                             │        │        │
                 查"谁来处理"│  "怎么调"│  "结果怎么渲染"
                             ▼        ▼        ▼
                     HandlerMapping  HandlerAdapter  ViewResolver
                             │        │        │
                             └────────┴────────┴──▶ 你的 Controller

它是怎么被注册到 Tomcat 的？

环境注册方式
传统 XMLweb.xml 中配置 <servlet> + <servlet-mapping>，url-pattern 通常为 /
Servlet 3.0+实现 WebApplicationInitializer，用 Java 代码注册
Spring BootDispatcherServletAutoConfiguration 自动注册，默认映射 /

WARNING

/ 和 /* 千万别写错，这是 XML 时代的经典事故：

  • /：匹配所有请求，但不包括 *.jsp（JSP 交给容器自带的 JspServlet）。✅ 正确写法
  • /*：匹配所有请求，包括 *.jsp。此时转发到 JSP 的请求会被 DispatcherServlet 再次拦下，当成一个"handler 找不到"的普通请求 → 404 或死循环。❌

判断口诀：/ 是"兜底"，/* 是"通吃"；视图层有 JSP 就必须用 /。

2.2 九大组件全景 ​

DispatcherServlet 在 initStrategies() 里初始化九个策略组件，默认实现写在 spring-webmvc 包下的 DispatcherServlet.properties 中——这也是"组件可插拔"的物理证据。

组件职责常用默认实现
HandlerMapping根据请求找到 Handler（方法）+ 拦截器链RequestMappingHandlerMapping
HandlerAdapter适配不同类型的 Handler 并真正执行它RequestMappingHandlerAdapter
HandlerExceptionResolver处理 Handler 抛出的异常ExceptionHandlerExceptionResolver
ViewResolver把逻辑视图名解析成 View 对象InternalResourceViewResolver
LocaleResolver解析国际化区域信息AcceptHeaderLocaleResolver
ThemeResolver解析主题（现已基本不用）FixedThemeResolver
MultipartResolver解析文件上传请求（multipart/form-data）StandardServletMultipartResolver
RequestToViewNameTranslator没有返回视图名时，按请求路径推断一个DefaultRequestToViewNameTranslator
FlashMapManager管理重定向之间传递的 Flash 属性SessionFlashMapManager

TIP

九大组件不用死记，只要记住三个"主力"：HandlerMapping（找谁）、HandlerAdapter（怎么调）、HandlerExceptionResolver（出错了谁兜底）。前后端分离项目里 ViewResolver、ThemeResolver 几乎用不到，面试被问到时能点出「前三个是核心，其余按需」比背全九个更能体现理解。

          │⑪ afterCompletion()  ← 拦截器逆序执行（无论成败都走）
          ▼
  ⑫ 响应返回浏览器

分叉点在第 ⑦ 步，这是理解整条链路的关键：

分支走的路线典型场景
有 @ResponseBody返回值 → HttpMessageConverter → 直接写进响应体前后端分离接口
无 @ResponseBody返回值 → ModelAndView → ViewResolver → View 渲染JSP / Thymeleaf

WARNING

@ResponseBody 之后 ViewResolver 完全不参与。很多人困惑"为什么配了视图解析器前缀后缀却不生效"，答案就在这里：方法（或类）上带 @RestController / @ResponseBody 时，流程在第 ⑦ 步就已经终止，postHandle() 虽然还会执行，但此时响应体早已写出，在 postHandle() 里修改 ModelAndView 没有任何效果（此时它本身就是 null）。

2.4 HandlerMapping 与 HandlerAdapter ​

这两个组件名字像、位置挨着，但职责完全不同，是必须拆清的一组边界。

概念

  • HandlerMapping（映射器）：解决 "谁来处理这个请求"。输入是 HttpServletRequest，输出是 HandlerExecutionChain（处理器 + 匹配到的拦截器链）。
  • HandlerAdapter（适配器）：解决 "这个处理器怎么调用"。输入是上一步找到的 Handler，输出是 ModelAndView（或 null）。

为什么需要适配器？ 因为 Handler 的形态不止一种：

Handler 形态对应 HandlerAdapter说明
@RequestMapping 标注的方法RequestMappingHandlerAdapter99% 的场景，参数千变万化
实现 Controller 接口的类SimpleControllerHandlerAdapter老式写法
实现 HttpRequestHandler 的类HttpRequestHandlerAdapter静态资源、远程调用导出器

注解方法的签名完全自由——参数可以是 String、POJO、HttpServletRequest、@RequestBody 对象……DispatcherServlet 不可能为每种签名写一套调用逻辑，于是用适配器模式把"怎么解析参数、怎么反射调用、怎么处理返回值"全部下沉给 HandlerAdapter。

TIP

判断口诀：Mapping 管"找人"，Adapter 管"干活"。 排查时也对应两类问题：404 查 HandlerMapping（路由没注册 / 路径写错），400、参数为 null 查 HandlerAdapter（参数解析器没匹配上）。

2.5 父子容器与组件装配 ​

传统 SSM 项目里存在两个 IoC 容器，这是许多"注入为 null""事务不生效"问题的根源：

text
  ┌──────────────────────── 父容器（Root WebApplicationContext）────────────────────┐
  │   由 ContextLoaderListener 创建                                                  │
  │   扫描：@Service / @Repository / 数据源 / 事务管理器 / MyBatis                    │
  └──────────────────────────────────────────────────────────────────────────────────┘
                                      ▲
                                      │ 子可见父，父不可见子
                                      │
  ┌──────────────────────── 子容器（Servlet WebApplicationContext）──────────────────┐
  │   由 DispatcherServlet 创建                                                      │
  │   扫描：@Controller / 拦截器 / 视图解析器 / 消息转换器                            │
  └──────────────────────────────────────────────────────────────────────────────────┘
规则说明
子 → 父 可见Controller 能注入 Service ✅
父 → 子 不可见Service 无法注入 Controller ❌（也不应该这么做）
同名 Bean子容器优先使用自己的那份，容易造成"两份单例"

WARNING

经典事故：事务失效。如果父容器扫描时写成 <context:component-scan base-package="com.at"/>（全包扫描），Controller 会在父容器里先被创建一份；子容器再扫一遍又创建一份。请求实际用的是子容器那份，而 AOP 事务代理可能只织入了父容器那份 → 表现为"事务注解明明加了却不回滚"。

正确做法是父子各扫各的：

xml
<!-- 父容器：排除 Controller -->
<context:component-scan base-package="com.at">
    <context:exclude-filter type="annotation"
        expression="org.springframework.stereotype.Controller"/>
</context:component-scan>

<!-- 子容器：只扫 Controller -->
<context:component-scan base-package="com.at" use-default-filters="false">
    <context:include-filter type="annotation"
        expression="org.springframework.stereotype.Controller"/>
</context:component-scan>

TIP

Spring Boot 下没有父子容器，只有一个 AnnotationConfigServletWebServerApplicationContext，所以上面的坑天然不存在。但面试仍高频提问，且维护老 SSM 项目时必然遇到——记住判断口诀：看到"注入为 null / 事务不回滚 / 拦截器不生效"三连，先问有没有重复扫描。

三、请求映射与参数绑定篇 ​

3.1 @RequestMapping 详解 ​

概念

@RequestMapping 用来把请求地址和处理方法绑定起来。它可以标注在类上（作为公共前缀）和方法上（具体路径），最终路径是两者拼接的结果。

① 标注位置

java
@Controller
@RequestMapping("/user")          // 类级：公共前缀
public class UserController {

    @RequestMapping("/list")      // 方法级：最终访问 /user/list
    @ResponseBody
    public String list() {
        return "user list";
    }
}

② 常用属性

属性作用示例
value请求路径，支持数组（多路径映射同一方法）@RequestMapping({"/a", "/b"})
method限定请求方式method = RequestMethod.POST
params限定必须/禁止携带某参数params = {"type", "!debug", "status=1"}
headers限定请求头headers = "X-Token"
consumes限定请求体类型（Content-Type）consumes = "application/json"
produces限定响应体类型（Accept），常用于指定编码produces = "application/json;charset=UTF-8"
java
@RequestMapping(
    value = "/save",
    method = RequestMethod.POST,
    params = {"type", "status=1"},   // 必须带 type，且 status 必须等于 1
    consumes = "application/json",
    produces = "application/json;charset=UTF-8"
)

③ 路径匹配通配符

通配符含义示例匹配
?任意一个字符/a?c/abc ✅ ／ /ac ❌ ／ /abbc ❌
*任意多个字符（单层）/user/*/list/user/1/list ✅ ／ /user/1/2/list ❌
**任意多层路径/static/**/static/a/b/c.js ✅

④ 五个组合注解（Spring 4.3+，推荐使用，语义更清晰）

组合注解等价写法RESTful 语义
@GetMapping@RequestMapping(method = RequestMethod.GET)查询
@PostMapping@RequestMapping(method = RequestMethod.POST)新增
@PutMapping@RequestMapping(method = RequestMethod.PUT)全量更新
@DeleteMapping@RequestMapping(method = RequestMethod.DELETE)删除
@PatchMapping@RequestMapping(method = RequestMethod.PATCH)局部更新

WARNING

**只能出现在路径末尾。Spring 5.3 启用了新的PathPatternParser，/a/\*_/b这种"中间双星"写法会直接抛PatternParseException，启动即失败。需要这种匹配时改用 /a/_/b 或多写几条映射。

TIP

判断口诀：类级定模块，方法级定动作；能用组合注解就别用 @RequestMapping。@RequestMapping("/save") 不限定 method 时，GET/POST/PUT/DELETE 全部都能打进来，这在 RESTful 接口里是隐患——同一路径的增与查会相互冲突（启动报 Ambiguous mapping）。

3.2 查询参数与 @RequestParam ​

最简单的写法：形参名与请求参数名一致，什么注解都不用加。

java
// GET /user/search?name=tom&age=18
@GetMapping("/search")
public String search(String name, Integer age) {
    return name + "-" + age;
}

当名字对不上或需要默认值/必填校验时，才用 @RequestParam：

java
// GET /user/page?pageNum=2
@GetMapping("/page")
public String page(
        @RequestParam("pageNum") Integer num,                      // 改名
        @RequestParam(required = false) String keyword,            // 非必填
        @RequestParam(defaultValue = "10") Integer pageSize,       // 默认值
        @RequestParam("hobby") List<String> hobbies) {             // 多值 hobby=a&hobby=b
    return num + "/" + pageSize;
}
属性作用默认值
value/name请求参数名无
required是否必传，不传则 400true
defaultValue缺省值（隐含非必填）ValueConstants.DEFAULT_NONE

WARNING

两个高频坑：

  1. required = true 下不传参数 → 400 而不是 null。想要"不传就为 null"，必须显式写 required = false，同时形参用包装类型（Integer 而不是 int）——基本类型收到 null 会抛 IllegalStateException（Optional int parameter is present but cannot be translated into a null value）。
  2. 写了 defaultValue 就不要再写 required = true，前者会自动把必填关掉，两者同写容易误导读代码的人。

TIP

编译参数提醒：不加 @RequestParam 能按名字自动绑定，依赖编译时保留形参名（-parameters）。Spring Boot 的 maven 插件默认已开启；但在一些手写 pom.xml 的老工程里没开，表现为线上参数全是 null、本地却正常。保险做法是：对外接口一律显式写 @RequestParam("xxx")。

3.3 POJO 入参与集合绑定 ​

参数一多（超过 3 个）就该用对象接收，Spring MVC 会按属性名 = 参数名自动封装。

java
@Data
public class UserQuery {
    private String name;
    private Integer age;
    private Address address;      // 级联属性：address.city=北京
    private List<String> hobbies; // 多值：hobbies=篮球&hobbies=音乐

    @DateTimeFormat(pattern = "yyyy-MM-dd")
    private LocalDate birthday;   // 日期必须声明格式，否则 400
}
java
// GET /user/query?name=tom&age=18&address.city=北京&hobbies=篮球&hobbies=音乐&birthday=2000-01-01
@GetMapping("/query")
public String query(UserQuery query) {   // 不需要任何注解
    return query.toString();
}
绑定场景请求写法要求
普通属性name=tom属性名一致
级联属性address.city=北京嵌套对象需有无参构造 + setter
集合/数组hobbies=a&hobbies=b 或 hobbies=a,b类型为 List<String> / String[]
Mapparams['key']=v较少用，可读性差
日期birthday=2000-01-01必须 @DateTimeFormat 或全局 Formatter

WARNING

POJO 绑定必须有无参构造和 setter。用 Lombok 时只写 @Data 是安全的；但如果同时加了 @AllArgsConstructor 而没有 @NoArgsConstructor，无参构造会被覆盖掉 → 直接 500（BeanInstantiationException: No default constructor found）。记住：POJO 入参类上要么只写 @Data，要么 @NoArgsConstructor 必须补齐。

3.4 @PathVariable：路径变量 ​

RESTful 风格把资源标识放进路径，用 @PathVariable 取出来。

java
// GET /user/1
@GetMapping("/user/{id}")
public String getUser(@PathVariable("id") Integer id) {
    return "user:" + id;
}

// 多个占位符
@GetMapping("/user/{userId}/order/{orderId}")
public String detail(@PathVariable Integer userId,
                     @PathVariable Integer orderId) {   // 名字一致可省略 value
    return userId + "-" + orderId;
}

// 一次性接收全部占位符
@GetMapping("/a/{x}/b/{y}")
public String all(@PathVariable Map<String, String> vars) {
    return vars.toString();
}

WARNING

路径变量里带 . 会被截断（Spring 5.3 之前的后缀匹配机制）：/file/a.txt 中 @PathVariable String name 只能拿到 a。 解决方式是用正则占位符把整段吃掉：

java
@GetMapping("/file/{name:.+}")      // ✅ name = a.txt
public String file(@PathVariable String name) { ... }

3.5 @RequestBody：JSON 请求体 ​

概念

@RequestBody 把请求体（body）的原始字节流交给 HttpMessageConverter 反序列化成对象。前后端分离项目里，POST/PUT 接口几乎全靠它。

java
@PostMapping("/user")
public Result<User> save(@RequestBody User user) {       // Content-Type: application/json
    userService.save(user);
    return Result.success(user);
}

// 接收 JSON 数组
@PostMapping("/users")
public Result<Void> batch(@RequestBody List<User> users) { ... }

// 不想建类时，用 Map 接
@PostMapping("/raw")
public Result<Void> raw(@RequestBody Map<String, Object> body) { ... }
属性作用
required默认 true，body 为空直接 400

WARNING

一个方法里最多只能有一个 @RequestBody。因为请求体是只能读一次的流，第一个参数读完流就空了，第二个必然失败（报 Required request body is missing 或拿到 null）。需要多个对象时，合并成一个外层 DTO：

java
// ❌ 错误：两个 @RequestBody
public Result save(@RequestBody User user, @RequestBody Order order) { ... }

// ✅ 正确：合并成一个包装类
@Data
public class SaveRequest {
    private User user;
    private Order order;
}
public Result save(@RequestBody SaveRequest req) { ... }

3.6 四大入参注解边界澄清 ​

这是参数绑定里最容易混的一组，先看定位表：

注解数据来自哪里典型 Content-Type典型请求示例
@RequestParamURL 查询串 或 表单体无 / x-www-form-urlencoded/user?name=tom
@PathVariableURL 路径本身任意/user/1
@RequestBody请求体原始流application/jsonbody: {"name":"tom"}
无注解 POJO查询串 + 表单体（同 @RequestParam）无 / x-www-form-urlencoded/user?name=tom&age=18

📌 单独澄清一：@RequestParam 和 @RequestBody 到底差在哪？

差别不在"参数写在哪"，而在"谁来解析"：

  • @RequestParam 走的是 Servlet 原生的 request.getParameter()，数据源是查询串 + 表单体，拿到的永远是字符串，再做类型转换。
  • @RequestBody 走的是 HttpMessageConverter，直接读字节流反序列化，和 getParameter() 毫无关系。
java
// ❌ 前端发 JSON，后端用 @RequestParam 接 → name 永远是 null
// 前端：axios.post('/user', { name: 'tom' })      Content-Type: application/json
@PostMapping("/user")
public String save(@RequestParam String name) { ... }

// ✅ 前端发 JSON，后端就必须用 @RequestBody
@PostMapping("/user")
public String save(@RequestBody User user) { ... }

// ✅ 前端发表单，后端用 @RequestParam 或 POJO
// 前端：Content-Type: application/x-www-form-urlencoded, body: name=tom
@PostMapping("/user")
public String save(@RequestParam String name) { ... }

TIP

判断口诀：看 Content-Type，不看请求方法。application/json → @RequestBody；x-www-form-urlencoded 或 query → @RequestParam / POJO；multipart/form-data → MultipartFile + @RequestParam。 POST 不等于 @RequestBody，GET 也不等于 @RequestParam，"POST 就用 RequestBody" 是错误记忆。

📌 单独澄清二：为什么 @RequestBody 和 POJO 不能混用在同一个方法？

java
// ❌ user 能拿到值，但 age 永远是 null
// 因为 @RequestBody 已把流读完，getParameter() 再也取不到 body 里的数据
@PostMapping("/mix")
public String mix(@RequestBody User user, Integer age) { ... }

// ✅ 要混用，额外的参数必须放在 URL 查询串里
// POST /mix?age=18   body: {"name":"tom"}
@PostMapping("/mix")
public String mix(@RequestBody User user, @RequestParam Integer age) { ... }

java

3.8 文件上传 ​

① 开启并配置限制（Spring Boot）：

properties
spring.servlet.multipart.enabled=true
spring.servlet.multipart.max-file-size=10MB        # 单个文件上限
spring.servlet.multipart.max-request-size=50MB     # 单次请求总上限
spring.servlet.multipart.file-size-threshold=0     # 超过该值写入磁盘临时文件

② 前端表单的三个必要条件：

html
<!-- method 必须 post；enctype 必须 multipart/form-data；input 必须有 name -->
<form action="/upload" method="post" enctype="multipart/form-data">
  <input type="file" name="file" />
  <input type="text" name="remark" />
  <button type="submit">上传</button>
</form>

③ 后端接收：

java
@PostMapping("/upload")
public Result<String> upload(@RequestParam("file") MultipartFile file,
                             @RequestParam(required = false) String remark) throws IOException {
    if (file.isEmpty()) {
        return Result.fail("文件为空");
    }

    String original = file.getOriginalFilename();                 // 原始文件名
    String ext = original.substring(original.lastIndexOf('.'));   // 后缀
    String newName = UUID.randomUUID() + ext;                     // 防重名

    File dir = new File("/data/upload/");
    if (!dir.exists()) {
        dir.mkdirs();
    }
    file.transferTo(new File(dir, newName));                      // 落盘
    return Result.success(newName);
}

// 多文件：形参换成数组或 List
@PostMapping("/uploads")
public Result<Void> uploads(@RequestParam("files") MultipartFile[] files) { ... }
MultipartFile 常用方法说明
getOriginalFilename()客户端原始文件名
getSize()字节大小
getContentType()MIME 类型
isEmpty()是否为空文件
getInputStream()读取内容流（推荐上传 OSS）
transferTo(File)直接落盘

WARNING

四个必须注意的点：

  1. 文件名不能直接用。getOriginalFilename() 来自客户端，可能包含 ../../etc/passwd 这类路径穿越攻击，必须重命名（UUID）或做白名单校验。
  2. transferTo 用相对路径有坑。相对路径基于临时目录而非项目目录，务必传绝对路径。
  3. 超限异常要兜住。超过 max-file-size 抛的是 MaxUploadSizeExceededException，发生在进入 Controller 之前，只能在 @ControllerAdvice 里捕获。
  4. transferTo 只能调一次，调用后临时文件即被移动/清理，第二次会抛 FileNotFoundException。

3.9 类型转换：Converter / Formatter / @InitBinder ​

概念

HTTP 传来的永远是字符串，而形参可能是 Integer、LocalDate、自定义枚举。中间这层字符串 → 对象的工作由 ConversionService 完成，内部注册了大量 Converter（纯类型转换）和 Formatter（带格式与国际化的字符串互转）。

① 日期：优先用注解，一行解决

java
@DateTimeFormat(pattern = "yyyy-MM-dd HH:mm:ss")
private LocalDateTime createTime;     // 入参格式化

@JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss", timezone = "GMT+8")
private LocalDateTime updateTime;     // 出参（JSON 序列化）格式化

WARNING

@DateTimeFormat 与 @JsonFormat 不是一回事，方向相反且分属两套体系：

  • @DateTimeFormat（Spring）：管 query / 表单 → 对象，走 ConversionService。
  • @JsonFormat（Jackson）：管 JSON ↔ 对象，走 HttpMessageConverter。

所以 @RequestBody 接收的 JSON 日期不受 @DateTimeFormat 控制，必须用 @JsonFormat；反之 query 里的日期加 @JsonFormat 也无效。两个都配上是最省心的做法。

② 自定义 Converter：把 1,2,3 转成 List<Integer>

java
@Component
public class StringToUserConverter implements Converter<String, User> {
    @Override
    public User convert(String source) {        // source = "tom-18"
        String[] arr = source.split("-");
        User user = new User();
        user.setName(arr[0]);
        user.setAge(Integer.valueOf(arr[1]));
        return user;
    }
}

注册到 MVC：

java
@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Resource
    private StringToUserConverter converter;

    @Override
    public void addFormatters(FormatterRegistry registry) {
        registry.addConverter(converter);
    }
}

此后 GET /user?user=tom-18 即可直接用 User user 形参接收。

③ 全局日期格式（不想每个字段都写注解）

java
@Override
public void addFormatters(FormatterRegistry registry) {
    DateTimeFormatterRegistrar registrar = new DateTimeFormatterRegistrar();
    registrar.setDateFormatter(DateTimeFormatter.ofPattern("yyyy-MM-dd"));
    registrar.setDateTimeFormatter(DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss"));
    registrar.registerFormatters(registry);
}

④ @InitBinder：只作用于当前 Controller 的局部定制

java
@InitBinder
public void initBinder(WebDataBinder binder) {
    // 禁止绑定 id 字段，防止"越权改主键"
    binder.setDisallowedFields("id");

    // 空字符串转成 null
    binder.registerCustomEditor(String.class,
            new StringTrimmerEditor(true));
}
方案作用范围适用场景
@DateTimeFormat单个字段零星的日期字段
Converter全局自定义类型、枚举
addFormatters全局统一日期格式
@InitBinder单个 Controller字段黑名单、去空格等局部规则

TIP

判断口诀：字段级用注解，全局用 Converter，单 Controller 特例用 @InitBinder。 顺带记一条安全准则：接收更新请求时用 binder.setDisallowedFields("id", "createTime") 或改用专门的 DTO，避免前端伪造字段直接覆盖主键和审计字段。

四、响应与数据转换篇 ​

4.1 @ResponseBody 与 @RestController ​

概念

@ResponseBody 告诉 DispatcherServlet：方法的返回值不是视图名，而是响应体本身，请交给 HttpMessageConverter 序列化后直接写回。

java
@Controller
public class DemoController {

    @GetMapping("/view")
    public String view() {
        return "index";                 // ❌ 不带注解 → 被当成视图名 index.html
    }

    @GetMapping("/text")
    @ResponseBody
    public String text() {
        return "index";                 // ✅ 直接返回字符串 "index"
    }

    @GetMapping("/json")
    @ResponseBody
    public User json() {
        return new User("tom", 18);     // ✅ 自动转成 {"name":"tom","age":18}
    }
}

类上的所有方法都要返回数据时，用 @RestController 一次性搞定：

java
@RestController          // = @Controller + @ResponseBody
@RequestMapping("/api/user")
public class UserApiController { ... }
注解组成适用场景
@Controller@Component 的派生返回视图（JSP/Thymeleaf）
@RestController@Controller + @ResponseBody前后端分离、纯接口

WARNING

@RestController 里返回视图会"翻车"：return "index" 得到的是纯文本 index，不是页面。混合项目（部分页面 + 部分接口）正确做法是拆成两个类：页面类用 @Controller，接口类用 @RestController——而不是在 @RestController 里补 ModelAndView。

4.2 HttpMessageConverter 原理 ​

概念

HttpMessageConverter<T> 是请求体/响应体与 Java 对象之间的双向转换器，@RequestBody 和 @ResponseBody 全靠它。接口只有四个核心方法：

  • canRead(clazz, mediaType) / read(...)：能否读、怎么读（入参方向）
  • canWrite(clazz, mediaType) / write(...)：能否写、怎么写（出参方向）
text
   入参方向（@RequestBody）
   请求体字节流 ──▶ canRead? ──▶ read() ──▶ Java 对象 ──▶ Controller 形参

   出参方向（@ResponseBody）
   Controller 返回值 ──▶ canWrite? ──▶ write() ──▶ 响应体字节流 ──▶ 浏览器

常用内置实现（按注册顺序遍历，第一个 canRead/canWrite 返回 true 的胜出）：

实现类处理的类型对应 MediaType

StringHttpMessageConverterStringtext/plain

MappingJackson2HttpMessageConverter任意 POJOapplication/json
MappingJackson2XmlHttpMessageConverter任意 POJOapplication/xml

自定义：全局统一 Jackson 配置

@Configuration
public class JacksonConfig {

4.3 内容协商 ​

概念

内容协商（Content Negotiation） 指同一个接口根据客户端的"期望格式"返回 JSON 或 XML。Spring MVC 默认按请求头 Accept 判断。

java
@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void configureContentNegotiation(ContentNegotiationConfigurer configurer) {
        configurer
            .favorParameter(true)                               // 开启 ?format=xml 方式
            .parameterName("format")
            .ignoreAcceptHeader(false)                          // 仍然尊重 Accept 头
            .defaultContentType(MediaType.APPLICATION_JSON)     // 都没指定时的兜底
            .mediaType("json", MediaType.APPLICATION_JSON)
            .mediaType("xml", MediaType.APPLICATION_XML);
    }
}
协商方式请求示例优先级说明
请求参数/user/1?format=xml高需 favorParameter(true)
Accept 请求头Accept: application/xml中默认开启，最符合规范
默认 ContentType都不带低兜底

TIP

90% 的项目不需要内容协商，前后端分离直接固定 JSON 即可。真正用得上的是两个场景：对外开放 API 需兼容老系统的 XML；同一接口既给浏览器返回 HTML 又给 App 返回 JSON。 顺带一提：返回 XML 需要额外引入 jackson-dataformat-xml，否则 Accept: application/xml 会得到 406（Not Acceptable）。

4.4 ResponseEntity 与状态码 ​

直接返回对象时，状态码永远是 200。需要自定义状态码、响应头时用 ResponseEntity：

java
@GetMapping("/user/{id}")
public ResponseEntity<User> get(@PathVariable Long id) {
    User user = userService.getById(id);
    if (user == null) {
        return ResponseEntity.notFound().build();              // 404，无响应体
    }
    return ResponseEntity.ok()
            .header("X-Trace-Id", UUID.randomUUID().toString())
            .body(user);                                        // 200 + 自定义头
}

@PostMapping("/user")
public ResponseEntity<User> create(@RequestBody User user) {
    userService.save(user);
    return ResponseEntity
            .status(HttpStatus.CREATED)                         // 201
            .header("Location", "/user/" + user.getId())
            .body(user);
}

也可以用 @ResponseStatus 把状态码写死在方法或异常类上：

java
@PostMapping("/user")
@ResponseStatus(HttpStatus.CREATED)      // 固定返回 201
public User create(@RequestBody User user) { ... }
方案状态码来源适用场景
直接返回对象固定 200统一结果封装项目（最常用）
ResponseEntity运行时决定需按业务动态返回 404/201/304
@ResponseStatus编译期固定固定语义接口、自定义异常类

WARNING

ResponseEntity 和统一结果封装 Result 不要混用。混用会导致前端拿到两种格式的响应：一类要判 res.data.code，一类要判 res.status，拦截器逻辑分裂。 判断口诀：要么全项目统一 Result<T> + HTTP 恒 200，要么全项目遵循 HTTP 语义用 ResponseEntity——团队内必须二选一。

4.5 统一结果封装 Result ​

前后端分离项目的标配：所有接口返回同一种结构，前端只写一套拦截器。

java
import lombok.Data;
import java.io.Serializable;

@Data
public class Result<T> implements Serializable {

    private Integer code;      // 业务状态码：200 成功，其他失败
    private String message;    // 提示信息
    private T data;            // 业务数据

    private Result(Integer code, String message, T data) {
        this.code = code;
        this.message = message;
        this.data = data;
    }

    public static <T> Result<T> success() {
        return new Result<>(200, "操作成功", null);
    }

    public static <T> Result<T> success(T data) {
        return new Result<>(200, "操作成功", data);
    }

    public static <T> Result<T> success(String message, T data) {
        return new Result<>(200, message, data);
    }

    public static <T> Result<T> fail(String message) {
        return new Result<>(500, message, null);
    }

    public static <T> Result<T> fail(Integer code, String message) {
        return new Result<>(code, message, null);
    }
}

配套的状态码枚举，避免魔法数字散落各处：

java
@Getter
@AllArgsConstructor
public enum ResultCode {
    SUCCESS(200, "操作成功"),
    PARAM_ERROR(400, "参数校验失败"),
    UNAUTHORIZED(401, "未登录或登录已过期"),
    FORBIDDEN(403, "无权限访问"),
    NOT_FOUND(404, "资源不存在"),
    SYSTEM_ERROR(500, "系统繁忙，请稍后再试");

    private final Integer code;
    private final String message;
}

使用：

java
@RestController
@RequestMapping("/api/user")
public class UserApiController {

    @Resource
    private UserService userService;

    @GetMapping("/{id}")
    public Result<User> get(@PathVariable Long id) {
        return Result.success(userService.getById(id));
    }

    @PostMapping
    public Result<Void> save(@RequestBody @Validated User user) {
        userService.save(user);
        return Result.success();
    }
}

TIP

三条实战约定：

  1. 业务码与 HTTP 码解耦。HTTP 恒 200，业务结果看 code——这样前端的 axios 不会因为 500 直接走 catch 分支，错误提示能统一在拦截器里弹。
  2. message 只给用户看。堆栈、SQL 这类技术细节必须留在日志里，不能塞进 message 返回前端（信息泄露）。
  3. 不要让每个 Controller 自己 try-catch 再包 Result。失败分支交给第七篇的全局异常处理器，Controller 里只写成功路径。

4.6 转发、重定向与 FlashAttributes ​

java
@Controller
public class PageController {

    @GetMapping("/forward")
    public String forward() {
        return "forward:/target";       // 请求转发：一次请求，URL 不变，可带 request 域数据
    }

    @GetMapping("/redirect")
    public String redirect() {
        return "redirect:/target";      // 重定向：两次请求，URL 改变，request 域丢失
    }

    // 重定向时携带一次性数据
    @PostMapping("/save")
    public String save(RedirectAttributes attrs) {
        attrs.addFlashAttribute("msg", "保存成功");   // 存 Session，取一次即删
        attrs.addAttribute("id", 1);                 // 拼到 URL：/target?id=1
        return "redirect:/target";
    }

    @GetMapping("/target")
    public String target(@ModelAttribute("msg") String msg, Model model) {
        return "target";
    }
}
维度转发 forward重定向 redirect
请求次数1 次2 次
浏览器 URL不变变成新地址
request 域保留丢失（需用 FlashAttributes）
能否跳外部站不能（只能站内）能
状态码200302 / 303

POST 后必须重定向，不能转发。表单提交成功后若用 forward，浏览器 URL 仍是 /save，用户按 F5 会再次提交表单造成重复下单。这就是经典的 POST-Redirect-GET（PRG）模式，而 FlashAttributes 存在的唯一理由就是让 PRG 还能传提示语。

4.7 文件下载 ​

方案一：小文件，一次性读入内存

java
@GetMapping("/download")
public ResponseEntity<byte[]> download(@RequestParam String fileName) throws IOException {
    File file = new File("/data/upload/", fileName);
    byte[] bytes = Files.readAllBytes(file.toPath());

    // 中文文件名必须 URL 编码，否则乱码或下载失败
    String encoded = URLEncoder.encode(fileName, StandardCharsets.UTF_8);

    HttpHeaders headers = new HttpHeaders();
    headers.setContentType(MediaType.APPLICATION_OCTET_STREAM);
    headers.setContentDispositionFormData("attachment", encoded);

    return new ResponseEntity<>(bytes, headers, HttpStatus.OK);
}

方案二：大文件，流式输出（推荐）

java
@GetMapping("/download/stream")
public void downloadStream(@RequestParam String fileName,
                           HttpServletResponse response) throws IOException {
    File file = new File("/data/upload/", fileName);
    String encoded = URLEncoder.encode(fileName, StandardCharsets.UTF_8);

    response.setContentType("application/octet-stream");
    response.setContentLengthLong(file.length());
    response.setHeader("Content-Disposition", "attachment;filename=" + encoded);

    try (InputStream in = new FileInputStream(file);
         OutputStream out = response.getOutputStream()) {
        StreamUtils.copy(in, out);          // 边读边写，内存占用恒定
    }
}
维度ResponseEntity<byte[]>流式写 OutputStream
内存占用整个文件进堆恒定（缓冲区大小）
适用大小< 10MB任意大小
异常处理可被全局异常器捕获响应已开始，无法再改

WARNING

Content-Disposition 的两个值别搞混：

  • attachment：浏览器弹出下载框 ✅ 下载场景
  • inline：浏览器尝试直接预览（PDF、图片） ✅ 预览场景

另外流式下载一旦开始写出就不能再改状态码。所以"文件不存在"这类校验必须放在 response.getOutputStream() 之前，否则会出现"200 响应 + 一半的错误 HTML"这种诡异结果。

4.8 静态资源映射 ​

Spring Boot 默认把以下目录当作静态资源根路径（优先级从高到低）：

text
classpath:/META-INF/resources/   →   classpath:/resources/
        →   classpath:/static/   →   classpath:/public/

需要额外映射本地磁盘目录（例如上传的图片）时：

java
@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addResourceHandlers(ResourceHandlerRegistry registry) {
        registry.addResourceHandler("/upload/**")                 // URL 前缀
                .addResourceLocations("file:/data/upload/")        // 磁盘路径，注意 file: 前缀和结尾斜杠
                .setCachePeriod(3600);
    }
}

WARNING

三个最常踩的坑：

  1. addResourceLocations 的磁盘路径必须带 file: 前缀且以 / 结尾，少任何一个都是 404。
  2. 自定义拦截器会连静态资源一起拦。登录拦截器配 addPathPatterns("/**") 后，图片、JS 也要带 token 才能访问 → 页面白屏。必须用 excludePathPatterns 放行静态资源。
  3. 继承 WebMvcConfigurationSupport 会让默认静态资源配置全部失效，而实现 WebMvcConfigurer 接口不会。老项目里"加了个配置类之后静态资源全 404"基本都是这个原因——永远实现 WebMvcConfigurer 接口，不要继承 WebMvcConfigurationSupport。

4.9 异步请求处理 ​

概念

普通请求里，Tomcat 工作线程会被业务代码一路占用到响应写完。如果业务要等 3 秒的第三方接口，这 3 秒线程纯粹在空等。异步处理的作用是：业务一开始就释放 Tomcat 线程，把活交给业务线程池，完成后再由容器把结果写回。

① Callable：最简单的异步

java
@GetMapping("/async/callable")
public Callable<Result<String>> callable() {
    log.info("主线程开始：{}", Thread.currentThread().getName());   // http-nio-8080-exec-1

    Callable<Result<String>> task = () -> {
        log.info("副线程执行：{}", Thread.currentThread().getName()); // MvcAsync1
        Thread.sleep(2000);
        return Result.success("done");
    };

    log.info("主线程结束，线程已释放");
    return task;        // 返回的瞬间 Tomcat 线程就回收了
}

② DeferredResult：跨线程/跨服务回填结果

java
// 队列由其他线程（如 MQ 消费者）持有
private static final Queue<DeferredResult<Result<String>>> QUEUE = new ConcurrentLinkedQueue<>();

@GetMapping("/async/deferred")
public DeferredResult<Result<String>> deferred() {
    DeferredResult<Result<String>> dr = new DeferredResult<>(5000L);   // 5 秒超时

    dr.onTimeout(() -> dr.setErrorResult(Result.fail("处理超时")));
    dr.onCompletion(() -> log.info("请求结束，可在此清理资源"));

    QUEUE.add(dr);      // 交给别的线程，将来调用 dr.setResult(...) 即完成响应
    return dr;
}

// 另一个线程里回填
@GetMapping("/async/notify")
public Result<String> notifyResult() {
    DeferredResult<Result<String>> dr = QUEUE.poll();
    if (dr != null) {
        dr.setResult(Result.success("由 notify 回填"));
    }
    return Result.success("ok");
}

③ 配置异步线程池与超时

java
@Override
public void configureAsyncSupport(AsyncSupportConfigurer configurer) {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(10);
    executor.setMaxPoolSize(50);
    executor.setQueueCapacity(200);
    executor.setThreadNamePrefix("mvc-async-");
    executor.initialize();

    configurer.setTaskExecutor(executor);
    configurer.setDefaultTimeout(10_000);
}
返回类型谁来执行任务适用场景
Callable<T>Spring MVC 的线程池单纯耗时计算/调用，逻辑在本方法内
DeferredResult<T>任意外部线程长轮询、MQ 回调、等待第三方通知
CompletableFuture<T>自定义线程池多个异步任务编排（组合、串联）
SseEmitter任意外部线程服务端推送（消息流、AI 流式输出）

WARNING

异步请求下，ThreadLocal 和拦截器行为都会变：

  1. ThreadLocal 失效。业务跑在新线程，主线程里 ThreadLocal 存的用户上下文取不到 → 必须显式传递（或用 TaskDecorator 做跨线程复制）。
  2. 拦截器会被调用两次。异步流程是：preHandle → 立即返回、释放线程 → 结果就绪后重新派发（dispatch） → preHandle 再走一遍 → postHandle → afterCompletion。要跳过第二次，用 AsyncHandlerInterceptor#afterConcurrentHandlingStarted 做区分。
  3. 异步里抛的异常默认不进 @ControllerAdvice，需要通过 dr.setErrorResult(ex) 主动交回给 MVC，才能被全局异常处理器接管。

五、RESTful 与跨域篇 ​

5.1 RESTful 风格与设计规范 ​

概念

REST（Representational State Transfer，表现层状态转移） 是一种 API 设计风格，核心主张是：URL 用名词标识"资源"，HTTP 方法表达"动作"，状态码表达"结果"。

操作传统风格RESTful 风格
查询全部GET /getAllUserGET /users
查询单个GET /getUserById?id=1GET /users/1
新增POST /addUserPOST /users
全量更新POST /updateUserPUT /users/1
局部更新POST /updateUserNamePATCH /users/1
删除GET /deleteUser?id=1DELETE /users/1
子资源GET /getUserOrders?id=1GET /users/1/orders

设计要点：

  1. URL 里只出现名词，而且用复数：/users 而不是 /getUser、/user。
  2. 动作交给 HTTP 方法，不要写进路径。
  3. 版本号前置：/api/v1/users，方便不兼容升级。
  4. 过滤/分页/排序用查询串：/users?page=1&size=10&sort=createTime,desc。
  5. 层级不超过两层：/users/1/orders 可以，/users/1/orders/2/items/3 就该拆成 /items?orderId=2。
  6. 状态码表达结果：200 成功、201 已创建、204 无内容、400 参数错、401 未登录、403 无权限、404 不存在、500 服务端错。

WARNING

最常见的"伪 RESTful"：用 GET 做删除（GET /deleteUser?id=1）。 危害不只是"不优雅"：GET 在规范上是幂等且安全的，会被浏览器预取、被 CDN/代理缓存、被爬虫扫描——结果就是没人点击，数据却被删了。写操作必须用 POST/PUT/DELETE。

TIP

判断口诀：看到 URL 里有动词就是没做对。 但也别教条：批量操作、登录登出这类"非资源语义"的接口，直接写 POST /users/batch-delete、POST /auth/login 比强行套 REST 更清晰——一致性优先于纯粹性。

5.2 RESTful 实战案例 ​

以员工管理为例，先建表：

sql
CREATE TABLE `t_emp` (
  `id`     INT         NOT NULL AUTO_INCREMENT COMMENT '主键',
  `name`   VARCHAR(50) NOT NULL COMMENT '姓名',
  `age`    INT                  COMMENT '年龄',
  `gender` VARCHAR(10)          COMMENT '性别',
  `email`  VARCHAR(100)         COMMENT '邮箱',
  PRIMARY KEY (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

完整的 RESTful Controller：

java
@RestController
@RequestMapping("/api/v1/emps")
public class EmpController {

    @Resource
    private EmpService empService;

    /** 分页查询：GET /api/v1/emps?page=1&size=10 */
    @GetMapping
    public Result<PageVO<EmpVO>> page(@RequestParam(defaultValue = "1") Integer page,
                                      @RequestParam(defaultValue = "10") Integer size,
                                      @RequestParam(required = false) String name) {
        return Result.success(empService.page(page, size, name));
    }

    /** 查询单个：GET /api/v1/emps/1 */
    @GetMapping("/{id}")
    public Result<EmpVO> get(@PathVariable Integer id) {
        return Result.success(empService.getById(id));
    }

    /** 新增：POST /api/v1/emps */
    @PostMapping
    public Result<Void> save(@RequestBody @Validated(Insert.class) EmpDTO dto) {
        empService.save(dto);
        return Result.success();
    }

    /** 全量更新：PUT /api/v1/emps/1 */
    @PutMapping("/{id}")
    public Result<Void> update(@PathVariable Integer id,
                               @RequestBody @Validated(Update.class) EmpDTO dto) {
        dto.setId(id);                 // 以路径里的 id 为准，防止 body 伪造
        empService.update(dto);
        return Result.success();
    }

    /** 删除：DELETE /api/v1/emps/1 */
    @DeleteMapping("/{id}")
    public Result<Void> delete(@PathVariable Integer id) {
        empService.removeById(id);
        return Result.success();
    }

    /** 批量删除：DELETE /api/v1/emps?ids=1,2,3 */
    @DeleteMapping
    public Result<Void> batchDelete(@RequestParam List<Integer> ids) {
        empService.removeByIds(ids);
        return Result.success();
    }
}

TIP

注意 update 方法里的 dto.setId(id) 这一行：路径里的 id 永远优先于 body 里的 id。否则前端请求 PUT /emps/1 而 body 写 {"id": 2} 时，就会出现"越权修改他人数据"的安全漏洞。

5.3 跨域原理与 CORS 配置 ​

概念

同源策略要求 协议、域名、端口三者完全相同，否则浏览器就判定为"跨域"，会拦截响应。 CORS（Cross-Origin Resource Sharing） 是 W3C 标准方案：服务端在响应头里声明"我允许哪些源访问"，浏览器据此决定是否放行。

text
  http://localhost:3000  ──请求──▶  http://localhost:8080/api/user

📌 单独澄清：跨域被拦的到底是"请求"还是"响应"？

是响应，不是请求。 跨域请求已经到达后端并正常执行完了（数据库该插的已经插了），只是浏览器在拿到响应后发现缺少允许头，于是不把结果交给 JS。所以：

  • 看到 CORS 报错不代表接口没执行——非幂等接口可能已经产生副作用。
  • 用 Postman / curl 测永远不报跨域，因为同源策略是浏览器的行为，与服务端无关。

方案一：全局配置（推荐）

java
@Configuration
public class CorsConfig implements WebMvcConfigurer {

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOriginPatterns("*")        // 允许的源（带凭证时不能用 "*"）
                .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
                .allowedHeaders("*")
                .exposedHeaders("X-Total-Count")   // 允许 JS 读取的自定义响应头
                .allowCredentials(true)            // 允许携带 Cookie
                .maxAge(3600);                     // 预检结果缓存 1 小时
    }
}

text
When allowCredentials is true, allowedOrigins cannot contain the special value "*"

原因是浏览器规范禁止"允许任意源 + 允许带 Cookie"这种组合（等于把用户凭证敞开给所有站点）。 解决办法：用 allowedOriginPatterns("*")（Spring 5.3+）代替 allowedOrigins("*")，它会把实际的 Origin 原样回写而非 *。

5.4 预检请求与跨域踩坑 ​

概念

预检请求（Preflight） 是浏览器在发送"非简单请求"之前，自动先发的一个 OPTIONS 请求，用来问服务端"我接下来要发的这个请求，你允许吗"。

什么是简单请求？ 同时满足以下条件才算简单请求（不触发预检）：

条件要求
方法GET / HEAD / POST 之一
Content-Typetext/plain / multipart/form-data / application/x-www-form-urlencoded
请求头不含自定义头（如 X-Token、Authorization）
text
  【非简单请求的完整两步】

  ① 预检  OPTIONS /api/user
          Origin: http://localhost:3000
          Access-Control-Request-Method: PUT
          Access-Control-Request-Headers: X-Token, Content-Type
                      │
                      ▼
          204 / 200
          Access-Control-Allow-Origin: http://localhost:3000
          Access-Control-Allow-Methods: GET,POST,PUT,DELETE
          Access-Control-Allow-Headers: X-Token,Content-Type
          Access-Control-Max-Age: 3600       ← 缓存后，1 小时内不再预检
                      │
                      ▼
  ② 真实请求  PUT /api/user   （只有预检通过才会发出）

WARNING

跨域排查手册（按顺序逐条排除）：

  1. application/json 一定会触发预检。所以"GET 接口正常、POST JSON 接口报跨域"是最典型现象——根因是 OPTIONS 请求被拦下了。

  2. OPTIONS 被登录拦截器拦住 → 401 → 预检失败。预检请求不携带 Cookie 和自定义头，必然过不了鉴权。拦截器里必须放行：

    java
    if (HttpMethod.OPTIONS.matches(request.getMethod())) {
    return true;       // 预检请求直接放行
}

  3. allowedMethods 漏写 OPTIONS（或没用 "*"），预检直接 403。

  4. 自定义请求头没加进 allowedHeaders，预检通过但真实请求被拦。

  5. 前端读不到自定义响应头（如分页总数 X-Total-Count）：必须配 exposedHeaders，CORS 默认只暴露 6 个基本头。

  6. Nginx 也配了一份 CORS 头 → 响应里出现两个 Access-Control-Allow-Origin，浏览器判定非法。网关层和应用层只能留一处配置。

  7. 重定向 + 跨域：302 跳转后的新地址同样需要 CORS 头，否则第二跳失败。

TIP

开发期最省事的方案其实不是 CORS，而是前端代理。Vite / webpack-dev-server 配 proxy 后，浏览器看到的始终是同源请求，后端一行都不用改：

js

  proxy: {
    '/api': { target: 'http://localhost:8080', changeOrigin: true }
  }
}

判断口诀：开发用代理，生产用网关统一配 CORS（或干脆同域部署），应用代码里的 CORS 配置只作兜底。

六、拦截器与过滤器篇 ​

6.1 拦截器三方法与执行顺序 ​

概念

拦截器（HandlerInterceptor） 是 Spring MVC 提供的 AOP 式横切组件，在 DispatcherServlet 内部、Handler 前后切入，典型用途是登录鉴权、权限校验、日志、耗时统计。

java
@Component
public class LogInterceptor implements HandlerInterceptor {

    private static final Logger log = LoggerFactory.getLogger(LogInterceptor.class);

    /** Handler 执行前。返回 false 则中断，后续流程全部不走 */
    @Override
    public boolean preHandle(HttpServletRequest request,
                             HttpServletResponse response,
                             Object handler) {
        request.setAttribute("startTime", System.currentTimeMillis());
        log.info("preHandle: {} {}", request.getMethod(), request.getRequestURI());
        return true;
    }

    /** Handler 执行后、视图渲染前。可修改 ModelAndView */
    @Override
    public void postHandle(HttpServletRequest request,
                           HttpServletResponse response,
                           Object handler,
                           ModelAndView mav) {
        log.info("postHandle");
    }

    /** 视图渲染完成后。无论成功失败都会执行，适合清理资源 */
    @Override
    public void afterCompletion(HttpServletRequest request,
                                HttpServletResponse response,
                                Object handler,
                                Exception ex) {
        long cost = System.currentTimeMillis() - (long) request.getAttribute("startTime");
        log.info("afterCompletion: 耗时 {}ms, 异常={}", cost, ex);
    }
}

注册并配置拦截路径：

java
@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Resource private LogInterceptor logInterceptor;
    @Resource private LoginInterceptor loginInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(logInterceptor)
                .addPathPatterns("/**")
                .order(1);                        // 数字越小越先执行

        registry.addInterceptor(loginInterceptor)
                .addPathPatterns("/**")
                .excludePathPatterns(             // 放行名单
                        "/api/auth/login",
                        "/api/auth/captcha",
                        "/doc.html", "/webjars/**", "/v3/api-docs/**",
                        "/static/**", "/favicon.ico")
                .order(2);
    }
}

多个拦截器的执行顺序（关键：preHandle 正序，另两个逆序）：

text
  注册顺序：A(order=1) → B(order=2)

  A.preHandle  ─────▶ true
        │
  B.preHandle  ─────▶ true
        │
     Controller 执行
        │
  B.postHandle  ◀────
        │
  A.postHandle  ◀────
        │
     视图渲染
        │
  B.afterCompletion ◀────
        │
  A.afterCompletion ◀────

WARNING

preHandle 返回 false 时的连带效应，这是最容易写出 bug 的地方：

  • 返回 false 的那个拦截器，它的 postHandle 和 afterCompletion 都不会执行。
  • 但它之前已经成功放行的拦截器，afterCompletion 会执行（逆序执行已通过的部分）。

所以"在 preHandle 里加锁、在 afterCompletion 里解锁"这种写法是安全的；但"在 preHandle 里 return false 后又指望自己的 afterCompletion 清理 ThreadLocal"就会内存泄漏。

另外 return false 时必须自己写响应，否则前端拿到的是一个 200 + 空 body：

java
response.setStatus(HttpStatus.UNAUTHORIZED.value());
response.setContentType("application/json;charset=UTF-8");
response.getWriter().write(new ObjectMapper()
        .writeValueAsString(Result.fail(401, "未登录")));
return false;

6.2 拦截器实战：鉴权与耗时统计 ​

登录鉴权拦截器（JWT 版）：

java
@Component
public class LoginInterceptor implements HandlerInterceptor {

    @Resource private JwtUtil jwtUtil;

    @Override
    public boolean preHandle(HttpServletRequest request,
                             HttpServletResponse response,
                             Object handler) throws IOException {

        // ① 预检请求直接放行，否则跨域必失败
        if (HttpMethod.OPTIONS.matches(request.getMethod())) {
            return true;
        }

        // ② 非 Controller 方法（如静态资源）放行
        if (!(handler instanceof HandlerMethod handlerMethod)) {
            return true;
        }

        // ③ 方法上标了 @PublicApi 的放行（比 excludePathPatterns 更灵活）
        if (handlerMethod.hasMethodAnnotation(PublicApi.class)) {
            return true;
        }

        // ④ 校验 token
        String token = request.getHeader("Authorization");
        if (token == null || !token.startsWith("Bearer ")) {
            writeJson(response, 401, "未登录");
            return false;
        }

        try {
            Claims claims = jwtUtil.parse(token.substring(7));
            UserContext.set(new LoginUser(
                    Long.valueOf(claims.getSubject()),
                    claims.get("username", String.class)));
            return true;
        } catch (ExpiredJwtException e) {
            writeJson(response, 401, "登录已过期");
            return false;
        } catch (JwtException e) {
            writeJson(response, 401, "无效的凭证");
            return false;
        }
    }

    /** 无论成败都要清理 ThreadLocal */
    @Override
    public void afterCompletion(HttpServletRequest request,
                                HttpServletResponse response,
                                Object handler, Exception ex) {
        UserContext.clear();
    }

    private void writeJson(HttpServletResponse response, int code, String msg) throws IOException {
        response.setStatus(code);
        response.setContentType("application/json;charset=UTF-8");
        response.getWriter().write(
                "{\"code\":" + code + ",\"message\":\"" + msg + "\",\"data\":null}");
    }
}

慢接口监控拦截器：

java
@Component
public class CostInterceptor implements HandlerInterceptor {

    private static final Logger log = LoggerFactory.getLogger(CostInterceptor.class);
    private static final long SLOW_THRESHOLD = 1000L;
    private final ThreadLocal<Long> start = new ThreadLocal<>();

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse resp, Object h) {
        start.set(System.currentTimeMillis());
        MDC.put("traceId", UUID.randomUUID().toString().replace("-", ""));
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse resp,
                                Object h, Exception ex) {
        try {
            long cost = System.currentTimeMillis() - start.get();
            if (cost > SLOW_THRESHOLD) {
                log.warn("慢接口 {} {} 耗时 {}ms", req.getMethod(), req.getRequestURI(), cost);
            }
        } finally {
            start.remove();      // 必须清理
            MDC.clear();
        }
    }
}

TIP

用注解放行比用路径放行更可靠。excludePathPatterns 写的是字符串，接口改路径时很容易忘记同步维护，导致"本该公开的接口突然要登录"或更糟的"本该鉴权的接口被意外放行"。自定义一个 @PublicApi 注解标在方法上，放行规则就跟着代码走，重构不会漏。

6.4 ThreadLocal 上下文与清理 ​

鉴权拦截器里解析出的"当前登录人"，要让 Service 层也能用到，最常见的做法是 ThreadLocal：

java
public final class UserContext {

    private static final ThreadLocal<LoginUser> HOLDER = new ThreadLocal<>();

    public static void set(LoginUser user) {
        HOLDER.set(user);
    }

    public static LoginUser get() {
        return HOLDER.get();
    }

    public static Long getUserId() {
        LoginUser user = HOLDER.get();
        return user == null ? null : user.getId();
    }

    public static void clear() {
        HOLDER.remove();        // 关键
    }

    private UserContext() {}
}

WARNING

不清理 ThreadLocal 会导致两类严重问题，都比"内存泄漏"更直接：

  1. 用户数据串号。Tomcat 的工作线程是复用的：用户 A 的请求结束后线程归还线程池，用户 B 复用了这个线程，如果没清理，B 读到的 UserContext.get() 就是 A 的身份 → 越权。这是实际发生过的线上事故类型。
  2. 内存泄漏。ThreadLocalMap 的 key 是弱引用，但 value 是强引用；线程常驻（线程池）意味着 value 永远不会被回收。

清理位置必须是 afterCompletion（而不是 postHandle），因为只有它在异常路径下也会执行。

异步场景额外注意：@Async、Callable、CompletableFuture 里的新线程拿不到父线程的 ThreadLocal。需要用 TransmittableThreadLocal（阿里 TTL）或给线程池配 TaskDecorator 做跨线程传递：

java
executor.setTaskDecorator(runnable -> {
    LoginUser user = UserContext.get();          // 主线程取
    return () -> {
        try {
            UserContext.set(user);               // 子线程塞
            runnable.run();
        } finally {
            UserContext.clear();
        }
    };
});

WARNING

没写 groups 的注解属于 Default 组。一旦在方法上写了 @Validated(Insert.class)，不带 groups 的注解就不会执行（例如上面的 @Email、@Length）。 两种修法：① 让分组接口继承 Default（interface Insert extends Default {}）；② 显式写成 @Validated({Insert.class, Default.class})。 这是分组校验最隐蔽的坑——表现是"明明加了 @Email 却放进了非法邮箱"。

③ 自定义校验注解：以"性别只能是 男/女"为例

java
@Target({ElementType.FIELD, ElementType.PARAMETER})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = GenderValidator.class)
public @interface Gender {
    String message() default "性别只能是 男 或 女";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}
java
public class GenderValidator implements ConstraintValidator<Gender, String> {

    private static final Set<String> ALLOWED = Set.of("男", "女");

    @Override
    public boolean isValid(String value, ConstraintValidatorContext context) {
        // null 交给 @NotBlank 管，这里只校验"非空时的合法性"
        if (value == null) {
            return true;
        }
        return ALLOWED.contains(value);
    }
}

使用：

④ 方法级参数校验（直接校验 @RequestParam/@PathVariable）

java
@RestController
@Validated                       // ⚠️ 必须加在类上
@RequestMapping("/api/emps")
public class EmpController {

    @GetMapping("/{id}")
    public Result<EmpVO> get(@PathVariable @Min(value = 1, message = "id 必须大于 0") Integer id) {
        return Result.success(empService.getById(id));
    }
}

WARNING

自定义校验器里 null 必须返回 true。这是 Bean Validation 的约定："是否允许为空"由 @NotNull/@NotBlank 负责，其他注解只负责"非空时是否合法"。如果在 isValid 里对 null 返回 false，那么这个注解就隐含了"必填"语义，字段想变成可选时无法关掉。

TIP

类上的 @Validated 和参数上的 @Validated 是两件事：

  • 参数上的 @Validated UserDTO dto → 校验对象内部字段，失败抛 MethodArgumentNotValidException。
  • 类上的 @Validated + 参数上的 @Min → 校验单个简单参数，失败抛 ConstraintViolationException。

两者异常类型不同，全局异常处理器必须都兜住，否则会出现"有的校验返回友好提示、有的直接 500"。

7.3 VO / DTO / Entity 分层 ​

概念

  • Entity（PO）：与数据库表结构一一对应，字段名贴着表字段。
  • DTO（Data Transfer Object）：入参载体，描述"前端能传什么"，校验注解挂在这里。
  • VO（View Object）：出参载体，描述"前端能看到什么"，敏感字段在此被剔除。

WARNING

直接把 Entity 当出参返回是真实的安全事故来源。典型表现：

  • password、salt、idCard、openid 等敏感字段原样返回给前端（即便页面不显示，抓包就能看到）。
  • deleted、version、tenantId 等内部字段暴露了系统实现。
  • 数据库加字段后，接口响应结构悄悄发生变化，前端可能被动兼容。

TIP

三层对象不是过度设计，而是"变更隔离"：数据库表改字段不应该影响接口契约，接口加参数不应该被迫改表结构。 小项目可以简化为 DTO + Entity 两层（出参复用 DTO），但绝不要省掉入参的 DTO——校验注解没地方放，就只能回到 Controller 里写 if。 转换工具建议用 MapStruct（编译期生成代码，无反射开销），而不是 BeanUtils.copyProperties（反射慢，且字段名写错时静默不赋值，极难排查）。

概念

@ControllerAdvice / @RestControllerAdvice 是作用于所有 Controller 的增强类，配合 @ExceptionHandler 可以把异常集中处理，让 Controller 里只写成功路径。

① 自定义业务异常

java
@Getter

② 全局异常处理器

java
@Slf4j
@RestControllerAdvice            // = @ControllerAdvice + @ResponseBody
public class GlobalExceptionHandler {

    /** 业务异常：预期内的失败，只打 warn，不打堆栈 */
    @ExceptionHandler(BizException.class)
    public Result<Void> handleBiz(BizException e) {
        log.warn("业务异常: {}", e.getMessage());
        return Result.fail(e.getCode(), e.getMessage());
    }

    /** @RequestBody 对象校验失败 */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<Void> handleValid(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
                .map(f -> f.getField() + ": " + f.getDefaultMessage())
                .collect(Collectors.joining("; "));
        return Result.fail(400, msg);
    }

    /** 表单/POJO 绑定校验失败 */
    @ExceptionHandler(BindException.class)
    public Result<Void> handleBind(BindException e) {
        FieldError first = e.getBindingResult().getFieldError();
        return Result.fail(400, first == null ? "参数错误" : first.getDefaultMessage());
    }

    /** 单个参数校验失败（类上 @Validated + 参数上 @Min 等） */
    @ExceptionHandler(ConstraintViolationException.class)
    public Result<Void> handleConstraint(ConstraintViolationException e) {
        String msg = e.getConstraintViolations().stream()
                .map(ConstraintViolation::getMessage)
                .collect(Collectors.joining("; "));
        return Result.fail(400, msg);
    }

    /** 必传参数缺失 */
    @ExceptionHandler(MissingServletRequestParameterException.class)
    public Result<Void> handleMissing(MissingServletRequestParameterException e) {
        return Result.fail(400, "缺少必要参数: " + e.getParameterName());
    }

    /** 参数类型不匹配，如 /user/abc */
    @ExceptionHandler(MethodArgumentTypeMismatchException.class)
    public Result<Void> handleTypeMismatch(MethodArgumentTypeMismatchException e) {
        return Result.fail(400, "参数类型错误: " + e.getName());
    }

    /** JSON 格式错误、body 为空 */
    @ExceptionHandler(HttpMessageNotReadableException.class)
    public Result<Void> handleUnreadable(HttpMessageNotReadableException e) {
        return Result.fail(400, "请求体格式错误，请检查 JSON 是否合法");
    }

    /** 请求方法不支持 */
    @ExceptionHandler(HttpRequestMethodNotSupportedException.class)
    public Result<Void> handleMethod(HttpRequestMethodNotSupportedException e) {
        return Result.fail(405, "不支持的请求方法: " + e.getMethod());
    }

    /** 上传文件超限 */
    @ExceptionHandler(MaxUploadSizeExceededException.class)
    public Result<Void> handleUpload(MaxUploadSizeExceededException e) {
        return Result.fail(400, "文件大小超出限制");
    }

    /** 兜底：未预期的异常，必须打完整堆栈，但不能把细节返回前端 */
    @ExceptionHandler(Exception.class)
    public Result<Void> handleOther(Exception e, HttpServletRequest request) {
        log.error("系统异常 uri={}", request.getRequestURI(), e);
        return Result.fail(500, "系统繁忙，请稍后再试");
    }
}

WARNING

全局异常处理失效的五种情况，排查时逐条对照：

  1. 异常被 Controller 里的 try-catch 吃掉了 → 最常见。业务代码里 catch (Exception e) { return Result.fail("失败"); } 会让异常根本传不到 advice。
  2. 异常发生在 Filter 或拦截器里 → 那时还没进 DispatcherServlet 的 handler 执行阶段，@ControllerAdvice 管不着，需要配 ErrorController 或在 Filter 里自己 try-catch。
  3. 异步请求里抛的异常 → 需要 DeferredResult#setErrorResult 主动交回。
  4. @ControllerAdvice 所在包不在扫描范围 → 和 Controller 同一个坑。
  5. 多个 handler 同时能匹配 → Spring 选继承层次上最接近的那个。写了 handle(Exception) 不会抢走 handle(BizException) 的活，但两个平级的自定义异常父类会导致匹配不确定。

TIP

@ExceptionHandler 的两条实战纪律：

  1. 业务异常打 warn 不打 error，且不要打堆栈。预期内的"余额不足"打一堆堆栈会把日志淹掉，真正的系统异常就找不到了。
  2. 兜底 handler 返回给前端的 message 必须是固定文案。千万别写 Result.fail(e.getMessage())——那会把 SQL 语句、类名、文件路径直接吐给外部，是典型的信息泄露漏洞。

8.4 面试问答：流程与组件 ​

Q1：说一下 Spring MVC 的完整执行流程。

A：① 请求到达 DispatcherServlet；② 调 HandlerMapping 得到 HandlerExecutionChain（Handler + 拦截器链）；③ 根据 Handler 类型选 HandlerAdapter；④ 执行拦截器 preHandle（正序）；⑤ HandlerAdapter 通过参数解析器完成类型转换与校验，反射调用 Controller；⑥ 返回值交给返回值处理器——有 @ResponseBody 就走 HttpMessageConverter 直接写响应体并结束，否则封装为 ModelAndView；⑦ 执行 postHandle（逆序）；⑧ ViewResolver 解析视图并 render；⑨ 执行 afterCompletion（逆序，异常也走）。

Q2：HandlerMapping 和 HandlerAdapter 为什么要分开？

A：职责不同。前者解决"谁来处理"，后者解决"怎么调用"。Handler 形态多样（注解方法、Controller 接口、HttpRequestHandler），注解方法的签名更是完全自由，所以用适配器模式把参数解析、反射调用、返回值处理下沉到 HandlerAdapter，DispatcherServlet 就不必关心具体形态，符合开闭原则。

Q3：DispatcherServlet 的 url-pattern 配 / 和 /* 有什么区别？

A：/ 匹配所有请求但不含 *.jsp，JSP 交给容器的 JspServlet，是正确写法；/* 连 JSP 也拦，导致转发到 JSP 的请求被再次拦截，出现 404 或死循环。

Q4：Spring MVC 是线程安全的吗？

A：DispatcherServlet 和 Controller 都是单例，框架本身不保证业务线程安全。只要 Controller 里不定义可变成员变量、只使用方法局部变量，就是安全的；需要请求级共享数据时用 ThreadLocal 并务必在 afterCompletion 清理。

Q5：@RequestBody 是怎么把 JSON 变成对象的？

A：由 RequestResponseBodyMethodProcessor 这个参数解析器处理：它遍历注册的 HttpMessageConverter 列表，根据请求的 Content-Type 和目标类型调 canRead 筛选，命中 MappingJackson2HttpMessageConverter 后用 Jackson 的 ObjectMapper 读取请求体输入流完成反序列化。出参方向同理走 canWrite/write。

Q6：父子容器是怎么回事？Spring Boot 里还有吗？

A：传统 SSM 中 ContextLoaderListener 创建父容器（Service、DAO、事务、数据源），DispatcherServlet 创建子容器（Controller、视图解析器、拦截器）；子可访问父，父不可访问子。Spring Boot 只有一个容器，不存在父子结构，因此也没有"重复扫描导致事务失效"这类问题。

8.5 面试问答：绑定、拦截与异常 ​

Q7：@RequestParam 和 @RequestBody 的区别？

A：数据源和解析机制都不同。@RequestParam 走 Servlet 的 getParameter()，数据来自查询串或表单体；@RequestBody 走 HttpMessageConverter，直接读请求体字节流。所以 application/json 必须用 @RequestBody，而且一个方法里只能有一个（流只能读一次）。判断依据是 Content-Type，不是请求方法。

Q8：@Valid 和 @Validated 的区别？

A：@Valid 是 JSR 标准注解，支持嵌套级联（加在字段上），不支持分组；@Validated 是 Spring 扩展，支持分组校验和方法级参数校验（配合类上注解），但不支持字段级联。实践上方法参数用 @Validated，实体内部嵌套字段用 @Valid。

Q9：拦截器和过滤器的区别？什么时候用 AOP？

A：过滤器属 Servlet 规范、由容器管理、作用于所有请求（含静态资源），能拿到原始流、可包装请求；拦截器属 Spring MVC、由 Spring 管理、只作用于 DispatcherServlet 处理的请求，能拿到 HandlerMethod（方法和注解信息）；AOP 作用于任意 Spring Bean 方法，能拿到真实入参对象和返回值。选型：改流用过滤器，基于接口/注解判断用拦截器，需要方法参数对象用 AOP。

Q10：多个拦截器的执行顺序？preHandle 返回 false 会怎样？

A：preHandle 按注册/order 正序执行，postHandle 和 afterCompletion 逆序执行。某个 preHandle 返回 false 时流程中断，它自己的 postHandle 和 afterCompletion 都不执行，但之前已放行的拦截器的 afterCompletion 会逆序执行。此时必须自己写响应，否则前端收到 200 + 空 body。

Q11：为什么会跨域？后端怎么解决？拦的是请求还是响应？

A：浏览器同源策略要求协议、域名、端口三者一致。拦的是响应——请求实际已到达后端并执行完毕，只是浏览器检查到响应缺少 Access-Control-Allow-Origin 就不把结果交给 JS，所以 Postman 测不出跨域。解决方案有三层：CorsFilter（优先级最高，适合有 Security 的项目）、addCorsMappings（MVC 全局，推荐）、@CrossOrigin（类/方法级）。注意 allowCredentials(true) 不能与 allowedOrigins("*") 并存，要改用 allowedOriginPatterns。

Q12：什么是预检请求？什么情况下会触发？

A：浏览器在发非简单请求前自动发一个 OPTIONS 询问服务端是否允许。简单请求需同时满足：方法为 GET/HEAD/POST、Content-Type 为 text/plain/multipart/form-data/x-www-form-urlencoded、无自定义请求头。所以发 JSON 或带 Authorization 头必然触发预检——这也是"GET 正常、POST 跨域"的根因，解决要点是拦截器放行 OPTIONS 并把自定义头写进 allowedHeaders。

Q13：全局异常处理怎么做？什么情况下会失效？

A：用 @RestControllerAdvice + @ExceptionHandler，按异常类型分别返回统一 Result，并用 @ExceptionHandler(Exception.class) 兜底。失效场景：① Controller 里自己 try-catch 吞了异常（最常见）；② 异常发生在 Filter 或拦截器中，还没进 handler 执行阶段；③ 异步请求需要 setErrorResult 主动交回；④ advice 类不在扫描包内；⑤ 404 默认不抛 NoHandlerFoundException，需开配置。

Q14：@ResponseBody 之后拦截器还会执行吗？

A：postHandle 和 afterCompletion 仍然执行，但响应体此时已经写出，ModelAndView 为 null，在 postHandle 里改数据没有任何效果。要改响应体只能用 ResponseBodyAdvice 或过滤器包装响应。
