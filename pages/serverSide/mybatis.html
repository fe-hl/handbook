1.1 没有持久层框架的日子有多痛 ​

先看一段纯 JDBC 查询员工的代码，它是 MyBatis 存在的全部理由：

java
// ❌ 纯 JDBC：真正有价值的只有一行 SQL，其余全是噪音
public Employee selectById(int id) {
    Connection conn = null;
    PreparedStatement ps = null;
    ResultSet rs = null;
    try {
        Class.forName("com.mysql.cj.jdbc.Driver");                  // 1. 加载驱动
        conn = DriverManager.getConnection(URL, USER, PWD);         // 2. 建连接（每次新建！）
        ps = conn.prepareStatement(
                "SELECT emp_id, emp_name, emp_salary FROM t_emp WHERE emp_id = ?"); // 3. SQL 硬编码
        ps.setInt(1, id);                                           // 4. 手工设参数
        rs = ps.executeQuery();
        Employee emp = null;
        if (rs.next()) {                                            // 5. 手工拆结果集
            emp = new Employee();
            emp.setEmpId(rs.getInt("emp_id"));
            emp.setEmpName(rs.getString("emp_name"));
            emp.setEmpSalary(rs.getDouble("emp_salary"));
        }
        return emp;
    } catch (Exception e) {
        throw new RuntimeException(e);
    } finally {
        close(rs); close(ps); close(conn);                          // 6. 手工关资源，漏一个就泄漏
    }
}

把这段代码拆开看，痛点一共六类：

text

│ 1. 连接管理    每次 new 一个 Connection，没有池化    │
│ 2. SQL 硬编码  SQL 混在 Java 字符串里，改一次要重编译│
│ 3. 参数设置    setInt / setString 下标对错不报错     │
│ 4. 结果解析    字段多一个就多写三行，纯体力活        │
│ 5. 资源释放    finally 里三层 close，漏一个连接泄漏  │
│ 6. 异常处理    checked 异常层层 try-catch，代码淹没  │
└─────────────────────────────────────────────────────┘
          │
          ▼  MyBatis 接管 1/3/4/5/6，把 2 搬到 XML/注解
┌─────────────────────────────────────────────────────┐
│ List<Employee> list = employeeMapper.selectAll();    │
└─────────────────────────────────────────────────────┘

常见误解

"用了 MyBatis 就不用懂 JDBC 了"——恰恰相反。MyBatis 本身就是 JDBC 的一层封装，PreparedStatement、事务提交、连接泄漏这些概念一个都没消失，只是被藏了起来。后面排查"连接池耗尽""事务不回滚"这类问题时，没有 JDBC 基础会寸步难行。

1.2 MyBatis 是什么、不是什么 ​

概念

MyBatis 是一款半自动的持久层框架。它把 JDBC 中"连接管理、参数设置、结果映射、资源释放"这些模板代码全部接管，但把 SQL 的编写权完整地留给开发者。它的前身是 Apache 的 iBatis，2010 年迁出并更名为 MyBatis。

它是什么：

  • 一个 SQL 映射器（SQL Mapper）：核心职责是把"Java 方法调用"和"一条 SQL 语句"绑定起来，并负责双向的数据搬运
  • 一个 JDBC 的薄封装：底层仍然是 Connection/PreparedStatement/ResultSet，没有任何魔法
  • 一个 可插拔的框架：Executor、StatementHandler、ParameterHandler、ResultSetHandler 四大组件都可以被插件拦截和替换

它不是什么：

常见误解实际情况
"MyBatis 能自动生成所有 SQL"不能。单表 CRUD 要自己写，想自动生成请用 MyBatis-Plus 或逆向工程
"MyBatis 自带连接池所以不用配"MyBatis 自带的 POOLED 很简陋，生产一律用 HikariCP / Druid
"MyBatis 管事务"它只提供 commit()/rollback() 的入口，事务边界靠 Spring @Transactional 划
"数据库换了 MyBatis 能无感迁移"恰恰最难。SQL 是你手写的，方言差异（分页、函数）全部要自己改
"二级缓存开了就能提升性能"多数场景下是坑，见 6.3

📌 单独澄清：MyBatis 不负责"写 SQL"，这既是缺点也是它的核心卖点

很多人把"要自己写 SQL"当成 MyBatis 的缺陷，其实这是它被广泛采用的根本原因：

text
Hibernate 的世界：你描述"要什么对象"，框架生成 SQL
   ↓ 优点：单表开发飞快
   ↓ 缺点：SQL 不可控。慢查询出现时，你只能去猜框架生成了什么，
          然后用 HQL / Criteria / 原生 SQL 绕过框架

MyBatis 的世界：你直接写 SQL，框架只负责搬运数据
   ↓ 优点：SQL 完全可控，能用上索引提示、覆盖索引、强制走某个执行计划
   ↓ 缺点：单表 CRUD 要写一堆重复代码（这正是 MyBatis-Plus 补的位）

在互联网业务里，SQL 可控 > 开发快：一条没走索引的 SQL 能把整个数据库拖垮，而多写二十行单表 CRUD 只是手累。这就是国内 MyBatis 几乎一统天下的原因。

1.3 JDBC / Hibernate / MyBatis / MyBatis-Plus 的边界 ​

这四个名字经常被放在一起比较，但它们处在不同的抽象层次上：

┌─────────────────────────────────────────────┐

判断口诀：SQL 由框架生成的是全自动（Hibernate），SQL 由你写的是半自动（MyBatis）；MyBatis-Plus 不是第三种框架，它只是帮你把单表那部分 SQL 省掉。

📌 单独澄清：MyBatis-Plus 不是"MyBatis 的替代品"

MyBatis-Plus 启动时会扫描实体类，把单表 CRUD 的 MappedStatement 动态注入到 MyBatis 的 Configuration 里。也就是说它生成的东西和你手写 XML 生成的东西是同一种对象，走的是同一套执行流程。

java
// ✅ 二者可以在同一个 Mapper 里共存
public interface UserMapper extends BaseMapper<User> {   // MP 提供单表 CRUD
    // MyBatis 原生写法：复杂 SQL 照样手写 XML 或注解
    List<UserVO> selectReportByDept(@Param("deptId") Long deptId);
}

所以学习顺序不能颠倒：先懂 MyBatis 的执行流程，再用 MyBatis-Plus。否则遇到"Wrapper 拼出来的 SQL 不走索引""逻辑删除让唯一索引失效"这类问题，连从哪儿看日志都不知道。

1.4 "半自动 ORM"到底半在哪 ​

ORM（Object Relational Mapping）要解决的是两个世界的阻抗不匹配：Java 里是对象和引用，数据库里是行和外键。一个完整的 ORM 要干三件事。

text
① 表 ←→ 类        （t_emp  ←→ Employee）
② 字段 ←→ 属性     （emp_name ←→ empName）
③ 外键 ←→ 对象引用 （dept_id ←→ Employee.dept）
             ┬
             │  再加上一件最关键的：
④ 对象操作 ←→ SQL 语句（emp.save() ←→ INSERT INTO ...）

Hibernate：①②③④ 全包           → 全自动
MyBatis  ：①②③ 包了，④ 不包     → 半自动
ORM 职责HibernateMyBatis
表 ←→ 类@Entity @TableresultType / typeAliases
字段 ←→ 属性@Column驼峰自动映射 / resultMap 手配
外键 ←→ 引用@ManyToOne 自动 JOINassociation / collection 手配
生成 SQL框架生成开发者手写
脏检查自动更新支持（Session 托管）❌ 不支持
一级缓存默认开启且强绑定对象默认开启但只缓存查询结果

判断口诀：半自动的"半"，指的就是第 ④ 件事——SQL 不替你生成。

📌 单独澄清：MyBatis 没有"托管对象"的概念

这是 Hibernate 用户转 MyBatis 时最容易踩的认知坑。

java
// ❌ Hibernate 的思维：改了对象属性，事务提交时自动 UPDATE
@Transactional
public void raiseSalary(int id) {
    Employee emp = employeeMapper.selectById(id);
    emp.setEmpSalary(emp.getEmpSalary() + 500);
    // Hibernate：Session 检测到脏数据，提交时自动发 UPDATE
    // MyBatis：什么都不会发生！数据库里的数据一点没变
}

// ✅ MyBatis 的思维：想改数据库，就必须显式调用一次更新方法
@Transactional
public void raiseSalary(int id) {
    Employee emp = employeeMapper.selectById(id);
    emp.setEmpSalary(emp.getEmpSalary() + 500);
    employeeMapper.updateById(emp);   // 必须这一行
}

MyBatis 查出来的对象是普通的 POJO，和框架彻底脱钩，改它只是改内存。这个设计让 MyBatis 的行为极其可预测：只有你调用的方法会发 SQL，不会有任何"框架偷偷帮你执行"的情况。

2.1 四大核心对象：从 Factory 到 Executor ​

MyBatis 的内部结构可以用一条链条串起来，记住这条链，整个框架就不再是黑盒：

text
mybatis-config.xml / application.yml
   │  解析（XMLConfigBuilder）
   ▼
Configuration                 ← 全局配置中心，单例，启动后基本只读
   │  持有 mappedStatements、typeHandlers、plugins、cache...
   ▼
SqlSessionFactory             ← 重量级，一个数据源一个，应用级单例
   │  openSession()
   ▼
SqlSession                    ← 轻量级，一次会话（通常=一次请求/一个事务）
   │  非线程安全，用完必须 close
   ▼
Executor                      ← 真正的执行者，持有一级缓存
   │  query() / update()
   ├──▶ StatementHandler      ← 创建 Statement、设置参数、执行
   │       ├──▶ ParameterHandler  ← 把 Java 参数塞进 PreparedStatement
   │       └──▶ ResultSetHandler   ← 把 ResultSet 拼成 Java 对象
   ▼
JDBC（Connection / PreparedStatement / ResultSet）
对象作用域与生命周期线程安全实战要点
Configuration应用级，启动时构建启动后只读可共享所有 Mapper 元数据都在这里
SqlSessionFactory应用级单例，和应用同生命周期安全不要反复创建，构建代价很高
SqlSession请求级 / 方法级不安全绝不能定义成成员变量或静态变量
Executor跟随 SqlSession不安全一级缓存就挂在它身上
StatementHandler一次 SQL 执行不安全插件最常拦截的对象

SqlSession 线程安全的真实后果

把 SqlSession 存成 Spring Bean 的成员变量，在并发下会出现：A 请求的查询结果被 B 请求读到（一级缓存串了）、A 的事务提交把 B 未完成的修改一起提交、Connection 被提前关闭导致 Connection is closed。

Spring 整合后你拿到的 SqlSession 其实是 SqlSessionTemplate——它是线程安全的代理，内部通过 ThreadLocal 为每个线程绑定真正的 SqlSession。所以在 Spring 项目里你不需要也不应该自己 openSession()。

java
// ❌ 原生 API 下最经典的错误：SqlSession 当成员变量
public class EmpService {
    private SqlSession sqlSession = factory.openSession();  // 全局共享，并发必炸
}

// ✅ 原生 API：每次使用都新建并用 try-with-resources 关闭
public List<Employee> list() {
    try (SqlSession session = factory.openSession()) {
        return session.getMapper(EmployeeMapper.class).selectAll();
    }
}

// ✅ Spring 项目：直接注入 Mapper，session 的生命周期由 Spring 管
@Service
public class EmpService {
    @Autowired
    private EmployeeMapper employeeMapper;
}

2.3 Mapper 接口没有实现类，方法为什么能调用 ​

这是 MyBatis 的面试必考题，也是理解"接口 + XML"这套写法的关键。

概念

MyBatis 为每个 Mapper 接口用 JDK 动态代理生成了一个代理对象 MapperProxy。你调用接口方法时，实际执行的是 MapperProxy.invoke()，它把"方法调用"翻译成"SqlSession 上的一次 SQL 执行"。

java
// 简化后的核心逻辑
public class MapperProxy<T> implements InvocationHandler {
    private final SqlSession sqlSession;
    private final Class<T> mapperInterface;

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        // Object 自带方法（toString/hashCode）直接放过
        if (Object.class.equals(method.getDeclaringClass())) {
            return method.invoke(this, args);
        }
        // 1. 方法签名 → MapperMethod（含 statementId、命令类型、返回类型）
        MapperMethod mapperMethod = cachedMapperMethod(method);
        // 2. 执行：内部根据命令类型调 sqlSession.selectList / insert / update ...
        return mapperMethod.execute(sqlSession, args);
    }
}

statementId 是怎么拼出来的：

text

com.at.mapper.EmployeeMapper        +  .  +  selectById
            │                                     │
            └─────── 必须等于 XML 的 namespace ────┘
                     必须等于 <select> 的 id

拼出的 key：com.at.mapper.EmployeeMapper.selectById
           ↓ 去 Configuration.mappedStatements 里查
           找到 → 正常执行
           找不到 → BindingException: Invalid bound statement (not found)

3.3 接口与 XML 的绑定规则：四条铁律 ​

Invalid bound statement (not found) 是 MyBatis 报错榜第一名，根因永远是这四条里的某一条没满足。

注解方式：能不能不写 XML？

java
public interface EmployeeMapper {
    // ✅ 简单 SQL 用注解很干净
    @Select("SELECT emp_id, emp_name FROM t_emp WHERE emp_id = #{empId}")
    Employee selectById(Integer empId);

    // ❌ 复杂动态 SQL 用注解会变成这样，可读性灾难
    @Select("<script>SELECT * FROM t_emp <where>"
          + "<if test='empName != null'>AND emp_name = #{empName}</if>"
          + "</where></script>")
    List<Employee> selectByCondition(Employee emp);
}
维度XML注解
简单单表略啰嗦✅ 干净
动态 SQL✅ 清晰❌ 字符串拼接，难读难改
复杂结果映射✅ resultMap 直观❌ @Results 极其冗长
SQL 格式化✅ IDE 支持高亮/格式化❌ 字符串里无高亮
改 SQL改 XML，可热加载改 Java，必须重新编译

判断口诀：单表、固定 SQL 用注解；只要出现 <if> 或多表映射，立刻换 XML。 同一个项目里两种混用完全没问题，但同一个方法不能既有注解又有 XML，否则启动报 Mapped Statements collection already contains value。

生效阶段参数设置（第 ⑨ 步）SQL 拼装（第 ⑦ 步）
底层PreparedStatement + ?字符串拼接

类型转换✅ 走 TypeHandler❌ 直接 toString()

执行计划缓存✅ SQL 文本固定，可复用❌ 每个值一条新 SQL

public List<Employee> list(String orderColumn) {
    return mapper.selectAllOrderBy(orderColumn);   // 传入 "1; DROP TABLE t_emp" 呢？
}

// ✅ 枚举白名单，前端只能传 key，不能传 SQL 片段
private static final Map<String, String> SORT_WHITELIST = Map.of(
        "salary", "emp_salary",
        "name",   "emp_name",
        "id",     "emp_id");

public List<Employee> list(String sortKey, boolean asc) {
    String column = SORT_WHITELIST.get(sortKey);
    if (column == null) {
        throw new IllegalArgumentException("非法排序字段: " + sortKey);
    }
    return mapper.selectAllOrderBy(column, asc ? "ASC" : "DESC");
}

📌 单独澄清：LIKE 模糊查询不要用 ${}

这是 ${} 被滥用最多的地方，其实有三种更安全的写法：

xml
<!-- ❌ 字符串拼接，有注入风险 -->
WHERE emp_name LIKE '%${empName}%'

<!-- ✅ 方案 A：CONCAT，推荐，MySQL 通用 -->
WHERE emp_name LIKE CONCAT('%', #{empName}, '%')

<!-- ✅ 方案 B：bind 标签，数据库无关 -->
<bind name="pattern" value="'%' + empName + '%'"/>
WHERE emp_name LIKE #{pattern}

<!-- ✅ 方案 C：在 Java 层拼好通配符再传进来 -->
WHERE emp_name LIKE #{pattern}

另外提醒：LIKE '%xxx%' 的前置通配符无法使用索引，数据量大时要改用全文索引或 ES，这是性能问题而非语法问题。

判断口诀：传值用 #{}，传 SQL 结构用 ${}；只要用了 ${}，旁边就必须有一段白名单校验。

4.4 主键回填：useGeneratedKeys 与 selectKey ​

业务里"插入主表后要拿到主键去插子表"极其常见。注意：插入方法的返回值是受影响行数，不是主键。

java
// ❌ 误解：以为返回值是新主键

// ✅ 主键被回填到了入参对象上
employeeMapper.insert(emp);
Integer newId = emp.getEmpId();          // 这才是新主键

自增主键（MySQL AUTO_INCREMENT）：

xml
<insert id="insert" useGeneratedKeys="true" keyProperty="empId">
    INSERT INTO t_emp(emp_name, emp_salary, dept_id)
    VALUES (#{empName}, #{empSalary}, #{deptId})
</insert>
属性含义
useGeneratedKeys让 JDBC 通过 getGeneratedKeys() 取回主键
keyProperty回填到入参对象的哪个属性（不是列名）
keyColumn数据库那边的主键列名，一般不用写

非自增主键（UUID、雪花 ID、序列）：

xml
<insert id="insertWithUuid">
    <!-- order="BEFORE"：先执行它拿到 id，再执行 INSERT -->
    <selectKey keyProperty="id" resultType="string" order="BEFORE">
        SELECT REPLACE(UUID(), '-', '')
    </selectKey>
    INSERT INTO t_user(id, username) VALUES (#{id}, #{username})
</insert>
order 取值执行时机适用场景
BEFOREINSERT 之前UUID、Oracle 序列（主键要先生成）
AFTERINSERT 之后MySQL LAST_INSERT_ID()（主键由库生成）

批量插入的主键回填有坑

xml

<insert id="insertBatch" useGeneratedKeys="true" keyProperty="empId">
    INSERT INTO t_emp(emp_name, emp_salary) VALUES
    <foreach collection="list" item="e" separator=",">
        (#{e.empName}, #{e.empSalary})
    </foreach>
</insert>

MySQL 驱动能把自增 ID 依次回填到列表中每个对象，但必须满足两个条件：JDBC URL 带上 rewriteBatchedStatements=true，且主键是单列自增。换成 Oracle 或者复合主键，回填直接失效且不报错——不要在批量插入后无条件信任 e.getEmpId()，要么验证过再用，要么改成先生成 ID（雪花算法）再插入。

属性作用

JOIN 方式 vs 分步方式：

维度JOIN（嵌套结果）分步（嵌套查询）
SQL 条数1 条1 + N 条
支持延迟加载❌ 不支持✅ 支持
一对多可分页❌ 会出错✅ 可以
SQL 复杂度高（多表 JOIN）低（每条都是单表）
代码复用差好（子 statement 可独立被调用）
N+1 风险无有

N+1 问题是什么：

text
查 100 个员工及其部门（分步查询，未开延迟加载）：

  SELECT * FROM t_emp                        ← 1 条，返回 100 行
  SELECT * FROM t_dept WHERE dept_id = 1     ← 第 1 条
  SELECT * FROM t_dept WHERE dept_id = 2     ← 第 2 条
  ...
  SELECT * FROM t_dept WHERE dept_id = 100   ← 第 100 条
  ────────────────────────────────────────
  合计 101 条 SQL = 1 + N

单条 SQL 耗时 2ms，网络往返 1ms → 101 × 3ms ≈ 300ms
换成一条 JOIN → 5ms

开启延迟加载：

yaml
mybatis:
  configuration:
    # 开启延迟加载总开关
    lazy-loading-enabled: true
    # 必须设为 false：true 时访问任意属性都会触发全部关联加载
    aggressive-lazy-loading: false

延迟加载的三个致命前提

  1. Session 必须还活着。 延迟加载的本质是对象里存着一个未执行的查询，等到调用 getter 时才真正去数据库。如果 SqlSession 已关闭（比如数据已经返回到 Controller 层、事务已提交），再访问就会抛 ExecutorException: Executor was closed。
  2. 序列化会触发全量加载。 返回给前端做 JSON 序列化时，Jackson 会调用所有 getter，延迟加载瞬间全部触发——省下的 SQL 一条没少，还多了一层代理开销。
  3. 对象不再是纯 POJO。 MyBatis 用 Javassist/CGLIB 生成代理子类，equals、hashCode、getClass() 的行为都可能和预期不同。

📌 单独澄清：解决 N+1 的正确姿势不是"开延迟加载"

java
// ❌ 伪解决：延迟加载只是把 N 次查询推迟了，没有减少
// ❌ 反模式：在 for 循环里一条条查
for (Employee e : employees) {
    e.setDepartment(deptMapper.selectById(e.getDeptId()));  // N 次 SQL
}

// ✅ 方案 A：JOIN 一次查完（关联数据量可控时）
// ✅ 方案 B：批量查 + 内存组装（最通用，推荐）
List<Employee> emps = empMapper.selectAll();
Set<Integer> deptIds = emps.stream()
        .map(Employee::getDeptId).collect(Collectors.toSet());
Map<Integer, Department> deptMap = deptMapper.selectByIds(deptIds).stream()
        .collect(Collectors.toMap(Department::getDeptId, d -> d));
emps.forEach(e -> e.setDepartment(deptMap.get(e.getDeptId())));
// 总共 2 条 SQL，与数据量无关

判断口诀：N+1 的根因是"循环里发 SQL"，解法永远是"把 N 次合并成 1 次"，而不是"让这 N 次晚点发生"。

5.1 动态 SQL 的本质：SqlNode 树 + OGNL ​

概念

动态 SQL 不是"模板引擎做字符串拼接"，而是：XML 解析阶段把 SQL 拆成一棵 SqlNode 树，运行时带着参数遍历这棵树，每个节点决定自己输出什么，最后拼成带 ? 占位符的 BoundSql。

text
<select id="selectByCondition">
    SELECT * FROM t_emp
    <where>
        <if test="empName != null"> AND emp_name = #{empName} </if>
        <if test="deptId != null">  AND dept_id  = #{deptId}  </if>
    </where>
</select>

解析为 SqlNode 树：
  MixedSqlNode
    ├── StaticTextSqlNode("SELECT * FROM t_emp")
    └── WhereSqlNode
          ├── IfSqlNode(test="empName != null")
          │     └── TextSqlNode(" AND emp_name = #{empName} ")
          └── IfSqlNode(test="deptId != null")
                └── TextSqlNode(" AND dept_id = #{deptId} ")

运行时 apply(DynamicContext)：
  每个 IfSqlNode 用 OGNL 求值 test 表达式 → true 才把子节点内容追加进去
         ↓
  "SELECT * FROM t_emp WHERE emp_name = ?"
标签对应 SqlNode职责
纯文本StaticTextSqlNode原样输出
含 ${}TextSqlNode运行时做字符串替换
<if>IfSqlNodeOGNL 求值决定是否输出
<where>WhereSqlNode有内容才加 WHERE，并去掉开头的 AND/OR
<set>SetSqlNode加 SET，并去掉结尾的逗号
<trim>TrimSqlNode上面两者的通用版
<foreach>ForEachSqlNode循环并生成 __frch_ 前缀的临时参数
<choose>ChooseSqlNode多选一

test 表达式用的是 OGNL，不是 Java：

xml
<!-- ✅ OGNL 支持的写法 -->
<if test="empName != null and empName != ''">
<if test="list != null and list.size() > 0">
<if test="status == 1">
<if test="'ACTIVE'.equals(status)">

<!-- ❌ 常见错误 -->
<if test="empName != null && empName != ''">   <!-- & 是 XML 特殊字符，要写 and 或 &amp;&amp; -->
<if test="empName.length > 0">                  <!-- empName 为 null 时抛 NPE，没有短路保护 -->

OGNL 的单字符字符串会被当成 char

xml
<!-- ❌ status 是 String 类型时，这里比较的是 String 和 char，永远 false -->
<if test="status == 'Y'">

<!-- ✅ 三种正确写法 -->
<if test='status == "Y"'>              <!-- 外层单引号、内层双引号 -->
<if test="status == 'Y'.toString()">
<if test="'Y'.equals(status)">

这个坑的恶心之处在于不报错，只是条件永远不成立，SQL 少了一段 WHERE，查出来一堆数据。

📌 单独澄清：动态 SQL 拼的是"SQL 结构"，不是"参数值"

text
<if> 决定的是：这段 SQL 文本要不要出现
#{} 决定的是：参数值怎么通过 PreparedStatement 传进去

所以：
  <if> 里写 #{xxx}   → 安全，最终还是占位符    ✅
  <if> 里写 ${xxx}   → 字符串直接拼进 SQL 结构  ⚠️ 需白名单

5.2 if / where / set / trim 的组合与坑 ​

<if> 单独用的经典翻车现场：

xml
<!-- ❌ 所有条件都不成立时：SELECT * FROM t_emp WHERE
     第一个条件不成立、第二个成立时：... WHERE AND dept_id = ? -->
<select id="bad" resultType="employee">
    SELECT * FROM t_emp WHERE
    <if test="empName != null"> emp_name = #{empName} </if>
    <if test="deptId != null">  AND dept_id = #{deptId} </if>
</select>

三种修法：

xml
<!-- 方案 1：恒真条件（土办法，但真实项目里很常见） -->
SELECT * FROM t_emp WHERE 1 = 1
<if test="empName != null"> AND emp_name = #{empName} </if>

<!-- 方案 2：<where>（推荐） -->
SELECT * FROM t_emp
<where>
    <if test="empName != null"> AND emp_name = #{empName} </if>
    <if test="deptId != null">  AND dept_id  = #{deptId}  </if>
</where>

<!-- 方案 3：<trim>（最灵活） -->
SELECT * FROM t_emp
<trim prefix="WHERE" prefixOverrides="AND |OR ">
    ...
</trim>

<where> 的行为规则：

text
1. 内部没有任何内容  → 整个 WHERE 都不输出
2. 内部有内容        → 自动加上 WHERE
3. 内容以 AND / OR 开头 → 自动删掉开头的 AND / OR
4. 结尾的 AND / OR   → ❌ 不处理！
xml
<!-- ❌ 条件写在 AND 前面，<where> 管不了结尾 -->
<where>
    <if test="empName != null"> emp_name = #{empName} AND </if>
    <if test="deptId != null">  dept_id  = #{deptId}      </if>
</where>
<!-- deptId 为 null 时 → WHERE emp_name = ? AND  → 语法错误 -->

<!-- ✅ 统一把 AND 写在每个条件的开头 -->

<set> 用于 UPDATE，自动去掉结尾逗号：

xml
<update id="updateSelective">
    UPDATE t_emp
    <set>
        <if test="empName != null">   emp_name   = #{empName},   </if>
        <if test="empSalary != null"> emp_salary = #{empSalary}, </if>
        <if test="deptId != null">    dept_id    = #{deptId},    </if>
    </set>
    WHERE emp_id = #{empId}
</update>

<set> 全空会生成无效 SQL，而且会全表更新

text
所有 if 都不成立 →  UPDATE t_emp WHERE emp_id = ?   语法错误（好在会报错）

更危险的情况：WHERE 条件也是动态的
  UPDATE t_emp SET emp_salary = ?    ← 没有 WHERE
  → 全表工资被改掉，且事务提交后无法回滚

铁律：UPDATE 和 DELETE 的 WHERE 条件永远不要放在 <if> 里。 主键条件必须是硬编码的静态文本。如果业务上确实需要动态 WHERE，就在 Java 层先校验参数非空再调用。

<trim> 是 <where> 和 <set> 的通用底层实现：

属性作用
prefix有内容时在前面加上这段文本
suffix有内容时在后面加上这段文本
prefixOverrides删除内容开头匹配的文本
suffixOverrides删除内容结尾匹配的文本
xml
<!-- 等价于 <where> -->
<trim prefix="WHERE" prefixOverrides="AND |OR ">

<!-- 等价于 <set> -->
<trim prefix="SET" suffixOverrides=",">

<!-- <where> 做不到的：动态列名的 INSERT -->
<insert id="insertSelective">
    INSERT INTO t_emp
    <trim prefix="(" suffix=")" suffixOverrides=",">
        <if test="empName != null">   emp_name,   </if>
        <if test="empSalary != null"> emp_salary, </if>
    </trim>
    <trim prefix="VALUES (" suffix=")" suffixOverrides=",">
        <if test="empName != null">   #{empName},   </if>
        <if test="empSalary != null"> #{empSalary}, </if>
    </trim>
</insert>

📌 单独澄清：prefixOverrides="AND |OR " 后面的空格不能少

text
prefixOverrides="AND|OR"      →  会把 "ANDROID_ID = ?" 删成 "ROID_ID = ?"  ❌
prefixOverrides="AND |OR "    →  只匹配 "AND " 带空格的形式               ✅

多个候选值用 | 分隔，匹配是纯字符串前缀匹配，不是单词边界匹配。

5.3 choose / foreach / bind / sql-include ​

<choose>：多选一，等价于 Java 的 if-else if-else

xml
<select id="selectByPriority" resultType="employee">
    SELECT * FROM t_emp
    <where>
        <choose>
            <when test="empId != null">   emp_id   = #{empId}   </when>
            <when test="empName != null"> emp_name = #{empName} </when>
            <when test="deptId != null">  dept_id  = #{deptId}  </when>
            <otherwise> 1 = 2 </otherwise>
        </choose>
    </where>
</select>

和多个 <if> 的区别：<choose> 只会命中第一个成立的分支，后面的直接跳过。 适合"按优先级取一个查询条件"的场景；而多个 <if> 是"所有成立的条件都生效"，适合组合筛选。

<otherwise> 写 1=1 还是 1=2

text
<otherwise> 1 = 1 </otherwise>   → 没传任何条件时查全表，可能把百万数据拉出来
<otherwise> 1 = 2 </otherwise>   → 没传条件时返回空集合，更安全

面向外部接口的查询，<otherwise> 一律用 1 = 2 或直接抛参数校验异常。

<foreach>：循环拼接

属性含义
collection要遍历的集合（见 4.1 的命名规则）
item当前元素的变量名
indexList 是下标，Map 是 key
open循环开始前输出
close循环结束后输出
separator元素之间的分隔符
xml
<!-- IN 查询 -->
<select id="selectByIds" resultType="employee">
    SELECT * FROM t_emp WHERE emp_id IN
    <foreach collection="list" item="id" open="(" close=")" separator=",">
        #{id}
    </foreach>
</select>

<!-- 批量插入 -->
<insert id="insertBatch">
    INSERT INTO t_emp(emp_name, emp_salary) VALUES
    <foreach collection="list" item="e" separator=",">
        (#{e.empName}, #{e.empSalary})
    </foreach>
</insert>

<!-- 批量更新：需要 JDBC URL 加 allowMultiQueries=true -->
<update id="updateBatch">
    <foreach collection="list" item="e" separator=";">
        UPDATE t_emp SET emp_salary = #{e.empSalary} WHERE emp_id = #{e.empId}
    </foreach>
</update>

<!-- CASE WHEN 批量更新（不需要 allowMultiQueries，推荐） -->
<update id="updateBatchCase">
    UPDATE t_emp SET emp_salary = CASE emp_id
        <foreach collection="list" item="e">
            WHEN #{e.empId} THEN #{e.empSalary}
        </foreach>
    END
    WHERE emp_id IN
    <foreach collection="list" item="e" open="(" close=")" separator=",">
        #{e.empId}
    </foreach>
</update>

xml
<select id="selectByNameLike" resultType="employee">

    SELECT * FROM t_emp WHERE emp_name LIKE #{pattern}

value 里是 OGNL 表达式，可以做字符串拼接、调用方法。比 CONCAT() 更通用（不依赖数据库方言）。

xml

</sql>

<select id="selectAll" resultType="employee">
    SELECT <include refid="baseColumns"/> FROM t_emp
</select>

    SELECT <include refid="baseColumnsWithAlias"><property name="alias" value="e"/></include>

<!-- 跨文件引用：加上命名空间前缀 -->

📌 单独澄清：<foreach> 的 separator 和手写分隔符的区别

xml
<!-- ❌ 手写逗号：最后会多一个 -->

<!-- → (1,2,3,)   语法错误 -->

<!-- ✅ separator 只在元素之间插入，不会出现在首尾 -->

<!-- → (1,2,3) -->

5.4 动态 SQL 的性能陷阱 ​

动态 SQL 带来了灵活性，代价是同一个方法可能产出几十种不同的 SQL 文本，这会在三个层面造成性能问题。

陷阱一：执行计划缓存命中率低

text
一个 5 个条件的动态查询 → 理论上 2^5 = 32 种 SQL 组合

MySQL 不缓存执行计划（8.0 已移除 Query Cache），影响相对小；
Oracle / PostgreSQL 按 SQL 文本缓存执行计划：
  → 32 种文本 = 32 份执行计划 = 共享池碎片化
  → 硬解析次数上升，高并发下 CPU 飙升

陷阱二：索引失效

text
表 t_emp 有索引 idx_dept_status (dept_id, status)

6.1 一级缓存：作用域、失效与原理 ​

概念

一级缓存（Local Cache）是 SqlSession 级别的缓存，默认开启且无法真正关闭。它存在于 BaseExecutor 内部的一个 PerpetualCache（本质是 HashMap）里，SqlSession 关闭时随之销毁。

text
SqlSession
   └── Executor (BaseExecutor)
          └── localCache : PerpetualCache
                 └── Map<CacheKey, Object>

查询流程：
  mapper.selectById(1)
      ↓
  构造 CacheKey
      ↓
  localCache 里有？ ──是──> 直接返回缓存对象（不发 SQL）
      │否
      ↓
  查数据库 → 放入 localCache → 返回

CacheKey 由五部分组成，任何一部分不同就是不同的 key：

组成部分举例
statementIdcom.at.mapper.EmployeeMapper.selectById
分页参数 offset0
分页参数 limitInteger.MAX_VALUE
SQL 文本SELECT * FROM t_emp WHERE emp_id = ?
参数值1
（+ 环境 id）development
java
// ✅ 第二次查询不发 SQL
Employee e1 = mapper.selectById(1);
Employee e2 = mapper.selectById(1);
System.out.println(e1 == e2);     // true —— 返回的是同一个对象引用！

一级缓存失效的五种情况：

情况原因
不同的 SqlSession缓存挂在 Executor 上，各自独立
查询条件不同CacheKey 不同
两次查询之间执行了增删改update() 会调用 clearLocalCache() 清空全部
手动调用 sqlSession.clearCache()显式清空
flushCache="true"该 statement 执行前强制清空

一级缓存返回的是同一个对象，改了会污染缓存

java
Employee e1 = mapper.selectById(1);
e1.setEmpName("被改了");               // 只改了内存对象，没有 update 数据库

Employee e2 = mapper.selectById(1);    // 命中缓存
System.out.println(e2.getEmpName());   // "被改了"  ❌ 和数据库不一致

MyBatis 不做对象拷贝，缓存里存的就是你拿到的那个引用。这在同一个事务里连续处理同一条数据时很容易出问题。要么不要修改查出来的对象，要么在 <select> 上加 flushCache="true"。

localCacheScope 配置：

yaml
mybatis:
  configuration:
    # SESSION（默认）：整个 SqlSession 共享
    # STATEMENT：每条语句执行完就清空，等于关闭一级缓存
    local-cache-scope: STATEMENT

📌 单独澄清：Spring 环境下一级缓存"看起来经常失效"

text
Spring 整合 MyBatis 后，SqlSession 由 SqlSessionTemplate 管理：

  没有事务时：
    每次 Mapper 方法调用 → 新建 SqlSession → 用完立刻关闭
    → 一级缓存只在单次方法调用内有效，等于没有

  有 @Transactional 时：
    整个事务共享同一个 SqlSession
    → 一级缓存在事务范围内生效

所以"一级缓存在 Spring 里有没有用"的答案是：取决于有没有事务。这也是为什么很多人觉得一级缓存"不存在"——因为他们的查询方法没加事务注解。

6.2 二级缓存：开启条件与工作时机 ​

概念

二级缓存是 namespace 级别（一个 Mapper 一份）的缓存，跨 SqlSession 共享，生命周期与应用进程相同。实现类是 CachingExecutor，它包装在 SimpleExecutor 外面，形成装饰器链。

text
查询请求
   ↓
CachingExecutor          ← 二级缓存（namespace 级，跨 Session）
   ↓ miss
BaseExecutor.localCache  ← 一级缓存（Session 级）
   ↓ miss
数据库

开启二级缓存的四个条件，缺一不可：

yaml
# 条件 1：全局开关（默认就是 true，一般不用动）
mybatis:
  configuration:
    cache-enabled: true
xml
<!-- 条件 2：在 Mapper XML 里声明 <cache/> -->
<mapper namespace="com.at.mapper.EmployeeMapper">
    <cache eviction="LRU" flushInterval="60000" size="1024" readOnly="false"/>
    ...
</mapper>

<!-- 条件 3：该 select 的 useCache 必须是 true（默认 true） -->
<select id="selectById" resultType="employee" useCache="true">
java
// 条件 4：SqlSession 必须提交或关闭，缓存才真正写入
sqlSession.commit();   // 或 sqlSession.close()
<cache> 属性可选值 / 默认含义
evictionLRU（默认）/ FIFO / SOFT / WEAK淘汰策略
flushInterval不设置则永不定时刷新自动刷新间隔（毫秒）
size1024最多缓存多少个对象引用
readOnlyfalsetrue 直接返回引用；false 返回反序列化副本

第 4 个条件最反直觉：commit 之前读不到二级缓存

java
SqlSession s1 = factory.openSession();
Employee e1 = s1.getMapper(EmployeeMapper.class).selectById(1);
// 此刻数据还在 s1 的"事务暂存区"TransactionalCache 里，没进二级缓存

SqlSession s2 = factory.openSession();
Employee e2 = s2.getMapper(EmployeeMapper.class).selectById(1);
// ❌ 没命中，又发了一条 SQL

s1.close();   // ← 此刻 TransactionalCache 才 flush 进二级缓存
SqlSession s3 = factory.openSession();
Employee e3 = s3.getMapper(EmployeeMapper.class).selectById(1);
// ✅ 命中二级缓存

设计原因：如果 s1 的事务最终回滚了，缓存里就会留下脏数据。所以 MyBatis 用 TransactionalCache 做了一层暂存，只有事务成功提交才真正写入。

readOnly 的取舍：

text
readOnly="true"   → 所有调用方拿到同一个对象引用
                    快（没有序列化开销），但任何一方修改都会污染缓存
                    要求：业务上保证绝不修改查询结果

readOnly="false"  → 每次返回一个反序列化的新副本（默认）
                    安全，但实体类必须实现 Serializable，且有序列化开销
java
// readOnly="false" 时实体必须可序列化，否则抛
// java.io.NotSerializableException: com.at.pojo.Employee
public class Employee implements Serializable {
    private static final long serialVersionUID = 1L;
    ...
}

6.3 为什么生产环境基本不用二级缓存 ​

二级缓存在教程里很美好，在生产环境里几乎是禁区。原因有五个，每一个都是硬伤。

硬伤一：集群下必然脏读

text
应用部署 3 个实例，每个实例有独立的 JVM 内存：

  实例 A：缓存了 emp_id=1 的数据（工资 10000）
  实例 B：执行 UPDATE 把工资改成 20000，清空了【自己】的缓存
  实例 C：缓存里也还是旧数据

  用户请求被负载均衡打到 A  →  读到 10000  ❌ 脏数据
  下一次打到 B              →  读到 20000  ✅
  → 同一个用户连续刷新，数据在新旧之间反复横跳

MyBatis 二级缓存默认是本地 JVM 内存缓存，没有任何跨节点同步机制。单机部署的时代它还成立，微服务 + 多副本的今天根本不成立。

硬伤二：namespace 隔离 → 关联表数据无法感知

text
EmployeeMapper 的 selectWithDept 做了 JOIN，结果缓存在 EmployeeMapper 的 namespace
   ↓
DepartmentMapper 执行 UPDATE t_dept SET dept_name = '新研发部'
   ↓
只清空 DepartmentMapper 的缓存
   ↓
EmployeeMapper 缓存里的部门名字还是旧的  ❌

官方给了 <cache-ref namespace="..."/> 让多个 Mapper 共用一份缓存，但这等于放弃隔离，只要有三四张表互相 JOIN，缓存共享关系就会复杂到无人敢动。

硬伤三：清空粒度太粗，命中率接近零

text
一个订单表 Mapper，QPS 1000（900 读 + 100 写）
每秒 100 次写 → 每秒清空 100 次整个 namespace
→ 缓存平均存活时间 10ms
→ 命中率 ≈ 0，白白增加了序列化和加锁开销

硬伤四：缺乏运维手段

能力MyBatis 二级缓存Redis
查看缓存内容❌ 无✅ 直接查
手动清除某个 key❌ 无✅ DEL
过期时间（TTL）只有全局定时刷新✅ 每个 key 独立
内存占用监控❌ 无✅ INFO memory
容量超限行为按 LRU 淘汰✅ 多种淘汰策略可配
跨节点共享❌✅

线上出问题时，你无法回答"现在缓存里到底存了什么"，这在排障时是致命的。

硬伤五：它解决的问题，应该在更上层解决

text
缓存应该贴近业务语义，而不是贴近 SQL：

  ❌ MyBatis 二级缓存：缓存"一条 SQL 的结果集"
     业务不知道它存在，失效策略由框架决定

  ✅ Spring Cache / 手动 Redis：缓存"一个业务对象"
     @Cacheable(key="'user:'+#id")
     业务明确知道缓存了什么、什么时候失效、TTL 多久

生产环境的正确做法

yaml
# 显式关掉，避免有人在某个 Mapper 里偷偷加了 <cache/>
mybatis:
  configuration:
    cache-enabled: false

缓存需求交给 Redis + Spring Cache，并遵循：缓存只放读多写少、能容忍短暂不一致的数据；写操作采用"先更新数据库、再删除缓存"；设置合理 TTL 兜底。

📌 单独澄清：什么情况下二级缓存"可以"用

text
同时满足以下全部条件时，二级缓存是可接受的：
  ✅ 单机部署（或缓存数据只读、永不变更）
  ✅ 数据是字典表 / 配置表这类几乎不写的
  ✅ 查询频率高、结果集小
  ✅ 能容忍最长 flushInterval 的数据延迟

但即便如此，用一个 Caffeine 本地缓存或启动时加载到内存 Map，
都比二级缓存更可控、更好排查。

判断口诀：二级缓存不是"不好用"，是"没有它不可替代的场景"。

6.4 缓存与 Spring 事务的交互 ​

这一节把一级缓存、二级缓存和 Spring 事务放在一起看，解释几个"看起来很诡异"的现象。

Spring 环境下 SqlSession 的生命周期：

text
无事务（没有 @Transactional）：
  Service.method()
    ├─ mapper.selectA()  → 新建 SqlSession → 查库 → 关闭 Session（缓存销毁）
    └─ mapper.selectB()  → 新建 SqlSession → 查库 → 关闭 Session
  → 两次调用之间没有任何缓存共享

有事务（@Transactional）：
  Service.method()  ← 事务开始，SqlSession 绑定到当前线程
    ├─ mapper.selectA()  → 复用 SqlSession → 查库 → 写入一级缓存
    └─ mapper.selectA()  → 复用 SqlSession → 命中一级缓存，不发 SQL
  ← 事务提交，SqlSession 关闭，一级缓存销毁、二级缓存写入
场景一级缓存是否生效
无事务，两次相同查询❌
@Transactional，两次相同查询✅
事务中间夹了一次 update❌（被清空）
两个不同的事务❌
@Transactional(propagation=REQUIRES_NEW) 内层❌（新 Session）

现象一：事务里修改了数据，再查还是旧值？

java
@Transactional
public void bad(Integer empId) {
    Employee e1 = mapper.selectById(empId);      // 发 SQL，进缓存
    jdbcTemplate.update("UPDATE t_emp SET ...");  // ⚠️ 绕过了 MyBatis
    Employee e2 = mapper.selectById(empId);      // 命中一级缓存，拿到旧值 ❌
}

一级缓存只在通过 MyBatis 执行写操作时才会被清空。任何绕过 MyBatis 的更新（JdbcTemplate、原生 JDBC、存储过程、其他服务改库）都不会触发清空。

修法：在 select 上加 flushCache="true"，或显式调用 sqlSession.clearCache()，或把写操作也走 MyBatis。

现象二：读未提交——事务中的二级缓存

text
事务 A：  UPDATE t_emp SET salary = 20000 WHERE id = 1   （未提交）
事务 B：  SELECT * FROM t_emp WHERE id = 1

如果事务 A 的写操作已经清空了二级缓存：
  → 事务 B miss，去数据库查，按隔离级别读到 10000（旧值），然后【写进二级缓存】

事务 A 回滚：
  → 数据库是 10000，二级缓存也是 10000     ✅ 碰巧一致

事务 A 提交：
  → 数据库是 20000，二级缓存还是 10000     ❌ 脏数据，直到下次清空

MyBatis 的 TransactionalCache 只保证"本 Session 的写不污染缓存"，保证不了"其他 Session 并发写时缓存的正确性"。这是 6.3 里"集群脏读"在单机并发下的版本。

现象三：@Transactional(readOnly = true) 与缓存

java
@Transactional(readOnly = true)
public List<Employee> list() { ... }

readOnly = true 的作用是：告诉数据库驱动这是只读事务（MySQL 下可跳过部分 undo log 开销），以及让 Spring 跳过脏检查。它不会关闭一级缓存，也不会改变二级缓存行为。 查询方法加上它的主要收益是让 SqlSession 在方法内复用，顺带让一级缓存生效。

📌 单独澄清：MyBatis 缓存与 Spring Cache 不是一回事

维度MyBatis 一级/二级缓存Spring Cache (@Cacheable)
缓存粒度SQL 结果集方法返回值
作用层次DAO 层（框架内部）任意层，通常 Service 层
存储介质JVM 内存可插拔：Redis / Caffeine / EhCache
失效控制框架自动（粗粒度）业务显式声明 @CacheEvict
事务感知一级随事务，二级有暂存区默认不感知，需要配事务同步
生产推荐度一级可用；二级不推荐✅ 主流方案

判断口诀：缓存"同一个事务里重复查"用一级缓存就够了；缓存"跨请求的热点数据"用 Redis；二级缓存两边都不占。

7.1 插件机制：拦截器到底能拦什么 ​

概念

MyBatis 插件本质是基于 JDK 动态代理的责任链：在创建四大对象时，把它们层层包装成代理对象，方法调用时先走插件逻辑，再调原方法。

只有四个对象可以被拦截，不多不少：

可拦截对象可拦截方法（常用）典型用途
Executorupdate、query、commit、rollback分页、全局拦截、多租户
ParameterHandlersetParameters、getParameterObject参数加密、自动填充
ResultSetHandlerhandleResultSets、handleOutputParameters结果脱敏、解密
StatementHandlerprepare、parameterize、query、update、batchSQL 改写、耗时统计、SQL 审计
text
插件的包装时机（Configuration 里）：
  newExecutor()          →  interceptorChain.pluginAll(executor)
  newParameterHandler()  →  interceptorChain.pluginAll(parameterHandler)
  newResultSetHandler()  →  interceptorChain.pluginAll(resultSetHandler)
  newStatementHandler()  →  interceptorChain.pluginAll(statementHandler)

多个插件的包装顺序：
  配置 A、B、C 三个插件
       ↓ pluginAll 按顺序包装
  C代理( B代理( A代理( 真实对象 ) ) )
       ↓ 执行时
  C.intercept → B.intercept → A.intercept → 真实方法
  （后配置的先执行，像栈一样）

插件的三个要素：

java
@Intercepts({
    @Signature(
        type = StatementHandler.class,   // 拦哪个对象
        method = "query",                 // 拦哪个方法
        args = {Statement.class, ResultHandler.class}  // 方法参数类型（用于重载区分）
    )
})
public class MyPlugin implements Interceptor {

    // 核心逻辑：invocation.proceed() 放行
    @Override
    public Object intercept(Invocation invocation) throws Throwable {
        // 前置处理
        Object result = invocation.proceed();
        // 后置处理
        return result;
    }

    // 决定是否包装；不重写则默认 Plugin.wrap
    @Override
    public Object plugin(Object target) {
        return Plugin.wrap(target, this);
    }

    // 读取配置的属性
    @Override
    public void setProperties(Properties properties) { }
}

args 写错会导致插件静默失效

java
// StatementHandler.query 只有一个签名：query(Statement, ResultHandler)
// ❌ 写错参数类型 → Plugin.wrap 匹配不上 → 不报错，插件就是不生效
args = {Statement.class}

// ✅ 必须和接口方法签名完全一致
args = {Statement.class, ResultHandler.class}

排查方法：在 intercept 方法第一行打日志，启动后发一条 SQL，看日志有没有输出。插件不生效的排查顺序：是否注册 → @Signature 的 type/method/args 是否匹配 → 是否被其他插件短路（没有调用 proceed()）。

📌 单独澄清：拦不到的东西比拦得到的更值得记

text
❌ 拦不到 Mapper 接口方法本身      → 那是 MapperProxy，不在四大对象里
❌ 拦不到动态 SQL 的解析过程       → 解析发生在插件链之外
❌ 拦不到 Connection 的获取        → 那是 DataSource 的事
❌ 拦不到一级缓存命中的查询        → 缓存命中时根本不会走到 StatementHandler

想统计"所有查询"（含缓存命中）→ 拦 Executor
想统计"真正发到数据库的 SQL"    → 拦 StatementHandler

这个区别在做 SQL 耗时统计时很关键：拦 Executor 统计出来的是"方法耗时"，拦 StatementHandler 统计出来的才是"数据库耗时"。

7.2 手写一个 SQL 耗时统计插件 ​

目标：打印每条真实执行的 SQL、参数和耗时，超过阈值标记为慢 SQL。

java
package com.at.plugin;

import org.apache.ibatis.executor.statement.StatementHandler;
import org.apache.ibatis.mapping.BoundSql;
import org.apache.ibatis.mapping.MappedStatement;
import org.apache.ibatis.plugin.*;
import org.apache.ibatis.reflection.MetaObject;
import org.apache.ibatis.reflection.SystemMetaObject;

import java.sql.Statement;
import java.util.Properties;

@Intercepts({
    @Signature(type = StatementHandler.class, method = "query",
               args = {Statement.class, org.apache.ibatis.session.ResultHandler.class}),
    @Signature(type = StatementHandler.class, method = "update",
               args = {Statement.class}),
    @Signature(type = StatementHandler.class, method = "batch",
               args = {Statement.class})
})
public class SqlCostPlugin implements Interceptor {

    /** 慢 SQL 阈值，毫秒 */
    private long threshold = 200L;

    @Override
    public Object intercept(Invocation invocation) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            return invocation.proceed();
        } finally {
            long cost = System.currentTimeMillis() - start;
            try {
                log(invocation, cost);
            } catch (Exception ignore) {
                // 插件自身异常绝不能影响业务
            }
        }
    }

    private void log(Invocation invocation, long cost) {
        StatementHandler handler = (StatementHandler) invocation.getTarget();
        // StatementHandler 可能被其他插件包装过，用 MetaObject 穿透代理取原始属性
        MetaObject meta = SystemMetaObject.forObject(handler);
        while (meta.hasGetter("h")) {
            meta = SystemMetaObject.forObject(meta.getValue("h"));
        }
        MappedStatement ms = (MappedStatement) meta.getValue("delegate.mappedStatement");
        BoundSql boundSql = handler.getBoundSql();

        String sql = boundSql.getSql().replaceAll("\\s+", " ").trim();
        String tag = cost >= threshold ? "[SLOW SQL]" : "[SQL]";
        System.out.printf("%s %s | cost=%dms | %s%n",
                tag, ms.getId(), cost, sql);
    }

    @Override
    public Object plugin(Object target) {
        // 只对 StatementHandler 做代理，减少无谓包装
        return target instanceof StatementHandler ? Plugin.wrap(target, this) : target;
    }

    @Override
    public void setProperties(Properties properties) {
        String v = properties.getProperty("threshold");
        if (v != null) {
            this.threshold = Long.parseLong(v);
        }
    }
}

注册方式（Spring Boot 下最简单的是声明成 Bean）：

    @Bean
    public SqlCostPlugin sqlCostPlugin() {
        SqlCostPlugin plugin = new SqlCostPlugin();
        Properties props = new Properties();
        props.setProperty("threshold", "100");
        plugin.setProperties(props);
        return plugin;
    }
}

写插件的三条纪律

  1. 必须调用 invocation.proceed()，且返回它的结果。忘了调用 = 业务逻辑被吃掉，查询永远返回 null；忘了返回 = 同样的后果。
  2. 插件内部异常必须吞掉或单独处理。 统计、日志这类旁路逻辑抛异常会直接让业务 SQL 失败——用 try-finally 包住，catch 住所有异常。
  3. 不要在插件里做耗时操作。 插件在 SQL 执行路径上，远程调用、同步写文件都会直接拖慢全部数据库操作。要上报就丢队列异步处理。

📌 单独澄清：为什么要用 while (meta.hasGetter("h")) 穿透代理

text
只有你一个插件时：
  StatementHandler 实例就是 RoutingStatementHandler  → 直接取 delegate 即可

装了 PageHelper 等其他插件时：
  Plugin代理( Plugin代理( RoutingStatementHandler ) )
  Plugin 类内部持有被代理对象的字段名就叫 "h"
       ↓
  循环取 "h" 直到取不到，才拿到最里层的真实对象

直接 ((RoutingStatementHandler) handler).getDelegate() 在单插件下能跑通，一旦叠加其他插件就会抛 ClassCastException——这是自研插件上线后最常见的崩溃原因。

7.3 PageHelper 的原理与误用 ​

使用方式：

java
PageHelper.startPage(1, 10);                 // 第 1 页，每页 10 条
List<Employee> list = employeeMapper.selectAll();   // 下一条查询自动分页
PageInfo<Employee> page = new PageInfo<>(list);     // 包装拿总数等信息

原理：ThreadLocal + Executor 拦截器

text
PageHelper.startPage(1, 10)
      ↓
  把 Page 对象存进 ThreadLocal<Page>
      ↓
mapper.selectAll()  →  PageInterceptor 拦截 Executor.query
      ↓
  从 ThreadLocal 取出 Page，不为空则：
      1. 复制一份 MappedStatement，SQL 改写为 SELECT count(0) FROM (原SQL) → 查总数
      2. 按数据库方言给原 SQL 加 LIMIT ? OFFSET ?
      3. 执行、把结果包装成 Page（它是 ArrayList 的子类）
      ↓
  finally 中 ThreadLocal.remove()
关键点说明
存储载体ThreadLocal，所以必须同线程、紧邻调用
生效范围紧跟其后的第一条查询
count 查询自动生成，可用 countSuffix 指定手写 count 方法
方言自动根据 JDBC URL 识别，也可显式配置
返回类型Page extends ArrayList，所以能直接当 List 用

四个高频误用

java
// ❌ 误用 1：startPage 和查询之间插了别的语句
PageHelper.startPage(1, 10);
Integer total = otherMapper.count();      // ⚠️ 分页被这条消费掉了
List<Employee> list = empMapper.selectAll();  // 没分页，全表返回

// ❌ 误用 2：startPage 之后的查询没执行（异常/条件分支跳过）
PageHelper.startPage(1, 10);
if (flag) {
    list = empMapper.selectAll();
}
// flag 为 false → ThreadLocal 没被清理 → 污染同一线程的【下一个请求】
// 现象：某个本不该分页的接口莫名其妙只返回 10 条

// ❌ 误用 3：在异步线程 / 线程池里查询
PageHelper.startPage(1, 10);
CompletableFuture.supplyAsync(() -> empMapper.selectAll());  // 不同线程，ThreadLocal 取不到

// ❌ 误用 4：一对多 collection 映射 + 分页
// LIMIT 作用在 JOIN 后的结果集上，折叠后条数不对（见 4.6）

误用 2 最隐蔽：PageHelper 内部会在查询的 finally 里清理 ThreadLocal，但查询压根没执行时就没人清理。解决办法是用 try-finally 兜底：

java
try {
    PageHelper.startPage(1, 10);
    if (flag) { list = empMapper.selectAll(); }
} finally {
    PageHelper.clearPage();
}

count 查询的性能问题：

text
PageHelper 默认每次分页都会先执行一次 count：
  SELECT count(0) FROM ( 你的原始 SQL ) tmp

原 SQL 是复杂多表 JOIN 时：
  count 查询可能比数据查询还慢（它要跑完整个 JOIN）
  → 一次分页请求 = 两次慢查询

优化手段：

java
// 方案 1：不需要总数时关掉 count
PageHelper.startPage(1, 10, false);

// 方案 2：只要"有没有下一页"，用 count=false + 多查一条判断
PageHelper.startPage(pageNum, pageSize + 1, false);

// 方案 3：手写优化过的 count 方法（命名约定 原方法名 + "_COUNT"）
// selectComplexReport  →  selectComplexReport_COUNT
PageHelper.startPage(1, 10).setCountColumn("emp_id");

📌 单独澄清：PageHelper 的深分页问题它解决不了

sql
-- 第 10000 页：MySQL 要扫描并丢弃 100000 行
SELECT * FROM t_emp ORDER BY emp_id LIMIT 100000, 10;   -- 慢

-- ✅ 游标分页（keyset pagination）：用上一页最后一条的 id 做条件
SELECT * FROM t_emp WHERE emp_id > #{lastId} ORDER BY emp_id LIMIT 10;  -- 快

PageHelper 只是帮你拼 LIMIT，LIMIT 本身的深分页代价还在。 面向 C 端的大数据量列表，应该用游标分页或搜索引擎，而不是无限页码。

7.4 TypeHandler：自定义类型转换 ​

概念

TypeHandler 负责 Java 类型 ↔ JDBC 类型的双向转换：设置参数时把 Java 对象写进 PreparedStatement，读结果时把 ResultSet 的列值转成 Java 对象。MyBatis 内置了几十个（String、Integer、Date、Enum...），缺的自己写。

text
写入：  Java 对象 ──setParameter()──>  PreparedStatement  ──>  数据库
读取：  数据库 ──>  ResultSet  ──getResult()──>  Java 对象

典型场景一：List 与逗号分隔字符串互转

java
package com.at.handler;

import org.apache.ibatis.type.*;
import java.sql.*;
import java.util.*;

@MappedTypes(List.class)                 // 处理的 Java 类型
@MappedJdbcTypes(JdbcType.VARCHAR)       // 对应的 JDBC 类型
public class ListStringTypeHandler extends BaseTypeHandler<List<String>> {

    @Override
    public void setNonNullParameter(PreparedStatement ps, int i,
                                    List<String> parameter, JdbcType jdbcType) throws SQLException {
        ps.setString(i, String.join(",", parameter));
    }

    @Override
    public List<String> getNullableResult(ResultSet rs, String columnName) throws SQLException {
        return split(rs.getString(columnName));
    }

    @Override
    public List<String> getNullableResult(ResultSet rs, int columnIndex) throws SQLException {
        return split(rs.getString(columnIndex));
    }

    @Override
    public List<String> getNullableResult(CallableStatement cs, int columnIndex) throws SQLException {
        return split(cs.getString(columnIndex));
    }

    private List<String> split(String value) {
        if (value == null || value.isEmpty()) {
            return new ArrayList<>();
        }
        return new ArrayList<>(Arrays.asList(value.split(",")));
    }
}

典型场景二：敏感字段自动加解密

7.5 Executor 三种类型与批量操作 ​

Executor 类型行为适用场景
SIMPLE（默认）每次执行都创建新的 PreparedStatement常规 CRUD
REUSE按 SQL 文本缓存 PreparedStatement 并复用同一 SQL 反复执行
BATCH把 update 攒起来，flushStatements() 时批量发大批量写入
text
SIMPLE：
  insert → prepare → execute → close
  insert → prepare → execute → close     ← 每条都有一次完整往返
  × 10000 次 = 10000 次网络往返

BATCH：
  insert → addBatch
  insert → addBatch
  ...（攒在客户端）
  flushStatements() → executeBatch()     ← 一次网络往返发送全部

Spring Boot 里使用 BATCH 模式：

java
@Service
public class EmployeeBatchService {

    @Autowired
    private SqlSessionFactory sqlSessionFactory;

    public void batchInsert(List<Employee> list) {
        // 第二个参数 false：关闭自动提交
        try (SqlSession session = sqlSessionFactory.openSession(ExecutorType.BATCH, false)) {
            EmployeeMapper mapper = session.getMapper(EmployeeMapper.class);
            int i = 0;
            for (Employee e : list) {
                mapper.insert(e);
                // 每 1000 条 flush 一次，避免攒太多撑爆内存
                if (++i % 1000 == 0) {
                    session.flushStatements();
                }
            }
            session.commit();
        }
    }
}
yaml

三种批量写入方式的对比（插入 10 万条的量级参考）：

方式SQL 形态耗时量级主键回填备注
for 循环单条 insert10 万条 INSERT分钟级✅最慢，禁止
<foreach> 拼 VALUES若干条超长 INSERT秒级有条件需分批，注意包大小
ExecutorType.BATCH10 万条 INSERT，一次发送秒级❌ 不可靠需 rewriteBatchedStatements=true
text
JDBC URL 必须加这个参数，BATCH 才能真正合并：
  jdbc:mysql://localhost:3306/db_mybatis?rewriteBatchedStatements=true

不加的话：MySQL 驱动仍然逐条发送，BATCH 模式几乎没有提速

BATCH 模式的四个行为差异

  1. update / delete 的返回值不可信。 BATCH 下方法立即返回 -2147482646（Statement.SUCCESS_NO_INFO），真正的影响行数要等 flushStatements() 才知道。任何基于"影响行数判断是否更新成功"的乐观锁逻辑在 BATCH 下都会失效。
  2. 同一个 Session 里穿插查询会强制 flush。 BATCH Executor 执行 query 前会先把攒着的写操作发出去，所以"插入后立刻查询验证"不会报错，但批量优势被打断。
  3. 不能和 Spring 的 @Transactional 简单混用。 SqlSessionTemplate 持有的是默认 ExecutorType，自己 openSession(BATCH) 开出来的 Session 不在 Spring 事务里，需要手动 commit / rollback，或者配置一个专门的 SqlSessionTemplate Bean。
  4. 异常定位困难。 批量执行失败时抛 BatchUpdateException，只知道哪一批失败，定位到具体某条需要靠 getUpdateCounts() 逐个比对。

📌 单独澄清：REUSE 不是"连接复用"

text
REUSE 复用的是 PreparedStatement 对象，缓存在 Executor 内部的 Map 里
     key = SQL 文本，Session 关闭时清空

它不复用：Connection（那是连接池的事）
         执行计划（那是数据库的事）

收益场景：同一个 Session 内反复执行【同一条 SQL】但参数不同
         且该 SQL 文本完全一致（动态 SQL 拼出不同文本就复用不了）

绝大多数业务下 REUSE 的收益微乎其微，默认的 SIMPLE 加上连接池就够了，不要为了"听起来更快"去改它。

流式查询（导出百万行数据时的标准写法）：

java
@Select("SELECT emp_id, emp_name FROM t_emp")
@Options(resultSetType = ResultSetType.FORWARD_ONLY, fetchSize = Integer.MIN_VALUE)
Cursor<Employee> scanAll();

8.4 面试高频问答 ​

Q1：MyBatis 和 Hibernate 的区别？为什么国内更流行 MyBatis？

A：核心差异是对 SQL 的控制权归谁。Hibernate 是全自动 ORM，SQL 由框架根据对象模型生成，开发者通过 HQL/Criteria 间接表达；MyBatis 是半自动，SQL 完全手写，框架只负责参数绑定与结果映射。

国内流行 MyBatis 的原因：互联网业务数据量大、对 SQL 和索引的精细控制要求高；团队里 DBA 和开发需要对同一条 SQL 达成共识；复杂报表类查询用 HQL 表达困难。代价是开发者要自己写所有 SQL，跨数据库移植性差。

Q2：#{} 和 ${} 的区别？

A：#{} 编译为 ? 占位符，走 PreparedStatement 预编译，参数作为值传入，能防 SQL 注入且字符串会自动加引号；${} 是字符串直接替换，拼进 SQL 文本本身。

但更关键的是"能力边界"：表名、列名、ORDER BY 的排序字段这些属于 SQL 结构的部分，预编译占位符无法表达，只能用 ${}。所以不是"永远不用 ${}"，而是"用 ${} 的地方必须做白名单校验"。

Q3：Mapper 接口没有实现类，方法是怎么被调用的？

A：MapperProxyFactory 用 JDK 动态代理生成代理对象（MapperProxy）。调用接口方法时进入 MapperProxy.invoke，它把"接口全限定名 + 方法名"拼成 statementId，在 Configuration 里找到对应的 MappedStatement，再交给 SqlSession 执行。因为 statementId 是"类名.方法名"，所以 Mapper 接口不支持方法重载。

Q4：一级缓存和二级缓存的区别？生产环境怎么用？

A：一级缓存是 SqlSession 级，默认开启，不可真正关闭，存在 BaseExecutor 的 localCache 里；二级缓存是 namespace 级，跨 Session 共享，需要显式配置 <cache/> 且 Session 提交后才生效。

生产实践：一级缓存保持默认即可（Spring 下只在 @Transactional 范围内生效）；二级缓存建议显式关闭——集群下必然脏读、namespace 隔离导致关联数据失效不同步、清空粒度是整个 namespace 导致命中率低、缺少查看和手动清除的运维手段。缓存需求交给 Redis + Spring Cache。

Q5：resultType 和 resultMap 什么时候必须用后者？

A：列名与属性名无法通过"驼峰映射 + 列别名"对上时；需要 association / collection 做嵌套对象或集合映射时；需要延迟加载或字段级 TypeHandler 时。另外 resultMap 里主键必须用 <id>，它承担嵌套映射的行去重职责。

Q6：MyBatis 的插件能拦截什么？实现原理？

A：只能拦截 Executor、ParameterHandler、ResultSetHandler、StatementHandler 四个对象。原理是 Configuration 创建这四个对象时调用 interceptorChain.pluginAll()，用 JDK 动态代理层层包装，形成责任链。多个插件时后配置的先执行。注意拦不到 Mapper 接口方法本身，也拦不到一级缓存命中的查询。

Q7：什么是 N+1 问题？怎么解决？

A：分步查询（嵌套查询）时，主查询返回 N 条记录，每条记录的关联属性各触发一次子查询，总共 1+N 条 SQL。解决方式是"把 N 次合并成 1 次"：关联数据量可控时用 JOIN 一次查完；更通用的做法是批量查关联表再在内存里按 Map 组装。延迟加载不是解药——它只是推迟了这 N 次查询，序列化返回给前端时还是会全部触发。

Q8：<where> 和 1=1 哪个好？<trim> 的作用？

A：<where> 更规范：内容为空时整个 WHERE 都不输出，有内容时自动去掉开头的 AND/OR。但要注意它只处理开头不处理结尾，所以 AND 必须写在条件前面。<trim> 是它们的通用底层实现，四个属性 prefix/suffix/prefixOverrides/suffixOverrides 可以组合出任意前后缀处理，比如动态列名的 INSERT。

Q9：MyBatis 怎么做批量插入？各方案的取舍？

A：三种方案。for 循环单条 insert 最慢，禁止使用；<foreach> 拼 VALUES 速度快但 SQL 文本很长，需要分批（500~1000）且注意 max_allowed_packet；ExecutorType.BATCH 攒批后一次发送，需要 JDBC URL 加 rewriteBatchedStatements=true 才真正生效，但影响行数返回不可信、主键回填不可靠。常规场景优先 <foreach> 分批。

Q10：说说一条 SQL 在 MyBatis 里的完整执行流程。

text
mapper.selectById(1)
  → MapperProxy.invoke          拼 statementId
  → SqlSession.selectOne
  → CachingExecutor             查二级缓存
  → BaseExecutor                查一级缓存
  → StatementHandler.prepare    创建 PreparedStatement
  → ParameterHandler            设置参数（TypeHandler 做 Java→JDBC 转换）
  → Statement.execute           发送到数据库
  → ResultSetHandler            按 resultMap/resultType 映射（TypeHandler 做 JDBC→Java）
  → 写入一级缓存 → 返回

8.5 面试补充：执行流程、延迟加载与缓存实战 ​

Q11：MyBatis 的执行流程是怎样的？

  1. 读取 MyBatis 配置文件 mybatis-config.xml，加载运行环境和映射文件。
  2. 构造会话工厂 SqlSessionFactory，一个项目只需要一个，是单例的，一般由 Spring 管理。
  3. 会话工厂创建 SqlSession 对象，这里面包含了执行 SQL 语句的所有方法。
  4. 操作数据库靠 Executor 执行器，它同时负责查询缓存的维护。
  5. Executor 接口的执行方法中有一个 MappedStatement 类型的参数，封装了映射信息。
  6. 输入参数映射。
  7. 输出结果映射。

Q12：MyBatis 是否支持延迟加载？

支持。延迟加载的意思是：需要用到数据时才进行加载，不需要用到时就不加载数据。

MyBatis 支持一对一关联对象（association）和一对多关联集合对象（collection）的延迟加载。在配置文件中通过 lazyLoadingEnabled=true|false 控制是否启用，默认是关闭的。

Q13：延迟加载的底层原理是什么？

  1. 使用 CGLIB 为目标对象创建代理对象。
  2. 当调用目标方法 user.getOrderList() 时，会先进入代理对象的 invoke 拦截方法，发现 orderList 属性是 null，于是执行 SQL 查询订单列表。
  3. 把订单数据查询上来后，调用 user.setOrderList(List<Order> orderList) 完成属性填充，再继续执行 user.getOrderList()，此时就能拿到数据了。

Q14：MyBatis 的一级缓存用过吗？

用过。一级缓存是 SqlSession 级别的，底层就是 PerpetualCache，本质是一个 HashMap，而且默认开启，不需要任何配置。

同一个 SqlSession 中，执行相同的 SQL（相同的 statementId、参数、分页条件），第二次就会直接从缓存里拿，不再发出 SQL：

java
SqlSession sqlSession = sqlSessionFactory.openSession();
UserMapper mapper = sqlSession.getMapper(UserMapper.class);

User u1 = mapper.selectById(1L); // 走数据库，发出 SQL
User u2 = mapper.selectById(1L); // 命中一级缓存，不发 SQL
System.out.println(u1 == u2);    // true

sqlSession.commit();             // 或 clearCache()，缓存被清空
User u3 = mapper.selectById(1L); // 缓存已清空，重新发出 SQL

失效时机有三个：

  1. SqlSession 执行了 commit / close；
  2. 同一个 SqlSession 中执行了增删改操作；
  3. 手动调用 sqlSession.clearCache()。

注意：一级缓存跨 SqlSession 不共享，两个会话查同一条数据还是各发一次 SQL。另外在 Spring 环境下，如果没有开启事务，每次 Mapper 调用都是一个新的 SqlSession，一级缓存基本是失效的。

Q15：MyBatis 的二级缓存用过吗？

用过。二级缓存是 Namespace（Mapper）级别的，多个 SqlSession 可以共享，底层同样是 PerpetualCache，但默认关闭，需要手动配置。

第一步，全局配置文件开启总开关（默认即为 true，一般无需改动）：

xml
<settings>
    <setting name="cacheEnabled" value="true"/>
</settings>

第二步，在具体的 Mapper 映射文件中声明 <cache> 标签：

xml
<mapper namespace="com.example.mapper.UserMapper">
    <!-- eviction：回收策略，LRU 最近最少使用
         flushInterval：刷新间隔，单位毫秒
         size：最多缓存多少个对象
         readOnly：true 返回缓存对象本身(快但不安全)，false 返回反序列化副本 -->
    <cache eviction="LRU" flushInterval="60000" size="512" readOnly="true"/>
</mapper>

如果用注解方式，则在 Mapper 接口上加 @CacheNamespace：

java
@CacheNamespace(eviction = LruCache.class, flushInterval = 60000, size = 512)
public interface UserMapper {
    User selectById(Long id);
}

注意两点：

  1. 二级缓存的实体类必须实现 Serializable，否则序列化时会报错。
  2. 二级缓存在 SqlSession commit 或 close 之后才真正写入，所以同一个会话里不关闭是命中不了的。
java
public class User implements Serializable {
    private Long id;
    private String name;
    // getter / setter 略
}
java
SqlSession session1 = factory.openSession();
User u1 = session1.getMapper(UserMapper.class).selectById(1L); // 发出 SQL
session1.close();  // 关闭后，数据才真正写入二级缓存

SqlSession session2 = factory.openSession();
User u2 = session2.getMapper(UserMapper.class).selectById(1L); // 命中二级缓存，不发 SQL
session2.close();

Q16：二级缓存什么时候会清理缓存中的数据？

只要在对应作用域（一级缓存是 SqlSession，二级缓存是 Namespace）内执行了增、删、改操作，默认就会清空该作用域下所有 select 的缓存，目的是保证不会读到脏数据。

原因在于增删改标签的 flushCache 属性默认为 true，而 select 标签的 flushCache 默认为 false、useCache 默认为 true：

xml
<!-- 查询：默认使用缓存，且不清空缓存 -->
<select id="selectById" resultType="User" useCache="true" flushCache="false">
    select * from user where id = #{id}
</select>

<!-- 增删改：默认 flushCache="true"，执行后清空该 namespace 的缓存 -->
<update id="updateUser" flushCache="true">
    update user set name = #{name} where id = #{id}
</update>

也可以手动干预：

  • 某条查询不想走缓存：<select ... useCache="false">。
  • 某条查询执行后就清缓存：<select ... flushCache="true">。
  • 代码里手动清一级缓存：sqlSession.clearCache()。

另外，<cache> 标签上配置的 flushInterval（定时刷新）到期，以及缓存条数超过 size 触发回收策略时，也会导致缓存数据被清理。

需要注意：二级缓存是 namespace 级别的，如果多个 Mapper 操作同一张表，A 的更新不会清掉 B 的缓存，就会出现脏读。所以实际项目中一般不用 MyBatis 二级缓存，而是用 Redis 做缓存。
