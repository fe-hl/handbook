一、概述篇 ​

1.1 MVCC 是什么 ​

INFO

MVCC（Multi-Version Concurrency Control，多版本并发控制）：给普通 select 实现无锁快照读，让读写互不阻塞；底层依靠 版本链 + ReadView 控制一条数据对当前事务是否可见。

一句话总结：

同一行数据在不同时刻存在多个历史版本，每个事务按自己的"快照时刻"去版本链上挑一个它该看见的版本。

这样带来的直接收益：

  • 普通查询不用等锁，写操作也不用等查询
  • 同一个事务内多次查询结果稳定（RR 隔离级别下）
  • 代价是需要保留历史版本（undo log），长事务会拖慢版本清理

1.2 适用范围与前置条件 ​

维度说明
存储引擎仅 InnoDB 支持，MyISAM 没有 MVCC（也没有事务）
隔离级别主要服务 RC（读已提交）与 RR（可重复读）
读类型只对 快照读 生效，当前读不走 MVCC
依赖结构行隐藏字段（trx_id、roll_ptr）+ undo log + ReadView

WARNING

注意：Serializable 隔离级别下普通 select 也会被转成加锁读，此时不再依赖 MVCC；Read Uncommitted 直接读最新版本，也用不上 ReadView。

二、两种读篇 ​

INFO

学习 MVCC 的第一道门槛：先把「快照读」和「当前读」分清楚，后面所有结论都建立在这个区分之上。

2.1 快照读 ​

INFO

快照读：普通 select 语句，不加任何锁，走 MVCC 读历史快照版本。

sql
-- 快照读：默认的普通查询
select * from t where id = 1;

特征：

  • 不加任何锁（既不加 S 锁，也不加 X 锁）
  • 走 MVCC，读的是某个时刻的快照版本，不一定是数据库最新数据
  • 其他事务可以正常对这一行增删改，互不阻塞

2.2 当前读 ​

INFO

当前读：读取磁盘上的最新版本，并且会加锁，不走快照。

sql
-- 当前读：手动加共享 S 锁
select * from t where id = 1 lock in share mode;

-- 当前读：手动加排他 X 锁
select * from t where id = 1 for update;

-- DML 天然是当前读，自动加排他 X 锁
insert into t values (...);
update t set name = 'a' where id = 1;
delete from t where id = 1;

特征：

  • 读取的是最新已提交版本，不受旧快照约束
  • 会加锁，阻止其他事务修改该行或申请冲突锁
  • 但不会阻塞其他事务的普通快照 select

WARNING

常见误解：锁不是自动加的

普通 select 默认不带任何锁。for update / lock in share mode 是我们主动要求上锁；insert / update / delete 则由引擎自动加排他锁。不要以为"查询也会锁表"。

2.3 快照读与当前读对比 ​

维度快照读（普通 select）当前读（for update / DML）
加锁不加锁加 S 锁或 X 锁
读取版本版本链上对自己可见的旧版本磁盘上的最新已提交版本
是否走 MVCC是否
并发表现读写互不阻塞与其他锁请求互斥，可能等待
典型场景列表查询、报表统计扣库存、转账、唯一性校验后写入

三、版本链篇 ​

INFO

版本链：MVCC 能读到"旧数据"，靠的就是 undo log 把一条记录的历史版本用指针串成链表。

3.1 行记录的隐藏字段 ​

聚簇索引的每一行，除了业务字段外，还自带隐藏列：

隐藏字段作用说明
DB_TRX_ID最近一次修改这条记录的事务 ID；只有 insert / update / delete 会更新，select 不会更新
DB_ROLL_PTR回滚指针，指向 undo log 中这条记录的上一个版本
DB_ROW_ID没有主键且无唯一非空索引时，InnoDB 自动生成的隐藏行 ID（与 MVCC 无关）

3.2 undo log 与版本链 ​

修改数据不会直接覆盖旧数据：旧版本信息会被写入 undo log，再通过 roll_ptr 串成一条链表。

text
聚簇索引上的最新行                 undo log 中的历史版本
┌────────────────────┐          ┌────────────────────┐          ┌────────────────────┐
│ name = 'C'         │          │ name = 'B'         │          │ name = 'A'         │
│ DB_TRX_ID   = 101  │  ─────►  │ DB_TRX_ID   = 100  │  ─────►  │ DB_TRX_ID   = 99   │
│ DB_ROLL_PTR ───────┼──────────┤ DB_ROLL_PTR ───────┼──────────┤ DB_ROLL_PTR = null │
└────────────────────┘          └────────────────────┘          └────────────────────┘
        最新版本                        较旧版本                         最早版本

关键补充：

  • undo log 有两个作用：事务回滚 和 为 MVCC 提供历史版本
  • undo 不一定保存完整的旧行副本，而是保存"恢复旧版本所需的信息"
  • 读取时如果当前版本不可见，就顺着 roll_ptr 向下找，直到找到第一个可见版本

3.3 删除标记与 purge ​

  • delete 不是立即物理删除，只是给记录打上删除标记（delete mark），行仍留在版本链上
  • purge 后台线程：当没有任何活跃事务还需要某个旧版本时，才真正清理 undo 记录、释放空间

DANGER

长事务的隐患

长时间不提交的事务会持有老的 ReadView（老快照），导致它可能用到的历史版本都不能被 purge 清理，表现为：

  • undo 表空间持续膨胀，磁盘被吃满
  • 版本链越来越长，快照读要回溯更多版本，查询变慢

排查方式：select * from information_schema.innodb_trx order by trx_started; 找出最早开始、仍未结束的事务。

四、ReadView 篇 ​

INFO

ReadView（读视图）：快照读时生成的一张"活跃事务快照表"，用来判断版本链上的某个版本当前事务能不能看见。

4.1 ReadView 的四个字段 ​

字段含义
m_ids创建 ReadView 时，活跃（已开启未提交）事务 ID 集合
min_trx_idm_ids 中的最小事务 ID（下边界）
max_trx_id创建 ReadView 时，下一个将要分配的事务 ID（上边界）
creator_trx_id创建这个 ReadView 的事务自己的 ID

TIP

边界说明：max_trx_id 不是 m_ids 里的最大值，而是"下一个待分配的事务 ID"；当 m_ids 为空时，min_trx_id 等于 max_trx_id。

4.2 两类可见情况 ​

很多人只记住"比 min 小才可见"，这是不完整的。实际上有两类不同的可见情况：

  1. 版本的事务 ID 小于 min_trx_id：一定可见，修改它的事务在"拍照"前就提交完了
  2. 版本的事务 ID 在 min（含）到 max（不含）之间，且不在 m_ids 中：也可见，虽然 ID 落在区间内，但拍照那一刻它已经提交了

拿同一个 ReadView 举例：m_ids = [102, 104, 105]，min_trx_id = 102，max_trx_id = 106。

  • trx_id = 101：比 min = 102 小 → 可见
  • trx_id = 103：在 102（含）~ 106（不含）区间内，但不在 m_ids 中 → 也可见

4.3 区间含义详解 ​

min_trx_id（含）到 max_trx_id（不含）这个区间，表示从拍照时最小的活跃事务 ID，到下一个待分配事务 ID 之前的范围，并不代表里面的事务都还活跃。

先排除"自己事务"的特殊情况，这个区间里有两种事务：

情况是否在 m_ids可见性
拍照时还活着、没提交在看不见
拍照前已经提交结束不在看得见

为什么会出现 103 这种情况？

事务 ID 是递增分配的。假设依次分配了 102、103、104、105：

  • 103 拿到事务 ID 之后，在拍照之前就提交了
  • 拍照瞬间，活跃的只剩 102、104、105，所以 m_ids 里没有 103
  • 但 103 的 ID 仍然落在 min ~ max 之间，所以必须单独判断它在不在 m_ids

WARNING

注意：事务开启不一定立即分配事务 ID（只读事务可能不分配）。这里说的是获得事务 ID 的顺序，而不是简单的 begin 顺序。

4.4 可见性判断顺序 ​

拿到某个版本的 trx_id 后，按以下顺序判断：

  1. trx_id == creator_trx_id → 自己事务修改的数据，自己一定看得见，优先判断
  2. trx_id < min_trx_id → 修改它的事务早已提交，可见
  3. trx_id >= max_trx_id → 该事务 ID 是快照生成之后才分配的，不可见
  4. min_trx_id <= trx_id < max_trx_id → 查 m_ids 名单：
    • 在 m_ids 中 → 拍照时活跃未提交，不可见
    • 不在 m_ids 中 → 拍照前已提交，可见

4.5 可见与不可见规则汇总 ​

满足下面任意一条，就是可见：

  1. trx_id == creator_trx_id（自己改的）
  2. trx_id < min_trx_id
  3. min_trx_id <= trx_id < max_trx_id 且 不在 m_ids 中

先排除自己事务的版本，再满足下面任意一条，就是不可见：

  1. trx_id >= max_trx_id
  2. min_trx_id <= trx_id < max_trx_id 且 在 m_ids 中

仍使用 m_ids = [102, 104, 105]，min = 102，max = 106，假设下列版本都不是当前事务自己修改的：

trx_id判断条件是否可见
101比 min 小可见
102在区间 + 在 m_ids不可见
103在区间 + 不在 m_ids可见
104在区间 + 在 m_ids不可见
105在区间 + 在 m_ids不可见
106大于等于 max不可见

TIP

口诀

自己改的，一定看得见，优先判断； 比最小还小 → 看得见； 大于等于最大 → 看不见； 中间区间看名单（m_ids）：不在名单看得见，在名单看不见。

4.6 版本链回溯 ​

如果当前版本不可见，就顺着 roll_ptr 找上一个 undo 版本，循环执行同样的判断，直到找到第一个可见版本；若整条链都不可见，则这条记录对本次快照查询"不存在"。

text
最新版本 trx_id=105  → 不可见（在 m_ids）
   │ roll_ptr
   ▼
旧版本  trx_id=103  → 可见（在区间但不在 m_ids）→ 返回这个版本

五、隔离级别篇 ​

INFO

核心结论：RC 和 RR 用的是同一套 MVCC 机制，差别只在 ReadView 的创建时机。

5.1 RC 与 RR 的本质区别 ​

隔离级别ReadView 创建时机表现
RC（读已提交）每一次快照 select 都新建 ReadView能读到别的事务刚提交的数据 → 不可重复读
RR（可重复读，默认）事务内第一次快照 select 生成，后续复用快照固定，多次查询结果一致 → 解决不可重复读
sql
-- 会话 A（RR 隔离级别）
begin;
select * from account where id = 1;   -- 第一次快照读，生成 ReadView，balance = 100

-- 会话 B
begin;
update account set balance = 80 where id = 1;
commit;                               -- 已提交

-- 会话 A 继续
select * from account where id = 1;   -- 复用旧 ReadView，仍然读到 100
select * from account where id = 1 for update;  -- 当前读，读到最新的 80
commit;

TIP

为什么 RC 会不可重复读

因为每条快照 select 都重新"拍照"，别人在两次查询之间提交的修改自然就被拍进来了。RR 只拍一次照，后面都看这张照片。

5.2 ReadView 复用只对快照读生效 ​

WARNING

重要限制

RR 下"复用 ReadView"的规则只对快照读生效。当前读（for update、lock in share mode、update、delete）不受旧快照约束，每次都读最新数据并加锁。

这正是上面示例中同一个事务里 select 读到 100、select ... for update 读到 80 的原因。

另外要注意一个经典场景：RR 下如果事务内先执行了当前读（如 update），后续快照读可能看到自己修改后的结果，因为自己的修改对自己永远可见（trx_id == creator_trx_id）。

六、幻读篇 ​

6.1 什么是幻读 ​

INFO

幻读：同一个事务内，使用相同的查询条件，后一次查询读到了之前不存在的新行。

幻读和不可重复读的区别：

问题关注点典型表现
不可重复读同一行的内容变了第一次读 100，第二次读 80
幻读行数变了第一次读 3 条，第二次读到 4 条

6.2 InnoDB 如何解决幻读 ​

  1. 快照读：没有幻读。快照是某个瞬间的固定视图，后续新插入的数据不在快照里，自然读不到
  2. 当前读：单纯靠 MVCC 解决不了幻读。当前读总是读最新数据，别的事务插入并提交后就能被读到
  3. InnoDB 在 RR 下的完整方案：MVCC（负责快照读） + Next-Key Lock 临键锁（负责当前读，锁住区间禁止插入新记录） 一起解决幻读
sql
-- RR 下的当前读会加临键锁，锁住 (10, 20] 这样的区间
select * from t where id > 10 and id <= 20 for update;
-- 此时其他事务向该区间 insert 会被阻塞，从而避免幻读

DANGER

不要只背一半

"RR 解决了幻读"这句话必须补完整：快照读靠 MVCC，当前读靠间隙锁 / 临键锁。只说 MVCC 解决幻读是错的。

七、执行流程篇 ​

7.1 快照读执行流程 ​

text
1. 执行普通 select
2. 生成 / 复用 ReadView
   ├─ RC：每次 select 都新建 ReadView
   └─ RR：事务内第一次快照 select 生成，之后复用
3. 读取聚簇索引上的最新行，取出 DB_TRX_ID
4. 用 DB_TRX_ID 与 ReadView 做可见性判断
   ├─ 可见   → 直接返回该版本
   └─ 不可见 → 顺着 DB_ROLL_PTR 去 undo 找旧版本，回到第 4 步
5. 返回第一个满足可见性的版本；整条链都不可见则该行不返回

7.2 当前读执行流程 ​

text
1. 加锁
   ├─ lock in share mode → S 锁
   └─ for update / update / delete / insert → X 锁
   （RR 下还可能加间隙锁、临键锁）
2. 读取磁盘上的最新版本，不走快照、不看 ReadView
3. 若发生修改：
   ├─ 把旧数据写入 undo log
   └─ 更新新版本的 DB_TRX_ID、DB_ROLL_PTR
4. commit 时释放锁；旧的 undo 版本交给 purge 线程后续清理

TIP

两条流程的交汇点

当前读产生的新版本，会成为后续快照读版本链的"最新节点"；而快照读是否能看到它，取决于读方 ReadView 的四个字段。

八、误区与面试篇 ​

8.1 五个高频误区 ​

DANGER

MVCC 五个高频误区

  1. MVCC 不是隔离级别，它是 InnoDB 实现 RC、RR 隔离级别的底层机制
  2. 普通 select 默认不加锁；锁需要手动写 for update / lock in share mode，DML 才自动加锁
  3. undo log 不只用来回滚，它同时为 MVCC 存放历史版本
  4. RR 下只有快照读复用 ReadView，当前读不受快照约束
  5. MVCC 搞不定当前读的幻读，必须靠临键锁配合

8.2 主回答：MVCC 是什么，如何实现 ​

MVCC 是多版本并发控制。在 MySQL InnoDB 中，它主要用于实现 RC 和 RR 隔离级别下的一致性快照读，让普通查询与数据修改通常不会因为行锁而相互阻塞，从而提高并发性能。

它的核心是版本链和 ReadView。

一条记录被修改时，InnoDB 会把恢复旧版本所需的信息记录到 undo log 中。记录上有两个核心隐藏字段：DB_TRX_ID 表示最近修改这条记录的事务 ID；DB_ROLL_PTR 是回滚指针，指向对应的 undo 记录。通过回滚指针和 undo 信息，就可以沿版本链还原历史版本。

普通快照查询时，InnoDB 根据 ReadView 判断数据版本是否可见。如果最新版本不可见，比如是其他事务尚未提交的修改，就沿版本链寻找更早的可见版本。

RC 和 RR 的主要区别是 ReadView 的创建时机：RC 每次快照读都创建新的 ReadView，因此可能出现不可重复读；RR 通常在事务第一次快照读时创建 ReadView，后续快照读复用，因此能够保持快照一致性。事务自己的修改对自己始终可见。

MVCC 主要服务于快照读。加锁查询以及更新、删除等操作属于当前读，不受旧快照约束，并通过锁保护相关记录，遇到冲突锁就可能等待。在 RR 下，连续快照读通过复用同一个 ReadView，避免看到其他事务后来插入的数据；对于当前读，则主要通过间隙锁、临键锁防止其他事务在被保护范围内插入新的匹配记录。

TIP

答题节奏：讲到这里即可停下，等待面试官追问，不必一口气背完所有可见性规则。

8.3 追问：ReadView 如何判断可见性 ​

ReadView 主要包含四类信息：创建者事务 ID；创建时活跃的读写事务 ID 集合；下边界（活跃集合中的最小事务 ID，集合为空时等于上边界）；上边界（创建 ReadView 时下一个待分配的事务 ID）。

判断时，先看是不是自己事务修改的版本，自己的修改可见。

对于其他事务产生的版本：

  1. 事务 ID 小于下边界：说明在快照建立前已经提交，可见
  2. 事务 ID 大于等于上边界：说明事务 ID 在快照建立后才分配，不可见
  3. 事务 ID 落在两者之间：检查活跃事务集合。在集合里说明快照建立时还没提交，不可见；不在集合里说明快照建立时已经提交，可见

如果当前版本不可见，就沿版本链继续寻找旧版本，直到找到可见版本；如果不存在可见版本，则该记录对本次快照查询不可见。

TIP

口诀：自己可见、小的可见、大的不可见、中间查活跃名单。

8.4 追问：为什么更新时普通查询仍可执行 ​

更新会对相关记录加排他 X 锁，通常持有到事务提交或回滚。其他事务如果要修改同一条记录，或者执行加锁查询，会因为锁冲突而等待。

但普通快照查询通常不申请记录的 S/X 锁，而是通过 MVCC 读取可见版本，所以不会因为这条记录上的 X 锁而等待。

举个例子，某行余额原来是 100，事务 A 将它改成 80 但尚未提交：

操作方结果
事务 B 普通快照查询沿版本链读到可见的旧版本 100
事务 B 修改同一行 / 加锁查询需要等待事务 A 释放冲突锁
事务 A 自己查询看到自己修改后的 80

INFO

结论：排他锁不是禁止所有查询，而是阻止其他事务获取冲突锁。

8.5 追问：undo log 有什么作用 ​

undo log 主要有两个作用：一是支持事务回滚，撤销尚未提交的修改；二是支持 MVCC，根据 undo 信息还原历史版本供快照读使用。

undo 不一定保存完整的旧行副本，而是保存恢复旧版本所需的信息。

不再需要的历史版本会由 purge 机制清理。如果长事务长期持有老 ReadView，就可能阻碍清理，导致历史版本积累、undo 空间增长。
