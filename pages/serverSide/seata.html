一、认知与定位篇 ​

1.1 分布式事务到底在解决什么问题 ​

概念

分布式事务：一次业务操作需要修改多个独立的数据库连接（通常分布在不同服务、不同机器上），要求这些修改"要么全成功，要么全失败"。

关键词不是"多个服务"，而是多个独立的事务资源。同一个服务里连两个库，也是分布式事务。

单体应用里，一个 @Transactional 就能搞定，因为所有 SQL 跑在同一个数据库连接上，数据库自己保证了 ACID：

java
@Transactional(rollbackFor = Exception.class)
public void createOrder() {
    orderMapper.insert(order);     // 连接 A
    stockMapper.decrease(id, 1);   // 还是连接 A
    accountMapper.decrease(uid, m);// 还是连接 A
    // 任何一步抛异常 → 数据库 ROLLBACK，三条全回退
}

微服务拆分后，这三步落到三个服务、三个库：

text
order-service   →  order_db     （连接 A，自己提交）
stock-service   →  stock_db     （连接 B，自己提交）
account-service →  account_db   （连接 C，自己提交）

问题：B 已提交，C 失败了
      A、B 的数据回不去 → 库存扣了、钱没扣 → 超卖

📌 单独澄清：@Transactional 为什么失效？

它根本没"失效"，它一直工作得很好——只是它的管辖范围只有本地那一个连接。stock-service 内部的本地事务确实回滚了它自己的 SQL，但它管不到已经提交的 order_db。

判断口诀

一个连接 → 本地事务（@Transactional）就够。

多个连接 → 需要一个"上帝视角"的协调者，这就是 Seata。

1.2 Seata 是什么：它不是数据库也不是中间件代理 ​

概念

Seata（Simple Extensible Autonomous Transaction Architecture）是一个分布式事务协调框架，由一个独立部署的 Seata Server（TC） 加上嵌入业务应用的 Client SDK 组成。

它的工作方式是：记录"谁参与了这次全局事务"，在最后统一通知所有参与者提交或回滚。

很多人第一次接触 Seata 会有三个误解，先一次性澄清：

误解真相
Seata 是一个数据库中间件，SQL 要经过它❌ 业务 SQL 仍直连自己的数据库，Seata 只是在本地多插了一条 undo_log
装了 Seata 就有强一致性❌ AT 模式是最终一致，中间存在短暂不一致窗口
Seata 能自动让所有代码变事务安全❌ 它只管数据库写操作，发出去的短信、调用的第三方 API 它回滚不了

📌 单独澄清：Seata Server 存的是什么？

它不存业务数据，只存事务元数据：全局事务 ID、分支事务列表、每个分支的状态、全局锁。真正的回滚数据（undo_log）存在业务库自己里。

text
┌──────────────────────────────────────────────┐
│             Seata Server (TC)                │
│   global_table   : XID、状态、超时时间        │
│   branch_table   : 分支 ID、资源 ID、状态     │
│   lock_table     : 全局锁（表名 + 主键）      │
└──────────────────────────────────────────────┘
          ▲ 注册/上报            ▼ 提交/回滚指令
┌─────────────────┐  ┌─────────────────┐
│  order-service  │  │  stock-service  │
│  业务表 + undo_log │  │ 业务表 + undo_log │  ← 回滚快照在这里
└─────────────────┘  └─────────────────┘

注意

Seata Server 挂了并不会让业务立刻不可用，但新的全局事务开不起来，已有事务的提交/回滚会延迟到 Server 恢复。生产环境必须集群部署 + db 存储模式。

1.3 四种模式速览：AT / TCC / SAGA / XA ​

Seata 提供四种模式，本质区别只有一个问题：回滚的时候，靠什么把数据改回去？

模式靠什么回滚谁写回滚逻辑一致性
AT框架自动生成的反向 SQL（undo_log）Seata 自动最终一致
TCC你自己写的 Cancel 方法业务开发手写最终一致
SAGA你自己写的补偿服务业务开发手写最终一致
XA数据库原生的 XA ROLLBACK数据库负责强一致

用一句话记住它们的画风：

text
AT   ：我偷偷帮你拍了张"改之前的照片"，出事了照着改回去
TCC  ：你先预留资源，我喊 Confirm 就坐实，喊 Cancel 就还回去
SAGA ：每一步都配一个"反向步骤"，出事了倒着执行一遍
XA   ：所有数据库先别提交，都等我一声令下（锁一直占着）

判断口诀

能改 SQL、改表结构 → 优先 AT（零侵入）。

资金类、要预冻结 → TCC（控制最细）。

流程超长、含人工审批 → SAGA（异步补偿）。

必须强一致、不接受中间态 → XA（代价是性能）。

二、核心角色与原理篇 ​

2.1 TC / TM / RM：三个角色的职责边界 ​

概念

  • TC（Transaction Coordinator，事务协调者）：独立部署的 Seata Server，维护全局事务状态，最终下达提交/回滚指令。
  • TM（Transaction Manager，事务管理器）：发起全局事务的那个服务，决定全局提交还是全局回滚。
  • RM（Resource Manager，资源管理器）：管理本地数据库资源，注册分支事务、执行本地提交/回滚。

三者最容易混的是 TM 和 RM，先把边界划清楚：

对比项TMRM
在哪加了 @GlobalTransactional 的那个服务每个操作数据库的服务（包括 TM 自己）
职责开始/结束全局事务注册分支、上报分支状态、执行分支回滚
数量一次全局事务只有一个可以有 N 个
由谁触发业务方法入口数据源代理拦截 SQL 时自动触发

📌 单独澄清：order-service 既是 TM 又是 RM

order-service 加了 @GlobalTransactional，所以它是 TM；它自己也要往 order_db 写数据，所以它同时是 RM。角色是按行为划分的，不是按服务划分的。

text
order-service ──┬── TM 身份：向 TC 申请 XID、最后决定提交/回滚
                └── RM 身份：注册自己那条 insert 的分支事务

stock-service ───── 只有 RM 身份
account-service ─── 只有 RM 身份

判断口诀

谁写 @GlobalTransactional，谁就是 TM（全局只有一个）。

谁连数据库执行 SQL，谁就是 RM（有几个库就有几个）。

跑在外面那台 Seata Server 是 TC（大脑）。

2.2 全局事务与分支事务：两层事务模型 ​

Seata 的整个设计可以浓缩成一张两层结构图：

text
全局事务 (Global Transaction)  XID = 192.168.1.10:8091:2000123
│
├─ 分支事务1 (Branch) branchId=1  order_db     本地事务已提交 ✔
├─ 分支事务2 (Branch) branchId=2  stock_db     本地事务已提交 ✔
└─ 分支事务3 (Branch) branchId=3  account_db   本地事务已提交 ✔
                                   ▲
            每个分支的本地事务都是"一阶段就提交"的
            所以 Seata AT 不会长时间占着数据库连接
对比项全局事务分支事务
标识XIDbranchId（挂在某个 XID 下）
范围整条业务链路单个服务的单个数据库操作
谁管理TC + TMRM
提交时机所有分支都成功后一阶段立即提交（AT 模式）

📌 单独澄清：分支为什么敢"一阶段就提交"？

传统 XA 是"先不提交，等协调者发话"，所以数据库锁要一直持有到最后，性能很差。

Seata AT 反过来：先提交，出事了再用 undo_log 补偿回去。代价是中间存在一个"数据已经改了但全局还没确认"的窗口期——这就是 AT 只能做到最终一致的根本原因，也是需要全局锁的原因（见 4.3）。

2.3 XID：全局事务的身份证与传播链路 ​

概念

XID 是全局事务的唯一标识，格式为 TC 的 IP:端口:事务ID，例如 192.168.1.10:8091:2000123。

它必须在整条调用链里原样传递，下游服务拿到 XID 才知道"我要加入哪个全局事务"。

XID 的生命周期：

text
① order-service 进入 @GlobalTransactional 方法
       ↓
② TM 向 TC 申请 → TC 返回 XID
       ↓
③ XID 绑定到当前线程  RootContext.bind(xid)
       ↓
④ Feign 拦截器读取 RootContext.getXID()
   塞进 HTTP Header: TX_XID
       ↓
⑤ stock-service 的拦截器从 Header 取出 XID
   再次 RootContext.bind(xid)
       ↓
⑥ stock-service 执行 SQL → RM 带着这个 XID 注册分支
       ↓
⑦ 方法结束 RootContext.unbind()

查看当前线程的 XID：

java
@RestController
@RequestMapping("/xid")
public class XidController {

    @GetMapping("/current")
    public String currentXid() {
        // 为 null 说明没进全局事务，或者 XID 没传过来
        String xid = RootContext.getXID();
        return xid == null ? "无全局事务" : xid;
    }
}

注意

XID 存放在 ThreadLocal（RootContext）里。这意味着：

  • ✅ 同步的 Feign / RestTemplate 调用 → 自动透传，没问题
  • ❌ new Thread()、线程池 @Async、MQ 异步消费 → XID 丢失，下游不会加入全局事务

解法见 7.3。

判断口诀

XID 在 = 分支能注册 = 事务能回滚。

排查"全局事务不回滚"时，第一件事永远是：在下游服务打印 RootContext.getXID()，看是不是 null。

2.4 两阶段提交：Seata 和传统 2PC 的差别 ​

完整的 AT 模式时序：

text
【一阶段】
TM  ──begin──────────────────────────►  TC   （生成 XID）
RM1 ──解析SQL/存undo_log/本地提交────►  TC   （注册分支1，报告成功）
RM2 ──解析SQL/存undo_log/本地提交────►  TC   （注册分支2，报告成功）
RM3 ──执行时抛异常───────────────────►  TC   （报告失败）

【二阶段 - 回滚】
TM  ──rollback───────────────────────►  TC
TC  ──branch rollback────────────────►  RM1  （查 undo_log，生成反向 SQL 执行）
TC  ──branch rollback────────────────►  RM2  （同上）
TC  ──删除全局锁、清理 undo_log

【二阶段 - 提交】（全部成功时）
TM  ──commit─────────────────────────►  TC
TC  ──异步删除 undo_log、释放全局锁        （不需要操作业务数据，极快）

和传统 XA/2PC 的核心差别：

对比项传统 2PC（XA）Seata AT
一阶段执行 SQL 但不提交，持有数据库锁执行 SQL 并提交，立即释放数据库锁
锁持有时间整个全局事务期间单个分支的本地事务期间（毫秒级）
二阶段提交真正执行 XA COMMIT只是异步删 undo_log，几乎无成本
二阶段回滚XA ROLLBACK，数据库原生回退用 undo_log 生成反向 SQL 补偿
隔离性数据库原生保证靠 Seata 的全局锁自己保证
一致性强一致最终一致（存在中间可见窗口）

📌 单独澄清：为什么 AT 的"提交"比"回滚"快得多？

提交时业务数据已经是正确的终态，TC 只需异步清理 undo_log；而回滚需要反查快照、生成并执行反向 SQL、校验脏写，是真正的数据库写操作。所以正常链路几乎零额外开销，异常链路才付代价——这正是 AT 敢于默认启用的原因。

4.1 AT 模式原理：前置镜像与后置镜像 ​

概念

AT（Automatic Transaction）模式：框架在执行业务 SQL 前后各查一次数据，分别称为前置镜像（before image）和后置镜像（after image），把两份快照写进 undo_log。回滚时拿前置镜像生成反向 SQL 把数据改回去。

对业务代码零侵入——你只写正常的 SQL，回滚逻辑框架替你生成。

以 UPDATE stock SET count = count - 1 WHERE id = 1 为例：

text
① 解析 SQL，提取表名 stock、条件 id=1
       ↓
② 查前置镜像：SELECT id,count FROM stock WHERE id = 1
   结果：{id:1, count:100}
       ↓
③ 执行业务 SQL：UPDATE stock SET count = count-1 WHERE id = 1
       ↓
④ 查后置镜像：SELECT id,count FROM stock WHERE id = 1
   结果：{id:1, count:99}
       ↓
⑤ 把 ③④ 两份快照组装成 rollback_info，
   INSERT 进 undo_log（和业务 SQL 在同一个本地事务里）
       ↓
⑥ 向 TC 注册分支 + 申请全局锁（stock:1）
       ↓
⑦ 本地事务 COMMIT（业务数据 + undo_log 一起落盘）

回滚时：

text
① 根据 xid + branchId 查出 undo_log
② 拿【当前数据库值】和【后置镜像】比对
   ├─ 一致   → 没人动过，安全回滚
   └─ 不一致 → 脏写！抛异常，转人工处理
③ 用前置镜像生成反向 SQL：
   UPDATE stock SET count = 100 WHERE id = 1
④ 执行反向 SQL + 删除 undo_log（同一本地事务）

不同 SQL 类型的反向操作：

业务 SQL前置镜像后置镜像反向 SQL
INSERT空新插入的行DELETE
UPDATE改之前的行改之后的行UPDATE 回旧值
DELETE删之前的行空INSERT 回去

📌 单独澄清：为什么要存两份镜像？只存前置镜像不够吗？

不够。后置镜像是用来做脏写校验的。回滚前先确认"当前数据 == 我改完之后的样子"，才能证明这期间没有别人修改过。否则直接拿前置镜像覆盖，会把别人的修改一起冲掉。

4.3 全局锁与写隔离：AT 如何防止脏写 ​

AT 的分支事务一阶段就提交了，数据库锁立刻释放。那么在全局事务结束之前，别人完全可以改同一行数据——如果真让他改了，回滚时就会把他的修改一起冲掉。这就是脏写。

Seata 的解法是全局锁：

概念

全局锁（Global Lock）：分支事务提交前，必须先向 TC 申请"我要锁定 stock 表 id=1 这一行"。锁的粒度是表名 + 主键，存在 TC 的 lock_table 里，直到全局事务结束才释放。

两个全局事务并发改同一行：

text
时间    全局事务 A                      全局事务 B
 │
 t1    拿本地锁 → 改 count 100→99
 t2    申请全局锁 stock:1  ✔ 拿到
 t3    提交本地事务（本地锁释放）
 t4                                   拿本地锁 → 改 count 99→98
 t5                                   申请全局锁 stock:1  ✘ 被 A 占着
 t6                                   重试...重试...（默认 30 次 × 10ms）
 t7    业务异常 → 全局回滚
       校验后置镜像一致 ✔ → 改回 100
       释放全局锁
 t8                                   重试成功，拿到全局锁，提交

注意

B 在 t6 阶段是持有本地锁、等待全局锁。如果等待超时，B 会回滚本地事务并释放本地锁，避免死锁。但这意味着高并发下热点行会出现大量 get global lock fail, xid:... 的失败重试。

重试参数调优：

yaml
seata:
  client:
    rm:
      # 获取全局锁失败的重试次数
      lock:
        retry-times: 30
        # 每次重试间隔（毫秒）
        retry-interval: 10
        # 分支回滚时获取锁失败是否一直重试
        retry-policy-branch-rollback-on-conflict: true

📌 单独澄清：全局锁和数据库行锁的区别

对比项数据库行锁Seata 全局锁
谁维护MySQL InnoDBSeata TC（lock_table 表）
持有时长本地事务期间（毫秒级）整个全局事务期间（可能数百毫秒）
作用范围单库内跨服务跨库
冲突表现阻塞等待抛 LockConflictException 后重试

判断口诀

本地锁防的是同库并发，全局锁防的是跨服务脏写。

4.4 读隔离与 @GlobalLock ​

写隔离解决了，那读呢？

AT 模式的默认隔离级别是读未提交（Read Uncommitted）。因为分支一阶段就提交了，此时数据已经对所有人可见，但全局事务还没结束——如果后面回滚了，读到的就是"幻觉数据"。

text
全局事务 A：把余额从 100 改成 0，分支已提交
          ↓
用户 B 查询余额 → 看到 0     ← 读到了尚未最终确认的数据
          ↓
全局事务 A 回滚 → 余额改回 100
          ↓
用户 B 刚才看到的 0 是错的

如果业务确实不能接受这种读，Seata 提供两种手段：

java
@GlobalLock
@Transactional
public Account queryForUpdate(Long userId) {
    // FOR UPDATE 会触发 Seata 校验全局锁
    // 若该行正被其他全局事务占用，这里会抛 LockConflictException
    return accountMapper.selectForUpdate(userId);
}
java
@GlobalTransactional
public Account query(Long userId) {
    // 开销更大：会真的开一个全局事务
    return accountMapper.selectById(userId);
}

📌 单独澄清：@GlobalLock 和 @GlobalTransactional 到底差在哪？

对比项@GlobalTransactional@GlobalLock
是否开全局事务✅ 会向 TC 申请 XID❌ 不开，只做锁校验
是否注册分支✅❌
开销大小
用途需要跨服务回滚的写操作只想读到"全局确认后"数据的读操作

注意

@GlobalLock 必须和 @Transactional 一起用，并且 SQL 要带 FOR UPDATE，否则它什么都不做。它不是"加个注解就安全"的魔法。

判断口诀

绝大多数业务不需要处理读隔离——对账、余额展示这类场景容忍短暂不一致。

只有"读完立刻据此做决策"（如风控扣额度）才需要 @GlobalLock + FOR UPDATE。

  • 禁止任何人绕过 Seata 直接改参与全局事务的表
  • undo_log 表设置定期清理（删 7 天前且 log_status=1 的记录）

五、TCC 模式篇 ​

5.1 Try / Confirm / Cancel 三阶段拆解 ​

概念

TCC（Try-Confirm-Cancel）：把一个业务操作拆成三个方法，由开发者手写资源的预留与释放逻辑。

  • Try：预留资源（冻结，而不是真正扣除）
  • Confirm：确认执行（把冻结坐实为扣除）
  • Cancel：取消执行（把冻结释放回去）

和 AT 的根本差别在于数据模型。AT 只有一列余额，TCC 要拆成两列：

text
AT 模式的账户表：
  balance = 1000
  扣 100 → balance = 900 ，回滚靠 undo_log 改回 1000

TCC 模式的账户表：
  balance = 1000,  frozen = 0
  Try     → balance = 900, frozen = 100   （钱还在，只是冻结了）
  Confirm → balance = 900, frozen = 0     （冻结的钱真正扣掉）
  Cancel  → balance = 1000, frozen = 0    （冻结的钱退回可用）
对比项ATTCC
回滚逻辑框架自动生成反向 SQL开发者手写 Cancel
表结构不用改通常要加冻结字段
资源占用全局锁锁住行不占全局锁，靠业务字段隔离
性能有锁冲突更高（无全局锁）
开发量1 个方法3 个方法 + 防悬挂表
能否跨数据库必须是关系库任意资源（Redis、第三方 API 都行）

📌 单独澄清：TCC 为什么不需要全局锁？

因为 Try 阶段已经把资源"圈出来了"。别人来查余额看到的是 900（可用余额），根本不可能再动这 100 块——业务层面的冻结字段本身就是一把锁，不需要 Seata 再加全局锁。这也是 TCC 性能优于 AT 的根本原因。

判断口诀

AT 是"先做了再说，错了我帮你改回去"。

TCC 是"先占个坑，确认了才落地"。

能改表结构、且对性能/一致性要求高 → TCC；追求快速接入 → AT。

5.2 TCC 三大坑：空回滚、幂等、悬挂 ​

TCC 的复杂度几乎全部来自这三个问题，面试也必问。

坑一：空回滚

text
TC → 调用 Try    ✘ 网络超时 / 服务宕机，Try 根本没执行
TC → 判定失败，调用 Cancel
Cancel 要释放"从未被冻结"的资源 → 可能把余额加多了

解法：建一张事务控制表 tcc_fence_log，Try 成功时插一条记录。Cancel 执行前先查：没查到 Try 记录 → 说明是空回滚，直接返回 true，什么都不做。

坑二：幂等

text
TC → 调用 Confirm  ✔ 执行成功，但返回时网络抖动
TC 没收到响应 → 重试 Confirm
→ 同一笔钱被扣了两次

解法：同一张 tcc_fence_log 表，用 xid + branch_id 做唯一键，记录状态。Confirm/Cancel 执行前先查状态，已是终态就直接返回成功。

坑三：悬挂

text
TC → 调用 Try    ✘ 网络拥塞，请求卡在路上
TC → 超时，调用 Cancel  ✔ 先执行完了
     ...
     迟到的 Try 请求终于到达 ✔ 冻结了资源
→ 资源被永久冻结，再也没人来 Confirm 或 Cancel

解法：Cancel 执行时，往 tcc_fence_log 插一条状态为"已回滚"的记录。Try 执行前先查：发现已有回滚记录 → 说明自己是迟到的 Try，直接放弃执行。

三个坑的统一解法就是 Seata 内置的 TCC Fence 机制，开启后框架自动处理：

java
@TwoPhaseBusinessAction(
    name = "accountTccAction",
    commitMethod = "confirm",
    rollbackMethod = "cancel",
    useTCCFence = true   // ← 开启防悬挂，Seata 自动管理 tcc_fence_log
)

对应的防悬挂表（建在业务库）：

sql
CREATE TABLE IF NOT EXISTS `tcc_fence_log` (
  `xid`           VARCHAR(128) NOT NULL COMMENT '全局事务ID',
  `branch_id`     BIGINT       NOT NULL COMMENT '分支事务ID',
  `action_name`   VARCHAR(64)  NOT NULL,
  `status`        TINYINT      NOT NULL COMMENT '1=tried 2=committed 3=rollbacked 4=suspended',
  `gmt_create`    DATETIME(3)  NOT NULL,
  `gmt_modified`  DATETIME(3)  NOT NULL,
  PRIMARY KEY (`xid`, `branch_id`),
  KEY `idx_gmt_modified` (`gmt_modified`),
  KEY `idx_status` (`status`)
) ENGINE = InnoDB CHARSET = utf8mb4;

注意

useTCCFence = true 要求 Try / Confirm / Cancel 三个方法都加 @Transactional，因为 Seata 需要把 fence 记录和你的业务 SQL 放在同一个本地事务里，否则防悬挂逻辑本身就不可靠。

判断口诀

空回滚：Cancel 来了，Try 没来过 → Cancel 要能"空跑"。

幂等：同一个 Confirm/Cancel 来了两次 → 第二次要"直接返回"。

悬挂：Cancel 跑完了，Try 才来 → Try 要能"拒绝执行"。

第二步：定义 TCC 接口

@LocalTCC
public interface AccountTccAction {

    /**
     * Try 阶段方法
     * BusinessActionContext         ：Seata 传入的上下文，Confirm/Cancel 可取到参数
     * BusinessActionContextParameter：标记该参数需要传递给二阶段方法
     */

            name = "accountTccAction",
            commitMethod = "confirm",
            rollbackMethod = "cancel",
            useTCCFence = true)
    boolean prepare(BusinessActionContext ctx,
                    @BusinessActionContextParameter(paramName = "userId") Long userId,
                    @BusinessActionContextParameter(paramName = "amount") BigDecimal amount);

第三步：实现三阶段

java
@Component
@RequiredArgsConstructor
public class AccountTccActionImpl implements AccountTccAction {

    private final AccountMapper accountMapper;

    /** Try：balance -= amount, frozen += amount */
    @Override
    @Transactional(rollbackFor = Exception.class)
    public boolean prepare(BusinessActionContext ctx, Long userId, BigDecimal amount) {
        int rows = accountMapper.freeze(userId, amount);
        if (rows == 0) {
            // 抛异常才能让 TC 感知失败并触发 Cancel
            throw new BizException("余额不足, userId=" + userId);
        }
        return true;
    }

    /** Confirm：frozen -= amount（钱真正扣掉） */
    @Override
    @Transactional(rollbackFor = Exception.class)
    public boolean confirm(BusinessActionContext ctx) {
        Long userId = Long.valueOf(ctx.getActionContext("userId").toString());
        BigDecimal amount = new BigDecimal(ctx.getActionContext("amount").toString());
        accountMapper.confirmFreeze(userId, amount);
        return true;
    }

    /** Cancel：frozen -= amount, balance += amount（钱退回可用） */
    @Override
    @Transactional(rollbackFor = Exception.class)
    public boolean cancel(BusinessActionContext ctx) {
        Long userId = Long.valueOf(ctx.getActionContext("userId").toString());
        BigDecimal amount = new BigDecimal(ctx.getActionContext("amount").toString());
        accountMapper.unfreeze(userId, amount);
        return true;
    }
}

  WHERE user_id = #{userId} AND balance >= #{amount}
</update>

<!-- Confirm：冻结金额真正扣除 -->
<update id="confirmFreeze">
  UPDATE account SET frozen = frozen - #{amount}

</update>

<!-- Cancel：冻结金额退回可用余额 -->

  UPDATE account SET balance = balance + #{amount}, frozen = frozen - #{amount}

</update>

6.1 SAGA：长事务的正向加补偿编排 ​

概念

SAGA 模式：把长流程拆成一串可独立提交的子事务 T1、T2、...、Tn，并为每个子事务配一个补偿操作 C1、C2、...、Cn。某一步失败时，倒序执行已完成步骤的补偿。

Seata 的 SAGA 基于状态机引擎，流程用 JSON 定义。

text
正向流程：  T1 ──► T2 ──► T3 ──► T4
           创建订单  扣库存  扣余额  发货

T3 失败时倒序补偿：
                    C2  ◄── C1
                   退库存    取消订单
（注意：补偿是"反向业务操作"，不是数据库回滚）

状态机定义（简化版 order_saga.json）：

json
{
  "Name": "orderSaga",
  "Comment": "下单状态机",
  "StartState": "CreateOrder",
  "States": {
    "CreateOrder": {
      "Type": "ServiceTask",
      "ServiceName": "orderService",
      "ServiceMethod": "create",
      "CompensateState": "CancelOrder",
      "Next": "DecreaseStock"
    },
    "CancelOrder": {
      "Type": "ServiceTask",
      "ServiceName": "orderService",
      "ServiceMethod": "cancel"
    },
    "DecreaseStock": {
      "Type": "ServiceTask",
      "ServiceName": "stockService",
      "ServiceMethod": "decrease",
      "CompensateState": "RestoreStock",
      "Next": "Succeed"
    },
    "RestoreStock": {
      "Type": "ServiceTask",
      "ServiceName": "stockService",
      "ServiceMethod": "restore"
    },
    "Succeed": { "Type": "Succeed" }
  }
}

SAGA 和 TCC 都要手写补偿，区别在哪：

注意

SAGA 没有资源预留，意味着T2 执行完后、T3 失败前，外部已经能看到 T2 的真实结果。如果 T2 是"给用户发了优惠券"，C2 就得"把券收回来"——而用户可能已经用掉了。所以 SAGA 的补偿必须考虑业务上能否真的补偿回去。

6.2 XA：数据库原生两阶段提交 ​

概念

XA 模式：依赖数据库自身的 XA 协议（MySQL 5.7+、Oracle、PostgreSQL 都支持）。一阶段执行 SQL 后只做 XA PREPARE 不提交，等 TC 发令才 XA COMMIT 或 XA ROLLBACK。

text
【一阶段】
RM1: XA START → 执行 SQL → XA END → XA PREPARE   （锁一直持有，不提交）
RM2: XA START → 执行 SQL → XA END → XA PREPARE   （锁一直持有，不提交）

【二阶段】
TC → XA COMMIT   给所有 RM    （数据库真正提交，释放锁）
或
TC → XA ROLLBACK 给所有 RM    （数据库原生回滚）

接入极其简单，只改一个配置，业务代码和 AT 完全一样：

yaml
seata:
  # AT 改成 XA 即可
  data-source-proxy-mode: XA

XA 和 AT 的对照：

对比项ATXA
一阶段是否提交✅ 提交❌ 只 PREPARE
数据库锁持有时长毫秒级整个全局事务期间
需要 undo_log 吗✅ 需要❌ 不需要
需要全局锁吗✅ 需要❌ 不需要（数据库锁已经够了）
隔离级别读未提交读已提交及以上
中间态可见✅ 可见❌ 不可见
性能高低（锁竞争 + 连接占用）
对数据库要求支持本地事务即可必须支持 XA 协议

📌 单独澄清：既然 XA 更强一致，为什么默认是 AT？

因为 XA 的代价在高并发下是致命的：

  1. 数据库连接要从一阶段一直持有到二阶段，连接池极易耗尽
  2. 行锁持有时间从毫秒级拉长到整个链路耗时（含网络 RTT）
  3. 如果 TC 在 PREPARE 后宕机，数据库里会残留悬挂的 XA 事务，锁永不释放，必须人工 XA RECOVER 清理

判断口诀

XA = 一致性拉满，吞吐量拉垮。

适合：对账、清算、低并发的内部系统。

不适合：C 端高并发链路。

7.2 @GlobalTransactional 与 @Transactional 的关系 ​

概念

@Transactional 管的是一个数据库连接内的提交/回滚；@GlobalTransactional 管的是一条调用链上所有分支的提交/回滚。

两者不是替代关系，而是嵌套关系：全局事务由若干个本地事务组成。

维度@Transactional@GlobalTransactional
作用范围单个服务、单个数据源整条调用链
实现者Spring + 数据库Seata TM/TC
回滚依据数据库 undo/redoSeata undo_log 反向 SQL
加在哪里每个写库的方法只加在发起方的入口方法
失败表现当前方法内数据回滚全链路数据回滚

正确写法

java
// 发起方（order-service）
@GlobalTransactional(rollbackFor = Exception.class)
public void createOrder(OrderDTO dto) {
    orderService.save(dto);          // 内部方法有 @Transactional
    storageClient.deduct(...);        // 远程调用
    accountClient.debit(...);         // 远程调用
}

// 参与方（storage-service）—— 只要 @Transactional，不要 @GlobalTransactional
@Transactional(rollbackFor = Exception.class)
public void deduct(Long skuId, Integer count) {
    storageMapper.deduct(skuId, count);
}

❌ 错误写法一：参与方也加 @GlobalTransactional

java
@GlobalTransactional   // ❌ 参与方不该开新全局事务
@Transactional
public void deduct(Long skuId, Integer count) { ... }

为什么这是错的

默认传播级别下 Seata 会复用上游的 XID，看起来好像没问题；但一旦有人把它改成 propagation = Propagation.REQUIRES_NEW，参与方就会开一个独立的新全局事务，上游回滚时它不会跟着回滚，数据直接撕裂。

规则：一条链路只允许有一个入口持有 @GlobalTransactional。

❌ 错误写法二：只加 @GlobalTransactional，参与方没有 @Transactional

参与方没有本地事务，意味着"业务 SQL"和"写 undo_log"不在同一个事务里。极端情况下业务 SQL 成功、undo_log 写入失败，这条分支就永远回滚不了。

判断口诀

发起方：@GlobalTransactional；参与方：@Transactional。

一个管"大家一起活/一起死"，一个管"我自己这一步的原子性"。

两个注解可以同时加在发起方的同一个方法上，顺序是先进全局、再进本地。

📌 单独澄清：@GlobalTransactional 的 rollbackFor 和 @Transactional 一样吗？

语义一样，默认行为的坑也一样：默认只对 RuntimeException 和 Error 回滚，受检异常（Exception 的子类但非 Runtime）不会触发回滚。

所以生产代码里统一写 rollbackFor = Exception.class，这不是迷信，是为了避免某天有人往方法上加了 throws IOException 后事务静默失效。

常用属性

属性含义建议值
name全局事务名，用于日志排查填业务语义，如下单
timeoutMills全局事务超时时间（毫秒）默认 60000，按链路调
rollbackFor哪些异常触发回滚Exception.class
noRollbackFor哪些异常不回滚慎用
lockRetryInterval抢全局锁失败后的重试间隔默认 10ms
lockRetryTimes抢全局锁重试次数默认 30

7.3 XID 在 Feign、异步线程、MQ 中的传播 ​

概念

全局事务能不能串起来，只看一件事：下游有没有拿到 XID。

XID 存在 RootContext 里，而 RootContext 底层是 ThreadLocal。只要换了线程或跨了进程，XID 就会丢。

XID 传播的全景图

text
order-service (TM)
  RootContext.bind(xid)          ← @GlobalTransactional 切面写入
        │
        ├── Feign 调用 ──→ SeataFeignClient 拦截器
        │                    把 xid 塞进 HTTP Header: TX_XID
        │                           │
        │                           ↓
        │                   storage-service
        │                   SeataHandlerInterceptor 从 Header 取出
        │                   RootContext.bind(xid)   ✅ 链路续上
        │
        ├── new Thread(...) ──→ ❌ 新线程 ThreadLocal 为空，XID 丢失
        │
        └── 发 MQ 消息 ──→ ❌ 消息体里没有 xid，消费端拿不到

场景一：Feign / RestTemplate —— 自动传播，无需改代码

引入 spring-cloud-starter-alibaba-seata 后会自动装配：

调用方式自动装配的组件是否需手工配置
OpenFeignSeataFeignClient否
RestTemplateSeataRestTemplateInterceptor否
DubboTransactionPropagationFilter否
网关转发—需透传 Header

网关是最容易断链的一环

如果 Gateway 配置了 Header 白名单，或者用了 RemoveRequestHeader 过滤器，TX_XID 可能被剥掉。

排查方法：在下游入口打印 RootContext.getXID()，为 null 就是断在网关了。

场景二：异步线程 —— 必须手动传递

❌ 错误写法：

java
@GlobalTransactional
public void createOrder(OrderDTO dto) {
    orderMapper.insert(...);
    CompletableFuture.runAsync(() -> {
        storageClient.deduct(...);  // ❌ 这里 XID 是 null，扣库存不受全局事务管控
    });
}

✅ 正确写法：

java
@GlobalTransactional
public void createOrder(OrderDTO dto) {
    orderMapper.insert(...);
    String xid = RootContext.getXID();          // 主线程先取出来
    CompletableFuture.runAsync(() -> {
        RootContext.bind(xid);                   // 子线程绑定
        try {
            storageClient.deduct(...);
        } finally {
            RootContext.unbind();                // 必须解绑，防止线程池污染
        }
    });
}

判断口诀

XID 跟着线程走，不跟着代码走。

换线程 = 换上下文，必须 bind + finally unbind。

少写 unbind 的后果比丢 XID 更严重：线程池复用时，下一个无关请求会误绑到上一个事务，造成莫名其妙的回滚。

📌 单独澄清：异步线程里的分支真的能被全局事务回滚吗？

能注册上，但不保证时序。主线程可能在异步任务还没注册分支时就提交了全局事务，这时异步分支成了"孤儿"。

所以结论是：全局事务内部不要用异步调用。如果必须异步，就把它拆到事务之外，用消息最终一致性兜底（见 8.3）。

场景三：MQ —— Seata 不管，必须自己设计

Seata 的全局事务不会跨越 MQ。消息一旦发出去就是另一条独立链路。

常见做法：

text
方案 A：事务提交后再发消息（推荐）
  @GlobalTransactional 方法内只写库
  用 TransactionSynchronizationManager.registerSynchronization
  在 afterCommit 回调里发消息
  → 保证"事务成功才发消息"，但消息可能丢（需 MQ 本地消息表兜底）

方案 B：本地消息表
  业务写库 + 消息写入本地 message 表（同一个事务）
  定时任务扫描 message 表投递
  → 最可靠，但引入额外表和定时任务

方案 C：RocketMQ 事务消息
  half 消息 + 本地事务 + 回查
  → MQ 原生支持，但只有 RocketMQ 有

undo_log 的清理

AT 模式二阶段提交时会异步删除 undo_log，但异常场景会残留。必须配定时清理：

sql
-- 清理 7 天前的残留记录（确认对应全局事务已结束）
DELETE FROM undo_log
WHERE log_modified < DATE_SUB(NOW(), INTERVAL 7 DAY)
LIMIT 1000;

判断口诀

undo_log 只涨不降 = 二阶段没跑完。

先查 TC 日志有没有 branch commit failed，再查 branch_table 里是否有长期停留的分支。

不要直接清 undo_log 了事——那等于把"还没回滚的证据"删了，之后想补都补不回来。

📌 单独澄清：为什么"缩短事务范围"对 Seata 比对单库事务更重要？

单库事务只锁数据库的行锁，耗时通常在毫秒级。

而全局事务要持有全局锁，时长 = 整条链路的耗时，包含所有网络 RTT。一次远程调用超时 3 秒，这 3 秒里其他请求全都抢不到这一行的全局锁——放大效应是数量级的。

8.1 全局事务不回滚的七种根因 ​

概念

"加了 @GlobalTransactional 但数据没回滚"是 Seata 最高频的线上问题。

排查顺序永远是：事务有没有开起来 → XID 有没有传下去 → 分支有没有注册上 → 异常有没有抛出来。

根因一：异常被 catch 掉了

java
@GlobalTransactional
public void createOrder(OrderDTO dto) {
    try {
        storageClient.deduct(...);
    } catch (Exception e) {
        log.error("扣库存失败", e);   // ❌ 吞了异常，TM 认为一切正常，照常提交
    }
}

✅ 要么不 catch，要么 catch 之后重新抛出，或手动标记回滚：

java
} catch (Exception e) {
    log.error("扣库存失败", e);
    throw new BizException("下单失败", e);          // 方案一
    // 或 GlobalTransactionContext.reload(RootContext.getXID()).rollback(); // 方案二
}

根因二：方法内部自调用，注解失效

java
public void entry() {
    this.createOrder(dto);   // ❌ this 调用不走代理，@GlobalTransactional 完全不生效
}

@GlobalTransactional
public void createOrder(OrderDTO dto) { ... }

原因和 Spring @Transactional 失效一模一样：注解靠 AOP 代理生效，this.xxx() 绕过了代理对象。

解法：注入自己（@Lazy）、用 AopContext.currentProxy()、或把方法拆到另一个 Bean。

根因三：数据源没被代理

自定义了 DataSource Bean 却没包 DataSourceProxy：

java
@Bean   // ❌ 原生数据源，RM 拦截不到 SQL，undo_log 根本不会写
public DataSource dataSource() {
    return new HikariDataSource(config);
}

✅ 修复：

java
@Bean
@Primary
public DataSource dataSource(HikariDataSource hikari) {
    return new DataSourceProxy(hikari);
}

判断依据：启动日志没有 RM register，或 undo_log 表始终为空。

根因四：XID 没传到下游

下游入口打印 RootContext.getXID() 为 null。常见原因：

  • 网关把 TX_XID Header 过滤了
  • 用了 new Thread / 线程池 / @Async 却没手动 bind
  • 调用方式不是 Feign/RestTemplate/Dubbo（比如手写 OkHttp）

根因五：参与方漏了 @Transactional

业务 SQL 和 undo_log 不在同一本地事务，undo_log 写失败时分支无法回滚。

根因六：rollbackFor 没配，抛的是受检异常

默认只对 RuntimeException 回滚。

根因七：表没有主键

AT 模式靠主键定位行来生成反向 SQL。无主键表会报 Not found rollback info 或直接回滚不生效。

判断口诀

先看日志里有没有 Begin new global transaction，再看下游 XID 是不是 null。

前者为空 = 注解没生效（自调用/没加/代理问题）。

后者为 null = 链路断了（网关/线程/调用方式）。

两个都正常还不回滚 = 异常被吞了，或者数据源没代理。

  2. 怎么快速判断是"事务没开起来"还是"XID 没传下去"？
  3. 表没有主键为什么会导致 AT 模式回滚失败？

这个报错的含义是：Seata 要回滚的那行数据，已经不是它一阶段时看到的样子了。

说明有人绕过 Seata 直接改了库（手工 SQL、定时任务、另一个没接 Seata 的服务）。

此时 Seata 会停止回滚并挂起该分支——这是保护机制，强行重试只会把正确数据覆盖掉。正确做法是人工核对数据后手动处理，并找出绕过 Seata 的那条写入路径。

text

  有 "register branch successfully, xid=..." 吗？

8.3 Seata 与消息最终一致性的取舍 ​

概念

分布式事务有两条主流技术路线：Seata 这类事务协调框架，和 MQ 消息最终一致性。

它们解决的是同一个问题，但付出的代价完全不同。

维度Seata（AT/TCC）消息最终一致性（MQ）
一致性时间窗毫秒～秒级秒～分钟级，甚至更久
代码侵入AT 零侵入 / TCC 高中（本地消息表 + 消费幂等）
基础设施需部署 TC 集群需 MQ 集群（通常已有）
耦合度调用链同步耦合服务间解耦
失败处理自动回滚重试 + 人工补偿
性能上限受全局锁限制高（异步削峰）
调用关系要求必须同步可达可异步、可离线

什么时候选 Seata

text
✅ 调用链短（2~4 个服务）
✅ 要求用户提交后立刻看到最终结果
✅ 回滚逻辑复杂，不想手写补偿
✅ 团队没有成熟的消息幂等/补偿体系

典型：下单扣库存扣余额、后台批量操作

什么时候选 MQ 最终一致性

text
✅ 链路长、涉及多个团队的系统
✅ 下游允许延迟（积分、通知、报表、同步到 ES）
✅ 下游可能不可用，需要削峰和重试
✅ 追求服务解耦，不接受同步强依赖

典型：下单后送积分、发券、同步搜索索引

判断口诀

用户要"立刻看到结果"的用 Seata，用户"看不见也不急"的用 MQ。

核心业务（订单、库存、资金）走 Seata 保证强约束；

衍生业务（积分、通知、统计）走 MQ 保证最终一致。

📌 单独澄清：两者能不能混用？

能，而且这是生产里最常见的架构：

text
@GlobalTransactional
下单流程 {
    创建订单   ┐
    扣减库存   ├─ Seata 管这段，必须原子
    扣减余额   ┘
}
        ↓ 事务提交成功后
    发送 MQ 消息
        ↓
    送积分 / 发券 / 推送通知  ← MQ 最终一致，失败重试即可

边界划分的原则：失败必须整体回滚的放进 Seata，失败可以重试补救的放到 MQ。

不要把所有东西都塞进全局事务

常见反模式：在 @GlobalTransactional 方法里调用短信接口、写日志文件、推送 ES。

这些操作一来不可回滚（短信发出去收不回），二来拉长了全局锁持有时间。

正确做法是把它们移到事务之外，或用 MQ 异步化。

8.4 面试问答加分点 ​

概念

面试官问 Seata，考的从来不是"你会不会配 YAML"，而是你知不知道它的代价。

能说出限制和权衡的人，远比能背出四种模式名字的人加分。

Q1：Seata AT 模式的两阶段提交和传统 XA 有什么本质区别？

关键答点：XA 的一阶段只是 PREPARE，本地事务不提交，数据库连接和锁一直持有到二阶段；AT 的一阶段本地事务直接提交并释放数据库连接，只保留 Seata 的全局锁。

所以 AT 性能高得多，代价是中间态对外可见（默认读未提交）。

一句话：XA 是"锁住资源等结果"，AT 是"先提交再准备回滚"。

Q2：AT 模式的全局锁和数据库行锁是什么关系？

两者在不同层面：行锁在数据库，生命周期是本地事务；全局锁在 TC 的 lock_table，生命周期是整个全局事务。

一阶段提交后行锁释放了，但全局锁还在，所以别的全局事务改不了这一行——这就是 AT 的隔离机制。

加分点：非 Seata 管控的 SQL 不受全局锁约束，直接手工改库会造成脏写。

Q3：AT 模式会脏读吗？怎么解决？

会。默认隔离级别是读未提交，因为一阶段已经提交到库里了。

解决方案：对一致性敏感的查询用 SELECT ... FOR UPDATE，Seata 的 SelectForUpdateExecutor 会去抢全局锁，抢不到就重试，从而达到读已提交。

加分点：这个方案会显著降低并发，所以只在必须的查询上加，不要全局开启。

Q4：TCC 的三大坑是什么？

空回滚、幂等、悬挂。

  • 空回滚：Try 没执行（超时/网络失败）却收到 Cancel
  • 幂等：Confirm/Cancel 可能被重复调用
  • 悬挂：Cancel 比 Try 先到，Try 后执行导致资源永久冻结

统一解法是 fence 日志表（tcc_fence_log）：记录 xid + branch_id + 状态，Cancel 时先插记录，Try 时检查记录是否已存在。

Q5：Seata 的 TC 挂了会怎样？

分情况：

  • 事务还没开始：新请求报错，服务不可用但数据安全
  • 一阶段进行中：分支注册失败，本地事务回滚，数据安全
  • 一阶段完成、二阶段未下发：数据处于中间态，全局锁未释放，TC 恢复后会从 global_table 读取状态继续推进

所以 TC 必须用 db/redis 存储 + 多节点，file 模式一旦挂掉状态就丢了。

Q6：如果让你不用 Seata 实现跨服务一致性，你怎么做？

这是考察深度的题，别说"没 Seata 就做不了"。

答：用本地消息表 + 定时重试实现最终一致性；强一致场景用 TCC 思路手写"冻结-确认-解冻"；或者重新审视服务边界——很多分布式事务是服务拆分不合理造成的，把强关联的数据放回同一个服务/库是最彻底的解法。

判断口诀

面试答 Seata，一定要主动说出它的三个限制：

必须有主键、默认读未提交、全局锁会放大锁时长。

主动说限制 = 你真的用过；只说优点 = 你只看过文档。

概念

  TM  发起方   @GlobalTransactional 所在的服务   begin/commit/rollback

  TC  协调者   独立部署的 seata-server          记状态 + 下发指令

  TCC   手写 Try/Confirm/Cancel        ← 非数据库资源、资金冻结

  1. 表必须有主键
  2. 默认读未提交，中间态可见
  3. 全局锁持有时长 = 整条链路耗时
