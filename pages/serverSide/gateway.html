一、认知与定位篇 ​

1.1 没有网关的系统有多痛 ​

先看一个只有三个微服务的小系统，如果前端直连会发生什么：

text
                  ┌──▶ user-service   :8081   自己写一遍 Token 校验
浏览器 / App ─────┼──▶ order-service  :8082   自己写一遍 Token 校验
                  └──▶ pay-service    :8083   自己写一遍 Token 校验

前端要维护 3 个地址 + 3 套跨域配置
鉴权逻辑复制 3 份，改一次要改 3 个仓库
限流、日志、黑名单各做各的，口径还不一致
内网服务端口全部对公网暴露
痛点没有网关时的状况有网关后
地址管理前端硬编码多个 host:port，扩缩容就要改前端只认一个域名，后端随便加服务
鉴权每个服务重复实现，容易漏网关统一拦截，服务只管业务
跨域每个服务配一遍 CORS网关统一配置一次
限流 / 黑名单没有统一入口，无从下手入口处统一拦截
安全内网服务直接暴露公网只暴露网关，服务藏在内网
灰度 / 多版本前端改地址才能切流量网关按规则路由，前端无感

判断口诀：凡是"每个服务都要做一遍"的横切逻辑，都应该上收到网关。

但网关不是万能的

网关做的是横切关注点（鉴权、限流、路由、日志），不是业务逻辑的存放处。见过最糟的实践是在网关过滤器里查数据库拼业务数据——网关一旦变成业务中心，它就同时是性能瓶颈和发布瓶颈：任何一个业务改动都要重启全站入口。

1.2 Gateway 是什么、不是什么 ​

概念

Spring Cloud Gateway 是 Spring 官方的 API 网关，构建在 Spring WebFlux + Project Reactor + Netty 之上，用 Route（路由）+ Predicate（断言）+ Filter（过滤器）三件套描述"什么请求转到哪里、转之前转之后做什么"。

它是什么：

  • 一个普通的 Spring Boot 应用，有自己的 main 方法、自己的端口、自己的 jar 包
  • 一个可编程的反向代理，路由规则可以写在 yml 里，也可以写在 Java 里、存在 Nacos 里、存在数据库里
  • Spring Cloud 生态的原生成员，天然能用 lb:// 从注册中心取实例、天然能被 Sentinel 接管

它不是什么：

常见误解实际情况
"Gateway 能替代 Nginx"不能。静态资源、SSL 卸载、超大并发裸转发还是 Nginx 更合适
"Gateway 是个独立中间件"不是。它就是你自己写的一个 Spring Boot 服务，要自己部署、自己扩容
"引入 Gateway 就安全了"不是。网关只是收口，鉴权逻辑仍然要你自己写对
"Gateway 里可以照常写 MVC 代码"❌ 绝对不行，见 1.4

📌 单独澄清：Gateway 和 spring-boot-starter-web 不能共存

Gateway 基于 WebFlux（Netty），spring-boot-starter-web 基于 Servlet（Tomcat）。两者同时在 classpath 上，Spring Boot 会优先选择 Servlet 栈，导致 Gateway 完全不工作，启动日志里只会给一句不起眼的提示。

xml
<!-- ❌ 网关模块里出现这个依赖，Gateway 直接失效 -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>

<!-- ✅ 网关只能用 WebFlux 栈 -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-gateway</artifactId>
</dependency>

这个坑的典型诱因是：网关模块依赖了一个 common 模块，而 common 里传递依赖了 starter-web。排查方法：

bash
mvn dependency:tree -Dincludes=org.springframework.boot:spring-boot-starter-web

📌 单独澄清：为什么 Zuul 1.x 被淘汰了？

Zuul 1.x 是同步阻塞模型：每个请求独占一个 Tomcat 线程，直到下游返回。假设线程池 200，下游响应变成 5 秒，那么网关的吞吐上限就是 200 / 5 = 40 QPS——下游一慢，网关自己先崩，而且会连锁拖垮所有经过它的业务。Gateway 用 Netty 事件循环，等待下游时线程会去处理别的请求，几十个线程就能扛住上万并发连接。

❌ 常见错误认知："我们流量不大，用哪个都一样。" ✅ 实际情况：流量不大时确实都能用，但故障时的表现天差地别。网关的价值恰恰体现在异常时刻。

生产上的标准组合：

text
Nginx / SLB（证书、静态资源、基础防护）
   └─▶ Gateway 集群（鉴权、路由、限流、灰度）
          └─▶ 微服务集群

1.4 WebFlux 模型：理解所有坑的前提 ​

Gateway 90% 的"诡异问题"都源于一件事：它跑在 WebFlux 上，而大多数人习惯的是 Spring MVC。

对比项Spring MVC（Servlet）Spring Cloud Gateway（WebFlux）
容器TomcatNetty
线程模型一请求一线程，线程数 200+事件循环，线程数 ≈ CPU 核数
请求对象HttpServletRequestServerHttpRequest（不可变）
返回值直接返回对象Mono<Void> / Flux
阻塞的后果占用一个线程，其他请求不受影响卡死一条事件循环，拖垮一批请求
ThreadLocal基本可用不可靠，线程会在算子间切换
text
Netty 事件循环（假设 8 核 → 8 条 loop 线程）

loop-1 ──▶ 请求A读头 ─▶ 转发出去（不等待，去处理下一个）─▶ 请求B ─▶ 请求C ...
                 ▲                                             │
                 └──── 下游响应到达，事件唤醒，继续处理A ◀──────┘

❌ 如果在 loop-1 上执行了一次 3 秒的阻塞调用：
loop-1 ──▶ 请求A ──[阻塞 3 秒，什么都干不了]──▶ ...
           期间原本由 loop-1 负责的成百上千个连接全部挂起
           8 条线程若都被阻塞，整个网关对外表现为"完全无响应"

过滤器里绝对不能做的事

java
// ❌ 全部都是在事件循环线程上阻塞，生产级事故写法
Thread.sleep(100);                              // 休眠
jdbcTemplate.queryForObject(sql, ...);          // 同步 JDBC
restTemplate.getForObject(url, String.class);   // 同步 HTTP
redisTemplate.opsForValue().get(key);           // 同步 Redis（Lettuce 同步 API）
someMono.block();                               // 把响应式强行转同步，最隐蔽的一种
java
// ✅ 正确做法一：用响应式客户端
return webClient.get().uri(url).retrieve().bodyToMono(String.class)
        .flatMap(result -> chain.filter(exchange));

// ✅ 正确做法二：实在只有阻塞 API，就丢到独立线程池
return Mono.fromCallable(() -> blockingCheck(token))
        .subscribeOn(Schedulers.boundedElastic()) // 关键：切换到弹性线程池
        .flatMap(ok -> chain.filter(exchange));

📌 单独澄清：为什么网关里的 ThreadLocal 会"莫名其妙丢失"？

MVC 里一个请求全程在同一条线程上，ThreadLocal 自然可用。WebFlux 里一个请求会在不同算子、不同线程之间流转——在 filter() 开头 set 的值，到 flatMap 里可能已经换了线程，取出来就是 null。

java
// ❌ 网关里这么写，下游算子大概率取不到
UserContextHolder.set(user);
return chain.filter(exchange);

// ✅ 网关里传递上下文有两条正道
// 方式一：写进 exchange 的 attributes（推荐，最简单）
exchange.getAttributes().put("loginUser", user);
// 方式二：用 Reactor Context
return chain.filter(exchange).contextWrite(ctx -> ctx.put("loginUser", user));

判断口诀：在网关里，请求上下文放 exchange，不放 ThreadLocal。

2.1 Route：一条路由的完整构成 ​

概念

Route（路由） 是 Gateway 的最小调度单元，由四部分组成：

组成作用是否必填
id路由唯一标识，日志和排障时用否（默认随机）
uri命中后转发到哪里是
predicates什么样的请求算命中是
filters命中后在转发前后做什么否
order多条路由的匹配优先级，越小越先否（默认 0）
yaml
spring:
  cloud:
    gateway:
      routes:
        - id: order-service-route # ① 建议用"服务名-route"命名，排障一眼认出
          uri: lb://order-service # ② lb = LoadBalancer，从注册中心按服务名取实例
          order: 1 # ③ 数字越小越先匹配
          predicates:
            - Path=/api/order/** # ④ 命中条件：可以写多个，是"与"关系
            - Method=GET,POST
          filters:
            - StripPrefix=1 # ⑤ 转发前去掉 /api
            - AddRequestHeader=X-From, gateway

uri 的三种写法：

yaml
uri: lb://order-service        # ✅ 推荐：走注册中心 + 负载均衡，实例变化无感
uri: http://192.168.1.10:8082  # ⚠️ 写死 IP：机器一换就要改配置，仅测试用
uri: ws://localhost:9000       # WebSocket 转发

📌 单独澄清：lb:// 后面跟的到底是什么？

是注册中心里的服务名（即下游服务的 spring.application.name），不是主机名、不是路径。写错服务名的典型报错是 503 Service Unavailable，日志里会出现 Unable to find instance for xxx。

yaml
# ❌ 这三种写法都是错的
uri: lb://192.168.1.10:8082    # lb 后面不能跟 IP
uri: lb://order-service/api    # lb 后面不能带路径
uri: lb:order-service          # 少了两个斜杠

# ✅ 正确
uri: lb://order-service

2.2 Predicate：请求凭什么命中这条路由 ​

概念

Predicate（断言） 本质就是一个 Predicate<ServerWebExchange>：输入一个请求，输出 true / false。Gateway 内置了十余种工厂类，命名规则是 XxxRoutePredicateFactory，配置里写 Xxx=参数 即可。

text

         │   前置：记录开始时间                         │
         │  ┌──── GlobalFilter B (order = 0) ────┐     │
         │  │  前置：校验 Token                   │     │
         │  │  ┌── 局部 Filter: StripPrefix ──┐   │     │
请求 ──▶ │  │  │   ┌─ NettyRoutingFilter ─┐  │   │     │ ──▶ 响应
         │  │  │   │  真正发起下游调用     │  │   │     │
         │  │  │   └──────────────────────┘  │   │     │
         │  │  └──────────────────────────────┘   │     │
         │  │  后置：记录响应码                    │     │
         │  └────────────────────────────────────┘     │

         └──────────────────────────────────────────────┘

@Component
public class TimerFilter implements GlobalFilter, Ordered {
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        long start = System.currentTimeMillis(); // 前置逻辑

        return chain.filter(exchange).then(Mono.fromRunnable(() -> {
            // 后置逻辑：必须写在 then() 里，写在 chain.filter() 之后是拿不到响应的
            long cost = System.currentTimeMillis() - start;
            log.info("path={} status={} cost={}ms",
                    exchange.getRequest().getPath(),
                    exchange.getResponse().getStatusCode(), cost);
        }));
    }

    @Override
    public int getOrder() {
        return -100; // 值越小越先执行前置、越后执行后置
    }
}

问题背景： yml 里写死路由，加一个服务就要改配置、重启网关。生产上网关是流量入口，重启意味着抖动。

做法一：服务发现自动路由（最省事，但最粗糙）

优点缺点
零配置，新服务自动可达路径里暴露了服务名，对外不安全
适合内网、测试环境无法做精细的 filter 配置（限流、鉴权都挂不上）

生产建议：对外网关关闭它，只在内网调试网关开启。

做法二：Nacos 配置中心 + 监听器（最常用）

把路由规则放到 Nacos 的一个 JSON 配置里，监听变更后刷新。

java
@Component
public class NacosRouteConfig implements ApplicationEventPublisherAware {

    @Autowired
    private RouteDefinitionWriter routeDefinitionWriter;
    private ApplicationEventPublisher publisher;
    private final Set<String> routeIds = new HashSet<>();

    @Override
    public void setApplicationEventPublisher(ApplicationEventPublisher publisher) {
        this.publisher = publisher;
    }

    /** 由 Nacos 监听回调触发 */
    public void refresh(String configJson) {
        // 1. 先删掉旧路由
        routeIds.forEach(id ->
                routeDefinitionWriter.delete(Mono.just(id)).subscribe());
        routeIds.clear();

        // 2. 再加载新路由
        List<RouteDefinition> list =
                JSON.parseArray(configJson, RouteDefinition.class);
        list.forEach(def -> {
            routeDefinitionWriter.save(Mono.just(def)).subscribe();
            routeIds.add(def.getId());
        });

        // 3. 发布刷新事件，让 RouteLocator 重新读取 ★ 少了这步不生效
        publisher.publishEvent(new RefreshRoutesEvent(this));
    }
}

Nacos 里的配置长这样（dataId 如 gateway-routes.json）：

json
[
  {
    "id": "user-service",
    "uri": "lb://userservice",
    "order": 1,
    "predicates": [{ "name": "Path", "args": { "pattern": "/user/**" } }],
    "filters": [{ "name": "StripPrefix", "args": { "parts": "1" } }]
  }
]

做法三：自定义 RouteDefinitionRepository（最彻底）

实现 RouteDefinitionRepository 接口，把路由存到数据库或 Redis，网关启动时和刷新时都从这里读：

java
@Component
public class RedisRouteRepository implements RouteDefinitionRepository {

    @Autowired
    private StringRedisTemplate redis;
    private static final String KEY = "gateway:routes";

    @Override
    public Flux<RouteDefinition> getRouteDefinitions() {
        return Flux.fromIterable(redis.opsForHash().values(KEY))
                .map(v -> JSON.parseObject(v.toString(), RouteDefinition.class));
    }

    @Override
    public Mono<Void> save(Mono<RouteDefinition> route) {
        return route.flatMap(r -> {
            redis.opsForHash().put(KEY, r.getId(), JSON.toJSONString(r));
            return Mono.empty();
        });
    }

    @Override
    public Mono<Void> delete(Mono<String> routeId) {
        return routeId.flatMap(id -> {
            redis.opsForHash().delete(KEY, id);
            return Mono.empty();
        });
    }
}

三种做法选型对照：

做法改动成本可控性适用场景
discovery.locator最低最差内网调试、临时联调
Nacos 配置 + 监听中好绝大多数生产项目（推荐）
自定义 Repository高最好有路由管理后台、需要审计的平台

动态路由两个必踩的坑

① 忘记发 RefreshRoutesEvent。 只调 routeDefinitionWriter.save() 不发事件，CachingRouteLocator 里的缓存不会更新，新路由查不到也用不上。

② 新增路由不删旧路由。 每次刷新都 save 不 delete，id 相同会覆盖，id 变了就残留。正确做法是记录已加载的 id 集合，刷新时先删后加（见做法二的代码）。

命名约定（强制）： 类名必须是 XxxGatewayFilterFactory，yml 里用 Xxx 引用。写错名字会直接启动报错 Unable to find GatewayFilterFactory with name Xxx。

java
@Component
public class AuthCheckGatewayFilterFactory
        extends AbstractGatewayFilterFactory<AuthCheckGatewayFilterFactory.Config> {

    public AuthCheckGatewayFilterFactory() {
        super(Config.class); // ★ 必须调用，否则拿不到配置
    }

    @Override
    public GatewayFilter apply(Config config) {
        return (exchange, chain) -> {
            String value = exchange.getRequest()
                    .getHeaders().getFirst(config.getHeaderName());
            if (!config.getExpectValue().equals(value)) {
                exchange.getResponse().setStatusCode(HttpStatus.FORBIDDEN);
                return exchange.getResponse().setComplete(); // ★ 拦截：不调 chain
            }
            return chain.filter(exchange); // 放行
        };
    }

    /** 支持 yml 简写顺序：AuthCheck=X-Token,abc123 */
    @Override
    public List<String> shortcutFieldOrder() {
        return Arrays.asList("headerName", "expectValue");
    }

    @Data
    public static class Config {
        private String headerName;
        private String expectValue;
    }
}

4.3 自定义全局过滤器：GlobalFilter ​

适用场景： 所有路由都要执行、不需要参数的逻辑。鉴权、日志、链路追踪都属于这类。

java
@Component
public class AccessLogGlobalFilter implements GlobalFilter, Ordered {

    private static final Logger log =
            LoggerFactory.getLogger(AccessLogGlobalFilter.class);

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        long start = System.currentTimeMillis();
        ServerHttpRequest request = exchange.getRequest();
        String path = request.getPath().value();

        // ★ 后置逻辑写在 then() 里，不要写在 chain.filter() 之后
        return chain.filter(exchange).then(Mono.fromRunnable(() -> {
            long cost = System.currentTimeMillis() - start;
            log.info("{} {} -> {} cost={}ms",
                    request.getMethod(), path,
                    exchange.getResponse().getStatusCode(), cost);
        }));
    }

    @Override
    public int getOrder() {
        return -100; // 越小越先执行前置，越后执行后置
    }
}

📌 单独澄清：为什么响应式里"写在后面"不等于"后执行"？

chain.filter(exchange) 返回的是一个还没订阅的 Mono，相当于一张"执行计划书"，不是执行结果。只有被订阅（subscribe）时才真正跑。所以在它之后写的同步代码，执行时机是"组装阶段"，而不是"请求完成后"。要在请求完成后执行，必须挂到 .then() / .doFinally() 这类操作符上。

@Component
public class LogBodyGlobalFilter implements GlobalFilter, Ordered {

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        MediaType contentType = exchange.getRequest().getHeaders().getContentType();
        if (contentType == null || !contentType.includes(MediaType.APPLICATION_JSON)) {
            return chain.filter(exchange); // 非 JSON 直接放行，别碰流
        }
        // ★ 关键：缓存请求体，让后续还能再读一次
        return DataBufferUtils.join(exchange.getRequest().getBody())
                .flatMap(buffer -> {
                    byte[] bytes = new byte[buffer.readableByteCount()];
                    buffer.read(bytes);
                    DataBufferUtils.release(buffer);
                    String body = new String(bytes, StandardCharsets.UTF_8);
                    log.info("request body: {}", body);

                    // 重新包装一个能再读的 request
                    ServerHttpRequestDecorator decorator =
                            new ServerHttpRequestDecorator(exchange.getRequest()) {
                                @Override
                                public Flux<DataBuffer> getBody() {
                                    return Flux.just(exchange.getResponse()
                                            .bufferFactory().wrap(bytes));
                                }
                            };
                    return chain.filter(exchange.mutate().request(decorator).build());
                });
    }

    @Override
    public int getOrder() {
        return -10; // 必须早于 NettyRoutingFilter
    }
}

4.5 过滤器执行顺序的完整规则 ​

排序三条规则（按优先级）：

  1. GlobalFilter 和 GatewayFilter 混在同一条链里排序，不是先全局后局部。
  2. order 值越小越先执行前置逻辑，后置逻辑则逆序执行。
  3. order 相同时：default-filters 优先于路由级 filters，路由级 filters 按 yml 书写顺序（隐式 order 从 1 开始递增）。

内置 GlobalFilter 的 order 速查（排障必备）：

GlobalFilterorder职责
RemoveCachedBodyFilter-2147483648（MIN）释放缓存的请求体
AdaptCachedBodyGlobalFilter-2147482648适配缓存请求体
NettyWriteResponseFilter-1把下游响应写回客户端
ForwardPathFilter0处理 forward: 协议
ReactiveLoadBalancerClientFilter10150lb:// 解析成真实地址
RouteToRequestUrlFilter10000拼出最终请求 URL

自定义过滤器的 order 怎么选：

text
鉴权类        -100  ~  -1      要在转发前拦住，越早越好
请求体日志    -10               晚于鉴权（鉴权失败就不必读 body）
链路追踪      MIN + 10          最早，要覆盖全链路
响应体改写    -2                必须 < NettyWriteResponseFilter(-1)

📌 单独澄清：响应体改写为什么要 order < -1？

NettyWriteResponseFilter 的 order 是 -1，它负责真正往客户端写数据。你的装饰器必须比它更早执行前置（包装好 Response），才能在它写数据时走到你的 writeWith。如果你的 order > -1，包装动作发生在它之后，等于没包。

一个经典误解

"GlobalFilter 一定比 GatewayFilter 先执行" —— 错。两者在 FilteringWebHandler 里被合并成一个 List 统一按 order 排序。一个 order = 100 的 GlobalFilter，会排在 order = 1 的路由级 filter 后面。

5.1 为什么鉴权应该放在网关 ​

不放网关的代价：

text
❌ 每个服务自己校验 JWT
   user-service    → 写一遍 JwtUtil + 拦截器
   order-service   → 再写一遍
   product-service → 再写一遍
   ...
   密钥轮换 → 改 N 个服务 → 发 N 次版 → 漏一个就全线故障

放网关后：

text
✅ 网关统一校验，下游只信任网关透传的身份
   gateway  → 校验 JWT、解析 userId、塞进请求头
   下游服务 → 直接读 x-user-id，零校验成本
维度分散鉴权网关统一鉴权
代码重复N 份1 份
密钥管理N 处配置，易泄漏只在网关持有
策略变更改 N 个服务改 1 处
下游性能每个服务都解一次 JWT下游零解析开销
风险漏改导致鉴权绕过需防止绕过网关直连下游

统一鉴权的前提：下游不能被直连

网关鉴权的全部安全性，建立在"外部流量只能经过网关"之上。如果下游服务的端口暴露在公网，攻击者直接伪造 x-user-id 请求头就能冒充任意用户。

必须做到至少一条：① 下游只监听内网网段；② K8s 里下游是 ClusterIP，不开 Ingress；③ 网关和下游之间加签名校验（见 5.3）。

5.2 JWT 校验、白名单与错误响应 ​

① JWT 工具类（基于 jjwt）：

java
@Component
public class JwtUtil {

    /** 生产上从配置中心读，不要硬编码 */
    @Value("${jwt.secret}")
    private String secret;

    private Key key;

    @PostConstruct
    public void init() {
        this.key = Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
    }

    public String create(Long userId, String username, long ttlMillis) {
        return Jwts.builder()
                .setSubject(String.valueOf(userId))
                .claim("username", username)
                .setIssuedAt(new Date())
                .setExpiration(new Date(System.currentTimeMillis() + ttlMillis))
                .signWith(key, SignatureAlgorithm.HS256)
                .compact();
    }

    /** 解析失败统一抛异常，由调用方转成 401 */
    public Claims parse(String token) {
        return Jwts.parserBuilder()
                .setSigningKey(key)
                .build()
                .parseClaimsJws(token)
                .getBody();
    }
}

② 鉴权全局过滤器：

java
@Component
public class AuthGlobalFilter implements GlobalFilter, Ordered {

    @Autowired
    private JwtUtil jwtUtil;

    /** 白名单：登录、注册、健康检查、静态资源 */
    private static final List<String> WHITE_LIST = Arrays.asList(
            "/api/auth/login",
            "/api/auth/register",
            "/actuator/**",
            "/**/*.html",
            "/**/*.js"
    );

    private static final AntPathMatcher MATCHER = new AntPathMatcher();

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        ServerHttpRequest request = exchange.getRequest();
        String path = request.getPath().value();

        // ① CORS 预检请求直接放行（OPTIONS 不带 token）
        if (HttpMethod.OPTIONS.equals(request.getMethod())) {
            return chain.filter(exchange);
        }

        // ② 白名单放行
        if (WHITE_LIST.stream().anyMatch(p -> MATCHER.match(p, path))) {
            return chain.filter(exchange);
        }

        // ③ 取 token
        String token = request.getHeaders().getFirst("Authorization");
        if (!StringUtils.hasText(token)) {
            return unauthorized(exchange, 401, "未登录");
        }
        if (token.startsWith("Bearer ")) {
            token = token.substring(7);
        }

        // ④ 校验并透传身份
        try {
            Claims claims = jwtUtil.parse(token);
            ServerHttpRequest newRequest = request.mutate()
                    .header("x-user-id", claims.getSubject())
                    .header("x-user-name", claims.get("username", String.class))
                    .build();
            return chain.filter(exchange.mutate().request(newRequest).build());
        } catch (ExpiredJwtException e) {
            return unauthorized(exchange, 401, "登录已过期");
        } catch (JwtException e) {
            return unauthorized(exchange, 401, "无效的凭证");
        }
    }

    /** 返回 JSON 错误体，而不是空白的 401 */
    private Mono<Void> unauthorized(ServerWebExchange exchange, int code, String msg) {
        ServerHttpResponse response = exchange.getResponse();
        response.setStatusCode(HttpStatus.UNAUTHORIZED);
        response.getHeaders().setContentType(MediaType.APPLICATION_JSON);
        String body = String.format("{\"code\":%d,\"message\":\"%s\"}", code, msg);
        DataBuffer buffer = response.bufferFactory()
                .wrap(body.getBytes(StandardCharsets.UTF_8));
        return response.writeWith(Mono.just(buffer));
    }

    @Override
    public int getOrder() {
        return -100; // 尽量早，但要晚于链路追踪
    }
}

白名单的两个坑

① 用 startsWith 代替 Ant 匹配。 path.startsWith("/api/auth") 会把 /api/authorization-bypass 也放行。必须用 AntPathMatcher。

② 忘记放行 OPTIONS。 浏览器跨域预检请求不带 Authorization，被 401 后前端会报 CORS 错误，而不是 401，排查方向容易跑偏。

① 入口清洗（必做，成本最低）

② 网络隔离（推荐）

③ 签名校验（金融等高安全场景）

📌 单独澄清：request.mutate().header() 是追加还是覆盖？

是覆盖。ServerHttpRequest.Builder#header(name, values...) 内部调用的是 HttpHeaders#put，同名 header 的旧值会被整体替换。如果想追加，要用 headers(h -> h.add(name, value))。这点刚好帮我们挡住了伪造——但前提是鉴权过滤器一定会执行到（白名单路径就不会）。

白名单路径是伪造的突破口

白名单请求（如 /api/auth/login）不走 JWT 校验，鉴权过滤器直接 chain.filter() 放行，不会覆盖 x-user-id。如果某个白名单接口的下游又去读了 x-user-id，就被绕过了。所以入口清洗（方案 ①）必须独立于鉴权逻辑。

6.1 RequestRateLimiter 与 Redis 令牌桶 ​

① 依赖：

xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis-reactive</artifactId>
</dependency>

必须是 reactive 版本

用普通的 spring-boot-starter-data-redis（Lettuce 同步 API）会在事件循环线程上阻塞，等于把网关的异步优势毁掉。限流本身就在请求主路径上，阻塞影响最直接。

② 配置：

yaml
spring:
  redis:
    host: localhost
    port: 6379
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://orderservice
          predicates:
            - Path=/order/**
          filters:
            - name: RequestRateLimiter
              args:
                key-resolver: "#{@ipKeyResolver}" # SpEL 引用 Bean
                redis-rate-limiter.replenishRate: 10 # 每秒放 10 个令牌
                redis-rate-limiter.burstCapacity: 20 # 桶容量 20，可应对突发
                redis-rate-limiter.requestedTokens: 1 # 每个请求消耗 1 个

③ 三个参数的关系（令牌桶模型）：

text
            ┌──────────────────┐
  每秒补 10 │                  │  burstCapacity = 20（桶最多装 20 个）
  ─────────▶│   ● ● ● ● ●      │
            │   ● ● ● ●        │
            └────────┬─────────┘
                     │ 每个请求取 requestedTokens 个
                     ▼
            有令牌 → 放行
            没令牌 → 429 Too Many Requests

稳态速率 = replenishRate = 10 QPS
瞬时峰值 = burstCapacity = 20（桶满时一次性放 20 个）
参数含义怎么定
replenishRate稳态 QPS压测出的下游安全水位 × 0.8
burstCapacity允许的瞬时峰值一般是 replenishRate 的 1.5~2 倍
requestedTokens单请求权重重接口可设大值（如查报表设 5）

④ 自定义 429 响应：

默认只返回空白的 429，前端拿不到提示。可以加一个全局过滤器包装：

java
@Component
public class RateLimitResponseFilter implements GlobalFilter, Ordered {
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        ServerHttpResponse response = exchange.getResponse();
        response.beforeCommit(() -> {
            if (HttpStatus.TOO_MANY_REQUESTS.equals(response.getStatusCode())) {
                response.getHeaders().add("X-RateLimit-Hint", "too many requests");
            }
            return Mono.empty();
        });
        return chain.filter(exchange);
    }

    @Override
    public int getOrder() {
        return -2;
    }
}

6.2 KeyResolver 设计：按 IP / 用户 / 接口 ​

KeyResolver 决定"按什么维度限流"，返回的 key 就是 Redis 里令牌桶的标识。

① 按 IP（防爬虫、防刷）：

java
@Bean
public KeyResolver ipKeyResolver() {
    return exchange -> {
        // ★ 有 Nginx/SLB 时必须读 X-Forwarded-For，否则拿到的全是 LB 的 IP
        String xff = exchange.getRequest().getHeaders().getFirst("X-Forwarded-For");
        if (StringUtils.hasText(xff)) {
            return Mono.just(xff.split(",")[0].trim());
        }
        return Mono.just(Objects.requireNonNull(
                exchange.getRequest().getRemoteAddress()).getHostString());
    };
}

② 按用户（防单账号滥用）：

java
@Bean
public KeyResolver userKeyResolver() {
    return exchange -> {
        String userId = exchange.getRequest().getHeaders().getFirst("x-user-id");
        // 未登录用户归到一个桶，或降级成按 IP
        return Mono.just(StringUtils.hasText(userId) ? userId : "anonymous");
    };
}

③ 按接口（保护特定慢接口）：

java
@Bean
public KeyResolver apiKeyResolver() {
    return exchange -> Mono.just(exchange.getRequest().getPath().value());
}

④ 组合维度（最实用）：

java
@Bean
public KeyResolver userApiKeyResolver() {
    return exchange -> {
        String userId = Optional.ofNullable(
                exchange.getRequest().getHeaders().getFirst("x-user-id"))
                .orElse("anonymous");
        String path = exchange.getRequest().getPath().value();
        return Mono.just(userId + ":" + path);
    };
}

选型对照：

维度防什么风险
IP爬虫、脚本刷接口公司出口 NAT 下多人共用 IP，会误伤
用户单账号滥用未登录流量全挤一个桶
接口慢接口拖垮下游粒度太粗，一个用户能占满配额

两个高频错误

① KeyResolver 返回 Mono.empty()。 此时 Gateway 会直接拒绝请求（403），而不是放行。未登录场景一定要给默认值。

② yml 里 key-resolver 写错 Bean 名。 #{@ipKeyResolver} 里的名字必须和 @Bean 方法名一致，写错不会启动报错，而是运行时限流不生效（静默失败）。

6.4 跨域配置与重复响应头问题 ​

① 推荐配置（yml 全局）：

yaml
spring:
  cloud:
    gateway:
      globalcors:
        add-to-simple-url-handler-mapping: true # ★ 解决 OPTIONS 被拦
        cors-configurations:
          "[/**]":
            allowedOriginPatterns: # Spring 5.3+ 用这个，不要用 allowedOrigins
              - "https://*.jd.com"
              - "http://localhost:*"
            allowedMethods:
              - GET
              - POST
              - PUT
              - DELETE
              - OPTIONS
            allowedHeaders: "*"
            allowCredentials: true
            maxAge: 3600 # 预检结果缓存 1 小时，减少 OPTIONS 请求

allowedOrigins: "*" + allowCredentials: true 会启动报错

Spring 5.3 之后这是非法组合，错误信息是 When allowCredentials is true, allowedOrigins cannot contain the special value "*"。解法是改用 allowedOriginPatterns，它支持通配符且能和凭证共存。

② 最高频问题：响应头重复

text
现象：浏览器报
  The 'Access-Control-Allow-Origin' header contains multiple values
  'https://a.jd.com, https://a.jd.com', but only one is allowed.

根因：网关加了一次，下游服务（@CrossOrigin 或自己的 CorsFilter）又加了一次。

text
   浏览器 ──▶ 网关（加 ACAO）──▶ 下游（又加 ACAO）
                                     │
            响应头里出现两个 ◀────────┘

三种解法（按推荐度）：

解法做法评价
下游移除跨域配置（推荐）删掉 @CrossOrigin 和下游的 CorsFilter根治，职责清晰
网关去重DedupeResponseHeader兜底，改不动下游时用
只在下游做跨域网关不配 globalcors退化成每个服务都要配

去重配置：

yaml
spring:
  cloud:
    gateway:
      default-filters:
        - DedupeResponseHeader=Access-Control-Allow-Origin Access-Control-Allow-Credentials, RETAIN_FIRST

RETAIN_FIRST（保留第一个，默认）/ RETAIN_LAST（保留最后一个）/ RETAIN_UNIQUE（去重保留所有不同值）。

📌 单独澄清：add-to-simple-url-handler-mapping 到底干什么？

WebFlux 里 OPTIONS 预检请求在找不到对应 handler 时会被 SimpleUrlHandlerMapping 处理，而它默认没有 CORS 配置，导致预检被拒。开启这个开关后，globalcors 的配置会被同步注册给它。症状是：普通请求跨域正常，但带自定义 header 的请求全挂（因为只有后者会触发预检）。

6.5 超时、重试与熔断降级 ​

① 超时配置（最容易被忽略的生产配置）：

yaml
spring:
  cloud:
    gateway:
      httpclient:
        connect-timeout: 2000 # 建连超时，单位 ms（注意是 int）
        response-timeout: 5s # 响应超时，单位是 Duration
      routes:
        - id: slow-service
          uri: lb://slowservice
          predicates:
            - Path=/report/**
          metadata:
            connect-timeout: 3000 # 路由级覆盖全局
            response-timeout: 30000 # 注意：metadata 里单位是 ms 的 long

不配超时 = 等死

默认 response-timeout 为空（不超时）。下游 hang 住时，网关的连接会一直占着，Netty 的连接池很快被耗尽，一个慢服务可以拖垮整个网关。这是最典型的"网关雪崩"路径。

生产上必须配，且 response-timeout 要大于下游自己的业务超时，否则网关先断，下游还在跑，产生资源浪费和数据不一致。

② 重试：

yaml
filters:
  - name: Retry
    args:
      retries: 2 # 重试次数
      series: SERVER_ERROR # 只对 5xx 重试
      methods: GET # ★ 只对幂等方法重试
      exceptions:
        - java.io.IOException
        - java.util.concurrent.TimeoutException
      backoff:
        firstBackoff: 50ms
        maxBackoff: 500ms
        factor: 2
        basedOnPreviousValue: false

❌ 危险配置：

yaml
- name: Retry
  args:
    retries: 3
    methods: GET,POST # ❌ POST 重试会造成重复下单、重复扣款

重试三原则：

text
1. 只重试幂等方法（GET / HEAD / OPTIONS）
2. 只重试「确定没到达下游」的错误（连接超时、ConnectException）
   响应超时不要重试 —— 下游可能已经执行成功了
3. 必须配退避（backoff），否则下游抖动时重试风暴会把它彻底打死

③ 熔断降级（Resilience4j）：

xml

    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-circuitbreaker-reactor-resilience4j</artifactId>
</dependency>
yaml

    args:
      name: orderCircuitBreaker
      fallbackUri: forward:/fallback/order # 降级到网关内部接口
java
@RestController
public class FallbackController {

    @RequestMapping("/fallback/order")
    public Mono<Map<String, Object>> orderFallback() {
        Map<String, Object> result = new HashMap<>();
        result.put("code", 503);
        result.put("message", "订单服务暂时不可用，请稍后重试");
        return Mono.just(result);
    }
}

fallback 接口不能定义在 @RestController 里？

能，但必须是响应式返回值（Mono / Flux），不能返回普通对象后阻塞。另外 fallbackUri 只支持 forward: 协议，写成 http:// 不生效。

三者的配合关系：

text
请求 ──▶ 超时（兜底时间上限）
          │ 超时/5xx
          ▼
        重试（给瞬时抖动一次机会，仅幂等）
          │ 连续失败
          ▼
        熔断（打开后直接走 fallback，不再打下游）
          │
          ▼
        降级响应（友好提示，而不是 500）

@Component
public class AccessLogFilter implements GlobalFilter, Ordered {

    private static final Logger log = LoggerFactory.getLogger("ACCESS");

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        long start = System.currentTimeMillis();
        ServerHttpRequest req = exchange.getRequest();
        String traceId = UUID.randomUUID().toString().replace("-", "");

        // 透传给下游，并放进 exchange 供后续过滤器使用
        ServerHttpRequest newReq = req.mutate()
                .header("x-trace-id", traceId).build();
        exchange.getAttributes().put("traceId", traceId);

        return chain.filter(exchange.mutate().request(newReq).build())
                .doFinally(signal -> {
                    Route route = exchange.getAttribute(
                            ServerWebExchangeUtils.GATEWAY_ROUTE_ATTR);
                    log.info("traceId={} {} {} route={} status={} cost={}ms",
                            traceId,
                            req.getMethod(),
                            req.getURI().getRawPath(),
                            route == null ? "-" : route.getId(),
                            exchange.getResponse().getStatusCode(),
                            System.currentTimeMillis() - start);
                });
    }

    @Override
    public int getOrder() {
        return Ordered.HIGHEST_PRECEDENCE; // 最早执行，覆盖全链路
    }
}

7.4 灰度发布与多版本路由 ​

① 基于 Weight 断言的流量比例分配（最简单）：

yaml
routes:
  - id: order-v1
    uri: lb://orderservice-v1
    predicates:
      - Path=/order/**
      - Weight=order-group, 9 # 90% 流量
  - id: order-v2
    uri: lb://orderservice-v2
    predicates:
      - Path=/order/**
      - Weight=order-group, 1 # 10% 流量

同一个 group 内按权重比例分配。缺点：同一个用户多次请求可能落到不同版本，有状态场景会出问题。

② 基于请求头的定向灰度（可控性最好）：

yaml
routes:
  - id: order-gray
    uri: lb://orderservice
    order: 1
    predicates:
      - Path=/order/**
      - Header=x-gray, true # 带灰度标的走新版本
    metadata:
      version: v2
  - id: order-stable
    uri: lb://orderservice
    order: 10
    predicates:
      - Path=/order/**

③ 基于用户 ID 的稳定灰度（生产最常用）：

在网关里按用户 ID 哈希决定版本，保证同一用户始终落在同一版本：

java
@Component
public class GrayGlobalFilter implements GlobalFilter, Ordered {

    /** 灰度比例，从配置中心动态读取 */
    @Value("${gray.percent:0}")
    private int grayPercent;

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String userId = exchange.getRequest().getHeaders().getFirst("x-user-id");
        if (StringUtils.hasText(userId)) {
            // 同一用户哈希值固定 → 始终落在同一版本
            int bucket = Math.abs(userId.hashCode() % 100);
            if (bucket < grayPercent) {
                ServerHttpRequest req = exchange.getRequest().mutate()
                        .header("x-version", "v2").build();
                return chain.filter(exchange.mutate().request(req).build());
            }
        }
        return chain.filter(exchange);
    }

    @Override
    public int getOrder() {
        return -50; // 晚于鉴权（需要 x-user-id），早于路由转发
    }
}

配合自定义负载均衡器，按 x-version 筛选 Nacos 实例的 metadata：

yaml
# 新版本服务的注册配置
spring:
  cloud:
    nacos:
      discovery:
        metadata:
          version: v2

三种方案对照：

方案用户体验一致性可控性实现成本适用场景
Weight差（会跳版本）只能调比例最低无状态只读接口
Header好精确到人低内测、白名单验证

灰度必须配套的两件事

① 可快速回滚。 灰度比例必须放在配置中心，能秒级改成 0，而不是改代码重新发版。

② 链路要打标。 灰度请求的 traceId 要带版本标记，否则出问题时无法区分是新版本的锅还是老版本的。

8.3 面试高频问答 ​

Q1：Spring Cloud Gateway 和 Zuul 1.x 的本质区别？

本质是线程模型的区别。Zuul 1.x 基于 Servlet 阻塞模型，一个请求占一个线程，线程数决定并发上限，高并发下线程切换开销巨大。Gateway 基于 WebFlux + Netty 的事件循环，少量线程处理海量连接，内存占用和吞吐都明显更优。代价是编程模型变了——不能阻塞、不能用 ThreadLocal，学习成本更高。

Q2：一次请求在 Gateway 内部的完整流程？

Netty 收到请求封装成 ServerWebExchange → DispatcherHandler 交给 RoutePredicateHandlerMapping 做路由匹配 → 匹配到的 Route 存入 exchange → FilteringWebHandler 把全局过滤器和该路由的局部过滤器合并排序成一条链 → 依次执行前置逻辑 → 末端的 NettyRoutingFilter 发起真实调用 → 逆序执行后置逻辑 → NettyWriteResponseFilter 写回客户端。

Q3：GlobalFilter 和 GatewayFilter 的区别？执行顺序怎么定？

作用范围不同：GlobalFilter 对所有路由生效、加 @Component 即可、不支持参数；GatewayFilter 只对配置了它的路由生效、通过 AbstractGatewayFilterFactory 支持传参。

执行顺序上，两者会被合并到同一条链里统一按 order 排序，不存在"全局一定先于局部"。order 越小前置越早执行，后置则逆序。

Q4：为什么在过滤器里读了请求体，下游就收不到了？

请求体是 Flux<DataBuffer>，是只能被消费一次的数据流。你读完后流就空了，NettyRoutingFilter 再去取只能拿到空内容。解决办法是用 DataBufferUtils.join 读到字节数组后，用 ServerHttpRequestDecorator 重写 getBody() 把内容重新装填回去。同时要注意 DataBufferUtils.release()，否则堆外内存泄漏。

Q5：网关怎么做鉴权？身份怎么传给下游？

写一个 GlobalFilter，按白名单放行 OPTIONS 和登录接口，其余请求校验 JWT，解析出 userId 后用 request.mutate().header("x-user-id", ...) 写进请求头透传。下游用拦截器把这个头读进 ThreadLocal。

安全前提是：下游不能被外部直连，且网关入口要用 RemoveRequestHeader 清洗外部传入的同名头，防止伪造。

Q6：网关限流怎么实现？和 Sentinel 怎么选？

内置的 RequestRateLimiter 基于 Redis + Lua 实现令牌桶，replenishRate 控制稳态 QPS，burstCapacity 控制瞬时峰值，KeyResolver 决定限流维度。

内置方案规则静态、无监控；Sentinel 支持规则动态下发、多种流控算法和可视化控制台。只要有 Redis 又只需简单防刷，用内置的；要动态调规则、看监控、做熔断降级一体化，用 Sentinel。

Q7：为什么 Gateway 不能引入 spring-boot-starter-web？

Gateway 依赖 WebFlux 的 ReactiveWebServerApplicationContext。引入 web starter 后，Spring Boot 检测到 Spring MVC 在 classpath 上会优先创建 Servlet 容器（Tomcat），导致 Gateway 的自动配置不生效，启动时直接抛异常。

Q8：网关里能用 ThreadLocal 吗？不能的话用什么替代？

不能。WebFlux 下一个请求的不同阶段可能在不同的事件循环线程上执行，ThreadLocal 会取不到值甚至串数据。替代方案有两个：请求级数据用 exchange.getAttributes()（一个请求内共享的 Map）；需要跨响应式操作符传递时用 Reactor 的 contextWrite / Mono.deferContextual。

Q9：动态路由怎么做？刷新后不生效是什么原因？

常见做法是把路由规则存到 Nacos，监听配置变更后通过 RouteDefinitionWriter 增删路由。不生效最常见的原因是忘记发布 RefreshRoutesEvent —— CachingRouteLocator 缓存了路由列表，不发事件不会重新加载。另一个坑是只 save 不 delete，导致废弃路由残留。

Q10：网关的性能瓶颈通常在哪？

按出现频率排：① 过滤器里有阻塞调用（查库、同步 Redis、RestTemplate），直接堵死事件循环线程；② httpclient 连接池太小（默认值很低），请求排队等连接；③ 堆外内存泄漏，DataBuffer 没 release；④ 日志同步写盘或打了完整请求体；⑤ 没配超时，一个慢下游拖垮整个网关。

Q11：Gateway 和 Nginx 的关系，为什么两个都要？

不是替代关系，是分层关系。Nginx 在最外层做四层负载、SSL 卸载、静态资源、IP 限速，这些 C 实现的性能远好于 JVM；Gateway 在内层做和业务强相关的七层逻辑——鉴权、动态路由、灰度、服务发现集成。Nginx 不认识服务名，做不了 lb://；Gateway 做 SSL 卸载又太浪费。

Q12：如何保证网关自身高可用？

① 多实例部署，前面挂 Nginx/SLB 做流量分发；② 网关无状态，不存 session，任意实例可处理任意请求；③ 配置优雅停机 + 发布前摘流量，避免发版 502；④ 对下游配超时 + 熔断，防止被慢服务拖死；⑤ 完善监控告警，网关指标必须是最高优先级。
