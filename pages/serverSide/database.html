一、基础入门篇 ​

为什么需要数据库 ​

核心概念

数据库（Database） 是按照数据结构来组织、存储和管理数据的仓库；数据库管理系统（DBMS） 是操作和管理数据库的软件，MySQL 就是一款 DBMS。

写代码时数据可以放在变量、集合里，但程序一结束数据就没了。把数据写进文件可以持久化，但一旦数据量变大，"按条件查询""并发修改""保证一致性"这三件事会立刻变得难以处理。

存储方式持久化按条件查询并发安全适用规模
内存集合❌ 进程结束即丢失需手写遍历需自己加锁极小
普通文件✅❌ 只能全文扫描❌ 容易写坏小
数据库✅✅ 索引加速✅ 事务 + 锁中到大

所以数据库解决的不是"能不能存"，而是存了之后能不能又快又安全地用起来。

关系型与非关系型

  • 关系型数据库（RDBMS）：数据存在二维表中，表之间可以建立关系，支持 SQL 和事务。代表：MySQL、PostgreSQL、Oracle。
  • 非关系型数据库（NoSQL）：键值、文档、列族、图等模型，牺牲部分一致性换取扩展性和性能。代表：Redis、MongoDB、HBase。

实际项目里两者是配合关系，不是替代关系：MySQL 存核心业务数据保证一致性，Redis 做缓存扛读流量。

SQL 分类与书写规范 ​

SQL（Structured Query Language）是操作关系型数据库的通用语言，按职责分为五类：

分类全称常用关键字作用
DDLData Definition LanguageCREATE ALTER DROP TRUNCATE定义数据库对象（库、表、列、索引）
DMLData Manipulation LanguageINSERT UPDATE DELETE操作表中的数据
DQLData Query LanguageSELECT查询数据
DCLData Control LanguageGRANT REVOKE CREATE USER用户与权限管理
TCLTransaction Control LanguageSTART TRANSACTION COMMIT ROLLBACK事务控制

容易混淆：DDL 与 DML 的区别到底是什么

很多人把"删数据"和"删表"都理解成"删除操作"，但二者本质不同：

  • DDL 改的是"结构"：DROP TABLE 删掉的是表这个对象本身，表结构和数据一起消失。
  • DML 改的是"数据"：DELETE FROM 删掉的是表里的行，表结构仍然存在。

更关键的区别是：DDL 在 MySQL 中会隐式提交事务，执行后无法回滚；DML 在事务中可以 ROLLBACK。

sql
-- ❌ 错误认知：以为 DDL 也能回滚
START TRANSACTION;
DROP TABLE `product`;   -- 这一句会隐式提交，表已经没了
ROLLBACK;               -- 回滚无效，表回不来

-- ✅ 正确：DML 在事务中可以回滚
START TRANSACTION;
DELETE FROM `product` WHERE `pid` = 1;
ROLLBACK;               -- 数据恢复

书写规范

SQL 关键字不区分大小写，但工程实践中建议：

sql
-- ✅ 推荐：关键字大写、库表字段小写、一行一个子句
SELECT `pid`, `pname`, `price`
FROM `product`
WHERE `price` > 1000
ORDER BY `price` DESC;

-- ❌ 不推荐：全部挤在一行，大小写混乱
select PID,pname,Price from product where price>1000 order by Price desc;
规范说明
关键字大写与业务字段形成视觉区分
一条 SQL 一个职责便于排错、审计和回滚
注释用 -- 或 /* */-- 后必须有空格
字符串与日期用单引号MySQL 中双引号可用但不是标准写法
反引号包裹标识符避免与关键字冲突（如字段名叫 order）

标准 SQL 与 MySQL 方言

MySQL 遵循 SQL 标准，但也有自己的方言。例如分页的 LIMIT 是 MySQL/PostgreSQL 写法，Oracle 用 ROWNUM，SQL Server 用 TOP。写跨库兼容的 SQL 时要留意这些差异。

常用字段类型速查 ​

数值类型

类型字节有符号范围典型场景
TINYINT1-128 ~ 127状态位、是否删除
SMALLINT2-32768 ~ 32767较小计数值
MEDIUMINT3约 ±838 万中等计数

BIGINT8约 ±922 亿亿大数据量主键、流水号

DOUBLE8近似小数非金额统计

为什么金额必须用 DECIMAL

FLOAT / DOUBLE 是二进制浮点数，无法精确表示 0.1 这类十进制小数，累加会产生误差；DECIMAL 是定点数，按十进制精确存储。

sql
CREATE TABLE `t_money`(
  `d` DOUBLE,
  `dec` DECIMAL(10,2)
);
INSERT INTO `t_money` VALUES (0.1, 0.1), (0.2, 0.2);

-- ❌ DOUBLE 求和出现误差
SELECT SUM(`d`) FROM `t_money`;     -- 0.30000000000000004

-- ✅ DECIMAL 精确
SELECT SUM(`dec`) FROM `t_money`;   -- 0.30

只要是钱、折扣率、积分这类不能有误差的值，一律 DECIMAL。

字符串类型

类型说明典型场景
CHAR(n)定长，不足补空格，取出时去掉尾部空格固定长度编码（如性别 CHAR(1)）
VARCHAR(n)变长，额外用 1~2 字节记录长度名称、手机号
TEXT长文本，最大 64KB描述、备注
LONGTEXT超长文本，最大 4GB文章正文
BINARY(n)定长二进制固定长度二进制标记
VARBINARY(n)变长二进制二进制协议数据
BLOB二进制大对象小图片、文件内容
ENUM枚举，只能取定义内的值固定状态集合

CHAR 还是 VARCHAR

  • 长度固定且确定（身份证 18 位、MD5 32 位）→ CHAR，不需要额外长度字节，查询略快。
  • 长度不固定 → VARCHAR，省空间。
  • VARCHAR(50) 中的 50 是字符数不是字节数（MySQL 4.1+），utf8mb4 下一个汉字算 1 个字符、占 4 字节。

日期时间类型

类型格式范围受时区影响
DATEYYYY-MM-DD1000-01-01 ~ 9999-12-31❌
TIMEHH:MM:SS-838:59:59 ~ 838:59:59❌
YEARYYYY1901 ~ 2155❌
DATETIMEYYYY-MM-DD HH:MM:SS1000 ~ 9999 年❌
TIMESTAMPYYYY-MM-DD HH:MM:SS1970 ~ 2038 年✅

DATETIME 与 TIMESTAMP 的真正区别

二者看起来一样，但存的东西不一样：

  • DATETIME 存的是字面值，你写什么存什么，取出来还是什么，与时区无关。
  • TIMESTAMP 存的是从 1970-01-01 UTC 起的秒数，写入时按当前会话时区转成 UTC，读取时再转回会话时区。

这意味着：同一条 TIMESTAMP 数据，北京的连接看到 12:00:00，东京的连接会看到 13:00:00；而 DATETIME 两边都是 12:00:00。

需求选型
记录"事件发生的绝对时刻"，需跨时区展示TIMESTAMP
记录"业务日历时间"（生日、排班、合同日期）DATETIME
数据会存到 2038 年以后DATETIME（TIMESTAMP 有 2038 问题）

字段设计建议

  • 长度按业务上限设计，避免盲目 VARCHAR(255)，联合索引长度有 3072 字节限制。
  • 核心字段配 NOT NULL + DEFAULT，NULL 会让索引统计和 = 判断变复杂。
  • 状态字段必须加注释说明枚举含义：COMMENT '0=禁用,1=启用'。
  • BOOLEAN / BOOL 在 MySQL 中只是 TINYINT(1) 的别名，没有真正的布尔类型。

字符集与排序规则 ​

核心概念

字符集（Character Set） 决定"用什么编码存储字符"；排序规则（Collation） 决定"字符之间如何比较和排序"。两者总是配套出现。

配置项建议值说明
数据库字符集utf8mb4完整 UTF-8，兼容 emoji 与生僻字
排序规则utf8mb4_general_ci / utf8mb4_0900_ai_cici = case insensitive，大小写不敏感
连接字符集与库表保持一致防止插入/查询乱码

别再用 utf8 了：utf8 不是真正的 UTF-8

MySQL 里的 utf8实际是 utf8mb3，每个字符最多 3 字节，而标准 UTF-8 的 emoji、部分生僻汉字需要 4 字节。

sql
-- ❌ utf8（mb3）存 emoji 会报错或存成 ???
CREATE TABLE `t_bad`(`c` VARCHAR(10)) CHARSET utf8mb3;
INSERT INTO `t_bad` VALUES ('😀');
-- ERROR 1366: Incorrect string value

-- ✅ utf8mb4 正常
CREATE TABLE `t_ok`(`c` VARCHAR(10)) CHARSET utf8mb4;
INSERT INTO `t_ok` VALUES ('😀');   -- OK

新项目一律 utf8mb4，MySQL 8.0 默认字符集已经是 utf8mb4。

sql
-- 查看字符集与排序规则
SHOW VARIABLES LIKE 'character_%';
SHOW VARIABLES LIKE 'collation_%';

-- 查看某个库的字符集
SHOW CREATE DATABASE `mytest01`;
sql
-- 创建数据库时指定字符集与排序规则
CREATE DATABASE `mytest01`
CHARACTER SET utf8mb4
COLLATE utf8mb4_general_ci;
sql
-- 修改表字符集（会转换已有数据）
ALTER TABLE `product`
CONVERT TO CHARACTER SET utf8mb4
COLLATE utf8mb4_general_ci;
sql
-- 会话级临时设置（仅当前连接生效）
SET NAMES utf8mb4;

排序规则后缀含义

后缀含义示例效果
_cicase insensitive，不区分大小写'ABC' = 'abc' 为真
_cscase sensitive，区分大小写'ABC' = 'abc' 为假
_bin按二进制逐字节比较严格区分大小写和重音
_aiaccent insensitive，不区分重音'é' = 'e' 为真
_asaccent sensitive，区分重音'é' = 'e' 为假

一般业务用 _ci；需要区分大小写的字段（如密码哈希、Token）用 _bin。

三、DML 数据操作篇 ​

插入数据 ​

核心概念

DML（Data Manipulation Language）操作的是表里的数据，而不是表结构本身。 DML 语句在 InnoDB 下是可以回滚的，这点和 DDL 完全不同。

sql
-- 1. 全字段插入：必须按建表顺序给齐所有列
INSERT INTO `product` VALUES (NULL, '耳机', 199.00, 1, NOW(), NOW());

-- 2. 指定字段插入（推荐）：不受列顺序和新增列影响
INSERT INTO `product` (`pname`, `price`, `status`)
VALUES ('键盘', 299.00, 1);

-- 3. 批量插入：一条 SQL 插多行，性能远高于循环单条插入
INSERT INTO `product` (`pname`, `price`, `status`) VALUES
  ('鼠标',  89.00, 1),
  ('显示器', 1299.00, 1),
  ('支架',  59.00, 0);

-- 4. 查询结果插入：做数据迁移、归档时常用
INSERT INTO `product_archive` (`pname`, `price`)
SELECT `pname`, `price` FROM `product` WHERE `status` = 0;

为什么推荐"指定字段插入"

  • 不依赖列顺序，表结构调整后 SQL 不会错位。
  • 新增一个有默认值的列时，老代码不用改。
  • 可读性更好，Code Review 时能直接看出写了哪些字段。

主键冲突的三种处理方式，面试高频：

sql
-- ① 忽略：冲突就跳过，不报错（但会丢失自增值）
INSERT IGNORE INTO `product` (`pid`, `pname`) VALUES (1, '耳机');

-- ② 冲突则更新（推荐的"插入或更新"写法）
INSERT INTO `product` (`pid`, `pname`, `price`) VALUES (1, '耳机', 199.00)
ON DUPLICATE KEY UPDATE `pname` = VALUES(`pname`), `price` = VALUES(`price`);

-- ③ 替换：先删后插（危险）
REPLACE INTO `product` (`pid`, `pname`) VALUES (1, '耳机');
写法冲突时行为未冲突字段副作用
INSERT IGNORE跳过该行不变其他错误（如字段超长）也会被吞成 warning
ON DUPLICATE KEY执行 UPDATE保留原值推荐；返回受影响行数为 2 表示发生了更新
REPLACE INTODELETE + INSERT被重置为默认值触发删除触发器、外键级联删除，自增 ID 会变化

REPLACE INTO 的坑

REPLACE 本质是"删一行再插一行"。如果只传了部分字段，其余字段会被重置为默认值，而不是保留原值；同时该行的 created_at 等信息也会丢失。除非明确需要整行覆盖，否则请用 ON DUPLICATE KEY UPDATE。

更新数据 ​

sql
-- 基本语法
UPDATE 表名 SET 列1 = 值1, 列2 = 值2 [WHERE 条件];

-- 1. 更新单行
UPDATE `product` SET `price` = 159.00 WHERE `pid` = 1;

-- 2. 基于原值更新（涨价 10%）
UPDATE `product` SET `price` = `price` * 1.1 WHERE `status` = 1;

-- 3. 一次更新多个字段
UPDATE `product`
SET `pname` = '无线鼠标', `price` = 129.00, `status` = 1
WHERE `pid` = 3;

-- 4. 限制影响行数（配合排序，常用于灰度/分批处理）
UPDATE `product` SET `status` = 0
WHERE `status` = 1
ORDER BY `pid` ASC
LIMIT 100;

不带 WHERE 的 UPDATE 是生产事故

UPDATE product SET price = 0; 会把全表价格清零。防护手段：

  1. 客户端加 --safe-updates（又名 -U）：没有 WHERE 或 LIMIT 的 UPDATE/DELETE 直接报错。
  2. 执行前先把同样的条件改成 SELECT COUNT(*) 跑一遍，确认行数。
  3. 先开显式事务：BEGIN; → 执行 → 检查行数 → COMMIT; 或 ROLLBACK;。

多表关联更新：用一张表的数据去更新另一张表，比子查询更高效。

sql
-- 把订单表里的商品名同步成商品表的最新名称
UPDATE `orders` o
JOIN `product` p ON o.`pid` = p.`pid`
SET o.`pname` = p.`pname`
WHERE o.`created_at` > '2024-01-01';

MySQL 不允许"边查边改同一张表"

下面这种写法会报 You can't specify target table 'product' for update in FROM clause：

sql
-- ❌ 错误
UPDATE `product` SET `price` = 0
WHERE `pid` = (SELECT MAX(`pid`) FROM `product`);

解决办法是用派生表包一层，强制 MySQL 先把子查询物化：

sql
-- ✅ 正确
UPDATE `product` SET `price` = 0
WHERE `pid` = (SELECT m FROM (SELECT MAX(`pid`) AS m FROM `product`) AS t);

-- TRUNCATE：清空整表，速度快

-- DROP：连表结构一起删
DROP TABLE IF EXISTS `product`;

为什么 DELETE 删完数据文件还是那么大

InnoDB 的 DELETE 只是把行标记为"已删除"，留下的空间进入"可复用空间"等待新数据填入，并不会归还给操作系统。想真正收缩文件：

sql
-- 重建表并整理碎片（会锁表 / 耗时，低峰执行）
OPTIMIZE TABLE `product`;
-- 或者等价写法
ALTER TABLE `product` ENGINE = InnoDB;

自增值的版本差异

  • MySQL 5.7 及以前：自增计数器只存在内存里，DELETE 删掉最大 ID 后重启 MySQL，自增值会回退，可能导致 ID 重复使用。
  • MySQL 8.0 起：自增计数器写入 redo log 并持久化，重启后不再回退。
  • 无论哪个版本，TRUNCATE 都会把自增值重置为 1。

约束总览 ​

核心概念

约束（Constraint）是作用在表字段上的规则，由数据库在写入时强制校验。 它的价值在于：即使应用层代码有 bug，脏数据也进不来。约束是数据正确性的最后一道防线。

约束关键字作用可否为空
主键约束PRIMARY KEY唯一标识一行，一张表只能有一个❌ 自动非空
自增AUTO_INCREMENT数值列自动递增—
非空约束NOT NULL该列必须有值❌
唯一约束UNIQUE该列值不能重复✅ 允许多个 NULL
默认约束DEFAULT未显式赋值时使用默认值—
检查约束CHECK值必须满足表达式（8.0.16+ 生效）—
外键约束FOREIGN KEY关联另一张表，保证引用完整性✅

主键与自增 ​

sql
-- 建表时声明（推荐：独立 PRIMARY KEY 子句，便于扩展为联合主键）
CREATE TABLE `user` (
  `id`   BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '用户ID',
  `name` VARCHAR(50)     NOT NULL,
  PRIMARY KEY (`id`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

-- 联合主键（多对多中间表常用）
CREATE TABLE `user_role` (
  `user_id` BIGINT UNSIGNED NOT NULL,
  `role_id` INT UNSIGNED    NOT NULL,
  PRIMARY KEY (`user_id`, `role_id`)
) ENGINE = InnoDB;

-- 后期添加 / 删除主键
ALTER TABLE `user` ADD PRIMARY KEY (`id`);
ALTER TABLE `user` DROP PRIMARY KEY;

-- 指定自增起始值
ALTER TABLE `user` AUTO_INCREMENT = 10000;

为什么强烈建议主键用自增整型

InnoDB 是聚簇索引结构，数据按主键顺序物理存放：

  • 自增主键：新数据总是追加在 B+Tree 最右侧，很少发生页分裂，写入快、碎片少。
  • UUID / 随机字符串主键：插入位置随机，频繁页分裂与页移动，写放大严重；且主键长度会被所有二级索引冗余存储，索引体积暴涨。
  • 确实需要对外暴露无序 ID 时，做法是：内部自增主键 + 额外一列 biz_no 存 UUID/雪花 ID 并建唯一索引。

非空与唯一 ​

sql
CREATE TABLE `account` (
  `id`     INT UNSIGNED NOT NULL AUTO_INCREMENT,
  `phone`  CHAR(11)     NOT NULL,
  `email`  VARCHAR(100)     NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_account_phone` (`phone`),
  UNIQUE KEY `uk_account_email` (`email`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

-- 后期增删
ALTER TABLE `account` ADD UNIQUE KEY `uk_account_email` (`email`);
ALTER TABLE `account` DROP INDEX `uk_account_email`;

UNIQUE 与 NULL 的关系（高频面试点）

在 MySQL 中，NULL 表示"未知"，两个 NULL 之间不认为相等，所以唯一索引列上可以存在多行 NULL：

sql
INSERT INTO `account` (`phone`, `email`) VALUES ('13800000001', NULL); -- ✅
INSERT INTO `account` (`phone`, `email`) VALUES ('13800000002', NULL); -- ✅ 依然成功

如果业务要求"邮箱要么唯一要么不填且只能有一条空值"，必须把列设为 NOT NULL DEFAULT ''，用空串代替 NULL。

唯一约束 vs 唯一索引

二者在 MySQL 里是同一个东西：声明 UNIQUE 约束时，InnoDB 会自动创建一个唯一索引来实现它。所以唯一约束天然带来查询加速效果，删除它用的也是 DROP INDEX。

默认值与检查约束 ​

sql
CREATE TABLE `order` (
  `id`         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `amount`     DECIMAL(10,2)   NOT NULL DEFAULT 0.00,
  `status`     TINYINT         NOT NULL DEFAULT 0 COMMENT '0=待付款 1=已付款 2=已取消',
  `created_at` DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  CONSTRAINT `ck_order_amount` CHECK (`amount` >= 0)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

DEFAULT 的两个易错点

  1. 显式传 NULL 不会使用默认值。INSERT INTO order (amount) VALUES (NULL); 会直接报错（列是 NOT NULL），而不是填 0.00。只有完全不写这一列时默认值才生效。
  2. CHECK 约束在 MySQL 8.0.16 之前是"语法正确但不生效"：旧版本会解析并忽略它。如果运行在 5.7，校验逻辑必须放在应用层或触发器里。

外键约束 ​

sql
-- 建表时声明
CREATE TABLE `order_item` (
  `id`       BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `order_id` BIGINT UNSIGNED NOT NULL,
  PRIMARY KEY (`id`),
  KEY `idx_item_order` (`order_id`),
  CONSTRAINT `fk_item_order` FOREIGN KEY (`order_id`)
    REFERENCES `order` (`id`)
    ON UPDATE CASCADE
    ON DELETE RESTRICT
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

-- 后期添加 / 删除
ALTER TABLE `order_item` ADD CONSTRAINT `fk_item_order`
  FOREIGN KEY (`order_id`) REFERENCES `order` (`id`);
ALTER TABLE `order_item` DROP FOREIGN KEY `fk_item_order`;
删除/更新行为含义
RESTRICT子表仍有引用时，拒绝操作（默认行为，等价 NO ACTION）
CASCADE父表删/改，子表对应行一起删/改
SET NULL父表删/改，子表外键列置为 NULL（列必须可为空）

互联网业务为什么常常不用外键

  • 性能：每次写入都要去父表加锁校验，高并发下容易出现锁等待甚至死锁。
  • 分库分表：数据被拆到不同实例后，跨库外键根本无法建立。
  • 运维：导数据、清历史数据时必须严格按依赖顺序执行，灰度与回滚都变复杂。

取而代之的做法：逻辑外键——只存 order_id 并建普通索引，引用完整性由应用层事务保证。 内部管理系统、数据量不大且强一致要求高的场景，用外键依然是值得的。

数据库设计三范式与反范式 ​

范式要求违反时的典型表现
第一范式 1NF字段不可再分（原子性）address 里塞"省-市-区"字符串
第二范式 2NF非主键字段完全依赖整个主键联合主键表里混入只依赖部分主键的字段
第三范式 3NF非主键字段之间不能传递依赖订单表里同时存 user_id 和 user_name
3NF 反例（存在传递依赖）
┌──────────────────────────────────────────────┐
│ order(id, user_id, user_name, user_phone)    │
│   id → user_id → user_name                   │  用户改名要更新所有历史订单
└──────────────────────────────────────────────┘

拆分后
┌────────────────────┐        ┌────────────────────────────┐
│ order(id, user_id) │───────▶│ user(id, name, phone)      │
└────────────────────┘        └────────────────────────────┘

什么时候要故意"反范式"

范式减少冗余，但会带来更多 JOIN。以下场景建议冗余字段：

  • 订单需要留存下单时的快照（商品名、单价），商品后续改价不能影响历史订单——此时冗余不是违反范式，而是业务语义要求。
  • 列表页为避免每行都 JOIN 用户表，冗余一个 user_name，并通过异步任务/消息保证最终一致。

原则：先满足 3NF，再按查询压力有意识地反范式，并明确谁负责同步冗余数据。

实战建表规范 ​

sql
CREATE TABLE `t_user` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  `biz_no`      CHAR(32)        NOT NULL                COMMENT '业务编号(对外暴露)',
  `name`        VARCHAR(64)     NOT NULL DEFAULT ''     COMMENT '姓名',
  `balance`     DECIMAL(16,2)   NOT NULL DEFAULT 0.00   COMMENT '余额(元)',
  `status`      TINYINT         NOT NULL DEFAULT 1      COMMENT '1=正常 0=禁用',
  `is_deleted`  TINYINT         NOT NULL DEFAULT 0      COMMENT '逻辑删除 0=未删 1=已删',

建表检查清单

  • 表名、字段名统一小写 + 下划线，避免大小写敏感导致的跨平台问题。
  • 主键 BIGINT UNSIGNED AUTO_INCREMENT；金额必须 DECIMAL，不要用 FLOAT/DOUBLE。
  • 所有字段尽量 NOT NULL 并给 DEFAULT，减少 NULL 带来的索引与判断成本。
  • 每张表都带 created_at / updated_at，排查问题时极其有用。
  • 每个字段都写 COMMENT，表也写 COMMENT。
  • 显式指定 ENGINE = InnoDB 和 utf8mb4，不依赖服务端默认配置。

五、单表查询篇 ​

基础查询与去重 ​

示例数据

本篇统一使用 product 表（商品表）： pid 商品 ID、pname 商品名、price 价格、category 分类、stock 库存、status 状态、created_at 创建时间。

sql
-- 查询所有列（仅调试用）
SELECT * FROM `product`;

-- 查询指定列（线上代码请始终列明字段）
SELECT `pid`, `pname`, `price` FROM `product`;

-- 列起别名：AS 可省略，但建议保留以提升可读性
SELECT `pname` AS 商品名称, `price` AS 价格 FROM `product`;

-- 计算列：查询不会修改原数据
SELECT `pname`, `price`, `price` * 0.8 AS 折后价 FROM `product`;

-- 去重
SELECT DISTINCT `category` FROM `product`;

-- 多列去重：按"组合"去重，而不是分别去重
SELECT DISTINCT `category`, `status` FROM `product`;

为什么禁止线上使用 SELECT *

  • 多读无用列：大字段（TEXT/BLOB）被白拉一遍，网络和内存开销翻倍。
  • 无法用覆盖索引：即使索引里已有需要的列，* 也会强制回表。
  • 表结构变更即事故：新增列后，依赖下标取值的代码会错位。

条件查询 WHERE ​

NULL 的三值逻辑

NULL 参与任何比较运算结果都是 UNKNOWN，而不是 TRUE/FALSE：

sql
SELECT * FROM `product` WHERE `category` = NULL;    -- ❌ 永远查不到数据
SELECT * FROM `product` WHERE `category` IS NULL;   -- ✅ 正确写法

-- 更隐蔽的坑：NOT IN 遇到 NULL 会整体返回空集
SELECT * FROM `product` WHERE `pid` NOT IN (1, 2, NULL);  -- ❌ 结果一定为空

原因：pid NOT IN (1,2,NULL) 等价于 pid<>1 AND pid<>2 AND pid<>NULL，最后一项恒为 UNKNOWN，整个条件永远不成立。所以子查询用于 NOT IN 时必须排除 NULL，或改用 NOT EXISTS。

LIKE 与索引

LIKE '小%'（前缀匹配）可以用索引；LIKE '%米' 或 LIKE '%米%'（左侧通配）无法使用 B+Tree 索引，只能全表扫描。需要全文检索时请用 FULLTEXT 索引或 Elasticsearch。

排序 ORDER BY ​

sql
-- 单列排序：ASC 升序(默认)，DESC 降序
SELECT * FROM `product` ORDER BY `price` DESC;

-- 多列排序：第一列相同时才按第二列排
SELECT * FROM `product` ORDER BY `category` ASC, `price` DESC;

-- 按表达式 / 别名排序
SELECT `pname`, `price` * `stock` AS 货值 FROM `product` ORDER BY 货值 DESC;

-- 自定义顺序
SELECT * FROM `product` ORDER BY FIELD(`category`, '数码', '配件', '其他');

排序的两个注意点

  1. NULL 的位置：MySQL 中 NULL 被视为最小值，升序排在最前、降序排在最后。需要强制把 NULL 放末尾可以写 ORDER BY ISNULL(col), col。
  2. 不要用列序号排序：ORDER BY 2 这种写法在 SELECT 列调整后含义就变了，务必写列名。

AVG 与 NULL 的陷阱

假设 5 条记录中有 2 条 price 为 NULL，AVG(price) 的分母是 3 而不是 5。希望把 NULL 当 0 参与计算，需要显式处理：

sql
SELECT AVG(IFNULL(`price`, 0)) FROM `product`;

COUNT(_) 和 COUNT(1) 哪个快

在 InnoDB 中两者性能基本一致，优化器都会选择最小的可用索引来扫描，COUNT(_)还被特殊优化过，不会真的去取列值。而COUNT(列名)需要读取该列并判断是否为 NULL，反而更慢。因此**统计行数统一写COUNT(\*)**。

分组 GROUP BY 与 HAVING ​

sql
-- 按分类统计
SELECT `category`, COUNT(*) AS 数量, AVG(`price`) AS 均价
FROM `product`
WHERE `status` = 1          -- ① 分组前过滤：作用于每一行
GROUP BY `category`
HAVING AVG(`price`) > 200   -- ② 分组后过滤：作用于每一组
ORDER BY 均价 DESC;

WHERE 先把行过滤掉，参与分组的数据更少且能走索引；HAVING 要等分组算完才过滤，开销更大。

ONLY_FULL_GROUP_BY

MySQL 5.7 起默认开启 ONLY_FULL_GROUP_BY，SELECT 列表中的非聚合列必须出现在 GROUP BY 中：

sql
-- ❌ 5.7+ 直接报错；5.6 虽能执行，但 pname 取值随机、毫无意义
SELECT `category`, `pname`, COUNT(*) FROM `product` GROUP BY `category`;

-- ✅ 明确表达意图
SELECT `category`, MAX(`pname`) AS 任一商品名, COUNT(*) FROM `product` GROUP BY `category`;

正确做法是改 SQL，而不是去关闭这个 sql_mode。

分页 LIMIT ​

sql
-- LIMIT 偏移量, 行数
SELECT * FROM `product` ORDER BY `pid` LIMIT 0, 10;   -- 第 1 页
SELECT * FROM `product` ORDER BY `pid` LIMIT 10, 10;  -- 第 2 页

-- 等价写法，可读性更好
SELECT * FROM `product` ORDER BY `pid` LIMIT 10 OFFSET 10;

偏移量公式：offset = (page - 1) * pageSize

分页必须配 ORDER BY

不带 ORDER BY 的 LIMIT 返回顺序是不确定的，翻页时可能出现重复或漏数据。而且排序列的值必须唯一（通常用主键兜底）：ORDER BY created_at DESC, id DESC。

深分页性能问题

LIMIT 1000000, 10 需要先扫描并丢弃一百万行，非常慢。优化方案见索引与分页优化。

SQL 书写顺序与执行顺序 ​

sql
SELECT   DISTINCT 字段列表      -- 5
FROM     表名                   -- 1
WHERE    行级过滤条件            -- 2
GROUP BY 分组字段               -- 3
HAVING   分组后过滤条件          -- 4
ORDER BY 排序字段               -- 6
LIMIT    分页参数               -- 7
执行顺序（理解它就能解释"为什么 WHERE 里不能用 SELECT 的别名"）

FROM  →  WHERE  →  GROUP BY  →  HAVING  →  SELECT  →  ORDER BY  →  LIMIT
 ①         ②          ③           ④          ⑤           ⑥          ⑦

由执行顺序推导出的三条结论

  1. WHERE 里不能用 SELECT 的别名：WHERE（②）早于 SELECT（⑤）执行，别名此时还不存在。
  2. ORDER BY 里可以用别名：ORDER BY（⑥）晚于 SELECT（⑤）。
  3. HAVING 能用聚合函数，WHERE 不能：聚合值在 GROUP BY（③）之后才产生。

内连接与外连接 ​

sql
-- ❌ 笛卡尔积：没有连接条件，结果是 m × n 行
SELECT * FROM `emp`, `dept`;

-- ✅ 隐式内连接（SQL92，老写法）
SELECT e.`name`, d.`dname`
FROM `emp` e, `dept` d
WHERE e.`dept_id` = d.`id`;

-- ✅ 显式内连接（SQL99，推荐）
SELECT e.`name`, d.`dname`
FROM `emp` e
INNER JOIN `dept` d ON e.`dept_id` = d.`id`;

-- 左外连接：保留左表全部行，右表无匹配补 NULL
SELECT e.`name`, d.`dname`
FROM `emp` e
LEFT JOIN `dept` d ON e.`dept_id` = d.`id`;

-- 右外连接：保留右表全部行
SELECT e.`name`, d.`dname`
FROM `emp` e
RIGHT JOIN `dept` d ON e.`dept_id` = d.`id`;
连接方式结果集典型用途
INNER JOIN两表都匹配的行常规关联查询
LEFT JOIN左表全部 + 右表匹配项（无则 NULL）查"所有员工及其部门（含未分配）"
RIGHT JOIN右表全部 + 左表匹配项等价于交换表顺序的 LEFT JOIN
FULL JOIN两表全部（MySQL 不支持）用 LEFT UNION RIGHT 模拟

LEFT JOIN 的条件要放 ON 还是 WHERE

这是面试和线上 bug 的高频点：

sql
-- ① 条件在 ON：先过滤右表，再做左连接 → 左表所有员工都保留
SELECT e.`name`, d.`dname`
FROM `emp` e LEFT JOIN `dept` d
  ON e.`dept_id` = d.`id` AND d.`status` = 1;

-- ② 条件在 WHERE：连接完成后再过滤 → 右表为 NULL 的行被过滤掉
SELECT e.`name`, d.`dname`
FROM `emp` e LEFT JOIN `dept` d ON e.`dept_id` = d.`id`
WHERE d.`status` = 1;   -- ❗LEFT JOIN 退化成了 INNER JOIN

规律：对右表的过滤条件写在 ON 里；对左表的过滤条件写在 WHERE 里。想保留左表全部行时，右表条件绝不能放 WHERE。

子查询 ​

按返回结果分四类：

sql
-- ① 标量子查询：返回单个值，用 = > < 等
SELECT * FROM `emp`
WHERE `dept_id` = (SELECT `id` FROM `dept` WHERE `dname` = '研发部');

-- ② 列子查询：返回一列多行，用 IN / NOT IN / ANY / ALL
SELECT * FROM `emp`
WHERE `dept_id` IN (SELECT `id` FROM `dept` WHERE `city` = '北京');

-- 薪资高于研发部所有人 → ALL
SELECT * FROM `emp`
WHERE `salary` > ALL (SELECT `salary` FROM `emp` WHERE `dept_id` = 1);

-- ③ 行子查询：返回一行多列
SELECT * FROM `emp`
WHERE (`salary`, `dept_id`) = (SELECT `salary`, `dept_id` FROM `emp` WHERE `name` = '张三');

-- ④ 表子查询：返回多行多列，放在 FROM 后（派生表，必须起别名）
SELECT t.`dept_id`, t.`avg_sal`
FROM (SELECT `dept_id`, AVG(`salary`) AS avg_sal FROM `emp` GROUP BY `dept_id`) t
WHERE t.`avg_sal` > 10000;

子查询 vs JOIN，谁更快

MySQL 5.6 之前，IN 子查询常被反复执行（半连接优化不完善），通常把它改写成 JOIN 更快。 MySQL 5.6 起引入了子查询物化（Materialization）和半连接（Semi-join）优化，大部分 IN 子查询会被自动改写，性能已接近 JOIN。 实践建议：先按可读性写，再用 EXPLAIN 看执行计划；若出现 DEPENDENT SUBQUERY（相关子查询，逐行执行），就要考虑改成 JOIN。

自连接与 EXISTS ​

sql
-- 自连接：同一张表当两张用，必须起别名。查每个员工及其领导
SELECT e.`name` AS 员工, m.`name` AS 领导
FROM `emp` e
LEFT JOIN `emp` m ON e.`manager_id` = m.`id`;

-- EXISTS：只关心"有没有",匹配到一行就返回 true 并停止
SELECT * FROM `dept` d
WHERE EXISTS (SELECT 1 FROM `emp` e WHERE e.`dept_id` = d.`id`);

-- NOT EXISTS：查没有员工的部门（比 NOT IN 更安全，不受 NULL 影响）
SELECT * FROM `dept` d
WHERE NOT EXISTS (SELECT 1 FROM `emp` e WHERE e.`dept_id` = d.`id`);

NOT IN 的 NULL 陷阱（再次强调）

sql
-- ❌ 如果 emp.dept_id 存在 NULL，结果恒为空
SELECT * FROM `dept` WHERE `id` NOT IN (SELECT `dept_id` FROM `emp`);

-- ✅ 方案一：排除 NULL
SELECT * FROM `dept` WHERE `id` NOT IN (SELECT `dept_id` FROM `emp` WHERE `dept_id` IS NOT NULL);

-- ✅ 方案二：改用 NOT EXISTS（推荐）
SELECT * FROM `dept` d WHERE NOT EXISTS (SELECT 1 FROM `emp` e WHERE e.`dept_id` = d.`id`);

UNION 与 UNION ALL ​

sql
-- UNION：合并并去重（会排序，有额外开销）
SELECT `pname`, `price` FROM `product` WHERE `price` < 100
UNION
SELECT `pname`, `price` FROM `product` WHERE `category` = '数码';

-- UNION ALL：直接拼接，不去重，性能更好
SELECT `pname`, `price` FROM `product` WHERE `price` < 100
UNION ALL
SELECT `pname`, `price` FROM `product` WHERE `category` = '数码';

使用规则

  • 两个查询的列数必须一致，对应列类型要兼容。
  • 结果集列名取第一个 SELECT 的列名。
  • ORDER BY / LIMIT 只能写在最后，作用于合并后的整体；若要对子查询单独排序，需用括号包裹并套一层。
  • 能确定不会重复时一律用 UNION ALL，避免去重排序开销。

用 UNION 模拟 FULL JOIN

sql
SELECT e.`name`, d.`dname` FROM `emp` e LEFT JOIN `dept` d ON e.`dept_id` = d.`id`
UNION
SELECT e.`name`, d.`dname` FROM `emp` e RIGHT JOIN `dept` d ON e.`dept_id` = d.`id`;

多对多建模实战 ​

sql
-- 学生表
CREATE TABLE `student` (
  `id`   INT UNSIGNED NOT NULL AUTO_INCREMENT,
  `name` VARCHAR(50)  NOT NULL,
  PRIMARY KEY (`id`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

-- 课程表
CREATE TABLE `course` (
  `id`    INT UNSIGNED NOT NULL AUTO_INCREMENT,
  `cname` VARCHAR(50)  NOT NULL,
  PRIMARY KEY (`id`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

-- 中间表：联合主键天然防止重复选课
CREATE TABLE `student_course` (
  `student_id` INT UNSIGNED NOT NULL,
  `course_id`  INT UNSIGNED NOT NULL,
  `score`      DECIMAL(5,2)     NULL COMMENT '成绩',
  PRIMARY KEY (`student_id`, `course_id`),
  KEY `idx_sc_course` (`course_id`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
sql
-- 查询每个学生选了哪些课
SELECT s.`name`, c.`cname`, sc.`score`
FROM `student` s
JOIN `student_course` sc ON s.`id` = sc.`student_id`
JOIN `course` c          ON c.`id` = sc.`course_id`;

-- 统计每门课的选课人数与平均分
SELECT c.`cname`, COUNT(*) AS 人数, AVG(sc.`score`) AS 平均分
FROM `course` c
JOIN `student_course` sc ON c.`id` = sc.`course_id`
GROUP BY c.`id`, c.`cname`;

-- 查询一门课都没选的学生
SELECT s.* FROM `student` s
WHERE NOT EXISTS (SELECT 1 FROM `student_course` sc WHERE sc.`student_id` = s.`id`);

中间表的索引怎么建

联合主键 (student_id, course_id) 只能支撑"按 student_id 查"的场景（最左前缀原则）。 "按 course_id 反查学生"需要额外建 KEY (course_id)，否则会全表扫描——这是中间表最容易漏的一个索引。

  MAX(CASE WHEN c.`cname` = '语文' THEN sc.`score` END) AS 语文,
  MAX(CASE WHEN c.`cname` = '数学' THEN sc.`score` END) AS 数学,
  MAX(CASE WHEN c.`cname` = '英语' THEN sc.`score` END) AS 英语
FROM `student` s

JOIN `course` c          ON c.`id` = sc.`course_id`

这里用 MAX 而不是 SUM，是为了在"同一学生同一课程只有一条记录"时避免语义歧义；配合 CASE 未命中返回 NULL 被聚合忽略的特性即可完成透视。

窗口函数（8.0+） ​

核心概念

窗口函数在不折叠行的前提下做分组计算：GROUP BY 把 10 行变成 3 行，窗口函数仍然返回 10 行，只是每行多出一个"组内统计值"。 语法：函数() OVER (PARTITION BY 分组列 ORDER BY 排序列)。MySQL 8.0 起支持。

函数作用
ROW_NUMBER()组内行号，1,2,3,4（并列也不重复）
RANK()排名，1,1,3（并列占位，跳号）
DENSE_RANK()排名，1,1,2（并列不跳号）
LAG(col, n)取前 n 行的值（环比、同比常用）
LEAD(col, n)取后 n 行的值
SUM() OVER(...)累计求和（移动汇总）
NTILE(n)把组内数据均分成 n 桶
sql
-- 每个分类内按价格排名
SELECT `category`, `pname`, `price`,
  ROW_NUMBER() OVER (PARTITION BY `category` ORDER BY `price` DESC) AS rn,
  RANK()       OVER (PARTITION BY `category` ORDER BY `price` DESC) AS rk,
  DENSE_RANK() OVER (PARTITION BY `category` ORDER BY `price` DESC) AS drk
FROM `product`;

组内 TopN —— 窗口函数最典型的用途

"取每个分类里最贵的 2 个商品"，用传统 SQL 要写丑陋的自关联，窗口函数一行搞定（注意窗口函数不能直接写在 WHERE 里，要套一层子查询）：

sql
SELECT * FROM (
  SELECT `category`, `pname`, `price`,
         ROW_NUMBER() OVER (PARTITION BY `category` ORDER BY `price` DESC) AS rn
  FROM `product`
) t
WHERE t.rn <= 2;
sql
-- 按日累计销售额 + 环比
SELECT `stat_date`, `amount`,
  SUM(`amount`) OVER (ORDER BY `stat_date`)                 AS 累计金额,
  LAG(`amount`, 1) OVER (ORDER BY `stat_date`)              AS 前一天金额,
  `amount` - LAG(`amount`, 1) OVER (ORDER BY `stat_date`)    AS 环比增量
FROM `daily_sales`;

5.7 没有窗口函数怎么办

用变量模拟（可读性差且依赖执行顺序，8.0 已不推荐）：

sql
SELECT `category`, `pname`, `price`,
  @rn := IF(@prev = `category`, @rn + 1, 1) AS rn,
  @prev := `category`
FROM `product`, (SELECT @rn := 0, @prev := NULL) init
ORDER BY `category`, `price` DESC;

实际项目中更稳妥的做法是：升级到 8.0，或把 TopN 计算放到应用层。

CTE 公用表表达式（8.0+） ​

sql
-- 普通 CTE：给子查询起名，可多次引用，可读性远胜嵌套
WITH dept_avg AS (
  SELECT `dept_id`, AVG(`salary`) AS avg_sal
  FROM `emp`
  GROUP BY `dept_id`
)
SELECT e.`name`, e.`salary`, d.avg_sal
FROM `emp` e
JOIN dept_avg d ON e.`dept_id` = d.`dept_id`
WHERE e.`salary` > d.avg_sal;

-- 多个 CTE 用逗号分隔，后面的可以引用前面的
WITH
  t1 AS (SELECT `dept_id`, COUNT(*) AS cnt FROM `emp` GROUP BY `dept_id`),
  t2 AS (SELECT * FROM t1 WHERE cnt > 5)
SELECT * FROM t2;

递归 CTE：查询树形结构

部门/评论/菜单这类"无限层级"数据，以前只能在应用层递归查数据库（N+1 问题），8.0 可以一条 SQL 搞定：

sql
WITH RECURSIVE dept_tree AS (
  -- ① 种子查询：根节点
  SELECT `id`, `dname`, `parent_id`, 1 AS lvl
  FROM `dept` WHERE `parent_id` IS NULL

  UNION ALL

  -- ② 递归部分：引用自身，逐层向下
  SELECT d.`id`, d.`dname`, d.`parent_id`, t.lvl + 1
  FROM `dept` d
  JOIN dept_tree t ON d.`parent_id` = t.`id`
)
SELECT * FROM dept_tree ORDER BY lvl, `id`;

递归一定要设置终止条件

如果数据里存在环（A 的父是 B，B 的父是 A），递归会一直执行直到触发 cte_max_recursion_depth（默认 1000）报错。安全做法是在递归部分加深度限制：WHERE t.lvl < 10。

视图 ​

核心概念

视图是一条被命名的 SELECT 语句，本身不存储数据（MySQL 不支持物化视图）。 每次查询视图，MySQL 都会把它展开成底层 SQL 去执行。

sql
-- 创建 / 替换视图
CREATE OR REPLACE VIEW `v_product_on_sale` AS
SELECT `pid`, `pname`, `price`, `category`
FROM `product`
WHERE `status` = 1;

-- 像表一样查询
SELECT * FROM `v_product_on_sale` WHERE `price` < 500;

-- 查看定义 / 删除
SHOW CREATE VIEW `v_product_on_sale`;
DROP VIEW IF EXISTS `v_product_on_sale`;
视图的价值说明
简化复杂查询把多表 JOIN 封装成一张"表"
权限隔离只授权视图，隐藏敏感列（如薪资、身份证）
解耦底层表结构调整时，通过改视图保持对外接口不变

视图的限制

  • 可更新视图条件苛刻：含 GROUP BY、DISTINCT、UNION、聚合函数、子查询的视图不能执行 INSERT/UPDATE/DELETE。
  • 没有性能收益：视图只是 SQL 替换，不会缓存结果；嵌套多层视图反而容易让优化器选错执行计划。
  • 需要"物化"效果请自行建汇总表 + 定时任务刷新。

互联网项目为什么很少用存储过程

  • 无法版本管理：逻辑藏在数据库里，不进 Git，Code Review 和回滚都很困难。
  • 难以水平扩展：业务逻辑消耗的是数据库 CPU，而数据库是最难扩容的一层。

  • 迁移成本高：语法是 MySQL 方言，换数据库几乎要重写。

BEFORE/AFTER DELETE✅❌

触发器的坑

  • MySQL 只支持 行级触发器（FOR EACH ROW），没有语句级触发器。
  • 不会被 TRUNCATE 触发，也不会被主从复制中的 row 格式 binlog 二次触发。
  • 触发器和原语句在同一个事务里：触发器报错会导致原始 DML 一起回滚。
  • 隐式执行，排查问题时极易被忽略——"明明没写这条 INSERT，数据怎么多了一行"。

结论：审计日志优先用 binlog 订阅（Canal）或应用层 AOP，触发器只在小型系统或临时兜底时使用。

为什么 MyISAM 的 COUNT(_) 更快

MyISAM 把表的精确行数存在元数据里，COUNT(_)不带 WHERE 时直接返回。 InnoDB 因为 MVCC，不同事务在同一时刻看到的行数可能不同，无法维护一个全局行数，只能实时统计。 需要大表近似总数时，可以读SHOW TABLE STATUS的Rows（估算值），或单独维护计数表 / 用 Redis 计数。

InnoDB 逻辑存储结构 ​

表空间 Tablespace (.ibd)
  └─ 段 Segment（数据段 / 索引段 / 回滚段）
       └─ 区 Extent（固定 1MB = 64 个页）
            └─ 页 Page（默认 16KB，InnoDB 磁盘读写的最小单位）
                 └─ 行 Row（真实记录 + 隐藏列）

三个隐藏列

每行数据除业务字段外，InnoDB 还会维护：

  • DB_TRX_ID（6 字节）：最后一次插入/修改该行的事务 ID。
  • DB_ROLL_PTR（7 字节）：回滚指针，指向 undo log 中的上一版本。
  • DB_ROW_ID（6 字节）：当表没有主键也没有唯一非空索引时，自动生成的隐藏行号作为聚簇索引键。

前两个是 MVCC 的实现基础。

为什么页是 16KB

磁盘/文件系统按块读写，一次 IO 的成本远大于读取的数据量。InnoDB 以 16KB 页为单位读写，一次 IO 就能加载几十到上百行数据，摊薄了随机 IO 成本。 这也解释了"行越窄，一页装的行越多，同样 IO 能扫更多数据"——所以字段类型要尽量选小。

索引底层：为什么是 B+Tree ​

核心概念

索引是一种有序的数据结构，它帮助 MySQL 高效获取数据，代价是额外的存储空间和写入时的维护成本。

结构问题
二叉搜索树顺序插入会退化成链表，查询变 O(n)
红黑树虽然平衡，但层数过深，百万数据约 20 层 → 20 次磁盘 IO
B-Tree非叶子节点也存数据，导致每页能放的 key 更少、树更高；范围查询需回溯
B+Tree非叶子只存 key（扇出大、树更矮），叶子存全部数据并构成有序双向链表
Hash 索引等值查询 O(1)，但不支持范围查询、排序、最左前缀
B+Tree（三层可支撑约两千万行）

          ┌───────── 根页 ─────────┐
          │   30   |   70          │        非叶子节点：只存 key + 指针
          └───┬────────┬───────┬───┘
         ┌────▼──┐ ┌───▼───┐ ┌─▼─────┐
         │10|20  │ │40|50  │ │80|90  │     中间层
         └──┬────┘ └──┬────┘ └──┬────┘
   ┌────────▼──┐  ┌───▼──────┐ ┌▼─────────┐
   │ 数据行...  │◀▶│ 数据行... │◀▶│ 数据行... │  叶子层：存数据 + 双向链表
   └───────────┘  └──────────┘ └──────────┘

一棵三层 B+Tree 能存多少数据（经典面试题）

  • 一页 16KB。非叶子节点存 "key + 指针"，假设主键 BIGINT 8 字节 + 指针 6 字节 = 14 字节，一页约存 16384 / 14 ≈ 1170 个 key。
  • 叶子节点存完整行，假设一行 1KB，一页约存 16 行。
  • 两层（根 + 叶子）：1170 × 16 ≈ 1.8 万行。
  • 三层：1170 × 1170 × 16 ≈ 2190 万行。

也就是说，两千万行的表，通过主键查一行只需 3 次 IO，而且根页常驻 Buffer Pool，实际 IO 更少。这就是"单表别超过两千万行"这条经验法则的来源。

聚簇索引、二级索引与回表 ​

分类含义数量
聚簇索引（主键索引）叶子节点挂完整行数据只能有一个
二级索引（辅助索引）叶子节点挂索引列值 + 主键值可以有多个
聚簇索引（按 id）                    二级索引（按 name）
┌──────────────┐                    ┌──────────────┐
│ 10 | 20 | 30 │                    │ 李 | 王 | 张  │
└───┬──────────┘                    └───┬──────────┘

│ id=20 全部字段           │         │ 李四 → id=10      │
└─────────────────────────┘         └──────────────────┘
                   ▲                         │
                   └───────── 回表 ──────────┘

什么是回表

SELECT * FROM user WHERE name = '张三' 的执行过程：

  1. 在 name 二级索引上找到 张三 → 得到主键 id = 30。
  2. 拿着 id = 30 回到聚簇索引再查一次，取出完整行 —— 这一步就叫回表。

一次查询走了两棵树。如果 SELECT 的列二级索引里全都有，就不需要第二步，这叫覆盖索引（EXPLAIN 的 Extra 会显示 Using index）。

为什么二级索引叶子存主键而不是行地址

存主键的好处是：行在页内移动、页分裂时，不需要更新所有二级索引，只有主键变化才需要（而主键一般不变）。 代价是多一次回表。这也是不要用长字符串做主键的另一个原因——所有二级索引都会冗余一份主键值，索引体积被放大数倍。

前缀索引怎么选长度

用"选择性"评估：取值越接近 1 越好。

sql
SELECT
  COUNT(DISTINCT LEFT(`email`, 6))  / COUNT(*) AS sel_6,
  COUNT(DISTINCT LEFT(`email`, 10)) / COUNT(*) AS sel_10,
  COUNT(DISTINCT `email`)           / COUNT(*) AS sel_full

九、性能优化篇 ​

常见性能瓶颈 ​

优化的正确顺序

不要一上来就加索引。按收益从大到小排： ① 表结构/索引设计 → ② SQL 写法 → ③ 架构（缓存、读写分离、分库分表） → ④ 参数与硬件 前两项往往能解决 90% 的问题，而且成本最低。

现象常见原因
某条 SQL 突然变慢索引失效、数据量增长、统计信息过期导致选错索引
整库变慢慢 SQL 拖垮连接池、锁等待、磁盘/IO 打满
写入变慢索引过多、大事务、唯一索引冲突检查、binlog 刷盘
CPU 高大量排序/临时表、全表扫描、复杂 JOIN
连接数打满慢查询堆积、连接未释放、连接池配置过小

索引设计原则 ​

什么时候该建索引

  • 数据量较大（万级以上）且查询频繁的表。
  • 作为 WHERE、ORDER BY、GROUP BY、JOIN ON 条件的字段。
  • 区分度高的字段（如手机号、订单号）。

什么时候不该建索引

  • 数据量很小的表（全表扫描可能比走索引更快）。
  • 区分度极低的字段（如 性别、是否删除，只有 2~3 个值）。
  • 很少用于查询条件的字段 —— 索引会拖慢所有写操作。
  • 频繁更新的字段 —— 每次更新都要维护 B+Tree。

联合索引与最左前缀原则

假设有索引 idx_abc (a, b, c)：

查询条件能用到的索引部分说明
a = 1a✅
a = 1 AND b = 2a, b✅
a = 1 AND b = 2 AND c = 3a, b, c✅ 完全命中
b = 2无❌ 跳过了最左列
a = 1 AND c = 3仅 a⚠️ b 断档，c 用不上（但可能被 ICP 利用）
a > 1 AND b = 2仅 a⚠️ 范围查询后面的列失效
a = 1 AND b > 2 AND c = 3a, b⚠️ 同上

联合索引的列怎么排序

口诀：等值在前，范围在后；区分度高的在前。 因为 B+Tree 是按"先比 a，a 相同再比 b"的规则排序的，一旦某列用了范围条件，它后面的列在索引中就不再有序，无法继续用于定位。 一个 (a, b, c) 联合索引相当于同时拥有 (a)、(a,b)、(a,b,c) 三个索引，能用联合索引就不要建多个单列索引。

索引失效的典型场景 ​

以 idx_abc (a, b, c) 和 idx_name (name) 为例：

sql
-- ① 违反最左前缀
SELECT * FROM t WHERE b = 2;                      -- ❌

-- ② 索引列参与运算 / 使用函数
SELECT * FROM t WHERE a + 1 = 5;                  -- ❌
SELECT * FROM t WHERE SUBSTRING(name, 1, 3) = 'abc';  -- ❌
SELECT * FROM t WHERE a = 4;                      -- ✅ 把运算挪到等号右边

-- ③ 字符串不加引号（隐式类型转换）
SELECT * FROM `user` WHERE `phone` = 13800000000;  -- ❌ phone 是 varchar
SELECT * FROM `user` WHERE `phone` = '13800000000';-- ✅

-- ④ 左侧模糊匹配
SELECT * FROM t WHERE name LIKE '%abc';           -- ❌
SELECT * FROM t WHERE name LIKE 'abc%';           -- ✅

-- ⑤ OR 连接的列未全部建索引
SELECT * FROM t WHERE a = 1 OR other = 2;         -- ❌ other 无索引则整体失效
                                                  -- ✅ 给 other 也建索引，或改成 UNION ALL

-- ⑥ 不等于 / NOT IN / IS NOT NULL（取决于区分度，优化器可能放弃索引）
SELECT * FROM t WHERE a <> 1;                     -- ⚠️

-- ⑦ 范围过大，优化器判断回表成本高于全表扫描
SELECT * FROM t WHERE a > 0;                      -- ⚠️ 可能直接走 ALL

隐式类型转换：最隐蔽的线上杀手

WHERE phone = 13800000000（varchar 列传了数字）时，MySQL 会把列的每一行转成数字再比较，等价于 CAST(phone AS SIGNED) = 13800000000，索引彻底失效。 反过来，WHERE id = '100'（int 列传字符串）是把常量转成数字，索引仍然有效。 规律：转换发生在列上就失效，发生在常量上就没事。 ORM 传参时务必保证类型与列定义一致。

强制/忽略索引（临时手段）

sql
SELECT * FROM t USE INDEX (idx_abc) WHERE a = 1;      -- 建议使用
SELECT * FROM t FORCE INDEX (idx_abc) WHERE a = 1;    -- 强制使用
SELECT * FROM t IGNORE INDEX (idx_abc) WHERE a = 1;   -- 禁止使用

优化器选错索引多半是统计信息过期，先执行 ANALYZE TABLE t; 刷新；FORCE INDEX 只应作为应急方案，因为它会随数据分布变化而失效。

覆盖索引与索引下推（ICP） ​

sql
-- 假设有索引 idx_name_age (name, age)

-- ✅ 覆盖索引：要的列索引里都有，Extra = Using index
SELECT `id`, `name`, `age` FROM `user` WHERE `name` = '张三';

-- ❌ 需要回表：phone 不在索引中
SELECT `id`, `name`, `phone` FROM `user` WHERE `name` = '张三';

覆盖索引是最廉价的优化手段

SELECT * 必然回表；把高频查询真正需要的少数几列加进联合索引末尾，就能让查询完全在索引树上完成，IO 减半。 这也是禁止 SELECT * 最硬核的理由。

索引下推 ICP（Index Condition Pushdown，5.6+）

sql
-- 索引 idx_name_age (name, age)
SELECT * FROM `user` WHERE `name` LIKE '张%' AND `age` = 20;
5.5 及以前（无 ICP）                 5.6 起（有 ICP）
┌──────────────┐                    ┌──────────────┐
│ Server 层     │ ← 过滤 age=20      │ Server 层     │
└──────▲───────┘                    └──────▲───────┘
       │ 回表取出所有 张% 的整行         │ 只回表 age=20 的行
┌──────┴───────┐                    ┌──────┴───────┐
│ 引擎层        │                    │ 引擎层        │ ← age=20 在索引上就过滤掉
└──────────────┘                    └──────────────┘

因为 name LIKE '张%' 是范围条件，按最左前缀原则 age 无法用于定位；但 age 的值就在索引里，ICP 允许引擎层顺便用它过滤，大幅减少回表次数。EXPLAIN 的 Extra 显示 Using index condition 即为生效。

分页性能优化 ​

sql
-- ❌ 深分页：扫描 1000010 行，丢弃前 1000000 行
SELECT * FROM `product` ORDER BY `id` LIMIT 1000000, 10;
sql
-- ✅ 方案一：子查询先在索引上定位主键，再回表（通用，适合跳页）
SELECT p.* FROM `product` p
JOIN (SELECT `id` FROM `product` ORDER BY `id` LIMIT 1000000, 10) t
  ON p.`id` = t.`id`;

-- ✅ 方案二：游标分页 / 记住上次最大 ID（最快，但只能上下翻页）
SELECT * FROM `product` WHERE `id` > 1000000 ORDER BY `id` LIMIT 10;

-- ✅ 方案三：业务上限制最大页数，或引导用户用筛选条件缩小范围

方案一为什么更快

子查询 SELECT id ... LIMIT 1000000, 10 是覆盖索引扫描，不需要回表，只在索引树上顺序跳过 100 万个 key（每个 key 很小，一页能装上千个）；而原始写法每跳过一行都要回表取整行数据。

游标分页的前提

排序列必须唯一且单调（通常是自增主键或 created_at + id），否则会漏数据。另外它天然不支持"跳到第 500 页"，适合 App 信息流这类无限下拉场景。

事务与 ACID ​

事务是一组操作的集合，它是一个不可分割的工作单位，要么全部成功，要么全部失败回滚。

特性含义InnoDB 的实现

并发问题与隔离级别 ​

并发问题描述

RR 到底解决幻读了吗

快照读（普通 SELECT）下，RR 用 MVCC 保证整个事务看到同一份快照，不会幻读。 当前读（SELECT ... FOR UPDATE、UPDATE、DELETE）下，RR 靠间隙锁 + 临键锁阻止其他事务在范围内插入，也能避免幻读。 但仍存在边缘场景：事务内先快照读（看不到新行），再去 UPDATE 那一行（当前读能改到），就会出现"明明查不到却改成功了"的类幻读现象。所以严谨说法是：RR 在大多数场景下解决了幻读，但不是绝对的。

为什么很多互联网公司把隔离级别调成 RC

  1. RR 的间隙锁范围大，并发写入时更容易死锁；RC 没有间隙锁，锁冲突更少。
  2. RC 下主从复制必须用 row 格式 binlog（现在本来就是默认）。
  3. 业务层通常已用乐观锁/版本号解决一致性，不依赖数据库的可重复读。

MVCC 实现原理 ​

MVCC（Multi-Version Concurrency Control，多版本并发控制）让读不加锁、读写不阻塞，是 InnoDB 高并发的核心。

三个关键组成

  1. 隐藏字段
字段作用
DB_TRX_ID最近一次修改这行的事务 ID
DB_ROLL_PTR回滚指针，指向 undo log 里的上一个版本
DB_ROW_ID隐藏主键，仅当表无主键也无唯一索引时自动生成
  1. undo log 版本链：每次 UPDATE 都会把旧值写入 undo log，通过 DB_ROLL_PTR 串成一条从新到旧的链表。
最新记录                    undo log 版本链
┌───────────────┐      ┌───────────────┐      ┌───────────────┐
│ age=30        │      │ age=20        │      │ age=18        │
│ trx_id=102    │ ───▶ │ trx_id=101    │ ───▶ │ trx_id=100    │
│ roll_ptr ─────┼──────┤ roll_ptr ─────┼──────┤ roll_ptr=NULL │
└───────────────┘      └───────────────┘      └───────────────┘
  1. ReadView：快照读时生成的"活跃事务快照"，包含 m_ids（当前活跃事务 ID 列表）、min_trx_id、max_trx_id、creator_trx_id。

版本可见性判断规则（设当前版本的 trx_id 为 T）

条件结果
T == creator_trx_id✅ 自己改的，可见
T < min_trx_id✅ 生成快照前已提交，可见
T > max_trx_id❌ 快照后才开启的事务，不可见
min_trx_id ≤ T ≤ max_trx_id 且在 m_ids❌ 还活跃（未提交），不可见
min_trx_id ≤ T ≤ max_trx_id 且不在 m_ids✅ 已提交，可见

不可见时顺着 roll_ptr 找上一个版本，重复判断，直到找到可见版本或链表结束。

RC 与 RR 的唯一区别就在 ReadView 的生成时机

  • RC：每次 SELECT 都重新生成 ReadView → 所以能读到别人新提交的数据 → 不可重复读。
  • RR：只在事务内第一次 SELECT 时生成，之后复用 → 整个事务看到同一份快照 → 可重复读。

快照读 vs 当前读

类型语句行为
快照读普通 SELECT走 MVCC，不加锁
当前读SELECT ... FOR UPDATE / LOCK IN SHARE MODE / INSERT / UPDATE / DELETE读最新版本并加锁

redo log / undo log / binlog ​

日志所属层作用内容形式写入方式
redo logInnoDB崩溃恢复，保证持久性物理日志（页改动）循环写，固定大小
undo logInnoDB回滚 + MVCC，保证原子性逻辑日志（反向操作）随事务生成、purge 清理
binlogServer主从复制 + 数据恢复逻辑日志（SQL/行）追加写，不断生成新文件

redo log 为什么能提升性能（WAL）

UPDATE 执行流程（WAL：Write-Ahead Logging）
① 从磁盘/Buffer Pool 读到数据页
② 在内存中修改数据页（变成脏页）
③ 把"页的物理改动"顺序写入 redo log buffer
④ 提交时把 redo log 刷盘（顺序 IO，极快）
⑤ 脏页由后台线程异步刷回磁盘（随机 IO，慢）

即使 ④ 之后宕机，重启时根据 redo log 重做即可，不会丢数据——这就是用顺序写代替随机写。

sql
-- 控制 redo log 刷盘策略（持久性与性能的权衡）
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
取值行为安全性
1每次提交都刷盘（默认）最安全，不丢数据
0每秒由后台线程刷一次宕机最多丢 1 秒
2每次写入 OS 缓存，由 OS 每秒刷盘MySQL 崩溃不丢，机器断电可能丢

两阶段提交：为了保证 redo log 与 binlog 的一致性，InnoDB 采用 2PC。

① redo log 写入并置为 prepare 状态
② binlog 写入并刷盘
③ redo log 置为 commit 状态

如果没有两阶段提交会怎样

  • 先写 redo 后写 binlog：redo 写完崩溃 → 主库恢复后有这条数据，但 binlog 没有 → 从库少数据。
  • 先写 binlog 后写 redo：binlog 写完崩溃 → 主库回滚没这条数据，从库有 → 从库多数据。

两阶段提交 + 崩溃恢复时"binlog 完整就提交，不完整就回滚"的规则，保证了主从最终一致。

线上加字段为什么会把整个库打挂

ALTER TABLE 需要 MDL 写锁。若此时有一个长事务正持有 MDL 读锁（比如一个忘了提交的 SELECT），DDL 就会等待；而 MDL 等待是排队的，后续所有对该表的普通查询都会堵在它后面，连接数瞬间打满。

正确做法：

  1. 改表前先查 information_schema.innodb_trx 杀掉长事务。
  2. DDL 加超时：ALTER TABLE t WAIT 5 ADD COLUMN ...（MariaDB）或用 pt-online-schema-change / gh-ost 做在线改表。
  3. 避开业务高峰执行。
sql

WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 60;

-- 查看元数据锁等待（8.0）
SELECT * FROM performance_schema.metadata_locks;

死锁排查与规避 ​

死锁示例：两个事务互相等待对方持有的锁。

sql
-- 事务 A                              -- 事务 B
START TRANSACTION;                     START TRANSACTION;
UPDATE t SET x=1 WHERE id=1;           UPDATE t SET x=1 WHERE id=2;
-- 持有 id=1 的锁                        -- 持有 id=2 的锁
UPDATE t SET x=2 WHERE id=2;  ←等待 B
                                  UPDATE t SET x=2 WHERE id=1;  ←等待 A
-- 💥 Deadlock found when trying to get lock
sql
-- 查看最近一次死锁的详细信息（排查首选）
SHOW ENGINE INNODB STATUS;    -- 看 LATEST DETECTED DEADLOCK 段

-- 把所有死锁都打进 error log（建议线上开启）
SET GLOBAL innodb_print_all_deadlocks = ON;

-- 锁等待超时（默认 50 秒，建议调小到 5~10 秒快速失败）
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';

-- 死锁检测（默认开启，InnoDB 会自动回滚代价小的事务）
SHOW VARIABLES LIKE 'innodb_deadlock_detect';

规避死锁的六条实践

  1. 统一加锁顺序：多行更新时按主键升序处理（如对 ID 排序后再批量更新）。
  2. 缩短事务：不在事务里做 RPC、发 MQ、读文件；大批量拆小批。
  3. WHERE 必须命中索引，避免锁范围被放大。
  4. 降低隔离级别到 RC，去掉间隙锁，大幅减少死锁概率。
  5. 一次性锁定所需资源：把多条 UPDATE 合并，或先 SELECT ... FOR UPDATE 拿全锁。
  6. 业务层重试：死锁是正常现象，捕获错误码 1213 后退避重试即可。

全同步复制所有从库都应用完才返回最安全，性能最差

主从延迟导致的"写完读不到"

读写分离后，刚写入就去从库查，可能读到旧数据。常见对策：

  • 强制走主库：对一致性敏感的读（如下单后立刻查订单）直连主库。
  • 延迟双读：先读从库，查不到再读主库（注意防缓存穿透）。
  • 业务容忍：前端用本地数据先渲染，不依赖立即回读。
  • 监控 Seconds_Behind_Master，超阈值自动摘除该从库。

分库分表的代价

  • 跨库 JOIN 失效 → 只能改为多次查询在应用层拼装，或冗余字段。
  • 分布式事务 → 需要 Seata / 最终一致性方案，不能再靠一个 COMMIT。

  • 扩容迁移 → 数据搬迁 + 双写 + 校验，是一个项目级工程。

所以：能不分就不分。 优先考虑归档历史数据、上缓存、换更好的硬件。

十二、面试题篇 ​

索引面试题 ​

1. 为什么 InnoDB 用 B+Tree 而不是 B 树 / 红黑树 / 哈希表？
结构为什么不选
二叉/红黑树树高太高（百万数据约 20 层），每层一次磁盘 IO，IO 次数无法接受
B 树非叶子节点也存数据 → 单页能放的 key 变少 → 树更高；且不支持范围顺序扫描
哈希表只支持等值查询，不支持范围查询、排序、最左前缀

B+Tree 的优势：非叶子节点只存索引，单页能存上千个 key，三层即可支撑两千万级数据（3 次 IO）；叶子节点用双向链表相连，范围查询与排序极快。

2. 什么是聚簇索引和回表？
  • 聚簇索引：叶子节点存放整行数据的索引。InnoDB 必有且只有一个，优先用主键，无主键则用第一个唯一非空索引，都没有则用隐藏的 DB_ROW_ID。
  • 二级索引：叶子节点存放的是主键值。
  • 回表：通过二级索引查到主键，再拿主键去聚簇索引查整行，走了两棵树。

避免回表的手段就是覆盖索引。

3. 为什么推荐用自增主键，不建议用 UUID？
  1. 顺序写入：自增主键是顺序插入，只在 B+Tree 右侧追加，不会页分裂；UUID 随机插入会频繁页分裂与页合并，产生大量碎片。
  2. 体积更小：BIGINT 8 字节，UUID 字符串 36 字节。而所有二级索引的叶子节点都存主键值，主键越大，整个库的索引空间就越大。
  3. 范围查询友好：自增主键天然按时间有序。

分布式场景如果必须全局唯一，用雪花算法（趋势递增的 long）而不是 UUID。

4. 联合索引 (a, b, c) 哪些查询能用上？
查询条件能用到的部分
a = 1a
a = 1 AND b = 2a, b
a = 1 AND b = 2 AND c = 3a, b, c
b = 2 AND a = 1a, b（优化器会重排）
a = 1 AND c = 3仅 a（c 只能做 ICP 过滤）
a > 1 AND b = 2仅 a（a 是范围，b 断了）
b = 2 AND c = 3❌ 完全用不到

核心就是最左前缀原则：从最左列开始、不跳列，遇到范围查询后面的列失效。

5. 索引越多越好吗？

不是。索引的代价：

  • 占空间：每个索引都是一棵独立的 B+Tree。
  • 拖慢写入：INSERT / UPDATE / DELETE 都要维护所有相关索引。
  • 干扰优化器：候选索引过多会让优化器选错索引。

经验值：单表索引不超过 5~6 个，优先用联合索引替代多个单列索引（一个 (a,b,c) 顶 (a)、(a,b)、(a,b,c) 三个）。

SQL 优化面试题 ​

1. 一条慢 SQL 你怎么优化？

按固定套路回答：

  1. 定位：慢查询日志 / SHOW FULL PROCESSLIST 找到这条 SQL。
  2. 看计划：EXPLAIN 确认 type（是否 ALL）、key（有没有用索引）、rows（扫了多少行）、Extra（有没有 filesort / temporary）。
  3. 查原因：常见是缺索引、索引失效（函数、!=、OR、前导 %、隐式转换）、回表过多、深分页、JOIN 驱动表选错。
  4. 动手改：加/调整索引 → 改 SQL 写法（拆分、去 SELECT *、子查询改 JOIN）→ 必要时改表结构、加缓存、做归档。
  5. 验证：对比优化前后 rows 和真实耗时。
2. LIMIT 1000000, 10 为什么慢？怎么优化？

慢的原因：MySQL 必须扫描并回表前 1000010 行，然后把前 1000000 行丢掉。

优化方案：

sql
-- 子查询 + 延迟关联（覆盖索引扫主键，再统一回表 10 行）
SELECT p.* FROM `product` p
JOIN (SELECT `id` FROM `product` ORDER BY `id` LIMIT 1000000, 10) t ON p.`id` = t.`id`;

-- 游标分页（最优，但只能连续翻页）
SELECT * FROM `product` WHERE `id` > #{lastId} ORDER BY `id` LIMIT 10;
3. COUNT(*)、COUNT(1)、COUNT(字段) 哪个快？
  • COUNT(*)：InnoDB 专门做了优化，不取任何列的值，直接按行累加，并且会选择最小的那棵索引树来扫描。
  • COUNT(1)：每行返回常量 1 再累加，与 COUNT(*) 性能基本一致。
  • COUNT(主键)：要取出主键值，略慢。
  • COUNT(普通字段)：取值 + 判空，且不统计 NULL，语义都不一样，最慢。

结论：统计行数永远用 COUNT(*)。

另外 MyISAM 把行数存在表元信息里，无条件 COUNT(*) 是 O(1)；InnoDB 因为 MVCC（不同事务看到的行数不同）必须实时统计。

4. 为什么禁止 SELECT *？
  1. 无法使用覆盖索引，必然回表。
  2. 传输无用数据，增加网络 IO 与内存占用（尤其是 TEXT/BLOB 字段）。
  3. 表结构变更时容易引发应用端解析错误。
  4. 让人看不出这条 SQL 到底依赖哪些字段，不利于索引设计与 Review。
5. JOIN 和子查询哪个好？in 和 exists 怎么选？
  • 多数情况下 JOIN 优于子查询，因为子查询可能产生临时表且无法用索引（MySQL 5.6 后对部分子查询做了优化，差距缩小）。
  • IN vs EXISTS 的经验规则：小表驱动大表。
    • 子查询结果集小、外表大 → 用 IN。
    • 外表小、子查询表大 → 用 EXISTS。
  • ⚠️ NOT IN 遇到子查询结果含 NULL 会永远返回空，务必改用 NOT EXISTS 或 LEFT JOIN ... IS NULL。

事务与隔离级别面试题 ​

1. 讲一下 ACID 以及 InnoDB 分别靠什么实现？
  • 原子性：undo log，失败时反向执行回滚。
  • 持久性：redo log，WAL 先写日志，崩溃后重做。
  • 隔离性：锁（当前读）+ MVCC（快照读）。
  • 一致性：以上三者共同保证的最终结果。
2. 脏读、不可重复读、幻读的区别？
  • 脏读：读到未提交的数据（别人回滚了，你读到的是不存在的数据）。
  • 不可重复读：针对同一行，两次读结果不同（别人 UPDATE 并提交）。
  • 幻读：针对一个范围，两次读行数不同（别人 INSERT 并提交）。

记忆点：不可重复读关注数据被改，幻读关注行数变多。

3. MySQL 默认隔离级别是什么？RR 解决幻读了吗？

默认 REPEATABLE READ（可重复读）。

  • 快照读：靠 MVCC 固定 ReadView，不会幻读。
  • 当前读：靠间隙锁 + 临键锁阻止范围内插入，也能避免幻读。
  • 但先快照读再当前读的混合场景仍可能出现类幻读，所以不是 100% 解决。
4. RC 和 RR 在实现上的区别是什么？

唯一区别是 ReadView 的生成时机：

  • RC 每次 SELECT 都新建 ReadView → 能看到最新提交 → 不可重复读。
  • RR 只在事务第一次 SELECT 时建 ReadView 并全程复用 → 可重复读。

此外 RC 不加间隙锁，RR 加间隙锁。

5. 长事务有什么危害？
  1. undo log 无法 purge，版本链越来越长，回滚段膨胀（历史上的 ibdata 暴涨问题）。
  2. 持有 MDL 读锁，后续 DDL 全部阻塞，连带把普通查询也堵死。
  3. 锁持有时间长，锁冲突与死锁概率上升。
  4. 主从延迟变大。

排查：SELECT * FROM information_schema.innodb_trx WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 60;

锁与 MVCC 面试题 ​

1. MVCC 是什么？怎么工作的？

MVCC = 多版本并发控制，目的是让读不加锁、读写互不阻塞。

三要素：

  1. 隐藏字段 DB_TRX_ID（谁改的）、DB_ROLL_PTR（上一个版本在哪）。
  2. undo log 版本链：每次修改把旧版本串成链表。
  3. ReadView：快照读时记录当前活跃事务列表，按可见性规则沿版本链找到对自己可见的那个版本。
2. 快照读和当前读的区别？
  • 快照读：普通 SELECT，走 MVCC 读历史版本，不加锁。
  • 当前读：SELECT ... FOR UPDATE、SELECT ... LOCK IN SHARE MODE、INSERT、UPDATE、DELETE，读最新版本并加锁。
3. InnoDB 的行锁是加在什么上的？

加在索引上，不是加在行记录本身。所以：

  • 如果 WHERE 条件走不到索引，InnoDB 会扫全表并锁住所有行，效果等同表锁。
  • 这就是"UPDATE / DELETE 的条件必须命中索引"的根本原因。
4. 间隙锁和临键锁解决什么问题？
  • 间隙锁 (Gap Lock)：锁住索引记录之间的"空隙"，阻止其他事务在空隙中插入，用于解决幻读。
  • 临键锁 (Next-Key Lock) = 行锁 + 间隙锁，是 RR 下的默认加锁单位，锁的是左开右闭区间。
  • RC 隔离级别没有间隙锁，所以死锁更少，但会幻读。
5. 遇到死锁怎么排查和解决？

排查：SHOW ENGINE INNODB STATUS 查看 LATEST DETECTED DEADLOCK 段，能看到两个事务各自持有和等待的锁；线上建议开 innodb_print_all_deadlocks 把死锁打进 error log。

解决/规避：统一加锁顺序、缩短事务、保证 WHERE 命中索引、必要时降到 RC、业务层捕获 1213 错误码后退避重试。

MySQL 默认开启死锁检测，会自动回滚代价较小的事务，所以死锁不会一直挂着。

3. 为什么 8.0 移除了查询缓存？

查询缓存以 SQL 文本为 key 缓存结果集，但任何对该表的写操作都会清空该表所有缓存。在写多读少或读写混合的场景下，命中率极低而维护开销很大，反而成为性能瓶颈。应用层缓存（Redis）能做得更好更可控。

4. Buffer Pool 是什么？

InnoDB 的内存缓冲池，缓存数据页与索引页，读写都先在这里进行，脏页异步刷盘。

  • 大小由 innodb_buffer_pool_size 控制，专用数据库服务器建议设为物理内存的 50%~70%，这是 MySQL 最重要的性能参数。
  • 淘汰算法是改良版 LRU：链表分 young（5/8）和 old（3/8）两区，新页先进 old 区头部，只有在 old 区停留超过 innodb_old_blocks_time（默认 1000ms）后再次被访问才会晋升到 young 区。
  • 目的就是防止全表扫描/预读把真正的热数据从缓存里冲掉。
5. 一棵三层的 B+Tree 能存多少数据？

按默认 16KB 一页估算：

  • 叶子节点：假设一行 1KB，一页约放 16 行。
  • 非叶子节点：只存「主键 + 页号」，约 8 + 6 = 14 字节，一页约放 16384 / 14 ≈ 1170 个 key。
  • 两层非叶子：1170 × 1170 ≈ 136 万个指针。
  • 三层总容量：1170 × 1170 × 16 ≈ 2190 万行。

所以千万级单表只需 3 次磁盘 IO，而且根节点和非叶子节点通常常驻 Buffer Pool，真实 IO 更少。这也解释了"单表建议不超过 2000 万行"这条经验法则的由来。

索引原理面试题（口述版） ​

1. 什么是索引？

索引是帮助数据库加速数据查询的一种数据结构。MySQL 默认存储引擎 InnoDB 采用的是 B+ 树，树上的一个节点对应 InnoDB 的一个数据页，默认大小 16KB。

它带来的好处主要有两点：

  • 查询时需要扫描的数据页大幅减少，降低磁盘 IO；
  • 索引本身是有序的，ORDER BY、GROUP BY 这类场景可以直接利用这个顺序，避免额外的 filesort，减少 CPU 开销。
2. B 树和 B+ 树的区别是什么？为什么 B+ 树查询更快？

三点区别：

对比项B 树B+ 树
数据存放位置非叶子节点和叶子节点都存放数据只有叶子节点存数据，非叶子只存键值和指针
叶子节点组织方式叶子节点相互独立所有叶子节点用双向链表相连，有序
查询路径可能在非叶子节点就命中并返回每次查询都必须走到叶子节点

B+ 树更快的四个原因：

  • 树更矮，磁盘 IO 更少：非叶子节点不存数据，一页能放下更多键，树的阶数更高、层数更矮。实际三层 B+ 树就能存两千万左右的数据，查任意一条记录最多 3 次磁盘 IO；而 B 树非叶子节点要存数据，一页装不了几个键，树更高、IO 更多——数据库性能瓶颈主要就在磁盘 IO 上。
  • 查询效率更稳定：所有数据都在叶子节点，任何一次查询的路径长度都相同；B 树可能第一层就命中、也可能走到最底层，波动较大。
  • 范围查询和排序更快：叶子节点是有序双向链表，范围查询只要定位到起点再顺着链表扫，是顺序 IO；B 树范围查询需要不断中序遍历、在节点间来回跳，属于随机 IO。ORDER BY、分页同理。
  • 全表扫描更高效：只需遍历一遍叶子节点链表即可拿到全部数据，不用遍历整棵树。
3. 什么是聚簇索引，什么是非聚簇索引？
  • 聚簇索引：数据与索引存放在一起，B+ 树的叶子节点上保存的就是整行数据。一张表有且只有一个，一般就是主键索引。
  • 非聚簇索引（二级索引）：数据与索引分开存储，叶子节点上保存的是对应的主键值。一张表可以有多个，我们自己创建的索引基本都属于这一类。

聚簇索引的选取规则：

  1. 表中存在主键 → 主键索引就是聚簇索引；
  2. 不存在主键 → 选取第一个唯一（UNIQUE）索引作为聚簇索引；
  3. 既没有主键也没有合适的唯一索引 → InnoDB 自动生成一个隐藏的 rowid 作为聚簇索引。
4. 什么是回表查询？

这个和聚簇索引、非聚簇索引有关。因为非聚簇索引的叶子节点只存了主键值，并没有整行数据，所以当查询需要的字段不在这个索引里时，就得先通过二级索引找到主键值，再拿着主键值回到聚簇索引中查出整行数据——这个额外查一次的过程就叫回表。

回表相当于多走了一棵 B+ 树，会增加磁盘 IO，所以优化时我们会尽量避免。

如图，按姓名 Arm 查询时，先在下方的二级索引中找到对应的主键值 10，再根据主键值 10 到上方的聚簇索引中查出整行数据，这一步就是回表。

面试中如果直接问回表，需要先介绍聚簇索引和非聚簇索引，再引出回表。

5. 什么叫覆盖索引？

覆盖索引是指查询所需的字段都能直接从使用的索引中获取，不需要再回表。它不是一种独立的索引类型，而是索引刚好满足了这条查询的数据需求。

比如 InnoDB 中 id 是主键、name 上建了二级索引，这个索引的叶子节点就包含 name 和 id。如果按姓名查询且只返回 id 和 name，直接扫这个二级索引就能拿到结果，这就是覆盖索引；如果还要返回不在该索引中的 age，就需要根据主键值回表。

所以实际开发中要尽量只查需要的字段，避免不必要的 SELECT *；对于高频查询，可以根据查询条件和返回字段设计合适的联合索引来减少回表，但也要权衡索引占用的空间和增删改的维护成本。

6. 索引创建原则有哪些？
  1. 优先考虑数据量较大、查询频繁的表。这类表更容易从索引中受益，但是否建索引要结合实际查询需求判断，并没有固定的数据量门槛。
  2. 优先考虑经常用于查询、排序和分组的字段。比如 WHERE 条件、ORDER BY、GROUP BY 以及表关联条件中的字段；索引能否发挥作用，还取决于具体查询写法和索引设计。
  3. 关注字段区分度，符合业务唯一性要求时建唯一索引。区分度越高越有利于减少扫描行数；如果业务要求值不能重复，可以建唯一索引同时保证数据唯一性，但不能仅为性能强加唯一约束。
  4. 较长的字符串字段可以考虑前缀索引。选择区分度足够高的前缀能减少索引空间占用，不过前缀索引无法覆盖完整字符串字段，也不能直接用于保证完整字段的排序结果。
sql
create index idx_email on user(email(10)); -- 前缀索引，取前 10 位
  1. 根据查询需求合理使用联合索引。多个字段经常一起查询时，可以用联合索引替代部分单列索引，并结合最左前缀原则安排字段顺序；索引覆盖查询字段就能减少回表，但联合索引不一定比单列索引更省空间，要避免重复和冗余设计。
  2. 控制索引数量，权衡查询收益和写入成本。插入、删除、更新相关字段时都要维护索引，多余的索引会增加存储空间和维护开销。
  3. 业务不允许为空的字段加 NOT NULL 约束。既能明确数据约束，也有助于简化部分查询判断；但不能为了索引性能随意禁止空值，允许 NULL 的字段同样可以建立并使用索引。

建好索引后，还要结合 EXPLAIN 和实际执行耗时验证效果，不能只凭经验判断。

7. 什么情况下索引会失效？

这里的「失效」通常指无法利用索引高效定位数据，并不一定意味着完全不扫描索引。常见五种：

  1. 违反最左前缀法则。联合索引要从最左列开始连续使用。索引为 (a, b, c) 时，只按 b 查询通常无法高效定位；只按 a 和 c 查询，一般只能用 a 定位，c 可能用于后续过滤。
  2. 范围查询影响后续列的使用。某一列用了 >、< 等范围条件，其右侧列通常不能继续用于缩小索引扫描范围，但仍可能用于索引条件下推或覆盖索引；BETWEEN、>=、<= 的具体表现要看执行计划。
  3. 在索引列上做运算或调用函数。如 WHERE age + 1 = 20、WHERE YEAR(create_time) = 2024，普通索引无法直接用于定位。应改为 WHERE age = 19，让索引列保持原样；如果建了匹配的函数索引则另当别论。
  4. 字符串不加单引号，发生隐式类型转换。phone 是字符串类型却写成 WHERE phone = 13800138000，MySQL 可能把列转成数值比较，导致无法高效使用索引，应写成 WHERE phone = '13800138000'。
  5. LIKE 模糊查询以 % 开头。如 LIKE '%abc'、LIKE '%abc%' 无法确定起始部分，普通 B+ 树索引无法用于范围定位；而 LIKE 'abc%' 通常可以用上索引。

此外还有两种常被追问的情况：

  • OR 连接的条件中有一侧没有索引，整体往往退化为全表扫描；
  • 数据分布导致优化器判断全表扫描更快（如查询结果占全表比例过大）。

实际分析时通过 EXPLAIN 查看使用的索引、访问类型和预估扫描行数，判断是否真正利用了索引。

SQL 优化实战面试题 ​

1. MySQL 深分页怎么优化？（含完整 SQL 案例）

深分页变慢，主要是因为 LIMIT 的偏移量越大，需要扫描并丢弃的记录就越多。比如 LIMIT 1000000, 10 要先跳过前 100 万条，再返回 10 条；如果还涉及回表或额外排序，开销更大。

方案一：覆盖索引 + 延迟关联。 先在子查询中利用索引完成过滤、排序和分页，只查出当前页的主键 id，再与原表关联获取完整数据，并在外层显式排序保证顺序。这样分页扫描只需读索引，不必为大量最终被丢弃的记录读整行数据，减少回表和数据读取开销。但它仍然需要扫描并跳过前面的记录，并没有消除大偏移量的成本。

方案二：游标式分页。 如果业务只需要上一页、下一页，不要求跳到任意页，可以记录上一页最后一条数据的排序键，下次从这个位置继续查。按主键递增分页时用 WHERE id > 上一页最后的 id；如果按其他字段排序，要把主键作为辅助排序键保证排序唯一，避免同值记录遗漏。

假设用户表 tb_user 使用 InnoDB，id 是主键，含 name、age、create_time 等字段，按创建时间升序分页，并用 id 保证排序唯一：

sql
-- 建立联合索引，支持排序，并覆盖子查询所需的字段
CREATE INDEX idx_create_time_id ON tb_user (create_time, id);

-- 1. 原始深分页：偏移量越大，扫描和数据读取开销越大
SELECT id, name, age, create_time
FROM tb_user
ORDER BY create_time, id
LIMIT 1000000, 10;

-- 2. 覆盖索引 + 延迟关联：先查当前页的主键，再取完整数据
SELECT u.id, u.name, u.age, u.create_time
FROM tb_user AS u
JOIN (
    SELECT id, create_time
    FROM tb_user
    ORDER BY create_time, id
    LIMIT 1000000, 10
) AS page ON u.id = page.id
ORDER BY page.create_time, page.id;

-- 3. 游标式分页：假设上一页最后一条记录的时间和 id 如下
SELECT id, name, age, create_time
FROM tb_user
WHERE create_time > '2026-01-01 10:00:00'
   OR (create_time = '2026-01-01 10:00:00' AND id > 10086)
ORDER BY create_time, id
LIMIT 10;

第二种方案仍要扫描前面的索引记录，但只对当前页的 10 条记录获取完整数据；第三种方案从上一页的排序位置继续查，不使用大偏移量，但不适合直接跳到任意页。实际索引使用情况可通过 EXPLAIN 检查。

2. 你有哪些 SQL 优化经验？

先定位问题，再有针对性地优化。 先通过监控或慢查询日志找到慢 SQL，再结合 EXPLAIN 分析索引使用、扫描行数和排序情况，同时排查是否存在锁等待。

具体从三个方面入手：

  • 表结构：根据业务选择合适的字段类型和长度，避免不必要的大字段；
  • 索引：针对高频查询设计合适的联合索引，尽量利用覆盖索引减少回表，并避免索引失效；
  • SQL 写法：只查需要的字段，优化表关联和深分页，减少不必要的扫描、排序和重复查询。

如果单条 SQL 优化后数据库整体压力仍然较大，再考虑主从复制和读写分离分担读请求，但要注意复制延迟和数据一致性；如果数据量和访问量持续增长，才进一步评估数据归档或分库分表，不会一开始就上复杂架构。

最后会对比优化前后的执行计划和耗时，通过压测验证效果。

3. 创建表的时候，你们是如何优化的？

建表主要参考阿里巴巴《Java 开发手册（嵩山版）》，结合业务需求选择合适的字段类型和长度，在满足业务的前提下避免不必要的存储开销：

  • 数值字段：按取值范围选择 TINYINT / INT / BIGINT，而不是统一用 BIGINT；
  • 金额字段：需要精确计算的用 DECIMAL，避免浮点数精度问题；
  • 字符串字段：长度固定的内容可考虑 CHAR，长度变化大的用 VARCHAR 并合理设置最大长度；确实需要长文本再用 TEXT；不常查询的大字段可按业务拆到扩展表，减少主表查询时的数据读取开销；
  • 约束与索引：设置合适的主键，业务上不允许为空的字段加 NOT NULL，并根据实际查询需求设计索引。

整体原则：类型合适、长度合理、约束明确，兼顾查询和写入成本。

4. 你平时对 SQL 语句做了哪些优化？

前提是保证查询结果和业务含义不变：

  1. 只查询需要的字段，避免不必要的 SELECT *，减少数据读取和网络传输开销；如果所需字段都能从索引中获取，还能利用覆盖索引减少回表。
  2. 注意查询条件的写法，避免在索引列上做运算、调用函数或发生隐式类型转换；使用联合索引时注意最左前缀原则。
  3. 按需选择 UNION 或 UNION ALL。业务不需要去重就用 UNION ALL，避免 UNION 额外的去重开销；需要去重则不能直接替换。
  4. 优化表关联查询，为关联字段建合适的索引，并尽量通过过滤条件减少参与连接的数据量。INNER JOIN、LEFT JOIN、RIGHT JOIN 要按业务需求选择，不能为了性能随意替换；嵌套循环连接通常希望过滤后数据量较小的一侧作为驱动表，但实际连接顺序和算法要结合执行计划判断。
  5. 优化深分页和重复查询，按场景使用覆盖索引加延迟关联或游标式分页；同时避免在循环中逐条查询，能批量获取的尽量批量查询。

优化后结合 EXPLAIN 和实际执行耗时验证效果，而不是只凭 SQL 写法判断性能。

InnoDB 特点与引擎对比面试题 ​

1. InnoDB 有哪些核心特点？

InnoDB 是 MySQL 5.5 之后的默认存储引擎，面向事务型（OLTP）业务设计：

  1. 支持事务 —— 完整实现 ACID，默认隔离级别可重复读（RR）；原子性由 undo log 保证，持久性由 redo log 保证，隔离性由锁 + MVCC 保证；
  2. 支持行级锁 —— 锁加在索引上，命中索引才是行锁，索引失效会退化成表锁，并发性能远高于表锁引擎；
  3. 支持 MVCC —— 多版本并发控制，读写互不阻塞，快照读不加锁；
  4. 支持外键约束 —— 可以保证表之间的引用完整性（实际项目中常因性能考虑不使用）；
  5. 采用聚簇索引 —— 数据和主键索引在同一棵 B+ 树的叶子节点上，二级索引叶子节点存主键值，所以需要回表；
  6. 崩溃自动恢复（crash-safe） —— 基于 redo log，异常宕机重启后能恢复到一致状态；
  7. 有 Buffer Pool 缓冲池 —— 缓存数据页和索引页，大幅减少磁盘 IO；
  8. 必须有主键 —— 没有显式主键时会选一个唯一非空索引，再没有则自动生成 6 字节隐藏 row_id；
  9. 不保存表的总行数 —— count(*) 需要实时扫描统计。

事务、日志与 MVCC 面试题（口述版） ​

1. 事务的特性是什么？能举例说明吗？

ACID，分别指原子性、一致性、隔离性、持久性。以 A 向 B 转账 500 为例：

  • 原子性：A 扣 500、B 加 500 这两步要么都成功，要么都失败；
  • 一致性：转账过程中数据要一致，A 扣了 500，B 必须增加 500；
  • 隔离性：A 向 B 转账的过程不能受其他事务干扰；
  • 持久性：事务提交后数据要持久化（落盘），宕机也不丢。

3. 怎么解决这些问题？MySQL 默认隔离级别是什么？

通过设置合适的事务隔离级别，控制并发事务之间的相互影响。四种级别从低到高：

MySQL InnoDB 默认隔离级别是可重复读（RR）。 上表描述的是 SQL 标准，InnoDB 的实现有所不同：RR 下普通快照读通过 MVCC 复用读视图，避免重复查询出现幻读；锁定读和更新等操作则通过临键锁（记录锁 + 间隙锁）阻止其他事务在相关范围插入记录。因此不能简单说「InnoDB 的 RR 完全不能解决幻读」；但混用快照读和当前读时，也不能保证所有读取都看到同一份快照。

注意：隔离级别越高，一致性保障通常越强，但并发限制和开销也可能越大。 并不是级别越高就一定越慢，实际性能还取决于访问模式、锁冲突和事务长度。应根据业务需求选择合适的级别，并尽量缩短事务、及时提交。

4. undo log 和 redo log 的区别？
  • redo log 记录的是数据页的物理变化，服务宕机后可用来恢复/同步数据，保证事务的持久性；
  • undo log 记录的是逻辑日志，事务回滚时通过逆操作恢复原来的数据。比如删除一条数据时，undo log 里会记下一条对应的插入逆操作，回滚时执行它，保证事务的原子性和一致性。
5. 事务的隔离性是如何保证的？（讲一下 MVCC）

隔离性由锁 + MVCC 实现。MVCC 即多版本并发控制，指维护一份数据的多个版本，使读写操作不冲突，底层由三部分组成：

  • 隐藏字段：MySQL 给每张表都设置了隐藏字段，trx_id（事务 id）记录每一次操作的事务 id，是自增的；roll_pointer（回滚指针）指向上一个版本的事务版本记录地址；
  • undo log：记录回滚日志、存储老版本数据。多个事务并行操作同一行记录时，会通过 roll_pointer 把不同版本串成一个版本链；
  • ReadView（读视图）：解决「事务查询时该读哪个版本」的问题，内部按匹配规则结合当前活跃事务 id 判断访问哪个版本。不同隔离级别下快照读的表现不同：RC 每次执行快照读都生成新的 ReadView；RR 仅在事务中第一次快照读时生成 ReadView，后续复用，这正是 RR 能避免不可重复读的原因。

主从复制与分库分表面试题 ​

1. MySQL 主从同步原理是什么？

核心是 Binlog（二进制日志）：主库记录数据变更，从库接收这些记录，再按记录执行相应的变更，让自己的数据逐步与主库保持一致。分三步：

  1. 主库记录日志：主库执行数据变更，并在事务提交过程中把变更事件记录到 Binlog。Binlog 可以记录建表、改表结构以及增删改操作；根据日志格式不同，记录的可能是 SQL 语句，也可能是行数据的变化。
  2. 从库接收日志：从库的 IO 接收线程向主库请求 Binlog，主库通过 dump 发送线程传输日志，从库收到后写入自己的 Relay Log（中继日志）。
  3. 从库应用日志：从库的 SQL 执行线程读取中继日志，执行其中的变更事件，更新从库数据。
text
主库                                   从库
执行变更 → 写 Binlog
                  ──（dump 线程发送）──→ IO 线程接收 → 写 Relay Log
                                                        ↓
                                              SQL 线程重放 → 更新数据

一句话记忆：主库写 Binlog → 从库接收并写入 Relay Log → 从库执行日志中的变更。 默认主从复制是异步的，主库提交后从库不一定马上能查到最新数据，做读写分离时要注意复制延迟。

2. 你们项目用过 MySQL 的分库分表吗？

我们项目是微服务架构，按业务划分数据库，每个微服务使用自己的数据库，这属于按业务垂直分库：把不同业务的表放到不同的库中，让各业务的数据管理更独立。

垂直分库和水平拆分的区别：垂直分库是把不同业务的表分开；水平拆分是把同一张表中的数据按规则分开，分散到多个库或表中。多个库如果仍部署在同一台服务器上，也不一定能分摊服务器的资源压力。

3. 之前使用过水平分库吗？怎么做的？

用过。当时业务是（xxx），最初是单库，随着业务增长（xx）表的数据超过了 1000 万条，查询和写入压力不断增加。在做过索引、SQL 等优化后单库仍难以满足需求，才考虑水平分库。不是数据超过 1000 万条就必须分库，关键看单库是否已经成为瓶颈。

当时用了 3 台服务器，每台部署一个数据库，通过 Mycat 做分片路由：数据按 id 对 3 取模，余数 0、1、2 分别进入三个库，同一张逻辑表的数据就被分散到不同服务器上。已有的历史数据先做清洗，再按相同的分片规则迁移到各个库中。

这样可以分摊单库的存储和访问压力，但也会增加跨库查询、事务处理以及数据迁移的复杂度。

两个必须提前考虑的坑：

  • 扩容问题：按 id 取模分片时，如果直接把库数量从 3 改成 4，大量数据对应的目标库都会变化，需要重新迁移（可用一致性哈希或成倍扩容来缓解）；
  • 主键生成：自增 id 要有统一的生成机制（如雪花算法），避免各库独立生成时出现重复。

面试回答的通用套路

是什么 → 为什么 → 怎么做 → 有什么坑。 不要只背结论，一定要能说出代价和适用边界，例如"索引能加速查询，但会拖慢写入并占空间，所以单表控制在 5~6 个"。
