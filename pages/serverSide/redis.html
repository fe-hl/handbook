为什么需要 Redis？ ​

核心概念

Redis（REmote DIctionary Server） 是一个用 ANSI C 编写的基于内存的 key-value 数据结构服务器。它把数据放在内存里保证极致读写速度，同时提供持久化、主从复制、集群等能力，既能当缓存，也能当轻量数据库、消息队列和分布式协调组件。

业务量上来后，纯靠关系型数据库（MySQL）会先在这些地方顶不住：

单库痛点具体表现
磁盘 IO 瓶颈热门商品详情页每秒几万次查询，全部落到 MySQL，磁盘随机读被打满
复杂计算慢排行榜、UV 统计、附近的人，用 SQL 做聚合动辄几百毫秒
无法扛突发流量秒杀瞬间涌入，连接池被打满，连正常下单请求也被拖死
缺少共享内存多台应用服务器各自的本地缓存不一致，Session 无法共享
原子操作难扣库存、限流计数要靠行锁或分布式锁，MySQL 锁竞争严重

生活类比

MySQL 像仓库：东西全、容量大，但每次取货要走进去翻找；Redis 像收银台旁的货架：只放最常卖的爆款，伸手就能拿到。热门商品放货架（缓存），冷门商品才去仓库（回源数据库）。

Redis 为什么快 ​

  1. 纯内存操作：数据常驻内存，避免磁盘随机 IO，读 ≈ 10 万 QPS，写 ≈ 8 万 QPS
  2. 单线程模型（命令执行）：命令串行执行，没有多线程上下文切换和锁竞争，天然原子
  3. IO 多路复用：基于 epoll 的事件驱动，一个线程可同时监听上万连接，连接多但不阻塞
  4. 高效数据结构：SDS、ziplist/listpack、quicklist、skiplist、intset 都针对内存和复杂度做了优化
  5. RESP 协议简洁：文本协议解析成本低，支持 Pipeline 批量发送减少 RTT

「单线程」说的是哪一部分

Redis 执行命令的主逻辑是单线程，但它从来不是只有一个线程。Redis 4.0 起有后台线程做 UNLINK、FLUSHALL ASYNC 等惰性删除；Redis 6.0 起支持 IO 多线程（io-threads），用多线程并行读写 socket 和解析协议，但命令执行依然是单线程串行的。所以「单线程」≠「单核性能」，也不代表不能用多核。

NoSQL 与 Redis 的定位 ​

核心概念

NoSQL（Not Only SQL） 泛指非关系型数据库。它不以二维表 + 外键建模，而是用 key-value、文档、列族、图等更简单灵活的结构存储数据，换来水平扩展能力和极高吞吐。

NoSQL 与关系型数据库的边界 ​

维度关系型数据库（MySQL）NoSQL（Redis / MongoDB）
数据模型严格表结构、强 Schemakey-value / 文档，Schema 自由
查询能力完整 SQL、多表 JOIN、聚合按 key 访问，JOIN 能力弱或无
事务完整 ACID、可回滚弱事务，Redis 事务不支持回滚
扩展方式垂直扩容为主，分库分表复杂天然支持水平扩展（分片）
一致性强一致多为最终一致（AP 倾向）
适用交易、对账、强一致业务缓存、计数、海量读写、日志

不要用 Redis 替代主库

Redis 不适合做业务主存储：① 内存成本是磁盘的几十倍；② 事务无回滚、没有外键约束；③ 复杂条件查询（WHERE age > 18 AND city = ...）需要自己维护索引 key，极易写错。正确姿势是：MySQL 存全量数据，Redis 缓存热点数据。

选型口诀

问自己一句：「这份数据丢了会不会导致业务算错账？」 会 → 放 MySQL；不会（只是变慢）→ 可以放 Redis。

Key 操作与核心机制 ​

核心概念

Redis 是一个巨大的 全局哈希表：key 一律是 二进制安全的字符串，value 才分 String / List / Hash / Set / ZSet 等类型。所有「数据类型」的区别都在 value 上，key 的操作命令是通用的。

通用 Key 命令 ​

命令作用说明
KEYS pattern按模式匹配所有 key⛔ 线上禁用，O(N) 会阻塞主线程
SCAN cursor MATCH COUNT游标式分批遍历✅ 线上替代 KEYS 的正确方案
EXISTS key [key...]判断是否存在，返回存在的个数可一次传多个 key
TYPE key查看 value 类型string/list/hash/set/zset/stream
DEL key同步删除删大 key 会阻塞
UNLINK key异步删除（4.0+）✅ 删大 key 用它，后台线程回收内存
EXPIRE key seconds设置过期时间（秒）PEXPIRE 为毫秒
TTL key剩余存活秒数-1 永不过期，-2 key 不存在
PERSIST key移除过期时间，变永久—
RENAME key newkey重命名（newkey 存在则覆盖）RENAMENX 仅当 newkey 不存在才改
DBSIZE当前库 key 总数O(1)，可安全使用
FLUSHDB / FLUSHALL清空当前库 / 所有库⛔ 高危，建议 rename-command 禁用
bash
# ❌ 线上事故写法：10 万 key 的实例会卡住主线程数百毫秒
KEYS user:*

# ✅ 正确写法：游标分批扫，每次只取约 100 个
SCAN 0 MATCH "user:*" COUNT 100
# 返回 1) "2048"（下一次游标，为 0 表示遍历结束）  2) 1) "user:1" 2) "user:2"...

SCAN 的三个必须知道的特性

  1. 游标不是下标，必须把上一次返回的 cursor 原样传回，直到返回 0 才算遍历完；
  2. COUNT 只是「每次扫多少个槽」的提示，返回条数可能为 0 也可能多于 COUNT，不能用「返回空」判断结束；
  3. 它保证遍历期间始终存在的 key 一定被返回，但可能重复返回同一个 key —— 业务侧要做幂等处理。

Key 的命名规范 ​

bash
# ✅ 推荐：业务:对象:标识[:属性]，用冒号分层，Redis 客户端会自动折叠成树形
order:detail:202603150001
user:profile:10086
rank:sales:2026-03

# ❌ 反例
u10086                # 看不出含义，无法批量运维
用户信息_10086        # 含中文和下划线，排查时难输入
order:detail:{...整个JSON 2MB...}   # key 过长，浪费内存且影响哈希计算

三条经验

  • 长度：key 控制在 44 字节以内更省内存（embstr 编码边界同理于 value）；
  • 类型：同一个 key 不要先存 String 再改存 Hash，TYPE 不匹配会直接报 WRONGTYPE；
  • 过期：缓存类 key 一律加 TTL。不加 TTL 的 key 会一直占内存，最终触发淘汰策略把真正的热点数据挤掉。

String：最常用也最容易用错 ​

核心概念

String 是 Redis 最基础的类型，value 是二进制安全的字节序列，可以存文本、JSON、序列化对象甚至图片，单个 value 上限 512MB。它内部有三种编码：int（整数）、embstr（≤44 字节短串）、raw（长串），由 Redis 自动选择。

常用命令 ​

命令作用典型用途
SET k v [EX s] [NX/XX]赋值，可同时设过期与存在性条件缓存写入、分布式锁
GET k取值缓存读取
SETNX k v仅当 key 不存在时设置抢占式加锁（老写法）
MSET / MGET批量读写一次往返取多个值
INCR / DECR原子 ±1计数器、库存
INCRBY / INCRBYFLOAT原子增减指定值余额、积分
APPEND k v追加字符串日志拼接
STRLEN k值的字节长度—
GETRANGE / SETRANGE按下标读 / 改子串定长协议解析
GETSET / GETDEL取旧值并写新值 / 取值并删除重置计数器
bash
# 原子计数 —— 这是 Redis 做计数器的根本原因
INCR article:view:1001          # 返回 1
INCRBY article:view:1001 10     # 返回 11

# 带条件 + 过期的原子写入（分布式锁基础）
SET lock:order:1001 uuid-abc EX 10 NX   # 成功返回 OK，key 已存在返回 nil

INCR 不是「读出来 +1 再写回」

javascript
// ❌ 并发下会丢更新：两个请求都读到 100，都写回 101，实际应为 102
const v = await redis.get("count");
await redis.set("count", Number(v) + 1);

// ✅ 单条命令在服务端原子执行，天然并发安全
await redis.incr("count");

这正是「Redis 单线程」带来的红利：单个命令一定是原子的，不需要加锁。但 INCR 要求 value 必须是能被解析为 64 位整数的字符串，否则报 value is not an integer or out of range。

SET 的参数组合要背熟 ​

bash
SET k v NX          # 不存在才设置，等价 SETNX（加锁）
SET k v XX          # 存在才设置（只更新不新增）
SET k v EX 60       # 60 秒后过期
SET k v PX 60000    # 60000 毫秒后过期
SET k v KEEPTTL     # 更新值但保留原有剩余 TTL（6.0+）
SET k v EX 10 NX    # 加锁标准写法：原子地「加锁 + 设超时」

为什么必须用 SET k v EX 10 NX 而不是两条命令

bash
# ❌ 两条命令之间若进程崩溃，锁将永不过期 → 死锁
SETNX lock 1
EXPIRE lock 10

# ✅ 一条命令原子完成，不存在中间状态
SET lock 1 EX 10 NX

String 的内存坑 ​

bash
# ❌ 反例：把整个用户对象 JSON 存成一个 String
SET user:10086 '{"name":"Tom","age":20,"city":"BJ", ...50个字段... }'
# 想改 age 必须：GET 全量 → JSON.parse → 改 → stringify → SET 全量

# ✅ 字段多且需局部更新时，改用 Hash
HSET user:10086 name Tom age 20 city BJ
HINCRBY user:10086 age 1     # 只动一个字段

List：双端链表与消息队列 ​

核心概念

List 是有序、可重复的字符串列表，支持从两端插入弹出，底层在 3.2+ 统一为 quicklist（ziplist 组成的双向链表）。它既能当栈（同端进出），也能当队列（一端进另一端出），还能当阻塞队列。

阻塞队列：BLPOP vs 轮询 ​

javascript
// ❌ 轮询：空队列时疯狂请求，浪费 CPU 和网络
while (true) {
  const task = await redis.lpop("queue:task");
  if (!task) await sleep(100); // 还引入了最多 100ms 延迟
  else handle(task);
}

// ✅ BRPOP：服务端挂起连接，有数据立刻返回，零延迟零空转
while (true) {
  // 返回 [key, value]；0 表示无限等待，生产建议给 5~30 秒避免连接被中间件掐断
  const res = await redis.brpop("queue:task", 10);
  if (res) handle(res[1]);
}

List 做消息队列的三个硬伤

  1. 消息会丢：LPOP 取出即从 Redis 删除，消费者处理中崩溃，消息就没了（可用 LMOVE 搬到「处理中」队列做 ack 补偿）；
  2. 不支持多消费者组：一条消息只能被一个消费者拿到，做不到 Kafka 那种「同一消息投递给多个消费组」；
  3. 没有回溯和堆积可见性：消费完就没了，无法重放。

👉 真要用 Redis 做队列，优先选 Stream（有消费者组 + ack + 回溯），而不是 List。重要业务消息请用 RocketMQ / Kafka。

Hash：存对象的首选 ​

核心概念

Hash 是 field → value 的映射表，相当于「Redis 里的一个小 HashMap」。它最大的价值是支持对单个字段的读写，不必像 String 那样整体序列化/反序列化。

常用命令 ​

小 Hash 是省内存神器

Set：去重与集合运算 ​

核心概念

Set 是无序、不重复的字符串集合。它的独门绝技是集合运算：交集（共同好友）、并集（标签合并）、差集（我关注但他没关注）。底层为 intset（全整数且元素少）或 hashtable。

常用命令 ​

集合运算务必控制规模

ZSet：排行榜与延迟队列 ​

核心概念

ZSet（Sorted Set）= Set + 每个元素带一个 score（double 分值），集合按 score 排序。它是 Redis 中唯一支持范围查询的集合类型，底层为 listpack（小数据）或 跳表 + 哈希表（大数据）：跳表保证范围查询 O(logN)，哈希表保证按成员查 score 为 O(1)。

常用命令 ​

命令作用
ZADD k [NX/XX/GT/LT] score m添加/更新元素及分值
ZINCRBY k n m给成员分值原子增减

ZCARD k / ZCOUNT k min max总数 / 分值区间内的数量

ZRANK / ZREVRANK k m查成员排名（从 0 开始）

ZREMRANGEBYRANK/BYSCORE按排名 / 分值区间批量删除
ZPOPMIN / ZPOPMAX弹出分值最小 / 最大的成员

用 ZSet 实现订单超时延迟队列

这是「订单 30 分钟未支付自动关闭」最常见的轻量实现。

ZSet 的两个高频坑

  1. score 是 double，超过 2^53 的整数会丢精度。存毫秒时间戳（13 位，约 1.7e12）安全，但不要把「时间戳 * 1000000 + 自增 id」这种大数塞进 score；
  2. 相同 score 按成员字典序排序。做排行榜时若想实现「同分者先达到的排前面」，常用技巧是 score = 分数 * 10^10 + (最大时间戳 - 达成时间)，用低位反向编码时间。

高级类型：Bitmap / HyperLogLog / GEO / Stream ​

Bitmap：用位省内存 ​

核心概念

Bitmap 不是独立类型，而是在 String 上按位（bit）操作。1 个 bit 表示一个布尔状态，1 亿用户的「是否签到」只需 100000000 / 8 / 1024 / 1024 ≈ 12MB。

bash
# 日活统计：offset = 用户 id
SETBIT active:2026-03-15 10086 1     # 用户 10086 今日活跃
GETBIT active:2026-03-15 10086       # 查某人是否活跃 → 1
BITCOUNT active:2026-03-15           # 今日活跃总人数

# 连续活跃用户（两天都活跃 = 按位与）
BITOP AND active:both active:2026-03-14 active:2026-03-15
BITCOUNT active:both

# 月签到：31 个 bit 搞定一个用户一个月
SETBIT sign:10086:202603 14 1        # 3 月 15 日签到（offset 从 0 开始）
BITCOUNT sign:10086:202603           # 本月签到天数
BITPOS   sign:10086:202603 0         # 第一个未签到的日子

Bitmap 的 offset 陷阱

SETBIT key 100000000 1 会立刻分配 12MB 内存（Redis 要把中间所有位补 0）。所以 offset 千万不要直接用「毫秒时间戳」或「雪花 id」这类巨大数值，必须先映射成从 0 开始的紧凑序号，否则一条命令就能打爆内存并阻塞主线程。

HyperLogLog：12KB 算基数 ​

核心概念

HLL 是一种概率基数统计算法：无论塞入多少元素，固定只占约 12KB，能统计「不重复元素个数」，标准误差 0.81%。

bash
PFADD uv:2026-03-15 user1 user2 user3
PFADD uv:2026-03-15 user1            # 重复元素不会增加基数
PFCOUNT uv:2026-03-15                # → 3（近似值）
PFMERGE uv:week uv:2026-03-14 uv:2026-03-15   # 合并多天去重后的 UV
方案1 亿 UV 的内存精确度能否取出成员
Set数 GB精确能
Bitmap约 12MB精确能（按位）
HyperLogLog12KB±0.81%不能

选型判断

要精确值或要知道具体是谁 → Set / Bitmap；只要一个「大概多少人」的运营数字 → HyperLogLog。注意 UV 报表若与财务结算相关（如按去重用户数结算广告费），不能用 HLL。

GEO：地理位置 ​

核心概念

GEO 本质是 ZSet：把经纬度用 GeoHash 编码成一个 52 位整数作为 score，于是「查附近」就变成了「查 score 区间」。

bash
GEOADD shops 116.397 39.908 "店A" 116.405 39.915 "店B"
GEODIST shops "店A" "店B" km                 # 两店距离
GEOSEARCH shops FROMLONLAT 116.40 39.91 BYRADIUS 5 km ASC WITHDIST
# 以当前坐标为中心查 5 公里内的店，按距离升序并返回距离（6.2+ 推荐用法）
GEOPOS shops "店A"                           # 查坐标
ZREM shops "店A"                             # 删除就是 ZSet 的删除

Stream：真正的消息队列 ​

核心概念

Stream（5.0+）是 Redis 官方的消息队列实现：append-only 日志 + 消费者组 + ACK 确认 + 消息回溯，补齐了 List 和 Pub/Sub 的全部短板。

bash

# 创建消费者组，从头开始消费
XGROUP CREATE orders g1 0

# 消费者 c1 读取新消息（> 表示未被本组消费过的）
XREADGROUP GROUP g1 c1 COUNT 10 BLOCK 2000 STREAMS orders >

# 处理成功后确认
XACK orders g1 1773000000000-0

# 查看本组已投递但未 ACK 的消息（宕机恢复的关键）
XPENDING orders g1
# 把超时未 ACK 的消息转移给其他消费者
XCLAIM orders g1 c2 60000 1773000000000-0

XTRIM orders MAXLEN 10000        # 只保留最新 1 万条，防止无限增长

Pub/Sub 不要用来传重要消息

PUBLISH / SUBSCRIBE 是即发即弃的：订阅者不在线就永久丢失，也没有 ACK 和持久化。它只适合做「配置变更通知」「缓存失效广播」这类可丢失的信号，绝不能用于订单、支付等业务消息。

案例一：秒杀库存扣减 ​

lua
-- stock.lua：判断 + 扣减必须原子，否则会超卖

javascript
// ❌ 两步走必超卖：高并发下大量请求同时读到 stock = 1
const stock = await redis.get("stock:sku:1001");
if (Number(stock) > 0) await redis.decr("stock:sku:1001"); // 可能扣成负数

const left = await redis.eval(script, 1, "stock:sku:1001", 1);

为什么不直接用 DECR 的返回值判断

DECR 可以判断返回值是否 < 0，但那时库存已经被扣成负数，需要再 INCR 回滚；回滚期间其它请求读到的是错误的负库存。用 Lua 做「先判断后扣减」才能保证库存永不为负。

案例三：接口限流（滑动窗口） ​

lua
-- 1 分钟内最多 100 次请求
-- KEYS[1]=limit:api:uid  ARGV[1]=当前毫秒  ARGV[2]=窗口60000  ARGV[3]=上限100
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1] - ARGV[2])  -- 清理窗口外记录
local cnt = redis.call('ZCARD', KEYS[1])
if cnt >= tonumber(ARGV[3]) then return 0 end                  -- 超限
redis.call('ZADD', KEYS[1], ARGV[1], ARGV[1])                  -- 记录本次
redis.call('PEXPIRE', KEYS[1], ARGV[2])                        -- 防止冷 key 堆积
return 1

固定窗口 vs 滑动窗口

INCR + EXPIRE 60 实现的是固定窗口：在 0:59 和 1:01 各打满 100 次，2 秒内实际放过 200 次请求（临界突刺）。上面用 ZSet 的滑动窗口能精确限制「任意连续 60 秒内不超过 100 次」，代价是每个请求要存一条记录，内存更高。QPS 极高的场景应改用令牌桶。

核心概念

public class RedisUtil {
    private static final JedisPool POOL;

    static {
        JedisPoolConfig cfg = new JedisPoolConfig();
        cfg.setMaxTotal(50);                 // 最大连接数
        cfg.setMaxIdle(10);                  // 最大空闲
        cfg.setMinIdle(5);                   // 预热最小空闲，避免首次请求现建连接
        cfg.setMaxWait(Duration.ofMillis(200)); // 拿不到连接最多等 200ms 就失败

    }

    public static Jedis getJedis() {
        return POOL.getResource();
    }
}

管道（Pipeline）批量提交 ​

java
// ❌ 1 万次循环 = 1 万次网络往返（RTT 0.5ms → 耗时 5 秒）
for (int i = 0; i < 10000; i++) jedis.set("k" + i, "v" + i);

// ✅ Pipeline 一次性发送，1 次往返（耗时几十毫秒）

}

Pipeline 不是事务

Pipeline 只是把多条命令打包减少 RTT，它不保证原子性：中间某条命令失败，其他命令依然会执行，而且期间其他客户端的命令可能插在中间执行。需要原子性请用 MULTI/EXEC 或 Lua。另外单个 Pipeline 不要打包过多命令（建议 ≤ 1000 条一批），否则会撑大服务端输出缓冲区。

过期删除与内存淘汰 ​

核心概念

这是两个完全不同的机制，面试极易混淆：

  • 过期删除：key 自己设了 TTL，时间到了被清理 —— 处理「该走的 key」；
  • 内存淘汰：内存达到 maxmemory，Redis 被迫挑一些 key 删掉腾空间 —— 处理「内存不够」，没设 TTL 的 key 也可能被删。

过期删除的三种策略 ​

┌─────────────────────────────────────────────────────┐
│  惰性删除（Lazy）                                    │
│  访问 key 时才检查是否过期 → 过期则删除并返回 nil     │
│  优点：零额外 CPU   缺点：永不访问的 key 永久占内存    │
├─────────────────────────────────────────────────────┤
│  定期删除（Active）                                  │
│  每秒 10 次（hz=10），每次随机抽 20 个带 TTL 的 key，  │
│  删掉其中已过期的；若过期比例 > 25% 则立刻再抽一轮，   │
│  单轮耗时上限 25ms，防止阻塞主线程                    │
│  优点：能回收冷数据   缺点：有抽样遗漏，非实时         │
├─────────────────────────────────────────────────────┤
│  Redis 实际采用：惰性删除 + 定期删除 组合             │
│  （不采用「定时删除」：每个 key 挂一个定时器太耗资源） │
└─────────────────────────────────────────────────────┘

过期 key 不是「到点立刻消失」

由于是抽样回收，一个已过期的 key 可能在内存里多停留一段时间。所以： ① 不能依赖 TTL 做精确的时间逻辑（比如用 key 是否存在判断「活动是否已结束」，应改为比较时间戳）； ② DBSIZE 和 INFO keyspace 里的数量包含尚未被回收的过期 key，统计口径要注意； ③ 主从环境下，从节点不会自己删过期 key，而是等主节点的 DEL 命令同步过来。因此在从节点上读取一个「刚过期」的 key，旧版本 Redis 可能读到旧值（3.2+ 已修正为返回 nil，但内存仍未释放）。

八种内存淘汰策略 ​

策略作用范围淘汰依据适用场景
noeviction不淘汰—默认值，写命令直接报 OOM
allkeys-lru所有 key最久未使用✅ 纯缓存场景首选
allkeys-lfu所有 key使用频率最低✅ 有明显热点数据时更优
allkeys-random所有 key随机key 访问概率均匀时
volatile-lru仅带 TTL 的 key最久未使用缓存与持久数据混存
volatile-lfu仅带 TTL 的 key使用频率最低同上，有热点时
volatile-random仅带 TTL 的 key随机—
volatile-ttl仅带 TTL 的 key剩余存活时间短希望先淘汰快到期的

volatile-* 策略的致命陷阱

如果选了 volatile-lru，但业务中有相当比例的 key 没设 TTL，那么内存满时 Redis 找不到可淘汰的 key，行为退化为 noeviction，所有写命令开始报错：

(error) OOM command not allowed when used memory > 'maxmemory'

这是线上「Redis 突然只能读不能写」的典型原因。

决策建议：

  • 实例纯做缓存 → allkeys-lru（或有热点时用 allkeys-lfu），并给所有 key 加 TTL；
  • 实例里混有不能丢的数据（如分布式锁、幂等标记）→ 先考虑物理隔离到另一个实例，而不是靠 volatile-* 策略去保护。

LRU vs LFU ​

场景：某个月初活动页被访问 1 万次，之后再无人访问；
      某个商品详情页每天稳定被访问 500 次。

LRU（最近最少使用）：
  只看「最后一次访问时间」
  → 活动页刚被访问过，被保留；稳定的商品页反而可能被淘汰  ❌

LFU（最不常使用，4.0+）：
  看「访问频率」，且频率会随时间衰减（lfu-decay-time）
  → 活动页热度衰减后被淘汰，长期稳定的商品页被保留        ✅

持久化：RDB 与 AOF ​

核心概念

Redis 数据在内存，重启即丢，所以需要持久化：

  • RDB：某一时刻的全量内存快照（二进制压缩文件），恢复快、体积小；
  • AOF：追加写命令日志（文本协议），丢数据少、可读性好；
  • 混合持久化（4.0+）：AOF 文件的开头是 RDB 格式的全量快照，后面追加增量命令 —— 兼顾两者优点。

RDB 配置与原理 ​

bash
# save <秒数> <修改次数>：满足任一条件即触发 bgsave
save 3600 1        # 1 小时内有 1 次修改
save 300 100       # 5 分钟内有 100 次修改
save 60 10000      # 1 分钟内有 1 万次修改
# save ""          # 注释掉所有 save 即关闭 RDB 自动触发

dbfilename dump.rdb
dir /var/lib/redis
rdbcompression yes            # 用 LZF 压缩字符串，省磁盘略耗 CPU
rdbchecksum yes               # 校验和，防止文件损坏
stop-writes-on-bgsave-error yes  # bgsave 失败时拒绝写入（提醒你磁盘满了）
BGSAVE 的 fork + COW 机制：

主进程                            子进程
  │                                 │
  ├── fork() ──────────────────────▶ 复制页表（不复制数据）
  │   （此刻会短暂阻塞，耗时与内存量成正比）
  │                                 │
  ├── 继续处理客户端命令             ├── 遍历内存，写 temp.rdb
  │   写操作触发 Copy-On-Write      │
  │   → 复制被修改的内存页          │
  │   → 内存占用最多翻倍            ├── 写完后 rename 为 dump.rdb
  ▼                                 ▼
命令行为线上可用性
SAVE主线程同步生成快照，期间完全阻塞⛔ 绝对禁用
BGSAVEfork 子进程后台生成，主线程几乎不受影响✅ 自动触发用的就是它

fork 的隐藏成本

fork() 本身不复制数据，但要复制页表。10GB 内存的实例，页表约 20MB，fork 耗时可达 几十到上百毫秒，这段时间 Redis 完全无法响应。再加上 COW 可能让内存翻倍，所以： ① 单实例内存不要超过 10GB，大了就分片； ② vm.overcommit_memory = 1（否则内存不足时 fork 直接失败）； ③ 关闭 THP（透明大页），否则 COW 的复制单位从 4KB 变成 2MB，延迟飙升。

AOF 配置与原理 ​

bash
appendonly yes                    # 开启 AOF
appendfilename "appendonly.aof"
appenddirname "appendonlydir"     # 7.0+ 使用 multi-part AOF 目录

appendfsync everysec              # 刷盘策略（见下表）
no-appendfsync-on-rewrite no      # 重写期间是否暂停 fsync（yes 可降延迟但可能丢更多）

auto-aof-rewrite-percentage 100   # 比上次重写后体积增长 100% 触发重写
auto-aof-rewrite-min-size 64mb    # 且文件至少 64MB 才重写
aof-use-rdb-preamble yes          # ✅ 开启混合持久化
appendfsync刷盘时机最多丢多少性能
always每条写命令都 fsync几乎不丢最差
everysec每秒 fsync 一次（默认）约 1 秒数据✅ 均衡
no交给操作系统决定（~30s）可能丢 30 秒最好
AOF 重写（bgrewriteaof）解决的问题：

重写前（记录了全部历史命令，文件膨胀）：
  SET count 1
  INCR count    ... 重复 10000 次
  DEL count
  SET name Tom

重写后（只保留能还原当前状态的最小命令集）：
  SET name Tom          ← count 已被删除，10001 条命令全部消失

RDB vs AOF 怎么选 ​

维度RDBAOF
文件内容二进制全量快照文本命令日志
体积小（压缩后）大（重写后仍大于 RDB）
恢复速度快（直接加载内存镜像）慢（需逐条重放命令）
丢数据量两次快照之间全丢（可能几分钟）everysec 下约 1 秒
对性能影响fork 瞬时阻塞每秒 fsync，持续轻微 IO
适合备份、灾备、主从全量同步对丢数据敏感的业务

生产标准配置

两个都开，aof-use-rdb-preamble yes 用混合持久化：

  • 日常重启恢复 → 读 AOF（丢数据最少）；
  • 冷备与异地容灾 → 定期把 RDB 文件传到对象存储；
  • 从节点开 AOF，主节点只开 RDB 也是常见方案，把 fsync 的 IO 压力挪到从节点。

另外记住优先级：同时存在 AOF 和 RDB 时，Redis 重启只加载 AOF（因为它更完整）。所以用 RDB 做数据恢复时，必须先临时关掉 appendonly，否则会加载到空的 AOF 而「数据丢失」。

持久化 ≠ 高可用

RDB/AOF 只能防「进程重启」，防不了「磁盘损坏」和「机器宕机」。真正的高可用必须依靠主从复制 + 哨兵/集群，并把备份文件传到另一台机器上。

事务、WATCH 与 Lua 脚本 ​

核心概念

Redis 事务 = MULTI 开启 → 命令入队 → EXEC 一次性顺序执行。它提供的是**「不被其他客户端命令插队」的隔离性**，不提供回滚。

bash
MULTI
SET account:A 900
SET account:B 1100
EXEC            # 返回每条命令的结果数组

MULTI
SET k v
DISCARD         # 放弃事务，队列清空

Redis 事务不是 ACID ​

ACID 特性Redis 事务的真实情况
原子性 A⚠️ 部分满足：命令要么全入队要么不执行，但运行时出错不回滚
一致性 C✅ 满足
隔离性 I✅ 满足：单线程串行执行，EXEC 期间不会被插入其他命令
持久性 D⚠️ 取决于持久化配置（appendfsync always 才接近持久）
bash
# 情况一：语法错误（入队时即报错）→ EXEC 整体拒绝执行 ✅
MULTI
SET k1 v1
INCRR k2            # 命令不存在，入队就报错
EXEC                # (error) EXECABORT Transaction discarded

# 情况二：运行时错误（入队正常，执行才出错）→ 其他命令照样生效 ❌
MULTI
SET str hello
LPUSH str world     # 入队成功（语法合法）
INCR counter
EXEC
# 1) OK                              ← 生效了
# 2) (error) WRONGTYPE ...           ← 这条失败
# 3) (integer) 1                     ← 依然生效，没有任何回滚

这就是「Redis 事务不能回滚」的真正含义

MySQL 事务中任一语句失败可 ROLLBACK 回到起点；Redis 没有回滚日志（undo log），失败命令只是被跳过，其余命令的副作用永久保留。 👉 结论：需要「一组操作要么全成功要么全失败」时，不要用 MULTI/EXEC，请用 Lua 脚本并在脚本内部自行做前置校验。

WATCH：乐观锁 ​

bash
WATCH stock:1001           # 监视 key
GET stock:1001             # 假设得到 10
MULTI
DECRBY stock:1001 1
EXEC
# 若 EXEC 之前 stock:1001 被任何客户端改动过 → EXEC 返回 nil，事务不执行
# 业务侧需要自行重试（CAS 的典型模式）
WATCH 的工作时序：

客户端A: WATCH stock ──┐
客户端A: GET stock = 10│
                        │  客户端B: SET stock 5   ← 改动了被监视的 key
客户端A: MULTI          │
客户端A: DECRBY stock 1 │
客户端A: EXEC ─────────▶ 返回 nil（事务作废），A 必须重试

WATCH 的三个注意点

  1. EXEC 或 DISCARD 后 WATCH 自动失效，重试时必须重新 WATCH；
  2. 高并发下冲突率极高，重试会放大压力 —— 秒杀这类场景用 Lua 比 WATCH 更合适；
  3. Cluster 模式下 WATCH 的多个 key 必须在同一个槽，否则报 CROSSSLOT。

Lua 脚本：真正的原子操作 ​

为什么 Lua 是原子的

Redis 把整个脚本当成一条命令交给单线程执行，执行期间绝不会插入其他客户端的命令。所以脚本里的「读 → 判断 → 写」是一个不可分割的整体。

bash
# EVAL 脚本 key数量 key... arg...
EVAL "return redis.call('SET', KEYS[1], ARGV[1])" 1 mykey myvalue

# 先加载拿 sha1，之后用 EVALSHA 调用，省带宽
SCRIPT LOAD "return redis.call('GET', KEYS[1])"
# → "4e6d8fc8bb01276962cce5371fa795a7763657ae"
EVALSHA 4e6d8fc8bb01276962cce5371fa795a7763657ae 1 mykey
lua
-- 实战：安全释放分布式锁（只能删自己加的锁）
-- KEYS[1] = 锁的 key   ARGV[1] = 加锁时写入的唯一标识
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
lua
-- 实战：带上限的原子计数（如「每人限领 3 张券」）
local cnt = tonumber(redis.call('GET', KEYS[1]) or '0')
if cnt >= tonumber(ARGV[1]) then return 0 end
redis.call('INCR', KEYS[1])
redis.call('EXPIRE', KEYS[1], ARGV[2])
return 1

Lua 脚本的四条铁律

  1. key 必须通过 KEYS 传入，不能在脚本里拼接 key 名 —— 否则 Cluster 无法正确路由到节点；
  2. 脚本必须足够短。它独占单线程，一个慢脚本会阻塞整个实例（lua-time-limit 只是开始返回 BUSY 的阈值，并不会中断脚本）；
  3. 禁止写出随机性/时间依赖的脚本（如用 math.random、TIME 决定写入内容），否则主从复制的结果会不一致（5.0+ 采用「复制效果而非脚本」已缓解，但仍应避免）；
  4. redis.call 出错会中断脚本并向客户端抛错，redis.pcall 则返回错误对象让你自行处理。

三者怎么选

需求方案
只想减少网络往返，无原子性要求Pipeline
一组命令不被插队，能容忍部分失败MULTI/EXEC
读 + 判断 + 写 必须原子Lua 脚本 ✅
低冲突下的 CAS 更新WATCH + 重试

主从复制 ​

核心概念

主从复制（Replication）让从节点（replica）保存主节点（master）数据的副本。它解决三件事：读扩展（读请求分流到从节点）、数据冗余（主节点磁盘坏了还有副本）、故障切换的前提（哨兵/集群都建立在主从之上）。

bash
# 方式一：配置文件（永久生效，推荐）
replicaof 192.168.1.10 6379
masterauth your_master_pass        # 主节点有密码时必填
replica-read-only yes              # 从节点只读，防止写入导致数据分叉

# 方式二：运行时命令（重启失效）
REPLICAOF 192.168.1.10 6379
REPLICAOF NO ONE                   # 断开复制，自己变成主节点

INFO replication                   # 查看角色、从节点列表、复制偏移量

复制流程 ​

      首次连接（全量复制）
从节点                                主节点
  │── PSYNC ? -1 ──────────────────▶   │
  │                                    ├── BGSAVE 生成 RDB
  │                                    ├── 期间新写命令存入 repl backlog
  │◀──────────── RDB 文件 ─────────────┤
  ├── 清空自身数据，加载 RDB            │
  │◀────── backlog 中的增量命令 ───────┤
  │                                    │
         之后（命令传播 / 增量复制）
  │◀────── 主节点异步转发每条写命令 ────┤

         断线重连（部分复制，2.8+）
  │── PSYNC <replid> <offset> ──────▶  │
  │   若 offset 仍在 backlog 范围内 ──▶ 只补发缺失部分（+CONTINUE）
  │   若已被覆盖 ───────────────────▶  退化为全量复制（+FULLRESYNC）
bash
repl-backlog-size 64mb        # 复制缓冲区，调大可显著降低全量复制概率
repl-backlog-ttl 3600         # 从节点全部断开后，backlog 保留多久
repl-diskless-sync yes        # 无盘复制：RDB 直接走 socket，不落磁盘

主从复制是异步的 —— 必然会丢数据

主节点执行完写命令立刻返回客户端成功，之后才异步发给从节点。所以： ① 主节点宕机时，尚未同步的数据永久丢失； ② 从节点读到的可能是旧数据（复制延迟），这就是「读写分离下的一致性问题」。

缓解手段（不能根治）：

bash
min-replicas-to-write 1       # 至少 1 个从节点在线才允许写入
min-replicas-max-lag 10       # 且其延迟不超过 10 秒，否则主节点拒绝写

对一致性要求极高的读（如「下单后立刻查订单」），必须强制读主节点。

主从拓扑的实践建议

  • 一主两从起步，从节点分布在不同物理机 / 可用区；
  • 从节点过多会拖垮主节点（每个都要转发写命令），可用级联复制（A → B → C）分担；
  • 主节点别开 AOF，从节点开 AOF，把 fsync 的 IO 开销转移出去；
  • 从节点的 replica-read-only 永远保持 yes，在从节点写入的数据会在下次全量同步时被静默清空。

哨兵（Sentinel） ​

核心概念

主从复制解决了数据冗余，但主节点挂了需要人工把从节点提升为主。哨兵是一组独立进程，负责监控、通知、自动故障转移、向客户端提供最新主节点地址，实现真正的高可用。

       ┌──────────┐  ┌──────────┐  ┌──────────┐
       │Sentinel-1│  │Sentinel-2│  │Sentinel-3│   ← 哨兵集群（奇数个，≥3）
       └────┬─────┘  └────┬─────┘  └────┬─────┘
            │  相互通信 + 共同监控主从   │
            └──────┬───────┴─────┬──────┘
                   ▼             ▼
              ┌─────────┐   ┌─────────┐
              │ Master  │──▶│ Replica │
              └─────────┘   └─────────┘
                   ▲
          客户端先问哨兵「主节点是谁」，再直连该主节点
bash
# sentinel.conf
port 26379
daemonize yes
dir /var/lib/redis

# 监控名为 mymaster 的主节点，2 表示「至少 2 个哨兵同意才算客观下线」
sentinel monitor mymaster 192.168.1.10 6379 2
sentinel auth-pass mymaster your_master_pass
sentinel down-after-milliseconds mymaster 30000   # 30 秒无响应判定主观下线
sentinel failover-timeout mymaster 180000         # 故障转移超时
sentinel parallel-syncs mymaster 1                # 切换后同时同步的从节点数

# 启动
redis-sentinel /etc/redis/sentinel.conf

故障转移四步 ​

1. 主观下线（SDOWN）
   单个哨兵 ping 主节点超过 down-after-milliseconds 无响应

2. 客观下线（ODOWN）
   该哨兵询问其他哨兵，达到 quorum 个数同意 → 确认主节点真的挂了
   （这一步是为了排除「哨兵自己网络有问题」的误判）

3. 选举领导哨兵
   哨兵之间基于 Raft 投票，选出一个 leader 执行本次转移
   需获得 超过半数哨兵（N/2+1）的票

4. 挑选新主并切换
   过滤：已下线的、断连超时的从节点
   排序：replica-priority 越小优先 → 复制偏移量越大优先 → runid 越小优先
   执行：对新主 REPLICAOF NO ONE，让其他从节点 REPLICAOF 新主
         并把旧主标记为从节点（它恢复后自动成为新主的从）

quorum 与「半数」是两个不同的数

  • quorum：判定客观下线需要的哨兵同意数（配置文件里写的那个数字）；
  • 半数以上（N/2+1）：选举领导哨兵需要的票数，这是 Raft 的硬要求，不受 quorum 配置影响。

举例：3 个哨兵、quorum=2。若挂掉 2 个哨兵，剩下 1 个即使判定了下线，也凑不到 2 票（3/2+1=2）当选 leader，故障转移无法执行。

所以哨兵必须 ≥ 3 个且为奇数，并且部署在不同机器上（跟 Redis 实例放同一台机器，机器挂了哨兵也没了）。

客户端必须用哨兵模式连接

yaml
# Spring Boot
spring:
  data:
    redis:
      sentinel:
        master: mymaster
        nodes: 192.168.1.11:26379,192.168.1.12:26379,192.168.1.13:26379
javascript

  sentinels: [
    { host: "192.168.1.11", port: 26379 },

❌ 如果客户端仍然硬编码主节点 IP，故障转移后会连到一个只读的旧主，所有写操作报 READONLY You can't write against a read only replica。

Cluster 集群 ​

核心概念

哨兵解决了「高可用」，但所有数据仍在一个主节点上，内存和写入能力无法横向扩展。Cluster 把数据按 16384 个哈希槽（slot） 分散到多个主节点，每个主节点再带从节点，同时具备分片 + 高可用。

                16384 个槽的分配
   ┌──────────────┬──────────────┬──────────────┐
   │ Master A     │ Master B     │ Master C     │
   │ slot 0-5460  │ 5461-10922   │ 10923-16383  │
   └──────┬───────┴──────┬───────┴──────┬───────┘
          ▼              ▼              ▼
      Replica A      Replica B      Replica C

  路由规则：slot = CRC16(key) mod 16384
  客户端算出 slot → 找到对应节点 → 直接请求（客户端分片）
bash
# 每个节点的配置
port 7001
cluster-enabled yes
cluster-config-file nodes-7001.conf      # 自动维护，不要手改
cluster-node-timeout 15000               # 节点失联判定时间
appendonly yes

# 创建集群：3 主 3 从，--cluster-replicas 1 表示每个主配 1 个从
redis-cli --cluster create \
  192.168.1.11:7001 192.168.1.12:7002 192.168.1.13:7003 \
  192.168.1.11:7004 192.168.1.12:7005 192.168.1.13:7006 \
  --cluster-replicas 1 -a your_pass

常用运维命令 ​

bash
redis-cli -c -p 7001 -a your_pass     # -c 必须加！否则不会跟随重定向

CLUSTER INFO                 # 集群状态，cluster_state:ok 才正常
CLUSTER NODES                # 节点列表、角色、负责的槽
CLUSTER KEYSLOT user:1       # 查某个 key 落在哪个槽
CLUSTER COUNTKEYSINSLOT 866  # 某个槽里有多少 key

redis-cli --cluster check 192.168.1.11:7001      # 体检：槽覆盖是否完整
redis-cli --cluster add-node 新节点 已有节点      # 加节点
redis-cli --cluster reshard 192.168.1.11:7001    # 迁移槽（扩缩容核心步骤）
redis-cli --cluster rebalance 192.168.1.11:7001  # 自动均衡槽分布

集群模式下的四个重大限制

  1. 不支持多 key 跨槽操作。MSET、SINTER、MGET 等命令，若 key 分布在不同槽会报：
(error) CROSSSLOT Keys in request don't hash to the same slot
  1. 只有 0 号数据库，SELECT 1 直接报错；
  2. 事务和 Lua 的所有 key 必须同槽；
  3. Pub/Sub 会广播到全集群（7.0+ 提供 SPUBLISH 分片订阅缓解）。

用 hash tag 把相关 key 锁定到同一个槽

Redis 计算槽时，若 key 中含有 {...}，只用大括号内的内容计算：

bash
# ❌ 三个 key 分散在不同节点，无法一起操作
MGET user:1:profile user:1:follow user:1:cart

# ✅ 用 {1} 作为 hash tag，三个 key 必定落在同一槽
CLUSTER KEYSLOT user:{1}:profile    # 与下面两个结果相同
MGET user:{1}:profile user:{1}:follow user:{1}:cart   # 可以正常执行

⚠️ 但 hash tag 用猛了会造成数据倾斜：如果大量 key 都用 {hot}，这些数据会全挤到一个节点。只在「必须原子操作」的少量 key 上使用。

MOVED 与 ASK 重定向 ​

客户端请求了不属于本节点的 key：

槽已稳定归属其他节点 → MOVED
  (error) MOVED 866 192.168.1.12:7002
  含义：这个槽永久归 7002，客户端应更新本地槽映射表，之后直接请求 7002

槽正在迁移中 → ASK
  (error) ASK 866 192.168.1.12:7002
  含义：这次请求临时转到 7002（需先发 ASKING 命令），
        但不要更新本地映射表 —— 迁移还没完成

为什么一定要带 -c

redis-cli 不加 -c 时，遇到 MOVED 只会把错误打印出来，不会自动跳转，看起来像「集群坏了」。而成熟的客户端（JedisCluster / Lettuce / ioredis）会在内部缓存槽映射表并自动处理 MOVED/ASK，业务代码无感知。

集群的故障转移与脑裂 ​

bash
cluster-require-full-coverage no   # ✅ 部分槽不可用时，其余槽仍可服务
                                   #    设 yes 会让整个集群停摆
cluster-node-timeout 15000
cluster-replica-validity-factor 10 # 从节点与主节点断连过久则不参与选举
Cluster 自己就能完成故障转移，不需要哨兵：
  节点间通过 Gossip 协议互相 PING/PONG
  → 半数以上主节点认为 A 下线（PFAIL → FAIL）
  → A 的从节点发起选举，获得多数主节点投票后升为主
  → 接管 A 的槽

脑裂（split-brain）会丢数据

网络分区时，旧主 A 与多数派失联，但仍有客户端连着它继续写入；多数派那边已把 A 的从节点 B 提升为新主。网络恢复后，A 降级为 B 的从节点并清空自身数据，分区期间写入 A 的数据全部丢失。

缓解配置（主从、集群都适用）：

bash
min-replicas-to-write 1     # 没有健康从节点时，主节点直接拒绝写入
min-replicas-max-lag 10

本质上这是 CAP 中的取舍：宁可分区期间不可写（牺牲 A），也不要写进去再丢（牺牲 C）。

三种架构怎么选

架构容量上限高可用复杂度适用
单机单机内存❌低本地开发、内部工具
主从+哨兵单机内存✅中数据量 < 10GB 的绝大多数业务
Cluster节点数 × 内存✅高数据量大 / 写 QPS 极高

不要过度设计：数据量不大就用「主从 + 哨兵」，它没有跨槽限制，运维和排障都简单得多。只有当单实例内存撑不住（> 10GB）或写入打满单核时，才上 Cluster。

缓存穿透 / 击穿 / 雪崩 ​

三者的本质区别

问题触发条件一句话概括
缓存穿透查根本不存在的数据缓存里没有，数据库里也没有
缓存击穿某个热点 key 突然过期一个热 key 失效，大量请求压库
缓存雪崩大批 key 同时过期/宕机一大片 key 同时失效

缓存穿透 ​

请求 id = -1（不存在的 id）
  → 查 Redis：miss
  → 查 MySQL：也没有
  → 不写缓存（因为没数据可写）
  → 下一个同样的请求再次打到 MySQL
  👉 攻击者用随机 id 刷接口，数据库被打爆

方案一：缓存空值

javascript
async function getUser(id) {
  const cached = await redis.get(`user:${id}`);
  if (cached !== null) {
    // ✅ 注意：必须区分「没有缓存」和「缓存了空值」
    return cached === "" ? null : JSON.parse(cached);
  }
  const user = await db.findUser(id);
  if (!user) {
    // 空值也要缓存，但 TTL 要短，避免数据真的写入后长期读不到
    await redis.set(`user:${id}`, "", "EX", 60);
    return null;
  }
  await redis.set(`user:${id}`, JSON.stringify(user), "EX", 3600);
  return user;
}

缓存空值的两个副作用

① 内存浪费：被恶意刷的随机 id 都会占一个 key，所以 TTL 必须短（30~60 秒）且 key 要有长度校验； ② 数据不一致：缓存了「用户 999 不存在」后，若该用户真的注册了，60 秒内接口仍返回不存在。解决办法是写入数据库成功后主动删除这个空值 key。

缓存击穿 ​

热点商品详情（QPS 5 万）缓存到期的那一瞬间：
  5 万个请求同时发现 miss → 5 万个请求同时查 MySQL → DB 直接崩

方案一：互斥锁重建（推荐）

javascript
async function getWithMutex(key, loader, ttl = 3600) {
  let val = await redis.get(key);
  if (val !== null) return JSON.parse(val);

  const lockKey = `lock:${key}`;
  const token = crypto.randomUUID();
  // 只有抢到锁的那一个请求去查库
  const locked = await redis.set(lockKey, token, "EX", 10, "NX");

  if (!locked) {
    await sleep(50); // 其余请求短暂等待后重试读缓存
    return getWithMutex(key, loader, ttl);
  }

  try {
    // ⚠️ 双重检查：等锁期间可能已被别人写好了
    val = await redis.get(key);
    if (val !== null) return JSON.parse(val);

    const data = await loader();
    await redis.set(key, JSON.stringify(data), "EX", ttl);
    return data;
  } finally {
    await redis.unlock(lockKey, token); // Lua 保证只删自己的锁
  }
}

缓存雪崩 ​

场景一：大批 key 用了相同 TTL（如凌晨统一预热，全设 3600 秒）
        → 一小时后同时失效 → DB 瞬时被打满

场景二：Redis 实例整体宕机
        → 所有请求直接穿透到 DB → DB 崩 → 服务整体不可用
javascript
// ✅ 对策一：TTL 加随机抖动，把失效时间打散
const ttl = 3600 + Math.floor(Math.random() * 600); // 3600~4200 秒
await redis.set(key, value, "EX", ttl);

雪崩的完整防御体系

  • 打散过期时间：基础 TTL + 随机值，避免集中失效；
  • 多级缓存：本地缓存（Caffeine / LRU Map）兜底 Redis，Redis 挂了还能扛住一部分；
  • 熔断降级：Redis 不可用时直接返回兜底数据或友好提示，不要让请求全涌向 DB；
  • 限流：在 DB 入口加信号量，最多放 N 个并发查询进去，其余快速失败；
  • 高可用部署：主从 + 哨兵 / Cluster，从根上降低「整体宕机」的概率；
  • 缓存预热：上线或重启前先把热点数据灌进去，别让流量来冲刷空缓存。

缓存一致性 ​

核心问题

数据既在 MySQL 又在 Redis，更新时改哪个、先改谁？只要是两个存储，就不存在绝对的强一致，我们能做的是把不一致的窗口压到足够小、并保证最终一致。

四种方案对比 ​

方案做法问题
先更新库，再更新缓存写双份并发下两次写顺序可能颠倒 → 缓存是旧值
先更新缓存，再更新库写双份库写失败则缓存是脏数据，更糟
先删缓存，再更新库Cache Aside 变体删完到更新完之间，读请求会把旧值重新写入缓存
先更新库，再删缓存✅ Cache Aside 标准仅在极端时序下短暂不一致，概率极低
javascript
// ✅ 标准 Cache Aside（旁路缓存）
async function updateUser(id, data) {
  await db.updateUser(id, data); // 1. 先写数据库
  await redis.del(`user:${id}`); // 2. 再删缓存（不是更新！）
}

为什么是「删缓存」而不是「更新缓存」

  1. 避免无效写：更新后的数据可能很久都没人读，白白做了一次序列化和写入；
  2. 规避并发覆盖：两个线程 A、B 都更新，若「更新缓存」，可能出现 A写库 → B写库 → B写缓存 → A写缓存，缓存最终留下的是 A 的旧值；而「删缓存」是幂等的，删两次结果一样；
  3. 省去聚合逻辑：缓存值常常是多表聚合结果，更新缓存意味着要在写路径上重算一遍。

为什么「先删缓存再更新库」是错的

时刻 1  线程A（写）：DEL user:1                 缓存已空
时刻 2  线程B（读）：GET user:1 → miss
时刻 3  线程B（读）：查库得到【旧值】
时刻 4  线程A（写）：UPDATE 数据库为【新值】
时刻 5  线程B（读）：SET user:1 = 【旧值】       ❌ 脏数据长期驻留

旧值会一直存在，直到 TTL 到期 —— 这是真正危险的不一致。

反观「先更新库再删缓存」，只有在「读请求的查库恰好发生在写请求更新库之前，而写缓存恰好发生在删缓存之后」这种毫秒级错位下才会出问题，概率极低且有 TTL 兜底。

分布式锁 ​

核心概念

单机锁（synchronized、Mutex）只在一个进程内有效。服务部署成多实例后，需要一个所有实例都认的外部裁判 —— 这就是分布式锁。Redis 实现它的基础是 SET key value NX EX。

从错误到正确的四次演进 ​

javascript
// ❌版本一：没有过期时间 —— 进程崩溃后永久死锁
await redis.setnx("lock", "1");

// ❌ 版本二：两条命令 —— 中间崩溃则锁永不释放
await redis.setnx("lock", "1");
await redis.expire("lock", 10);

// ❌ 版本三：有了原子加锁，但释放锁会删掉别人的锁
await redis.set("lock", "1", "EX", 10, "NX");

// → A 执行完毕执行 DEL lock → ❌ 删掉了 B 的锁！

// ✅ 版本四：唯一标识 + Lua 校验删除
const token = crypto.randomUUID();
const ok = await redis.set(lockKey, token, "EX", 10, "NX");
if (!ok) throw new Error("获取锁失败");
try {
  await doBusiness();
} finally {
  // 必须用 Lua：「判断是不是我的锁」和「删除」要原子完成
  await redis.unlock(lockKey, token);
}

为什么解锁一定要用 Lua

时刻 1  A 执行 GET lock，发现值是自己的 token  ✅
时刻 2  锁刚好到期自动删除
时刻 3  B 加锁成功，lock 的值变成 B 的 token
时刻 4  A 执行 DEL lock                        ❌ 删掉了 B 的锁

GET 和 DEL 之间存在时间窗口，必须用 Lua 合并成一个原子操作。

一个可用的实现 ​

javascript
export async function withLock(key, fn, { ttl = 10000, wait = 3000 } = {}) {
  const lockKey = `lock:${key}`;
  const token = crypto.randomUUID();
  const deadline = Date.now() + wait;

  // 自旋获取锁
  while (Date.now() < deadline) {
    if (await redis.set(lockKey, token, "PX", ttl, "NX")) {
      // 看门狗：每 1/3 TTL 续期一次，防止业务未执行完锁就过期
      const timer = setInterval(() => {
        redis.renew(lockKey, token, ttl).catch(() => {});
      }, ttl / 3);
      try {
        return await fn();
      } finally {
        clearInterval(timer);
        await redis.unlock(lockKey, token);
      }
    }
    await sleep(50 + Math.random() * 50); // 加随机，避免惊群
  }
  throw new Error(`获取锁超时: ${key}`);
}

TTL 设多久？这是最难的取舍

  • 设短了：业务没跑完锁就过期，两个线程同时进入临界区 → 锁失效；
  • 设长了：持有锁的进程宕机后，其他进程要白等很久 → 可用性差。

所以生产环境必须有**看门狗（自动续期）**机制：锁的 TTL 设短（如 10 秒），后台定时续期，进程崩溃时续期自然停止，锁 10 秒后释放。这正是 Redisson 默认做的事，自己实现容易漏掉边界。

Redis 分布式锁不是绝对安全的

主从架构下存在这个经典问题：

1. A 在主节点加锁成功
2. 主节点还没把这条命令同步给从节点就宕机了
3. 哨兵把从节点提升为新主 —— 新主上没有这把锁
4. B 在新主上加锁，也成功了
   👉 A 和 B 同时持有「同一把锁」

官方提出 RedLock（向 N 个独立主节点加锁，超过半数成功才算持有），但它依赖时钟同步，业界对其安全性仍有争议，且运维成本高。

务实的结论：

  • Redis 锁适合做性能优化（减少重复计算、避免定时任务重复执行）；
  • 涉及资金、库存等绝对不能出错的场景，必须在数据库层面加最终防线 —— 唯一索引、乐观锁版本号（UPDATE ... WHERE version = ?）或 SELECT ... FOR UPDATE。锁只是第一道闸门，不是唯一保障；
  • 需要强一致的锁，考虑 ZooKeeper / etcd（CP 系统）。

缓存穿透与布隆过滤器 ​

什么是缓存穿透？怎么解决？ ​

缓存穿透是指请求查询缓存和数据库中都不存在的数据。若未缓存空结果，这类请求就会绕过缓存，直接访问数据库。当这类请求数量很大或并发很高时，会增加数据库压力，严重时可能导致数据库服务不可用。

缓存穿透不一定是攻击导致的，恶意请求、无效参数或正常业务中查询不存在的数据都可能引发缓存穿透。

解决方案的话，我们通常都会用布隆过滤器来解决它

你能介绍一下布隆过滤器吗？ ​

布隆过滤器主要是用于检索一个元素是否在一个集合中。我们当时使用的是 redisson 实现的布隆过滤器。

它的底层主要是先去初始化一个比较大数组，里面存放的二进制 0 或 1。在一开始都是 0，当一个 key 来了之后经过 3 次 hash 计算，模于数组长度找到数据的下标然后把数组中原来的 0 改为 1，这样的话，三个数组的位置就能标明一个 key 的存在。查找的过程也是一样的。

布隆过滤器的缺点

当然是有缺点的，布隆过滤器有可能会产生一定的误判，我们一般可以设置这个误判率，大概不会超过 5%，其实这个误判是必然存在的，要不就得增加数组的长度，其实已经算是很划分了，5%以内的误判率一般的项目也能接受，不至于高并发下压倒数据库。

缓存击穿与缓存雪崩 ​

什么是缓存击穿？怎么解决？ ​

缓存击穿的意思是对于设置了过期时间的 key，缓存在某个时间点过期的时候，恰好这时间点对这个 Key 有大量的并发请求过来，这些请求发现缓存过期一般都会从后端 DB 加载数据并回设到缓存，这个时候大并发的请求可能会瞬间把 DB 压垮。

解决方案有两种方式：

  • 互斥锁：当缓存失效时，不立即去 load db，先使用如 Redis 的 setnx 去设置一个互斥锁，当操作成功返回时再进行 load db 的操作并回设缓存，否则重试 get 缓存的方法

  • 逻辑过期：可以设置当前 key 逻辑过期，具体步骤如下：

    1. 在设置 key 的时候，设置一个过期时间字段一块存入缓存中，不给当前 key 设置过期时间

    2. 当查询的时候，从 redis 取出数据后判断时间是否过期

    3. 如果过期则开通另外一个线程进行数据同步，当前线程正常返回数据，这个数据不是最新

两种方案的取舍

  • 如果选择数据的强一致性，建议使用分布式锁的方案，性能上可能没那么高，锁需要等，也有可能产生死锁的问题

  • 如果选择 key 的逻辑删除，则优先考虑的高可用性，性能比较高，但是数据同步这块做不到强一致。

什么是缓存雪崩？怎么解决？ ​

缓存雪崩意思是设置缓存时采用了相同的过期时间，导致缓存在某一时刻同时失效，请求全部转发到 DB，DB 瞬时压力过重雪崩。与缓存击穿的区别：雪崩是很多 key，击穿是某一个 key 缓存。

解决方案主要是可以将缓存失效时间分散开，比如可以在原有的失效时间基础上增加一个随机值，比如 1-5 分钟随机，这样每一个缓存的过期时间的重复率就会降低，就很难引发集体失效的事件。

双写一致性与读写锁 ​

Redis 作为缓存，MySQL 的数据如何与 Redis 进行同步呢（双写一致性）？ ​

对于缓存与数据库一致性要求较高的场景，可以使用 Redisson 的分布式读写锁协调同一份业务数据的读写操作，减少并发读取与更新造成的不一致。

读写锁包含两种锁模式，并不是读写锁、共享锁、排他锁三把独立的锁：

  • 读锁（共享锁，S）：允许多个线程同时持有，适用于只读取数据的操作。
  • 写锁（排他锁，X）：不同线程之间互斥；持有写锁期间，其他线程不能获取同一份数据的读锁或写锁，适用于更新数据的操作。

对同一个锁资源、不同线程而言，兼容关系如下（同一线程的可重入等行为另行讨论）：

  1. S + S：兼容。读读可以共存，多个线程可以同时读取。
  2. S + X：互斥。已有读锁时，其他线程不能获取写锁，需要等待读锁释放。
  3. X + S：互斥。已有写锁时，其他线程不能获取读锁，需要等待写锁释放。
  4. X + X：互斥。已有写锁时，其他线程不能获取写锁，即写写互斥。

在缓存读写场景中，可以按以下方式使用：

  • 读取数据：先获取读锁，再查询缓存；缓存未命中时查询数据库，必要时回填缓存，最后释放读锁。读锁只用于协调与业务更新的互斥，并不能防止多个读线程同时回源；热点数据的缓存重建仍可配合独立的互斥机制。
  • 更新数据：先获取写锁，更新数据库并确保事务提交成功，再删除缓存，最后释放写锁。后续读取在缓存未命中时，从数据库加载新数据。

关键前提与边界

关键是：针对同一份业务数据，读方法和写方法必须使用同一个读写锁资源，且所有相关访问路径都遵守该协议。数据库事务必须在释放写锁前提交，异常路径也必须可靠释放锁。

读写锁不等于直接保证 MySQL 与 Redis 的强一致性。缓存删除失败、进程崩溃、锁提前失效或故障转移仍可能造成不一致，需要结合重试、补偿和业务一致性要求设计。

排他锁是如何保证读写、写写互斥的？ ​

Redisson 的读写锁通过 Redis 中的锁状态与原子 Lua 脚本完成加锁、重入计数、续期和释放等操作，不能简单概括为底层只使用一个 SETNX。

  • 获取读锁：其他线程未持有写锁时，允许多个线程共同持有读锁。
  • 获取写锁：其他线程没有持有读锁或写锁时，才允许获取写锁；已有写锁的线程可以按可重入规则再次获取。
  • 释放锁：校验持有者并更新持有状态；等待线程收到通知或到达重试时机后，再尝试获取锁。

由于锁状态的检查与修改是原子操作，不同客户端不会同时通过互斥条件的检查。其结果是读读共享、读写互斥、写写互斥，而不是读读互斥。

你听说过延时双删吗？为什么不用它呢？ ​

延迟双删，如果是写操作，我们先把缓存中的数据删除，然后更新数据库，最后再延时删除缓存中的数据，其中这个延时多久不太好确定，在延时的过程中可能会出现脏数据，并不能保证强一致性，所以没有采用它。

Redis 作为缓存，MySQL 的数据如何与 Redis 进行同步呢（双写一致性）？ ​

就说我最近做的这个项目，里面有 xxxx（根据自己的简历上写）的功能，数据同步可以有一定的延时（符合大部分业务）

我们当时采用的阿里的 canal 组件实现数据同步：不需要更改业务代码，部署一个 canal 服务。canal 服务把自己伪装成 mysql 的一个从节点，当 mysql 数据更新以后，canal 会读取 binlog 数据，然后在通过 canal 的客户端获取到数据，更新缓存即可。

持久化、过期与淘汰 ​

Redis 作为缓存，数据的持久化是怎么做的？ ​

一、RDB ​

RDB 是某一时间点的二进制快照，保存数据最终结果。

  1. 两种生成方式：

    • save：主线程同步执行，阻塞，线上不用
    • bgsave：fork 子进程，配合 Linux COW 写时复制
      • fork 瞬间短暂阻塞主线程；fork 后父子共享内存页，标记只读
      • 类比理解：一张纸，父子两个人一起看（共享），约定这张纸暂时不能涂改。
        • 只是看（读）：随便看，不用复印；
        • 想在上面写字修改（写）：不能直接在原版上改，必须先复印一份，在复印件上改。原版留给子进程不动。
      • 两个细节：
        1. 拷贝粒度是内存页（一般 4KB），不是单个 key。一页里只要有一个 key 被写，整页复制；同页其他 key 哪怕只读，也跟着拷贝。
        2. 子进程只读取快照，不会修改内存，所以子进程永远不会触发 COW；只有父进程的写才会触发。
      • 子进程生成 RDB；fork 之后新写入的数据不会进入本次 RDB

  2. 配置：save 秒数 变更次数，多条规则为或关系

  3. 优点：文件压缩小、恢复速度快，适合异地冷备份

  4. 缺点：两次快照之间的数据会丢失

  5. 风险：bgsave 期间大量写入，持续触发 COW 拷贝，内存上涨，可能 OOM

AOF ​

AOF 追加记录写命令，保存数据变更过程。

  1. 流程：写命令 → AOF 缓冲区 → write 写入内核页缓存 → fsync 刷盘落盘

  2. 刷盘策略 appendfsync

    • always：每条命令都 fsync，几乎不丢数据，性能差
    • everysec（生产常用）：后台线程每秒 fsync，最坏丢约 1 秒数据
    • no：交给操作系统刷盘，丢失数据不可控

  3. AOF 重写（AOF 去重机制）

    AOF 持续追加，同一个 key 反复修改会堆积大量无效重复命令。

    fork 子进程，直接读取内存中 key 的最终值，生成精简命令实现去重；重写期间新命令存入重写缓冲区，重写完成后追加进新 AOF，原子替换文件，保证数据完整。

  4. 优点：数据丢失窗口小，支持 redis-check-aof 修复

  5. 缺点：纯命令 AOF 恢复慢，文件容易膨胀

混合持久化（Redis4.0+） ​

AOF 文件内部 = RDB 快照基线 + 后续增量 AOF 命令 恢复：先加载 RDB 快照，再回放少量增量命令；兼顾恢复快、丢失窗口小。

RDB + AOF 同时开启（线上标准方案） ​

  • 启动恢复：优先加载 AOF；只有 AOF 关闭/损坏无法修复，才加载 RDB，不会合并加载
  • 分工：AOF 作为主持久化，依靠重写去重、混合持久化提速；RDB 定时冷备，用于 AOF 损坏、误删数据兜底

选型

  • 缓存、数据可重建：关闭持久化
  • 容忍较多丢数据，看重备份恢复：单独 RDB
  • 数据重要：AOF everysec + 开启混合持久化 + RDB 冷备

Redis 的数据过期策略有哪些？ ​

Redis 使用 惰性删除 + 定期删除。

一、惰性删除 ​

访问 key 时检查：过期就删除并返回空，否则正常返回。

  • 优点：不主动扫描，只在访问时承担检查和删除的 CPU 开销。
  • 缺点：只靠惰性删除，没人访问的过期 key 会继续占内存。

二、定期删除 ​

主动抽样检查带过期时间的 key，删除已过期的数据。

  • SLOW：定时执行，hz 默认 10，基础频率约每 100ms 一次；默认参数下时间预算约 25ms，随实际频率和配置变化。
  • FAST：事件循环中按条件执行，不是只在空闲时执行；默认预算约 1ms，间隔至少约 2ms。

抽样不是每次遍历全库，仍可能有未清理的过期 key。

三、总结与追问 ​

惰性删除访问时兜底，定期删除主动回收，兼顾 CPU 与内存。

内存超过 maxmemory 时，按内存淘汰策略处理，可能淘汰未过期 key；noeviction 不淘汰，对需要新增内存的写入通常报错。

Redis 的数据淘汰策略有哪些？ ​

这个在 redis 中提供了很多种，默认是 noeviction，不删除任何数据，内部不足直接报错

是可以在 redis 的配置文件中进行设置的，里面有两个非常重要的概念，一个是 LRU，另外一个是 LFU

  • LRU：最少最近使用，用当前时间减去最后一次访问时间，这个值越大则淘汰优先级越高。

  • LFU：最少频率使用。会统计每个 key 的访问频率，值越小淘汰优先级越高

我们在项目设置的 allkeys-lru，挑选最近最少使用的数据淘汰，把一些经常访问的 key 留在 redis 中

数据库有 1000 万数据，Redis 只能缓存 20w 数据，如何保证 Redis 中的数据都是热点数据？ ​

可以使用 allkeys-lru （挑选最近最少使用的数据淘汰）淘汰策略，那留下来的都是经常访问的热点数据

Redis 的内存用完了会发生什么？ ​

这个要看 redis 的数据淘汰策略是什么，如果是默认的配置，redis 内存用完以后则直接报错。我们当时设置的 allkeys-lru 策略。把最近最常访问的数据留在缓存中。

分布式锁与 Redisson ​

Redis 分布式锁如何实现？ ​

在 redis 中提供了一个命令 setnx(SET if not exists)

由于 redis 的单线程的，用了命令之后，只能有一个客户端对某一个 key 设置值，在没有过期或删除 key 的时候是其他客户端是不能设置这个 key 的

如何控制 Redis 实现分布式锁有效时长呢？ ​

redis 的 setnx 指令不好控制这个问题，我们当时采用的 redis 的一个框架 redisson 实现的。

在 redisson 中需要手动加锁，并且可以控制锁的失效时间和等待时间，当锁住的一个业务还没有执行完成的时候，在 redisson 中引入了一个看门狗机制，就是说每隔一段时间就检查当前业务是否还持有锁，如果持有就增加加锁的持有时间，当业务执行完成之后需要使用释放锁就可以了

还有一个好处就是，在高并发下，一个业务有可能会执行很快，先客户 1 持有锁的时候，客户 2 来了以后并不会马上拒绝，它会自旋不断尝试获取锁，如果客户 1 释放之后，客户 2 就可以马上持有锁，性能也得到了提升。

Redisson 实现的分布式锁是可重入的吗？ ​

是可以重入的。这样做是为了避免死锁的产生。这个重入其实在内部就是判断是否是当前线程持有的锁，如果是当前线程持有的锁就会计数，如果释放锁就会在计算上减一。在存储数据的时候采用的 hash 结构，大 key 可以按照自己的业务进行定制，其中小 key 是当前线程的唯一标识，value 是当前线程重入的次数

Redisson 实现的分布式锁能解决主从一致性的问题吗？ ​

这个是不能的。

  1. 线程 A 向 master 请求加锁 lock:order，写入成功并收到加锁成功。
  2. 锁还没异步复制到 slave，master 就宕机了。
  3. 哨兵 / 集群将没有该锁的 slave 提升为新 master。
  4. 线程 B 向新 master 请求同一把锁。
  5. 新 master 没有这个锁，B 也加锁成功。

A 仍认为自己持锁并继续执行，B 也拿到锁，两个线程可能同时进入临界区，互斥被打破。

红锁（Redlock）的取舍

为降低这类故障导致的丢锁风险，可以考虑红锁（Redlock）。它不是只在一个 Redis 实例上加锁，而是在多个相互独立的 Redis 实例上尝试加锁。只有在有效时间内，超过半数实例加锁成功，才认为获取锁成功，从而降低对单个实例的依赖。但红锁的安全性仍依赖时钟、执行暂停等假设，不能保证所有故障场景下的互斥。

不过，红锁需要与多个实例通信，会增加加锁延迟和运维成本。因此，项目中是否采用红锁，需要结合业务的一致性要求和性能需求评估，不能简单认为它一定优于普通锁。另外，Redisson 中某个红锁实现被标记为弃用，不等于 Redlock 算法被官方废弃；具体应以所用版本的文档为准。

如果业务非要保证数据的强一致性，这个该怎么解决呢？ ​

redis 本身就是支持高可用的，做到强一致性，就非常影响性能，所以，如果有强一致性要求高的业务，建议使用 zookeeper 实现的分布式锁，它是可以保证强一致性的。

主从、哨兵与分片集群 ​

Redis 集群有哪些方案？ ​

在 Redis 中提供的集群方案总共有三种：主从复制、哨兵模式、分片集群。

什么是主从同步？ ​

单节点 Redis 的并发能力是有上限的，要进一步提高 Redis 的并发能力，就需要搭建主从集群，实现读写分离。一般都是一主多从，主节点负责写数据，从节点负责读数据,主节点写入数据之后，需要把数据同步到从节点中

主从同步数据的流程是什么？ ​

主从同步分为了两个阶段，一个是全量同步，一个是增量同步

全量同步是指从节点第一次与主节点建立连接的时候使用全量同步，流程是这样的:

  • 第一：从节点请求主节点同步数据，其中从节点会携带自己的 replication id 和 offset 偏移量。
  • 第二：主节点判断是否是第一次请求，主要判断的依据就是，主节点与从节点是否是同一个 replication id，如果不是，就说明是第一次同步，那主节点就会把自己的 replication id 和 offset 发送给从节点，让从节点与自己的信息保持一致。
  • 第三：在同时主节点会执行 bgsave，生成 rdb 文件后，发送给从节点去执行，从节点先把自己的数据清空，然后执行主节点发送过来的 rdb 文件，这样就保持了一致。

当然，如果在 rdb 生成执行期间，依然有请求到了主节点，而主节点会以命令的方式记录到缓冲区，缓冲区是一个日志文件，最后把这个日志文件发送给从节点，这样就能保证主节点与从节点完全一致了，后期再同步数据的时候，都是依赖于这个日志文件，这个就是全量同步

增量同步指的是，当从节点服务重启之后，数据就不一致了，所以这个时候，从节点会请求主节点同步数据，主节点还是判断不是第一次请求，不是第一次就获取从节点的 offset 值，然后主节点从命令日志中获取 offset 值之后的数据，发送给从节点进行数据同步

怎么保证 Redis 的高并发高可用？ ​

首先可以搭建主从集群，再加上使用 redis 中的哨兵模式，哨兵模式可以实现主从集群的自动故障恢复，里面就包含了对主从服务的监控、自动故障恢复、通知；如果 master 故障，Sentinel 会将一个 slave 提升为 master。当故障实例恢复后也以新的 master 为主；同时 Sentinel 也充当 Redis 客户端的服务发现来源，当集群发生故障转移时，会将最新信息推送给 Redis 的客户端，所以一般项目都会采用哨兵的模式来保证 redis 的高并发高可用

你们使用 Redis 是单点还是集群，哪种集群？ ​

  • 生产常规哨兵 / 主从架构：Redis maxmemory 给到机器物理内存的 60%～ 70% 是稳妥区间

主从（1 主 1 从）加哨兵。一般单节点不超过 10G 内存，如果 Redis 内存不足则可以给不同服务分配独立的 Redis 主从节点。尽量不做分片集群。因为集群维护起来比较麻烦，并且集群之间的心跳检测和数据通信会消耗大量的网络带宽，也没有办法使用 lua 脚本和事务

Redis 集群脑裂，该怎么解决呢？ ​

Redis 哨兵用于一主多从的自动故障转移。 如果主节点真宕机，哨兵选从升主，不会脑裂。 脑裂的场景：老主进程还活着，只是和哨兵、从节点网络隔离(ping 不通了)。哨兵收不到心跳，达到仲裁数选出新主；老主依旧可以接收写请求，集群出现双主。 网络恢复后，老主降级为从，同步新主数据，隔离期间写入的数据丢失。

配置 min-replicas-to-write + min-replicas-max-lag： 老主和从节点断开后，会主动拒绝写请求，减少数据丢失。 ⚠️ 重点：只能止损，不能杜绝脑裂。

Redis 的分片集群有什么作用？ ​

分片集群主要解决的是，海量数据存储的问题，集群中有多个 master，每个 master 保存不同数据，并且还可以给每个 master 设置多个 slave 节点，就可以继续增大集群的高并发能力。同时每个 master 之间通过 ping 监测彼此健康状态，就类似于哨兵模式了。当客户端请求可以访问集群任意节点，最终都会被转发到正确节点

Redis 分片集群中数据是怎么存储和读取的？ ​

在 redis 集群中是这样的

  • Redis 集群引入了哈希槽的概念，有 16384 个哈希槽，集群中每个主节点绑定了一定范围的哈希槽范围, key 通过 CRC16 校验后对 16384 取模来决定放置哪个槽，通过槽找到对应的节点进行存储。
  • 取值的逻辑是一样的

hash tag

如果想要让某一些数据总是存在同一个 redis 中，这个可以吗？

可以的，redis 计算槽编号的时候可以根据 hash tag（key 中用 {} 括起来的部分）计算，可以让包含相同 hash tag 的 key 落到同一个槽。

单线程与 I/O 多路复用 ​

Redis 是单线程的，但是为什么还那么快？ ​

  1. 完全基于内存的，C 语言编写
  2. 采用单线程，避免不必要的上下文切换可竞争条件
  3. 使用多路 I/O 复用模型，非阻塞 IO

例如：bgsave 和 bgrewriteaof 都是在后台执行操作，不影响主线程的正常使用，不会产生阻塞

能解释一下 I/O 多路复用模型？ ​

  • 阻塞 IO：一个线程等一个连接，没来数据就卡死，一个连接一个线程，资源爆炸
  • 非阻塞 IO：循环轮询所有 socket，不停问有没有数据，CPU 空转浪费
  • IO 多路复用（Redis 用的）：交给操作系统内核去监听一堆 socket，有事件就绪了再通知用户线程，线程不用轮询等待
