Day11 Java 后端：集合体系（ArrayList、LinkedList、HashMap、ConcurrentHashMap 高频手撕） ​

📖 基础知识讲解【基础原理 + 高级深挖知识点】 ​

基础原理 ​

1. 集合体系全景：两大根接口 ​

Java 集合框架（java.util）只有两条根：Collection 单列集合（一个一个存元素）和 Map 双列集合（按 key-value 存）。Map 并不是 Collection 的子接口，这是面试里常被问倒的一个点。

text
Iterable（可迭代，提供 iterator()）
└── Collection
    ├── List          有序、可重复、有索引
    │     ├── ArrayList            动态数组   ★最常用
    │     ├── LinkedList           双向链表（同时是 Deque）
    │     ├── Vector               古老，方法级 synchronized（废弃）
    │     │     └── Stack          继承 Vector（废弃，用 ArrayDeque）
    │     └── CopyOnWriteArrayList 并发包，写时复制
    ├── Set           无序、不可重复（底层大多就是一个 Map）
    │     ├── HashSet              底层 HashMap
    │     │     └── LinkedHashSet  底层 LinkedHashMap，保留插入顺序
    │     ├── TreeSet              底层 TreeMap，红黑树，自动排序
    │     └── CopyOnWriteArraySet  并发包，底层 COWArrayList
    └── Queue         队列，先进先出
          ├── ArrayDeque           循环数组双端队列 ★栈/队列首选
          ├── PriorityQueue        二叉小顶堆，优先级队列
          └── BlockingQueue        并发包（ArrayBlockingQueue / LinkedBlockingQueue…）

Map（独立根接口，不属于 Collection）
├── HashMap                数组 + 链表 + 红黑树   ★最常用
│    └── LinkedHashMap    HashMap + 双向链表（可做 LRU）
├── TreeMap                红黑树，key 自动排序
├── Hashtable              全方法 synchronized（废弃）
│     └── Properties       读 .properties 配置
└── ConcurrentHashMap      并发包，CAS + synchronized 锁桶   ★并发首选
接口核心特征典型实现判重依据
List有序、可重复、有下标ArrayList不判重
Set不可重复、一般无序HashSethashCode() + equals()
Queue先进先出 / 按优先级出队ArrayDeque不判重
Mapkey 不重复、value 可重复HashMapkey 的 hashCode() + equals()

一句话结论： Set 和 Map 是一回事 —— HashSet 内部就是一个 HashMap，元素存在 key 上，value 统一塞一个固定的 PRESENT 占位对象。所以掌握了 HashMap，等于同时掌握了 HashSet，面试考 HashMap 的频率也远高于其他所有集合。

2. ArrayList：动态数组 ​

text
ArrayList 内部结构
  elementData ──► [ A ][ B ][ C ][ D ][  ][  ][  ][  ][  ][  ]
                    0    1    2    3                        9
  size = 4（实际元素个数）      capacity = 10（数组长度）

查询 get(2)：直接 elementData[2]              → O(1)
尾部 add(E)：elementData[size++] = e           → O(1) 均摊
中间 add(1, E)：System.arraycopy 整体后移      → O(n)
中间 remove(1)：后面元素整体前移                → O(n)
  • 底层是 Object[] elementData，不是泛型数组（泛型擦除，运行期就是 Object[]）。
  • 默认初始容量 10，但 JDK8 起是懒加载：new ArrayList<>() 时数组是空数组 {}，第一次 add 才扩到 10。
  • 扩容 1.5 倍：newCapacity = oldCapacity + (oldCapacity >> 1)，底层靠 Arrays.copyOf 整体拷贝到新数组。
  • 查询快、随机访问 O(1)；中间插入删除要移位，性能差。
  • 线程不安全，并发 add 会丢数据甚至数组下标越界。
  • 只会扩容，不会自动缩容，remove 掉大量元素后内存不会还给你，需要手动 trimToSize()。
java
List<String> list = new ArrayList<>();      // 此时 elementData 是空数组，容量 0
list.add("a");                              // 首次 add 才真正分配 capacity = 10
List<String> sized = new ArrayList<>(1000); // ✅ 已知数据量就一次给够，避免反复扩容拷贝

// 中间插入/删除的真实代价
list.add(0, "head");   // System.arraycopy 把后面全部元素往后挪一格
list.remove(0);        // 再挪回来

加粗要点： ArrayList 的性能优势不只是「下标寻址」，更重要的是内存连续带来的 CPU 缓存命中率。所以即使是遍历场景，ArrayList 也普遍比 LinkedList 快几倍 —— 这是回答「两者区别」时最能加分的一句。

3. LinkedList：双向链表 ​

text
LinkedList 内部结构（每个 Node 持有 prev / item / next 三个引用）
  first ──► ┌──────┐ ⇄ ┌──────┐ ⇄ ┌──────┐ ◄── last
            │ null │   │      │   │      │
            │  A   │   │  B   │   │  C   │
            └──────┘   └──────┘   └──────┘ null

addFirst / addLast / removeFirst / removeLast  → O(1)，只改指针
get(index)                                      → O(n)，从头或从尾遍历一半
  • 底层双向链表，Node 节点有 prev、item、next，没有容量概念，不需要扩容。
  • 头尾增删 O(1)；随机访问要遍历，get(i) 内部会判断 i 在前半还是后半，从近的一端开始走（仍是 O(n)）。
  • 实现了 Deque，所以它天然可以当栈、队列、双端队列使用。
  • 线程不安全。
  • 内存开销远大于 ArrayList：每个元素额外多两个引用 + 对象头，单个 Node 在 64 位 JVM 开启指针压缩下约 24 字节。
java
LinkedList<String> deque = new LinkedList<>();
deque.addFirst("a");            // 当栈/双端队列用
deque.addLast("b");
deque.pollFirst();

// ❌ 最经典的误用：用下标遍历 LinkedList，复杂度直接 O(n²)
for (int i = 0; i < list.size(); i++) { list.get(i); }
// ✅ 链表必须用迭代器 / 增强 for 遍历
for (String s : list) { }

加粗要点： 面试答「频繁增删用 LinkedList」只对了一半，完整答案是 「频繁在头尾增删才用，而且现实中更应该用 ArrayDeque」：ArrayDeque 基于循环数组，同样 O(1) 头尾操作，但内存连续、没有节点对象开销，实测比 LinkedList 快一个档次。真正非用 LinkedList 不可的场景极少。

4. 线程安全的 List：Vector、synchronizedList、CopyOnWriteArrayList ​

实现加锁方式读性能写性能结论
Vector每个方法 synchronized差（也要锁）差古老，已废弃
Collections.synchronizedList包装类，方法内 synchronized差（也要锁）差偶尔用于快速改造老代码
CopyOnWriteArrayList写时整个数组复制 + ReentrantLock极好（无锁）极差（O(n) 复制）读多写极少场景（白名单、监听器列表）
java
// Vector：连 get 都要抢锁，多线程读反而比加读写锁更慢
Vector<String> v = new Vector<>();

// 包装类：注意复合操作仍然不安全
List<String> sync = Collections.synchronizedList(new ArrayList<>());
if (!sync.contains("a")) { sync.add("a"); }   // ❌ 两步之间可能被插入，需要自己 synchronized (sync) {}

// CopyOnWriteArrayList：每次 add 都 Arrays.copyOf 一份新数组再替换引用
List<String> cow = new CopyOnWriteArrayList<>();
cow.add("a");  // 写：加锁 + 复制整个数组
cow.get(0);    // 读：直接读 volatile 数组，完全不加锁

加粗要点： CopyOnWriteArrayList 换来无锁读的代价是两份内存 + 写操作 O(n)，并且迭代器是弱一致性的（遍历的是开始迭代那一刻的快照，遍历期间别人的修改看不到，但也因此永远不会抛 ConcurrentModificationException）。写多的场景用它等于自杀。

5. Set 三兄弟：本质都是包了一层 Map ​

java
// HashSet 的真实实现（JDK 源码简化）
public class HashSet<E> {
    private transient HashMap<E, Object> map;
    private static final Object PRESENT = new Object(); // 固定占位 value

    public boolean add(E e) {
        return map.put(e, PRESENT) == null; // put 返回旧值，为 null 说明是新元素
    }
}
实现底层顺序判重依据额外要求
HashSetHashMap无序（哈希顺序）hashCode() + equals()元素必须正确重写这两个方法
LinkedHashSetLinkedHashMap插入顺序同上比 HashSet 多一条双向链表的开销
TreeSetTreeMap排序顺序compareTo / Comparator 返回 0元素必须可比较，否则 ClassCastException
java
// ⚠️ TreeSet 的判重用的是比较器而不是 equals，这会造成「看起来不重复却被去掉」
TreeSet<User> set = new TreeSet<>(Comparator.comparingInt(User::getAge));
set.add(new User("张三", 20));
set.add(new User("李四", 20));   // ❌ 被当成重复元素，加不进去！因为比较器只看 age

// ⚠️ HashSet 去重失效的典型原因：只重写了 equals 没重写 hashCode
Set<User> users = new HashSet<>();
users.add(new User("张三", 20));
users.add(new User("张三", 20));
System.out.println(users.size()); // 没重写 hashCode → 2（两条一样的数据）

加粗要点： Set 的「不可重复」完全依赖元素自己的判重实现 —— 哈希类看 hashCode+equals，树类看比较结果是否为 0。用自定义对象做 Set 元素或 Map 的 key 之前，必须先确认 equals/hashCode 是否成对重写（Lombok 的 @Data、IDEA 的 Generate、Objects.hash() 都能生成）。

6. Queue 与 Deque：栈、队列、优先级队列 ​

text
队列三套 API（这就是为什么同一件事有两个方法名）
            抛异常          返回特殊值
 入队        add(e)          offer(e)   → 队列满时返回 false
 出队        remove()        poll()     → 队列空时返回 null
 查看队首    element()       peek()     → 队列空时返回 null

ArrayDeque 的循环数组（head/tail 指针绕圈走，不需要搬移元素）
   ┌───┬───┬───┬───┬───┬───┬───┬───┐
   │ D │   │   │ A │ B │ C │   │   │
   └───┴───┴───┴───┴───┴───┴───┴───┘
     ↑tail        ↑head
   addFirst → head 往左绕；addLast → tail 往右走；容量不足则翻倍扩容
实现底层用途注意点
ArrayDeque循环数组栈 / 队列 / 双端队列不允许 null（null 被用作空标记）
LinkedList双向链表队列（可存 null）节点开销大，缓存不友好
PriorityQueue二叉堆（数组）TopK、任务优先级只保证堆顶最小，遍历顺序不是有序的
ArrayBlockingQueue定长数组 + 锁线程池工作队列必须指定容量，满了会阻塞
LinkedBlockingQueue链表 + 双锁生产者消费者默认容量是 Integer.MAX_VALUE，容易 OOM
java
// ✅ Java 里用栈，首选 ArrayDeque，不要用 Stack（继承 Vector，全方法加锁）
Deque<Integer> stack = new ArrayDeque<>();
stack.push(1);          // 等价 addFirst
stack.pop();            // 等价 removeFirst

// PriorityQueue 求 TopK：维护一个大小为 k 的小顶堆
PriorityQueue<Integer> heap = new PriorityQueue<>();      // 默认小顶堆
for (int num : nums) {
    heap.offer(num);
    if (heap.size() > k) heap.poll();                     // 堆顶是最小的，弹掉
}
// 堆里剩下的就是最大的 k 个；heap.peek() 是第 k 大

// 大顶堆写法
PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Comparator.reverseOrder());

加粗要点： 三个必记结论 —— ① 栈用 ArrayDeque，别用 Stack；② ArrayDeque 不能存 null；③ PriorityQueue 直接 toString() 或遍历出来不是有序的，想要有序必须不断 poll()。

7. HashMap：数组 + 链表 + 红黑树 ​

text
JDK8 HashMap 结构（table 数组长度恒为 2 的 n 次方）
table
 [0] → null
 [1] → Node(k1,v1) → Node(k9,v9) → null          ← 哈希冲突，链表（尾插）
 [2] → null
 [3] → TreeNode(红黑树根)                         ← 链表过长已树化
 ...        ├── TreeNode
 [15]→ null └── TreeNode

              JDK7                         JDK8
结构      数组 + 链表                  数组 + 链表 + 红黑树
插入      头插法（并发扩容会成环）      尾插法
冲突查询  O(n)                        链表 O(n) / 红黑树 O(log n)

四个必须背下来的常量：

常量值含义
DEFAULT_INITIAL_CAPACITY16（1 << 4）默认数组长度，必须是 2 的 n 次方
DEFAULT_LOAD_FACTOR0.75f负载因子，阈值 = 容量 × 0.75，超过就扩容（翻倍）
TREEIFY_THRESHOLD8链表长度 ≥ 8 时尝试树化
UNTREEIFY_THRESHOLD6扩容拆分后树节点 ≤ 6 退化回链表
MIN_TREEIFY_CAPACITY64数组容量 < 64 时优先扩容而不是树化
java
// 树化的真实判断（putVal → treeifyBin 源码简化）
if (binCount >= TREEIFY_THRESHOLD - 1) {   // 链表长度达到 8
    treeifyBin(tab, hash);
}
void treeifyBin(Node<K,V>[] tab, int hash) {
    if (tab == null || tab.length < MIN_TREEIFY_CAPACITY) {
        resize();          // ⚠️ 容量不足 64，先扩容而不是树化
    } else {
        // 真正转成红黑树
    }
}

加粗要点： 树化条件是两个条件同时满足：链表长度 ≥ 8 且 数组容量 ≥ 64。只答前半句是最常见的扣分点。原因是容量小的时候冲突多是因为「桶太少」，扩容比树化更划算、代价也更低。

8. hash 扰动与寻址：为什么容量必须是 2 的 n 次方 ​

java
// ① 扰动函数：把 hashCode 的高 16 位异或到低 16 位
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

// ② 寻址：用位与代替取模
int index = (table.length - 1) & hash;
text
为什么要扰动？（容量 16 时，取模只用到 hash 的低 4 位）
  hashCode : 1111 1111 1111 1111 0000 0000 0000 0101
  (n-1)    : 0000 0000 0000 0000 0000 0000 0000 1111
  直接相与 → 高 28 位全部被丢弃，高位的差异完全不参与寻址 → 冲突率高

  h ^ (h >>> 16) 先把高 16 位的特征混进低 16 位，再相与
  → 让 hash 的高位也能影响桶下标，分布更均匀，冲突更少

为什么 (n-1) & hash 能代替 hash % n？
  n = 16  → n-1 = 0000 1111（低位全 1）
  任意 hash & 0000 1111 的结果 ∈ [0, 15]，与 hash % 16 完全等价
  前提：n 必须是 2 的 n 次方，否则 n-1 的二进制有 0 位，
        那些位永远取不到 1 → 部分桶永远空着，另一些桶冲突翻倍
  收益：位运算比除法/取模快一个数量级（CPU 层面差几十倍）
设计目的
容量恒为 2 的 n 次方让 (n-1) & hash 等价于取模，用位运算提速
高 16 位异或扰动弥补「只用低位寻址」导致的高位信息丢失，降低冲突
扩容按 2 倍保持 2 的 n 次方，且让 rehash 可以用高低位拆分优化
负载因子 0.75空间利用率与冲突概率的折中（泊松分布下冲突概率最优）
java
// 即使你传入一个奇怪的初始容量，HashMap 也会向上取整到 2 的 n 次方
Map<String, String> map = new HashMap<>(13);
// tableSizeFor(13) = 16

// tableSizeFor 的位运算推导：把最高位的 1 向右「铺满」再 +1
static final int tableSizeFor(int cap) {
    int n = cap - 1;
    n |= n >>> 1;  n |= n >>> 2;  n |= n >>> 4;
    n |= n >>> 8;  n |= n >>> 16;
    return (n < 0) ? 1 : (n >= MAXIMUM_CAPACITY) ? MAXIMUM_CAPACITY : n + 1;
}

加粗要点： 「容量 2 的 n 次方」不是为了好看，而是同时服务了三件事：寻址可用位运算、扩容可用高低位拆分免重算 hash、桶分布均匀。回答时把这三点串起来，比只说「为了取模快」深一个层次。

9. LinkedHashMap 与 TreeMap ​

text
LinkedHashMap = HashMap 的桶结构 + 一条贯穿所有节点的双向链表
 table: [0]→Entry(A)   [3]→Entry(B)   [7]→Entry(C)
          ╱                ╱                ╱

new LinkedHashMap<K, V>(capacity, 0.75f, true) {
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > maxSize;   // 返回 true 时自动淘汰链表头（最久未访问）

11. equals 与 hashCode 契约 ​

text
HashMap 判断「两个 key 是否是同一个 key」的完整流程：
  1. 算 hash → 定位桶，桶里没节点 → 直接插入

       p.hash == hash                       ← 先比 hash（int 比较，极快）

→ 只重写 equals 不重写 hashCode：两个「相等」的对象 hash 不同

→ 只重写 hashCode 不重写 equals：落到同一个桶但 equals 为 false
   → 同样被当成两个不同的 key

a.equals(b) 为 true → hashCode 必须相等强制，违反则集合行为错乱
hashCode 相等 → equals 不一定为 true允许，这就是哈希冲突

1. ArrayList 扩容源码逐行拆解 ​

// JDK8 ArrayList 核心字段
private static final int DEFAULT_CAPACITY = 10;
private static final Object[] EMPTY_ELEMENTDATA = {};
private static final Object[] DEFAULTCAPACITY_EMPTY_ELEMENTDATA = {};  // ⚠️ 两个空数组
transient Object[] elementData;
private int size;

public boolean add(E e) {
    ensureCapacityInternal(size + 1);   // 确保容量够
    elementData[size++] = e;
    return true;
}

private void ensureCapacityInternal(int minCapacity) {
    if (elementData == DEFAULTCAPACITY_EMPTY_ELEMENTDATA) {
        minCapacity = Math.max(DEFAULT_CAPACITY, minCapacity);  // 首次 add 才真正开 10
    }
    ensureExplicitCapacity(minCapacity);
}

private void grow(int minCapacity) {
    int oldCapacity = elementData.length;
    int newCapacity = oldCapacity + (oldCapacity >> 1);   // ⭐ 1.5 倍（右移 1 位 = 除 2）
    if (newCapacity - minCapacity < 0) newCapacity = minCapacity;        // 一次加太多元素
    if (newCapacity - MAX_ARRAY_SIZE > 0) newCapacity = hugeCapacity(minCapacity);
    elementData = Arrays.copyOf(elementData, newCapacity);  // ⭐ 新建数组 + 整体拷贝
}

  第 11 次 add           → 10 + 10>>1 = 15
  第 16 次               → 15 + 7  = 22

3. LinkedList 为什么实际上比 ArrayList 更慢 ​

text
理论：ArrayList 中间插入 O(n)，LinkedList 插入 O(1)

   → 同样 100 万个元素，LinkedList 多占近 10 倍内存，GC 压力更大

5. 扩容的高低位拆分：e.hash & oldCap ​

text
JDK8 最精妙的优化：扩容后节点的新下标只有两种可能
  旧容量 16 → 新容量 32
  旧下标 i = hash & 15（低 4 位）
  新下标     = hash & 31（低 5 位）
  → 差别仅在于「第 5 位（即 oldCap=16 这一位）」是 0 还是 1

  hash & oldCap == 0  →  新下标 = 原下标 i        （留在低位链 loHead）
  hash & oldCap != 0  →  新下标 = 原下标 i + 16   （搬到高位链 hiHead）

举例：oldCap = 16
  hash = ...0 0101  & 15 = 5    & 16 = 0  → 新下标仍是 5
  hash = ...1 0101  & 15 = 5    & 16 = 16 → 新下标 5 + 16 = 21

迁移示意
  旧 table[5] : A → B → C → D
                ↓ 按 e.hash & 16 拆成两条链（保持相对顺序）
  新 table[5] : A → C          （lo 链）
  新 table[21]: B → D          （hi 链）
java
// resize() 中链表拆分的源码（简化）
Node<K,V> loHead = null, loTail = null;
Node<K,V> hiHead = null, hiTail = null;
do {
    next = e.next;
    if ((e.hash & oldCap) == 0) {      // ⭐ 核心判断，不需要重算 hash，不需要重新取模
        if (loTail == null) loHead = e; else loTail.next = e;
        loTail = e;
    } else {
        if (hiTail == null) hiHead = e; else hiTail.next = e;
        hiTail = e;
    }
} while ((e = next) != null);
if (loTail != null) { loTail.next = null; newTab[j] = loHead; }
if (hiTail != null) { hiTail.next = null; newTab[j + oldCap] = hiHead; }

迁移方式遍历每个节点，indexFor 重新计算下标e.hash & oldCap 判断高低位
是否重算 hash要重新取模不用，只做一次位与
链表顺序头插 → 顺序反转尾插 → 保持原相对顺序
并发下的后果可能形成环形链表导致 CPU 100%不会成环（但仍可能丢数据，依旧不安全）

加粗要点： e.hash & oldCap 这一行是 JDK8 HashMap 的灵魂：把「重新取模」变成「一次位与」，把「全量 rehash」变成「链表二分」。它成立的前提依然是容量为 2 的 n 次方，和前面的寻址优化是同一套设计在呼应。

6. JDK7 并发扩容的死循环 ​

text
JDK7 transfer 用头插法，两个线程同时扩容时：
  初始 旧桶: A → B → null

  线程 1 执行到 e = A, next = B 后被挂起
  线程 2 完整执行完迁移，头插导致顺序反转 → 新桶: B → A → null

  线程 1 恢复，它手里的 e = A, next = B（旧快照）
    put A → 新桶: A → ...
    e = B，put B，头插 → B.next = A
    e = A（B.next 在线程 2 的结果里指向 A）
    put A，头插 → A.next = B

  最终:  A ⇄ B   形成环形链表
  后续任何 get() 落到这个桶 → while 死循环 → CPU 飙到 100%

  ① 选 8 → 正常情况下永远不会触发树化，树化只是「极端 hash 冲突」的兜底保险
  ② TreeNode 的体积约是普通 Node 的 2 倍，无脑树化纯属浪费内存
  ③ 链表长度小于 8 时，O(n) 遍历的实际开销并不比 O(log n) 的红黑树差
     （红黑树还有旋转、变色、比较器调用的额外成本）

为什么退化阈值是 6，而不是 8？
  如果树化和退化都用 8，那么节点数在 7 ⇄ 8 之间反复抖动时，
  会不停地「树化 → 退化 → 树化」，频繁结构转换代价极高。
  中间留一个 7 作为缓冲区 → 这就是「滞后/迟滞（hysteresis）」设计。
阈值值设计动机
TREEIFY_THRESHOLD8泊松分布下概率 ≈ 6e-8，作为兜底而非常态
UNTREEIFY_THRESHOLD6与 8 之间留缓冲，避免临界点反复抖动
MIN_TREEIFY_CAPACITY64小表冲突多是桶太少，扩容比树化更划算

8. 负载因子 0.75 与初始容量预估 ​

负载因子 = 阈值 / 容量，决定「多满就扩容」

  负载因子太小（如 0.5）→ 数组很空就扩容 → 空间浪费、扩容频繁

④ 多线程协助扩容：ForwardingNode + transferIndex

10. ConcurrentHashMap 的 size() 为什么是估算值 ​

java
// CHM 没有用一个 volatile int size（那会成为并发瓶颈，所有线程都在抢同一个变量）
// 而是借鉴 LongAdder 的「分段累加」思想
private transient volatile long baseCount;        // 无竞争时累加到这里
private transient volatile CounterCell[] counterCells;  // 有竞争时分散到数组

final long sumCount() {
    CounterCell[] as = counterCells;
    long sum = baseCount;
    if (as != null)
        for (CounterCell a : as)
            if (a != null) sum += a.value;         // ⚠️ 遍历求和期间，别的线程还在改
    return sum;
}

public int size() {
    long n = sumCount();
    return ((n < 0L) ? 0 : (n > Integer.MAX_VALUE) ? Integer.MAX_VALUE : (int) n);
}
public long mappingCount() { return Math.max(sumCount(), 0L); }  // ⭐ 推荐用这个，返回 long
text
分段累加示意
  线程 1 ─┐
  线程 2 ─┼─ CAS baseCount 失败 → 转而写入自己哈希到的 CounterCell
  线程 3 ─┘
            baseCount = 100
            counterCells = [ 12 | 7 | — | 23 | — ]
            size ≈ 100 + 12 + 7 + 23 = 142

  好处：把「一个热点变量」拆成「多个独立变量」→ 消除 CAS 竞争（伪共享用 @Contended 解决）
  代价：size() 是遍历求和，结果是某个时间点的「近似快照」，不保证精确

加粗要点： 答题要点：CHM 的 size() 用 baseCount + CounterCell[] 分段累加（同 LongAdder），目的是消除单一计数器的 CAS 热点，代价是结果只是估算值。所以绝对不要用 chm.size() 做精确的业务判断（比如「满 100 个就触发」），JDK8+ 还提供了返回 long 的 mappingCount()。

12. 复合操作的原子性与弱一致迭代器 ​

java
ConcurrentHashMap<String, Integer> counter = new ConcurrentHashMap<>();

// ❌ 错误 1：check-then-act 不原子
if (!counter.containsKey(k)) counter.put(k, 1);

// ❌ 错误 2：read-modify-write 不原子（丢更新的经典案例）
counter.put(k, counter.get(k) + 1);

// ❌ 错误 3：以为加了 synchronized 就万事大吉（锁对了，但完全丧失并发性能）
synchronized (this) { counter.put(k, counter.get(k) + 1); }

// ✅ 正确：用 CHM 提供的原子复合方法
counter.merge(k, 1, Integer::sum);              // 最简洁的原子累加
counter.compute(k, (key, v) -> v == null ? 1 : v + 1);
counter.computeIfAbsent(k, key -> loadFromDb(key));
counter.putIfAbsent(k, 0);
counter.replace(k, oldVal, newVal);             // CAS 语义

// ✅ 高并发计数的更优解：value 用 LongAdder，避免每次都走 CHM 的桶锁
ConcurrentHashMap<String, LongAdder> fast = new ConcurrentHashMap<>();
fast.computeIfAbsent(k, key -> new LongAdder()).increment();

⚠️ computeIfAbsent 的两个致命坑

坑 1：mapping 函数里不能再操作同一个 map（JDK8 会死锁 / 死循环）
  map.computeIfAbsent("a", k -> {
      map.put("b", 1);        // ❌ 可能死锁：b 恰好 hash 到同一个桶，而该桶已被当前线程 synchronized
      return 1;
  });

坑 2：mapping 函数耗时很长（如远程调用）会把整个桶锁住
  map.computeIfAbsent(k, key -> rpcCall(key));   // ⚠️ 同桶的其他 key 全部阻塞
  → 缓存场景应改为「先 get，miss 再加载，最后 putIfAbsent」或用 Caffeine
迭代器类型行为代表
fail-fast结构变化立即抛 CMEArrayList、HashMap
弱一致（weakly consistent）不抛 CME；能看到创建后的部分修改，但不保证全部ConcurrentHashMap
快照（snapshot）完全基于创建时的数组副本，后续修改一概看不到CopyOnWriteArrayList

加粗要点： ConcurrentHashMap 只保证单个方法的原子性，不保证多个方法组合的原子性。遇到「判断再写」「读改写」一律换成 merge / compute / computeIfAbsent / putIfAbsent。另外记住 computeIfAbsent 的函数体里绝不能回头操作同一个 map。

13. CopyOnWriteArrayList 的适用边界 ​

java
public boolean add(E e) {
    final ReentrantLock lock = this.lock;
    lock.lock();                                  // 写操作加独占锁（JDK11 后改为 synchronized）
    try {
        Object[] es = getArray();
        int len = es.length;
        es = Arrays.copyOf(es, len + 1);          // ⭐ 每次写都复制整个数组
        es[len] = e;
        setArray(es);                             // ⭐ volatile 写，一次性切换引用
        return true;
    } finally { lock.unlock(); }
}

public E get(int index) {
    return elementAt(getArray(), index);          // ⭐ 读完全无锁，无 volatile 开销之外的成本
}
text
写时复制（Copy-On-Write）示意
  读线程持有的引用 ──► [a][b][c]       ← 老数组，读线程继续安全遍历
  写线程            ──► [a][b][c][d]   ← 复制一份加上 d，然后 array = 新数组

  ⇒ 读写不互斥，读永远不会被阻塞，也永远不会抛 CME
  ⇒ 但迭代器拿到的是「创建那一刻的快照」，看不到之后的写入
  ⇒ 写操作 O(n)：10 万元素的列表，每次 add 都复制 10 万个引用
维度CopyOnWriteArrayListCollections.synchronizedList
读性能极高（无锁）低（要抢锁）
写性能极低（O(n) 复制 + 独占锁）中（锁但不复制）
内存写时双倍占用正常
迭代器快照，不抛 CME，不支持 removefail-fast
数据实时性最终一致（读可能读到旧数据）强一致
适用读远多于写：配置、白名单、监听器列表写较频繁且并发不高

17. 遍历 Map 的五种方式与性能差异 ​

java
Map<String, Integer> map = new HashMap<>();

// ① keySet + get ——❌ 最差，每个 key 都要再查一次 hash（两次遍历成本）
for (String k : map.keySet()) { Integer v = map.get(k); }

// ② entrySet —— ✅ 推荐，一次遍历同时拿到 key 和 value
for (Map.Entry<String, Integer> e : map.entrySet()) {
    String k = e.getKey();  Integer v = e.getValue();
    e.setValue(v + 1);            // ⭐ 只有 entrySet 能原地改 value
}

// ③ 迭代器 —— ✅ 需要边遍历边删除时用
Iterator<Map.Entry<String, Integer>> it = map.entrySet().iterator();
while (it.hasNext()) {
    if (it.next().getValue() == null) it.remove();
}

// ④ forEach（JDK8）—— ✅ 代码最简洁，但不能 break、不能删除
map.forEach((k, v) -> System.out.println(k + "=" + v));

// ⑤ Stream —— 适合「遍历 + 过滤 + 转换」一气呵成，单纯遍历反而更慢
map.entrySet().stream()
   .filter(e -> e.getValue() > 10)
   .forEach(e -> System.out.println(e.getKey()));

// ✅ 批量删除的最佳写法
map.entrySet().removeIf(e -> e.getValue() == null);
map.values().removeIf(Objects::isNull);           // keySet/values/entrySet 都是视图，删除会反映到源 map

entrySet✅✅❌✅默认选择
Iterator✅✅✅✅要删除时用
forEach✅✅❌❌简洁场景

18. 比较器契约与 Comparison method violates its general contract! ​

这是 Java 集合里**最典型的「本地测不出、上量才炸」**的异常，根因不是 JDK 的 bug，而是自己写的 Comparator 违反了契约。

三条契约（必须同时满足）：

契约形式化表述最常见的违反写法
反对称性sgn(compare(a,b)) == -sgn(compare(b,a))漏掉「相等返回 0」，相等时两边都返回 -1
传递性compare(a,b)>0 && compare(b,c)>0 ⇒ compare(a,c)>0多字段比较时分支写漏、互相覆盖
等价传递compare(a,b)==0 ⇒ sgn(compare(a,c)) == sgn(compare(b,c))相等判定依据和排序依据不是同一个字段
java
// ❌ 违约写法 1：漏掉「相等返回 0」—— 直接违反反对称性
list.sort((a, b) -> a.getScore() > b.getScore() ? 1 : -1);
// 当 a.score == b.score 时，compare(a,b) = -1，compare(b,a) 也 = -1
// 两个元素互相认为「我比你小」，TimSort 归并时发现 run 不单调 → 抛异常

// ❌ 违约写法 2：整数相减溢出
list.sort((a, b) -> a.getBalance() - b.getBalance());
// balance 是 int 且跨正负大数时，相减溢出符号翻转：
// 2_000_000_000 - (-2_000_000_000) = -294_967_296 → 结果变成「大的更小」

// ❌ 违约写法 3：比较依据不稳定（随机数 / 当前时间 / 可变字段）
list.sort((a, b) -> Double.compare(Math.random(), 0.5));          // 每次比较结果都不同
list.sort((a, b) -> Long.compare(a.refreshAt(), b.refreshAt()));  // 排序过程中字段被别的线程改了

// ❌ 违约写法 4：null 字段直接 NPE 或被当成最小值随意处理
list.sort((a, b) -> a.getName().compareTo(b.getName()));          // name 为 null 直接炸

// ✅ 正确写法：全部交给 Comparator 工厂方法，杜绝手写分支
list.sort(Comparator
        .comparingInt(User::getAge)                               // 不会溢出（内部用 Integer.compare）
        .thenComparing(User::getName, Comparator.nullsLast(Comparator.naturalOrder()))
        .thenComparing(User::getId));                             // ⭐ 兜底加一个唯一字段，保证全序

为什么「小数据量不报、上量才报」：

text
Arrays.sort(Object[])  →  TimSort
   ├─ 数组长度 < 32（MIN_MERGE）→ 走 binarySort（二分插入排序）
   │                             不做 run 合并，不校验契约 → 违约也不报错，只是结果顺序乱
   └─ 数组长度 ≥ 32              → 切分 run + 归并
                                   mergeLo / mergeHi 里依赖「run 内单调」这一前提
                                   发现越界 → throw IllegalArgumentException
                                              ("Comparison method violates its general contract!")

所以这个异常的本质是：违约一直存在，只是数据量小的时候表现为「排序结果不对」，数据量大了才表现为「抛异常」。线上报这个错，不要去查 JDK 版本，直接去审 Comparator。

-Djava.util.Arrays.useLegacyMergeSort=true 能让异常消失，但这是掩盖问题：它只是退回 JDK6 的归并排序（不校验契约），排序结果依然是错的，而且多占一倍临时内存。只应作为「线上紧急止血 + 当天修比较器」的手段。

另一个隐蔽后果：比较器与 equals 不一致

set.add(new User(1, "张三", 20));
set.add(new User(2, "李四", 20));     // ⚠️ 加不进去！size 仍为 1
// TreeMap / TreeSet 判重用的是 compare(a,b) == 0，完全不看 equals
// 两个 equals 不等的对象，只要年龄相同就被认为是「同一个元素」

set.contains(new User(99, "王五", 20));  // → true，但 HashSet 下会是 false

HashSet / HashMaphashCode + equals—

排序稳定性也要记住：Arrays.sort(int[]) 等基本类型用双轴快排（不稳定，但基本类型没有「相等但不同」的概念，无影响）；Arrays.sort(Object[]) 和 List.sort 用 TimSort（稳定），这是「先按 A 排再按 B 排」能叠加生效的前提。

加粗要点： Comparison method violates its general contract! 是自己的比较器违约，不是 JDK 问题。三条铁律：绝不用 a - b 相减（用 Integer.compare）、绝不漏掉相等返回 0（用 Comparator.comparing 系列工厂方法而不是手写三元）、多字段链末尾补一个唯一字段保证全序。另外记住 TreeSet/TreeMap 判重只看 compare()==0，完全不看 equals，比较器只比一个字段就会把不同对象误去重。

19. 三个特种 Map：EnumMap、IdentityHashMap、WeakHashMap ​

这三个平时用得少，但它们各自解决一类「普通 HashMap 解决不了」的问题，面试问到能答出场景就很加分。

实现底层key 判等依据典型场景
EnumMap数组，下标 = ordinal()枚举身份（==）枚举做 key 的所有场景
IdentityHashMap线性探测的平坦数组== 引用相等对象图遍历去重、序列化/深拷贝防循环引用
WeakHashMap数组 + 链表，key 是弱引用equalskey 生命周期由外部决定的旁路缓存
java
// ① EnumMap：没有 hash、没有冲突、没有扩容，就是一个数组
EnumMap<Status, Integer> counter = new EnumMap<>(Status.class);
counter.put(Status.PAID, 10);
// 内部：vals[Status.PAID.ordinal()] = 10
// 优势：O(1) 且常数极小、迭代顺序天然按枚举声明顺序、内存只有 HashMap 的几分之一
// ⚠️ 不接受 null key；ordinal 依赖枚举声明顺序，但它不会被持久化，所以改枚举顺序是安全的

// ② IdentityHashMap：故意不用 equals
Map<Object, Object> visited = new IdentityHashMap<>();
void deepCopy(Object node) {
    if (visited.containsKey(node)) return;   // 只有「同一个对象」才算访问过
    visited.put(node, Boolean.TRUE);
    // ...
}
// 为什么不能用 HashMap：两个 equals 相等但不同的节点会被误判为「已访问」，
// 导致对象图被错误折叠。JDK 的序列化、Jackson 的循环引用检测都用它。
// ⚠️ 它故意违反 Map 接口契约（Map 规定用 equals），别当通用 Map 用

// ③ WeakHashMap：key 没人引用了，整个 entry 自动消失
Map<ClassLoader, Config> cache = new WeakHashMap<>();
cache.put(loader, config);
loader = null;        // 外部不再引用 key
System.gc();          // GC 后这个 entry 会被自动清掉（下次访问 map 时清理队列）

WeakHashMap 的两个致命误解：

java
// ❌ 误解 1：以为「value 没人用了也会被回收」—— 弱的是 key，不是 value
Map<String, byte[]> cache = new WeakHashMap<>();
cache.put(key, new byte[10 * 1024 * 1024]);
// 如果 value 内部直接或间接引用了 key，就形成「强引用环」：
// Entry.value → key，而 Entry 被 table 强引用 → key 永远不会被回收 → 永不失效的泄漏

// ❌ 误解 2：用字符串常量当 key
cache.put("userConfig", config);     // 字面量在常量池里被永久强引用 → 这个 entry 永远不会回收

// ✅ 正确姿势：key 必须是「生命周期由外部明确控制」的对象
// 典型：ClassLoader、Thread、Class、框架里的组件实例

顺带讲清 ThreadLocal 内存泄漏的真正机制（面试高频，很多人答错）：

text
Thread 对象
  └─ threadLocals: ThreadLocalMap
       └─ Entry[]           ← Entry extends WeakReference<ThreadLocal<?>>
            ├─ key   : 弱引用指向 ThreadLocal 实例   ← ThreadLocal 没人引用时会被回收 → key = null
            └─ value : 强引用指向你放进去的值         ← ⚠️ 没人清，就一直在

泄漏链：线程池的核心线程不死 → Thread 一直活
       → ThreadLocalMap 一直活 → key=null 但 value 还被强引用
       → value（可能是一个大对象 / 持有上下文的整条引用链）永远回收不掉
  • 为什么 key 设计成弱引用：避免「ThreadLocal 变量本身」成为泄漏源，这是减轻泄漏而不是解决泄漏
  • get / set 时会顺手清理一部分 key == null 的槽位（expungeStaleEntry），但不保证清完
  • 真正的解法只有一个：try { ... } finally { threadLocal.remove(); }，在线程池场景下这是硬性要求
  • InheritableThreadLocal 在线程池里还会错传上下文（线程复用时继承的是创建时的快照），要用 TransmittableThreadLocal 这类方案

加粗要点： 枚举做 key 一律用 EnumMap（就是个数组，没 hash 没扩容）；对象图去重、防循环引用用 IdentityHashMap（按 == 判等，故意不走 equals）；WeakHashMap 弱的是 key 不是 value，value 若引用了 key 就是永不失效的泄漏，且字符串字面量当 key 永远不会被回收。ThreadLocal 泄漏的根源是 Entry.value 是强引用（key 才是弱引用），线程池里必须 finally { remove(); }。

20. 集合拷贝的三个层次，以及 toArray 的三个坑 ​

「把集合复制一份」这句话在 Java 里有三种完全不同的语义，混淆它们是线上数据被意外改动的常见原因。

java
List<User> src = new ArrayList<>(List.of(new User(1, "张三")));

// 层次 ①：视图（View）—— 没有新容器，共享同一份底层数据
List<User> view1 = Collections.unmodifiableList(src);   // 只读视图，src 改了它也变
List<User> view2 = src.subList(0, 1);                   // 子视图，改它会写回 src
Set<String> view3 = map.keySet();                       // keySet/values/entrySet 都是视图

// 层次 ②：浅拷贝（Shallow Copy）—— 新容器，但装的是同一批对象引用
List<User> shallow1 = new ArrayList<>(src);             // ⭐ 最常用，是浅拷贝
List<User> shallow2 = (List<User>) ((ArrayList<User>) src).clone();
List<User> shallow3 = src.stream().collect(Collectors.toList());
List<User> shallow4 = List.copyOf(src);                 // 不可变 + 浅拷贝
User[] arr = src.toArray(new User[0]);                  // 也是浅拷贝

shallow1.add(new User(2, "李四"));   // ✅ 不影响 src —— 容器是独立的
shallow1.get(0).setName("王五");     // ⚠️ src.get(0).getName() 也变成了"王五"！

// 层次 ③：深拷贝（Deep Copy）—— 容器和元素都是新的
List<User> deep = src.stream().map(User::copy).collect(Collectors.toList());
操作新容器新元素源集合改动会影响它吗它的改动会影响源集合吗
unmodifiableList / subList❌❌✅ 会✅ 会（subList 可写回）
new ArrayList<>(src)✅❌结构不影响，元素内部会结构不影响，元素内部会
List.copyOf / ImmutableList✅❌同上不可改（但元素内部仍可改）
map(::copy) 深拷贝✅✅❌❌

关键认知：Java 里没有任何一个 API 会帮你做深拷贝。clone()、拷贝构造、Collectors.toList()、List.copyOf 全是浅拷贝。只要元素是可变对象，「拷贝一份再改」就会穿透到源集合。防御性拷贝要生效，必须要么元素本身不可变（全 final 字段），要么手写元素级的 copy。

Collections.copy 不是你想的那个 copy：

java
List<User> dest = new ArrayList<>(src.size());   // ⚠️ size 是 0，capacity 才是 10
Collections.copy(dest, src);                     // → IndexOutOfBoundsException: Source does not fit in dest
// 它要求 dest.size() >= src.size()，是「按下标覆盖已有元素」，不是「填充空集合」
// 想复制一份：直接 new ArrayList<>(src)

toArray 的三个坑：

java
List<String> list = List.of("a", "b");

// 坑 1：无参 toArray() 返回 Object[]，强转会抛 ClassCastException
String[] bad = (String[]) list.toArray();        // ❌ ClassCastException
// 原因：底层数组的「运行时类型」就是 Object[]，泛型擦除后 JDK 没法知道你要什么类型

// ✅ 正确：传入类型化数组
String[] ok1 = list.toArray(new String[0]);      // ⭐ 推荐，传长度 0 最快（JIT 对 0 长度有优化）
String[] ok2 = list.toArray(String[]::new);      // JDK11+，等价且更直观

// 坑 2：Arrays.asList 包装数组后结构不可变
List<String> fixed = Arrays.asList(ok1);
fixed.add("c");                                  // ❌ UnsupportedOperationException
fixed.set(0, "z");                               // ✅ set 可以，而且会写回原数组 ok1！

// 坑 3：基本类型数组被当成单个元素
int[] nums = {1, 2, 3};
List<int[]> wrong = Arrays.asList(nums);         // ⚠️ size = 1，装的是整个数组对象
List<Integer> right = Arrays.stream(nums).boxed().collect(Collectors.toList());

并行流写入非线程安全集合（高频事故）：

java
// ❌ 看起来很美，实际会丢数据、甚至抛 ArrayIndexOutOfBoundsException
List<String> result = new ArrayList<>();
data.parallelStream().forEach(result::add);       // ArrayList 的 add 没有任何同步

// ✅ 方案 A：用 collect，Stream 框架自己负责分段合并
List<String> r1 = data.parallelStream().collect(Collectors.toList());
// ✅ 方案 B：确实要 forEach 就用线程安全容器
List<String> r2 = Collections.synchronizedList(new ArrayList<>());
// ✅ 方案 C：收集到 Map 时用并发版本，避免 merge 阶段的额外拷贝
Map<String, Long> r3 = data.parallelStream()
        .collect(Collectors.groupingByConcurrent(Function.identity(), Collectors.counting()));

加粗要点： 分清三个层次：视图共享底层数据（subList、unmodifiableList、keySet）、new ArrayList<>(src) 是浅拷贝（容器独立但元素共享）、深拷贝必须自己写，JDK 没有任何 API 帮你做。toArray 一律用 toArray(new T[0])，无参版本返回 Object[] 强转必崩。并行流绝不能 forEach(list::add)，要用 collect。

❓ 高频面试题【基础简答 + 连环追问链 + 精简口述答案 + 项目关联话术】 ​

题 1：ArrayList 和 LinkedList 的区别？你平时怎么选？ ​

精简口述答案：

底层结构不同：ArrayList 是动态数组，内存连续，支持下标随机访问，get(i) 是 O(1)；LinkedList 是双向链表，get(i) 要从头或尾遍历，是 O(n)，但它同时实现了 Deque，头尾增删是 O(1)。

扩容上 ArrayList 用 oldCapacity + (oldCapacity >> 1)，也就是 1.5 倍，底层是 Arrays.copyOf 整体拷贝；LinkedList 不需要扩容，但每个元素要多包一个 Node 对象。

但工程上我基本只用 ArrayList。理由有三个：① LinkedList 的 O(1) 插入前提是你已经持有节点引用，add(index, e) 本身还是要先 O(n) 遍历定位；② ArrayList 内存连续，CPU 缓存行命中率高，而链表节点散落在堆上每跳一次都可能 cache miss；③ LinkedList 每个元素的额外开销约 40 字节，是 ArrayList 的近 10 倍，GC 压力大。真的需要双端操作时我用 ArrayDeque，它是循环数组，比 LinkedList 更快也更省内存。

连环追问链：

  1. 追问：ArrayList 的默认容量是 10，是在什么时候分配的？

    • 答：不是构造的时候，是第一次 add 的时候。无参构造只是把 elementData 指向一个静态空数组 DEFAULTCAPACITY_EMPTY_ELEMENTDATA，ensureCapacityInternal 发现是这个数组时才把 minCapacity 提升到 10。这是个懒加载优化 —— 很多 ArrayList 创建出来可能一个元素都不放，提前开 10 个槽位纯属浪费。顺带一提，源码里有两个空数组，EMPTY_ELEMENTDATA 对应「显式传了容量 0」，这种情况第一次 add 只扩到 1，不会扩到 10。

  2. 追问：ArrayList 删除元素后，底层数组会变小吗？

    • 答：不会。remove 只做两件事：System.arraycopy 把后面的元素整体前移一位，然后把最后一个槽位置 null 帮助 GC，elementData.length 完全不变。所以一个曾经放过 100 万元素的 ArrayList，即使清空了也还占着 100 万个引用的内存。需要释放得手动调 trimToSize()。这也是一类隐蔽的内存占用问题 —— 长生命周期的 ArrayList 被当缓冲区反复填充清空，内存只升不降。

  3. 追问：list.remove(1) 和 list.remove(Integer.valueOf(1)) 有什么区别？

    • 答：这是重载的坑。remove(int index) 按下标删，remove(Object o) 按对象删。写 list.remove(1) 会优先匹配 int 版本，删的是第 2 个元素，而不是值为 1 的元素。List<Integer> 场景下想按值删必须写 remove(Integer.valueOf(1)) 或 remove((Integer) 1)。我代码评审时专门盯这一行。

  4. 追问：既然 ArrayList 查询是 O(1)、插入是 O(n)，那中间插入 1 万次会很慢吧？

    • 答：理论上慢，实际上通常不慢。因为 System.arraycopy 是 JVM 的 intrinsic 内建方法，底层直接走 memmove，是按字节块批量搬运的，比「逐个节点跳指针」快得多。实测在几万量级，ArrayList 的中间插入经常还是比 LinkedList 快。只有在元素数量非常大（十万以上）且插入位置集中在头部时，链表才可能占优 —— 而那种场景更应该换数据结构，比如 ArrayDeque 或跳表。

  5. 追问：ArrayList 怎么做到线程安全？

    • 答：三个档位。① Collections.synchronizedList：方法级加锁，但复合操作（如「判断不存在再 add」）仍然不安全，且遍历时必须手动在外层加同一把锁；② CopyOnWriteArrayList：写时复制，读无锁、迭代器是快照不抛 CME，适合读多写极少（监听器列表、白名单），写是 O(n) 复制；③ 干脆不共享 —— 用局部变量，或并发收集后再合并。我们项目里真正用 COW 的只有事件监听器那一处。

✅ 项目关联话术（按真实经历替换）：

我之前排查过一个接口 P99 从 80ms 飙到 1.2s 的问题，最后定位到是一段用 LinkedList 存明细、然后用 for (int i = 0; i < list.size(); i++) list.get(i) 遍历的代码。数据量从几百涨到两万后，这个写法实际是 O(n²)，每次 get 都从头遍历。改成 ArrayList 之后 P99 直接回到 90ms。那之后我在团队的代码规范里加了两条：集合声明统一用 ArrayList 并预估初始容量、禁止对 List 接口用下标 for 循环遍历，统一用 for-each 或迭代器，并且在 CI 的静态扫描里加了规则。

题 2：HashMap 的底层结构？JDK7 和 JDK8 有什么区别？为什么负载因子是 0.75？ ​

精简口述答案：

JDK8 的 HashMap 是数组 + 链表 + 红黑树。数组叫 table，长度恒为 2 的 n 次方；冲突的节点挂成链表，当链表长度达到 8 且数组容量 ≥ 64 时转成红黑树，查询从 O(n) 变 O(log n)；扩容拆分后树节点 ≤ 6 时退化回链表。

和 JDK7 的区别主要三点：① JDK7 只有数组 + 链表，没有红黑树；② JDK7 插入用头插法，并发扩容时可能形成环形链表导致 get 死循环、CPU 100%，JDK8 改成尾插法；③ JDK7 扩容要对每个节点重新计算下标，JDK8 利用容量是 2 的 n 次方这个性质，用 e.hash & oldCap 把一条链直接拆成「低位链留在原下标」和「高位链放到原下标 + oldCap」，不需要重算 hash。

负载因子 0.75 是时间和空间的折中：太小（0.5）会导致数组很空就扩容，浪费内存且扩容频繁；太大（1.0）会让冲突链变长，查询退化。另外 0.75 等于 3/4，而容量是 2 的 n 次方，容量 × 3 / 4 一定是整数，不会有浮点误差，这也是选它而不是 0.7、0.8 的工程原因。

连环追问链：

  1. 追问：为什么树化阈值是 8，退化阈值是 6，不设成一样？

    • 答：8 这个数字来自源码注释里的泊松分布计算 —— 负载因子 0.75 时，一个桶里出现 8 个节点的概率约是 0.00000006，千万分之六。也就是说在 hash 分布正常的情况下永远不会触发树化，树化只是对「hash 被恶意攻击或 hashCode 实现很差」的兜底。TreeNode 的体积大约是普通 Node 的两倍，无脑树化是浪费。退化设成 6 而不是 8，是为了在 6 和 8 之间留一个 7 作缓冲区，避免节点数在临界点抖动时反复树化、退化，这是典型的滞后设计。

  2. 追问：你刚才说树化还要容量 ≥ 64，为什么？

    • 答：因为容量小的时候，冲突多的根本原因是桶太少，不是 hash 分布差。treeifyBin 里先判断 tab.length < MIN_TREEIFY_CAPACITY（64），如果成立就调 resize() 扩容而不是树化 —— 扩容把桶数翻倍，冲突链自然就短了，代价还比建红黑树低。只有数组已经够大（≥ 64）、链表还是那么长，才说明是 hash 分布本身有问题，这时候树化才值得。

  3. 追问：为什么容量必须是 2 的 n 次方？

    • 答：服务了三件事，不只是一件。① 寻址：n 是 2 的 n 次方时，n-1 的二进制低位全是 1，(n-1) & hash 完全等价于 hash % n，但位运算比取模快一个数量级；② 分布均匀：如果容量不是 2 的 n 次方，n-1 的二进制里有 0 位，那些位永远与不出 1，导致一部分桶永远取不到，另一部分冲突翻倍；③ 扩容优化：正因为是 2 倍关系，新旧下标只差 oldCap 这一个 bit，才能用 e.hash & oldCap 做高低位拆分。另外即使你 new HashMap<>(13)，tableSizeFor 也会用一串右移或运算把它向上取整到 16。

  4. 追问：hash 扰动函数在做什么？不做扰动会怎样？

    • 答：扰动就是 h ^ (h >>> 16)，把 hashCode 的高 16 位异或到低 16 位。原因是寻址只用到 hash 的低位 —— 容量 16 的时候只用低 4 位，高 28 位的差异被完全丢弃。假设两个对象 hashCode 分别是 0x0000_0005 和 0xFFFF_0005，不扰动的话它们会落到同一个桶。做一次异或后高位特征被混入低位，分布明显更均匀。这个优化成本只有一次移位加一次异或，收益很高。

  5. 追问：知道初始容量要怎么估算吗？new HashMap<>(1000) 放 1000 个元素会扩容吗？

    • 答：会扩容。tableSizeFor(1000) 得到 1024，阈值是 1024 × 0.75 = 768，放到第 769 个就触发扩容了。正确公式是 expectedSize / 0.75 + 1，1000 个元素要传 1334，tableSizeFor 后是 2048。工程上直接用 Guava 的 Maps.newHashMapWithExpectedSize(1000) 更省心。阿里规约要求集合初始化指定容量，就是因为默认 16 放 1000 个元素要扩容 7 次，每次都是 O(n) 的 rehash 加一次数组分配。

  6. 追问：HashMap 能存 null 吗？存在哪里？

    • 答：可以，而且只能存一个 null key，value 可以有多个 null。源码里 hash(null) 直接返回 0，所以 null key 恒定落在 table[0]。但要注意这带来了 get 返回 null 的二义性 —— 分不清「key 不存在」还是「value 本身是 null」，所以判断存在性要用 containsKey。Hashtable 和 ConcurrentHashMap 则是 key、value 都不允许 null，TreeMap 的 key 也不行（要比较大小）。

✅ 项目关联话术（按真实经历替换）：

我们有个批量导入的接口，一次处理 5 万条数据，里面用 HashMap 做 ID 到对象的索引，原来是 new HashMap<>() 默认 16。压测时发现这个接口的 GC 频率明显偏高，用 JFR 抓下来看，HashMap.resize 和 Arrays.copyOf 占了可观的分配量 —— 5 万条数据要扩容 12 次，中间产生了一堆废弃的 table 数组。改成 Maps.newHashMapWithExpectedSize(50000) 之后，Young GC 次数降了约三分之一，接口 P99 快了 15% 左右。这件事之后我们在代码规范里明确：只要数据量可预估，集合必须指定初始容量，且用 expectedSize / 0.75 + 1 计算。

题 3：HashMap 为什么线程不安全？具体会出什么问题？ ​

精简口述答案：

要分版本回答。JDK7 最严重的问题是扩容形成环形链表：transfer 用头插法迁移，两个线程同时扩容时，一个线程手里拿着旧的 next 快照，另一个线程已经把链表顺序反转了，交错执行后两个节点会互相指向，形成环。之后任何 get 落到这个桶就是 while 死循环，CPU 直接打满 100%，而且是那种重启才能恢复的故障。

JDK8 改成尾插法 + 高低位拆分，不会再成环了，但依然线程不安全，还有三个问题：① 数据覆盖丢失 —— 两个线程同时判断同一个空桶为 null，都执行写入，后者覆盖前者；② size 不准 —— ++size 不是原子操作；③ 扩容期间读到中间状态，可能拿到 null。

所以结论是：任何版本的 HashMap 都不能在多线程写入的场景使用，并发场景用 ConcurrentHashMap。

连环追问链：

  1. 追问：能把 JDK7 成环的过程讲细一点吗？

    • 答：假设旧桶是 A → B → null。线程 1 执行到 Entry next = e.next（此时 e = A，next = B）后被挂起。线程 2 完整跑完迁移，头插导致新桶变成 B → A → null。线程 1 恢复，它用的还是旧快照：先头插 A，然后 e = B，头插 B 时 B.next = A；接着 e = B.next，而在线程 2 的结果里 B.next 是 A，于是又处理 A，头插时 A.next = B —— A 和 B 互相指向，环就形成了。关键点是「头插法会反转顺序」和「线程 1 持有过期的 next 快照」这两个因素叠加。

  2. 追问：JDK8 的数据丢失具体是哪一行代码导致的？

    • 答：putVal 里这一段：
      java
      if ((p = tab[i = (n - 1) & hash]) == null)
    tab[i] = newNode(hash, key, value, null);
      判断为 null 和赋值之间没有任何同步。线程 A 和线程 B 同时判断 tab[5] == null 成立，A 写入 k1，B 紧接着写入 k2 覆盖掉，k1 就凭空消失了。ConcurrentHashMap 对应的位置用的是 casTabAt(tab, i, null, newNode) —— CAS 保证「判断 + 写入」是一步原子操作，失败就重试。

  3. 追问：既然不安全，Collections.synchronizedMap 够用吗？

    • 答：它能保证单个方法线程安全，但有三个明显短板：① 锁的是整个 map 对象，并发度等于 1，所有读写互相阻塞；② 复合操作仍不安全，「containsKey 再 put」这种还是要自己在外面加同一把锁；③ 遍历必须手动 synchronized (map) 包起来，否则照样抛 CME。它存在的意义主要是把已有的非线程安全 Map 临时包一下，正式的并发场景应该直接用 ConcurrentHashMap。

  4. 追问：那 Hashtable 呢？它和 ConcurrentHashMap 比差在哪？

    • 答：Hashtable 是把 synchronized 直接加在每个方法上，和 synchronizedMap 本质一样，全表一把锁，读也要抢锁。ConcurrentHashMap（JDK8）是空桶 CAS、非空桶 synchronized 锁头节点，并发度约等于桶的数量，而且读完全不加锁，靠 Node.val 和 next 的 volatile 以及 tabAt 的 volatile 读保证可见性。另外 Hashtable 的默认容量是 11、扩容是 2n+1、取模用的是除法，性能也更差。Hashtable 现在只在很老的代码里能见到，属于被淘汰的类。

  5. 追问：JDK8 的 HashMap 在并发下还会死循环吗？

    • 答：不会死循环，但会死在别的地方。有个真实案例：并发 put 时如果恰好触发树化，TreeNode 的 root 和 parent 指针在没有同步保护的情况下可能被改成互相引用，导致 treeify 或 balanceInsertion 里的循环出不来，表现同样是 CPU 100%。所以更稳妥的说法是：「JDK8 修掉了链表成环这一类死循环，但在并发下行为完全未定义，照样可能出现 CPU 打满」。面试时这么说比简单答「JDK8 不会死循环」要准确。

✅ 项目关联话术（按真实经历替换）：

我们有过一次线上事故就是这个。一个本地缓存用的是 static HashMap，初版是单线程定时任务刷新，后来有人加了个接口可以手动触发刷新，就变成了多线程写。某天运营连点了几次刷新按钮，那台机器的 CPU 直接 100%，接口全部超时。用 jstack 抓线程栈，看到好几个线程卡在 HashMap.getNode 里，基本就确定是哈希表的环。当时紧急重启恢复，后面做了两件事：把 HashMap 换成 ConcurrentHashMap，并且把「刷新」改成单线程执行器串行化加去重。复盘时我们还在静态扫描里加了规则：static 修饰的集合字段禁止使用非线程安全实现。

题 4：ConcurrentHashMap 在 JDK8 是怎么实现的？和 JDK7 比有什么改进？ ​

精简口述答案：

JDK7 用的是分段锁：把整个表切成默认 16 个 Segment，每个 Segment 自己是一个 ReentrantLock 加一张小哈希表，不同段的写互不影响，所以并发度是段的个数，默认 16。缺点是两层结构内存占用大、定位要算两次 hash、并发度写死在初始化时。

JDK8 彻底重构，抛弃了 Segment，结构变回和 HashMap 一样的「数组 + 链表 + 红黑树」，用三个手段保证并发安全：① 桶为空时用 casTabAt 做 CAS 写入，完全无锁；② 桶不为空时 synchronized 锁住该桶的头节点，只阻塞落到同一个桶的线程；③ 读操作完全不加锁，靠 Node 的 val、next 是 volatile 以及 tabAt 的 volatile 读保证可见性。

另外扩容也优化了：迁移时把旧表按步长切成多个区间，多个线程可以并行迁移；某个桶迁移完就在旧表该位置放一个 ForwardingNode，其他线程读到它就去新表查，写到它就调 helpTransfer 加入协助。所以 JDK8 的并发度从「16 段」提升到了「桶的数量」，一句话总结就是 锁的是桶，不是表。

连环追问链：

  1. 追问：为什么 JDK8 敢用 synchronized 而不是 ReentrantLock？

    • 答：因为 JDK6 之后 synchronized 有了锁升级：偏向锁 → 轻量级锁（CAS 自旋）→ 重量级锁。ConcurrentHashMap 里锁桶头节点的竞争通常非常短、非常低，绝大多数情况停在轻量级锁阶段，性能和 CAS 接近，而且 synchronized 由 JVM 原生支持，不需要像 ReentrantLock 那样维护 AQS 队列对象，内存开销更小。再加上 synchronized 的代码更简洁、不会忘记 unlock，Doug Lea 在注释里也说明了这个选择。

  2. 追问：sizeCtl 这个字段是干什么的？

    • 答：它是一个 volatile int，用不同的取值复用了多种状态：0 表示还没初始化；-1 表示某个线程正在初始化（通过 CAS 抢到这个值，其他线程 Thread.yield() 自旋等待）；小于 -1 时，低 16 位记录的是正在参与扩容的线程数（-(1 + 扩容线程数)）；大于 0 时表示下一次扩容的阈值。用一个变量承载这么多语义，是为了让状态切换可以用一次 CAS 完成，这是 Doug Lea 典型的写法。

  3. 追问：size() 为什么是估算的？

    • 答：因为它没有用一个 volatile int size —— 那会变成所有写线程争抢的热点，CAS 失败率极高。它借鉴 LongAdder 的分段累加：无竞争时 CAS 累加到 baseCount，一旦 CAS 失败说明有竞争，就改为累加到 CounterCell[] 数组里线程各自哈希到的槽位。size() 是 baseCount 加上所有 CounterCell 的求和，遍历求和的过程中其他线程还在改，所以结果只是某个时间点的近似值。工程上千万不要用 chm.size() 做精确的业务判断，另外 JDK8 还提供了返回 long 的 mappingCount()，比 size() 更推荐。

  4. 追问：ConcurrentHashMap 用了它就一定线程安全了吗？

    • 答：不是。它只保证单个方法的原子性，不保证多个方法组合的原子性。像「containsKey 不存在则 put」、「get 出来加一再 put 回去」这种 check-then-act、read-modify-write 都会丢更新。正确做法是用它自带的原子复合方法：putIfAbsent、computeIfAbsent、compute、merge、replace(k, old, new)。高并发计数我更倾向于 ConcurrentHashMap<String, LongAdder> 配 computeIfAbsent(k, x -> new LongAdder()).increment()，这样连桶锁都不用反复抢。

  5. 追问：computeIfAbsent 有什么坑？

    • 答：两个。① mapping 函数里不能再操作同一个 map —— 当前线程已经 synchronized 住了这个桶，如果函数体里 put 的 key 恰好 hash 到同一个桶，JDK8 下会直接死锁或死循环（JDK9 之后会抛 IllegalStateException 提示递归更新）；② mapping 函数不要做耗时操作，比如远程调用或查库 —— 整个桶在这期间都被锁住，落到同桶的其他 key 全部阻塞。缓存场景更安全的写法是「先 get，miss 了在锁外加载，最后 putIfAbsent」，或者直接用 Caffeine 这类专业缓存。

  6. 追问：它的迭代器是什么行为？遍历时别人在改会怎样？

    • 答：是**弱一致（weakly consistent）**迭代器 —— 不会抛 ConcurrentModificationException，也不会像 CopyOnWriteArrayList 那样是完整快照。它能保证遍历到创建迭代器时已存在的元素，对于之后的修改则「可能看到也可能看不到」。所以它适合做监控统计、批量导出这种对实时性要求不高的遍历；如果需要「遍历期间数据不变」的强一致语义，ConcurrentHashMap 给不了，得在业务层加锁或者先拷贝一份。

✅ 项目关联话术（按真实经历替换）：

我们做过一个接口限流的本地计数器，最早的实现是 ConcurrentHashMap<String, Integer> 加 map.put(key, map.get(key) + 1)。灰度的时候就发现统计值明显偏小 —— 典型的 read-modify-write 丢更新。第一版修复用了 merge(key, 1, Integer::sum)，正确了但压测时发现热点 key 上有锁竞争。最终版改成 ConcurrentHashMap<String, LongAdder>，用 computeIfAbsent 初始化、increment() 累加，热点 key 的竞争被 LongAdder 内部的 Cell 分散掉，QPS 提升了一倍多。这件事让我记住了一个原则：ConcurrentHashMap 保证的是单方法原子性，组合操作必须用它提供的原子 API，而高并发计数要进一步把热点拆散。

题 5：为什么重写 equals 必须重写 hashCode？ ​

精简口述答案：

因为 HashMap、HashSet 判断「是不是同一个 key」是两步：先用 hash 定位桶，再在桶内用 == 或 equals 比较。

如果只重写 equals 不重写 hashCode，两个业务上「相等」的对象会因为继承了 Object 的 hashCode（基于对象地址）而算出不同的 hash，落到不同的桶里，第一步就分道扬镳了，equals 根本没机会被调用。结果就是：HashSet 里出现两个相等的元素、用一个「相等」的新对象去 map.get 拿不到值。

反过来只重写 hashCode 不重写 equals，两个对象会落到同一个桶，但 equals 返回 false，照样被当成两个不同的 key —— 只是退化成了哈希冲突。

所以 JDK 的契约是：a.equals(b) 为 true，则 a.hashCode() 必须等于 b.hashCode()；反之不要求。实际写代码我一律用 IDE 生成或者 Objects.equals / Objects.hash，不手写。

连环追问链：

  1. 追问：为什么 hashCode 相等不要求 equals 相等？

    • 答：因为 hashCode 返回的是 int，只有约 43 亿个取值，而对象的可能状态是无限的 —— 鸽笼原理决定了冲突不可避免。所以哈希表的设计前提就是「hash 相等只是候选，还要 equals 确认」。顺带说一个经典例子："Aa".hashCode() 和 "BB".hashCode() 都是 2112，可以无限拼接构造出大量 hash 相同的字符串 —— 这就是**哈希碰撞攻击（Hash DoS）**的原理，往请求参数里塞大量这种 key，能把 HashMap 退化成链表打满 CPU。Java 8 用红黑树树化缓解了这个问题。

  2. 追问：用可变对象当 HashMap 的 key 会有什么问题？

    • 答：放进去之后就再也取不出来。因为节点是按放入时的 hash 挂在某个桶上的，之后你改了参与 hashCode 的字段，再用这个对象去 get，算出的新 hash 指向另一个桶，那里什么都没有，返回 null。而旧桶里的节点谁也访问不到，但它和 value 的引用还在，GC 回收不了，就是内存泄漏。所以作为 key 的类应该设计成不可变：字段加 final、不提供 setter。这也是 String 为什么是完美的 key —— 不可变而且缓存了 hash 值。

  3. 追问：Objects.hash(a, b, c) 内部是怎么算的？为什么用 31？

    • 答：内部就是 result = 31 * result + element.hashCode() 的循环（Arrays.hashCode 的实现）。选 31 有两个原因：① 31 是奇素数，奇数能避免乘法丢失信息（偶数相当于左移，会把高位丢掉），素数则让散列分布更均匀；② 31 * i 可以被 JVM 优化成 (i << 5) - i，一次移位加一次减法，比乘法快。顺便一提，Objects.hash 内部要创建可变参数数组，在超高频路径上有装箱和数组分配开销，极致性能场景会手写展开。

  4. 追问：Lombok 的 @Data 生成的 equals 有什么坑？

    • 答：主要是继承场景。@Data 默认生成的 equals 不比较父类字段，而且默认 callSuper = false，父类字段不参与比较会导致「两个父类字段不同的子类对象被判为相等」；如果加了 @EqualsAndHashCode(callSuper = true) 但父类没有正确实现 equals，又会退化成 Object 的地址比较。另外 @Data 会把所有字段纳入比较，包括那些你其实不希望参与身份判断的字段（比如 updateTime、懒加载的关联集合 —— 后者还可能触发 N+1 查询）。我们团队的做法是：实体类只用 @Getter/@Setter，equals/hashCode 显式写、只基于业务主键。

  5. 追问：JPA / Hibernate 实体的 equals 该怎么写？

    • 答：这是个经典难题。不能只用自增主键 —— 实体在持久化之前 id 是 null，放进 HashSet 后再 persist，id 变了 hash 也变了，就取不出来了。常见的三种做法：① 用业务唯一键（如订单号、UUID）而不是数据库自增 id；② 在构造时就生成一个 UUID 作为标识；③ hashCode 返回一个常量（比如类名的 hash），equals 比 id —— 牺牲哈希分布换正确性，适用于集合规模很小的关联场景。我倾向第一种，顺带还解决了幂等的问题。

题 6：遍历集合时删除元素为什么会抛异常？有几种正确写法？ ​

精简口述答案：

因为 ArrayList 这类集合有一个 modCount 字段，记录结构性修改（add / remove / clear）的次数。创建迭代器时会把当前 modCount 存成 expectedModCount，之后每次 next() 都会调 checkForComodification() 比较两者 —— 一旦不等就抛 ConcurrentModificationException。

for-each 本质就是迭代器的语法糖，你在循环体里调 list.remove(e) 只会让 modCount 自增，expectedModCount 没同步，下一次 next() 就炸了。而 iterator.remove() 在删除之后会执行 expectedModCount = modCount 把快照同步回来，所以它是安全的。

正确写法主要四种：iterator.remove()、removeIf()（JDK8+，最推荐）、倒序下标遍历、遍历时收集待删元素最后 removeAll。另外还有一个阴险的点：用 for-each 删除「倒数第二个」元素时恰好不会抛异常，因为删完 size 减一，hasNext() 里 cursor != size 直接为 false 就结束了 —— 这种代码在测试数据下是「正常」的，换批数据就暴雷。

连环追问链：

  1. 追问：为什么说 CME 不是「并发」异常？

    • 答：名字有误导性。它的触发条件只是 modCount != expectedModCount，单线程里自己边遍历边删同样会抛。它的设计目的是「快速失败」—— 让错误在第一次出现时就暴露，而不是留下一个行为未定义的集合继续跑下去。反过来说，它也不能作为并发检测的保证：多线程修改时它只是「尽力而为」地抛，modCount 本身不是 volatile，完全可能漏检。

  2. 追问：removeIf 的实现和 Iterator.remove 有什么不同？

    • 答：Iterator.remove 是一次删一个，每次删除都要 System.arraycopy 把后面的元素前移，删 n 个元素是 O(n·m) 的拷贝量。ArrayList.removeIf 聪明得多：先用一个 BitSet 标记所有要删的位置（这一轮只读不改），然后一次性批量压缩数组，整体是 O(n)。所以删除比例高的时候 removeIf 明显更快，而且代码更短、不会写错。它内部也会做 modCount 校验，遍历过程中如果 predicate 里改了集合同样会抛 CME。

  3. 追问：Map 怎么安全地边遍历边删？

    • 答：Map 本身没有迭代器，要通过它的三个视图来操作：entrySet().iterator() 然后 it.remove()，或者更简洁的 map.entrySet().removeIf(e -> 条件)、map.values().removeIf(...)、map.keySet().removeIf(...)。关键是要理解 keySet、values、entrySet 都是视图而不是副本，在视图上删除会直接作用到源 Map。反过来要小心：拿到 keySet 后不要随便当独立集合传出去。

  4. 追问：CopyOnWriteArrayList 和 ConcurrentHashMap 为什么不抛 CME？

    • 答：机制不同。CopyOnWriteArrayList 的迭代器基于创建那一刻的数组快照，之后的写操作换的是新数组，老数组不会变，所以遍历永远安全 —— 代价是看不到新数据，而且它的迭代器不支持 remove（会抛 UnsupportedOperationException）。ConcurrentHashMap 是弱一致迭代器，它直接遍历当前的桶数组，能看到部分新修改，但不保证完整性，也不做 modCount 校验。所以这两个类遍历时删除不会异常，但语义是「最终一致」而不是「强一致」。

  5. 追问：实际项目里你怎么写？

    • 答：优先级是 removeIf > Iterator > 新建集合收集保留项。能用一行 list.removeIf(条件) 表达的绝不写循环；需要同时访问上下文、或者删除时还要做别的事（记日志、发事件）才用 Iterator；如果是函数式风格的数据流处理，我更倾向于不删除原集合，直接 stream().filter(...).collect(...) 生成新集合 —— 不改原数据在并发和可读性上都更安全。另外绝对禁止在 for-each 里调 list.remove，这条写进了团队规范。

我们有个过滤下架商品的逻辑，最初写的是 for-each 里 list.remove(item)。测试用的是三条数据，刚好删的是第二条 —— 倒数第二个，hasNext() 提前返回 false，一次异常都没抛，就这么上线了。结果真实数据下 CME 直接把接口打成 500。修复时我没有简单换成 Iterator，而是改成了 list.removeIf(SkuVO::isOffline)，一行解决。复盘之后我们把「禁止在 for-each 中对被遍历集合做结构性修改」写进了规范，并加了静态扫描规则。这个坑给我的最大教训是：「测试没报错」不等于「写法正确」，边界恰好掩盖 bug 的情况比直接报错危险得多。

题 7：线上突然报 Comparison method violates its general contract!，怎么定位和修？ ​

精简口述答案：

这个异常不是 JDK 的 bug，是自己写的 Comparator 违反了比较契约。List.sort / Arrays.sort(Object[]) 用的是 TimSort，它会先把数组切成一段段单调的 run 再归并，归并时依赖「run 内严格单调」这个前提；一旦比较器自相矛盾，mergeLo / mergeHi 里的指针会越界，JDK 检测到就直接抛这个 IllegalArgumentException。

它典型的表现是**「测试环境一直好的，上线一段时间后突然报」**，原因是 TimSort 对长度小于 32（MIN_MERGE）的数组走的是二分插入排序，根本不做 run 合并，也就不校验契约 —— 违约一直存在，只是数据量小的时候表现为「排序结果不对」，数据量涨上去才表现为抛异常。

定位就看栈顶是哪个 sort 调用，然后去审对应的比较器，九成是这三种写法之一：漏掉相等返回 0（a.x > b.x ? 1 : -1）、用 a - b 相减导致 int 溢出、比较依据不稳定（排序过程中字段被别的线程改了，或者比较里用了 Math.random() / 当前时间）。修法是一律改用 Comparator.comparingInt / comparing + thenComparing 这套工厂方法，不手写三元分支。

连环追问链：

  1. 追问：为什么漏掉「相等返回 0」就一定违约？

    • 答：违反的是反对称性：契约要求 sgn(compare(a,b)) == -sgn(compare(b,a))。写成 a.x > b.x ? 1 : -1 时，如果 a.x == b.x，那么 compare(a,b) 返回 -1，compare(b,a) 也返回 -1 —— 两个元素互相认为「对方比我大」，这在数学上就不是一个序关系了。TimSort 归并时会据此一直往前推指针，最后越界。顺带一提，这种写法即使不抛异常，排序结果也是不确定的，而且会破坏稳定性。

  2. 追问：a - b 为什么不安全？不是都这么写吗？

    • 答：只有在能确定两个值都是非负且差值不溢出 int 的情况下才安全，这个前提在业务代码里基本不成立。比如余额、时间戳差、带符号的分数，2_000_000_000 - (-2_000_000_000) 的结果是 -294_967_296，符号直接翻转，「大的变成了小的」。long 字段更危险，强转 int 还会截断。正确写法是 Integer.compare(a, b) / Long.compare(a, b)，或者直接用 Comparator.comparingInt，它内部就是调 Integer.compare。

  3. 追问：-Djava.util.Arrays.useLegacyMergeSort=true 能解决问题吗？

    • 答：只能让异常消失，不能解决问题。它退回 JDK6 的归并排序实现，那个实现不校验契约，所以不报错 —— 但排序结果依然是错的，而且归并排序要额外开一倍的临时数组，内存开销更大。我只会把它当成「线上凌晨紧急止血」的手段，且必须当天把比较器修掉、把参数摘掉，不然就是埋了个「排序结果随机错」的雷。

  4. 追问：多字段排序怎么写才稳？reversed() 放在哪？

    • 答：用链式 comparing(...).thenComparing(...)，并且末尾一定补一个唯一字段（主键、ID），保证是全序 —— 否则相等元素的相对顺序虽然由 TimSort 的稳定性保证，但一旦上游数据顺序变了，结果就会跟着变，排查起来很痛苦。reversed() 的陷阱在于它作用于前面整条链：comparing(A).thenComparing(B).reversed() 是「A 和 B 都倒序」，如果只想倒 A，要写 comparing(A, Comparator.reverseOrder()).thenComparing(B)。另外 null 字段必须显式处理，用 Comparator.nullsFirst/nullsLast 包一层，不能靠 compareTo 碰运气。

  5. 追问：TreeMap 传了比较器之后，判重还看 equals 吗？

    • 答：完全不看。TreeMap / TreeSet 的所有判等逻辑（put 覆盖、contains、去重）都只看 compare(a, b) == 0。所以 new TreeSet<>(Comparator.comparingInt(User::getAge)) 会把所有同龄用户当成同一个人，第二个加不进去。这就是 SortedSet 文档里那句「应当与 equals 一致」的实际含义 —— 不一致不会报错，但会静默丢数据，这类 Bug 极难发现。要排序又要按业务主键判重，就必须把主键加到比较链末尾。

我们有个运营后台的列表接口，支持按多字段排序，上线半年一直正常。后来某个类目的商品数涨到几千条之后，这个接口开始间歇性报 500，日志里就是 Comparison method violates its general contract!。一开始以为是 JDK 版本问题，后来看栈顶定位到排序那行，发现比较器写的是 (a, b) -> a.getWeight() > b.getWeight() ? 1 : -1 —— 权重相等时两边都返回 -1，违反反对称性。数据量小的时候走二分插入排序不校验，所以一直没暴露。我把它改成 Comparator.comparingInt(Item::getWeight).reversed().thenComparing(Item::getId)，顺手在团队规范里加了两条硬性要求：禁止在比较器里用减法、禁止手写三元比较，并在静态扫描里加了对应规则，之后又扫出来四处同样的写法。

题 8：WeakHashMap 什么时候用？ThreadLocal的内存泄漏到底泄漏在哪？ ​

精简口述答案：

WeakHashMap 的 key 是弱引用，当某个 key 除了这个 map 之外再没有强引用时，GC 就会回收它，对应的 entry 也会被自动清掉（下次访问 map 时从 ReferenceQueue 里批量清理）。它适合的场景是**「缓存的生命周期应该跟随 key 对象，而不是由缓存自己决定」**，典型是以 ClassLoader、Class、Thread、框架组件实例为 key 的元数据缓存。

最关键的一点是：弱的是 key，不是 value。Entry.value 是强引用。所以如果 value 直接或间接引用了 key，就形成了一条「table → Entry → value → key」的强引用链，key 永远不会被回收，这个 entry 就成了永不失效的泄漏。另外用字符串字面量当 key 也没用 —— 常量池会永久强引用它。

ThreadLocal 的泄漏是同一个机制的经典案例：ThreadLocalMap.Entry 继承 WeakReference<ThreadLocal<?>>，key 是弱引用、value 是强引用。ThreadLocal 实例被回收后 key 变成 null，但 value 还被 Entry 强引用着。在线程池里核心线程不会销毁，Thread → ThreadLocalMap → Entry → value 这条链一直活着，value 就永远回收不掉。get / set 会顺手清理一部分 stale entry，但不保证清完。唯一可靠的解法就是 try { ... } finally { tl.remove(); }。

连环追问链：

  1. 追问：既然 value 是强引用才泄漏，为什么 JDK 还要把 key 设成弱引用？

    • 答：这是减轻泄漏而不是解决泄漏。如果 key 也是强引用，那么只要线程活着，ThreadLocal 实例本身就永远回收不掉 —— 连「这个 ThreadLocal 已经没人用了」这个信息都拿不到。设成弱引用之后，至少 JDK 能通过「key == null」识别出哪些槽位是废弃的，从而在 get / set / remove 时调 expungeStaleEntry 做启发式清理。value 之所以不能设成弱引用，是因为很多场景下 value 就只有这一处引用（比如 ThreadLocal<SimpleDateFormat>），设成弱引用的话随时会被回收，功能就废了。

  2. 追问：ThreadLocalMap 为什么用线性探测而不是链表解决冲突？

    • 答：因为它的使用场景决定了元素数量极少（一个线程通常只有几个 ThreadLocal），线性探测的平坦数组比「数组 + 链表」更省内存、缓存局部性更好，而且不需要为每个节点额外分配 Node 对象。代价是删除时不能简单置 null（会断开探测链），必须做 rehash 式的整理，这就是 expungeStaleEntry 里那段「向后扫描并重新定位」的逻辑。另外它的 hash 用的是 threadLocalHashCode，按黄金分割数 0x61c88647 递增，能让连续创建的 ThreadLocal 在数组里均匀散开。

  3. 追问：InheritableThreadLocal 在线程池里能用吗？

    • 答：不能。它的继承发生在 Thread 创建的那一刻（init 里从父线程拷贝 inheritableThreadLocals）。线程池的线程是复用的，创建时继承的是「第一次提交任务那个线程」的上下文，后面所有任务拿到的都是这个过期快照，表现为「traceId 串了」「用户身份串了」，而且是概率性的，极难排查。要在线程池里透传上下文，得用阿里开源的 TransmittableThreadLocal，它在任务提交时抓快照、执行前后做 replay 和还原。

  4. 追问：WeakHashMap 是线程安全的吗？能当并发缓存用吗？

    • 答：不是线程安全的，而且它比普通 HashMap 更危险 —— 因为它的「清理 stale entry」动作发生在 size()、get()、put() 这些看起来是读操作的方法里，也就是说连 get 都会修改内部结构。并发访问时不仅可能丢数据，还可能像 JDK7 的 HashMap 那样出现结构错乱。要并发用必须 Collections.synchronizedMap 包一层。但说实话，需要「带自动回收的并发缓存」时，直接用 Caffeine（支持 weakKeys / softValues / 容量与时间淘汰）比自己拼 WeakHashMap 靠谱得多。

  5. 追问：软引用和弱引用做缓存，该选哪个？

    • 答：都不该选。软引用（SoftReference）的回收时机由 JVM 根据内存压力决定，不可控 —— 实测表现往往是「内存快满了才回收」，这意味着它在回收前会加剧 GC 压力、拉长 Full GC 时间，而且回收策略在不同 JDK / 不同 GC 下差异很大，缓存命中率完全不可预期。弱引用则是「下次 GC 就没了」，作为缓存几乎没有命中率。生产上做本地缓存，正确答案是显式容量上限 + 显式过期时间 + 明确的淘汰算法，也就是 Caffeine 这类方案。软弱引用的真实用途是「旁路元数据」而不是「缓存热数据」。

✅ 项目关联话术（按真实经历替换）：

我排查过一次线上老年代缓慢上涨、大约三天一次 Full GC 的问题。用 MAT 看堆 dump，支配树里最大的一块是线程池里几十个核心线程的 ThreadLocalMap，每个 Entry 的 key 都是 null、value 是一个几 MB 的上下文对象，里面还挂着整个请求的参数和中间结果。根因是一个工具类用 ThreadLocal 存请求上下文，但只在拦截器的 preHandle 里 set，没有在 afterCompletion 里 remove —— 线程池的线程不死，这些 value 就一直在。加上 finally { CONTEXT.remove(); } 之后老年代曲线立刻变平。这件事之后我们做了两件事：在统一的拦截器基类里强制做 remove，业务方不允许自己裸用 ThreadLocal；以及在 code review checklist 里加了「ThreadLocal.set 必须有配对的 remove」这一条。

HashMap + 双向链表的组合拳
  HashMap：key → 节点引用，保证 get 定位是 O(1)
  双向链表：维护访问顺序，head 侧是最近访问，tail 侧是最久未访问
  为什么要「双向」？删除一个节点需要知道它的前驱 —— 单链表拿不到，必须 O(n) 找

  get(k)   : map 找到 node → 把 node 移到 head → 返回 value          O(1)

  哨兵节点（dummy head / dummy tail）的作用：
    让「插入」「删除」不需要判断 null，代码从 20 行缩到 8 行
    head ⇄ [最近] ⇄ ... ⇄ [最久] ⇄ tail

public class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    public LruCache(int capacity) {
        // 第三个参数 accessOrder = true → get/put 命中后把节点移到链表尾部
        super((int) (capacity / 0.75f) + 1, 0.75f, true);
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;   // 返回 true 时自动删除链表头（最久未访问的）
    }
}

/* ========== 方案二：手写双向链表 + HashMap，考察真实功底 ========== */
public class LruCacheManual<K, V> {

    private static class Node<K, V> {
        K key; V value;
        Node<K, V> prev, next;
        Node(K key, V value) { this.key = key; this.value = value; }
    }

    private final int capacity;
    private final Map<K, Node<K, V>> map;
    private final Node<K, V> head;   // 哨兵：head.next 是最近使用
    private final Node<K, V> tail;   // 哨兵：tail.prev 是最久未使用

    public LruCacheManual(int capacity) {
        if (capacity <= 0) throw new IllegalArgumentException("capacity must be > 0");
        this.capacity = capacity;
        this.map = new HashMap<>((int) (capacity / 0.75f) + 1);
        this.head = new Node<>(null, null);
        this.tail = new Node<>(null, null);
        head.next = tail;
        tail.prev = head;
    }

    public V get(K key) {
        Node<K, V> node = map.get(key);
        if (node == null) return null;
        moveToHead(node);
        return node.value;
    }

    public void put(K key, V value) {
        Node<K, V> node = map.get(key);
        if (node != null) {                 // 命中：更新值 + 提到最前
            node.value = value;
            moveToHead(node);
            return;
        }
        node = new Node<>(key, value);
        map.put(key, node);
        addToHead(node);
        if (map.size() > capacity) {        // ⚠️ 先插入再判断，顺序不能反
            Node<K, V> eldest = tail.prev;
            remove(eldest);
            map.remove(eldest.key);         // ⚠️ 必须同时清 map，否则内存泄漏
        }
    }

    public V remove(K key) {
        Node<K, V> node = map.remove(key);
        if (node == null) return null;
        remove(node);
        return node.value;
    }

    public int size() { return map.size(); }

    /* ---- 三个链表基本操作，全部 O(1) ---- */
    private void addToHead(Node<K, V> node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }

    private void remove(Node<K, V> node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
        node.prev = node.next = null;      // 断开引用，帮助 GC
    }

    private void moveToHead(Node<K, V> node) {
        remove(node);
        addToHead(node);
    }
}

public class ConcurrentLruCache<K, V> {
    private final LruCacheManual<K, V> delegate;
    private final ReentrantReadWriteLock lock = new ReentrantReadWriteLock();

    public ConcurrentLruCache(int capacity) { this.delegate = new LruCacheManual<>(capacity); }

    public V get(K key) {
        // ⚠️ 注意：LRU 的 get 会移动节点，是「写」操作，不能用读锁！
        lock.writeLock().lock();
        try { return delegate.get(key); } finally { lock.writeLock().unlock(); }
    }
    public void put(K key, V value) {
        lock.writeLock().lock();
        try { delegate.put(key, value); } finally { lock.writeLock().unlock(); }
    }
}

  1. 必须是双向链表：删除节点要改前驱的 next，单链表拿不到前驱就得 O(n) 遍历，整体就不是 O(1) 了。

  3. LRU 的 get 是写操作（要移动节点），所以线程安全版不能用读锁；LinkedHashMap 的 accessOrder=true 本质就是在 afterNodeAccess 里做了 moveToHead。

场景期望行为
capacity = 0 或负数构造时抛 IllegalArgumentException
capacity = 1，put 两个不同 key只保留后一个
get 不存在的 key返回 null，不改变任何顺序
put 已存在的 key更新 value 且提到最前，size 不变、不触发淘汰
淘汰后再 get 被淘汰的 key返回 null
先 put A B C（cap=3），get(A) 后 put D淘汰 B（A 刚被访问过，不是最久未用）

全部 remove 后head.next == tail，map 为空
value 允许为 null 吗手写版允许，但 get 返回 null 产生二义性 → 建议禁止

🔁 变种拓展题：

  1. LFU 缓存（LeetCode 460）：按「访问频次」淘汰，频次相同时淘汰最久未用。实现是 HashMap<K, Node> + HashMap<freq, DoubleLinkedList> + minFreq 指针，全部 O(1)。
  2. 带过期时间的 LRU：节点加 expireAt 字段，get 时懒删除；再配一个 ScheduledExecutorService 定期清扫，或用小顶堆按过期时间排序做主动淘汰。
  3. LRU-K：记录最近 K 次访问，只有被访问 K 次以上的数据才进主缓存，能有效防止偶发的批量扫描把热点数据冲掉（缓存污染）。
  4. 分段 LRU 提升并发度：按 key.hashCode() 把缓存分成 N 个 LruCache 分片，每片一把锁 —— 这正是 ConcurrentHashMap JDK7 分段锁的思路。
  5. 用 LinkedHashMap 实现 FIFO 缓存：accessOrder 保持默认 false，只按插入顺序淘汰，代码完全一样。
  6. 为什么 Redis 的 LRU 是「近似 LRU」？ 因为维护完整链表的内存和 CPU 成本太高，Redis 改为随机采样若干 key（maxmemory-samples，默认 5）淘汰其中最久未用的，用精度换性能 —— 这是工程上典型的权衡。

java
import java.util.*;

public class MyArrayList<E> implements Iterable<E> {

    private static final int DEFAULT_CAPACITY = 10;
    private static final Object[] EMPTY = {};

    private Object[] elementData;
    private int size;
    private int modCount;            // ⭐ 结构性修改计数，fail-fast 的核心

    public MyArrayList() { this.elementData = EMPTY; }

    public MyArrayList(int initialCapacity) {
        if (initialCapacity < 0) throw new IllegalArgumentException("capacity < 0");
        this.elementData = initialCapacity == 0 ? EMPTY : new Object[initialCapacity];
    }

    /* ---------- 增 ---------- */
    public boolean add(E e) {
        ensureCapacity(size + 1);
        elementData[size++] = e;
        return true;
    }

    public void add(int index, E e) {
        checkPositionIndex(index);                 // 插入允许 index == size
        ensureCapacity(size + 1);
        System.arraycopy(elementData, index, elementData, index + 1, size - index);
        elementData[index] = e;
        size++;
    }

    /* ---------- 删 ---------- */
    @SuppressWarnings("unchecked")
    public E remove(int index) {
        checkElementIndex(index);
        modCount++;                                // ⭐ 结构变了
        E old = (E) elementData[index];
        int moved = size - index - 1;
        if (moved > 0) System.arraycopy(elementData, index + 1, elementData, index, moved);
        elementData[--size] = null;                // ⭐ 置 null 帮助 GC，但数组长度不变（不缩容）
        return old;
    }

    public boolean remove(Object o) {              // ⚠️ 与 remove(int) 构成重载陷阱
        int i = indexOf(o);
        if (i < 0) return false;
        remove(i);
        return true;
    }

    public void clear() {
        modCount++;
        for (int i = 0; i < size; i++) elementData[i] = null;
        size = 0;
    }

    /* ---------- 查改 ---------- */
    @SuppressWarnings("unchecked")
    public E get(int index) { checkElementIndex(index); return (E) elementData[index]; }

    @SuppressWarnings("unchecked")
    public E set(int index, E e) {
        checkElementIndex(index);
        E old = (E) elementData[index];
        elementData[index] = e;                    // ⭐ set 不是结构性修改，modCount 不变
        return old;
    }

    public int indexOf(Object o) {
        for (int i = 0; i < size; i++) {
            if (o == null ? elementData[i] == null : o.equals(elementData[i])) return i;
        }
        return -1;
    }

    public boolean contains(Object o) { return indexOf(o) >= 0; }
    public int size() { return size; }
    public boolean isEmpty() { return size == 0; }

    /* ---------- 扩容：核心考点 ---------- */
    private void ensureCapacity(int minCapacity) {
        if (elementData == EMPTY) {
            elementData = new Object[Math.max(DEFAULT_CAPACITY, minCapacity)];  // 懒加载
            modCount++;
            return;
        }
        if (minCapacity - elementData.length > 0) grow(minCapacity);
    }

    private void grow(int minCapacity) {
        modCount++;
        int oldCapacity = elementData.length;
        int newCapacity = oldCapacity + (oldCapacity >> 1);          // ⭐ 1.5 倍
        if (newCapacity - minCapacity < 0) newCapacity = minCapacity;        // 一次加太多
        if (newCapacity - Integer.MAX_VALUE + 8 > 0) newCapacity = Integer.MAX_VALUE - 8;
        elementData = Arrays.copyOf(elementData, newCapacity);       // ⭐ O(n) 拷贝
    }

    public void trimToSize() {
        modCount++;
        if (size < elementData.length) {
            elementData = size == 0 ? EMPTY : Arrays.copyOf(elementData, size);
        }
    }

    /* ---------- 越界校验：区分「访问」和「插入」 ---------- */
    private void checkElementIndex(int index) {
        if (index < 0 || index >= size)
            throw new IndexOutOfBoundsException("Index: " + index + ", Size: " + size);
    }
    private void checkPositionIndex(int index) {
        if (index < 0 || index > size)
            throw new IndexOutOfBoundsException("Index: " + index + ", Size: " + size);
    }

    /* ---------- fail-fast 迭代器 ---------- */
    @Override
    public Iterator<E> iterator() { return new Itr(); }

    private class Itr implements Iterator<E> {
        int cursor;                       // 下一个要返回的下标
        int lastRet = -1;                 // 上一个返回的下标，-1 表示不可删除
        int expectedModCount = modCount;  // ⭐ 创建时拍快照

        @Override public boolean hasNext() { return cursor != size; }

        @Override
        @SuppressWarnings("unchecked")
        public E next() {
            checkForComodification();
            if (cursor >= size) throw new NoSuchElementException();
            lastRet = cursor;
            return (E) elementData[cursor++];
        }

        @Override
        public void remove() {
            if (lastRet < 0) throw new IllegalStateException();   // next() 之前不能删
            checkForComodification();
            MyArrayList.this.remove(lastRet);
            cursor = lastRet;
            lastRet = -1;
            expectedModCount = modCount;    // ⭐ 关键：把快照同步回来，所以 it.remove 安全
        }

        private void checkForComodification() {
            if (modCount != expectedModCount) throw new ConcurrentModificationException();
        }
    }

    @Override
    public String toString() {
        StringBuilder sb = new StringBuilder("[");
        for (int i = 0; i < size; i++) {
            sb.append(elementData[i]);
            if (i < size - 1) sb.append(", ");
        }
        return sb.append(']').toString();
    }

    /* ---------- 自测 ---------- */
    public static void main(String[] args) {
        MyArrayList<String> list = new MyArrayList<>();
        for (int i = 0; i < 12; i++) list.add("e" + i);   // 触发一次扩容 10 → 15
        System.out.println(list + " size=" + list.size());

        list.add(0, "head");
        System.out.println(list.get(0) + " / " + list.remove(0));

        Iterator<String> it = list.iterator();
        while (it.hasNext()) if (it.next().endsWith("1")) it.remove();   // ✅ 安全
        System.out.println(list);

        try {
            for (String s : list) list.remove(s);          // ❌ 预期抛 CME
        } catch (ConcurrentModificationException e) {
            System.out.println("CME 触发 ✅");
        }
    }

题 4：手写一个简易 HashMap（扰动 + 位与寻址 + 扩容高低位拆分） ​

核心实现：

java
import java.util.*;

public class MyHashMap<K, V> {

    static final int DEFAULT_CAPACITY = 16;
    static final float DEFAULT_LOAD_FACTOR = 0.75f;
    static final int MAXIMUM_CAPACITY = 1 << 30;

    static class Node<K, V> {
        final int hash;
        final K key;
        V value;
        Node<K, V> next;
        Node(int hash, K key, V value, Node<K, V> next) {
            this.hash = hash; this.key = key; this.value = value; this.next = next;
        }
    }

    private Node<K, V>[] table;
    private int size;
    private int threshold;
    private final float loadFactor;

    public MyHashMap() { this(DEFAULT_CAPACITY, DEFAULT_LOAD_FACTOR); }

    public MyHashMap(int initialCapacity) { this(initialCapacity, DEFAULT_LOAD_FACTOR); }

    public MyHashMap(int initialCapacity, float loadFactor) {
        if (initialCapacity < 0) throw new IllegalArgumentException("capacity < 0");
        if (loadFactor <= 0 || Float.isNaN(loadFactor))
            throw new IllegalArgumentException("illegal loadFactor");
        this.loadFactor = loadFactor;
        this.threshold = tableSizeFor(initialCapacity);   // ⭐ 与 JDK 一致：先存到 threshold
    }

    /* ---------- 向上取整到 2 的 n 次方：把最高位的 1 向右铺满再 +1 ---------- */
    static int tableSizeFor(int cap) {
        int n = cap - 1;
        n |= n >>> 1;  n |= n >>> 2;  n |= n >>> 4;
        n |= n >>> 8;  n |= n >>> 16;
        return (n < 0) ? 1 : (n >= MAXIMUM_CAPACITY) ? MAXIMUM_CAPACITY : n + 1;
    }

    /* ---------- 扰动函数：高 16 位异或到低 16 位 ---------- */
    static int hash(Object key) {
        int h;
        return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
    }

    /* ---------- put ---------- */
    public V put(K key, V value) {
        if (table == null) resize();
        int hash = hash(key);
        int i = (table.length - 1) & hash;        // ⭐ 位与代替取模
        Node<K, V> first = table[i];

        if (first == null) {                      // 空桶，直接放
            table[i] = new Node<>(hash, key, value, null);
        } else {
            Node<K, V> e = first, prev = null;
            while (e != null) {
                // ⭐ 先比 hash（快），再比引用，最后才 equals
                if (e.hash == hash && (e.key == key || (key != null && key.equals(e.key)))) {
                    V old = e.value;
                    e.value = value;
                    return old;                   // ⭐ 覆盖已有 key：size 不变，不扩容
                }
                prev = e; e = e.next;
            }
            prev.next = new Node<>(hash, key, value, null);   // ⭐ 尾插（JDK8 行为）
        }
        if (++size > threshold) resize();
        return null;
    }

    /* ---------- get / containsKey / remove ---------- */
    public V get(Object key) {
        Node<K, V> e = getNode(key);
        return e == null ? null : e.value;
    }

    public boolean containsKey(Object key) { return getNode(key) != null; }

    private Node<K, V> getNode(Object key) {
        if (table == null || size == 0) return null;
        int hash = hash(key);
        for (Node<K, V> e = table[(table.length - 1) & hash]; e != null; e = e.next) {
            if (e.hash == hash && (e.key == key || (key != null && key.equals(e.key)))) return e;
        }
        return null;
    }

    public V remove(Object key) {
        if (table == null) return null;
        int hash = hash(key);
        int i = (table.length - 1) & hash;
        Node<K, V> e = table[i], prev = null;
        while (e != null) {
            if (e.hash == hash && (e.key == key || (key != null && key.equals(e.key)))) {
                if (prev == null) table[i] = e.next;    // 删的是头节点
                else prev.next = e.next;
                size--;
                return e.value;
            }
            prev = e; e = e.next;
        }
        return null;
    }

    /* ---------- 扩容：高低位拆分，不重算 hash ---------- */
    @SuppressWarnings("unchecked")
    private void resize() {
        Node<K, V>[] oldTab = table;
        int oldCap = (oldTab == null) ? 0 : oldTab.length;
        int newCap, newThr;

        if (oldCap > 0) {
            if (oldCap >= MAXIMUM_CAPACITY) { threshold = Integer.MAX_VALUE; return; }
            newCap = oldCap << 1;                       // ⭐ 2 倍，保持 2 的 n 次方
            newThr = (int) (newCap * loadFactor);
        } else if (threshold > 0) {                     // 构造时传了初始容量
            newCap = threshold;
            newThr = (int) (newCap * loadFactor);
        } else {
            newCap = DEFAULT_CAPACITY;
            newThr = (int) (DEFAULT_CAPACITY * DEFAULT_LOAD_FACTOR);
        }
        threshold = newThr;
        Node<K, V>[] newTab = (Node<K, V>[]) new Node[newCap];
        table = newTab;
        if (oldTab == null) return;

        for (int j = 0; j < oldCap; j++) {
            Node<K, V> e = oldTab[j];
            if (e == null) continue;
            oldTab[j] = null;
            if (e.next == null) {                       // 只有一个节点，直接定位
                newTab[e.hash & (newCap - 1)] = e;
                continue;
            }
            // ⭐ 链表拆成「低位链」和「高位链」，保持相对顺序
            Node<K, V> loHead = null, loTail = null, hiHead = null, hiTail = null;
            while (e != null) {
                Node<K, V> next = e.next;
                if ((e.hash & oldCap) == 0) {           // ⭐ 核心：一次位与定去向
                    if (loTail == null) loHead = e; else loTail.next = e;
                    loTail = e;
                } else {
                    if (hiTail == null) hiHead = e; else hiTail.next = e;
                    hiTail = e;
                }
                e = next;
            }
            if (loTail != null) { loTail.next = null; newTab[j] = loHead; }
            if (hiTail != null) { hiTail.next = null; newTab[j + oldCap] = hiHead; }
        }
    }

    public int size() { return size; }
    public int capacity() { return table == null ? 0 : table.length; }

    /* ---------- 调试用：打印桶分布，直观看冲突 ---------- */
    public void printDistribution() {
        if (table == null) { System.out.println("table 未初始化"); return; }
        for (int i = 0; i < table.length; i++) {
            int len = 0;
            for (Node<K, V> e = table[i]; e != null; e = e.next) len++;
            if (len > 0) System.out.println("bucket[" + i + "] 链长 = " + len);
        }
    }

    public static void main(String[] args) {
        MyHashMap<String, Integer> map = new MyHashMap<>();
        for (int i = 0; i < 20; i++) map.put("key" + i, i);
        System.out.println("size=" + map.size() + " capacity=" + map.capacity());  // 20 / 32
        System.out.println(map.get("key7") + " " + map.get("none"));
        System.out.println(map.put("key7", 700) + " → " + map.get("key7"));        // 7 → 700
        System.out.println(map.remove("key7") + " " + map.containsKey("key7"));    // 700 false

        map.put(null, -1);                       // null key 固定落在 table[0]
        System.out.println("null key = " + map.get(null));
        System.out.println("tableSizeFor(13) = " + tableSizeFor(13));              // 16
        map.printDistribution();
    }
}

三个必须记住的点：

  1. 三件套必须一字不差：扰动 (h = key.hashCode()) ^ (h >>> 16)、寻址 (n - 1) & hash、扩容拆分 (e.hash & oldCap) == 0。
  2. 覆盖已有 key 时 size 不变、不触发扩容，而且要返回旧值 —— 这是 put 的语义，写漏了直接判错。
  3. 链表比较顺序是 hash → == → equals，先比 int 极快，能挡掉绝大多数不相等的情况；同时 key 为 null 时要走单独分支，不能直接调 key.equals。

import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.LongAdder;
import java.util.function.Function;
import java.util.stream.Collectors;

public class ConcurrentCollectionDemo {

    /* ========== ① 并发词频统计：三种写法对比 ========== */
    static void wordCount() throws Exception {
        List<String> words = new ArrayList<>();
        for (int i = 0; i < 100_000; i++) words.add("w" + (i % 100));

        // ❌ 错误：read-modify-write 不原子，统计值会偏小
        Map<String, Integer> wrong = new ConcurrentHashMap<>();
        // wrong.put(w, wrong.getOrDefault(w, 0) + 1);

        // ✅ 写法 A：merge，最简洁的原子累加
        Map<String, Integer> byMerge = new ConcurrentHashMap<>();
        runParallel(words, w -> byMerge.merge(w, 1, Integer::sum));

        // ✅ 写法 B：LongAdder，热点 key 下性能最好
        Map<String, LongAdder> byAdder = new ConcurrentHashMap<>();
        runParallel(words, w -> byAdder.computeIfAbsent(w, k -> new LongAdder()).increment());

        // ✅ 写法 C：并行流 + groupingByConcurrent
        Map<String, Long> byStream = words.parallelStream()
                .collect(Collectors.groupingByConcurrent(Function.identity(), Collectors.counting()));

        System.out.println("merge  w0 = " + byMerge.get("w0"));         // 1000
        System.out.println("adder  w0 = " + byAdder.get("w0").sum());   // 1000
        System.out.println("stream w0 = " + byStream.get("w0"));        // 1000
    }

    /* ========== ② 并发安全的本地缓存 ========== */
    static class LocalCache<K, V> {
        private final ConcurrentHashMap<K, V> map = new ConcurrentHashMap<>();
        private final Function<K, V> loader;

        LocalCache(Function<K, V> loader) { this.loader = loader; }

        /* ⚠️ 看着没问题，但 loader 是远程调用时会把整个桶锁住 */
        V getBad(K key) { return map.computeIfAbsent(key, loader); }

        /* ✅ 推荐：锁外加载 + putIfAbsent，牺牲「可能重复加载」换取不阻塞同桶的其他 key */
        V get(K key) {
            V v = map.get(key);
            if (v != null) return v;
            v = loader.apply(key);                  // 在锁外执行耗时加载
            if (v == null) return null;             // ⚠️ CHM 不允许 null value
            V prev = map.putIfAbsent(key, v);       // 原子写入，输掉竞争就用别人的
            return prev != null ? prev : v;
        }

        /* ✅ 要求「只加载一次」时用 Future 占位，这是 Guava/Caffeine 的核心思路 */
        private final ConcurrentHashMap<K, Future<V>> futures = new ConcurrentHashMap<>();

        V getOnce(K key) throws Exception {
            Future<V> f = futures.get(key);
            if (f == null) {
                FutureTask<V> task = new FutureTask<>(() -> loader.apply(key));
                f = futures.putIfAbsent(key, task);   // ⭐ 原子占位
                if (f == null) { f = task; task.run(); }  // 抢到的线程负责真正加载
            }
            try {
                return f.get();                       // 其他线程在这里等结果，不阻塞别的 key
            } catch (ExecutionException e) {
                futures.remove(key, f);               // ⚠️ 失败要移除，否则缓存了异常
                throw e;
            }
        }
    }

    /* ========== ③ TopK：小顶堆，O(n log k) ========== */
    static List<Map.Entry<String, Integer>> topK(Map<String, Integer> counts, int k) {
        // 小顶堆：堆顶是「当前 K 个中最小的」，比它大就替换掉
        PriorityQueue<Map.Entry<String, Integer>> heap =
                new PriorityQueue<>(k, Map.Entry.comparingByValue());
        for (Map.Entry<String, Integer> e : counts.entrySet()) {
            if (heap.size() < k) {
                heap.offer(e);
            } else if (e.getValue() > heap.peek().getValue()) {
                heap.poll();
                heap.offer(e);
            }
        }
        // ⚠️ 堆本身不是有序的，要全量 poll 出来再反转
        List<Map.Entry<String, Integer>> result = new ArrayList<>(k);
        while (!heap.isEmpty()) result.add(heap.poll());
        Collections.reverse(result);
        return result;
    }

    /* 对照：Stream 版 TopK，代码短但是 O(n log n) 全排序 */
    static List<Map.Entry<String, Integer>> topKByStream(Map<String, Integer> counts, int k) {
        return counts.entrySet().stream()
                .sorted(Map.Entry.<String, Integer>comparingByValue().reversed())
                .limit(k)
                .collect(Collectors.toList());
    }

    /* ========== ④ 生产者消费者：阻塞队列 ========== */
    static void producerConsumer() throws Exception {
        BlockingQueue<Integer> queue = new ArrayBlockingQueue<>(100);   // ⭐ 必须有界
        ExecutorService pool = Executors.newFixedThreadPool(3);
        final Integer POISON = Integer.MIN_VALUE;                       // 毒丸，优雅停机

        pool.submit(() -> {
            try {
                for (int i = 0; i < 1000; i++) queue.put(i);            // 满了自动阻塞
                queue.put(POISON);
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        });
        pool.submit(() -> {
            try {
                while (true) {
                    Integer v = queue.take();                           // 空了自动阻塞
                    if (POISON.equals(v)) break;
                }
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        });
        pool.shutdown();
        pool.awaitTermination(10, TimeUnit.SECONDS);
        System.out.println("生产者消费者结束，剩余 = " + queue.size());
    }

    private static void runParallel(List<String> data, java.util.function.Consumer<String> action)
            throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(8);
        int chunk = data.size() / 8;
        List<Future<?>> futures = new ArrayList<>();
        for (int i = 0; i < 8; i++) {
            List<String> sub = data.subList(i * chunk, (i + 1) * chunk);
            futures.add(pool.submit(() -> sub.forEach(action)));
        }
        for (Future<?> f : futures) f.get();
        pool.shutdown();
    }

    public static void main(String[] args) throws Exception {
        wordCount();
        LocalCache<String, String> cache = new LocalCache<>(k -> "value-" + k);
        System.out.println(cache.get("a") + " " + cache.getOnce("b"));
        Map<String, Integer> counts = Map.of("a", 5, "b", 9, "c", 1, "d", 7);
        System.out.println(topK(new HashMap<>(counts), 2));
        producerConsumer();
    }
}

三个必须记住的点：

  1. ConcurrentHashMap 只保证单方法原子性：计数一律用 merge / compute，热点 key 进一步用 LongAdder 把竞争打散。
  2. computeIfAbsent 的函数体里不能做耗时操作、不能回头操作同一个 map；要「只加载一次」就用 Future 占位（Guava/Caffeine 的做法），要「不阻塞」就锁外加载 + putIfAbsent。
  3. TopK 用小顶堆是 O(n log k)，远优于全排序的 O(n log n)；注意 PriorityQueue 本身遍历无序，必须靠 poll() 才能拿到有序结果。

import java.util.*;

/** ① 比较器契约自测器：O(n³) 暴力校验，只在单元测试里用 */
public final class ComparatorContract {

    public static <T> void verify(List<T> samples, Comparator<T> cmp) {
        int n = samples.size();

        // 契约 1：反对称性 sgn(c(a,b)) == -sgn(c(b,a))
        for (int i = 0; i < n; i++) {
            for (int j = 0; j < n; j++) {
                T a = samples.get(i), b = samples.get(j);
                int ab = sgn(cmp.compare(a, b));
                int ba = sgn(cmp.compare(b, a));
                if (ab != -ba) {
                    throw new AssertionError(String.format(
                            "违反反对称性: compare(%s,%s)=%d, compare(%s,%s)=%d", a, b, ab, b, a, ba));
                }
            }
        }

        // 契约 2：自反性 compare(a, a) == 0（反对称性的特例，单独报错更好定位）
        for (T a : samples) {
            if (cmp.compare(a, a) != 0) {
                throw new AssertionError("compare(a, a) != 0: " + a);
            }
        }

        // 契约 3：传递性 a>b && b>c ⇒ a>c
        for (int i = 0; i < n; i++) {
            for (int j = 0; j < n; j++) {
                for (int k = 0; k < n; k++) {
                    T a = samples.get(i), b = samples.get(j), c = samples.get(k);
                    if (sgn(cmp.compare(a, b)) > 0 && sgn(cmp.compare(b, c)) > 0
                            && sgn(cmp.compare(a, c)) <= 0) {
                        throw new AssertionError(String.format(
                                "违反传递性: %s > %s > %s 但 compare(%s,%s)=%d",
                                a, b, c, a, c, cmp.compare(a, c)));
                    }
                }
            }
        }

        // 契约 4：等价传递 c(a,b)==0 ⇒ sgn(c(a,x)) == sgn(c(b,x))
        for (int i = 0; i < n; i++) {
            for (int j = 0; j < n; j++) {
                T a = samples.get(i), b = samples.get(j);
                if (cmp.compare(a, b) != 0) continue;
                for (T x : samples) {
                    if (sgn(cmp.compare(a, x)) != sgn(cmp.compare(b, x))) {
                        throw new AssertionError(String.format(
                                "违反等价传递: %s == %s 但对 %s 的比较结果不同", a, b, x));
                    }
                }
            }
        }
    }

    /** 稳定性与「结果是否真的有序」双重校验 */
    public static <T> void verifySorted(List<T> src, Comparator<T> cmp) {
        List<T> sorted = new ArrayList<>(src);
        sorted.sort(cmp);
        for (int i = 1; i < sorted.size(); i++) {
            if (cmp.compare(sorted.get(i - 1), sorted.get(i)) > 0) {
                throw new AssertionError("排序结果并非有序，位置 " + i);
            }
        }
    }

    private static int sgn(int v) { return Integer.compare(v, 0); }

    private ComparatorContract() {}
}

/** ② 动态多字段排序构建器：把前端传的 "age,desc;name,asc" 变成安全的 Comparator */
public final class SortBuilder<T> {

    /** ⭐ 白名单：绝不能直接把前端字符串当字段名反射取值（SQL/反射注入 + 性能黑洞） */
    private final Map<String, Comparator<T>> allowed = new LinkedHashMap<>();

    public <U extends Comparable<? super U>> SortBuilder<T> field(String name, Function<T, U> getter) {
        // nullsLast 包一层，彻底杜绝字段为 null 时的 NPE
        allowed.put(name, Comparator.comparing(getter, Comparator.nullsLast(Comparator.naturalOrder())));
        return this;
    }

    /** 基本类型专用，避免装箱 */
    public SortBuilder<T> intField(String name, java.util.function.ToIntFunction<T> getter) {
        allowed.put(name, Comparator.comparingInt(getter));   // 内部用 Integer.compare，不会溢出
        return this;
    }

    /**
     * @param expr      形如 "age,desc;name,asc"，非法字段直接忽略（也可以选择抛 400）
     * @param tieBreak  ⭐ 兜底唯一字段比较器，保证全序与结果可复现
     */
    public Comparator<T> build(String expr, Comparator<T> tieBreak) {
        Comparator<T> result = null;
        if (expr != null && !expr.isBlank()) {
            for (String seg : expr.split(";")) {
                String[] kv = seg.trim().split(",");
                if (kv.length == 0) continue;
                Comparator<T> one = allowed.get(kv[0].trim());
                if (one == null) continue;                              // 不在白名单，静默忽略
                if (kv.length > 1 && "desc".equalsIgnoreCase(kv[1].trim())) {
                    one = one.reversed();                               // ⭐ 只反转当前这一个字段
                }
                result = (result == null) ? one : result.thenComparing(one);
            }
        }
        // 没有任何合法字段时，也必须返回一个确定的顺序，不能返回 null
        return result == null ? tieBreak : result.thenComparing(tieBreak);
    }

    private SortBuilder() {}
    public static <T> SortBuilder<T> of(Class<T> type) { return new SortBuilder<>(); }
}

✅ 边界 Case 自测：

  • 把 (a, b) -> a.getScore() > b.getScore() ? 1 : -1 丢给 verify，确认在样本里有两个相等元素时就报违反反对称性（这是最有价值的一条）
  • 构造 balance = Integer.MAX_VALUE 和 Integer.MIN_VALUE 的两个对象，验证 a - b 写法被 verify 抓出来、而 comparingInt 能通过
  • 样本里放 name == null 的对象，确认 nullsLast 生效且不抛 NPE
  • 同一组数据用 build("age,desc", ...) 排两次，结果必须完全一致（验证 tieBreak 保证了可复现性）
  • 传入 "password,asc" 这种不在白名单的字段，确认被忽略且不会反射到任何字段
  • 传入 null、空串、";;;"、"age"（缺方向）这几种畸形输入，确认都返回可用的比较器而不是 NPE
  • 用 comparing(A).thenComparing(B).reversed() 和 comparing(A, reverseOrder()).thenComparing(B) 各排一次，亲手对比两者结果的差异
  • 准备 40 个以上的元素（跨过 MIN_MERGE = 32）再用违约比较器排序，复现 IllegalArgumentException；再把元素减到 10 个，确认不报错但顺序是错的

🔁 变种拓展题：

  • 把 verify 的 O(n³) 降成抽样：传入 maxSamples，超过阈值就随机抽样 + 固定随机种子，保证失败可复现；这样可以把它挂到 CI 里跑真实数据
  • 支持中文按拼音排序：Comparator.comparing(User::getName, Collator.getInstance(Locale.CHINA))，注意 Collator 不是线程安全的，必须每次新建或用 ThreadLocal（并配 remove）
  • 支持「自定义枚举顺序」：业务要求状态按「待支付 → 已支付 → 已取消」而不是枚举声明序，用 Comparator.comparingInt(u -> ORDER.indexOf(u.getStatus()))，ORDER 用 List.of 固化
  • 排序下推到数据库：白名单模式天然可以复用成 ORDER BY 的字段白名单 —— 内存排序只适合「已经全量加载」的小数据集，上了分页就必须下推，否则会出现「每页内部有序、跨页乱序」的经典 Bug
  • TopK 场景不要全排序：只要前 N 条时用 PriorityQueue 维护大小为 N 的堆，复杂度从 O(n log n) 降到 O(n log N)
