1. CommonJS 模块机制 ​

Node 加载一个 .js 文件时，并不是直接执行文件内容，而是先把代码包进一个函数再调用，这就是模块作用域的来源：

js
// 你写的代码
const fs = require("fs");
module.exports = { a: 1 };

// Node 实际执行的（模块包装器 Module.wrap）
(function (exports, require, module, __filename, __dirname) {
  const fs = require("fs");
  module.exports = { a: 1 };
});
text
require('./a.js') 的完整过程
┌──────────────────────────────────────────────────┐
│ 1. Module._resolveFilename  路径解析 → 绝对路径    │
│ 2. 查 Module._cache[绝对路径]                     │
│      命中 → 直接返回 cached.exports（不再执行）     │
│ 3. new Module()  创建模块对象                      │
│      { id, exports: {}, loaded: false, children } │
│ 4. 先写入缓存（关键！这一步在执行之前）             │
│ 5. module.load() → 按扩展名选 extension 处理器     │
│      .js   → 读文件 + 包装 + compile              │
│      .json → JSON.parse                          │
│      .node → process.dlopen 加载 C++ 插件         │
│ 6. loaded = true，返回 module.exports             │
└──────────────────────────────────────────────────┘

第 4 步「先缓存再执行」是循环依赖能跑通的根本原因：a 引 b、b 又引 a 时，b 拿到的是 a 当前已经赋值的那部分 exports（一个不完整的对象），而不是死循环。

模块查找优先级：

text
require('x')
  ├─ 核心模块（fs / path / http…，或带 node: 前缀）→ 直接返回，优先级最高
  ├─ './' '../' '/' 开头 → 当作文件路径
  │     x → x.js → x.json → x.node → x/package.json(main) → x/index.js
  └─ 裸模块名 → 逐层向上找 node_modules
        /app/src/node_modules/x
        /app/node_modules/x
        /node_modules/x        ← 找不到抛 MODULE_NOT_FOUND
五个模块变量本质
exports形参，初始指向 module.exports，重新赋值会失效
module当前模块对象，module.exports 才是真正的导出
require函数，挂着 require.cache / require.resolve
__filename当前文件绝对路径
__dirname当前文件所在目录绝对路径
js
// 经典坑：直接给 exports 赋值会断开与 module.exports 的引用
exports.a = 1; // ✅ 有效
exports = { a: 1 }; // ❌ 无效，只是改了形参指向
module.exports = { a: 1 }; // ✅ 有效

为什么 exports = {...} 不生效，module.exports = {...} 就可以？

一句话答案：require 返回的永远是 module.exports，不是 exports。exports 只是包装函数的一个形参（局部变量），初始时和 module.exports 指向同一个对象；你直接 exports = {} 只改了局部变量的指向，动不了 module 对象身上的 exports 属性。

js
// Node 内部 Module 简化版（还原 require 的返回值从哪来）
class Module {
  constructor(filePath) {
    this.exports = {}; // ✅ 真正要导出的东西挂在 module 对象上
  }
}

function require(file) {
  const m = new Module(file);
  // 把文件源码套进包装函数并执行
  (function (exports, require, module, __filename, __dirname) {
    // ← 你写的模块代码放在这里
  })(m.exports, require, m, file, dir); // 注意第一个实参就是 m.exports

  return m.exports; // ✅ 最终 return 的是 module.exports，和局部 exports 无关
}

三种写法的内存指向变化：

text
初始状态（包装函数刚进来）
  module ──┐
           ├─ exports 属性 ──┐
  exports(形参) ─────────────┴──► 堆：{}        ← 两者同一个地址

① exports.a = 1                               ✅ 生效
  module.exports ─┐
  exports ────────┴──► { a: 1 }                引用没断，只是加属性
                                               require 返回 { a: 1 }

② exports = { a: 1 }                           ❌ 不生效
  module.exports ─────► {}                     ← require 返回这个空对象
  exports ────────────► { a: 1 }（新对象）      ← 局部变量重定向，彻底分家

③ module.exports = { a: 1 }                    ✅ 生效
  module.exports ─────► { a: 1 }               ← require 返回这个
  exports ────────────► {}（旧的空对象，没人要） ← 此后用 exports.x 已无意义

跑一遍就能复现：

js
// test.cjs —— ❌ 错误写法
exports = { msg: "直接给 exports 赋值" };

// main.cjs
const test = require("./test.cjs");
console.log(test); // {}  空对象，拿不到 msg

// test.cjs —— ✅ 正确写法
module.exports = { msg: "给 module.exports 赋值" };
// main.cjs 打印：{ msg: '给 module.exports 赋值' }

// 既想整体覆盖、又想继续用 exports 简写，可以一行重新绑定
module.exports = exports = { msg: "两者重新指向同一个新对象" };
// 原理：赋值从右往左，先把新对象赋给 exports，再赋给 module.exports
写法是否生效原因
exports.a = 1✅给两者共同指向的对象追加属性，引用没断
exports = { a: 1 }❌局部形参重定向，与 module.exports 断开
module.exports.a = 1✅直接操作模块的导出对象
module.exports = { a: 1 }✅替换导出对象，require 返回的就是它
module.exports = exports = { a: 1 }✅同时赋值，恢复两者引用一致
module.exports = {a:1} 后 exports.b = 2❌（b 丢失）第一行已让两者分家，再给 exports 加属性无效

配套追问：为什么要设计成这样，不让 exports 直接当返回值？ 为了同时支持两种导出风格：追加多个成员时写 exports.xxx 更省事；只导出一个函数/类时则直接 module.exports = Class 整体覆盖。如果把局部 exports 当返回值，后者就没法实现了。

加粗要点： CommonJS 的出口只有一个 —— module.exports。exports 是「给 module.exports 起的一个局部别名」，只能用来加属性，不能整体赋值；一旦你覆盖了 module.exports，之前那个 exports 别名就作废了，后续 exports.x = ... 一律丢失。

text
   ┌──────────────────────────────┐
┌─>│          timers              │  setTimeout / setInterval 到期回调
│  └─────────────┬────────────────┘
│  ┌─────────────┴────────────────┐
│  │     pending callbacks        │  上一轮延迟下来的系统级 I/O 回调(如 TCP ECONNREFUSED)
│  └─────────────┬────────────────┘
│  ┌─────────────┴────────────────┐
│  │       idle / prepare         │  libuv 内部使用
│  └─────────────┬────────────────┘      ┌───────────────┐
│  ┌─────────────┴────────────────┐      │   incoming:   │
│  │            poll              │<─────│  connections, │
│  └─────────────┬────────────────┘      │   data, etc.  │
│  ┌─────────────┴────────────────┐      └───────────────┘
│  │            check             │  setImmediate 专属阶段
│  └─────────────┬────────────────┘
│  ┌─────────────┴────────────────┐
└──┤      close callbacks         │  socket.on('close') 等
   └──────────────────────────────┘

每个阶段之间都会清空：nextTick 队列 → 微任务队列（Promise）
阶段干什么面试要点
timers执行到期的 setTimeout / setInterval定时器不保证精确，只保证不早于
pending callbacks上一轮循环延迟下来的系统级 I/O 回调比如 TCP 连接错误的 ECONNREFUSED
idle / preparelibuv 内部使用，业务无感面试只需知道存在
poll取 I/O 事件并执行回调，可能阻塞等待事件循环的核心，决定阻塞多久
check执行 setImmediate 回调名字反直觉：它比 timers 更"立即"
close callbacks执行 close 事件回调socket.destroy() 后的清理

poll 阶段的阻塞策略： 如果 poll 队列非空就依次执行回调；队列空时 —— 有 setImmediate 待执行就立刻进 check；否则看有没有即将到期的 timer，有就阻塞到那个时间点，都没有就一直阻塞等 I/O。这就是为什么纯 I/O 的 Node 进程 CPU 占用接近 0。

4. 微任务：process.nextTick 与 Promise.then ​

js
console.log("start");

setTimeout(() => console.log("timer"), 0);
setImmediate(() => console.log("immediate"));

process.nextTick(() => console.log("nextTick1"));
Promise.resolve().then(() => console.log("promise1"));
process.nextTick(() => console.log("nextTick2"));

console.log("end");

// start → end → nextTick1 → nextTick2 → promise1 → timer → immediate
队列归属优先级说明
process.nextTickNode 自有队列最高每个阶段结束先清空它，且可以无限插队
Promise.thenV8 微任务队列次高nextTick 清空后才执行
setTimeout(fn, 0)timers 阶段宏任务实际最小延迟约 1ms
setImmediatecheck 阶段宏任务当前阶段跑完就执行，不等 timer

nextTick 可以饿死事件循环： 因为它在每个阶段结束时被完全清空，并且清空过程中新加入的 nextTick 也要一并执行。递归调用 process.nextTick 会让 I/O 永远得不到执行机会；换成 setImmediate 则会把控制权交还给事件循环。所以库作者才建议默认用 setImmediate。

5. Buffer：Node 的二进制缓冲区 ​

Buffer 是 Node 处理二进制数据的核心，底层继承自 Uint8Array，分配的是 V8 堆外内存（不受 --max-old-space-size 限制，但受系统内存限制）。

js
// 三种创建方式
const b1 = Buffer.alloc(8); // 分配并填 0（安全，推荐）
const b2 = Buffer.allocUnsafe(8); // 不清零，更快，但可能含旧数据（有泄露风险）
const b3 = Buffer.from("中文", "utf8"); // 从字符串/数组/ArrayBuffer 创建

console.log(Buffer.from("中").length); // 3 —— 一个中文 UTF-8 占 3 字节
console.log("中".length); // 1 —— 字符串长度按 UTF-16 码元算

// 常用操作
b3.toString("utf8"); // 转字符串
b3.toString("base64"); // base64 编码
b3.toString("hex"); // 十六进制
Buffer.concat([b1, b3]); // 拼接（比 += 高效）
b3.slice(0, 3); // 返回**共享内存**的视图，不是拷贝！
Buffer.byteLength("中文"); // 6，算真实字节数
编码用途
utf8默认，文本
base64图片/文件转字符串传输（体积涨 1/3）
hex调试、哈希值展示
latin1单字节映射，二进制安全的"伪字符串"
ascii只取低 7 位，会丢信息

最大的坑：切割多字节字符。 流式读取时如果一个中文字符的 3 个字节被分到了两个 chunk 里，直接 chunk.toString() 会出现乱码「�」。正确做法是用 require('string_decoder').StringDecoder，它会把不完整的字节缓存到下一次。

8. CPU 密集型 与 I/O 密集型 ​

上一节反复提到"CPU 密集"和"I/O 密集"，这两个词几乎是所有 Node 性能话题的分水岭，必须先把定义钉死。

  • CPU 密集型（CPU-bound）：大部分时间 CPU 都在做计算 / 逻辑运算，I/O 等待很短，瓶颈是CPU 算力。
  • I/O 密集型（I/O-bound）：大部分时间都在等外部资源返回（磁盘、数据库、网络），CPU 大多闲着，瓶颈是I/O 速度。

I/O = Input / Output（输入 / 输出），指程序和 CPU 外部的设备打交道：读写磁盘文件、查数据库、发网络请求、读写 socket 等。只要数据不在 CPU/内存里，就要"走出去取"，而走出去这一趟比 CPU 算一次慢几个数量级。

一次请求耗时 100ms，时间花在哪里决定了它的类型：

text
CPU 密集型（算 95ms，等 5ms）
时间轴 ├████████████████████████████████████████████░┤
        ↑ CPU 满载跑指令（加密 / 编解码 / 大循环）    ↑ 少量 I/O
        → 瓶颈：核数 × 主频，加机器/加进程才有用

I/O 密集型（等 95ms，算 5ms）
时间轴 ├░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░███┤
        ↑ CPU 空闲，在等磁盘/数据库/HTTP 响应     ↑ 少量计算
        → 瓶颈：外部资源延迟，提高并发才有用

CPU 工作状态对照
CPU 密集：running ──────────────────────────► 很少进入阻塞等待
I/O 密集：running ─┐            ┌─ running ─┐            ┌─
                   └─ 阻塞/挂起 ─┘           └─ 阻塞/挂起 ─┘

CPU 密集型的三个特征：

  1. CPU 占用率一直很高，持续消耗时间片；
  2. 核心动作是算数、循环、加密、解析、渲染、复杂算法；
  3. 磁盘、网络等待时间占比极低。

常见场景：大数运算、斐波那契递归、MD5 / SHA256 加密、图片视频编解码、矩阵运算、AI 推理、超大 JSON 解析、复杂排序。

js
// CPU 密集型：纯计算，CPU 一直在执行指令
let sum = 0
for (let i = 0; i < 1e8; i++) {
  sum += i
}
// 现象：CPU 飙到接近 100%，磁盘和网络毫无动静
// 在 Node 里：这段代码会把主线程彻底堵死，事件循环停转，所有请求排队

I/O 密集型的三个特征：

  1. 大部分时间在等外部资源返回；
  2. CPU 经常处于空闲 / 阻塞等待状态；
  3. 代码逻辑往往很简单，只是外部资源慢。

常见场景：文件与日志读写、MySQL / Redis 查询、调用第三方 HTTP 接口、文件上传下载、爬虫。

js
const fs = require('fs/promises')

// I/O 密集型：等磁盘
const log = await fs.readFile('./big.log')

// I/O 密集型：等网络
const res = await fetch('https://api.example.com/user')
const data = await res.json()

// 现象：CPU 占用很低，磁盘 / 网卡在工作
// 在 Node 里：await 期间主线程被释放，可以同时处理成百上千个请求
类型瓶颈CPU 状态耗时大头典型场景适合方案
CPU 密集型CPU 算力（核数/主频）高占用，一直在跑计算本身加密、音视频编解码、算法运算多进程 / 多线程，避开单线程限制
I/O 密集型外部 I/O（磁盘/网络）大部分空闲在等待等待资源返回文件读写、数据库、HTTP 请求异步非阻塞 + 提高并发

怎么判断自己的任务属于哪一类？

  • 看 CPU 占用率：压测时 CPU 接近打满 → CPU 密集；CPU 很低但 QPS 上不去 → I/O 密集；
  • 看耗时分布：在关键步骤前后打点，看时间是花在"算"还是花在"等"；
  • 用工具定位：node --prof + --prof-process、clinic doctor、0x 火焰图；火焰图上又宽又平的 JS 栈帧 = CPU 密集，栈里大量 await / libuv 回调且 CPU 空转 = I/O 密集。

Node 里的对症下药：

js
// CPU 密集：丢出主线程
const { Worker } = require('worker_threads')      // 同进程多线程，适合纯计算
// const cluster = require('cluster')             // 多进程利用多核，适合 HTTP 服务整体扩容
// const { fork } = require('child_process')      // 独立进程跑脚本，隔离崩溃风险

// I/O 密集：永远用异步 API + 控制并发，别用 fs.readFileSync
const results = await Promise.all(ids.map((id) => queryUser(id)))  // 并发发起
// 并发量大时要加限流（见手撕代码题 4 的并发限制调度器），避免打爆下游

加粗要点： 判断标准只有一句话 —— 时间花在"算"上就是 CPU 密集，花在"等"上就是 I/O 密集。Node 的单线程事件循环天生为 I/O 密集设计（等待时主线程可以服务别人），但对 CPU 密集是致命的（一个大循环就能让整个服务失去响应）。所以I/O 密集 → 异步 + 并发；CPU 密集 → worker_threads / cluster / 独立进程，千万不要指望 async/await 能加速计算。

2. setTimeout(fn, 0) 与 setImmediate 的顺序为什么不确定 ​

js
setTimeout(() => console.log("timeout"), 0);
setImmediate(() => console.log("immediate"));
// 主模块里执行：顺序随机！可能 timeout 先，也可能 immediate 先

原因：setTimeout(fn, 0) 会被 Node 强制改成 1ms。事件循环启动时如果准备工作耗时 ≥ 1ms，进入 timers 阶段时定时器已到期 → timeout 先；如果准备工作 < 1ms，timers 阶段发现还没到期 → 跳过，走到 check 阶段 → immediate 先。

js
// 但在 I/O 回调内部，顺序是 100% 确定的
fs.readFile(__filename, () => {
  setTimeout(() => console.log("timeout"), 0);
  setImmediate(() => console.log("immediate"));
});
// 永远是：immediate → timeout

为什么确定？ I/O 回调在 poll 阶段执行，poll 的下一站就是 check 阶段（setImmediate），而 timers 要等到下一轮循环开头。所以"在 I/O 回调里 setImmediate 一定先于 setTimeout"是标准答案。

题 1：说说 Node 的事件循环，它和浏览器的事件循环有什么区别？ ​

精简口述答案：

Node 的事件循环由 libuv 实现，一轮分 6 个阶段：timers 执行到期定时器、pending callbacks 处理上轮遗留的系统 I/O 回调、idle/prepare 内部使用、poll 取 I/O 事件并执行回调（这是核心，队列空时会阻塞等待）、check 执行 setImmediate、close callbacks 处理关闭事件。

和浏览器的区别主要有三点：第一，浏览器只有宏任务和微任务两个概念，Node 多了明确的阶段划分和 setImmediate；第二，Node 多了一个优先级最高的 process.nextTick 队列，它在每个阶段结束时先于 Promise 微任务被清空；第三，早期 Node（10 以前）是一个阶段跑完所有宏任务才清微任务，Node 11 之后对齐了浏览器，改成每执行完一个宏任务就清一次微任务队列，所以现在两边输出顺序基本一致了。

连环追问链：

  1. 追问：setTimeout(fn, 0) 和 setImmediate 谁先执行？
    • 答：在主模块里不确定。因为 setTimeout(fn, 0) 会被改成 1ms，事件循环启动的准备耗时是否超过 1ms 决定了进入 timers 时定时器有没有到期。但在 I/O 回调内部是确定的：一定是 setImmediate 先 —— 因为 I/O 回调在 poll 阶段执行，紧接着就是 check 阶段，而 timers 要等下一轮。
  2. 追问：process.nextTick 为什么优先级最高？滥用会有什么后果？
    • 答：它不属于事件循环的任何阶段，而是在每个阶段切换时被完全清空，且清空过程中新入队的也会一并执行。所以递归调用 nextTick 会饿死事件循环，I/O 永远得不到执行。库里需要"延迟到当前操作之后"的场景应该优先用 setImmediate。
  3. 追问：poll 阶段什么时候会阻塞？
    • 答：poll 队列为空时，如果有 setImmediate 待执行就立刻进 check；否则看最近的 timer 还有多久到期，阻塞到那个时刻；如果连 timer 都没有，就一直阻塞等新的 I/O 事件。这就是空闲 Node 进程 CPU 占用接近 0 的原因。
  4. 追问：Node 是单线程的，为什么能处理高并发？
    • 答：单线程指的是执行 JS 的线程只有一条。底层 libuv 对网络 I/O 用 epoll/kqueue 这种内核事件通知机制，一条线程可以管理上万连接；文件 I/O、DNS、zlib 则交给默认 4 条的线程池。所以 Node 擅长 I/O 密集，但一段 CPU 密集的同步代码会直接堵死整个服务。
  5. 追问：如果有一段 CPU 密集型计算，怎么办？
    • 答：拆成小块用 setImmediate 分片让出主线程；或者丢给 worker_threads（推荐用 piscina 这种线程池，避免频繁创建）；量大的话直接拆成独立服务或用 C++ addon / WASM 加速。

我在做 XX 服务的导出功能时踩过这个坑。原来是在接口里同步做大 JSON 的序列化和加密，QPS 一上来接口整体 RT 从 50ms 涨到 2s，火焰图看下来主线程被这段同步计算占满了。我们把加密部分迁到了 worker_threads 线程池里，并把序列化改成流式输出，RT 回落到 80ms 以内，而且 P99 的波动也明显变小。

题 2：Stream 有哪几种？什么是背压，怎么处理？ ​

精简口述答案：

Stream 有四类：Readable 可读流、Writable 可写流、Duplex 双工流（读写两条独立通道，比如 socket）、Transform 转换流（Duplex 的特例，输出由输入转换而来，比如 gzip、加解密）。

背压指的是生产速度大于消费速度时数据在内存里堆积。Writable 内部有个 highWaterMark 水位线，write() 返回 false 就代表缓冲区已满，此时调用方应该 pause() 暂停读取，等 Writable 触发 drain 事件再 resume()。pipe 内部已经实现了这套逻辑，所以手写 data 事件转发时最容易出问题。

但生产上我一定用 pipeline 而不是 pipe，因为 pipe 不会传递错误，中间任何一个流出错，其他流不会被销毁，会造成文件句柄和内存泄漏；pipeline 会统一回调错误并自动 destroy 所有流。

连环追问链：

  1. 追问：fs.readFile 和 fs.createReadStream 有什么区别，什么时候必须用流？
    • 答：readFile 把整个文件读进内存再回调，内存占用等于文件大小，且单个 Buffer 有上限（buffer.constants.MAX_LENGTH，64 位机约 4GB，老版本 2GB），超了直接抛错。流按 highWaterMark（文件流默认 64KB）分片，内存恒定，还能边读边处理降低首字节延迟。只要文件大小不可控（用户上传、日志、导出），就必须用流。
  2. 追问：highWaterMark 调大调小有什么影响？
    • 答：调大减少系统调用次数、吞吐更高，但单次内存占用和延迟变大；调小内存更省、响应更快，但系统调用频繁、CPU 开销上升。默认值是经验平衡值：文件流 64KB，object mode 下是 16 个对象。
  3. 追问：为什么流式读取中文会乱码？
    • 答：一个 UTF-8 中文占 3 字节，chunk 边界可能把它切开，单独 toString() 就得到「�」。要用 string_decoder 的 StringDecoder，它会把不完整的尾部字节缓存到下一次 write 再拼接。
  4. 追问：Transform 流怎么实现？_transform 里的 callback 必须调用吗？
    • 答：继承 Transform 实现 _transform(chunk, enc, cb)，用 this.push() 输出数据，处理完必须调 cb()，否则流会卡住不再读取下一个 chunk。另外还有 _flush(cb)，用于在流结束前把缓存的残余数据 push 出去（比如按行分割时的最后一行）。
  5. 追问：object mode 是什么？
    • 答：默认流只能传 Buffer/string，开 objectMode: true 后可以传任意 JS 对象，此时 highWaterMark 的单位从字节变成个数。常用于把数据库游标、CSV 行记录做成流水线处理。

✅ 项目关联话术（按真实经历替换）：

我们有个百万级数据导出 Excel 的需求，最初的实现是全量查库 → 内存里拼数组 → 生成文件返回，数据量一大就 OOM，容器被 OOMKilled。我重构成了流水线：数据库游标流 → Transform 转 CSV 行 → gzip → 响应流，全程用 pipeline 串起来并加了错误兜底。改完以后内存从峰值 1.5G 降到稳定 80M，导出 200 万行也不会挂，而且用户能立刻看到下载进度条动起来。

题 3：CommonJS 和 ES Module 有什么区别？ ​

精简口述答案：

核心区别有四点。第一，加载时机：CJS 是运行时同步加载，require 可以写在 if 里、拼接路径；ESM 是编译期静态分析依赖，import 必须在顶层，所以才能做 tree-shaking。第二，导出值的性质：CJS 导出的是值的拷贝（原始类型改了外部感知不到），ESM 导出的是引用绑定（live binding），模块内部变量变化外部能看到，而且导入的变量是只读的。第三，this 和内置变量：CJS 顶层 this 是 module.exports，有 __dirname、__filename、require；ESM 顶层 this 是 undefined，只有 import.meta.url。第四，循环依赖的表现：CJS 会拿到不完整的 exports，表现为 undefined；ESM 由于变量提升，函数能互相调用，但访问未初始化的 const/let 会抛 TDZ 错误。

连环追问链：

  1. 追问：为什么 exports = {...} 不生效，module.exports = {...} 就可以？
    • 答：因为模块包装函数的参数里，exports 只是 module.exports 的一个引用别名。给 exports 整体重新赋值只是改了局部变量的指向，真正被返回的 module.exports 没变。所以挂属性可以用 exports.a = 1，整体替换必须用 module.exports = ...。
  2. 追问：Node 里怎么区分一个文件是 CJS 还是 ESM？
    • 答：看三个依据：扩展名 .mjs 强制 ESM、.cjs 强制 CJS；.js 看最近的 package.json 里 "type" 字段，module 走 ESM，缺省或 commonjs 走 CJS。库的 exports 字段还能用条件导出给两种环境提供不同入口。
  3. 追问：两者能互相引用吗？
    • 答：ESM 里可以 import CJS，整个 module.exports 会作为 default 导出，具名导入靠 Node 的静态分析"尽力而为"，复杂场景可能失败。反过来 CJS 不能同步 require ESM（ESM 是异步加载的），只能用 await import() 动态导入。
  4. 追问：ESM 里怎么拿 __dirname？
    • 答：import { fileURLToPath } from 'url' 配合 path.dirname(fileURLToPath(import.meta.url))。Node 20.11+ 已经提供了 import.meta.dirname 和 import.meta.filename。
  5. 追问：require 的缓存机制是什么？怎么清缓存？
    • 答：每个模块第一次加载后，解析出的绝对路径作为 key 存进 require.cache，之后直接返回同一个 module.exports，这也是单例模式的实现基础。delete require.cache[require.resolve('./m')] 可以清掉，常用于单测和开发热更新。ESM 的模块缓存没有官方清除手段，只能用加 query 参数这种 hack。

✅ 项目关联话术（按真实经历替换）：

我们在把老项目迁到 ESM 时集中踩了这几个坑：__dirname 全部报未定义、几个只提供 CJS 的老依赖在 ESM 下具名导入失败、jest 的 mock 因为 ESM 静态分析失效。最后方案是先用 tsup 做双产物（同时输出 cjs 和 esm），内部代码统一 ESM 并用 import.meta.url 替换 __dirname，测试框架换成原生支持 ESM 的 vitest，平滑过渡完成。

题 4：进程和线程的区别？Node 里 cluster 和 worker_threads 怎么选？ ​

精简口述答案：

进程是操作系统资源分配的基本单位，有独立的内存空间；线程是 CPU 调度的基本单位，同一进程内的线程共享内存。所以进程间通信要走 IPC/socket，开销大但隔离性好；线程间可以共享内存，快但要处理竞态。

在 Node 里：cluster（多进程）用来利用多核扛 I/O 并发，它让多个 worker 进程共享同一个监听端口，主进程 accept 后按 round-robin 把连接句柄分发下去，适合 HTTP 服务横向扩展，一个 worker 崩了不影响其他。worker_threads（多线程）用来解决 CPU 密集型任务，它在同进程内创建独立的 V8 实例和事件循环，启动快、内存省，还能通过 SharedArrayBuffer 零拷贝共享数据。

选型原则：扛并发用 cluster 或者直接交给 pm2 / k8s 多副本；解决单个请求里的重计算用 worker_threads。

连环追问链：

  1. 追问：cluster 为什么多个进程 listen 同一个端口不报 EADDRINUSE？
    • 答：因为子进程的 listen 被 cluster 模块劫持了，它并没有真的 bind 端口，而是向主进程发消息，由主进程持有真正的 listening socket，accept 到连接后通过 IPC 把文件描述符传给子进程。Windows 下走的是另一套（句柄共享由系统调度），所以负载可能不均衡。
  2. 追问：cluster 下有什么东西是不能用的？
    • 答：所有依赖进程内状态的东西：内存缓存、express-session 的 MemoryStore、限流计数、全局自增 ID、定时任务。缓存和 session 必须外置到 Redis，定时任务要加分布式锁或只在主进程里跑，WebSocket 场景还需要 sticky session 或 Redis 适配器做跨进程广播。
  3. 追问：worker_threads 之间怎么传数据，有什么性能陷阱？
    • 答：默认用 postMessage，走结构化克隆，大对象的序列化开销很大。优化手段有两个：用 transferList 把 ArrayBuffer 的所有权转移（零拷贝，但原线程里就不能再用了）；或者用 SharedArrayBuffer 真正共享内存，配合 Atomics 做同步避免竞态。
  4. 追问：worker 数量开多少合适？
    • 答：CPU 密集任务按 os.cpus().length 来，开更多只会增加上下文切换。而且不要每个任务都 new Worker，创建成本在 10ms 量级，应该封装固定大小的线程池复用（可以直接用 piscina）。注意容器环境里 os.cpus() 返回的是宿主机核数，要读 cgroup 的 limit 或用 os.availableParallelism()。
  5. 追问：child_process 的 spawn / exec / execFile / fork 怎么区分？
    • 答：spawn 流式返回输出，适合大量输出的长任务；exec 起 shell 并一次性回调完整输出，有 1MB 的 maxBuffer 限制，且拼接用户输入有命令注入风险；execFile 不经过 shell，更安全；fork 是 spawn 的特例，专门跑 Node 脚本并自动建立 IPC 通道。

✅ 项目关联话术（按真实经历替换）：

我们的 Node BFF 服务原来是单进程，4 核的容器只用得上 1 核。改造时用 pm2 的 cluster 模式按核数起实例，吞吐直接提升了 3 倍多。但上线后发现两个问题：一是本地内存缓存命中率掉到 1/4，改成了 Redis；二是定时对账任务被执行了 4 次，加了只在 NODE_APP_INSTANCE === '0' 时启动的判断。另外有个海报合成的接口是 CPU 密集的，单独迁到了 worker 线程池里，避免它拖慢同进程的其他请求。

题 5：线上 Node 服务内存持续上涨，你怎么排查？ ​

精简口述答案：

我会按四步走。第一步确认现象：看监控里的 RSS 和 heapUsed 曲线，如果是阶梯式上涨且 GC 后不回落，基本可以确定是泄漏而不是正常波动；同时看 external 和 arrayBuffers，如果是这两项涨，说明是 Buffer 或 C++ 层对象没释放。

第二步抓快照：在压测环境或低峰期用 --inspect 连 Chrome DevTools，间隔几分钟打两次 heap snapshot，用 Comparison 视图按 size delta 排序，看哪个构造函数的实例数一直在涨。

第三步定位引用链：选中可疑对象看 Retainers，顺着引用链找到是哪个模块级变量或闭包在持有它。

第四步对症修复：最常见的四类来源是模块级 Map/数组无限增长（改成 LRU 并设上限和 TTL）、事件监听器没 off（尤其是在请求级别反复 on）、未清理的定时器和未关闭的流/连接、以及闭包意外捕获大对象。修完一定要回归压测对比内存曲线。

连环追问链：

  1. 追问：process.memoryUsage() 几个字段分别是什么意思？
    • 答：rss 是进程实际占用的物理内存总量；heapTotal/heapUsed 是 V8 堆的分配量和使用量；external 是 V8 管理的 C++ 对象内存；arrayBuffers 是 ArrayBuffer 和 Buffer 占用。Buffer 分配在堆外，所以 heapUsed 正常但 rss 飙高时要重点查 Buffer。
  2. 追问：MaxListenersExceededWarning 是什么原因？
    • 答：同一个 EventEmitter 上同一事件注册超过 10 个监听器时的告警。它是泄漏的强信号 —— 通常是在每次请求/每次循环里重复 on 却没 off。正确做法是用 once、在结束时 removeListener，确实需要多个才用 setMaxListeners 调高。
  3. 追问：Node 的内存上限是多少，怎么调？
    • 答：老生代默认约 1.5~2GB（新版本会根据系统内存自适应），用 --max-old-space-size=4096 调整。但调大只是缓解，如果是泄漏迟早还会满。容器里要注意这个值要小于容器的 memory limit，否则会先被 OOMKilled 而不是抛 JS 堆溢出错误。
  4. 追问：怎么发现是哪段代码阻塞了事件循环？
    • 答：监控事件循环延迟（perf_hooks 的 monitorEventLoopDelay，或用 setInterval 对比预期间隔），延迟高说明有同步阻塞。然后用 --prof + --prof-process 或 clinic flame 做 CPU 火焰图，找出占用最高的同步函数。
  5. 追问：AsyncLocalStorage 是干什么的？
    • 答：它基于 async_hooks，能在整条异步调用链上透传上下文，不需要把 traceId、用户信息一层层当参数传。典型用法是在中间件里 als.run({ traceId }, next)，之后任意深度的异步函数里 als.getStore() 都能拿到。日志串联、全链路追踪、多租户隔离都靠它。

✅ 项目关联话术（按真实经历替换）：

我们有次线上容器每隔两三天就被 OOMKilled 重启一次。排查时先从监控确认 heapUsed 是阶梯上涨的，然后在预发环境压测并打了两次 heap snapshot 对比，发现一个 Map 实例的 retained size 一直在涨 —— 是一个用来做接口防重的模块级 Map，只写不删。修复方案是换成带 TTL 和容量上限的 LRU，并把这类缓存统一挪到 Redis。同时我们补了事件循环延迟和内存的告警，这类问题现在能在影响用户之前就发现。

题 1：实现大文件拷贝（手动处理背压 + pipeline 版本） ​

核心实现：

const fs = require("fs");
const { pipeline } = require("stream/promises");

// 方案一：手动处理背压（面试要求手写时考这个）
function copyManual(src, dest) {
  return new Promise((resolve, reject) => {
    const rs = fs.createReadStream(src, { highWaterMark: 64 * 1024 });
    const ws = fs.createWriteStream(dest);

    rs.on("data", (chunk) => {
      // write 返回 false 表示写缓冲已超过 highWaterMark
      if (!ws.write(chunk)) rs.pause();
    });
    // 缓冲排空后恢复读取
    ws.on("drain", () => rs.resume());

    rs.on("end", () => ws.end());
    ws.on("finish", resolve);

    // 任一端出错，都要销毁另一端，避免句柄泄漏
    rs.on("error", (err) => {
      ws.destroy();
      reject(err);
    });
    ws.on("error", (err) => {
      rs.destroy();
      reject(err);
    });
  });
}

// 方案二：生产推荐 —— pipeline 自动处理背压 + 错误 + 销毁
async function copyBest(src, dest) {
  await pipeline(fs.createReadStream(src), fs.createWriteStream(dest));
}

// 方案三：带进度 + gzip 压缩的流水线
const zlib = require("zlib");
async function copyWithProgress(src, dest, onProgress) {
  const total = (await fs.promises.stat(src)).size;
  let done = 0;
  const rs = fs.createReadStream(src);
  rs.on("data", (c) => onProgress(((done += c.length) / total) * 100));
  await pipeline(rs, zlib.createGzip(), fs.createWriteStream(dest));
}

三个必须记住的点：

  1. write() 返回 false 就必须 pause()，等 drain 再 resume() —— 这是背压的全部。
  2. pipe 不传递错误也不销毁流，生产环境一律用 pipeline。
  3. 两端的 error 都要监听，Stream 的 error 未监听会直接抛成未捕获异常把进程干掉。

✅ 边界 Case 自测：

  • 源文件不存在 → rs 触发 error（ENOENT），需能被 reject 捕获
  • 目标目录不存在 → ws 触发 error（ENOENT），要销毁 rs
  • 磁盘写满 → ws 报 ENOSPC，检查是否正确清理了临时文件
  • 拷贝 0 字节空文件 → 不应触发 data，但 finish 必须正常触发
  • 拷贝 10GB 大文件 → 内存占用应恒定在 highWaterMark 量级
  • 拷贝过程中删除源文件 → Linux 下 fd 仍有效可继续读完，Windows 会报错
  • 中途主动 rs.destroy() → 确认目标文件被清理，没有残留半截文件

async function resumeCopy(src, dest) {
  let start = 0;
  try {
    start = (await fs.promises.stat(dest)).size;
  } catch {}
  await pipeline(
    fs.createReadStream(src, { start }),
    fs.createWriteStream(dest, { flags: "a" }) // 追加模式
  );
}

// 变种 3：分片并发拷贝（大文件多段并行，适合网络存储）
async function chunkCopy(src, dest, chunks = 4) {
  const { size } = await fs.promises.stat(src);
  const step = Math.ceil(size / chunks);
  await fs.promises.writeFile(dest, ""); // 预创建
  await Promise.all(
    Array.from({ length: chunks }, (_, i) => {
      const start = i * step;
      const end = Math.min(start + step - 1, size - 1);
      return pipeline(
        fs.createReadStream(src, { start, end }),
        fs.createWriteStream(dest, { start, flags: "r+" })
      );
    })
  );
}

const { Readable, Writable, Transform } = require("stream");

// ① 自定义可读流：把数组变成流
class ArrayReadable extends Readable {
  constructor(arr, opts) {
    super({ ...opts, objectMode: true });
    this.arr = arr;
    this.index = 0;
  }
  // 消费方需要数据时被调用，push(null) 表示结束
  _read() {
    if (this.index >= this.arr.length) return this.push(null);
    this.push(this.arr[this.index++]);
  }
}

// ② 自定义可写流：批量入库
class BatchWritable extends Writable {
  constructor(size = 100) {
    super({ objectMode: true });
    this.size = size;
    this.buf = [];
  }
  _write(chunk, enc, cb) {
    this.buf.push(chunk);
    if (this.buf.length < this.size) return cb(); // 攒够再落库
    this.flush().then(() => cb(), cb); // 错误通过 cb(err) 传出
  }
  // 流结束时调用，把残余数据写完
  _final(cb) {
    this.flush().then(() => cb(), cb);
  }
  async flush() {
    if (!this.buf.length) return;
    const rows = this.buf;
    this.buf = [];
    await db.batchInsert(rows);
  }
}

  constructor() {

  }
  _transform(chunk, enc, cb) {
    const lines = (this.tail + chunk.toString("utf8")).split("\n");
    this.tail = lines.pop(); // 最后一段可能不完整，留到下次
    for (const line of lines) this.push(line);
    cb(); // 必须调用，否则流卡死
  }
  // 流结束前把最后一行 push 出去
  _flush(cb) {
    if (this.tail) this.push(this.tail);
    cb();
  }
}

// 使用
const { pipeline } = require("stream/promises");
await pipeline(
  fs.createReadStream("big.log"),
  new LineSplitter(),
  new Writable({
    objectMode: true,
    write(line, enc, cb) {
      console.log("一行:", line);
      cb();
    },
  })
);

三个必须记住的点：

  1. _read 里 push(null) 结束流；_transform / _write 里必须调 cb()，不调就永久卡住。
  2. 跨 chunk 的不完整数据（半行、半个中文字符）必须自己缓存到下一次，并在 _flush / _final 里收尾。
  3. 异步错误用 cb(err) 往外传，不要直接 throw，否则无法被 pipeline 捕获。

✅ 边界 Case 自测：

  • 空输入 → 不应触发任何 push，但 finish 要正常触发
  • 文件不以 \n 结尾 → 最后一行必须由 _flush 补发，不能丢
  • 连续空行 \n\n\n → 应产出相应数量的空字符串，不要被静默吞掉
  • Windows 换行 \r\n → 需额外 trimEnd('\r')，否则每行尾部多个 \r
  • 单行超大（如 10MB 一行无换行）→ tail 会无限增长，需加长度上限保护
  • 中文被切断 → 用 StringDecoder 替代 chunk.toString() 才安全
  • 下游 cb(err) → 确认 pipeline 能 reject 且上游流被销毁

核心实现：

const fs = require("fs");
const path = require("path");
const vm = require("vm");

function Module(id) {
  this.id = id; // 模块绝对路径
  this.exports = {}; // 对外导出对象
  this.loaded = false;
}

Module._cache = Object.create(null);
Module._extensions = {
  ".js"(module) {
    const content = fs.readFileSync(module.id, "utf8");
    // 关键：用函数包装器隔离作用域，并注入 5 个变量
    const wrapper = Module.wrap(content);
    const fn = vm.runInThisContext(wrapper, { filename: module.id });
    const dirname = path.dirname(module.id);
    const require = Module.createRequire(module.id);
    // this 指向 module.exports —— 这就是 CJS 顶层 this 的来历
    fn.call(
      module.exports,
      module.exports,
      require,
      module,
      module.id,
      dirname
    );
  },
  ".json"(module) {
    module.exports = JSON.parse(fs.readFileSync(module.id, "utf8"));
  },
};

Module.wrap = (code) =>
  `(function (exports, require, module, __filename, __dirname) {\n${code}\n})`;

// 路径解析：补全扩展名、处理目录与 node_modules
Module._resolveFilename = function (request, parentId) {
  let filename = request.startsWith(".")
    ? path.resolve(path.dirname(parentId), request)
    : Module._resolveNodeModules(request, parentId);

  if (fs.existsSync(filename) && fs.statSync(filename).isFile())
    return filename;

  for (const ext of Object.keys(Module._extensions)) {
    if (fs.existsSync(filename + ext)) return filename + ext;
  }
  // 目录：先看 package.json 的 main，再退 index
  const pkg = path.join(filename, "package.json");
  if (fs.existsSync(pkg)) {
    const main = JSON.parse(fs.readFileSync(pkg, "utf8")).main;
    if (main)
      return Module._resolveFilename("./" + main, path.join(filename, "x"));
  }
  for (const ext of Object.keys(Module._extensions)) {
    const i = path.join(filename, "index" + ext);
    if (fs.existsSync(i)) return i;
  }
  throw new Error(`Cannot find module '${request}'`);
};

Module._resolveNodeModules = function (request, parentId) {
  let dir = path.dirname(parentId);
  while (true) {
    const p = path.join(dir, "node_modules", request);
    if (fs.existsSync(p)) return p;
    const parent = path.dirname(dir);
    if (parent === dir) break; // 到根目录了
    dir = parent;
  }
  throw new Error(`Cannot find module '${request}'`);
};

Module._load = function (request, parentId) {
  const filename = Module._resolveFilename(request, parentId);

  // ① 命中缓存直接返回（单例 + 循环依赖的基础）
  if (Module._cache[filename]) return Module._cache[filename].exports;

  const module = new Module(filename);
  // ② 关键：先写缓存再执行，循环依赖时拿到的是「半成品 exports」而不是死循环
  Module._cache[filename] = module;

  try {
    Module._extensions[path.extname(filename)](module);
    module.loaded = true;
  } catch (e) {
    delete Module._cache[filename]; // 加载失败要清缓存，否则下次拿到坏模块
    throw e;
  }
  return module.exports;
};

Module.createRequire = function (parentId) {
  const require = (request) => Module._load(request, parentId);
  require.cache = Module._cache;
  require.resolve = (r) => Module._resolveFilename(r, parentId);
  return require;
};

module.exports = Module.createRequire(path.join(process.cwd(), "__main__"));

三个必须记住的点：

  1. 先缓存再执行（_cache[filename] = module 在执行代码之前），这是循环依赖不死循环、但会拿到不完整 exports 的根本原因。
  2. 函数包装器注入 exports, require, module, __filename, __dirname 五个参数，且 fn.call(module.exports, ...) 让顶层 this === module.exports。
  3. 返回的是 module.exports 而非 exports 形参 —— 所以 exports = {} 整体赋值无效。

✅ 边界 Case 自测：

  • require('./a') 省略扩展名 → 按 .js → .json 顺序补全
  • require('./dir') → 读 package.json 的 main，缺失则退回 index.js
  • require('lodash') → 逐级向上查找 node_modules，到根目录仍无则报错
  • 同一模块 require 两次 → 只执行一次，两次拿到同一引用（可用计数器验证）
  • 循环依赖 a↔b → 不死循环，先加载方拿到对方的不完整 exports
  • 模块内 throw → 缓存必须被清除，重新 require 时能再次执行
  • require('./a.json') → 走 json 扩展处理，返回解析后的对象

核心实现：

// ① 手写 EventEmitter（Node 事件系统的核心）
class EventEmitter {
  constructor() {
    this._events = Object.create(null);
    this._maxListeners = 10;
  }

  on(type, fn) {
    (this._events[type] ||= []).push(fn);
    if (this._events[type].length > this._maxListeners) {
      console.warn(
        `MaxListenersExceededWarning: ${type} 超过 ${this._maxListeners} 个监听器`
      );
    }
    return this; // 支持链式调用
  }

  // 关键：用包装函数实现，且挂 listener 以便 off 时能匹配到原函数
  once(type, fn) {
    const wrapper = (...args) => {
      this.off(type, wrapper);
      fn.apply(this, args);
    };
    wrapper.listener = fn;
    return this.on(type, wrapper);
  }

  off(type, fn) {
    const arr = this._events[type];
    if (!arr) return this;
    this._events[type] = arr.filter((f) => f !== fn && f.listener !== fn);
    if (!this._events[type].length) delete this._events[type];
    return this;
  }

  emit(type, ...args) {
    const arr = this._events[type];
    // error 事件没有监听器时，Node 的行为是直接 throw
    if (!arr || !arr.length) {
      if (type === "error")
        throw args[0] instanceof Error ? args[0] : new Error("Unhandled error");
      return false;
    }
    // 必须拷贝一份：回调里可能 off 掉自己，直接遍历原数组会漏执行
    [...arr].forEach((fn) => fn.apply(this, args));
    return true;
  }

  listenerCount(type) {
    return this._events[type]?.length ?? 0;
  }
  removeAllListeners(type) {
    type ? delete this._events[type] : (this._events = Object.create(null));
    return this;
  }
  setMaxListeners(n) {
    this._maxListeners = n;
    return this;
  }
}

// ② 并发限制调度器（控制同时进行的异步任务数量）
class TaskPool {
  constructor(limit = 4) {
    this.limit = limit;
    this.running = 0;
    this.queue = [];
  }

  add(taskFn) {
    return new Promise((resolve, reject) => {
      this.queue.push({ taskFn, resolve, reject });
      this._next();
    });
  }

  _next() {
    while (this.running < this.limit && this.queue.length) {
      const { taskFn, resolve, reject } = this.queue.shift();
      this.running++;
      // 用 Promise.resolve 包裹，兼容同步函数和同步抛错
      Promise.resolve()
        .then(taskFn)
        .then(resolve, reject)
        .finally(() => {
          this.running--;
          this._next(); // 腾出位置，继续取下一个
        });
    }
  }
}

// 使用：同时最多 3 个请求
const pool = new TaskPool(3);
const results = await Promise.all(
  urls.map((u) => pool.add(() => fetch(u).then((r) => r.json())))
);

三个必须记住的点：

  1. once 要用包装函数并把原函数挂在 wrapper.listener 上，否则 off(type, 原函数) 匹配不到、无法移除。
  2. emit 遍历前必须拷贝监听器数组，防止回调中增删监听器导致遍历错乱。
  3. 调度器的 finally 里递减计数并递归取下一个任务；任务失败也要释放名额，否则池子会被逐渐占死。

✅ 边界 Case 自测：

  • emit('error') 无监听器 → 必须抛出，与 Node 行为一致
  • 同一函数 on 两次 → 执行两次；off 一次只移除一个
  • 回调里 off 掉自己 → 本轮其余监听器仍要全部执行
  • once 的回调里再次 emit 同事件 → 不应重复执行（已被移除）
  • 调度器中任务 reject → 名额必须释放，后续任务能继续执行
  • limit 大于任务总数 → 全部立即并发，不应卡住
  • 任务函数同步 throw → 应被转成 reject，不能变成未捕获异常
  • 空队列调用 _next() → 不报错、不死循环

// 变种 4：worker_threads 线程池（CPU 密集任务复用线程）
const os = require("os");
const { Worker } = require("worker_threads");
class WorkerPool {
  constructor(file, size = os.availableParallelism?.() ?? os.cpus().length) {
    this.idle = Array.from({ length: size }, () => new Worker(file));
    this.queue = [];
  }
  run(data) {
    return new Promise((resolve, reject) => {
      this.queue.push({ data, resolve, reject });
      this._dispatch();
    });
  }
  _dispatch() {
    if (!this.idle.length || !this.queue.length) return;
    const worker = this.idle.pop();
    const { data, resolve, reject } = this.queue.shift();
    const done = (fn) => (v) => {
      worker.removeAllListeners("message");
      worker.removeAllListeners("error");
      this.idle.push(worker); // 归还线程
      fn(v);
      this._dispatch();
    };
    worker.once("message", done(resolve));
    worker.once("error", done(reject));
    worker.postMessage(data);
  }
  destroy() {
    this.idle.forEach((w) => w.terminate());
  }
}

常见坑解决方案
❌ 用 fs.readFile 读大文件导致容器 OOM 被 kill✅ 文件大小不可控时一律用 createReadStream + pipeline，内存恒定在 highWaterMark 量级
❌ Stream 没监听 error，一次 ENOENT 就把进程打挂✅ 每个流都要有 error 处理；更省事的办法是统一用 pipeline 做兜底
❌ 用 pipe 串流水线，中途报错后文件句柄泄漏✅ pipe 不传递错误也不销毁流，生产代码改用 stream/promises 的 pipeline
❌ 手写 rs.on('data', c => ws.write(c)) 内存暴涨✅ 判断 write() 返回值，为 false 时 rs.pause()，等 drain 再 resume()
❌ 流式读取日志出现乱码「�」✅ 中文被 chunk 边界截断，用 string_decoder 的 StringDecoder 缓存残缺字节
❌ exports = { foo } 导出后外部拿到空对象✅ exports 只是形参别名，整体替换必须写 module.exports = { foo }
❌ 循环依赖里拿到的属性是 undefined✅ CJS 先缓存再执行，拿到的是半成品 exports；把 require 延后到函数内部，或抽公共模块打破环
❌ 迁 ESM 后 __dirname is not defined✅ 用 path.dirname(fileURLToPath(import.meta.url))，Node 20.11+ 可直接用 import.meta.dirname
❌ package.json 加了 "type": "module" 后老文件全报错✅ 把 CJS 文件改名 .cjs，或拆成子目录单独放一个 {"type":"commonjs"} 的 package.json
❌ CJS 里 require 一个 ESM 包报 ERR_REQUIRE_ESM✅ 改用 await import() 动态导入，或找该包的 CJS 版本/双产物
❌ Buffer.allocUnsafe 写接口返回体里混进了别人的数据✅ 未清零内存可能残留敏感信息，不确定会被完全覆写时用 Buffer.alloc
❌ buf.slice() 改了一处，原 Buffer 也跟着变了✅ slice/subarray 是共享内存的视图，要真拷贝得用 Buffer.from(buf.subarray(...))
❌ 长期缓存大量小 Buffer，内存占用远超预期✅ 池化的小 Buffer 会持有整块 8KB，长期持有改用 Buffer.allocUnsafeSlow 或做一次真拷贝
❌ 递归 process.nextTick 后服务不响应请求了✅ nextTick 在每个阶段结束被完全清空，会饿死事件循环；需要让出控制权时用 setImmediate
❌ 断言 setTimeout(fn,0) 一定比 setImmediate 先✅ 主模块里顺序不确定；只有在 I/O 回调内部才保证 setImmediate 先执行
❌ 一段大 JSON 的 JSON.parse 把整个服务卡死 2 秒✅ 同步 CPU 操作会阻塞事件循环，改用流式解析（如 JSONStream）或丢给 worker 线程
❌ 并发读写上百个文件，耗时呈阶梯状递增✅ 文件 I/O 走 libuv 线程池，默认只有 4 条；在 require 任何模块前设置 UV_THREADPOOL_SIZE
❌ crypto.pbkdf2 和文件读写互相拖慢✅ 它们抢同一个线程池，高频加解密应独立进程/线程，或调大线程池
❌ process.exit(0) 后日志和落库丢了一半✅ exit 不等待异步，改设 process.exitCode 让事件循环自然结束，或在 beforeExit 里收尾
❌ 一个 unhandledRejection 让进程静默退出✅ Node 15+ 默认视为未捕获异常，必须注册 unhandledRejection / uncaughtException 兜底并记录后重启
❌ 收到 SIGTERM 立刻退出，存量请求全部 502✅ 优雅退出：server.close() 停止新连接 → 等存量请求完成 → 关连接池 → 退出
❌ 上 cluster 后缓存命中率骤降、session 掉登录✅ 进程间不共享内存，缓存与 session 外置到 Redis
❌ cluster 下定时任务被执行了 N 次✅ 只在主进程或 NODE_APP_INSTANCE === '0' 时启动，或用分布式锁
❌ 每个请求都 new Worker，QPS 反而更低了✅ 线程创建成本在 10ms 量级，封装固定大小线程池复用（或直接用 piscina）
❌ worker 之间传大对象，序列化开销比计算还大✅ 用 transferList 转移 ArrayBuffer 所有权，或用 SharedArrayBuffer + Atomics 零拷贝
❌ 容器里 os.cpus().length 返回宿主机核数，线程开爆✅ 用 os.availableParallelism() 或读取 cgroup 的 CPU limit
❌ 单测之间互相污染，模块状态被带到下一个用例✅ delete require.cache[require.resolve(path)]，或用 jest.resetModules() / vitest 的隔离
❌ 控制台一直刷 MaxListenersExceededWarning✅ 请求级别重复 on 未 off 的典型泄漏，改用 once 或结束时 removeListener
❌ --max-old-space-size 调得比容器内存还大✅ 结果是先被 OOMKilled 而非抛 JS 堆溢出，该值必须小于容器 limit
