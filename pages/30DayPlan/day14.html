Day14 Spring 核心：IOC、AOP、Bean 生命周期、循环依赖 ​

📖 基础知识讲解【基础原理 + 高级深挖知识点】 ​

基础原理 ​

1. 全景：没有 Spring 的世界长什么样 ​

面试问「Spring 解决了什么问题」，背「解耦」三个字是不够的。真正要讲清的是：手动 new 对象时，到底出现了哪三类无法消除的痛点。

text
【无 Spring 时代】
UserController
   │  new UserServiceImpl()            ← 痛点1：编译期写死实现类，换实现要改代码
   ▼
UserServiceImpl
   │  new UserDaoImpl(new DataSource(url, user, pwd))
   ▼                                   ← 痛点2：依赖链越深，装配代码越长
UserDaoImpl
   │  手写 try/catch + conn.commit() + conn.rollback()
   ▼                                   ← 痛点3：事务/日志/权限代码散落在每个方法里

【有 Spring 时代】
          Spring 容器（IOC Container）
                │ 读配置 → 生成 BeanDefinition → 实例化 → 注入 → 初始化
                ▼
   ┌ 负责"造对象 + 连对象"：IOC / DI 解决痛点 1、2
   └ 负责"给对象加能力"：AOP 解决痛点 3
                │
                ▼
UserController ← 注入 ← UserService 代理 ← 注入 ← UserDao

一句话总结：Spring 核心就两件事 —— IOC 管对象的"生与连"，AOP 管对象的"增与强"。Bean 生命周期是 IOC 的执行细节，循环依赖是 IOC 的疑难杂症，事务是 AOP 最典型的落地产物。

为什么面试必考这四块？ 因为它们串成一条完整因果链：

知识点在链路中的位置不懂它会在线上踩什么坑
IOC / DI对象从哪来、怎么连上注入了接口的错误实现、@Autowired 歧义启动失败
Bean 生命周期对象从创建到可用中间经过哪些钩子在构造器里用注入的字段 → NPE；初始化顺序错乱
AOP对象被容器悄悄换成了代理自调用事务失效、切面不生效、代理类型转换异常
循环依赖IOC 装配顺序打结时容器怎么自救Spring Boot 2.6+ 启动直接报 BeanCurrentlyInCreationException

2. IOC 控制反转：到底"反转"了什么 ​

很多人把 IOC 和 DI 混为一谈。准确说法是：IOC 是一种设计思想（目标），DI 是实现这种思想的手段。

📌 单独澄清：反转的是"控制权"，不是"创建动作"

对象终究还是要被 new 出来的，Spring 底层也是走反射调构造器。IOC 反转的是**"谁来决定什么时候 new、new 哪个实现、new 完连给谁"**这个决策权。

维度传统方式（控制权在业务代码）IOC 方式（控制权在容器）
谁决定创建时机业务代码执行到 new 那一行容器启动阶段（单例）或 getBean 时（多例）
谁决定用哪个实现类代码里写死 new UserServiceImpl()配置 / 注解 / 条件装配决定
谁负责装配依赖调用方手动一层层传进去容器递归解析依赖图自动注入
换实现的成本改源码 + 重新编译改配置或换一个 @Service 实现
java
// ❌ 控制权在自己手上：UserController 必须"认识"具体实现类
public class UserController {
    // 编译期依赖 UserServiceImpl，换成 UserServiceMockImpl 就得改这一行
    private UserService userService = new UserServiceImpl(new UserDaoImpl());
}

// ✅ 控制权交给容器：UserController 只声明"我需要一个 UserService"
@RestController
public class UserController {
    private final UserService userService;           // 只依赖接口
    public UserController(UserService userService) { // 容器在实例化时把实现塞进来
        this.userService = userService;
    }
}

DI 依赖注入的三种形态（下一节细讲差异）：

text
构造器注入  → 依赖作为构造参数传入，对象"出生即完整"
setter 注入 → 先无参造出对象，再调 setXxx() 填充
字段注入    → 直接反射写字段（@Autowired 打在 field 上），无需 setter

DL 依赖查找（Dependency Lookup）也属于 IOC：主动调 context.getBean(XxxService.class) 去"捞"对象。它和 DI 的区别是——DI 是"等别人喂"，DL 是"自己伸手拿"。业务代码优先用 DI，只有在工厂/策略路由这类运行时才知道类名的场景才用 DL。

3. 容器体系：BeanFactory、ApplicationContext、FactoryBean ​

这三个名字长得像，是面试故意设的坑，必须一次分清。

text
BeanFactory（IOC 容器的顶层接口，只定义"能取 Bean"这件事）
   │
   ├─ ListableBeanFactory      → 能按类型批量取：getBeansOfType()
   ├─ HierarchicalBeanFactory  → 支持父子容器：getParentBeanFactory()
   ├─ AutowireCapableBeanFactory → 能给"容器外的对象"做依赖注入
   │
   └─ ApplicationContext（子接口，在 BeanFactory 之上叠企业级能力）
         ├─ MessageSource              → 国际化
         ├─ ApplicationEventPublisher  → 事件发布
         ├─ ResourcePatternResolver    → 资源加载（classpath*: 通配）
         └─ EnvironmentCapable         → 环境 / Profile / 配置属性
              │
              ├─ ClassPathXmlApplicationContext      （XML 配置）
              ├─ AnnotationConfigApplicationContext  （注解配置）
              └─ AnnotationConfigServletWebServerApplicationContext（Spring Boot Web）
对比项BeanFactoryApplicationContext
定位基础 IOC 容器，功能最小集BeanFactory 的超集，面向应用的"完整容器"
加载策略懒加载，getBean() 时才实例化启动时 refresh() 预实例化所有非懒加载单例
扩展点注册需手动调用注册 BeanPostProcessor自动发现并注册所有 BeanPostProcessor
附加能力无国际化、事件、资源、Environment、AOP 自动代理
错误暴露时机运行时取 Bean 才报错启动即报错（配置写错当场挂，线上更安全）
实际使用几乎只作为内部引擎（DefaultListableBeanFactory）业务开发实际接触的就是它

关键认知：ApplicationContext 并不自己存 Bean，它内部组合了一个 DefaultListableBeanFactory 做真正的仓库，自己只做"门面 + 增强"。所以说 ApplicationContext「继承 BeanFactory 接口、组合 BeanFactory 实现」。

📌 单独澄清：FactoryBean 和 BeanFactory 完全是两回事

维度BeanFactoryFactoryBean
它是什么容器本身容器里的一个普通 Bean，但它是个"生产其他 Bean 的工厂"
解决什么问题统一管理所有 Bean某个 Bean 创建过程很复杂（需大量逻辑），交给工厂定制
取值行为getBean("a") 返回 agetBean("myFb") 返回 getObject() 的结果；加 & 前缀 getBean("&myFb") 才返回工厂自己
典型使用者Spring 内核MyBatis 的 MapperFactoryBean、Spring 的 ProxyFactoryBean
java
// FactoryBean 实战：MyBatis 的 Mapper 接口没有实现类，靠 FactoryBean 产出代理
@Component("userMapperFactory")
public class UserMapperFactoryBean implements FactoryBean<UserMapper> {
    @Override
    public UserMapper getObject() {
        // 这里可以写任意复杂的创建逻辑：动态代理、读远端配置、按环境切换实现
        return (UserMapper) Proxy.newProxyInstance(
                getClass().getClassLoader(),
                new Class[]{UserMapper.class},
                (proxy, method, args) -> executeSql(method, args));
    }
    @Override
    public Class<?> getObjectType() { return UserMapper.class; }
    @Override
    public boolean isSingleton() { return true; }
    private Object executeSql(Method m, Object[] args) { /* 省略 */ return null; }
}

// 使用方感知不到工厂的存在，拿到的直接是 UserMapper
@Autowired private UserMapper userMapper;              // ✅ 实际是 getObject() 的返回值
@Autowired @Qualifier("&userMapperFactory")
private FactoryBean<UserMapper> rawFactory;            // ✅ 加 & 才拿到工厂本体

4. BeanDefinition：Bean 在容器里的"身份证" ​

Spring 不是直接"读到注解就造对象"，中间一定有一层元数据描述。这层就是 BeanDefinition，它是理解 Spring 启动流程的关键抽象。

text
配置来源（三种殊途同归）
   ├─ XML： <bean id="userService" class="..."/>
   ├─ 注解：@Component / @Service / @Bean
   └─ 编程式：registry.registerBeanDefinition(...)
          │
          ▼  各类 BeanDefinitionReader / ClassPathBeanDefinitionScanner 解析
   BeanDefinition（一个 Bean 的"配置清单"）
          ├─ beanClass        要造哪个类
          ├─ scope            singleton / prototype / request...
          ├─ lazyInit         是否懒加载
          ├─ primary          是否为同类型首选
          ├─ dependsOn        必须先造好哪些 Bean
          ├─ initMethodName / destroyMethodName
          ├─ constructorArgumentValues  构造参数
          └─ propertyValues   属性值
          │
          ▼  注册进 beanDefinitionMap（Map<String, BeanDefinition>）
   DefaultListableBeanFactory
          │
          ▼  finishBeanFactoryInitialization() 遍历，按清单造对象
   真正的 Bean 实例 → singletonObjects（单例池）

记住这条分界线：BeanDefinition 注册完成 ≠ Bean 创建完成。BeanFactoryPostProcessor 作用在"清单阶段"（还能改配置），BeanPostProcessor 作用在"实例阶段"（只能改对象）。这是高级深挖里最常考的区分点。

java
// 编程式注册 BeanDefinition：Spring Boot 很多自动配置就是这么干的
public class MyRegistrar implements ImportBeanDefinitionRegistrar {
    @Override
    public void registerBeanDefinitions(AnnotationMetadata meta,
                                        BeanDefinitionRegistry registry) {
        AbstractBeanDefinition bd = BeanDefinitionBuilder
                .genericBeanDefinition(UserServiceImpl.class)
                .setScope(BeanDefinition.SCOPE_SINGLETON)
                .setLazyInit(false)
                .addPropertyValue("timeout", 3000)
                .getBeanDefinition();
        registry.registerBeanDefinition("userService", bd);
    }
}

5. 依赖注入三种方式：为什么官方只推荐构造器注入 ​

注入方式写法能否 final循环依赖单测友好度Spring 官方态度
构造器注入构造参数（单构造器可省 @Autowired）✅ 可以❌ 无法解决，启动报错✅ 直接 new 传 mock强烈推荐
setter 注入@Autowired 打在 setXxx() 上❌ 不行✅ 三级缓存可解✅ 可手动 set可选依赖时推荐
字段注入@Autowired 直接打在字段上❌ 不行✅ 三级缓存可解❌ 需反射或 Spring 上下文不推荐（IDEA 会警告）
java
// ✅ 推荐：构造器注入 —— 依赖不可变、不可为 null、易测试
@Service
public class OrderService {
    private final UserService userService;
    private final StockService stockService;
    // Spring 4.3+ 只有一个构造器时可以不写 @Autowired
    public OrderService(UserService userService, StockService stockService) {
        this.userService = userService;
        this.stockService = stockService;
    }
}

//❌ 不推荐：字段注入 —— 三个隐患
@Service
public class OrderServiceBad {
    @Autowired private UserService userService;  // 1. 不能 final，运行期可被反射改
    @Autowired private StockService stockService;// 2. 脱离 Spring 无法 new 出可用对象
    // 3. 依赖可以无限加而代码看不出"这个类太重了"，掩盖了设计问题
}

📌 单独澄清：构造器注入"解决不了"循环依赖，恰恰是它的优点

问题字段 / setter 注入构造器注入
遇到循环依赖容器用三级缓存悄悄兜住，程序能跑起来启动直接失败并打印依赖环
后果环一直在，某天加个 AOP / @Async 就爆炸第一天就被迫重新设计，环被消灭在源头
口诀"能跑但有病""跑不起来但健康"
java
// ❌ 这种环在字段注入下能启动成功，但本质是设计问题
@Service class A { @Autowired B b; }
@Service class B { @Autowired A a; }

// ✅ 正确做法不是换注入方式，而是抽出公共逻辑打破环
@Service class A { private final C c; A(C c){ this.c = c; } }
@Service class B { private final C c; B(C c){ this.c = c; } }
@Service class C { /* A、B 共用的那部分能力放这里 */ }

6. 自动装配与歧义解决：一个接口多个实现怎么办 ​

容器按类型找 Bean 时，如果找到多个候选者，会抛 NoUniqueBeanDefinitionException。解决手段有五种，优先级要记清。

text
@Autowired 解析流程
  1. 按类型 byType 找候选集合
  2. 候选只有 1 个  → 直接注入
  3. 候选 > 1 个    → 依次尝试：
        ① @Primary 标记的候选
        ② @Priority(数字小的优先)
        ③ 字段名 / 参数名 与 beanName 匹配（byName 兜底）
        ④ 都失败 → 抛 NoUniqueBeanDefinitionException
  4. 候选 0 个       → required=true 抛 NoSuchBeanDefinitionException
                      required=false 或 Optional<T> 注入 null / empty
手段作用适用场景
@Primary标记默认实现有一个明确的"主力实现"
@Qualifier("beanName")注入点指定具体 Bean不同调用方要不同实现
字段名与 beanName 一致利用 byName 兜底临时解法，可读性差，不推荐依赖
@Resource(name = "xxx")JSR-250 注解，默认按名称遗留代码常见
注入 List<T> / Map<String,T>一次性拿到全部实现策略模式 / 责任链
java
public interface PayService { String channel(); void pay(long amount); }

@Service("aliPay") @Primary
class AliPayService implements PayService { public String channel(){ return "ALI"; } ... }

@Service("wxPay")
class WxPayService implements PayService { public String channel(){ return "WX"; } ... }

// ✅ 场景1：要默认实现 → 直接注入，@Primary 生效，拿到 aliPay
@Service
class OrderA { private final PayService payService;
    OrderA(PayService payService){ this.payService = payService; } }

// ✅ 场景2：要指定实现 → @Qualifier 精确点名
@Service
class OrderB { private final PayService payService;
    OrderB(@Qualifier("wxPay") PayService payService){ this.payService = payService; } }

// ✅ 场景3：策略路由 → 注入 Map，key 自动是 beanName，彻底消灭 if-else
@Service
class PayRouter {
    private final Map<String, PayService> strategies;   // {aliPay=..., wxPay=...}
    PayRouter(Map<String, PayService> strategies){ this.strategies = strategies; }
    void pay(String channel, long amount) {
        strategies.values().stream()
                .filter(s -> s.channel().equals(channel))
                .findFirst()
                .orElseThrow(() -> new IllegalArgumentException("未知渠道"))
                .pay(amount);
    }
}

7. AOP 基础：七大术语 + 五种通知 + 执行顺序 ​

AOP 的术语密度极高，背散装定义很容易混。把它们放进一次方法调用的时间轴上就清楚了。

text
目标对象 TargetObject：UserService 真身（被增强的那个对象）
   │
   ▼  容器用 Weaving 织入，产出 →
代理对象 Proxy：UserService$$Proxy（调用方实际拿到的东西）
   │
   ▼  调用 proxy.createUser()
JoinPoint 连接点：程序执行中"可以被拦截"的那个点（Spring AOP 里只有"方法调用"）
   │
   ▼  Pointcut 切点：一个表达式，筛选出"我要拦哪些 JoinPoint"
Advice 通知：筛中以后"做什么"（下面五种）
   │
Aspect 切面 = Pointcut（拦哪里）+ Advice（做什么），打包成一个类
   │
Introduction 引介：给目标类动态加新接口/新方法（极少用）
通知类型注解执行时机能否阻止目标方法执行能否改返回值
前置通知@Before目标方法执行前❌（只能抛异常中断）❌
后置返回通知@AfterReturning目标方法正常返回后❌❌（只能读）
异常通知@AfterThrowing目标方法抛异常后❌❌
最终通知@After无论正常还是异常，一定执行❌❌
环绕通知@Around包裹整个调用，前后都能插代码✅ 不调 proceed() 即可✅

单切面执行顺序（Spring 5.2.7 之后已修正为符合直觉的顺序）：

text
进入代理方法
  ├─ @Around 前半段（proceed() 之前的代码）
  ├─ @Before
  ├─── 执行目标方法 ───┐
  │                    ├─ 正常返回 → @AfterReturning
  │                    └─ 抛出异常 → @AfterThrowing
  ├─ @After（finally 语义，必执行）
  └─ @Around 后半段（proceed() 之后的代码）
退出代理方法

多切面顺序：用 @Order 控制，数字小的"外层"，形成责任链。

text
@Order(1) 日志切面   ── 进 ──┐
  @Order(2) 事务切面 ── 进 ──┐│
    @Order(3) 缓存切面 ─ 进 ─┐││
      目标方法                │││
    缓存切面 ── 出 ───────────┘││
  事务切面 ── 出 ─────────────┘│
日志切面 ── 出 ────────────────┘

切点表达式常用写法（面试会让你现场写）：

java
// execution：最常用，按方法签名匹配
@Pointcut("execution(public * com.xxx.service..*.*(..))")   // service 包及子包所有公有方法

11. 循环依赖与三级缓存 ​

什么是循环依赖：A 依赖 B，B 又依赖 A（也可能是 A→B→C→A 的长环，甚至 A→A 的自依赖）。容器创建 A 时要先造 B，造 B 时又要回头拿 A，形成死锁式递归。

哪些能解、哪些不能解：

场景能否解决原因
单例 + setter/字段注入✅实例化与属性填充分离，可提前暴露半成品
单例 + 构造器注入❌实例化阶段就要依赖对象，没有"半成品"可暴露
单例 + 构造器注入 + @Lazy✅@Lazy 注入的是代理，真正调用时才去容器取真身
prototype 作用域❌多例不进缓存，无从暴露；直接抛 BeanCurrentlyInCreationException
@Async / 部分 AOP 场景⚠️ 部分失败代理在初始化后才生成，早期暴露的引用与最终代理不一致 → 抛错
Spring Boot 2.6+ 默认配置❌ 默认禁止需显式开 spring.main.allow-circular-references=true

三级缓存结构（都在 DefaultSingletonBeanRegistry 里）：

缓存级别类型存什么
singletonObjects一级Map<String, Object>完整可用的单例 Bean
earlySingletonObjects二级Map<String, Object>提前暴露的半成品（可能已是代理）
singletonFactories三级Map<String, ObjectFactory<?>>生产半成品的工厂（决定给真身还是代理）

查找顺序永远是：一级 → 二级 → 三级（getSingleton 方法里逐级下探，三级命中后把结果升到二级并移除三级）。

完整推演：A ⇄ B 字段注入

text
getBean(A)
 ├ 一/二/三级缓存都没有 A
 ├ 标记 A 为"创建中"：singletonsCurrentlyInCreation.add("a")
 ├ ② 实例化 A（堆上有了 a 对象，字段 b = null）
 ├ ④ 把 ObjectFactory 放进三级缓存：singletonFactories["a"] = () -> getEarlyBeanReference(a)

       ├ 缓存都没有 B
       ├ 标记 B 为"创建中"
       ├ ② 实例化 B（字段 a = null）
       ├ ④ singletonFactories["b"] = () -> getEarlyBeanReference(b)
       └ ⑤ 填充 B 的属性，发现需要 A → getBean(A)
             ├ 一级没有 → 二级没有 → 三级命中！
             ├ 执行工厂 getEarlyBeanReference(a)
             │    ├ 若 A 需要 AOP → 此刻提前创建代理，返回 proxyA
             │    └ 否则直接返回原始 a
             ├ 把结果放入二级缓存，从三级移除（保证多次取到同一个对象）

📌 单独澄清：为什么必须是三级，两级不够吗？

这是本节最高频的追问。关键在于**"要不要代理"这个决定必须延迟到真正有人来取的那一刻**。

方案做法问题
只要一级半成品和成品都放 singletonObjects别人可能拿到字段还没填完的 Bean，无法区分完整与否
两级实例化后立即创建代理放进二级缓存所有 Bean 不管有没有循环依赖，都被迫提前代理，破坏了"AOP 在初始化后织入"的生命周期约定
三级（现方案）只放工厂，有人来取时才决定返回真身还是代理无循环依赖时工厂永远不被调用，零额外开销；有循环依赖时才提前代理
java
// 三级缓存里放的工厂，本质是这一行（AbstractAutowireCapableBeanFactory）
addSingletonFactory(beanName, () -> getEarlyBeanReference(beanName, mbd, bean));

// getEarlyBeanReference 的核心逻辑
protected Object getEarlyBeanReference(String beanName, RootBeanDefinition mbd, Object bean) {
    Object exposedObject = bean;
    for (BeanPostProcessor bp : getBeanPostProcessors()) {
        if (bp instanceof SmartInstantiationAwareBeanPostProcessor sibp) {
            // AOP 的 AbstractAutoProxyCreator 在这里提前把代理造出来
            exposedObject = sibp.getEarlyBeanReference(exposedObject, beanName);
        }
    }
    return exposedObject;   // 没有切面匹配时，原样返回真身
}

那二级缓存是干嘛的？ 两个作用，缺一不可：

  1. 保证"同一性"：如果只有一三级，B 和 C 都依赖 A 时，工厂会被调用两次 → 产生两个不同的代理对象，单例语义被破坏。命中三级后立刻升到二级，后续全部走二级，保证只有一个。
  2. 避免重复执行工厂逻辑：代理创建是有成本的，没必要重复做。

一句话背诵版：一级存成品、二级存半成品、三级存工厂；三级解决"代理对象的提前生成"，二级解决"提前生成的对象只能有一份"。

    @Bean public A a(B b) { return new A(b); }   // 参数由容器解析，不要手动调 b()

5. @Transactional 失效的七种场景 ​

事务是 AOP 最典型的落地，失效原因基本都能归到"没走代理"或"异常没被识别"两类。

失效场景根因修复方式
① 同类内部 this.method() 自调用没经过代理对象注入自己 / AopContext.currentProxy() / 拆到另一个类
② 方法不是 publicSpring 默认只拦 public（CGLIB 无法覆写 private）改为 public
③ 方法或类是 final / staticCGLIB 无法覆写去掉 final，改为实例方法
④ 异常被 try/catch 吞掉代理层感知不到异常，照常 commit抛出异常，或手动 setRollbackOnly()
⑤ 抛出的是受检异常（Exception）默认只对 RuntimeException + Error 回滚@Transactional(rollbackFor = Exception.class)
⑥ 数据库引擎不支持事务（MyISAM）存储引擎层面没有事务改 InnoDB
⑦ 多线程 / 异步里执行 DB 操作事务绑定在 ThreadLocal，子线程拿不到连接子线程内部自己开事务，或改用消息/补偿

// ❌ 场景①+④ 双重失效的经典写法
@Service
public class OrderServiceBad {
    public void createOrder(Order o) {
        try {
            this.saveAndDeduct(o);      // ① this 调用，事务注解完全无效
        } catch (Exception e) {

        }
    }
    @Transactional
    public void saveAndDeduct(Order o) { orderDao.insert(o); stockDao.deduct(o); }
}

// ✅ 正确：事务入口在外层、让异常往外抛、跨类调用走代理

    private final OrderTxService txService;     // 拆到另一个 Bean
    public OrderServiceGood(OrderTxService txService) { this.txService = txService; }

    public void createOrder(Order o) {
        txService.saveAndDeduct(o);   // 跨 Bean 调用→ 走代理 → 事务生效
    }
}

@Service
public class OrderTxService {

Spring Boot 自动配置的"大脑"，面试常问「自动配置怎么做到按需生效」。

13. 单例 Bean 中安全使用请求级状态：ThreadLocal 与作用域代理 ​

// 方案 A：ThreadLocal —— 自己管，务必 finally remove，否则线程池复用导致脏数据 + 泄漏
public class UserContext {
    private static final ThreadLocal<Long> HOLDER = new ThreadLocal<>();
    public static void set(Long id) { HOLDER.set(id); }
    public static Long get() { return HOLDER.get(); }
    public static void clear() { HOLDER.remove(); }      // ★ 必须调
}

@Component
public class UserInterceptor implements HandlerInterceptor {
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object h) {
        UserContext.set(Long.valueOf(req.getHeader("uid")));
        return true;
    }
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res,
                                Object h, Exception e) {
        UserContext.clear();        // 不清就会被下一个请求读到上一个用户的 id
    }
}

// 方案 B：request 作用域 + 作用域代理 —— 交给容器管，单例里可直接注入
@Component
@Scope(value = WebApplicationContext.SCOPE_REQUEST,
       proxyMode = ScopedProxyMode.TARGET_CLASS)   // ★ 没有这行，单例无法注入 request Bean
public class RequestContext {
    private Long userId;
    public Long getUserId(){ return userId; }
    public void setUserId(Long id){ this.userId = id; }
}

    public ReportService(RequestContext rc){ this.requestContext = rc; }
}

题 1：什么是 IOC 和 DI？BeanFactory 和 ApplicationContext 有什么区别？ ​

精简口述答案（90 秒版）

IOC 控制反转是一种设计思想，反转的是"对象创建时机、实现类选择、依赖装配"这三项控制权，从业务代码交给容器。注意它反转的是控制权，不是取消创建动作，底层仍然是反射调构造器。

DI 依赖注入是 IOC 最主流的实现手段，分构造器、setter、字段三种；另一种实现手段是 DL 依赖查找，也就是主动 getBean。

BeanFactory 是 IOC 容器的顶层接口，只提供最基础的「按名/按类型取 Bean」，而且是懒加载，getBean 时才实例化。ApplicationContext 是它的子接口，在此之上叠了国际化、事件发布、资源加载、Environment 四大企业级能力，并且启动时就预实例化所有非懒加载单例，配置写错在启动阶段就暴露，线上更安全。

实际结构上，ApplicationContext 并不自己存 Bean，而是组合了一个 DefaultListableBeanFactory 当仓库，自己做门面和增强。

连环追问链

追问答题要点
FactoryBean 和 BeanFactory 的区别？BeanFactory 是容器本身；FactoryBean 是容器里的一个普通 Bean，但它负责生产别的 Bean。getBean("x") 拿到的是 getObject() 结果，加 & 前缀才拿到工厂本体。MyBatis 的 Mapper 代理就靠它

题 2：Spring AOP 的底层原理？JDK 动态代理和 CGLIB 有什么区别？哪些场景 AOP 会失效？ ​

精简口述答案（90 秒版）

Spring AOP 的本质是运行期动态代理。容器在 Bean 生命周期的「初始化后」这一步，由 AnnotationAwareAspectJAutoProxyCreator 这个 BeanPostProcessor 收集所有 Advisor，用切点表达式匹配当前 Bean 的方法；匹配上就生成代理对象，放进单例池的是代理，不是真身。

代理方式二选一：目标类实现了接口且没强制 CGLIB，就用 JDK 动态代理，运行期生成实现同样接口的 $Proxy0；没有接口或 proxyTargetClass=true，就用 CGLIB，用 ASM 生成目标类的子类并覆写方法。Spring Boot 默认 proxyTargetClass=true 统一走 CGLIB，避免「按实现类注入时类型转换失败」。

AOP 失效归根到底就一句：没走代理对象。具体有四类——同类内部 this.xxx() 自调用、private 方法、static 方法、final 类或方法。

题 3：Spring 怎么解决循环依赖？三级缓存分别是什么？为什么是三级而不是两级？ ​

精简口述答案（90 秒版）

三级缓存都在 DefaultSingletonBeanRegistry 里：一级 singletonObjects 存完整成品；二级 earlySingletonObjects 存提前暴露的半成品（可能已是代理）；三级 singletonFactories 存生产半成品的 ObjectFactory。查找顺序永远是一级 → 二级 → 三级。

流程：A 实例化后立刻把 ObjectFactory 放进三级缓存；A 填充属性时发现要 B，去创建 B；B 填充属性时发现要 A，一二级都没有，三级命中，执行工厂拿到半成品 A（如果 A 需要 AOP，这一刻就提前把代理造出来），同时把结果升到二级并移除三级；B 完成后进一级缓存；A 拿到完整的 B，完成后也进一级缓存。

为什么要三级？ 关键是「要不要代理」这个决定必须延迟到真正有人来取的那一刻。如果只有两级，就得在实例化后立刻给所有 Bean 创建代理，这破坏了「AOP 在初始化后织入」的生命周期约定，也给没有循环依赖的 Bean 带来无谓开销。三级只放工厂，没人取就永远不执行。

那二级缓存的作用是什么？ 保证同一性。如果 B 和 C 都依赖 A，没有二级缓存，工厂会被执行两次，产生两个不同的代理对象，单例语义就破了。

三级缓存是万能的吗？不是。@Async 的 AsyncAnnotationBeanPostProcessor 不是 SmartInstantiationAwareBeanPostProcessor，无法参与提前代理，导致早期暴露的引用和最终代理不一致，会报 "has been injected into other beans in its raw version"。这正是 Spring Boot 2.6+ 默认禁止循环依赖的原因

题 4：完整讲一下 Spring Bean 的生命周期，有哪些扩展点可以介入？ ​

精简口述答案（90 秒版）

大致分四大阶段、十二小步：

① 实例化前：InstantiationAwareBeanPostProcessor#postProcessBeforeInstantiation，返回非 null 会直接短路。 ② 实例化：推断构造器 → 反射 newInstance，此时字段全是默认值；随后把 ObjectFactory 放入三级缓存提前暴露。 ③ 属性填充与初始化：populateBean 反射注入依赖 → Aware 回调（BeanName / BeanClassLoader / BeanFactory）→ BeanPostProcessor 前置（这里执行 @PostConstruct、补齐 ApplicationContextAware）→ InitializingBean#afterPropertiesSet → init-method → BeanPostProcessor 后置（AOP 代理在这里产生）。 ④ 注册与销毁：注册销毁回调 → 放入一级缓存可用 → 容器关闭时 @PreDestroy → DisposableBean#destroy → destroy-method。

最重要的扩展点有两类：BeanFactoryPostProcessor 作用在 BeanDefinition 清单阶段（整个容器只执行一次，能改配置、能加删 Bean 定义）；BeanPostProcessor 作用在实例阶段（每个 Bean 都过一遍，能改对象、能返回代理替换原对象）。AOP 和 @Autowired 注入都是 BPP 实现的。

题 5：@Autowired 和 @Resource 有什么区别？一个接口多个实现时怎么注入？ ​

精简口述答案（90 秒版）

@Autowired 是 Spring 自有注解，默认按类型装配，歧义时才退化为按名称；由 AutowiredAnnotationBeanPostProcessor 处理，支持 required = false，可用在构造器、setter、字段和方法参数上。

@Resource 是 JSR-250 标准注解，默认按名称装配，找不到名字再按类型；由 CommonAnnotationBeanPostProcessor 处理，不支持 required，也不能用在构造器上。注意 Spring Boot 3 / Spring 6 之后包名从 javax.annotation 变成了 jakarta.annotation。

一个接口多个实现时，@Autowired 的解析顺序是：按类型拿到候选集合 → 只有一个直接注入 → 多个则依次尝试 @Primary、@Priority、字段名与 beanName 匹配 → 都失败就抛 NoUniqueBeanDefinitionException。

实战上有三种解法：有明确主力实现用 @Primary；注入点要指定具体实现用 @Qualifier；需要全部实现做策略路由，就注入 Map<String, T> 或 List<T>，这是消灭 if-else 最优雅的方式。

题 6：@Transactional 在哪些情况下会失效？事务传播行为有哪几种？ ​

精简口述答案（90 秒版）

失效原因归两大类：没走代理 和 异常没被识别。

没走代理的四种：① 同类内部 this.method() 自调用；② 方法不是 public；③ 方法或类是 final / static；④ 类根本没被 Spring 管理。

异常没被识别的两种：④ 异常被 try/catch 吞掉，代理层感知不到就照常提交；⑤ 抛的是受检异常，Spring 默认只对 RuntimeException 和 Error 回滚，必须显式写 rollbackFor = Exception.class。

另外还有两种环境因素：数据库引擎不支持事务（MyISAM）；以及在子线程里执行 DB 操作——事务通过 ThreadLocal 绑定连接，子线程拿不到。

传播行为七种，最常考三个：REQUIRED 默认，有就加入、没有就新建；REQUIRES_NEW 挂起外层、另开一个数据库连接，外层回滚时内层已提交的数据保留；NESTED 同一连接打 Savepoint，外层回滚时内层跟着一起回滚。这个「外层回滚时内层数据是否保留」正是两者最本质的区别。

追问答题要点
自调用失效的根因和解法？this 是真身引用，不经过代理，切面逻辑完全没机会执行。解法按推荐度：拆到另一个 Bean > 自注入 > exposeProxy=true + AopContext.currentProxy() > 用 TransactionTemplate 编程式事务
REQUIRES_NEW 有什么风险？占两个数据库连接，高并发下可能耗尽连接池；内外层操作同一行时可能互相锁等待导致死锁

题 7：Bean 有哪些作用域？单例 Bean 是线程安全的吗？ ​

精简口述答案（90 秒版）

作用域六种：singleton（默认，容器启动创建、关闭销毁）、prototype（每次 getBean 新建，容器不管销毁）、以及 Web 环境下的 request、session、application、websocket。

单例 Bean 本身不保证线程安全，但是否出问题取决于有没有可变的实例字段：

  • 只有方法局部变量 → 安全，局部变量在各线程自己的虚拟机栈上，天然隔离；
  • 有可变实例字段 → 不安全，所有线程共享同一块堆内存；
  • 字段不可变（final 且引用对象也不可变）→ 安全，没有写就没有竞态；
  • 用 ThreadLocal 存状态 → 安全，但必须在 finally 里 remove()，否则线程池复用会读到上一个请求的脏数据，还会内存泄漏。

所以结论是：Service / DAO 这类无状态组件用单例完全安全，前提是不要把请求级状态塞进实例字段。

连环追问链

追问答题要点
为什么单例是默认作用域？绝大多数 Service / DAO 是无状态的，单例省去重复创建开销、省内存，还能让 AOP 代理、连接池等资源复用
SimpleDateFormat 为什么不能做单例字段？它内部用 Calendar 实例字段保存解析中间状态，多线程并发会互相覆盖，可能解析出错误日期甚至抛异常。改用 DateTimeFormatter（不可变、线程安全）
request 作用域的 Bean 怎么注入到单例里？必须加 @Scope(proxyMode = ScopedProxyMode.TARGET_CLASS)。因为单例在容器启动时创建，那一刻没有 HTTP 请求。加了作用域代理后注入的是空壳代理，方法调用时才去 RequestContextHolder 找当前线程的实例
ThreadLocal 不 remove 会怎样？两个后果：① 线程池复用线程，下个请求读到上个请求的数据（数据串了，比泄漏更可怕）；② ThreadLocalMap 的 Entry key 是弱引用但 value 是强引用，key 被回收后 value 变成不可达却回收不掉，造成泄漏
Spring 的单例和设计模式的单例一样吗？不一样。设计模式的单例是整个 JVM 一个实例（私有构造器 + 静态持有）；Spring 的单例是每个容器内、每个 beanName 一个实例，同一个类注册两个不同 beanName 就有两个实例，父子容器也可能各有一份

题 8：@Configuration 的 proxyBeanMethods 是什么？@Bean 方法互相调用会创建两个实例吗？ ​

精简口述答案（90 秒版）

不会，默认情况下仍然只有一个实例。因为 @Configuration 默认 proxyBeanMethods = true（Full 模式），Spring 会用 ConfigurationClassEnhancer 给配置类生成一个 CGLIB 子类，覆写每个 @Bean 方法。拦截逻辑是：先查容器里有没有这个 beanName，有就直接返回容器里的，没有才调父类原方法创建并注册。这就保证了单例语义。

如果显式设成 proxyBeanMethods = false（Lite 模式），就不生成 CGLIB 子类，@Bean 方法退化为普通方法。这时手动调 b() 会真的 new 一个新对象，而且不进容器——这就是 Lite 模式下最容易踩的坑。

Lite 模式的好处是启动更快、少一次字节码生成，所以 Spring Boot 内部大量自动配置类都标了 proxyBeanMethods = false。

正确写法是不管哪种模式都不要在 @Bean 方法里直接调用另一个 @Bean 方法，要依赖就声明成方法参数，让容器去解析注入。

连环追问链

追问答题要点
@Configuration 和 @Component 里的 @Bean 有区别吗？有。@Component 里的 @Bean 方法等价于 Lite 模式（无 CGLIB 增强），方法间互调会产生不受容器管理的新对象。所以配置类要用 @Configuration
@Import 有哪几种用法？① 导入普通类注册成 Bean；② 导入 @Configuration 配置类；③ 导入 ImportSelector（返回类名数组，Spring Boot 自动配置的核心）；④ 导入 ImportBeanDefinitionRegistrar（编程式注册 BeanDefinition，MyBatis @MapperScan 用的就是它）
Spring Boot 自动配置的原理？@SpringBootApplication 里的 @EnableAutoConfiguration → @Import(AutoConfigurationImportSelector.class) → 读 META-INF/spring/*.AutoConfiguration.imports（2.7 之前是 spring.factories）→ 经过 @Conditional 过滤 → 注册成 BeanDefinition
@ConditionalOnMissingBean 为什么能让用户配置优先？它判断的是"评估那一刻容器里有没有"，所以依赖 BeanDefinition 注册顺序。自动配置类通过 @AutoConfigureAfter 保证在用户配置之后才被评估。在普通 @Component 上用它结果不可预测
为什么 AOT / 原生镜像下有些写法会失效？AOT 把 BeanDefinition 固化到编译期，运行期不再扫描、不再动态生成代理。所以运行期动态注册 BeanDefinition、运行期反射造类这类"黑魔法"都会失效，要改用 @Conditional 条件装配

✅ 项目关联话术

「我们写内部 Starter 时踩过 Lite 模式的坑：为了启动性能给配置类加了 proxyBeanMethods = false，但代码里还保留着 @Bean public A a(){ return new A(b()); } 这种互调写法，结果线上出现了两个 DataSource，连接数翻倍。修复后我们把团队规范定成：@Bean 方法之间一律通过方法参数声明依赖，绝不直接互相调用——这样两种模式下行为都正确，依赖关系在方法签名上也一目了然。」

// ========== 3. 容器核心 ==========
public class MiniApplicationContext {

    /** 一级缓存：完整可用的成品单例 */
    private final Map<String, Object> singletonObjects = new ConcurrentHashMap<>(64);
    /** 二级缓存：已曝光但未注入完成的半成品（可能是代理对象） */
    private final Map<String, Object> earlySingletonObjects = new ConcurrentHashMap<>(16);
    /** 三级缓存：对象工厂，延迟决定"暴露原始对象还是代理对象" */
    private final Map<String, ObjectFactory<?>> singletonFactories = new HashMap<>(16);
    /** 正在创建中的 Bean，用于检测构造器循环依赖 */
    private final Set<String> singletonsCurrentlyInCreation =
            Collections.synchronizedSet(new HashSet<>());

    private final Map<String, BeanDefinition> beanDefinitionMap = new LinkedHashMap<>();
    /** 模拟 BeanPostProcessor 链 */
    private final List<MyBeanPostProcessor> processors = new ArrayList<>();

    public MiniApplicationContext(String basePackage) {
        scan(basePackage);                 // ① 扫描并注册 BeanDefinition
        registerBeanPostProcessors();      // ② 先把后置处理器自己创建好
        preInstantiateSingletons();        // ③ 预实例化所有非懒加载单例
    }

    // ---------- ① 扫描 ----------
    private void scan(String basePackage) {
        for (Class<?> clazz : ClassScanner.scan(basePackage)) {
            MyComponent ann = clazz.getAnnotation(MyComponent.class);
            if (ann == null) continue;
            String beanName = ann.value().isEmpty()
                    ? Introspector.decapitalize(clazz.getSimpleName())
                    : ann.value();
            // ⚠️ 同名冲突必须快速失败，否则后注册的会静默覆盖前者
            if (beanDefinitionMap.containsKey(beanName)) {
                throw new IllegalStateException("重复的 beanName: " + beanName);
            }
            beanDefinitionMap.put(beanName, new BeanDefinition(beanName, clazz));
        }
    }

    private void registerBeanPostProcessors() {
        for (BeanDefinition bd : new ArrayList<>(beanDefinitionMap.values())) {
            if (MyBeanPostProcessor.class.isAssignableFrom(bd.getBeanClass())) {
                processors.add((MyBeanPostProcessor) getBean(bd.getBeanName()));
            }
        }
    }

    private void preInstantiateSingletons() {
        for (BeanDefinition bd : new ArrayList<>(beanDefinitionMap.values())) {
            if ("singleton".equals(bd.getScope())) {
                getBean(bd.getBeanName());
            }
        }
    }

    // ---------- ② 获取 Bean：三级缓存查找 ----------
    @SuppressWarnings("unchecked")
    public <T> T getBean(String beanName) {
        Object singleton = getSingleton(beanName, true);
        if (singleton != null) {
            return (T) singleton;
        }
        BeanDefinition bd = beanDefinitionMap.get(beanName);
        if (bd == null) {
            throw new NoSuchElementException("No bean named '" + beanName + "'");
        }
        if ("prototype".equals(bd.getScope())) {
            return (T) createBean(bd);     // prototype 不进缓存，也不解环
        }
        synchronized (singletonObjects) {
            singleton = getSingleton(beanName, true);
            if (singleton != null) return (T) singleton;
            if (!singletonsCurrentlyInCreation.add(beanName)) {
                throw new IllegalStateException("无法解决的循环依赖（构造器注入）: " + beanName);
            }
            try {
                Object bean = createBean(bd);
                singletonObjects.put(beanName, bean);
                earlySingletonObjects.remove(beanName);
                singletonFactories.remove(beanName);
                return (T) bean;
            } finally {
                singletonsCurrentlyInCreation.remove(beanName);
            }
        }
    }

    /** 一级 → 二级 → 三级 依次查找，这就是 Spring 的 getSingleton(name, true) */
    private Object getSingleton(String beanName, boolean allowEarlyReference) {
        Object bean = singletonObjects.get(beanName);
        if (bean == null && singletonsCurrentlyInCreation.contains(beanName)) {
            bean = earlySingletonObjects.get(beanName);
            if (bean == null && allowEarlyReference) {
                ObjectFactory<?> factory = singletonFactories.get(beanName);
                if (factory != null) {
                    bean = factory.getObject();          // 这里才决定代理还是原始对象
                    earlySingletonObjects.put(beanName, bean); // 升级到二级，保证唯一
                    singletonFactories.remove(beanName);
                }
            }
        }
        return bean;
    }
}

创建流程：实例化 → 提前曝光 → 注入 → 初始化

java
private Object createBean(BeanDefinition bd) {
    String beanName = bd.getBeanName();
    Object raw;
    try {
        Constructor<?> ctor = bd.getBeanClass().getDeclaredConstructor();
        ctor.setAccessible(true);
        raw = ctor.newInstance();                       // ③ 实例化（空壳）
    } catch (Exception e) {
        throw new IllegalStateException("实例化失败: " + beanName, e);
    }

    // ④ 提前曝光：放入三级缓存。注意放的是 lambda，不是对象本身
    final Object exposed = raw;
    if ("singleton".equals(bd.getScope())) {
        singletonFactories.put(beanName, () -> getEarlyBeanReference(beanName, exposed));
    }

    populateBean(beanName, raw);                        // ⑤ 字段注入
    return initializeBean(beanName, raw);               // ⑥ 初始化 + 后置处理
}

/** 模拟 SmartInstantiationAwareBeanPostProcessor：决定提前曝光的是原始对象还是代理 */
private Object getEarlyBeanReference(String beanName, Object bean) {
    Object result = bean;
    for (MyBeanPostProcessor p : processors) {
        result = p.getEarlyBeanReference(beanName, result);
    }
    return result;
}

private void populateBean(String beanName, Object bean) {
    for (Field field : bean.getClass().getDeclaredFields()) {
        if (!field.isAnnotationPresent(MyAutowired.class)) continue;
        // 简化版：先按名字找，找不到按类型找
        String dependName = field.getName();
        Object dependency = beanDefinitionMap.containsKey(dependName)
                ? getBean(dependName)
                : getBeanByType(field.getType());
        field.setAccessible(true);
        try {
            field.set(bean, dependency);
        } catch (IllegalAccessException e) {
            throw new IllegalStateException("注入失败: " + beanName + "." + field.getName(), e);
        }
    }
}

private Object getBeanByType(Class<?> type) {
    List<String> candidates = beanDefinitionMap.values().stream()
            .filter(bd -> type.isAssignableFrom(bd.getBeanClass()))
            .map(BeanDefinition::getBeanName)
            .collect(Collectors.toList());
    if (candidates.isEmpty()) {
        throw new NoSuchElementException("找不到类型为 " + type.getName() + " 的 Bean");
    }
    if (candidates.size() > 1) {   // 对应 Spring 的 NoUniqueBeanDefinitionException
        throw new IllegalStateException("存在多个候选 Bean: " + candidates);
    }
    return getBean(candidates.get(0));
}

private Object initializeBean(String beanName, Object bean) {
    // Aware 回调
    if (bean instanceof MyBeanNameAware) {
        ((MyBeanNameAware) bean).setBeanName(beanName);
    }
    // BPP before
    Object result = bean;
    for (MyBeanPostProcessor p : processors) {
        result = p.postProcessBeforeInitialization(beanName, result);
    }
    // 初始化方法
    if (result instanceof MyInitializingBean) {
        ((MyInitializingBean) result).afterPropertiesSet();
    }
    // BPP after：AOP 代理通常在这里产生
    for (MyBeanPostProcessor p : processors) {
        result = p.postProcessAfterInitialization(beanName, result);
    }
    return result;
}

// ========== 1. JDK 动态代理：基于接口 ==========
public class JdkLogProxy implements InvocationHandler {

    private final Object target;

    private JdkLogProxy(Object target) { this.target = target; }

    @SuppressWarnings("unchecked")
    public static <T> T create(T target) {
        return (T) Proxy.newProxyInstance(
                target.getClass().getClassLoader(),
                target.getClass().getInterfaces(),   // ⚠️ 只代理接口里的方法
                new JdkLogProxy(target));
    }

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        // Object 自带方法不要加增强，否则 equals/hashCode 行为会被污染
        if (method.getDeclaringClass() == Object.class) {
            return method.invoke(target, args);
        }
        long start = System.nanoTime();
        try {
            Object result = method.invoke(target, args);   // 环绕通知的"前后夹"
            System.out.println("  [jdk] " + method.getName() + " 返回: " + result);
            return result;
        } catch (InvocationTargetException e) {
            // ⚠️ 必须拆包，否则调用方看到的是 InvocationTargetException 而非业务异常
            System.out.println("  [jdk] 异常通知: " + e.getTargetException());
            throw e.getTargetException();
        } finally {
            System.out.println("  [jdk] 耗时 " + (System.nanoTime() - start) / 1000 + "us");
        }
    }
}

// ========== 2. CGLIB 代理：基于子类 ==========
public class CglibLogProxy implements MethodInterceptor {

    @SuppressWarnings("unchecked")
    public static <T> T create(Class<T> targetClass) {
        Enhancer enhancer = new Enhancer();
        enhancer.setSuperclass(targetClass);              // 生成目标类的子类
        enhancer.setCallback(new CglibLogProxy());
        return (T) enhancer.create();                     // 会调用一次父类构造器
    }

    @Override
    public Object intercept(Object obj, Method method, Object[] args, MethodProxy proxy)
            throws Throwable {
        if (Modifier.isFinal(method.getModifiers())) {     // final 方法根本不会走到这里
            return proxy.invokeSuper(obj, args);
        }
        System.out.println("  [cglib] before " + method.getName());
        try {
            // invokeSuper 走 FastClass，不走反射；invoke 会导致递归 StackOverflow
            return proxy.invokeSuper(obj, args);
        } finally {
            System.out.println("  [cglib] after " + method.getName());
        }
    }
}

把多个通知串成责任链（Spring 的 ReflectiveMethodInvocation 简化版）

public interface MyInterceptor {
    Object intercept(MyInvocation invocation) throws Throwable;
}

/** 维护一个游标，每次 proceed() 往后走一个拦截器，走完才调目标方法 */
public class MyInvocation {

    private final Object target;
    private final Method method;
    private final Object[] args;
    private final List<MyInterceptor> chain;
    private int cursor = -1;

    public MyInvocation(Object target, Method method, Object[] args,
                        List<MyInterceptor> chain) {
        this.target = target; this.method = method;
        this.args = args;     this.chain = chain;
    }

    public Object proceed() throws Throwable {
        if (++cursor == chain.size()) {
            return method.invoke(target, args);        // 链条走到底，执行真正业务
        }
        return chain.get(cursor).intercept(this);
    }

    public Method getMethod() { return method; }
    public Object[] getArgs()  { return args; }
}

// 三个拦截器，注册顺序即执行顺序
List<MyInterceptor> chain = Arrays.asList(
    inv -> {                                   // 事务（最外层）
        System.out.println("tx begin");
        try {
            Object r = inv.proceed();
            System.out.println("tx commit");
            return r;
        } catch (Throwable t) {
            System.out.println("tx rollback");
            throw t;
        }
    },
    inv -> {                                   // 日志
        System.out.println("log before " + inv.getMethod().getName());
        try { return inv.proceed(); }
        finally { System.out.println("log after"); }
    },
    inv -> {                                   // 参数校验（最内层）
        if (inv.getArgs()[0] == null) throw new IllegalArgumentException("sku 不能为空");
        return inv.proceed();
    }
);

// ========== 1. 幂等注解 ==========
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface Idempotent {
    /** 支持 SpEL，如 "#order.orderNo" 或 "#userId + ':' + #sku" */
    String key();
    long expire() default 5;
    TimeUnit unit() default TimeUnit.SECONDS;
    String message() default "操作正在处理中，请勿重复提交";
}

// ========== 2. 切面实现 ==========
@Aspect
@Component
@Order(20)   // 数字越小越外层；要在事务(默认 Ordered.LOWEST_PRECEDENCE)外面
public class IdempotentAspect {

    private final StringRedisTemplate redisTemplate;
    private final ExpressionParser parser = new SpelExpressionParser();
    private final ParameterNameDiscoverer discoverer =
            new DefaultParameterNameDiscoverer();

    public IdempotentAspect(StringRedisTemplate redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    @Around("@annotation(idempotent)")
    public Object around(ProceedingJoinPoint pjp, Idempotent idempotent) throws Throwable {
        String key = "idem:" + resolveKey(pjp, idempotent.key());
        String token = UUID.randomUUID().toString();

        Boolean ok = redisTemplate.opsForValue()
                .setIfAbsent(key, token, idempotent.expire(), idempotent.unit());
        if (!Boolean.TRUE.equals(ok)) {
            throw new BizException(idempotent.message());
        }
        try {
            return pjp.proceed();
        } catch (Throwable t) {
            // 业务失败要释放锁，允许重试；成功则让 key 自然过期防重放
            releaseIfOwner(key, token);
            throw t;
        }
    }

    /** ⚠️ 删锁必须校验持有者，否则会删掉别人的锁 */
    private void releaseIfOwner(String key, String token) {
        String script = "if redis.call('get', KEYS[1]) == ARGV[1] "
                      + "then return redis.call('del', KEYS[1]) else return 0 end";
        redisTemplate.execute(new DefaultRedisScript<>(script, Long.class),
                Collections.singletonList(key), token);
    }

    private String resolveKey(ProceedingJoinPoint pjp, String spel) {
        MethodSignature signature = (MethodSignature) pjp.getSignature();
        Method method = signature.getMethod();
        String[] names = discoverer.getParameterNames(method);
        Object[] args = pjp.getArgs();

        EvaluationContext ctx = new StandardEvaluationContext();
        if (names != null) {
            for (int i = 0; i < names.length; i++) {
                ctx.setVariable(names[i], args[i]);
            }
        }
        Object value = parser.parseExpression(spel).getValue(ctx);
        if (value == null) {

    @Pointcut("execution(public * com.example.*.controller..*.*(..))")
    public void controllerLayer() {}

    @Around("controllerLayer()")
    public Object monitor(ProceedingJoinPoint pjp) throws Throwable {
        MethodSignature sig = (MethodSignature) pjp.getSignature();
        String name = sig.getDeclaringType().getSimpleName() + "#" + sig.getName();
        long start = System.currentTimeMillis();
        String result = "success";
        try {
            return pjp.proceed();
        } catch (Throwable t) {
            result = "fail:" + t.getClass().getSimpleName();
            throw t;                              // ⚠️ 必须原样抛出，不能吞异常
        } finally {
            long cost = System.currentTimeMillis() - start;
            // 慢接口单独告警，正常接口只打 debug，避免日志爆量
            if (cost > 500) {
                log.warn("[slow] {} cost={}ms result={}", name, cost, result);
            } else if (log.isDebugEnabled()) {
                log.debug("[monitor] {} cost={}ms", name, cost);
            }
            Metrics.timer("api.cost", "api", name, "result", result)
                   .record(cost, TimeUnit.MILLISECONDS);
        }
    }
}

📌 单独澄清：幂等切面必须在事务切面的"外面"

顺序结果
❌ 事务在外、幂等在内事务先开启 → 加锁 → 业务失败回滚 → 但锁的释放在事务提交之前/之后不可控，容易出现"事务已回滚、锁还在"，用户重试被拦
✅ 幂等在外、事务在内先抢锁 → 再开事务 → 失败时事务已回滚完毕，切面才释放锁，状态一致

同样的道理适用于分布式锁切面：@Order 必须小于事务切面（事务默认 Ordered.LOWEST_PRECEDENCE，即最内层），否则就是经典的"锁在事务内部，锁释放早于事务提交"导致并发穿透。

public class MapperFactoryBean<T> implements FactoryBean<T> {

        this.mapperInterface = mapperInterface;

    @SuppressWarnings("unchecked")
    public T getObject() {

                mapperInterface.getClassLoader(),
                new Class[]{mapperInterface},
                (proxy, method, args) -> {

}

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
public @interface MyRedisKey {
    String prefix();
}

@Component
public class MyRedisKeyBpp implements BeanPostProcessor {

    @Override
    public Object postProcessBeforeInitialization(Object bean, String beanName) {
        // 属性注入类型的扩展放在 before（与 @Autowired 的处理阶段一致）
        ReflectionUtils.doWithFields(bean.getClass(), field -> {
            MyRedisKey ann = field.getAnnotation(MyRedisKey.class);
            if (ann == null) return;
            if (field.getType() != String.class) {
                throw new BeanCreationException(beanName,
                        "@MyRedisKey 只能标注在 String 字段上: " + field.getName());
            }
            ReflectionUtils.makeAccessible(field);
            ReflectionUtils.setField(field, bean, ann.prefix() + ":" + appEnv());
        });
        return bean;
    }

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        // 对象替换/代理放在 after（AOP 也在这一阶段）
        if (!(bean instanceof OrderService)) {
            return bean;
        }
        return Proxy.newProxyInstance(bean.getClass().getClassLoader(),
                bean.getClass().getInterfaces(),
                (proxy, method, args) -> {
                    System.out.println("[bpp-proxy] " + method.getName());
                    try {
                        return method.invoke(bean, args);
                    } catch (InvocationTargetException e) {
                        throw e.getTargetException();
                    }
                });
    }
}

@Service
public class OrderServiceImpl implements OrderService {

    @Autowired private OrderMapper orderMapper;
    /** ✅ 修复方案 A：注入自己的代理（Spring 会用三级缓存解掉这个自引用） */
    @Autowired @Lazy private OrderService self;

    @Override
    public void createBatchBad(List<Order> orders) {
        for (Order o : orders) {
            saveOne(o);          // ❌ this.saveOne()，绕过代理，@Transactional 完全失效
        }
    }

    @Override
    public void createBatchGoodA(List<Order> orders) {
        for (Order o : orders) {
            self.saveOne(o);     // ✅ 走代理，事务生效
        }
    }

    @Override
    public void createBatchGoodB(List<Order> orders) {
        for (Order o : orders) {
            // ✅ 修复方案 B：AopContext（需 @EnableAspectJAutoProxy(exposeProxy = true)）
            ((OrderService) AopContext.currentProxy()).saveOne(o);
        }
    }

    @Transactional(rollbackFor = Exception.class,
                   propagation = Propagation.REQUIRES_NEW)
    @Override
    public void saveOne(Order o) {
        orderMapper.insert(o);
        if (o.getAmount() < 0) {
            throw new IllegalStateException("金额非法");
        }
    }
}

❌ 坑✅ 解决方案
@Transactional 方法被同类其它方法 this.xxx() 调用，事务完全失效，日志里看不到任何提示本质是没走代理。三种修复：① 把事务方法挪到另一个 Bean（推荐）；② @Autowired @Lazy 注入自己；③ @EnableAspectJAutoProxy(exposeProxy = true) + AopContext.currentProxy()。验证手段用 TransactionSynchronizationManager.isActualTransactionActive()，不要靠肉眼
事务方法抛了受检异常（如 IOException），数据却没回滚默认只对 RuntimeException 和 Error 回滚。统一加 @Transactional(rollbackFor = Exception.class)，并写进团队规范/代码检查
事务方法里 try-catch 吞掉异常，以为"catch 了就回滚"异常被吞，代理感知不到失败 → 照常提交。要么原样抛出，要么在 catch 里手动 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()
@Transactional 加在 private / final / static 方法上，没有任何报错也没有效果CGLIB 靠生成子类覆写方法，这三类方法无法被覆写。改成 public 非 final 实例方法
把 @Transactional 加在 @Async 方法或新建线程里的逻辑上，事务莫名失效事务上下文绑定在 ThreadLocal 上，换线程即丢失。异步任务内部要自己开事务，且外层事务不能指望它一起回滚

构造器注入出现循环依赖，报 BeanCurrentlyInCreationException，以为是 Spring 的 bug构造器注入发生在实例化阶段，连"半成品"都造不出来，三级缓存无从下手。这其实是优点——把设计问题暴露在启动期。临时可用 @Lazy，根治靠重构
在构造器里使用 @Autowired 字段，必 NPE字段注入发生在实例化之后。依赖在构造期就要用 → 改构造器注入；只是初始化逻辑 → 挪到 @PostConstruct
循环依赖 + AOP 场景下，B 持有的 A 竟然是没有被切面增强的原始对象说明提前曝光时没有走 getEarlyBeanReference。排查是否自定义了 BPP 却没实现 SmartInstantiationAwareBeanPostProcessor；用 b.getA() == context.getBean("a") 断言同一性
以为 @Order 能控制 Bean 的创建顺序，加上之后依然报依赖未就绪@Order 只影响集合注入的排序和切面/处理器的执行顺序，与实例化顺序无关。要控创建顺序用 @DependsOn，或直接声明依赖关系
给配置类加 proxyBeanMethods = false 后，线上出现两个 DataSource，连接池翻倍Lite 模式下 @Bean 方法互调就是普通 Java 调用，每次 new 一个新对象。规范：@Bean 之间一律通过方法参数声明依赖，不直接互相调用
单例 Service 里用成员变量存当前用户/当前请求参数，压测时数据串号单例的实例变量被所有线程共享。改用 ThreadLocal，或 @Scope(value = "request", proxyMode = TARGET_CLASS)
ThreadLocal 用完没 remove()，线程池复用后读到上一个请求的数据，还伴随内存泄漏finally 里必须 remove()。Web 层统一用拦截器的 afterCompletion 兜底清理
@Scope("request") 的 Bean 注入到单例里，启动就报 No thread-bound request found必须加 proxyMode = ScopedProxyMode.TARGET_CLASS，注入的是作用域代理，每次方法调用时才去当前请求找真实对象
prototype Bean 的 @PreDestroy / destroy-method 从来不执行容器不管理 prototype 的销毁，交出去就不再持有引用。需要清理资源的自己 try-finally，或注册 DisposableBeanAdapter
把 prototype Bean 用 @Autowired 注入单例，结果每次拿到的都是同一个实例注入只发生一次。改用 ObjectProvider<T> / @Lookup / proxyMode 三种方式之一，在每次使用时向容器申请新实例
在 BeanPostProcessor 里 @Autowired 了一个业务 Bean，结果那个 Bean 的事务和切面全部失效启动日志里会有 is not eligible for getting processed by all BeanPostProcessors。BPP 里改成实现 BeanFactoryAware，用的时候再 getBean，不要在字段上注入
自定义 BeanPostProcessor 的 postProcessAfterInitialization 忘记 return bean，返回了 null，容器里 Bean 全空两个回调都必须返回对象；不做处理时原样返回入参
自定义 FactoryBean 的 getObjectType() 返回 null，按类型注入失败或 Bean 被提前实例化必须返回真实产品类型，容器靠它做类型匹配而不实例化。想拿工厂本身用 &beanName
在 BeanFactoryPostProcessor 里调 getBean()，启动日志出现一堆 "not eligible" 警告BFPP 阶段只应该改 BeanDefinition，不要触发实例化。确实要拿实例请挪到 ApplicationRunner / SmartInitializingSingleton
@PostConstruct 里调用其它 Bean 的方法报错或拿到半成品@PostConstruct 时自己虽已注入完成，但依赖方可能仍在初始化中。需要"全部 Bean 就绪"才执行的逻辑，用 ApplicationRunner 或 ApplicationReadyEvent
@Async 方法被同类调用不生效与事务自调用完全同源——都依赖代理。修复方式一致：挪到另一个 Bean
@Async 没配线程池，并发一上来就创建海量线程默认是 SimpleAsyncTaskExecutor，每次新建线程不复用。必须自定义 ThreadPoolTaskExecutor 并实现 AsyncConfigurer
@Async 返回 void 时异常被静默吞掉，线上问题完全无感实现 AsyncUncaughtExceptionHandler 统一兜底，或把返回值改成 CompletableFuture 让调用方感知
分布式锁/幂等切面加在事务切面内层，并发依然穿透锁的释放早于事务提交，形成"锁已放、数据未可见"的窗口。给锁切面设更小的 @Order（事务默认是最低优先级即最内层）
ApplicationEvent 发布后以为是异步的，结果接口响应变慢Spring 事件默认同步，在同一线程同一事务内执行。要异步请配 SimpleApplicationEventMulticaster 的 taskExecutor 或给监听器加 @Async
事务里发布事件通知下游，下游查不到数据监听器在事务提交前执行。改用 @TransactionalEventListener(phase = AFTER_COMMIT)
一个接口两个实现，@Autowired 启动报 NoUniqueBeanDefinitionException五种手段任选：@Primary、@Qualifier、字段名与 beanName 一致、注入 Map<String, T> 做策略路由、@Order + List<T>
@ConditionalOnMissingBean 加在普通 @Component 上，行为随机它判断的是"评估那一刻容器里有没有"，强依赖注册顺序。只应该用在自动配置类里，并配合 @AutoConfigureAfter
Spring MVC 下 @Service 在 Controller 里注入不到，或事务不生效父子容器问题：子容器（DispatcherServlet）能看父容器，反之不行。确保扫描范围不重叠——父容器扫 Service/Dao，子容器只扫 Controller
升级 Spring Boot 3 后大量编译错误：找不到 javax.servletJakarta EE 命名空间迁移，javax.* 全部变成 jakarta.*。同时注意 JDK 17 起步、三方库需同步升版本
打成 GraalVM 原生镜像后，运行期动态注册 BeanDefinition / 反射造类的代码全部失效AOT 把 BeanDefinition 固化到编译期，运行期不再扫描。把动态逻辑改成 @Conditional 条件装配，或补 reflect-config.json 提示文件
