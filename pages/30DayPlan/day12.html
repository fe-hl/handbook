📖 基础知识讲解【基础原理 + 高级深挖知识点】 ​

基础原理 ​

1. 进程、线程与 Java 的线程模型 ​

并发这套知识的所有结论，都建立在一个前提上：Java 的 Thread 不是「轻量级」的东西，它是操作系统内核线程的一层薄包装。理解这一点，才能理解后面「为什么要用线程池」「为什么上下文切换贵」「为什么 JDK21 要搞虚拟线程」。

text
进程 Process：资源分配的最小单位（独立地址空间、文件句柄、内存）
  └── 线程 Thread：CPU 调度的最小单位（共享进程内存，独享栈 + PC + 本地方法栈）

Java 线程模型（HotSpot）= 1 : 1 内核线程模型
  Java Thread 对象  ──映射──►  JVM 内部 JavaThread  ──1:1──►  OS 内核线程
                                                                  │
                                                      由 OS 调度器统一调度
  结论：
  ① new Thread().start() 会真的调用 pthread_create，是一次系统调用
  ② 线程切换需要陷入内核态，保存/恢复上下文，成本约 1~10 微秒
  ③ 每个线程默认栈 1MB（-Xss 可调），1 万个线程 ≈ 10GB 虚拟内存 → 开不起
  ④ 所以线程必须「池化复用」，这就是线程池存在的根本理由

对比：虚拟线程（JDK21 正式）= M : N 模型
  N 个虚拟线程  ──挂载/卸载──►  少量载体线程（ForkJoinPool）──►  内核线程
  阻塞时只卸载虚拟线程，不阻塞内核线程 → 可以开百万级
维度平台线程（Thread）虚拟线程（JDK21）
与内核线程1 : 1M : N（挂载在载体线程上）
创建成本高（系统调用 + 1MB 栈）极低（堆上对象，栈按需增长）
可创建数量几千百万级
阻塞代价内核线程被占用仅卸载虚拟线程，载体线程可复用
适用场景CPU 密集、需要线程池调控IO 密集、高并发请求处理

一句话结论： 线程贵，所以要池化；线程切换贵，所以线程数不是越多越好；虚拟线程解决的是「IO 密集场景下线程不够用」的问题，不能提升 CPU 密集任务的吞吐。

2. 线程创建的 5 种方式 ​

text
① 继承 Thread          —— 重写 run()，Java 单继承，侵入性强，不推荐
② 实现 Runnable        —— 无返回值、不能抛检查异常，最常用的任务抽象
③ Callable + FutureTask —— 有返回值、可抛异常，get() 阻塞获取结果
④ 线程池 ThreadPoolExecutor —— 生产唯一推荐，复用线程 + 可控可监控
⑤ CompletableFuture    —— 任务编排（串行/并行/聚合），本质还是跑在线程池上
java
// ① 继承 Thread
class MyThread extends Thread {
    @Override public void run() { System.out.println("run by " + getName()); }
}
new MyThread().start();

// ② 实现 Runnable（推荐：任务与执行解耦）
new Thread(() -> System.out.println("runnable"), "biz-thread-1").start();

// ③ Callable + FutureTask：有返回值
FutureTask<Integer> task = new FutureTask<>(() -> {
    Thread.sleep(100);
    return 666;                      // Callable 可以抛异常、可以有返回值
});
new Thread(task).start();
Integer r = task.get();              // 阻塞直到任务完成；get(timeout) 可超时

// ④ 线程池（生产写法：手动 new，不用 Executors）
ThreadPoolExecutor pool = new ThreadPoolExecutor(
        4, 8, 60L, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(1000),                 // 必须有界
        new ThreadFactoryBuilder().setNameFormat("order-%d").build(),
        new ThreadPoolExecutor.CallerRunsPolicy());
Future<Integer> f = pool.submit(() -> 1 + 1);

// ⑤ CompletableFuture 编排
CompletableFuture<String> cf = CompletableFuture
        .supplyAsync(() -> queryUser(), pool)           // 一定要传自定义线程池
        .thenApply(u -> u.getName())
        .exceptionally(e -> "default");
方式返回值抛检查异常线程复用生产可用性
继承 Thread❌❌❌❌ 不用
Runnable❌❌❌作为任务抽象 ✅
Callable+Future✅✅❌需要结果时 ✅
ThreadPoolExecutor✅✅✅✅ 唯一推荐
CompletableFuture✅✅✅✅ 多任务编排首选

面试高频细节： start() 和 run() 的区别 —— start() 由 JVM 调用本地方法 start0() 创建内核线程，由 OS 调度后回调 run()；直接调 run() 就是一次普通方法调用，仍在当前线程执行，没有任何并发。而且 start() 只能调用一次，第二次会抛 IllegalThreadStateException（threadStatus != 0）—— 线程是一次性用品，这也是线程池必须复用线程而不能复用 Thread 对象的原因。

3. 线程的 6 大状态与流转 ​

Java 的线程状态定义在 Thread.State 枚举里，只有 6 个，和操作系统的 5 态模型不是一回事。最容易答错的点：Java 把 OS 的「就绪」和「运行」合并成了一个 RUNNABLE。

text
NEW --start()--> RUNNABLE --run() 结束 / 抛未捕获异常--> TERMINATED

RUNNABLE 出去的三条路，最终都会回到 RUNNABLE：

RUNNABLE --抢 synchronized 锁失败--> BLOCKED
BLOCKED  --拿到监视器锁--> RUNNABLE

RUNNABLE --wait() / join() / LockSupport.park()--> WAITING
WAITING  --notify() / notifyAll() / 目标线程结束 / unpark()--> RUNNABLE
         （wait 被唤醒后需先变 BLOCKED 重新抢锁，再回 RUNNABLE）

RUNNABLE      --sleep(n) / wait(n) / join(n) / parkNanos(n)--> TIMED_WAITING
TIMED_WAITING --超时自动返回 / 被提前唤醒--> RUNNABLE

关键记忆点：
① RUNNABLE = OS 的「就绪」+「运行中」，Java 不区分，jstack 里看到
   RUNNABLE 不代表它正在占用 CPU
② BLOCKED 只有一种来源：抢 synchronized 监视器锁失败；
   ReentrantLock 抢锁失败是 park，显示 WAITING / TIMED_WAITING
③ WAITING 和 TIMED_WAITING 的唯一区别是「有没有超时参数」
④ IO 阻塞（socket read）在 Java 里仍然显示 RUNNABLE（JVM 不感知）
⑤ TERMINATED 不可逆：线程一次性，重复 start() 抛 IllegalThreadStateException
状态触发方式是否持有锁jstack 显示
NEWnew Thread()—不出现
RUNNABLEstart() 之后、IO 阻塞中视代码而定runnable
BLOCKED抢 synchronized 失败没拿到blocked on monitor entry
WAITINGwait()、join()、park()、await()wait 会释放锁in Object.wait() / parking
TIMED_WAITINGsleep(n)、wait(n)、join(n)、parkNanos、offer(timeout)sleep 不释放锁waiting on condition
TERMINATEDrun() 正常返回或抛未捕获异常已释放不出现

易错提醒： 面试常问「BLOCKED 和 WAITING 有什么区别」。答案不是「阻塞和等待」这种同义反复，而是：BLOCKED 是被动的 —— 线程想往前走但锁被别人占着，一旦锁释放立刻自动参与竞争；WAITING 是主动的 —— 线程自己交出了执行权，必须等别人显式 notify / unpark / 目标线程结束才可能回到 RUNNABLE。另外 BLOCKED 专属于 synchronized，ReentrantLock 的等待者是 WAITING，这是 jstack 排查时区分两类锁的关键特征。

4. 线程常用 API 与易错点 ​

java
Thread t = new Thread(task, "pay-worker");

t.setDaemon(true);   // 守护线程：必须在 start() 前设置，否则抛 IllegalThreadStateException
t.setPriority(8);    // 优先级 1~10，默认 5，但【OS 不保证】，生产不要依赖
t.start();           // 唯一合法启动方式，只能调一次

t.join();            // 当前线程等 t 结束（当前线程进 WAITING）
t.join(1000);        // 最多等 1 秒（TIMED_WAITING）

Thread.sleep(100);   // 当前线程睡 100ms，不释放 synchronized 锁
Thread.yield();      // 提示调度器「我可以让一让」，仅建议，可能被忽略
Thread.currentThread().getName();

t.interrupt();                            // 只是打「中断标记」，不会强行停止线程
t.isInterrupted();                        // 查标记，不清除
Thread.interrupted();                     // 查当前线程标记，【并清除】标记

① 守护线程 vs 用户线程

text
用户线程：只要还有一个存活，JVM 就不退出
守护线程：JVM 退出时直接被抛弃，finally 块【不保证】执行

典型守护线程：GC 线程、JIT 编译线程、Spring 的定时任务调度线程（部分）
使用原则：守护线程里【绝不能】写「必须完成」的逻辑（写文件、提交事务、刷日志）

② 中断机制：Java 没有「强杀线程」

stop()、suspend()、resume() 已全部 @Deprecated，因为 stop() 会在任意位置抛 ThreadDeath 并立刻释放所有锁，导致共享数据处于被改坏一半的状态。Java 的正确做法是协作式中断：

java
// 正确的可中断任务模板
public void run() {
    try {
        while (!Thread.currentThread().isInterrupted()) {   // ① 轮询检查标记
            doWork();
            Thread.sleep(100);                              // ② 阻塞方法会响应中断
        }
    } catch (InterruptedException e) {
        // ③ sleep/wait/join 抛出 InterruptedException 时，【标记会被自动清除】
        //    所以这里必须补回来，否则上层无法感知
        Thread.currentThread().interrupt();
    } finally {
        cleanup();                                          // ④ 资源清理
    }
}
场景interrupt() 的效果
线程正在正常执行计算只设置标记位，代码不检查就等于没发生
阻塞在 sleep / wait / join立刻抛 InterruptedException，并清除标记
阻塞在 lock.lockInterruptibly()抛 InterruptedException
阻塞在 lock.lock()（不可中断）只设标记，继续等锁
阻塞在 synchronized 抢锁只设标记，继续等（BLOCKED 不响应中断）
阻塞在 InputStream.read()（socket）不响应，需要关闭流/连接来打断
阻塞在 NIO 的 Selector.select()响应，select 立刻返回
线程已 TERMINATED无任何效果

三个必须记住的结论： ① InterruptedException 被捕获后标记会被清除，要么补 interrupt()、要么向上抛，吞掉它是并发代码里最常见的错误；② Thread.interrupted() 是静态方法且会清除标记，isInterrupted() 是实例方法不清除，名字很像但行为相反；③ 线程池的 shutdownNow() 本质就是对所有 worker 调 interrupt()，任务不响应中断，shutdownNow 就停不下来。

5. JMM 内存模型与并发三大特性 ​

并发 Bug 的根源只有一句话：每个 CPU 核心有自己的高速缓存，编译器和 CPU 还会重排指令。JMM（Java Memory Model）就是 Java 对这件事定义的一套抽象规则。

text
         ┌─────────── 主内存 Main Memory（所有线程共享）───────────┐
         │     堆上的实例字段、静态字段、数组元素                    │
         └───────▲───────────────────────────────▲────────────────┘
                 │ read / write                  │
     ┌───────────┴──────────┐        ┌───────────┴──────────┐
     │ 线程 A 工作内存       │        │ 线程 B 工作内存       │
     │ （CPU 寄存器 + L1/L2）│        │ （CPU 寄存器 + L1/L2）│
     │   count 的副本 = 0    │        │   count 的副本 = 0    │
     └──────────────────────┘        └──────────────────────┘

问题：A 把 count 改成 1，只改了自己的副本 → B 永远看到 0  →可见性问题
     count++ 实际是 read-modify-write 三步 → 交错执行丢更新 → 原子性问题
     编译器/CPU 为了性能调整语句顺序        → DCL 半初始化  → 有序性问题
特性含义被破坏的原因解决手段
原子性操作不可分割，要么全做要么不做时间片切换synchronized、Lock、CAS 原子类
可见性一个线程的修改其他线程立刻能看到CPU 缓存未同步volatile、synchronized、final
有序性程序执行顺序符合代码顺序编译器/CPU 指令重排volatile（内存屏障）、synchronized

happens-before 八条规则（JMM 的核心，面试必背前五条）：

text
① 程序次序规则：单线程内，前面的操作 happens-before 后面的操作
② 监视器锁规则：unlock 一个锁 happens-before 后续对【同一把锁】的 lock
③ volatile 规则：对 volatile 变量的写 happens-before 后续对它的读
④ 线程启动规则：Thread.start() happens-before 该线程的任何操作
⑤ 线程终止规则：线程的所有操作 happens-before 其他线程检测到它已终止
                （join() 返回、isAlive() 返回 false）
⑥ 线程中断规则：interrupt() happens-before 被中断线程检测到中断
⑦ 对象终结规则：构造函数结束 happens-before finalize() 开始
⑧ 传递性：A hb B，B hb C  ⇒  A hb C

happens-before 不是「时间上先发生」，而是「前一个操作的结果对后一个操作可见，且执行顺序不会被重排到它后面」。比如 synchronized 块内部的两条无依赖语句照样可能被重排，但只要不影响「锁释放前的全部修改对下一个持锁者可见」这个承诺就合法。理解这一点，才能理解「为什么加了锁就同时解决了可见性和有序性」—— 不是锁禁止了重排，而是锁的语义通过规则 ② + ⑧ 建立了 happens-before 链。

6. synchronized：JVM 内置锁 ​

java
public class SyncDemo {
    private int count;
    private static int total;

    // ① 修饰实例方法：锁的是 this（同一个对象的不同同步方法互斥）
    public synchronized void inc() { count++; }

    // ② 修饰静态方法：锁的是 SyncDemo.class（全类唯一，和实例锁互不干扰）
    public static synchronized void incTotal() { total++; }

    // ③ 修饰代码块：锁括号里的对象，范围最小，推荐
    private final Object lock = new Object();
    public void incBlock() {
        // 只锁必要的几行，其他耗时操作放锁外
        synchronized (lock) { count++; }
    }
}
用法锁对象作用范围注意
实例方法this同一实例的所有同步实例方法不同实例之间不互斥
静态方法类.class全类所有实例与实例锁是两把不同的锁
代码块括号内指定对象块内代码推荐，锁粒度可控

字节码层面：

text
synchronized 代码块  → monitorenter / monitorexit 两条字节码指令
                      编译器会生成【两个】monitorexit：一个正常出口，
                      一个异常出口（所以抛异常也会自动释放锁）
synchronized 方法    → 方法的 access_flags 带 ACC_SYNCHRONIZED 标志
                      JVM 执行时隐式做 monitorenter/exit

底层：每个 Java 对象都关联一个 ObjectMonitor（C++ 实现，重量级锁时才真正创建）
  ObjectMonitor {
      _owner       // 持锁线程
      _recursions  // 重入次数（这就是可重入的实现）
      _EntryList   // 抢锁失败阻塞的线程 → 对应 BLOCKED 状态
      _WaitSet     // 调用 wait() 后等待的线程 → 对应 WAITING 状态
      _count
  }

synchronized 的四个关键性质： ① 可重入 —— 同一线程可重复进入，靠 _recursions 计数，所以子类同步方法可以调父类同步方法而不会自锁死；② 非公平 —— 新来的线程可以直接抢，不排队，吞吐高但可能饿死；③ 不可中断 —— lock.lock() 的平替没有，等锁期间 interrupt() 无效；④ 自动释放 —— 方法返回或抛异常都会 monitorexit，这是它相比 ReentrantLock 最大的优势（后者忘了 unlock 就是永久死锁）。

7. 对象头与锁升级（锁膨胀） ​

JDK6 以后 synchronized 不再是「一上来就找 OS 要互斥量」的重量级锁，而是会随竞争激烈程度单向升级。升级状态记录在对象头的 Mark Word 里。

text
64 位 JVM 下，普通对象的对象头 = Mark Word(8B) + Klass Pointer(4B 压缩后)

Mark Word 的复用（同一块 8 字节，按锁标志位解释成不同含义）：
┌────────────────────────────────────┬──────────┬──────┐
│ 无锁    hashCode(31) 分代年龄(4)    │ 偏向 0   │ 01   │
│ 偏向锁  线程ID(54) epoch(2) 年龄(4) │ 偏向 1   │ 01   │
│ 轻量级锁  指向线程栈中 Lock Record 的指针(62)   │ 00   │
│ 重量级锁  指向 ObjectMonitor 的指针(62)         │ 10   │
│ GC 标记                                         │ 11   │
└────────────────────────────────────┴──────────┴──────┘

升级路径（只能升不能降，直到 GC 后对象重新分配）：
  无锁 ──第一个线程进入──► 偏向锁 ──出现第二个线程──► 轻量级锁
                                     （CAS 自旋抢）
       ──自旋失败/竞争加剧──► 重量级锁（向 OS 申请互斥量，线程挂起）
锁状态加锁方式竞争场景开销
偏向锁Mark Word 里 CAS 写入线程 ID，之后无同步开销全程只有一个线程几乎为 0

重量级锁进入 ObjectMonitor 的 _EntryList，线程 park 挂起真实并发，竞争激烈用户态↔内核态切换，微秒级

一个必须知道的版本变化： 偏向锁在 JDK15 被默认关闭（JEP 374），JDK18 彻底移除。原因是：① 偏向锁撤销（revoke）需要进入安全点 STW，在竞争多的现代应用里，撤销的总成本超过了它节省的 CAS 成本；② 现在的 CAS 在主流 CPU 上已经非常便宜；③ 这段代码维护复杂度高，阻碍了 Lilliput 等对象头压缩项目。所以面试答锁升级时，加一句「JDK15 之后偏向锁已默认禁用，升级路径简化成 无锁 → 轻量级 → 重量级」会是明显的加分项。

8. volatile：轻量级的可见性保证 ​

java
public class VolatileDemo {
    // ① 典型场景一：状态标记位（最经典、最安全的用法）
    private volatile boolean running = true;
    public void shutdown() { running = false; }      // 其他线程立刻可见
    public void run() { while (running) { work(); } }

    // ② 典型场景二：DCL 单例（靠的是「禁止重排」而不是可见性）
    private static volatile VolatileDemo instance;

    // ③ 反例：volatile 不保证原子性，这里依然会丢更新
    private volatile int count;
    public void inc() { count++; }                   // read + 1 + write 三步，非原子
}
text
volatile 做了两件事：

① 可见性：写操作立刻刷回主内存，并让其他 CPU 的缓存行失效（MESI 缓存一致性协议）
          底层是在汇编层加 lock 前缀指令（lock addl $0x0, (%rsp)）

② 有序性：插入内存屏障，禁止特定方向的重排
          volatile 写之前：StoreStore 屏障（前面的普通写不能排到它后面）
          volatile 写之后：StoreLoad 屏障（最重的屏障，保证写对后续读可见）
          volatile 读之后：LoadLoad + LoadStore 屏障（后面的读写不能排到它前面）

volatile 没做的事：
  ✗ 不保证原子性（count++ 三步仍会交错）
  ✗ 不会加锁，不会阻塞线程
  ✗ 不能替代 synchronized 做复合操作
对比项volatilesynchronized
原子性❌ 不保证✅ 保证
可见性✅✅
有序性✅（禁止重排）✅（临界区整体串行）
阻塞线程❌ 不阻塞✅ 会阻塞
作用对象变量代码块 / 方法
性能很轻（无上下文切换）升级到重量级锁后较重
适用状态标记、DCL、一写多读复合操作、需要互斥的临界区

判断是否能用 volatile 的一条准则： 写入的新值不依赖当前值（如 flag = false 可以，count++ 不行），或者只有单一线程写、多线程读。满足其一才能用，否则必须上锁或用原子类。

9. CAS 与原子类 ​

CAS（Compare And Swap）是「无锁并发」的基石：比较内存中的值是否等于预期值，相等才写入新值，整个过程由 CPU 的 cmpxchg 指令保证原子。它是乐观锁，失败就自旋重试，不会阻塞线程。

public final int getAndAddInt(Object o, long offset, int delta) {
    int v;
    do {
        v = getIntVolatile(o, offset);                       // ① 读当前值（volatile 读）
    } while (!compareAndSwapInt(o, offset, v, v + delta));   // ② CAS 失败就重试
    return v;
}

CAS(内存地址 V, 预期值 A, 新值 B)：
   if (V == A) { V = B; return true; }
   else        { return false; }      ← 失败则自旋重试

三个经典问题：
① ABA 问题：线程1 读到 A → 线程2 把 A 改成 B 又改回 A → 线程1 CAS 成功
             但中间状态已经丢失（栈顶替换、链表节点复用场景会出 Bug）
   解法：加版本号 → AtomicStampedReference（int 版本戳）
                     AtomicMarkableReference（boolean 标记）
② 自旋开销：高竞争下大量线程空转烧 CPU
   解法：分段累加 → LongAdder；或退化为阻塞锁
③ 只能保证一个变量的原子性
   解法：把多个字段封装成对象用 AtomicReference；或直接上锁
分类代表类用途
基本类型AtomicInteger、AtomicLong、AtomicBoolean计数器、开关
引用类型AtomicReference、AtomicStampedReference对象整体替换、解决 ABA
数组AtomicIntegerArray、AtomicReferenceArray数组元素级原子更新
字段更新器AtomicIntegerFieldUpdater给已有类的 volatile 字段加原子性
高性能累加LongAdder、LongAccumulator、DoubleAdder高并发计数首选

工程选择： 低并发计数用 AtomicLong（结果精确、get() 立即一致）；高并发只做累加、偶尔读总数的场景一律用 LongAdder —— 它把一个热点变量拆成 base + Cell[] 数组，不同线程 CAS 到不同 Cell 上，彻底避开了单点竞争，实测高并发下吞吐是 AtomicLong 的数倍。代价是 sum() 是瞬时估算值（遍历期间其他线程还在改），且占内存更多。

10. AQS：JUC 的半壁江山 ​

AbstractQueuedSynchronizer 是 ReentrantLock、CountDownLatch、Semaphore、ReentrantReadWriteLock、ThreadPoolExecutor.Worker 的共同父类。它只做两件事：用一个 volatile int state 表示同步状态，用一个 FIFO 双向队列（CLH 变体）存放抢不到资源的线程。

text
AQS 核心结构
  private volatile int state;      // 同步状态，含义由子类定义
  private transient Node head;     // 等待队列头（虚拟头节点，不存线程）
  private transient Node tail;     // 等待队列尾

  state 的含义由子类自己解释：
    ReentrantLock          → 0 未锁，n 表示重入 n 次
    Semaphore              → 剩余许可数
    CountDownLatch         → 剩余计数
    ReentrantReadWriteLock → 高 16 位读锁次数，低 16 位写锁次数

等待队列（CLH 的双向链表变体）
  head ⇄ Node(T1) ⇄ Node(T2) ⇄ Node(T3) ⇄ tail
         ▲
         每个 Node 里有：thread、prev、next、waitStatus、nextWaiter
  waitStatus：
     0          初始
    -1 SIGNAL   后继节点需要被唤醒（当前节点释放时要 unpark 后继）
    -2 CONDITION 在 Condition 的条件队列中
    -3 PROPAGATE 共享模式下需要向后传播唤醒
     1 CANCELLED 已取消（超时或被中断）

两种资源共享模式
  独占 Exclusive：同一时刻只有一个线程能拿到 state
                 → ReentrantLock、ReentrantReadWriteLock 的写锁
  共享 Shared   ：多个线程可同时获取
                 → CountDownLatch、Semaphore、ReadWriteLock 的读锁

CountDownLatch 与 CyclicBarrier 的本质区别： 前者是一个线程等 N个线程（计数只减不增，归零后永久失效）；后者是N 个线程互相等（到齐后自动重置，可循环使用）。还有一个工程细节：CyclicBarrier 任一线程超时或被中断，会让所有在屏障上等待的线程抛 BrokenBarrierException，屏障进入「损坏」状态，需要 reset() 才能恢复 —— 这是它比 CountDownLatch 危险的地方。

ThreadLocal 提供线程私有的变量副本，让每个线程访问同一个 ThreadLocal 对象时拿到互不干扰的值，是典型的空间换线程安全（与 synchronized 的"时间换安全"相反）。

ThreadLocalMap 的四个设计细节：

细节实现原因
哈希算法key.threadLocalHashCode & (len - 1)，每次 new ThreadLocal 自增魔数 0x61c88647斐波那契散列，使下标在 2 的幂长度数组上均匀分布
冲突解决开放地址法（线性探测下一个槽），不是链表Entry 数量通常极少（一个线程往往只有几个 ThreadLocal），链表的指针开销不值得
扩容阈值size >= len * 2/3 时先 rehash 清理，真实超过 3/4 再两倍扩容开放地址法必须保持低装载因子，否则探测退化为 O(n)
key 为弱引用Entry extends WeakReference<ThreadLocal<?>>让"没人再引用的 ThreadLocal"能被 GC 回收，避免 key 泄漏

内存泄漏链路（高频面试点）：

text
栈: ThreadLocal 强引用 tl ──┐
                            ├──> ThreadLocal 对象

  key  被 GC 回收 → Entry.key == null（变成"脏 Entry"）
  value 仍被 Entry 强引用 → 只要线程不死，value 永远回收不掉
  • 根因：key 是弱引用、value 是强引用，引用链为 Thread → ThreadLocalMap → Entry → value。
  • 线程池场景被放大：核心线程永不销毁，Thread 对象生命周期等于应用生命周期，脏 Entry 的 value 就一直活着 → 累积成 OOM。
  • JDK 的补救：get / set / remove 内部会调用 expungeStaleEntry() 顺带清理部分 key == null 的 Entry，但这是启发式、不保证的（只扫描探测路径上的槽位）。
  • 唯一可靠解法：try { ... } finally { threadLocal.remove(); }。

ArrayBlockingQueue 核心实现（一把锁 + 两个条件变量）：

final ReentrantLock lock = new ReentrantLock(fair);
private final Condition notEmpty = lock.newCondition();
private final Condition notFull  = lock.newCondition();

public void put(E e) throws InterruptedException {
    lock.lockInterruptibly();
    try {
        while (count == items.length) notFull.await();  // while 防虚假唤醒
        enqueue(e);                                     // 入队后唤醒消费者
    } finally { lock.unlock(); }
}

public E take() throws InterruptedException {
    lock.lockInterruptibly();
    try {
        while (count == 0) notEmpty.await();
        return dequeue();
    } finally { lock.unlock(); }
}

LinkedBlockingQueue 则是两把锁（putLock + takeLock）+ AtomicInteger count，头尾分离因此生产消费可以真正并行，吞吐更高；代价是 size() 等需要同时持有两把锁的操作更贵。

2. 虚假唤醒与条件谓词：为什么 wait 必须写在 while 里 ​

虚假唤醒（spurious wakeup） 指线程在没有任何线程调用 notify 的情况下也可能从 wait 返回（POSIX规范允许，JVM 在部分平台上存在）。更现实的场景是：notifyAll 唤醒了全部等待者，但条件只够满足其中一个。

java
// ❌ 错误：if 判断
synchronized (lock) {
    if (queue.isEmpty()) {
        lock.wait();
    }
    Object item = queue.remove(0);  // 可能 NPE / IndexOutOfBounds
}

// ✅ 正确：while 循环重新检查条件谓词
synchronized (lock) {
    while (queue.isEmpty()) {
        lock.wait();                // 被唤醒后回到 while 再判一次
    }
    Object item = queue.remove(0);
}

根因链路： wait 返回只意味着"你被唤醒了并且重新抢到了锁"，不意味着条件成立。两个消费者同时被 notifyAll 唤醒，A 先抢到锁消费了唯一的元素，B 再抢到锁时队列已空——用 if 就会越界。

JDK 规范级结论： wait 必须永远出现在循环中，循环条件是条件谓词；Condition.await() 同理。JDK 文档原话："wait should always be used in a loop"。

notify vs notifyAll： notify 只随机唤醒一个等待者，若唤醒的恰好是"不满足条件"的那个（比如队列满时唤醒了另一个生产者），就会造成信号丢失 + 全员死等。所以默认用 notifyAll；只有在"所有等待者等的是同一个条件且唤醒一个就够"时才敢用 notify。ReentrantLock 的 Condition 则允许按条件分组（notFull / notEmpty 两个队列），可以精准 signal，这是它相对 synchronized 的核心优势。

3. JVM 的锁优化：偏向锁、轻量级锁、自旋、锁消除、锁粗化 ​

JDK 6 之后 synchronized 性能大幅提升，靠的是这一整套优化：

优化触发时机原理
偏向锁只有一个线程访问同步块Mark Word 记下线程 ID，后续进入只做一次 CAS 比对，无原子操作
轻量级锁有竞争但不激烈，交替执行线程栈里建 Lock Record，CAS 把 Mark Word 指向它，失败则自旋
自适应自旋轻量级锁 CAS 失败先忙等若干次而不挂起；自旋次数由上次在同一锁上自旋成功率动态调整
重量级锁自旋失败 / 竞争激烈膨胀为 ObjectMonitor，线程进内核态挂起（BLOCKED）
锁消除JIT 逃逸分析证明对象不会逃逸直接把 monitorenter / monitorexit 删掉
锁粗化连续多次对同一锁加解锁把多个小同步块合并成一个大的，减少加解锁次数

偏向锁为何在 JDK 15 被默认关闭（JEP 374）：

  1. 撤销成本高：偏向锁撤销需要到达安全点并 STW，一旦出现竞争，批量撤销会造成明显停顿。
  2. 收益场景萎缩：现代应用普遍用线程池 + JUC，"单线程独占同一个锁"的场景大幅减少。
  3. 维护代价大：偏向锁逻辑渗透到 JVM 大量代码路径里，阻碍其他优化（如 Lilliput 压缩对象头）。

所以在 JDK 15+ 上回答锁升级，务必加一句"JDK 15 已默认禁用偏向锁，JDK 18 彻底移除，现在是无锁 → 轻量级 → 重量级三级"，这是区分「背八股」和「真的看过版本变更」的分水岭。

CPU 层面（x86）： 用 hsdis 反汇编可以看到 volatile 写被编译成带 lock 前缀的指令（如 lock addl $0x0,(%rsp)）。lock 前缀做了三件事：

  1. 锁定缓存行（现代 CPU 用缓存锁而非总线锁）；
  2. 把当前 CPU 的 store buffer 全部写回主内存（或 L3），使修改对其他核可见；
  3. 触发 MESI 协议的失效消息，让其他核的该缓存行标记为 Invalid，下次读必须重新加载。

lock addl $0x0,(%rsp) 是对栈顶做一次"加 0"的空操作，目的纯粹是借 lock 前缀的内存屏障语义，这是 x86 上实现 StoreLoad 屏障的惯用技巧（比 mfence 在部分 CPU 上更快）。

x86 的"强内存模型"带来的误区： x86 本身只允许 StoreLoad 重排（TSO 模型），所以在 x86 上漏写 volatile 的 bug 常常测不出来，但在 ARM（如 Apple Silicon、鲲鹏服务器）这种弱内存模型机器上就会暴露。不要用"我本地跑了一万次没问题"来证明并发正确性。

6. DCL 单例为什么必须加 volatile ​

java
public class Singleton {
    private static volatile Singleton instance;   // volatile 不可省

    public static Singleton getInstance() {
        if (instance == null) {                   // 第一次检查：无锁快速路径
            synchronized (Singleton.class) {
                if (instance == null) {           // 第二次检查：防止重复创建
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

new Singleton() 实际是三条字节码指令，不是原子操作：

text
① 分配内存空间      (new)
② 调用构造方法初始化对象  (invokespecial <init>)
③ 把引用赋给 instance    (putstatic)

JIT / CPU 允许 ② 和 ③ 重排序 → 变成 ① ③ ②

线程 A: ① 分配内存 → ③ instance 已非 null（但对象还没初始化！）
线程 B: 第一次检查 instance != null → 直接 return
       → 拿到一个"半初始化对象"，访问字段全是默认值 → NPE / 脏数据
  • volatile 通过 StoreStore 屏障禁止 ② ③ 重排，保证引用可见时对象已完全构造；同时保证线程 B 读到的是最新值（可见性）。
  • 只加 synchronized 不够：synchronized 只保证临界区内的原子性与进出时的可见性，并不禁止临界区内部的指令重排；线程 B 的第一次检查是在锁外读的，没有任何同步语义。

} while (!ref.compareAndSet(prev, next));

8. LongAdder 原理：分段 CAS + 伪共享消除 ​

AtomicLong 在高并发下所有线程 CAS 同一个 value，失败率随线程数急剧上升。LongAdder 的思路是空间换时间：把一个热点变量拆成多个。

text
LongAdder
  ├── base（无竞争时直接 CAS 这里）
  └── Cell[] cells（有竞争时才初始化，长度为 2 的幂，最大 ≈ CPU 核数）
          ├── Cell[0].value   ← 线程 T1 按 probe 哈希命中
          ├── Cell[1].value   ← 线程 T2
          └── ...

sum() = base + Σ cells[i].value
java
public void add(long x) {
    Cell[] cs; long b, v; int m; Cell c;
    if ((cs = cells) != null || !casBase(b = base, b + x)) {  // ① 先试 base
        boolean uncontended = true;
        if (cs == null || (m = cs.length - 1) < 0
            || (c = cs[getProbe() & m]) == null                // ② 按线程 probe 定位 Cell
            || !(uncontended = c.cas(v = c.value, v + x))) {   // ③ CAS 自己的 Cell
            longAccumulate(x, null, uncontended);              // ④ 扩容 / 重散列 / 初始化
        }
    }
}

四个关键设计：

  1. getProbe() 读的是 Thread.threadLocalRandomProbe，相当于线程的哈希值；CAS 失败时调用 advanceProbe() 换一个槽再试（而不是死磕同一个 Cell）。
  2. cells 懒初始化：没有竞争时只用 base，退化为 AtomicLong，零额外内存。
  3. 扩容上限≈ CPU 核数：再多也没意义，因为同时真正并行的线程数就那么多。
  4. @sun.misc.Contended 消除伪共享：
java
@sun.misc.Contended static final class Cell {
    volatile long value;
    // ...
}

伪共享（False Sharing）是什么： CPU 缓存以缓存行（通常 64 字节）为单位加载。两个毫不相关的变量若落在同一缓存行，一个核改 A 会让另一个核缓存的 B 整行失效（MESI 失效风暴），性能可能差 5~10 倍。Cell 只有 8 字节，8 个 Cell 就会挤在一行里——@Contended 通过填充到独占一个缓存行来解决（需 -XX:-RestrictContended 才能在用户代码使用，JDK 内部类默认生效）。

选型结论：

场景选择理由
低并发 / 需要精确的 CAS 语义AtomicLongincrementAndGet 返回值精确，compareAndSet 可用
高并发纯计数（QPS、埋点）LongAdder吞吐高一个量级
需要实时精确总数AtomicLongLongAdder.sum() 不是原子快照，统计期间有写入会不准

9. AQS 源码精读：acquire 的完整链路 ​

public final void acquire(int arg) {
    if (!tryAcquire(arg) &&                                  // ① 子类实现，抢一次
        acquireQueued(addWaiter(Node.EXCLUSIVE), arg))       // ② 入队 → ③ 排队自旋

② addWaiter：CAS 入队（尾分叉问题）

java
private Node addWaiter(Node mode) {
    Node node = new Node(Thread.currentThread(), mode);
    for (;;) {
        Node t = tail;
        if (t == null) {                 // 队列为空，先 CAS 建哨兵头节点（懒初始化）
            if (compareAndSetHead(new Node())) tail = head;
        } else {
            node.prev = t;               // ★ 先设 prev（此时 t.next 还没指向 node）
            if (compareAndSetTail(t, node)) {
                t.next = node;           // ★ 再设 next，这两步不是原子的
                return node;
            }
        }
    }
}

这就是"AQS 为什么从 tail 往前遍历"的答案：compareAndSetTail 成功到 t.next = node 之间存在窗口，此刻从 head 向后遍历会漏掉新节点，但 node.prev 一定已经设好，所以 unparkSuccessor 里从 tail 反向找最靠前的有效节点才是安全的。

③ acquireQueued：自旋 + 挂起

java
final boolean acquireQueued(Node node, int arg) {
    boolean interrupted = false;
    try {
        for (;;) {
            Node p = node.predecessor();
            if (p == head && tryAcquire(arg)) {   // 只有"老二"才有资格抢锁
                setHead(node);                    // 抢到 → 自己变哨兵头，断开旧 head
                p.next = null;                    // 帮助 GC
                return interrupted;
            }
            if (shouldParkAfterFailedAcquire(p, node))
                interrupted |= parkAndCheckInterrupt();  // 真正挂起
        }
    } catch (Throwable t) {
        cancelAcquire(node);                      // 异常时把节点标记 CANCELLED 并摘除
        throw t;
    }
}

shouldParkAfterFailedAcquire：挂起前的三种处理

java
private static boolean shouldParkAfterFailedAcquire(Node pred, Node node) {
    int ws = pred.waitStatus;
    if (ws == Node.SIGNAL) return true;           // 前驱承诺会唤醒我 → 可以安心睡
    if (ws > 0) {                                 // 前驱是 CANCELLED(1) → 向前跳过
        do { node.prev = pred = pred.prev; } while (pred.waitStatus > 0);
        pred.next = node;
    } else {
        compareAndSetWaitStatus(pred, ws, Node.SIGNAL);  // 把前驱改成 SIGNAL，下轮再判
    }
    return false;                                 // 返回 false → 再自旋一次确认
}

三个必须记住的点： ① 挂起前至少多试一轮（避免"刚好锁已释放却白白挂起"的开销）；② waitStatus 设在前驱节点上，表示"我有责任唤醒后继"；③ CANCELLED 节点在这里被顺手清理，AQS 没有独立的清理线程。

release：唤醒后继

java
public final boolean release(int arg) {
    if (tryRelease(arg)) {                        // 子类实现，state 归零才算真正释放
        Node h = head;
        if (h != null && h.waitStatus != 0) unparkSuccessor(h);
        return true;
    }
    return false;
}

Condition 的条件队列与同步队列迁移（AQS 最精妙的部分）：

text

11. 线程池源码：ctl、Worker 与 getTask 的回收逻辑 ​

ctl：一个 AtomicInteger 装两个状态

java
private final AtomicInteger ctl = new AtomicInteger(ctlOf(RUNNING, 0));
private static final int COUNT_BITS = Integer.SIZE - 3;      // 29
private static final int CAPACITY   = (1 << COUNT_BITS) - 1; // 低 29 位：最大线程数 ≈ 5 亿

private static int runStateOf(int c) { return c & ~CAPACITY; } // 高 3 位：运行状态
private static int workerCountOf(int c) { return c & CAPACITY; }
private static int ctlOf(int rs, int wc) { return rs | wc; }

为什么合成一个变量？ 为了用一次 CAS 同时修改"状态 + 线程数"，避免两个变量之间出现不一致的中间态（比如状态已 SHUTDOWN 但线程数还在涨）。这是并发设计里"把多个需要同时变更的字段压进一个原子变量"的经典技巧。

Worker：自己就是一个 AQS

java
private final class Worker extends AbstractQueuedSynchronizer implements Runnable {
    final Thread thread;
    Runnable firstTask;
    volatile long completedTasks;

    Worker(Runnable firstTask) {
        setState(-1);                                  // ★ 禁止中断，直到 runWorker 开始
        this.firstTask = firstTask;
        this.thread = getThreadFactory().newThread(this);
    }
    protected boolean isHeldExclusively() { return getState() != 0; }
    protected boolean tryAcquire(int unused) { return compareAndSetState(0, 1); }
}
  • Worker 继承 AQS 实现了一把不可重入的独占锁，用途是标记"我正在执行任务"：shutdown() 只中断空闲（能被 tryLock 成功）的 Worker，正在跑任务的不打扰；shutdownNow() 则无视锁全部中断。
  • 构造时 setState(-1) 是为了防止线程还没进入 runWorker 就被 interruptIdleWorkers 中断。

runWorker：Worker 的一生

java
final void runWorker(Worker w) {
    Runnable task = w.firstTask; w.firstTask = null;
    w.unlock();                                 // state 0 → 允许中断
    boolean completedAbruptly = true;
    try {
        while (task != null || (task = getTask()) != null) {  // ★ 核心循环
            w.lock();                           // 标记忙碌
            try {
                beforeExecute(w.thread, task);  // 钩子：可做 MDC / 链路透传
                task.run();                     // ★ 直接 run()，不是 start()
                afterExecute(task, null);
            } finally {
                task = null; w.completedTasks++; w.unlock();
            }
        }
        completedAbruptly = false;
    } finally {
        processWorkerExit(w, completedAbruptly); // 清理 + 必要时补充新 Worker
    }
}

getTask：线程回收的真正发生地

java
private Runnable getTask() {
    boolean timedOut = false;
    for (;;) {
        int c = ctl.get();
        // ① 状态校验：SHUTDOWN 且队列空，或 STOP → 线程数减一并退出
        if (runStateAtLeast(c, SHUTDOWN) && (runStateAtLeast(c, STOP) || workQueue.isEmpty())) {
            decrementWorkerCount();
            return null;
        }
        int wc = workerCountOf(c);
        // ② 是否需要超时回收：超出核心数，或开启了 allowCoreThreadTimeOut
        boolean timed = allowCoreThreadTimeOut || wc > corePoolSize;
        if ((wc > maximumPoolSize || (timed && timedOut))
            && (wc > 1 || workQueue.isEmpty())) {
            if (compareAndDecrementWorkerCount(c)) return null;  // ★ 回收点
            continue;
        }
        try {
            // ③ 核心线程 take() 无限阻塞；非核心 poll(keepAlive) 超时返回 null
            Runnable r = timed ? workQueue.poll(keepAliveTime, NANOSECONDS) : workQueue.take();
            if (r != null) return r;
            timedOut = true;
        } catch (InterruptedException retry) {
            timedOut = false;
        }
    }
}

三个必须记住的点：

  1. "核心线程不回收"的本质不是什么特殊标记，而是走了 take() 这个无限阻塞分支；线程池里没有任何字段区分哪个线程是核心线程，只看"当前线程数是否超过 corePoolSize"。
  2. 开启 allowCoreThreadTimeOut(true) 后核心线程也会被回收，适合流量稀疏的定时任务池。
  3. 线程复用的关键是 task.run()：Worker 线程只 start() 过一次，之后在 while 循环里不断取任务直接调用 run()，所以同一个线程会串行执行成千上万个任务——这也是 ThreadLocal 必须 remove 的根本原因。

14. 死锁：四个必要条件、jstack 定位与破除策略 ​

// 经典转账死锁：两个线程以相反顺序加锁

    synchronized (from) {
        synchronized (to) {           // 线程 A: lock(a)→lock(b)；线程 B: lock(b)→lock(a)
            from.debit(amount);
            to.credit(amount);
        }

四个必要条件（缺一不可，破除任意一个即可解开）：

条件含义破除手段
互斥资源同一时刻只能被一个线程占用几乎无法破除（锁的本质）
占有且等待持有 A 的同时去申请 B一次性申请全部资源（tryLock 全拿到才干活）
不可抢占已获得的资源不能被强行剥夺用 tryLock(timeout)，超时就主动释放已有锁
循环等待形成环形等待链按固定顺序加锁（如按对象 hashCode / 账号 ID 排序）
java
// ✅ 解法一：固定加锁顺序（按唯一且稳定的 ID 排序）
void transferSafe(Account from, Account to, long amount) {
    Account first  = from.getId() < to.getId() ? from : to;
    Account second = from.getId() < to.getId() ? to : from;
    synchronized (first) {
        synchronized (second) { from.debit(amount); to.credit(amount); }
    }
}

// ✅ 解法二：tryLock + 超时 + 退避重试（破"不可抢占"）
boolean transferTry(Account from, Account to, long amt) throws InterruptedException {
    while (true) {
        if (from.lock.tryLock(50, TimeUnit.MILLISECONDS)) {
            try {
                if (to.lock.tryLock(50, TimeUnit.MILLISECONDS)) {
                    try { from.debit(amt); to.credit(amt); return true; }
                    finally { to.lock.unlock(); }
                }
            } finally { from.lock.unlock(); }
        }
        Thread.sleep(ThreadLocalRandom.current().nextInt(10, 50)); // ★ 随机退避防活锁
    }
}

注意：死锁解开后要防"活锁"——两个线程同时超时、同时重试、再次冲突，无限循环。所以重试前必须加随机退避（抖动），这和网络重试的指数退避是同一个思路。

15. CompletableFuture 的四个生产级坑 ​

坑 1：默认线程池 commonPool 是全 JVM 共享的

java
// ❌ 不传池 → ForkJoinPool.commonPool()，并行度 = CPU核数 - 1
CompletableFuture.supplyAsync(() -> rpcCall());   // 一个慢 IO 拖垮全应用的异步编排

// ✅ 业务自己的池，并按业务域隔离（订单池、营销池互不影响）
CompletableFuture.supplyAsync(() -> rpcCall(), ORDER_POOL);

更隐蔽的是：commonPool 的线程是守护线程，若 main 结束它们会被直接杀掉，任务可能没跑完就没了。

坑 2：thenApply vs thenApplyAsync 的执行线程不确定

方法执行线程
thenApply不确定：前一步已完成则由调用 thenApply 的线程执行；未完成则由完成前一步的那个线程执行
thenApplyAsync明确提交到指定池（不传则 commonPool）

这会导致偶发的线程切换，如果回调里依赖了 ThreadLocal（比如 MDC 的 traceId），就会出现"本地能复现、线上偶发丢 traceId"的诡异问题。涉及上下文时请显式用 ...Async(fn, pool)。

坑 3：异常不会自动传播到"兄弟"分支，且 allOf 不短路

java
CompletableFuture<Void> all = CompletableFuture.allOf(f1, f2, f3);
all.join();   // ★ 若 f2 异常，这里抛 CompletionException；f1/f3 仍会跑完

// ✅ 正确：每个分支自己兜底，保证 allOf 永远不炸
CompletableFuture<Coupon> safe = couponFuture
        .exceptionally(ex -> { log.warn("优惠券查询失败，降级", ex); return Coupon.empty(); });

坑 4：没有超时控制会导致请求无限挂起

java
// JDK 8 只能靠 get(timeout)，且不会取消上游任务

// JDK 9+ 提供了更好的 API
future.orTimeout(500, TimeUnit.MILLISECONDS)              // 超时抛 TimeoutException
      .completeOnTimeout(DEFAULT_VO, 500, TimeUnit.MILLISECONDS);  // 超时给默认值

三个必须记住的点： ① 永远传自定义池；② 涉及 ThreadLocal 一律用 Async 显式指定池；③ 每个弱依赖分支都要有 exceptionally + 超时降级，否则异步聚合的可用性等于所有下游可用性的乘积。

核心变化：线程不再是稀缺资源。

调度模型：

text
虚拟线程（Virtual Thread，百万个，JVM 管理，存在堆上）
        ↓ mount / unmount（挂载与卸载）
载体线程（Carrier Thread = ForkJoinPool 的平台线程，数量 ≈ CPU 核数）
        ↓ 1:1

遇到阻塞 IO 时：虚拟线程把栈帧拷到堆上并 unmount，
              载体线程立刻去跑别的虚拟线程 → 零线程浪费

pinning（钉住）：虚拟线程最大的坑

某些情况下虚拟线程无法 unmount，会把载体线程一起阻塞住，等于退化成平台线程：

触发场景JDK 21 行为应对
在 synchronized 块内阻塞pinned（载体被占住）换成 ReentrantLock
执行 native 方法 / JNI 中阻塞pinned无法避免，减少此类调用
Object.wait()pinned换 Condition.await()

JDK 24（JEP 491）已经解决了 synchronized 的 pinning 问题，但在 21 这个 LTS 上回答时必须提到这个限制——这是真正用过虚拟线程的标志。诊断方式：-Djdk.tracePinnedThreads=full 会打印被钉住的栈。

使用准则：

  1. 不要池化虚拟线程。它本身就是"廉价、一次性"的，用 newVirtualThreadPerTaskExecutor() 而不是固定大小池；池化反而把并发度又限制回去了。
  2. 限流不再靠线程数，改用 Semaphore。以前"池子 50 个线程"天然就是对下游的限流；虚拟线程没有这个限制，必须显式加信号量，否则会把下游打崩。
  3. 只对 IO 密集有效。CPU 密集任务的瓶颈是核数，虚拟线程不会让计算变快。
  4. ThreadLocal 仍可用但要慎用：百万虚拟线程 × 每个一份副本 = 内存爆炸，JDK 21+ 推荐 ScopedValue（JEP 429/446）。

17. ForkJoinPool 与工作窃取：并行流的隐患 ​

text
传统线程池：所有线程抢一个全局队列  →  队列是竞争热点

ForkJoinPool：每个 Worker 一个双端队列（Deque）
  Worker-1: [t1][t2][t3]   ← 自己从队头 LIFO 取（缓存友好）
  Worker-2: []             ← 空了，从 Worker-1 的队尾 FIFO "窃取"
                              （两端操作，几乎不冲突）

ForkJoinTask 的分治模板：

java
class SumTask extends RecursiveTask<Long> {
    private static final int THRESHOLD = 10_000;   // 阈值：太小则拆分开销大于收益
    private final long[] arr; private final int lo, hi;

    protected Long compute() {
        if (hi - lo <= THRESHOLD) {                // ① 小到一定程度直接算
            long sum = 0;
            for (int i = lo; i < hi; i++) sum += arr[i];
            return sum;
        }
        int mid = (lo + hi) >>> 1;
        SumTask left  = new SumTask(arr, lo, mid);
        SumTask right = new SumTask(arr, mid, hi);
        left.fork();                               // ② 异步执行左半
        Long r = right.compute();                  // ③ ★ 当前线程直接算右半，不要两次 fork
        return left.join() + r;                    // ④ 合并
    }
}

fork() + compute() 比两次 fork() + 两次 join() 更优：减少一次任务入队和线程切换，这是 JDK 文档推荐的写法。

parallelStream 的三个坑（面试高频）：

选型结论： 并行流只适合纯 CPU 计算 + 数据量大（万级以上）+ 无共享状态 + 无 IO 的场景；其余一律用 CompletableFuture + 自定义线程池。

题 1：synchronized 和 ReentrantLock 有什么区别？ ​

精简口述答案：

两者都是可重入的独占锁，但层次不同：synchronized 是 JVM 层面的关键字，靠对象头 Mark Word 和 ObjectMonitor 实现，加解锁由 JVM 自动完成，异常时自动释放；ReentrantLock 是 JDK 层面的类，基于 AQS 的 volatile state 加 CLH 队列，必须手动 lock / unlock，并且 unlock 一定要写在 finally 里。

功能上 ReentrantLock 是超集，多了四样 synchronized 没有的能力：可中断（lockInterruptibly）、可超时（tryLock(timeout)）、可公平（构造参数 true）、多条件队列（多个 Condition 实现精准唤醒，比如阻塞队列的 notFull 和 notEmpty）。

性能上，JDK 6 之后 synchronized 引入了偏向锁、轻量级锁、自适应自旋、锁消除、锁粗化，低竞争下两者差距很小。所以我的选型原则是：能用 synchronized 就用它（代码简洁、不会漏释放、JVM 还能帮你优化掉），只有需要上面那四种高级能力时才换 ReentrantLock。

连环追问链：

  1. 追问：锁升级的完整过程是什么？
    • 答：无锁 → 偏向锁 → 轻量级锁 → 重量级锁，单向不可逆。偏向锁在 Mark Word 里记线程 ID，同一线程再进只需比对 ID；出现第二个线程竞争就升级为轻量级锁，线程在自己栈里建 Lock Record 并 CAS 指向它，失败则自适应自旋；自旋还失败就膨胀为重量级锁，走 ObjectMonitor，线程进内核态挂起变成 BLOCKED。
  2. 追问：JDK 15 对偏向锁做了什么改动？为什么？
    • 答：JEP 374 默认禁用偏向锁，JDK 18 彻底移除。原因有三：偏向锁撤销需要到安全点 STW，代价高；现代应用普遍用线程池 + JUC，"单线程独占一把锁"的场景大幅减少，收益萎缩；偏向锁代码渗透整个 JVM，阻碍 Lilliput 这类对象头压缩优化。所以在新版本上答锁升级要说"现在是无锁 → 轻量级 → 重量级三级"。
  3. 追问：为什么 synchronized 是可重入的？重入计数存在哪里？
    • 答：ObjectMonitor 里有 _owner和 _recursions 两个字段，_owner 记录持有者线程，同一线程再次进入只是 _recursions++，退出时递减，减到 0 才真正释放。ReentrantLock 则是把重入次数累加在 AQS 的 state 上。可重入的意义是避免"自己被自己锁死"——比如一个 synchronized 方法调用同类的另一个 synchronized 方法。
  4. 追问：ReentrantLock 的公平锁和非公平锁差在哪？为什么默认非公平？
    • 答：代码上只差一个 hasQueuedPredecessors() 判断——公平锁抢锁前先看队列里有没有人等，有就乖乖排队；非公平锁直接 CAS 插队。默认非公平是因为吞吐量高一个数量级：唤醒一个 park 的线程需要几微秒上下文切换，这期间锁是空闲的，让正在 CPU 上跑的线程直接拿走能填满这个空窗期。代价是理论上可能饥饿，但实测概率很低。
  5. 追问：synchronized 锁字符串常量会有什么问题？
    • 答：字符串常量在常量池里是同一个对象，不同模块各自 synchronized("lock") 会意外共享同一把锁，造成完全无关的代码互相阻塞，而且极难排查。同理也不能锁 Integer（有缓存池）、Boolean，以及不能锁会被重新赋值的变量（锁对象变了就等于没锁）。正确做法是 private static final Object LOCK = new Object();。
  6. 追问：Condition 的 await / signal 和 wait / notify 底层有什么不同？
    • 答：wait / notify 操作的是 ObjectMonitor 里的 _WaitSet，一个锁只有一个等待集合；Condition 则是 AQS 的条件队列，await 会先 fullyRelease 完全释放锁（保存重入次数）再 park，signal 把节点从条件队列转移到同步队列，它还得重新排队抢锁才能真正返回。关键区别是 Condition 可以有多个，支持按条件精准唤醒，避免 notifyAll 的无效唤醒风暴。

✅ 项目关联话术（按真实经历替换）：

我在做库存扣减的本地缓存刷新时用过 ReentrantLock 的 tryLock：缓存过期瞬间会有大量请求同时回源 DB，我用 tryLock(0) 让只有一个线程去回源，其余线程直接拿旧值返回，避免了缓存击穿。这里必须用 ReentrantLock 而不是 synchronized，因为 synchronized 没有"抢不到就立刻放弃"的语义，所有线程都会排队阻塞，反而把 Tomcat 线程全耗光了。

题 2：线程池的 7 个核心参数是什么？执行流程是怎样的？参数怎么定？ ​

精简口述答案：

7 个参数是：corePoolSize（核心线程数）、maximumPoolSize（最大线程数）、keepAliveTime + unit（非核心线程空闲存活时间）、workQueue（任务队列）、threadFactory（线程工厂）、handler（拒绝策略）。

执行流程是四级流水线：① 当前线程数 < core 就直接建核心线程执行（不管现有线程是否空闲）；② 否则入队；③ 队列满了才扩容到 max，新建的是非核心线程；④ 线程也满了就走拒绝策略。这里最容易答错的是顺序——是"先入队再扩容"，不是"先扩线程再入队"，所以用无界队列时 maximumPoolSize 这个参数永远不会生效。

参数怎么定：先按任务类型估初值，CPU 密集 N+1、IO 密集 N*2 起步或用 N × 利用率 × (1 + 等待/计算) 精算；但公式只给初值，最终必须靠压测定，看 QPS 拐点、P99、CPU 和队列积压。队列长度按"可接受的排队延迟 ÷ 单任务耗时"反推。另外生产上一律禁用 Executors 工厂方法，因为 newFixedThreadPool 队列无界会 OOM、newCachedThreadPool 线程数无上限也会 OOM。

连环追问链：

  1. 追问：为什么核心线程优先于复用空闲线程？
    • 答：这是 execute 第一步的设计——只要 workerCountOf(c) < corePoolSize 就 addWorker，不检查现有线程是否空闲。目的是让线程池尽快"预热"到核心规模，因为核心线程是常驻的，早建好后续就不用再付创建成本；而且判断"有没有空闲线程"本身需要额外的同步开销。
  2. 追问：线程池为什么不回收核心线程？源码里是怎么区分核心线程的？
    • 答：源码里根本没有区分哪个线程是核心线程。getTask() 里判断 timed = allowCoreThreadTimeOut || wc > corePoolSize，为 true 就走 poll(keepAliveTime) 超时返回 null 然后退出，为 false 就走 take() 无限阻塞。所以"核心线程不死"的本质是它走了 take() 这条永不超时的分支。调 allowCoreThreadTimeOut(true) 核心线程也会被回收。
  3. 追问：有哪几种拒绝策略？线上你会怎么选？
    • 答：JDK 自带四种——AbortPolicy 抛 RejectedExecutionException（默认）、CallerRunsPolicy 调用者线程自己执行（天然反压）、DiscardPolicy 静默丢弃、DiscardOldestPolicy 丢最老的再重试。线上我倾向自定义：先打点告警，然后按业务重要性分流——核心链路（下单）落 MQ 或降级到同步执行，非核心（埋点、推送）直接丢弃并记日志。绝对不用 DiscardPolicy，静默丢数据是最可怕的。
  4. 追问：CallerRunsPolicy 有什么隐患？
    • 答：它让提交任务的线程自己跑任务。如果提交者是 Tomcat 的 Web 线程，就会把 Web 线程占住，请求响应变慢，连锁反应是 Tomcat 线程池也打满，整个服务不可用。它的优点是天然反压（提交变慢了，上游自然就慢下来），所以适合离线批处理这种"宁慢不丢"的场景，不适合在线接口。
  5. 追问：线程池的 5 种状态和 shutdown / shutdownNow 的区别？
    • 答：RUNNING（接新任务、处理队列）→ SHUTDOWN（不接新任务但处理完队列）→ STOP（不接新任务、丢弃队列、中断正在执行的任务）→ TIDYING（任务全空、线程全销毁，执行 terminated() 钩子）→ TERMINATED。状态和线程数一起存在 ctl 这个 AtomicInteger 里，高 3 位状态、低 29 位线程数，这样一次 CAS 就能原子地改两个值。shutdown 温和，只中断空闲线程；shutdownNow 会中断所有线程并返回未执行的任务列表。
  6. 追问：怎么做动态线程池？哪些参数能改？
    • 答：corePoolSize、maximumPoolSize、keepAliveTime、handler 都有 setter 可以运行时改；队列容量是 final 改不了，所以要么自己复制 LinkedBlockingQueue 源码把 capacity 改成 volatile 并加 setter，要么用现成的 DynamicTp、Hippo4j。再把参数接到 Nacos / Apollo 上监听变更，同时把 getActiveCount、getQueue().size()、拒绝次数接到 Prometheus 做告警。
  7. 追问：execute 和 submit 的异常处理有什么区别？
    • 答：execute 的异常会一路抛出线程，触发 UncaughtExceptionHandler 并打印堆栈，该线程销毁后线程池补一个新的；submit 把任务包成 FutureTask，run 里 catch (Throwable) 后 setException 存进 outcome 字段，不 get() 就永远看不到异常，这是线上"任务静默失败"的常见原因。兜底办法是任务内部全包 try-catch，或者重写 afterExecute 把 Future 的异常挖出来统一打日志。

我接手的一个报表导出服务曾经因为用了 Executors.newFixedThreadPool(10) 出过一次 OOM：队列是无界的 LinkedBlockingQueue，大促期间导出请求激增，几万个任务对象（每个还持有查询参数和部分结果集）全堆在队列里把堆打满了。我的改造是三件事：换成手动 new ThreadPoolExecutor 并把队列改成容量 2000 的 ArrayBlockingQueue；拒绝策略自定义为"落 MQ 延迟重试 + 告警"；最后把队列积压和拒绝次数接到监控，积压超 80% 就告警。改完之后同样的流量下内存平稳，再也没有 OOM。

题 3：AQS 的原理是什么？它是怎么支撑整个 JUC 的？ ​

精简口述答案：

AQS 是 AbstractQueuedSynchronizer，JUC 几乎所有同步工具的骨架。它的核心就两样东西：一个 volatile int state 表示同步状态，一个 CLH 变体的双向等待队列存放抢不到锁的线程。

工作流程是：线程先调子类实现的 tryAcquire 尝试改 state，成功就直接执行；失败就被包成 Node 入队，然后在 acquireQueued 里自旋——只有前驱是 head 的"老二"才有资格再抢一次，抢不到就把前驱的 waitStatus 改成 SIGNAL 然后 LockSupport.park() 挂起。释放时 tryRelease 把 state 改回去，再 unparkSuccessor 唤醒后继节点。

AQS 用的是模板方法模式：它把入队、挂起、唤醒、取消这些最难写的部分都实现好了，子类只需要重写 tryAcquire / tryRelease（独占）或 tryAcquireShared / tryReleaseShared（共享），并定义 state 的语义。所以 ReentrantLock 的 state 是重入次数、Semaphore 是剩余许可数、CountDownLatch 是剩余计数、ReentrantReadWriteLock 把 state 拆成高 16 位读锁、低 16 位写锁——换个 state 语义就是一个新的同步器，这就是它支撑整个 JUC 的方式。

连环追问链：

  1. 追问：AQS 的队列为什么要从 tail 往前遍历？
    • 答：因为 addWaiter 入队是两步非原子操作：先 node.prev = t，再 compareAndSetTail 成功后才 t.next = node。中间存在一个窗口，此时新节点的 prev 已经接好但前驱的 next 还是 null——这叫尾分叉。所以从 head 向后遍历会漏掉节点，而反向遍历靠 prev 一定能走通，unparkSuccessor 和 cancelAcquire 里的遍历都是反向的。
  2. 追问：head 节点为什么是个"空"节点？
    • 答：head 是哨兵节点（dummy），不关联任何线程，它的作用是承载 waitStatus —— 队列里每个节点的唤醒职责都写在前驱节点的 waitStatus 上，队首线程需要一个前驱来存 SIGNAL 标记。而且线程抢到锁之后会 setHead(node) 把自己变成新的哨兵并清空 thread 字段，这样既复用了节点又帮助了 GC。
  3. 追问：独占模式和共享模式的区别是什么？
    • 答：独占模式（Node.EXCLUSIVE）同一时刻只有一个线程能拿到 state，释放时只唤醒一个后继，典型是 ReentrantLock、写锁。共享模式（Node.SHARED）允许多个线程同时持有，关键差别是 setHeadAndPropagate 的唤醒传播：一个线程拿到共享锁后会继续唤醒后面的共享节点，形成"连锁唤醒"，典型是 Semaphore、CountDownLatch、读锁。
  4. 追问：CountDownLatch 和 CyclicBarrier 的实现差别？
    • 答：CountDownLatch 基于 AQS 共享模式，state 初始化为计数，countDown 就是 releaseShared 把 state 减一，减到 0 时唤醒所有在 await 上阻塞的线程；一次性、不可重置。CyclicBarrier 根本不是直接用 AQS，而是用 ReentrantLock + Condition 实现的：每个线程到达就 count-- 并 await，最后一个到达的执行可选的 barrierAction 并 signalAll，然后重置 count 进入下一代（generation），所以可以循环使用。
  5. 追问：ReentrantReadWriteLock 怎么用一个 state 表示两种锁？会有什么问题？
    • 答：把 32 位的 state 拆开，高 16 位记读锁的持有总数、低 16 位记写锁的重入次数，所以读锁最多 65535 个。各线程自己的读锁重入次数则存在 ThreadLocal（HoldCounter）里。它的问题是写饥饿：读多写少时读锁源源不断进来，写线程可能长期拿不到锁，所以它提供了 apparentlyFirstQueuedIsExclusive 判断——非公平模式下如果队首是写线程，新来的读线程也要排队。另外它不支持锁升级（持读锁时直接 writeLock().lock() 会死锁），只支持降级（持写锁时获取读锁再释放写锁）。
  6. 追问：AQS 的 cancelAcquire 在什么时候触发？
    • 答：三种情况——lockInterruptibly 时线程被中断、tryLock(timeout) 超时、tryAcquire 抛异常。处理是把该节点 waitStatus 置为 CANCELLED(1)，然后从队列里摘除；它不会立刻清理整条链，剩下的脏节点由后续线程在 shouldParkAfterFailedAcquire 里"顺路"跳过并清理。AQS 没有专门的清理线程，这是一种惰性清理设计。

✅ 项目关联话术（按真实经历替换）：

我在做批量导入的并发控制时自己基于 AQS 写过一个"限流闭锁"：业务要求"最多 5 个分片并行处理，且主线程要等全部完成"。一开始我用 Semaphore + CountDownLatch 两个对象组合，后来发现用 AQS 共享模式把两件事合成一个同步器更清晰——state 既当许可数又当完成计数。虽然最终上线用的还是标准库的组合（毕竟自己写的同步器要承担正确性风险），但这次实践让我真正搞明白了 tryAcquireShared 返回值的含义：返回负数表示失败要入队，0 表示成功但后面没资源了，正数表示成功且还有剩余可以继续传播唤醒。

题 4：volatile 能保证什么？JMM 和 happens-before 是什么？ ​

精简口述答案：

volatile 保证两件事：可见性和有序性（禁止指令重排）。它不保证原子性，所以 i++ 这种复合操作用 volatile 依然是线程不安全的，必须用 AtomicInteger 或加锁。

底层实现是内存屏障：volatile 写之前插 StoreStore、之后插 StoreLoad；volatile 读之后插 LoadLoad 和 LoadStore。在 x86 上，volatile 写会被编译成带 lock 前缀的指令（比如 lock addl $0x0,(%rsp)），它会锁定缓存行、把 store buffer 刷回内存，并通过 MESI 协议让其他核的对应缓存行失效。

JMM 是 Java 内存模型，它规定了多线程下共享变量的访问规则。而 happens-before 是 JMM 的核心——它不是说"时间上先发生"，而是说"前一个操作的结果对后一个操作可见"。有八条规则，最常用的是：程序顺序规则（单线程内按代码顺序）、监视器锁规则（解锁 happens-before 后续加锁）、volatile 规则（写 happens-before 后续读）、线程启动规则（start() 之前的操作对新线程可见）、线程终止规则（线程内所有操作 happens-before join() 返回），以及传递性。有了 happens-before，我们就不需要去关心底层屏障的细节，只要能推出"A happens-before B"就说明并发是安全的。

连环追问链：

  1. 追问：volatile 为什么不能保证原子性？举个例子。
    • 答：i++ 编译成三步：读取 i、加 1、写回 i。volatile 只保证每次读拿到的是最新值、每次写立刻可见，但读到写之间的这段窗口里，别的线程完全可以插入自己的写——两个线程都读到 5，各自加 1 写回 6，结果丢了一次累加。20 个线程各加 10000 次，结果必然小于 200000。要原子就得用 AtomicInteger（CAS 自旋）或 synchronized。
  2. 追问：什么场景适合用 volatile？
    • 答：三个典型场景。① 状态标志位：volatile boolean running，一个线程写、其他线程读，没有复合操作；② DCL 单例的 instance 字段，靠的是它禁止重排的能力；③ 一写多读且写入值不依赖当前值，比如配置热更新的 volatile Config config = newConfig。判断准则就一句话：写入不依赖当前值，且没有其他变量参与不变式约束。
  3. 追问：DCL 单例为什么必须加 volatile？不加会怎样？
    • 答：new Singleton() 实际是三步：分配内存、初始化对象、把引用赋给变量。JIT 允许后两步重排，变成"先赋引用、后初始化"。这时线程 A 刚赋完引用还没初始化，线程 B 的第一次检查（在锁外，没有任何同步语义）发现 instance != null 就直接返回了一个半初始化对象，访问字段全是默认值，表现为诡异的 NPE 或脏数据。加 volatile 后 StoreStore 屏障禁止了这个重排。注意光加 synchronized 不够，因为它不禁止临界区内部的重排。
  4. 追问：volatile 和 synchronized 的区别？
    • 答：volatile 只能修饰变量，保证可见性和有序性，不保证原子性，不阻塞、无上下文切换、性能开销小；synchronized 可修饰方法和代码块，三个特性全保证，有竞争时会阻塞并可能膨胀为重量级锁。可以理解为 volatile 是轻量级的同步，适合状态通知；synchronized 适合保护临界区。
  5. 追问：happens-before 里哪条最容易被忽略？
    • 答：线程启动规则和终止规则。很多人以为"新线程里读到的变量要加 volatile"，其实 t.start() 之前主线程的所有写操作对新线程都是可见的（start 规则）；同样 t.join() 返回后，该线程内的所有写对主线程可见。这两条让"主线程准备数据 → 起线程计算 → join 后取结果"这种模式天然安全，不需要额外同步。
  6. 追问：为什么说"x86 上测不出重排 bug"？
    • 答：x86 是 TSO（Total Store Order）强内存模型，只允许 StoreLoad 一种重排，大部分漏写 volatile 的代码在 x86 上跑起来居然是对的。但 ARM / Power 是弱内存模型，允许的重排多得多——同样的代码在 Apple Silicon 的 Mac、鲲鹏或飞腾服务器上就会暴露问题。所以并发正确性必须靠 happens-before 推理，不能靠"我本地跑了一万次没问题"。

✅ 项目关联话术（按真实经历替换）：

我们有个消息消费的开关曾经踩过可见性的坑：管理后台调接口把 boolean consuming 改成 false，但消费线程的 while (consuming) 循环根本停不下来，只能靠重启。原因是这个字段没加 volatile，消费线程把它缓存在工作内存里一直读旧值（JIT 甚至可能把循环条件直接优化成常量 true）。加上 volatile 后立刻正常。这件事之后我们在 Code Review 里加了一条硬规则：所有跨线程的状态标志位必须 volatile，或者直接用 AtomicBoolean。

题 5：说一下 Java 线程的 6 种状态，以及 wait / sleep / join / park 的区别 ​

精简口述答案：

Java 线程状态定义在 Thread.State 枚举里，一共 6 个：NEW（已 new 未 start）、RUNNABLE（可运行，把操作系统层面的"就绪"和"运行中"合并了，也包含正在做 IO 阻塞的线程）、BLOCKED（等 synchronized 监视器锁）、WAITING（无限期等待，靠别人唤醒）、TIMED_WAITING（带超时的等待）、TERMINATED（结束）。

关键流转是：start() 从 NEW 到 RUNNABLE；抢 synchronized 失败进 BLOCKED；wait() / join() / park() 进 WAITING；带超时参数的 sleep(n) / wait(n) / join(n) / parkNanos 进 TIMED_WAITING；run() 结束或抛异常进 TERMINATED。注意 WAITING 被 notify() 唤醒后不是直接回 RUNNABLE，而是先进 BLOCKED 重新抢锁，抢到才回 RUNNABLE。

四个等待方法的核心区别是：wait 是 Object 方法、必须持锁调用、会释放锁；sleep 是 Thread 静态方法、不需要锁、不释放锁；join 本质是在目标线程对象上 wait，所以释放的是目标线程对象的锁（这也是不要对 Thread 对象加锁的原因）；park 是 LockSupport 提供的许可(permit)机制，不需要锁、不释放锁，且不要求 unpark 一定后发生——先 unpark 再 park 不会阻塞，这是它能安全替代 wait/notify 做 AQS 底座的关键。

连环追问链：

  1. 追问：为什么 Java 把操作系统的"就绪"和"运行中"合并成一个 RUNNABLE？

    • 答：因为 JVM 作为跨平台虚拟机，拿不到也不该依赖操作系统线程调度器的细粒度状态。一个线程是在 CPU 上跑还是在就绪队列里排队，由 OS 调度器决定、随时切换，JVM 查询到的瞬时值毫无意义。所以 Java 只区分"我有没有把自己主动挂起"这件自己能控制的事。
    • 答：一个重要的副作用是：做 socket 读写、磁盘 IO 而阻塞的线程，在 Java 里状态仍然是 RUNNABLE。所以线上 jstack 看到一堆 RUNNABLE 不代表 CPU 很忙，要结合栈顶是不是 socketRead0 这类 native 方法来判断。

  2. 追问：BLOCKED 和 WAITING 到底差在哪？为什么要分两个状态？

    • 答：BLOCKED 只有一个来源——竞争 synchronized 的监视器锁失败，被塞进 ObjectMonitor 的 _EntryList。它是被动的，线程自己没打算等，是因为锁被别人拿着才等。
    • 答：WAITING 是主动的，线程自己调 wait() / join() / park() 声明"我要等某个事件"，进入 _WaitSet 或 AQS 的条件队列。
    • 答：分开的实际价值在排查问题：jstack 里一片 BLOCKED 指向锁竞争激烈，要看锁粒度能不能拆；一片 WAITING 指向协作逻辑卡住，比如 notify 没发出来、CountDownLatch 没减到 0、从连接池拿不到连接。两者的优化方向完全不同。
    • 答：补充一个坑：ReentrantLock 抢锁失败走的是 LockSupport.park，所以状态是 WAITING / TIMED_WAITING 而不是 BLOCKED。只看状态猜不出是不是锁竞争，必须看栈。

  3. 追问：notify() 之后线程立刻变 RUNNABLE 吗？

    • 答：不是。notify() 只是把线程从 _WaitSet 挪到 _EntryList，状态从 WAITING 变成 BLOCKED。它必须重新竞争到那把 synchronized 锁，才能从 wait() 里真正返回变成 RUNNABLE。
    • 答：这也解释了为什么 notify() 之后不用急着退出同步块——通知方还持有锁，被唤醒方根本抢不到，得等通知方走出 synchronized 块。所以"notify() 放在同步块最后一行"是个优化习惯，不是正确性要求。

  4. 追问：sleep(0) 和 Thread.yield() 有什么用？

    • 答：yield() 是给调度器的一个建议："我这个时间片可以让出去"。它不释放锁，状态保持 RUNNABLE，而且调度器完全可以忽略它，下一个被选中的可能还是自己。所以它不能用来做任何同步保证，只适合自旋等待时降低 CPU 空转（Thread.onSpinWait() 是更现代的选择，会生成 pause 指令）。
    • 答：sleep(0) 在 HotSpot 上的效果和 yield() 类似（触发一次调度点），但它会抛 InterruptedException，语义更重。实践中都不建议依赖，它们属于"调优小手段"，不是同步原语。

  5. 追问：join() 的实现原理是什么？为什么不要对 Thread 对象加锁？

    • 答：join() 的实现非常朴素：synchronized 在目标 Thread 对象上，然后 while (isAlive()) wait(0)。线程结束时，JVM 在 native 层会对这个 Thread 对象执行 notifyAll()，所有 join 的线程被唤醒，检查 isAlive() 为 false 后返回。
    • 答：危险点有两个：第一，JVM 会在线程结束时自动 notifyAll 这个对象，如果你的业务代码也用 t.wait() / t.notify() 把 Thread 对象当锁用，就会和 join 机制互相干扰，出现莫名其妙的提前唤醒。第二，join 里用的是 wait，会释放 Thread 对象的锁，你以为的互斥区间其实是漏的。
    • 答：所以规则是：永远不要把 Thread 对象当作同步锁。要等多个线程结束，用 CountDownLatch 或 ExecutorService.awaitTermination()，语义清晰且不依赖 JVM 内部约定。

  6. 追问：LockSupport.park/unpark 凭什么能替代 wait/notify？它好在哪？

    • 答：第一，不需要持锁。wait 必须在 synchronized 块里，否则 IllegalMonitorStateException；park 可以在任何地方调用，这让 AQS 可以自己管理队列而不依赖 JVM 的 _WaitSet。
    • 答：第二，没有顺序要求（许可可以预先发放）。每个线程有一个最多为 1 的 permit：unpark 把 permit 置 1，park 发现有 permit 就直接消耗掉并返回。所以"先 unpark 后 park"不会阻塞，而"先 notify 后 wait"会永久丢失通知导致死等。这是解决并发唤醒竞态的关键武器。
    • 答：第三，精准唤醒单个线程。notify 是从 _WaitSet 里随机挑一个，notifyAll 会惊群；unpark(thread) 直接指定目标，AQS 据此实现"只唤醒队首后继节点"的高效传递。
    • 答：第四，park 可以被中断唤醒但不抛异常，只是设置中断标志并返回。所以 AQS 能做到"先返回、再统一处理中断"，实现 lock()（吞掉中断，退出前补 selfInterrupt()）和 lockInterruptibly()（抛异常）两套语义。
    • 答：代价是 park 返回的原因有四种（unpark / 中断 / 超时 / 虚假唤醒），所以必须在循环里 park 并自己检查条件，这和 wait 的循环要求是一样的。

  7. 追问：线上 jstack 抓出来一个线程一直是 TIMED_WAITING，你怎么判断正常还是异常？

    • 答：先看栈顶。如果是 ThreadPoolExecutor.getTask → DelayedWorkQueue.take / poll(keepAliveTime)，那是线程池核心线程在正常待命，完全健康。
    • 答：如果是业务代码里的 future.get(timeout)、lock.tryLock(timeout)、连接池 getConnection，就要连续抓 3~5 次 jstack 对比：如果同一个线程、同一行、卡了很久不变，说明超时时间设得过长或下游真的挂了。
    • 答：再结合线程名和数量：如果某个线程池的线程全部 TIMED_WAITING 在同一个下游调用上，基本可以判定下游故障引发了线程池耗尽，要立刻看熔断和超时配置。

✅ 项目关联话术（按真实经历替换）：

我们排查过一次"接口偶发超时但 CPU 和 GC 都很正常"的问题，就是靠线程状态定位的。连续抓了几次 jstack，发现业务线程池里大量线程处于 BLOCKED，栈顶都停在一个工具类的 synchronized 静态方法上——那是个做日期格式化的方法，里面用了共享的 SimpleDateFormat，前人为了修线程不安全问题直接在方法上加了 synchronized，结果把所有请求串行化了。改成 DateTimeFormatter（无状态、线程安全）之后 BLOCKED 全部消失，P99 从 800ms 降到 60ms。这件事让我养成了习惯：看到 BLOCKED 先找锁对象，看到 WAITING 先找谁该唤醒它。

题 6：ThreadLocal 的原理是什么？为什么会内存泄漏？ ​

精简口述答案：

ThreadLocal 的核心是把数据存在线程自己身上，而不是存在 ThreadLocal 对象里。每个 Thread 有一个 threadLocals 字段，类型是 ThreadLocal.ThreadLocalMap。set(v) 实际是 Thread.currentThread().threadLocals.put(this, v)——key 是 ThreadLocal 实例本身，value 是你的数据。所以线程之间天然隔离，不需要任何同步。

ThreadLocalMap 不是 HashMap：它是开放寻址 + 线性探测的数组结构，容量 2 的幂，初始 16，负载因子 2/3，扩容翻倍；它的 Entry extends WeakReference<ThreadLocal<?>>，也就是对 key 是弱引用，对 value 是强引用。

泄漏就出在这个强弱不对称上。引用链是：Thread → threadLocals → Entry → value，全是强引用。当 ThreadLocal 实例自身没有强引用了，GC 会回收 key，Entry 变成 key == null 的"脏 Entry"，但 value 还被 Entry 强引用着回收不掉，而且你再也拿不到它。如果这个 Thread 是线程池里长期复用的核心线程，它的生命周期等于应用生命周期，这块 value 就永久泄漏了。解决办法只有一个：try/finally 里必须 remove()。

连环追问链：

  1. 追问：为什么 key 要设计成弱引用？不用弱引用会怎样？

    • 答：弱引用是一道兜底的补救措施，不是泄漏的原因。如果 key 用强引用，那么只要线程活着，Entry 就强引用着 ThreadLocal 实例，即使业务代码里这个 ThreadLocal 变量已经不可达（比如它是个局部变量、或者它所属的类被卸载了），key 和 value 都回收不了，泄漏会更严重。
    • 答：用弱引用后，至少 key 能被回收，然后 ThreadLocalMap 在 set / get / remove 时遇到 key == null 的 Entry 会触发清理，有机会顺带把 value 置 null。注意是"有机会"——清理是启发式的、不保证执行，所以不能依赖它。
    • 答：一句话总结：弱引用让泄漏变得"可能被修复"，但 remove() 才是"确定被修复"。

  2. 追问：ThreadLocalMap 的清理机制具体是怎么工作的？

    • 答：有两个方法。expungeStaleEntry(i)：从位置 i 开始，把该脏 Entry 的 value 和 Entry 本身置 null，然后继续向后遍历直到遇到 null 槽，对途中的脏 Entry 清理、对正常 Entry 做 rehash 重新探测（因为开放寻址删除一个元素会破坏探测链，必须整段重排）。
    • 答：cleanSomeSlots(i, n)：一个对数复杂度的启发式扫描，循环 log2(n) 次，每次往后跳一格看是不是脏 Entry，是就触发 expungeStaleEntry。set 插入新元素后会调用它。
    • 答：所以清理的触发点是：get 探测过程中遇到脏 Entry、set 时遇到脏 Entry 或插入后抽查、rehash 前的全量 expungeStaleEntries。如果一个线程 set 完之后再也不碰这个 ThreadLocal，那就永远不会触发清理。这正是线程池场景泄漏的根因。

  3. 追问：ThreadLocalMap 为什么用开放寻址而不是 HashMap 的链地址法？

    • 答：第一，元素极少。一个线程通常只有个位数的 ThreadLocal（traceId、用户上下文、事务连接），数组线性探测的冲突概率低且缓存局部性好，不需要链表/红黑树的额外对象开销。
    • 答：第二，hash 分布很好。ThreadLocal 的 threadLocalHashCode 是用全局 AtomicInteger 以固定步长 0x61c88647（黄金分割数相关）递增生成的，这个魔数能让连续生成的 hash 在 2 的幂长度的数组里近似均匀分布，冲突本来就少。
    • 答：第三，Entry 需要继承 WeakReference。链地址法的 Node 要带 next 指针，而开放寻址下 Entry 可以就是一个纯粹的 WeakReference 子类，结构最简单，也方便 GC 语义的实现。

  4. 追问：线程池里用 ThreadLocal 除了泄漏，还有什么更危险的问题？

    • 答：脏数据污染，而且这个比泄漏危险得多。线程池复用线程，上一个任务 set 的值如果没 remove，下一个任务 get 就会拿到前一个请求的数据。如果里面存的是用户身份，就是实打实的越权/串号事故——A 用户的请求读到了 B 用户的上下文。
    • 答：泄漏只是内存慢慢涨，监控能发现；污染是数据正确性问题，而且只在高并发下偶发，极难复现。所以 remove() 的首要理由是防污染，其次才是防泄漏。
    • 答：工程上的做法：用拦截器/Filter 在请求出口统一 remove，或者封装一个 ContextHolder 工具类，只暴露 set/get/clear，并在 AOP 切面里强制 clear，不让业务代码直接接触 ThreadLocal。

  5. 追问：父线程的 ThreadLocal 怎么传给子线程？线程池场景怎么办？

    • 答：JDK 提供 InheritableThreadLocal，它利用 Thread 的另一个字段 inheritableThreadLocals。在 new Thread() 的构造过程中（Thread.init）会把父线程的 inheritableThreadLocals 浅拷贝一份给子线程，所以子线程能读到父线程的值。
    • 答：但它在线程池里完全失效：因为拷贝只发生在"创建线程"的那一刻，线程池的线程是第一次提交任务时创建的，之后一直复用，后续任务提交时不会再发生任何拷贝，子线程里的值永远是第一个任务那次留下的旧值。
    • 答：正确方案是阿里的 TransmittableThreadLocal (TTL)。思路是把传递时机从"创建线程"挪到"提交任务"：用 TtlRunnable.get(task) 包装任务，在提交时捕获当前线程的上下文快照，在任务 run 开始时回放到执行线程、结束时恢复原样。配合 TtlExecutors.getTtlExecutorService() 或 javaagent 可以做到无侵入。
    • 答：补充：浅拷贝还有个坑——父子线程拿到的是同一个对象引用。如果 value 是可变对象（比如 Map），子线程改了父线程也会看到，必须自己做深拷贝或用不可变对象。

  6. 追问：ThreadLocal 存储的 value 是弱引用吗？如果我把 ThreadLocal 声明成 static final 还会泄漏吗？

    • 答：value 是强引用，这是泄漏的必要条件之一。
    • 答：声明成 static final 是推荐做法，因为它保证 key 一直有强引用、不会变成脏 Entry，Entry 结构稳定，也避免了"每个请求 new 一个 ThreadLocal"这种灾难性写法（那会让 ThreadLocalMap 不断膨胀又不断产生脏 Entry）。
    • 答：但它不能免除 remove。static final 只解决了"key 被回收导致 value 不可达"这一种泄漏，而"线程长期存活 + value 一直被引用 + 业务不再需要它"这种泄漏和数据污染问题依然存在。所以结论不变：无论怎么声明，try/finally + remove() 是铁律。

  7. 追问：有哪些框架在用 ThreadLocal？它们怎么管理生命周期的？

    • 答：Spring 的事务管理用 TransactionSynchronizationManager（内部一堆 NamedThreadLocal）存当前线程绑定的 Connection，保证同一事务里的多次 DAO 操作用同一个连接；事务提交/回滚后的 cleanup 阶段会统一 remove。
    • 答：Spring MVC 的 RequestContextHolder 用 ThreadLocal 存 Request，FrameworkServlet 在 finally 里 reset。MyBatis 的 SqlSessionManager、日志框架的 MDC（MDCAdapter 底层就是 ThreadLocal 存 traceId）也都是同一套模式。
    • 答：共同点非常明确：所有框架都把 ThreadLocal 的 set 和 remove 配对放在一个"请求/事务"边界的 try/finally 里。我们自己写的时候照抄这个模式就不会错。

✅ 项目关联话术（按真实经历替换）：

我们线上出过一次 ThreadLocal 的事故，印象很深。当时做了一个"当前登录用户上下文"，用 static ThreadLocal<UserInfo> 在 Filter 里 set，业务层随处 get，但 Filter 里只在正常返回时 remove，异常分支漏了。平时没问题，有一天下游超时导致接口大量抛异常，于是线程池里的线程留下了一堆没清理的用户上下文；紧接着这些线程被复用去执行另一个请求，而那个接口对未登录用户有降级逻辑——结果降级没走，直接用了上一个请求残留的用户身份，产生了跨用户的数据读取。

复盘后我们做了三件事：一是把 remove 挪到 finally 里；二是写了一个 UserContextHolder 把 ThreadLocal 彻底封装起来，业务代码拿不到原始对象；三是在异步线程池上套了 TTL 的包装器，顺手解决了之前"异步任务里 traceId 丢失"的老问题。从那以后我 review 代码只要看到 ThreadLocal.set，第一反应就是去找对应的 remove 在不在 finally 里。

题 7：线上发生死锁了，你怎么定位和解决？怎么从设计上避免？ ​

精简口述答案：

死锁必须同时满足四个条件：互斥、持有并等待、不可剥夺、循环等待。打破任意一个就能消除死锁，工程上最常用的是打破"循环等待"（固定加锁顺序）和"持有并等待"（用 tryLock 带超时）。

定位分三步：第一步看现象——接口无响应但 CPU 不高、线程池活跃线程数打满不下降；第二步 jstack <pid> 导出线程栈，JVM 会在输出末尾自动打印 Found one Java-level deadlock 并列出环路（这是 synchronized 死锁的最快路径）；第三步如果是 ReentrantLock 死锁，jstack 不会自动检测，要靠 parking to wait for <ReentrantLock$NonfairSync> 的地址加上 - locked 信息手工串出环，或者用 Arthas 的 thread -b 直接找阻塞源头。

解决上，线上救急只能重启（死锁不可剥夺，无法在运行时打破）。代码上的根治手段按优先级是：统一加锁顺序 → 用 tryLock(timeout) 让出 → 缩小锁粒度/合并成一把锁 → 改成无锁结构（CAS / 不可变对象 / 单线程串行化）。

连环追问链：

  1. 追问：死锁、活锁、饥饿有什么区别？

    • 答：死锁是互相持有对方需要的锁，全部永久阻塞，线程状态是 BLOCKED / WAITING，CPU 占用为 0。
    • 答：活锁是线程都没有阻塞，但不断重试又不断失败，一直在"礼让"。典型场景是两个线程都用 tryLock 失败就回退重试，且重试间隔固定，于是永远在同一个节拍上撞车。解法是加随机退避（像以太网的指数退避），让重试时机错开。
    • 答：饥饿是某些线程长期拿不到资源。来源有三：非公平锁下的插队（新来的线程直接抢走锁，队列里的老线程一直等）、线程优先级设置不当、持锁线程执行时间过长。解法是改用公平锁、或者保证临界区足够短。
    • 答：三者的共性是"业务推进不下去"，但诊断手段不同：死锁看 jstack 环路；活锁看 CPU 高但吞吐为 0、日志里重试计数疯涨；饥饿看某些请求的 P999 异常高而平均值正常。

  2. 追问：怎么用代码复现一个死锁？

    • 答：最小模型是两个线程两把锁反向获取：线程 A 先 synchronized(lockA)，sleep 一下确保线程 B 也拿到自己的锁，再去 synchronized(lockB)；线程 B 反过来。那个 sleep 很关键，它保证两个线程都完成了"持有第一把锁"这一步，否则其中一个可能快速跑完全程不会死锁。
    • 答：实际项目里的死锁往往不这么直白，常见变形有：同一个方法被不同调用方以不同顺序传入两个账户对象（转账场景的经典死锁，A 转 B 和 B 转 A 并发）；嵌套调用，外层方法持有锁 X 后调用了一个自己也加锁 Y 的服务方法，而另一条链路顺序相反；数据库行锁死锁，两个事务按不同顺序更新同一批行。
    • 答：所以 review 时的信号是：一个临界区内又调用了别的加锁方法（锁嵌套），以及锁对象来自方法参数（顺序不可控）。

  3. 追问：转账场景 A→B 和 B→A 并发怎么解决？

    • 答：核心是给锁对象定义一个全局唯一的顺序，让所有线程按同一方向加锁。最常用的是按账户 ID 排序：先锁 ID 小的，再锁 ID 大的。这样 A→B 和 B→A 两条路径实际加锁顺序完全一致，环路被打破。
    • 答：如果没有天然可比的 ID，可以用 System.identityHashCode(obj) 排序。但要处理 hash 相同的极端情况：此时引入一个全局的"加时赛锁"（tie-breaker lock），先拿到它再按任意顺序加两把锁，保证这种罕见情况下也串行。这是《Java 并发编程实战》里的标准做法。
    • 答：更工程化的方案是直接绕开双锁：把转账做成单线程串行（按账户 ID 取模路由到固定的单线程执行器），或者交给数据库用一条带条件的 UPDATE ... WHERE balance >= amount 保证原子性，应用层不加锁。

  4. 追问：jstack 具体怎么看？输出里哪些信息最关键？

    • 答：关键有四块。一是 线程状态和锁信息行：- waiting to lock <0x000000076ab62208> (a java.lang.Object) 表示在等这个锁，- locked <0x000000076ab62218> 表示已持有这个锁。把"等的地址"和"别人持有的地址"对上就是环。
    • 答：二是 末尾的死锁报告。JVM 内置了死锁检测，对 synchronized 和 ReentrantLock（通过 AbstractOwnableSynchronizer 记录 owner）都能检出，会打印 Found one Java-level deadlock: 加上 "Thread-0" is waiting to lock monitor ..., which is held by "Thread-1" 的完整链条。所以第一步就该直接搜这个关键字。
    • 答：三是 parking to wait for 行：这是 LockSupport.park 导致的，后面跟的对象是 AQS 的 Sync 实例。配合 at java.util.concurrent.locks.ReentrantLock.lock 的栈帧可以确认是锁等待而不是业务等待。
    • 答：四是 要连续抓多次（比如间隔 5 秒抓 3 次）。死锁的特征是栈完全不动；如果两次栈不一样，那是慢而不是死。这一招能快速区分死锁和性能问题。

  5. 追问：除了 jstack 还有什么工具？Arthas 怎么用？

    • 答：jconsole / jvisualvm 的线程面板有"检测死锁"按钮，图形化最直观，但生产环境一般不开 JMX 远程端口。
    • 答：jcmd <pid> Thread.print 和 jstack 等价，是官方更推荐的入口。
    • 答：Arthas 最实用：thread 看所有线程概览和 CPU 占比；thread -b 直接找出阻塞其他线程的那个线程（它会分析 monitor 持有关系，一条命令定位"罪魁祸首"）；thread -n 3 看最忙的 3 个线程（排查 CPU 飙高）；thread <id> 看指定线程栈。
    • 答：代码层面还可以主动监控：ThreadMXBean.findDeadlockedThreads()（能检出 synchronized 和 Lock 死锁）或 findMonitorDeadlockedThreads()（只检 synchronized），起一个定时任务每分钟扫一次，发现非空就告警并打印栈。这是给核心服务加的保险。

  6. 追问：tryLock 带超时能彻底避免死锁吗？有什么代价？

    • 答：能避免死锁"永久卡死"，因为它打破了"持有并等待"——拿不到第二把锁就超时，然后必须释放已持有的第一把锁再整体重试。注意这个"释放已持有的锁"是关键，很多人只写了 tryLock 却忘了失败后 unlock 第一把，等于没解决。
    • 答：代价有三个：一是可能变成活锁，需要配随机退避；二是业务要能接受失败/重试，不是所有操作都幂等可重试；三是代码变复杂，嵌套 try/finally 容易写错，容易出现漏 unlock 或多 unlock（IllegalMonitorStateException）。
    • 答：所以我的取舍是：能固定加锁顺序就优先固定顺序（零成本、无副作用），只在锁顺序确实无法统一（比如锁对象动态来自外部）时才用 tryLock 兜底。

  7. 追问：从架构设计上怎么从根本上减少死锁的可能？

    • 答：第一，减少锁。能用不可变对象（final 字段 + 返回新实例）就不用锁；能用 ConcurrentHashMap / AtomicLong / LongAdder 就不用 synchronized；能把共享状态改成线程本地（ThreadLocal）或消息传递（队列 + 单消费者）就彻底没有竞争。
    • 答：第二，一把锁代替多把锁。两把细粒度锁带来的性能收益，常常抵不过死锁风险和维护成本。只有在压测证明锁竞争是瓶颈时，才拆锁。
    • 答：第三，禁止在持锁期间调用外部方法（开放调用 open call）。临界区内不要调 RPC、不要查数据库、不要调用可被子类覆盖的方法、不要触发回调——因为你无法知道被调方会不会去拿别的锁。把计算结果拿到锁外再处理。
    • 答：第四，分布式场景同理。Redis 分布式锁一定要设过期时间（打破"不可剥夺"），多把分布式锁也要按 key 排序获取，并且要考虑持锁进程宕机后的自动释放。
    • 答：第五，加防护网：锁超时时间必须有上限，线程池要隔离（核心链路和非核心链路分池），加上 findDeadlockedThreads 的定时巡检告警，让死锁在影响扩大前被发现。

我处理过一次典型的死锁告警。现象是某个后台批处理任务的线程池活跃数打满后再也不降，但机器 CPU 只有 5%。jstack 下来直接在末尾看到了 Found one Java-level deadlock，两个线程分别卡在"库存服务的 synchronized 方法里等订单锁"和"订单服务的 synchronized 方法里等库存锁"——根因是两个 service 互相调用，且各自都在方法上加了 synchronized，调用顺序一正一反。

题 8：CAS 是什么？有哪些问题？AtomicLong 和 LongAdder 怎么选？ ​

精简口述答案：

CAS 是 Compare-And-Swap，三个参数：内存位置 V、预期旧值 A、要写的新值 B。只有 V 当前等于 A 时才把 V 改成 B，否则什么都不做并返回失败。它的原子性由 CPU 指令保证——x86 上是 lock cmpxchg，lock 前缀锁定缓存行（现代 CPU 走缓存一致性协议而非锁总线）。Java 里通过 Unsafe（JDK 9+ 推荐 VarHandle）暴露，AtomicInteger 等原子类就是"volatile 字段 + CAS 自旋"的组合：volatile 保证可见性和有序性，CAS 保证原子性。

CAS 有三个经典问题：ABA 问题（值从 A 变 B 又变回 A，CAS 看不出中间发生过变化），用 AtomicStampedReference 加版本号或 AtomicMarkableReference 加布尔标记解决；循环时间长开销大（高竞争下自旋空转烧 CPU），用 Thread.onSpinWait() 退避、或竞争激烈时改用锁、或改用分段设计；只能保证一个变量的原子性，多个变量要么封装进一个不可变对象用 AtomicReference，要么直接上锁。

AtomicLong 和 LongAdder 的选择标准很清晰：低并发或需要精确实时值用 AtomicLong，高并发只做计数/统计用 LongAdder。AtomicLong 所有线程 CAS 同一个变量，竞争一高就大量自旋失败，而且所有核心都在争抢同一个缓存行（伪共享）；LongAdder 用 base + Cell[] 分段，每个线程按 probe 哈希到不同 Cell 上各自累加，sum() 时再把 base 和所有 Cell 相加。竞争被打散到多个缓存行（Cell 上有 @Contended 做填充），吞吐可以高一个数量级。代价是 sum() 不是原子快照，统计期间有并发写就可能不精确。

连环追问链：

  1. 追问：AtomicInteger.incrementAndGet() 的实现是什么样的？

    • 答：JDK 8 里是 unsafe.getAndAddInt(this, valueOffset, 1)，内部是一个 do-while 自旋：先 getIntVolatile 读当前值 v，然后 compareAndSwapInt(o, offset, v, v+1)，失败就重新读再试，直到成功。JDK 9+ 换成了 VarHandle 的 getAndAdd。
    • 答：value 字段必须是 volatile，否则自旋时读到的可能是缓存里的旧值，会导致无限失败或者 CAS 成功但别的线程看不到结果。
    • 答：在 x86 上，JIT 会把 getAndAddInt 直接内联成 lock xadd 这一条指令（因为加法有专门的原子指令），比"读-CAS-重试"的循环更快。所以 AtomicInteger 在低竞争下性能非常好，不要无脑换 LongAdder。

  2. 追问：ABA 问题在实际业务中真的会出事吗？举个例子。

    • 答：对于数值累加这类操作，ABA 通常无害——你关心的只是最终结果对不对，中间变成 B 又回来不影响。
    • 答：对于引用类型和链式结构就会出事。经典例子是无锁栈：线程 1 读到栈顶是节点 A（A.next = B），准备 CAS 把栈顶改成 B；此时线程 2 把 A 和 B 都弹出、又把 A 压回去（此时 A.next 已经不是 B，B 甚至已经被回收/复用）。线程 1 的 CAS 看到栈顶还是 A，成功了，于是栈顶被改成了一个已经不在栈里的 B，数据结构被破坏。
    • 答：业务层面的例子：用 CAS 更新"账户状态"，从"正常"改成"冻结"再改回"正常"，如果有个任务用 CAS 判断"状态还是正常就执行发放"，它就会错过中间的冻结事件。这种"关心是否发生过变化"的场景必须加版本号。
    • 答：Java 里 GC 帮我们缓解了一部分（不会出现 C/C++ 那种内存被 free 后重新分配到同一地址的问题），但逻辑层面的 ABA 依然存在。

  3. 追问：AtomicStampedReference 怎么用？它和 AtomicMarkableReference 的区别？

    • 答：AtomicStampedReference<V> 把引用和一个 int 版本号（stamp）打包成一个不可变的 Pair 对象，CAS 的时候比较的是整个 Pair 的引用，相当于同时比较引用和版本号。调用方式是 compareAndSet(expectedRef, newRef, expectedStamp, newStamp)，每次更新把 stamp +1，这样 A→B→A 的 stamp 变成了 0→1→2，CAS 会失败。
    • 答：AtomicMarkableReference<V> 用的是 boolean mark 而不是 int stamp，只能表达"有没有被改过/有没有被标记删除"，不能表达"改了几次"。它更省空间，典型用途是无锁链表的逻辑删除（先 mark 节点为"已删除"，再真正摘除）。
    • 答：两者的代价是每次 CAS 都要 new 一个 Pair 对象，有额外的分配和 GC 压力，所以只在确实需要防 ABA 时用。

  4. 追问：LongAdder 的 Cell[] 是怎么扩张的？为什么要 @Contended？

    • 答：LongAdder（继承 Striped64）是懒扩张的：一开始只有 base，所有线程直接 CAS base。只有当 CAS base 失败（说明出现了竞争），才创建长度为 2 的 cells 数组。之后线程用自己的 threadLocalRandomProbe 哈希到某个 Cell，CAS 那个 Cell。如果连 Cell 的 CAS 也失败，先尝试 advanceProbe 换一个 Cell（相当于重新哈希），还失败才把数组扩容一倍。
    • 答：数组长度上限是不超过 CPU 核数的最小 2 的幂——因为真正并行写入的线程最多就是核数，再多的 Cell 也没意义，只是浪费内存。
    • 答：@Contended（JDK 8 的 sun.misc.Contended，需要 -XX:-RestrictContended 才对用户代码生效）的作用是让 JVM 在字段前后填充 128 字节，保证每个 Cell 独占一条缓存行。否则多个 Cell 挤在同一条 64 字节缓存行里，一个核改 Cell[0] 会让其他核缓存的 Cell[1] 整行失效（伪共享 false sharing），分段的收益就全被缓存一致性流量吃掉了。实测伪共享能让性能差好几倍。

  5. 追问：LongAdder.sum() 为什么不准？什么场景不能用？

    • 答：sum() 的实现是 base 加上遍历 cells 的累加，整个过程没有加锁也没有快照机制。遍历到 Cell[2] 的时候，Cell[0] 可能又被改了，于是结果既不是开始时刻的值也不是结束时刻的值，是个"中间态"。
    • 答：所以不能用在需要精确判断的场景。比如"库存减到 0 就停止"、"限流计数超过阈值就拒绝"这种强一致判断，用 LongAdder 会放过一部分请求。这类场景要用 AtomicLong 的 decrementAndGet 返回值判断，或者用 Redis/数据库的原子操作。
    • 答：它适合的是监控指标、QPS 统计、总请求数、缓存命中数这类"最终统计、容忍瞬时偏差"的场景。而且注意 sum() 本身是 O(cells 长度) 的，高频调用也有成本，一般按秒级采样。
    • 答：另外 LongAdder 没有 compareAndSet，也没有返回自增后的值的方法（increment() 返回 void），所以需要"拿到自增后序号"的场景（比如生成递增 ID）只能用 AtomicLong。

  6. 追问：AtomicReference 和 AtomicXXXFieldUpdater 的区别？什么时候用后者？

    • 答：AtomicReference 是一个包装对象，每个被保护的字段都要多一个对象，内存开销在有海量实例时很可观（比如每个连接对象都带几个 AtomicReference）。
    • 答：AtomicIntegerFieldUpdater / AtomicReferenceFieldUpdater 是基于反射的静态工具：你直接声明一个 volatile int state 普通字段，然后用一个 static 的 Updater 对它做 CAS。全类只有一个 Updater 实例，零额外内存开销。代价是字段必须是 volatile、不能是 static、不能是 final，而且有访问权限检查。
    • 答：典型应用在 JDK 自己的代码和中间件里，比如 Netty 大量使用 FieldUpdater 来给每个 Channel 的状态做无锁更新，就是为了省掉百万连接场景下的对象开销。
    • 答：JDK 9+ 的 VarHandle 是官方替代品，性能更好（可以被 JIT 内联成直接的内存访问，没有反射开销）、功能更全（支持各种内存语义：plain / opaque / acquire-release / volatile），新代码应该优先用它。

  7. 追问：CAS 一定比锁快吗？

    • 答：不一定，取决于竞争程度和临界区长度。CAS 在低竞争下胜出明显，因为它没有用户态到内核态的切换、没有线程上下文切换、没有线程挂起唤醒的开销。
    • 答：但在高竞争下 CAS 会退化：N 个线程里只有 1 个能成功，其余 N-1 个白白自旋烧 CPU，而且每次失败都伴随缓存行在核间来回弹跳（cache line ping-pong），总吞吐可能比锁更差。锁虽然有切换开销，但它让失败者睡眠让出 CPU，整体更"节能"。
    • 答：另外 CAS 只适合极短的临界区（就是改一个变量）。如果临界区里有几十行逻辑，CAS 自旋重试意味着那几十行要重算多次，还可能有副作用，根本不能用。
    • 答：所以实践结论是：单变量更新用原子类，复杂逻辑用锁，高并发纯计数用 LongAdder，读多写少用 StampedLock 的乐观读或 ReadWriteLock。而 synchronized 本身在低竞争下也会走偏向锁/轻量级锁的 CAS 路径，并不慢——不要为了"无锁"硬凑 CAS。

✅ 项目关联话术（按真实经历替换）：

我们做过一次网关埋点统计的优化，很能说明 CAS 的适用边界。最初用 AtomicLong 给每个接口维度统计调用次数，压测到两万 QPS 以上时，火焰图上 getAndAddInt 的自旋占了相当比例的 CPU，而且 perf 能看到明显的缓存未命中。

题 1：手写线程安全的单例（DCL + 静态内部类 + 枚举） ​

核心实现：

/* ========== 写法一：双重检查锁 DCL（必须 volatile） ========== */
public class SingletonDCL {
    // volatile 的两个作用：1) 禁止 new 的指令重排 2) 保证写入对其他线程立即可见
    private static volatile SingletonDCL instance;

    private SingletonDCL() {
        // 防反射攻击：第二次通过反射调用构造器时直接抛异常
        if (instance != null) {
            throw new IllegalStateException("单例已存在，禁止反射创建");
        }
    }

    public static SingletonDCL getInstance() {
        if (instance == null) {                 // 第一次检查：无锁快速路径，99.99% 的调用走这里
            synchronized (SingletonDCL.class) {
                if (instance == null) {         // 第二次检查：防止多个线程都通过了第一次检查
                    instance = new SingletonDCL();
                }
            }
        }
        return instance;
    }
}

/* ========== 写法二：静态内部类（推荐，无锁且懒加载） ========== */
public class SingletonHolder {
    private SingletonHolder() {}

    // Holder 类只有在第一次被主动引用时才会被类加载器初始化
    private static class Holder {
        private static final SingletonHolder INSTANCE = new SingletonHolder();
    }

    public static SingletonHolder getInstance() {
        return Holder.INSTANCE;   // 线程安全由 JVM 的类初始化锁保证，零同步开销
    }
}

/* ========== 写法三：枚举（Effective Java 首推，天然防反射 + 防序列化） ========== */
public enum SingletonEnum {
    INSTANCE;

    private final Map<String, String> cache = new ConcurrentHashMap<>();

    public void put(String k, String v) { cache.put(k, v); }
    public String get(String k) { return cache.get(k); }
}

/* ========== 写法四：饿汉式（简单，但不支持懒加载） ========== */
public class SingletonEager {
    private static final SingletonEager INSTANCE = new SingletonEager();
    private SingletonEager() {}
    public static SingletonEager getInstance() { return INSTANCE; }
}

/* ========== 写法五：基于 CAS 的无锁单例（了解即可，有重复创建开销） ========== */
public class SingletonCas {
    private static final AtomicReference<SingletonCas> REF = new AtomicReference<>();
    private SingletonCas() {}

    public static SingletonCas getInstance() {
        for (;;) {
            SingletonCas cur = REF.get();
            if (cur != null) {
                return cur;
            }
            SingletonCas candidate = new SingletonCas();      // 可能被创建多次然后丢弃
            if (REF.compareAndSet(null, candidate)) {
                return candidate;
            }
        }
    }
}

/* ========== 配套：DCL 版本防序列化破坏 ========== */
class SingletonSerializable implements Serializable {
    private static final long serialVersionUID = 1L;
    private static volatile SingletonSerializable instance;
    private SingletonSerializable() {}

    public static SingletonSerializable getInstance() {
        if (instance == null) {
            synchronized (SingletonSerializable.class) {
                if (instance == null) {
                    instance = new SingletonSerializable();
                }
            }
        }
        return instance;
    }

    // 反序列化时 JVM 会优先调用这个方法，返回已有实例，从而避免生成新对象
    private Object readResolve() {
        return getInstance();
    }
}

三个必须记住的点：

  1. volatile 不是为了可见性那么简单：instance = new SingletonDCL() 分三步——① 分配内存 ② 执行构造器初始化 ③ 把引用指向内存。②③ 之间允许重排，一旦重排成 ①③②，另一个线程在第一次检查时就会拿到一个非 null 但字段全是默认值的半成品对象。volatile 通过插入 StoreStore / StoreLoad 屏障禁止这次重排。
  2. 两次检查都不能省：省掉第一次检查等于每次 getInstance 都进 synchronized，性能退化；省掉第二次检查则多个线程都可能通过第一次检查，排队进入同步块后各自 new 一个对象。
  3. 静态内部类的线程安全来自 JVM 规范：类的初始化（<clinit>）由 JVM 用一把初始化锁保证只执行一次，且对外部线程有 happens-before 保证。它比 DCL 更简洁，而且没有 volatile 读的屏障开销，是实际项目里的首选。

public class MyThreadPool {

    private final int coreSize;                       // 核心线程数
    private final int maxSize;                        // 最大线程数
    private final long keepAliveNanos;                // 非核心线程空闲存活时间
    private final BlockingQueue<Runnable> queue;      // 任务队列
    private final RejectHandler rejectHandler;   // 拒绝策略
    private final ThreadFactory threadFactory;

    /** 用一个 int 的高 3 位存状态、低 29 位存线程数，和 JDK 的 ctl 设计一致 */
    private static final int COUNT_BITS = 29;
    private static final int COUNT_MASK = (1 << COUNT_BITS) - 1;
    private static final int RUNNING   = -1 << COUNT_BITS;
    private static final int SHUTDOWN  =  0 << COUNT_BITS;
    private static final int STOP      =  1 << COUNT_BITS;
    private final AtomicInteger ctl = new AtomicInteger(RUNNING);

    private static int runStateOf(int c) { return c & ~COUNT_MASK; }
    private static int workerCountOf(int c) { return c & COUNT_MASK; }

    /** 用一把锁 + Set 管理 Worker，用于 shutdown 时遍历中断 */
    private final ReentrantLock mainLock = new ReentrantLock();
    private final Set<Worker> workers = new HashSet<>();
    private final Condition termination = mainLock.newCondition();

    public interface RejectHandler {
        void reject(Runnable task, MyThreadPool pool);
    }

    public MyThreadPool(int coreSize, int maxSize, long keepAlive, TimeUnit unit,
                        BlockingQueue<Runnable> queue, RejectHandler handler) {
        if (coreSize < 0 || maxSize <= 0 || maxSize < coreSize || keepAlive < 0) {
            throw new IllegalArgumentException("参数非法");
        }
        this.coreSize = coreSize;
        this.maxSize = maxSize;
        this.keepAliveNanos = unit.toNanos(keepAlive);
        this.queue = Objects.requireNonNull(queue);
        this.rejectHandler = Objects.requireNonNull(handler);
        AtomicInteger seq = new AtomicInteger();
        this.threadFactory = r -> {
            Thread t = new Thread(r, "my-pool-worker-" + seq.incrementAndGet());
            t.setUncaughtExceptionHandler((th, e) ->
                    System.err.println("[线程池] 线程 " + th.getName() + " 异常退出: " + e));
            return t;
        };
    }

    /* ======================= 提交任务：四级流水线 ======================= */
    public void execute(Runnable task) {
        Objects.requireNonNull(task, "任务不能为 null");
        int c = ctl.get();

        // 第 1 级：线程数 < 核心数，直接新建核心线程
        if (workerCountOf(c) < coreSize) {
            if (addWorker(task, true)) {
                return;
            }
            c = ctl.get();   // 添加失败（并发或状态变化），重新读取
        }

        // 第 2 级：池是 RUNNING 且队列能放下，就入队
        if (runStateOf(c) == RUNNING && queue.offer(task)) {
            // 二次校验：入队后池可能已经 shutdown，或者 worker 全死了
            int recheck = ctl.get();
            if (runStateOf(recheck) != RUNNING && queue.remove(task)) {
                rejectHandler.reject(task, this);
            } else if (workerCountOf(recheck) == 0) {
                addWorker(null, false);   // 补一个空 worker 来消费队列，防止任务饿死
            }
            return;
        }

        // 第 3 级：队列满了，尝试创建非核心线程
        if (addWorker(task, false)) {
            return;
        }

        // 第 4 级：线程数已到 maxSize，执行拒绝策略
        rejectHandler.reject(task, this);
    }

    /* ======================= 创建 Worker ======================= */
    private boolean addWorker(Runnable firstTask, boolean core) {
        for (;;) {
            int c = ctl.get();
            int rs = runStateOf(c);
            // 非 RUNNING 状态下只允许"无新任务 + 队列还有残留"的补偿式创建
            if (rs != RUNNING && !(rs == SHUTDOWN && firstTask == null && !queue.isEmpty())) {
                return false;
            }
            int wc = workerCountOf(c);
            if (wc >= (core ? coreSize : maxSize)) {
                return false;
            }
            if (ctl.compareAndSet(c, c + 1)) {   // CAS 抢占一个"名额"
                break;
            }
            // CAS 失败说明状态或数量被改了，重试整个循环
        }

        Worker w = new Worker(firstTask);
        boolean added = false;
        mainLock.lock();
        try {
            if (runStateOf(ctl.get()) == RUNNING
                    || (runStateOf(ctl.get()) == SHUTDOWN && firstTask == null)) {
                workers.add(w);
                added = true;
            }
        } finally {
            mainLock.unlock();
        }

        if (added) {
            w.thread.start();
            return true;
        }
        ctl.decrementAndGet();   // 回滚名额
        return false;
    }

    /* ======================= Worker：线程的载体 ======================= */
    private final class Worker implements Runnable {
        final Thread thread;
        Runnable firstTask;
        long completedTasks;

        Worker(Runnable firstTask) {
            this.firstTask = firstTask;
            this.thread = threadFactory.newThread(this);
        }

        @Override
        public void run() {
            Runnable task = firstTask;
            firstTask = null;              // 关键：置空，避免长期持有引用导致内存泄漏
            boolean abruptly = true;
            try {
                while (task != null || (task = getTask()) != null) {
                    try {
                        task.run();
                    } catch (Throwable t) {
                        // 必须捕获 Throwable：否则异常会冲出 run()，线程直接死亡
                        System.err.println("[线程池] 任务执行异常: " + t);
                    } finally {
                        task = null;       // 同样要置空，让任务对象尽早可回收
                        completedTasks++;
                    }
                }
                abruptly = false;          // 正常退出（getTask 返回 null）
            } finally {
                processWorkerExit(this, abruptly);
            }
        }
    }

    /* ======================= 取任务：核心阻塞 / 非核心超时 ======================= */
    private Runnable getTask() {
        boolean timedOut = false;
        for (;;) {
            int c = ctl.get();
            int rs = runStateOf(c);

            // STOP 直接退；SHUTDOWN 且队列已空也退（保证 shutdown 后把残留任务跑完）
            if (rs >= STOP || (rs == SHUTDOWN && queue.isEmpty())) {
                ctl.decrementAndGet();
                return null;
            }

            int wc = workerCountOf(c);
            boolean timed = wc > coreSize;   // 超出核心数的线程才需要超时回收

            if ((wc > maxSize || (timed && timedOut)) && (wc > 1 || queue.isEmpty())) {
                if (ctl.compareAndSet(c, c - 1)) {
                    return null;             // 该线程被回收
                }
                continue;                    // CAS 失败重试
            }

            try {
                Runnable r = timed
                        ? queue.poll(keepAliveNanos, TimeUnit.NANOSECONDS)
                        : queue.take();
                if (r != null) {
                    return r;
                }
                timedOut = true;             // poll 超时，下一轮循环执行回收判断
            } catch (InterruptedException e) {
                timedOut = false;            // 被中断（shutdown 触发），回到循环重新判断状态
            }
        }
    }

    private void processWorkerExit(Worker w, boolean abruptly) {
        if (abruptly) {
            ctl.decrementAndGet();           // 异常退出的线程没有在 getTask 里减过数
        }
        mainLock.lock();
        try {
            workers.remove(w);
            if (workers.isEmpty()) {
                termination.signalAll();     // 唤醒 awaitTermination
            }
        } finally {
            mainLock.unlock();
        }
        // 异常退出要补一个线程，保证池子不被"消耗"光
        int c = ctl.get();
        if (runStateOf(c) == RUNNING) {
            if (abruptly || workerCountOf(c) < Math.max(coreSize, queue.isEmpty() ? 0 : 1)) {
                addWorker(null, false);
            }
        }
    }

    /* ======================= 关闭 ======================= */
    /** 优雅关闭：不收新任务，已入队的任务继续执行完 */
    public void shutdown() {
        mainLock.lock();
        try {
            advanceRunState(SHUTDOWN);
            for (Worker w : workers) {
                // 只中断空闲线程（正在 take/poll 阻塞的），不打断正在干活的
                if (!w.thread.isInterrupted() && w.thread.getState() == Thread.State.WAITING
                        || w.thread.getState() == Thread.State.TIMED_WAITING) {
                    w.thread.interrupt();
                }
            }
        } finally {
            mainLock.unlock();
        }
    }

    /** 强制关闭：丢弃队列中未执行的任务，中断所有线程 */
    public List<Runnable> shutdownNow() {
        List<Runnable> remaining = new ArrayList<>();
        mainLock.lock();
        try {
            advanceRunState(STOP);
            for (Worker w : workers) {
                w.thread.interrupt();
            }
            queue.drainTo(remaining);
        } finally {
            mainLock.unlock();
        }
        return remaining;
    }

    private void advanceRunState(int targetState) {
        for (;;) {
            int c = ctl.get();
            if (runStateOf(c) >= targetState
                    || ctl.compareAndSet(c, targetState | workerCountOf(c))) {
                return;
            }
        }
    }

    public boolean awaitTermination(long timeout, TimeUnit unit) throws InterruptedException {
        long nanos = unit.toNanos(timeout);
        mainLock.lock();
        try {
            while (!workers.isEmpty()) {
                if (nanos <= 0) {
                    return false;
                }
                nanos = termination.awaitNanos(nanos);
            }
            return true;
        } finally {
            mainLock.unlock();
        }
    }

    public int getPoolSize() { return workerCountOf(ctl.get()); }
    public int getQueueSize() { return queue.size(); }

    /* ======================= 四种拒绝策略 ======================= */
    public static final RejectHandler ABORT = (task, pool) -> {
        throw new RejectedExecutionException("任务被拒绝: " + task);
    };
    public static final RejectHandler DISCARD = (task, pool) -> { /* 静默丢弃 */ };
    public static final RejectHandler DISCARD_OLDEST = (task, pool) -> {
        pool.queue.poll();        // 丢掉最老的那个
        pool.execute(task);
    };
    public static final RejectHandler CALLER_RUNS = (task, pool) -> {
        if (runStateOf(pool.ctl.get()) == RUNNING) {
            task.run();           // 由提交任务的线程自己执行，天然形成背压
        }
    };
}

三个必须记住的点：

  1. while (task != null || (task = getTask()) != null) 是整个线程池"复用"的灵魂。线程不会执行完一个任务就结束，而是在循环里不断从队列阻塞获取下一个任务。核心线程用 take() 永久阻塞，非核心线程用 poll(keepAlive) 超时后返回 null 跳出循环从而被回收——这就是 keepAliveTime 的全部实现。
  2. task.run() 外面必须包 try-catch(Throwable)。一旦异常冲出 Worker.run()，这个线程就彻底死亡，池子会被慢慢"吃光"。虽然 processWorkerExit 会补线程，但频繁创建销毁线程的代价很高，而且异常被静默吞掉会丢失关键日志。
  3. ctl 用一个 AtomicInteger 同时存状态和线程数，是为了让"状态校验 + 线程数检查 + 占名额"三件事能在一次 CAS 里原子完成。如果拆成两个变量，就必须加锁才能保证一致性，而 execute 是最热的路径，不能有锁。

🔁 变种拓展题：

  1. 支持 submit 返回 Future：自己实现一个简化版 FutureTask，内部用 CountDownLatch 或 AQS 保存结果/异常，get() 阻塞等待，get(timeout) 超时抛 TimeoutException。注意异常要包装成 ExecutionException。
  2. 支持动态调参：实现 setCorePoolSize(int)，调小时要中断多余的空闲线程，调大时如果队列非空要立即补线程。再实现一个可变容量的队列（LinkedBlockingQueue 的 capacity 是 final 的，要用反射改或自己写），这是美团动态线程池的核心。
  3. 加监控埋点：记录任务排队时长（提交时打时间戳，执行前算差值）、执行耗时、队列峰值、拒绝次数，并支持 beforeExecute / afterExecute 钩子（可以用来做 MDC traceId 传递和 ThreadLocal 清理）。
  4. 实现定时任务能力：把队列换成 DelayQueue 或自己写一个基于小顶堆的 DelayedWorkQueue，支持 schedule(task, delay) 和 scheduleAtFixedRate。重点说清 scheduleAtFixedRate 和 scheduleWithFixedDelay 的区别，以及任务抛异常会让后续调度永久停止这个大坑。
  5. 实现任务优先级：队列换成 PriorityBlockingQueue，任务实现 Comparable。要指出两个坑：优先级队列无界（容量只会扩容），以及低优先级任务可能饥饿。
  6. 实现线程池的"预热"：prestartAllCoreThreads()，在服务启动时就把核心线程创建好，避免第一批请求承担线程创建的开销（配合压测预热很有用）。
  7. 对比 Tomcat 的线程池改造：Tomcat 重写了 TaskQueue.offer，让它在"线程数还没到 max"时故意返回 false，从而先扩容线程再入队，这和 JDK 的"先入队后扩容"策略完全相反。解释为什么 IO 密集的 Web 场景更适合 Tomcat 这种策略。

/* ========== 解法一：synchronized + wait/notifyAll（最朴素，必须用 notifyAll） ========== */
class PrintAbcSync {
    private final Object lock = new Object();
    private int state = 0;          // 0->A, 1->B, 2->C
    private final int loop;

    PrintAbcSync(int loop) { this.loop = loop; }

    public void print(String name, int target) {
        for (int i = 0; i < loop; i++) {
            synchronized (lock) {
                // 必须用 while 而不是 if：防止虚假唤醒 + 被唤醒后条件可能已不满足
                while (state % 3 != target) {
                    try {
                        lock.wait();
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                        return;
                    }
                }
                System.out.print(name);
                state++;
                // 只能 notifyAll：notify 随机唤醒一个，可能唤醒的不是下一个该跑的线程 -> 死锁
                lock.notifyAll();
            }
        }
    }
}

/* ========== 解法二：ReentrantLock + 三个 Condition（精准唤醒，推荐） ========== */
class PrintAbcCondition {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition condA = lock.newCondition();
    private final Condition condB = lock.newCondition();
    private final Condition condC = lock.newCondition();
    private int state = 0;
    private final int loop;

    PrintAbcCondition(int loop) { this.loop = loop; }

    private void doPrint(String name, int target, Condition self, Condition next)
            throws InterruptedException {
        for (int i = 0; i < loop; i++) {
            lock.lock();
            try {
                while (state % 3 != target) {
                    self.await();           // 只挂在自己的条件队列上
                }
                System.out.print(name);
                state++;
                next.signal();              // 精准唤醒下一个，没有惊群
            } finally {
                lock.unlock();              // unlock 必须在 finally，否则异常会导致死锁
            }
        }
    }

    public void printA() throws InterruptedException { doPrint("A", 0, condA, condB); }
    public void printB() throws InterruptedException { doPrint("B", 1, condB, condC); }
    public void printC() throws InterruptedException { doPrint("C", 2, condC, condA); }
}

/* ========== 解法三：Semaphore（信号量传递令牌，最简洁） ========== */
class PrintAbcSemaphore {
    // A 初始有 1 个许可，B、C 初始 0 个，形成一条环形传递链
    private final Semaphore semA = new Semaphore(1);
    private final Semaphore semB = new Semaphore(0);
    private final Semaphore semC = new Semaphore(0);
    private final int loop;

    PrintAbcSemaphore(int loop) { this.loop = loop; }

    private void doPrint(String name, Semaphore self, Semaphore next)
            throws InterruptedException {
        for (int i = 0; i < loop; i++) {
            self.acquire();                 // 拿到许可才能打印
            System.out.print(name);
            next.release();                 // 把许可交给下一个
        }
    }

    public void printA() throws InterruptedException { doPrint("A", semA, semB); }
    public void printB() throws InterruptedException { doPrint("B", semB, semC); }
    public void printC() throws InterruptedException { doPrint("C", semC, semA); }
}

/* ========== 解法四：LockSupport park/unpark（无锁，性能最好） ========== */
class PrintAbcLockSupport {
    private static Thread tA, tB, tC;
    private static final int LOOP = 10;

    public static void run() throws InterruptedException {
        tA = new Thread(() -> {
            for (int i = 0; i < LOOP; i++) {
                System.out.print("A");
                LockSupport.unpark(tB);     // 先 unpark 下一个
                LockSupport.park();         // 再把自己挂起，等下一轮
            }
        }, "A");
        tB = new Thread(() -> {
            for (int i = 0; i < LOOP; i++) {
                LockSupport.park();         // B 先挂起，等 A 叫醒
                System.out.print("B");
                LockSupport.unpark(tC);
            }
        }, "B");
        tC = new Thread(() -> {
            for (int i = 0; i < LOOP; i++) {
                LockSupport.park();
                System.out.print("C");
                LockSupport.unpark(tA);     // 闭环，叫醒 A 开始下一轮
            }
        }, "C");

        tA.start(); tB.start(); tC.start();
        tA.join(); tB.join(); tC.join();
    }
}

/* ========== 解法五：AtomicInteger 自旋（无阻塞，但烧 CPU，仅适合演示） ========== */
class PrintAbcAtomic {
    private final AtomicInteger state = new AtomicInteger(0);
    private final int loop;

    PrintAbcAtomic(int loop) { this.loop = loop; }

    public void doPrint(String name, int target) {
        for (int i = 0; i < loop; ) {
            if (state.get() % 3 == target) {
                System.out.print(name);
                state.incrementAndGet();
                i++;
            } else {
                Thread.onSpinWait();        // JDK 9+：生成 pause 指令，降低自旋功耗
            }
        }
    }
}

三个必须记住的点：

  1. wait 必须写在 while 里，不能写 if。原因有两个：一是 wait 可能发生虚假唤醒（spurious wakeup，POSIX 规范允许）；二是 notifyAll 会唤醒所有等待者，被唤醒的线程重新抢到锁时条件可能已经被别人改掉了。规范写法永远是"循环检查条件谓词"。
  2. 解法一只能用 notifyAll，不能用 notify。notify 从 _WaitSet 里随机挑一个唤醒。假设当前该打印 B，而 notify 唤醒的是 C，C 发现条件不满足又 wait回去，于是没有任何线程能继续——整个程序死锁。用 notifyAll 虽然有惊群开销，但保证正确。想要既精准又高效就得用解法二的多 Condition。
  3. LockSupport 解法的正确性依赖"许可可以预先发放"。即使 A 的 unpark(tB) 发生在 B 的 park() 之前，B 的 permit 已经被置为 1，park() 会直接消耗许可并立即返回，不会阻塞。这是 wait/notify 做不到的（先 notify 后 wait 会永久丢失通知），也是 AQS 选它做底座的根本原因。

/* ========== 版本一：synchronized + wait/notifyAll ========== */
class BufferSync<T> {
    private final LinkedList<T> buf = new LinkedList<>();
    private final int capacity;

    BufferSync(int capacity) { this.capacity = capacity; }

    public void put(T t) throws InterruptedException {
        synchronized (this) {
            while (buf.size() == capacity) {   // 满了就等
                this.wait();
            }
            buf.addLast(t);
            this.notifyAll();                  // 唤醒可能在等"非空"的消费者
        }
    }

    public T take() throws InterruptedException {
        synchronized (this) {
            while (buf.isEmpty()) {            // 空了就等
                this.wait();
            }
            T t = buf.removeFirst();
            this.notifyAll();                  // 唤醒可能在等"未满"的生产者
            return t;
        }
    }
}

/* ========== 版本二：ReentrantLock + 两个 Condition（JDK ArrayBlockingQueue 的做法） ========== */
class BufferLock<T> {
    private final Object[] items;
    private int putIndex, takeIndex, count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    BufferLock(int capacity) { this.items = new Object[capacity]; }

    public void put(T t) throws InterruptedException {
        Objects.requireNonNull(t);
        lock.lock();
        try {
            while (count == items.length) {
                notFull.await();               // 生产者只挂在 notFull 队列
            }
            items[putIndex] = t;
            putIndex = (putIndex + 1) % items.length;   // 环形数组，避免数据搬移
            count++;
            notEmpty.signal();                 // 精准唤醒一个消费者
        } finally {
            lock.unlock();
        }
    }

    @SuppressWarnings("unchecked")
    public T take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) {
                notEmpty.await();
            }
            T t = (T) items[takeIndex];
            items[takeIndex] = null;           // 置 null，避免内存泄漏
            takeIndex = (takeIndex + 1) % items.length;
            count--;
            notFull.signal();
            return t;
        } finally {
            lock.unlock();
        }
    }

    /** 带超时的 offer：awaitNanos 返回剩余时间，必须用返回值重新赋值 */
    public boolean offer(T t, long timeout, TimeUnit unit) throws InterruptedException {
        long nanos = unit.toNanos(timeout);
        lock.lockInterruptibly();
        try {
            while (count == items.length) {
                if (nanos <= 0L) {
                    return false;
                }
                nanos = notFull.awaitNanos(nanos);   // 关键：防止"被唤醒后重新等满一个超时"
            }
            items[putIndex] = t;
            putIndex = (putIndex + 1) % items.length;
            count++;
            notEmpty.signal();
            return true;
        } finally {
            lock.unlock();
        }
    }
}

class ProducerConsumerApp {
    /** 毒丸对象：消费者拿到它就退出，避免用 interrupt 粗暴中断导致数据丢失 */
    private static final String POISON = new String("__POISON__");

    public static void main(String[] args) throws Exception {
        BlockingQueue<String> queue = new ArrayBlockingQueue<>(100);
        int consumerCount = 3;
        ExecutorService pool = new ThreadPoolExecutor(
                4, 4, 0L, TimeUnit.MILLISECONDS,
                new ArrayBlockingQueue<>(16),
                new ThreadFactoryBuilder().setNameFormat("pc-%d").build(),
                new ThreadPoolExecutor.CallerRunsPolicy());

        // 消费者
        for (int i = 0; i < consumerCount; i++) {
            pool.execute(() -> {
                try {
                    for (;;) {
                        String msg = queue.take();
                        if (msg == POISON) {       // 注意：用 == 比较身份，不是 equals
                            break;
                        }
                        handle(msg);
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            });
        }

        // 生产者
        pool.execute(() -> {
            try {
                for (int i = 0; i < 1000; i++) {
                    queue.put("msg-" + i);
                }
                for (int i = 0; i < consumerCount; i++) {
                    queue.put(POISON);             // 每个消费者发一颗毒丸
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        pool.shutdown();
        if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
            pool.shutdownNow();
        }
    }

    private static void handle(String msg) {
        try {
            // 业务处理：异常必须在这里消化，不能让它冲出消费循环
            System.out.println(Thread.currentThread().getName() + " -> " + msg);
        } catch (Throwable t) {
            System.err.println("处理失败，进死信: " + msg);
        }
    }
}

三个必须记住的点：

  1. 版本一的 notifyAll 不能换成 notify。因为生产者和消费者挂在同一个 _WaitSet 里，notify 可能唤醒一个同类：比如缓冲区满时，一个生产者消费掉通知唤醒了另一个生产者，后者发现还是满的又 wait 回去，于是真正该被唤醒的消费者永远收不到通知，形成信号丢失型死锁。这正是 JDK 要用两个 Condition 的原因。
  2. 两个 Condition 带来的是"精准唤醒"。notFull 和 notEmpty 是两条独立队列，生产者只会唤醒消费者、消费者只会唤醒生产者，避免了同类间的无效唤醒和惊群。这让 signal() 替代 signalAll() 成为可能，高并发下吞吐差距非常明显。
  3. 优雅停机优先用毒丸而不是 interrupt。interrupt 会让正在 take() 阻塞的消费者抛 InterruptedException，但如果它刚好取出了消息还没处理完，消息就丢了。毒丸是顺序语义的——它排在所有正常消息之后，消费者拿到它时前面的消息必然已经全部处理完毕。

/* ========== 一、不可重入的独占锁（AQS 独占模式入门） ========== */
public class MyNonReentrantLock implements Lock {

    /** AQS 的标准用法：静态内部类继承 AbstractQueuedSynchronizer */
    private static final class Sync extends AbstractQueuedSynchronizer {

        /** state == 0 空闲，== 1 已被占用 */
        @Override
        protected boolean tryAcquire(int arg) {
            assert arg == 1;
            if (compareAndSetState(0, 1)) {          // 不判断 owner，所以不可重入
                setExclusiveOwnerThread(Thread.currentThread());
                return true;
            }
            return false;
        }

        @Override
        protected boolean tryRelease(int arg) {
            assert arg == 1;
            if (getState() == 0) {
                throw new IllegalMonitorStateException("锁未被持有，不能释放");
            }
            setExclusiveOwnerThread(null);           // 先清 owner
            setState(0);                             // 再写 state（volatile 写，保证可见性）
            return true;
        }

        @Override
        protected boolean isHeldExclusively() {
            return getState() == 1;
        }

        Condition newCondition() {
            return new ConditionObject();            // 复用 AQS 的条件队列实现
        }
    }

    private final Sync sync = new Sync();

    @Override public void lock()                 { sync.acquire(1); }
    @Override public void unlock()               { sync.release(1); }
    @Override public boolean tryLock()           { return sync.tryAcquire(1); }
    @Override public Condition newCondition()    { return sync.newCondition(); }
    @Override public void lockInterruptibly() throws InterruptedException {
        sync.acquireInterruptibly(1);
    }
    @Override public boolean tryLock(long time, TimeUnit unit) throws InterruptedException {
        return sync.tryAcquireNanos(1, unit.toNanos(time));
    }
}

/* ========== 二、可重入版本（对比：只多了 owner 判断和计数累加） ========== */
class MyReentrantSync extends AbstractQueuedSynchronizer {
    @Override
    protected boolean tryAcquire(int acquires) {
        int c = getState();
        if (c == 0) {
            if (compareAndSetState(0, acquires)) {
                setExclusiveOwnerThread(Thread.currentThread());
                return true;
            }
        } else if (getExclusiveOwnerThread() == Thread.currentThread()) {
            int next = c + acquires;
            if (next < 0) {                          // 重入次数溢出
                throw new Error("Maximum lock count exceeded");
            }
            setState(next);                          // 已持锁，无竞争，不需要 CAS
            return true;
        }
        return false;
    }

    @Override
    protected boolean tryRelease(int releases) {
        int c = getState() - releases;
        if (getExclusiveOwnerThread() != Thread.currentThread()) {
            throw new IllegalMonitorStateException();
        }
        boolean free = false;
        if (c == 0) {                                // 只有完全释放才唤醒后继
            free = true;
            setExclusiveOwnerThread(null);
        }
        setState(c);
        return free;
    }
}

/* ========== 三、手写 CountDownLatch（AQS 共享模式） ========== */
public class MyCountDownLatch {

    private static final class Sync extends AbstractQueuedSynchronizer {
        Sync(int count) { setState(count); }        // state 就是剩余计数

        int getCount() { return getState(); }

        /** 共享模式：返回值 >= 0 表示获取成功（可以继续传播唤醒），< 0 表示失败 */
        @Override
        protected int tryAcquireShared(int acquires) {
            return getState() == 0 ? 1 : -1;
        }

        /** 返回 true 表示"需要唤醒后继节点"，即计数刚好减到 0 */
        @Override
        protected boolean tryReleaseShared(int releases) {
            for (;;) {
                int c = getState();
                if (c == 0) {
                    return false;                    // 已经是 0，countDown 多调无副作用
                }
                int next = c - 1;
                if (compareAndSetState(c, next)) {
                    return next == 0;                // 只有减到 0 这一次返回 true
                }
            }
        }
    }

    private final Sync sync;

    public MyCountDownLatch(int count) {
        if (count < 0) {
            throw new IllegalArgumentException("count < 0");
        }
        this.sync = new Sync(count);
    }

    public void await() throws InterruptedException {
        sync.acquireSharedInterruptibly(1);
    }

    public boolean await(long timeout, TimeUnit unit) throws InterruptedException {
        return sync.tryAcquireSharedNanos(1, unit.toNanos(timeout));
    }

    public void countDown() {
        sync.releaseShared(1);
    }

    public long getCount() {
        return sync.getCount();
    }
}

/* ========== 四、手写一个简易 Semaphore（共享模式 + 许可数） ========== */
class MySemaphore {
    private static final class Sync extends AbstractQueuedSynchronizer {
        Sync(int permits) { setState(permits); }

        @Override
        protected int tryAcquireShared(int acquires) {
            for (;;) {
                int available = getState();
                int remaining = available - acquires;
                // remaining < 0 时直接返回负数表示失败，不做 CAS
                if (remaining < 0 || compareAndSetState(available, remaining)) {
                    return remaining;
                }
            }
        }

        @Override
        protected boolean tryReleaseShared(int releases) {
            for (;;) {
                int cur = getState();
                int next = cur + releases;
                if (next < cur) {
                    throw new Error("Maximum permit count exceeded");
                }
                if (compareAndSetState(cur, next)) {
                    return true;                     // 释放许可后总是尝试唤醒
                }
            }
        }
    }

    private final Sync sync;
    MySemaphore(int permits) { this.sync = new Sync(permits); }

    public void acquire() throws InterruptedException { sync.acquireSharedInterruptibly(1); }
    public void release() { sync.releaseShared(1); }
    public int availablePermits() { return sync.getState(); }
}

三个必须记住的点：

  1. AQS 的使用范式是固定的：写一个继承 AQS 的静态内部类 Sync，只重写 tryAcquire/tryRelease（独占）或 tryAcquireShared/tryReleaseShared（共享），绝不重写 acquire/release 本身——排队、park、唤醒、中断处理这些复杂逻辑由 AQS 模板方法负责。外部类只做委托。
  2. state 的语义由你自己定义，这是 AQS 最精妙的地方：ReentrantLock 用它表示重入次数；CountDownLatch 用它表示剩余计数；Semaphore 用它表示可用许可；ReentrantReadWriteLock 把 32 位拆成高 16 位读锁 + 低 16 位写锁。同一套排队框架能支撑完全不同的同步语义。
  3. 独占和共享的核心区别在"唤醒是否传播"。独占模式释放时只唤醒队首一个节点；共享模式通过 setHeadAndPropagate 会连锁唤醒后继的所有共享节点——所以 CountDownLatch 的 countDown 减到 0 时，所有 await 的线程会一起被放行，而不是一个一个。

  3. 实现公平与非公平两种 tryAcquire：非公平直接 CAS 抢；公平版要先调 hasQueuedPredecessors() 检查队列里有没有人排在自己前面。用压测对比两者吞吐差距，并解释非公平为什么更快（减少了一次线程切换）。
  4. 给锁加上超时自动释放的"看门狗"：仿照 Redisson，持锁线程启动一个定时任务续期，超过阈值未续期则强制释放。讨论这在本地锁里为什么通常不需要（进程不会"半死"），但在分布式锁里是必需的。
  5. 实现一个可重入的"分段锁"：lock(String key) 对不同 key 互不阻塞、同一 key 互斥。用 ConcurrentHashMap<String, Sync> + 引用计数管理 Sync 的创建和回收，难点是回收时的竞态（刚判断引用为 0 准备删除时又有人来加锁）。
  6. 用 AQS 实现一个"限流器"：令牌桶，state 存当前令牌数，定时任务补充令牌并 releaseShared 唤醒等待线程。对比 Guava RateLimiter 的做法（它用的是"预支未来令牌"的 SmoothBursty 算法，不走 AQS）。
  7. 读 AbstractQueuedSynchronizer 源码后回答：为什么 CLH 队列需要一个虚拟头节点？waitStatus 的 5 个值（0 / SIGNAL=-1 / CANCELLED=1 / CONDITION=-2 / PROPAGATE=-3）各自在什么时候被设置？shouldParkAfterFailedAcquire 为什么要从后往前清理 CANCELLED 节点？（答案：addWaiter 里 node.prev = pred 先于 pred.next = node，所以 prev 链始终可靠，next 链可能瞬时断裂。）

/* ========== 一、CountDownLatch 做并行聚合（详情页三个数据源） ========== */
public class DetailAggregator {

    private final ExecutorService pool = new ThreadPoolExecutor(
            8, 16, 60L, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(200),
            new ThreadFactoryBuilder().setNameFormat("detail-agg-%d").build(),
            new ThreadPoolExecutor.CallerRunsPolicy());

    public DetailVO query(long itemId) throws InterruptedException {
        DetailVO vo = new DetailVO();
        CountDownLatch latch = new CountDownLatch(3);
        // 并发收集各子任务的异常，主线程统一处理
        List<Throwable> errors = Collections.synchronizedList(new ArrayList<>());

        pool.execute(wrap(latch, errors, () -> vo.setBase(itemService.getBase(itemId))));
        pool.execute(wrap(latch, errors, () -> vo.setStock(stockService.getStock(itemId))));
        pool.execute(wrap(latch, errors, () -> vo.setPrice(priceService.getPrice(itemId))));

        // 必须用带超时的 await，否则下游挂了主线程就永久阻塞
        if (!latch.await(500, TimeUnit.MILLISECONDS)) {
            log.warn("聚合查询超时，返回降级数据, itemId={}", itemId);
        }
        if (!errors.isEmpty()) {
            log.error("聚合查询部分失败, itemId={}, errCount={}", itemId, errors.size(), errors.get(0));
        }
        return vo;   // vo 的字段由不同线程写入，必须是 volatile 或在 await 后才读（happens-before 由 latch 保证）
    }

    /** 关键封装：countDown 必须在 finally，否则异常会让主线程等到超时 */
    private Runnable wrap(CountDownLatch latch, List<Throwable> errors, Runnable task) {
        return () -> {
            try {
                task.run();
            } catch (Throwable t) {
                errors.add(t);
            } finally {
                latch.countDown();
            }
        };
    }
}

/* ========== 二、CompletableFuture 编排（更优雅，支持依赖关系） ========== */
public class OrderOrchestrator {

    private final Executor bizPool = Executors.newFixedThreadPool(16);

    public OrderVO createOrder(long userId, long itemId) {
        // 两个无依赖的查询并行
        CompletableFuture<User> userF = CompletableFuture
                .supplyAsync(() -> userService.get(userId), bizPool)      // 必须传自定义线程池
                .orTimeout(300, TimeUnit.MILLISECONDS)                    // JDK 9+ 超时控制
                .exceptionally(e -> {
                    log.warn("查询用户失败，降级", e);
                    return User.guest();
                });

        CompletableFuture<Item> itemF = CompletableFuture
                .supplyAsync(() -> itemService.get(itemId), bizPool)
                .orTimeout(300, TimeUnit.MILLISECONDS);

        // 有依赖：拿到 item 后再查库存
        CompletableFuture<Integer> stockF = itemF
                .thenApplyAsync(item -> stockService.getStock(item.getSkuId()), bizPool);

        // 三路汇聚
        CompletableFuture<OrderVO> result = userF
                .thenCombine(itemF, (u, i) -> OrderVO.of(u, i))
                .thenCombine(stockF, (vo, stock) -> {
                    vo.setStock(stock);
                    return vo;
                })
                .whenComplete((vo, e) -> {
                    if (e != null) {
                        log.error("下单编排失败", e);     // whenComplete 不吞异常，只观察
                    }
                });

        try {
            // join 抛的是运行时的 CompletionException，get 抛的是受检的 ExecutionException
            return result.get(800, TimeUnit.MILLISECONDS);
        } catch (TimeoutException e) {
            result.cancel(true);
            throw new BizException("下单超时");
        } catch (ExecutionException e) {
            throw new BizException("下单失败", e.getCause());   // 注意要取 getCause
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new BizException("下单被中断");
        }
    }
}

/* ========== 四、修复方案 A：固定加锁顺序（转账场景） ========== */
class TransferFixedOrder {
    private static final Object TIE_LOCK = new Object();   // 加时赛锁，处理 hash 相同

    public void transfer(Account from, Account to, BigDecimal amount) {
        if (from.getId() == to.getId()) {
            throw new IllegalArgumentException("不能给自己转账");
        }
        int h1 = System.identityHashCode(from);
        int h2 = System.identityHashCode(to);
        if (h1 < h2) {
            synchronized (from) { synchronized (to) { doTransfer(from, to, amount); } }
        } else if (h1 > h2) {
            synchronized (to) { synchronized (from) { doTransfer(from, to, amount); } }
        } else {
            // 极端情况：identityHashCode 相同，用全局锁串行化
            synchronized (TIE_LOCK) {
                synchronized (from) { synchronized (to) { doTransfer(from, to, amount); } }
            }
        }
    }

    private void doTransfer(Account from, Account to, BigDecimal amount) {
        if (from.getBalance().compareTo(amount) < 0) {
            throw new BizException("余额不足");
        }
        from.setBalance(from.getBalance().subtract(amount));
        to.setBalance(to.getBalance().add(amount));
    }
}

class DeadlockMonitor {
    private final ThreadMXBean bean = ManagementFactory.getThreadMXBean();

    public void start() {
        ScheduledExecutorService ses = Executors.newSingleThreadScheduledExecutor(
                r -> { Thread t = new Thread(r, "deadlock-monitor"); t.setDaemon(true); return t; });
        ses.scheduleWithFixedDelay(() -> {
            try {
                // findDeadlockedThreads 能检测 synchronized 和 Lock；
                // findMonitorDeadlockedThreads 只能检测 synchronized
                long[] ids = bean.findDeadlockedThreads();
                if (ids != null && ids.length > 0) {
                    ThreadInfo[] infos = bean.getThreadInfo(ids, true, true);
                    StringBuilder sb = new StringBuilder("检测到死锁！\n");
                    for (ThreadInfo info : infos) {
                        sb.append(info.toString());
                    }
                    log.error(sb.toString());
                    alarmService.send("JVM 死锁", sb.toString());
                }
            } catch (Throwable t) {
                log.error("死锁巡检异常", t);     // 巡检任务自身必须吞掉异常，否则调度会永久停止
            }
        }, 1, 1, TimeUnit.MINUTES);
    }
}

三个必须记住的点：

  1. countDown() 永远放在 finally 里。这是聚合查询最容易踩的坑：子任务抛异常时没减计数，主线程就会一直等到超时（甚至永久阻塞，如果用了无参 await()）。同理，await() 必须带超时，这是服务不被下游拖死的最后一道防线。
  2. CompletableFuture 必须传自定义线程池。默认用 ForkJoinPool.commonPool()，它的并行度是 CPU 核数 - 1，所有业务共享；一旦某个业务提交阻塞型 IO 任务，整个 JVM 的所有并行流和异步任务都会被拖慢。更坑的是容器里如果没识别 cgroup 限制，核数可能被算成 1，commonPool 退化成在调用线程执行。
  3. 固定加锁顺序是零成本的死锁根治方案，优先级高于 tryLock。tryLock 虽然也能解决，但引入了重试、活锁风险和更复杂的代码。只有在锁对象顺序确实无法统一时才用它，而且失败后必须释放已持有的锁。

对 Thread 对象调 wait/notify 当同步用join() 内部就是在 Thread 对象上 wait，JVM 在线程结束时会 notifyAll 它，两者会互相干扰。等待线程结束请用 CountDownLatch
wait() 写在 if 里虚假唤醒和 notifyAll 的惊群会让条件失效。永远用 while (条件不满足) wait();
生产者消费者用了 notify() 导致偶发挂死生产者和消费者在同一个 _WaitSet，notify 可能唤醒同类导致信号丢失。要么 notifyAll，要么用两个Condition
lock.lock() 写在 try 里面如果 lock() 本身抛异常，finally 里的 unlock() 会抛 IllegalMonitorStateException 掩盖原始异常。正确写法是 lock(); try { ... } finally { unlock(); }

用 ReentrantReadWriteLock 后写线程长期拿不到锁非公平模式下读锁可以连续插队，写线程饥饿。改用公平模式，或换 StampedLock 的乐观读
StampedLock 当成可重入锁用它不可重入，重入会死锁；而且不支持 Condition，悲观读写锁也不响应中断（中断会导致 CPU 飙高的已知问题）
CountDownLatch 的 countDown() 没放 finally子任务异常时计数不减，主线程等到超时甚至永久阻塞。同理 await() 必须带超时
CountDownLatch 想重复使用它是一次性的，减到 0就不能重置。需要循环屏障用 CyclicBarrier，需要可增减用 Phaser
Semaphore.release() 调用次数多于 acquire()许可数会虚增，限流完全失效。acquire/release 必须用 try/finally 严格配对
ThreadLocal 在线程池里用完没 remove()两个后果：线程长期存活导致 value 永久泄漏；更危险的是脏数据污染，下一个请求读到上一个用户的上下文。必须 try/finally + remove()
以为 ThreadLocal 的 key 是弱引用就不会泄漏弱引用只让 key 被回收，value 仍被 Entry 强引用。清理是启发式的、不保证执行，remove() 才是唯一可靠手段
用 InheritableThreadLocal 给线程池传上下文拷贝只发生在创建线程那一刻，线程池复用线程后永远传不进去。用阿里的 TTL（TtlRunnable / TtlExecutors）在提交任务时传递
SimpleDateFormat 定义成静态成员多线程共用它内部的 Calendar 有可变状态，非线程安全，会出现日期解析错乱甚至死循环。换 DateTimeFormatter（无状态）或用 ThreadLocal 包装
用 HashMap 在并发下 putJDK 7 的环形链表会导致 CPU 100% 死循环，JDK 8 虽修复了但仍会丢数据、size 错乱。并发场景用 ConcurrentHashMap
ConcurrentHashMap 的 containsKey + put 组合使用两个原子操作的组合不是原子的，中间有竞态窗口。用 putIfAbsent / computeIfAbsent / merge 这类复合原子方法
ConcurrentHashMap.computeIfAbsent 的回调里又操作同一个 map会死锁或抛 IllegalStateException: Recursive update，因为该方法对桶加了锁
AtomicLong 在高并发计数场景 CPU 飙高所有线程 CAS 同一变量导致大量自旋失败 + 缓存行弹跳。纯计数场景换 LongAdder（分段 CAS + @Contended 消除伪共享）
把 LongAdder 用在需要精确判断的限流上sum() 不是原子快照，统计期间的并发写会导致结果不精确，会放过超额请求。精确判断用 AtomicLong.decrementAndGet()
用 CAS 更新引用类型时遇到 ABA值从 A→B→A，CAS 察觉不到。用 AtomicStampedReference 加版本号，或 AtomicMarkableReference 加标记位
CompletableFuture 没传自定义线程池默认用 ForkJoinPool.commonPool()，全 JVM 共享且并行度只有 核数-1；容器里核数被算成 1 时甚至退化成同步执行
parallelStream() 里做 RPC 调用同样占用 commonPool，一个慢调用会拖垮全局所有并行流。IO 任务一律用自己的线程池
CompletableFuture.get() 不带超时下游 hang 住就永久阻塞，线程池被打满。一律用 get(timeout, unit) 或 orTimeout
CompletableFuture 的异常被静默吞掉链式调用中间抛异常会跳过后续 thenApply，如果没有 exceptionally / handle / whenComplete 就彻底无感知。必须显式处理
future.cancel(true) 以为能中断正在执行的任务CompletableFuture 的 cancel 不传播中断，已经在跑的任务会跑完。要中断得自己持有 Thread 引用或用标志位
两把锁的获取顺序在不同代码路径不一致经典循环等待死锁（A→B 和 B→A）。统一按 ID 或 identityHashCode 排序加锁，hash 相同时用全局加时赛锁兜底
在 synchronized 块里调 RPC / 查库 / 触发回调临界区被无限拉长，而且被调方可能去拿别的锁导致死锁。遵守"开放调用"原则：把外部调用移到锁外
死锁后想在运行时打破它死锁满足"不可剥夺"，无法在运行时解除，只能重启。所以必须在设计阶段预防 + 加 tryLock 超时兜底
jstack 只抓了一次就下结论要连续抓 3~5 次对比：栈完全不动才是死锁/卡死，栈在变化只是慢。这是区分死锁和性能问题最快的方法
偏向锁在 JDK 15+ 失效了还在依赖它调优JEP 374 废弃了偏向锁（JDK 15 默认关闭，18 彻底移除），因为维护成本高且对现代 Java 代码收益为负。别再用 -XX:+UseBiasedLocking 相关参数
在虚拟线程里用 synchronized 包住 IO会导致 pinning（虚拟线程被钉在载体线程上无法卸载），并发度退化到载体线程数。虚拟线程场景要把 synchronized 换成 ReentrantLock
给虚拟线程配线程池虚拟线程创建极轻量（几百字节），不需要池化，用 Executors.newVirtualThreadPerTaskExecutor() 一个任务一个线程
ForkJoinPool 的任务里做阻塞 IO工作窃取依赖任务能快速完成，阻塞会导致窃取失效、并行度塌陷。要用 ManagedBlocker 或干脆换普通线程池
自旋等待里直接写空 while 循环纯空转烧 CPU 且阻碍超线程兄弟核。用 Thread.onSpinWait()（生成 pause 指令）或加随机退避
两个 tryLock 方案上线后出现活锁两线程以相同节拍互相礼让。加随机退避（sleep(random)）错开重试时机
自定义 AQS 时重写了 acquire() 而不是 tryAcquire()排队、park、中断处理都在模板方法里，重写它等于丢掉整个框架。只能重写 tryAcquire/tryRelease/tryAcquireShared/tryReleaseShared
多个状态变量分别用原子类，以为组合起来就线程安全CAS 只保证单个变量的原子性。多变量要封装成不可变对象配 AtomicReference，或者直接加锁
