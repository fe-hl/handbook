基础原理 ​

1. FastAPI 的定位：它其实是三个东西的组合 ​

FastAPI 自己并没有写网络层和校验层，它做的是把三块现成能力用类型注解缝在一起。搞清楚这个分层，后面所有「这个行为是谁决定的」的问题都能自己推出来。

text

│            @app.post("/chat")  async def chat(...)      │
└─────────────────────────────────────────────────────────┘
                 ↓ 类型注解驱动（FastAPI 的核心创新）
┌─────────────────────────────────────────────────────────┐
│  FastAPI：路由装饰器 / 依赖注入 / 参数来源推断 /   │
│           OpenAPI 文档生成 / 异常处理器注册               │
└────────────────────────┬────────────────────────────────┘

│ Pydantic（+ pydantic-core │  │ Starlette                │
│ 的 Rust 实现）            │  │ 路由匹配 / Request /     │
│ 入参校验、类型转换、       │  │ Response / 中间件 /      │
│ 出参序列化、JSON Schema    │  │ WebSocket / 后台任务     │

面试加分表述：「FastAPI 的核心创新不是性能，性能是 Starlette 和 uvloop 给的；它的创新在于把类型注解同时用于三件事——运行时校验、依赖注入、OpenAPI 文档生成。一份 ChatRequest 的定义，既是校验规则，又是接口文档，又是 IDE 的补全来源，三者天然不会不一致。这对我们这种前后端并行开发 AI 接口的场景收益非常大，前端不用等我写文档。」

2. ASGI 与 WSGI：为什么流式输出必须用 ASGI ​

这是 FastAPI 和 Flask 的根本分水岭，不是「语法糖差异」。

text
WSGI（Flask / Django 同步模式）
  app(environ, start_response) -> iterable
  ├─ 一个请求 = 一个线程，期间线程被占满
  ├─ 接口函数是普通函数，返回即结束
  └─ 没有 WebSocket，没有服务端推送的协议抽象

ASGI（FastAPI / Starlette）
  async def app(scope, receive, send)
  ├─ scope：本次连接的元信息（类型 http / websocket / lifespan）
  ├─ receive：异步拉取客户端事件（请求体分片、断开通知）
  └─ send：异步推送事件，可以调用【多次】
          ↑
     SSE / 分块传输的根基：send 多次 http.response.body

关键差异汇总：

维度WSGIASGI
接口形态同步可调用，返回一次协程 + receive/send 事件流
一个连接的并发代价一个线程（约 8MB 栈）一个协程（约 KB 级）
服务端能否多次推送靠生成器勉强可以，但线程一直占着原生支持，send 可调用任意多次
WebSocket不支持（需另起方案）协议内置
生命周期事件无标准lifespan scope 标准化
IO 密集（调 LLM）吞吐受线程数限制，百级并发受内存/下游限制，万级并发

⚠️ 很多人说「Flask 也能做流式，yield 就行」。能做，但每个在途连接独占一个线程。AI 场景一次对话要流式推 30 秒，100 个并发就是 100 个线程挂 30 秒，Gunicorn 默认几十个 worker 直接被打满，新请求全部排队。这不是写法问题，是模型问题。

3. 参数来源推断规则：FastAPI 怎么知道这个参数从哪来 ​

这是新手最容易「写对了但不知道为什么对」的地方。FastAPI 的判断顺序是固定的：

text
对函数的每个参数，依次判断：
  ① 参数名出现在路径模板里（如 /items/{item_id}）  → 路径参数 Path
  ② 显式标注了 Query/Header/Cookie/Body/Form/File → 按标注来
  ③ 类型是 Pydantic BaseModel 子类                → 请求体 Body（JSON）
  ④ 类型是 Request/Response/BackgroundTasks 等     → 框架对象，直接注入
  ⑤ 默认值是 Depends(...)                          → 依赖注入
  ⑥ 其余标量类型（int/str/float/bool/枚举/list）   → 查询参数 Query
python
from typing import Annotated
from fastapi import FastAPI, Path, Query, Header, Depends
from pydantic import BaseModel

app = FastAPI()

class ChatBody(BaseModel):
    prompt: str
    temperature: float = 0.7

@app.post("/agents/{agent_id}/chat")
async def chat(
    agent_id: Annotated[str, Path(min_length=1, max_length=64)],   # ① 路径
    body: ChatBody,                                                 # ③ 请求体
    stream: Annotated[bool, Query(description="是否流式")] = False,  # ⑥ 查询
    x_trace_id: Annotated[str | None, Header()] = None,             # ② 请求头
    user=Depends(get_current_user),                                 # ⑤ 依赖
):
    ...

几个必须知道的细节：

细节说明
Header 名字映射参数 x_trace_id 自动对应 X-Trace-Id（下划线转连字符），要关掉用 Header(convert_underscores=False)
多个 BaseModel 参数两个及以上 Body 模型时，FastAPI 会自动把它们嵌套成 {"body1": {...}, "body2": {...}}
单模型想要嵌套用 Body(embed=True) 强制包一层
list[str] 做查询参数必须显式 Query()，否则会被当成 Body；传参形式是 ?tag=a&tag=b
GET 请求带 Body协议不禁止但代理/网关常丢掉，不要这么设计

⚠️ 推荐统一用 Annotated 写法。老写法 stream: bool = Query(False) 把默认值和元信息混在一起，导致这个函数不能被当成普通 Python 函数直接调用（默认值是个 Query 对象）。Annotated[bool, Query()] = False 把「类型元信息」和「默认值」分开，函数仍然是可直接调用、可被测试复用的普通函数。这是 FastAPI 官方文档现在的首选写法。

4. Pydantic v2 核心用法与 v1 迁移对照 ​

Pydantic v2 把校验核心用 Rust 重写（pydantic-core），校验速度比 v1 快 5~50 倍，但 API 有大量重命名。现在新项目一律 v2，但线上老代码和网上大量教程还是 v1，必须能对上。

python
from typing import Annotated, Literal
from pydantic import BaseModel, Field, field_validator, model_validator, ConfigDict

class Message(BaseModel):
    role: Literal["system", "user", "assistant"]
    content: Annotated[str, Field(min_length=1, max_length=8000)]

class ChatRequest(BaseModel):
    # v2 用 model_config 替代 class Config
    model_config = ConfigDict(
        extra="forbid",            # 多传字段直接报错，防止前端拼错字段名却静默忽略
        str_strip_whitespace=True, # 自动去首尾空格
        frozen=False,
    )

    messages: Annotated[list[Message], Field(min_length=1, max_length=50)]
    temperature: Annotated[float, Field(ge=0.0, le=2.0)] = 0.7
    max_tokens: Annotated[int, Field(gt=0, le=4096)] = 1024
    model: str = "gpt-4o-mini"

    @field_validator("model")
    @classmethod
    def check_model_allowed(cls, v: str) -> str:
        allowed = {"gpt-4o-mini", "gpt-4o", "qwen-max"}
        if v not in allowed:
            raise ValueError(f"model 必须是 {allowed} 之一")
        return v

    @model_validator(mode="after")
    def check_last_is_user(self):
        # 跨字段校验：最后一条必须是用户提问，否则 LLM 调用没意义
        if self.messages[-1].role != "user":
            raise ValueError("messages 最后一条必须是 role=user")
        return self

v1v2备注
class Config:model_config = ConfigDict(...)类属性改成字典
@validator@field_validator + @classmethod忘加 @classmethod 会报错
@root_validator@model_validator(mode="before"/"after")after 拿到的是模型实例
.dict().model_dump()返回 Python 对象
.json().model_dump_json()返回 JSON 字符串
parse_obj()model_validate()从 dict 构造
parse_raw()model_validate_json()从 JSON 串构造，比先 json.loads 更快
.schema().model_json_schema()生成 JSON Schema
Field(regex=...)Field(pattern=...)名字变了
min_items / max_itemsmin_length / max_length列表长度统一成 length
allow_mutation=Falsefrozen=True
BaseSettings 在 pydantic 里拆到独立包 pydantic-settings必须额外装

⚠️ extra="forbid" 强烈建议在入参模型上打开。默认 extra="ignore" 会让前端把 temperture 拼错成这样时静默丢弃，接口返回 200 但温度参数根本没生效，这类 bug 极难定位。反过来出参模型不要 forbid，否则下游多返回一个字段就报 500。

5. 校验失败发生了什么：422 与 RequestValidationError ​

FastAPI 默认的校验错误响应长这样，状态码是 422 不是 400：

json
{
  "detail": [
    {
      "type": "greater_than_equal",
      "loc": ["body", "temperature"],
      "msg": "Input should be greater than or equal to 0",
      "input": -1,
      "ctx": { "ge": 0 }
    }
  ]
}

这个结构对前端很不友好：detail 是数组、字段路径在 loc 里、没有业务错误码。生产项目一定要统一包装：

python
from fastapi import FastAPI, Request, status
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse

app = FastAPI()

@app.exception_handler(RequestValidationError)
async def validation_handler(request: Request, exc: RequestValidationError):
    first = exc.errors()[0]
    # loc 形如 ("body", "messages", 0, "content")，跳过第一段来源标识
    field = ".".join(str(x) for x in first["loc"][1:]) or first["loc"][0]
    return JSONResponse(
        status_code=status.HTTP_422_UNPROCESSABLE_ENTITY,
        content={
            "code": 40001,
            "message": f"参数 {field} 不合法：{first['msg']}",
            "trace_id": request.headers.get("X-Trace-Id", ""),
            "errors": exc.errors(),   # 保留原始明细，方便前端联调和自己排查
        },
    )
要点说明
为什么是 422 不是 400400 表示「请求本身格式不对」，422 表示「格式对但语义不合法」。可以改成 400，但要全局统一
exc.errors() 里有 input 字段生产环境注意脱敏，它会把用户传的原始值（可能含敏感内容）回显出去
出参校验失败是 500入参不合法是客户端的错（422），response_model 校验失败是服务端自己的 bug，抛 ResponseValidationError → 500
自定义错误文案在 field_validator 里 raise ValueError("中文提示")，msg 会变成 Value error, 中文提示

6. response_model 与出参过滤：防止把密钥返回给前端 ​

response_model 不只是写文档用的，它会真的按模型过滤和校验返回值，这是一道实际生效的安全防线。

python
from pydantic import BaseModel, EmailStr

class UserInDB(BaseModel):
    id: int
    email: EmailStr
    hashed_password: str      # 绝不能出现在响应里
    api_key: str              # 绝不能出现在响应里

class UserOut(BaseModel):
    id: int
    email: EmailStr

# ❌ 错误写法：返回类型随手写成 DB 模型，密码哈希和 api_key 直接泄漏给前端
@app.get("/me_bad", response_model=UserInDB)
async def me_bad() -> UserInDB:
    return load_user()

# ✅ 正确写法：出参用独立的 Out 模型，多出来的字段被自动剔除
@app.get("/me", response_model=UserOut)
async def me():
    return load_user()        # 返回的是 UserInDB，但响应里只有 id 和 email

常用参数：

参数作用典型场景
response_model_exclude_none=True值为 None 的字段不输出减小 SSE/列表接口体积
response_model_exclude_unset=True只输出显式设置过的字段PATCH 接口回显
response_model_exclude={"a","b"}临时排除字段不想为一个接口单开模型
status_code=201指定成功状态码创建类接口
responses={404: {...}}补充其他状态码的文档让 OpenAPI 更完整

⚠️ StreamingResponse 和 response_model 不兼容。流式接口的返回值是响应对象本身，FastAPI 不会（也没法）用模型去校验流内容。所以流式接口的「出参契约」只能靠文档和前端约定，这也是后面 SSE 章节要专门定义 data 载荷结构的原因。

⚠️ 返回类型注解和 response_model 同时存在时，response_model 优先。上面 me_bad 的写法之所以危险，就是因为很多人把 -> UserInDB 当成「只是给 IDE 看的」，但 FastAPI 在没有 response_model 时会直接拿返回注解当出参模型。

7. 依赖注入 Depends 的本质：一个可调用对象 + 一次缓存 ​

Depends 没有任何魔法，它的规则只有三条：

  1. 传给它的东西必须是可调用对象（函数、协程函数、类、带 __call__ 的实例）；
  2. FastAPI 会递归解析这个可调用对象自己的参数（所以依赖可以嵌套依赖，也可以从请求里取参数）；
  3. 同一次请求内，同一个依赖只执行一次，结果被缓存复用。
python
from typing import Annotated
from fastapi import Depends, Header, HTTPException

# 一、函数依赖：自己也能声明 Header/Query 参数
async def get_token(authorization: Annotated[str | None, Header()] = None) -> str:
    if not authorization or not authorization.startswith("Bearer "):
        raise HTTPException(401, "缺少或非法的 Authorization 头")
    return authorization.removeprefix("Bearer ")

# 二、依赖嵌套依赖：解析用户时自动先解析 token
async def get_current_user(token: Annotated[str, Depends(get_token)]) -> dict:
    user = await verify_jwt(token)
    if not user:
        raise HTTPException(401, "token 已失效")
    return user

# 三、类依赖：适合一组相关的查询参数，自带类型提示
class Pagination:
    def __init__(self, page: int = 1, size: int = 20):
        self.page = max(page, 1)
        self.size = min(max(size, 1), 100)     # 强制上限，防止被拉全表
        self.offset = (self.page - 1) * self.size

# 四、带参数的依赖（可配置依赖）：用实例的 __call__
class RequireRole:
    def __init__(self, *roles: str):
        self.roles = set(roles)

    def __call__(self, user: Annotated[dict, Depends(get_current_user)]) -> dict:
        if user["role"] not in self.roles:
            raise HTTPException(403, "权限不足")
        return user

require_admin = RequireRole("admin", "owner")

@app.get("/admin/stats")
async def stats(
    user: Annotated[dict, Depends(require_admin)],
    page: Annotated[Pagination, Depends()],     # 类型即依赖，Depends() 可以不传参
):
    return {"user": user["id"], "offset": page.offset}

依赖缓存机制（面试高频）：

python
# 一次请求里 get_db 只会执行一次，a 和 b 拿到的是同一个 Session
async def handler(
    a: Annotated[Session, Depends(get_db)],
    b: Annotated[Session, Depends(get_db)],
): ...

# 想让它每次都重新执行（比如每次要不同的随机值 / 独立事务）
async def handler2(
    a: Annotated[Session, Depends(get_db, use_cache=False)],
): ...

依赖的四种挂载位置，覆盖范围从小到大：

位置写法适用场景
单个接口参数def f(u = Depends(get_user))需要拿到返回值
单个接口装饰器@app.get("/x", dependencies=[Depends(verify_sign)])只做校验，不要返回值
路由分组APIRouter(dependencies=[Depends(get_current_user)])整个模块统一鉴权
全局FastAPI(dependencies=[Depends(verify_api_key)])全站生效的轻量校验

⚠️ dependencies=[...] 里的依赖返回值会被丢弃，只用于「执行副作用或抛异常」。需要用返回值就必须写成函数参数。这是最常见的「我明明注入了怎么拿不到」的原因。

面试加分表述：「我会用一句话区分依赖和中间件：依赖是「这个接口需要什么」，中间件是「所有请求都要经过什么」。鉴权、取当前用户、拿 DB 会话这些和接口语义绑定的，一律用 Depends——它能进 OpenAPI 文档、能在测试里被 dependency_overrides 替换、还能按路由分组精确控制范围；而 trace_id 注入、全局耗时统计、CORS 这些与业务无关的横切关注点才用中间件。」

8. yield 依赖：请求级资源的获取与释放 ​

yield 依赖是 FastAPI 管理「用完必须释放」资源的标准方式——数据库会话、文件句柄、分布式锁、链路 span。

python
from collections.abc import AsyncGenerator
from sqlalchemy.ext.asyncio import AsyncSession

async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async with SessionLocal() as session:        # yield 之前：获取资源
        try:
            yield session                        # yield 的值注入给接口
            await session.commit()               # 接口正常返回后提交
        except Exception:
            await session.rollback()             # 接口抛异常则回滚
            raise
        # async with 退出时自动 close，无需手写 finally

执行时序必须记牢：

text
请求进入
  → 依赖 yield 之前的代码（建连接 / 开事务）
  → 接口函数执行
  → 接口返回值被 response_model 校验、序列化
  → 【响应已发送给客户端】
  → 依赖 yield 之后的代码（提交 / 回滚 / 释放）
  → 异常处理器（如果有异常）
坑点说明与对策
yield 之后抛 HTTPException 不生效响应已经发出去了，改不了状态码。校验要放在 yield 之前
yield 之后的代码里用了已关闭的资源退出顺序是后进先出，依赖 B 依赖 A 时，B 的清理先跑，A 后跑
同步 def + yield 依赖也支持，但会跑在线程池里；异步资源（AsyncSession）必须用 async def
懒加载对象在响应序列化时才访问 DB这时 session 可能已经在清理路径上，SQLAlchemy 会报 DetachedInstanceError。在接口内就把需要的字段取出来
python
# ❌ 错误写法：把权限校验放在 yield 之后，异常被吞，客户端拿到的还是 200
async def bad_dep():
    yield
    if not check():
        raise HTTPException(403, "无权限")   # 太晚了，响应已发送

# ✅ 正确写法：校验在前，清理在后
async def good_dep():
    if not check():
        raise HTTPException(403, "无权限")
    span = tracer.start("request")
    try:
        yield span
    finally:
        span.end()

9. dependency_overrides：为测试而生的覆盖机制 ​

这是 FastAPI 依赖注入最被低估的价值——不用 mock 库、不用 patch 路径，直接换掉依赖实现。

python
# main.py
def get_llm_client() -> LLMClient: ...
def get_db() -> AsyncSession: ...

# test_chat.py
from fastapi.testclient import TestClient
from main import app, get_llm_client

class FakeLLM:
    async def chat(self, messages, **kw):
        return "这是固定的假回答"

app.dependency_overrides[get_llm_client] = lambda: FakeLLM()

def test_chat():
    with TestClient(app) as client:
        r = client.post("/chat", json={"messages": [{"role": "user", "content": "hi"}]})
        assert r.status_code == 200
        assert r.json()["answer"] == "这是固定的假回答"

app.dependency_overrides.clear()    # 用完一定清理，否则污染其他用例
要点说明
key 必须是原始依赖函数对象不是字符串路径，所以重命名函数时测试会直接报错而不是静默失效
覆盖是递归生效的覆盖 get_db 后，所有依赖 get_db 的上层依赖都用新实现
推荐用 pytest fixture 管理在 fixture 里设置、yield、然后 clear()，避免用例间互相污染
真实依赖应该写成「可被覆盖的粒度」不要在接口里直接 LLMClient()，那样没法替换——可测性反过来约束了设计

面试加分表述：「我们所有外部依赖——LLM 客户端、向量库、Redis、DB——都统一走 Depends 注入而不是在接口里 new。这么做的直接收益是单测里用 dependency_overrides 一行就能换成假实现，CI 上跑接口测试完全不需要连真实的大模型，一次完整回归从原来烧十几块钱 token、跑 8 分钟，变成不花钱、20 秒跑完。」

10. async def 还是 def：这是 FastAPI 最大的性能陷阱 ​

FastAPI 对两种函数的调度方式完全不同：

text
async def 接口
  └─ 直接在事件循环里 await 执行
     ├─ 优点：没有线程切换开销，并发能力只受内存和下游限制
     └─ 要求：函数体内【不能有任何同步阻塞调用】

def 接口（普通同步函数）
  └─ 被 run_in_threadpool 丢到 anyio 线程池执行
     ├─ 线程池默认上限 40（anyio 的 total_tokens 默认值）
     ├─ 优点：写同步阻塞代码是安全的，不会卡住事件循环
     └─ 缺点：并发上限 = 线程池大小，超了就排队

四种组合的后果：

写法函数体内容结果
async def全是 await（httpx 异步、异步 ORM）✅ 最佳，高并发
def同步阻塞（requests、同步 ORM、文件 IO）✅ 可接受，并发上限约 40
async def含同步阻塞（requests.get、time.sleep）❌ 灾难：卡住整个事件循环，所有请求一起变慢
def全是异步调用❌ 协程没被 await，直接报错或静默不执行
python
import asyncio, time
import httpx, requests
from fastapi import FastAPI

app = FastAPI()

# ❌ 最危险的写法：async def 里用同步客户端
@app.post("/chat_bad")
async def chat_bad(req: ChatRequest):
    r = requests.post(LLM_URL, json=req.model_dump(), timeout=30)   # 阻塞事件循环 30 秒
    return r.json()          # 这一个请求会让全服务所有接口都卡住

# ✅ 方案一：全异步（首选）
@app.post("/chat")
async def chat(req: ChatRequest, client: Annotated[httpx.AsyncClient, Depends(get_http)]):
    r = await client.post(LLM_URL, json=req.model_dump())
    return r.json()

# ✅ 方案二：实在只有同步 SDK，就把接口写成 def，让框架帮你丢线程池
@app.post("/chat_sync")
def chat_sync(req: ChatRequest):
    return legacy_sdk.invoke(req.prompt)        # 跑在线程池里，不影响事件循环

# ✅ 方案三：异步接口里局部调用同步代码，显式丢线程
@app.post("/chat_mixed")
async def chat_mixed(req: ChatRequest):
    text = await asyncio.to_thread(legacy_sdk.invoke, req.prompt)
    return {"answer": text}

⚠️ 自查清单：async def 接口里出现以下任何一个，都是 bug——requests、time.sleep、同步 pymysql/psycopg2、open() 读大文件、subprocess.run、CPU 密集循环（如本地跑 embedding）。装 ruff 并开启 ASYNC 和 ASYNC1 规则集可以自动扫出大部分。

⚠️ 线程池大小可以调，但不是解决方案：

python
import anyio
@app.on_event("startup")       # 新项目用 lifespan，见下一节

    anyio.to_thread.current_default_thread_limiter().total_tokens = 80

调大它只是把「排队」换成「更多线程竞争 GIL」，真正的解法是把阻塞 IO 换成异步客户端。

from fastapi import FastAPI
import httpx, redis.asyncio as aioredis

@asynccontextmanager
async def lifespan(app: FastAPI):

    await app.state.vector.close()
    await app.state.redis.close()
    await app.state.http.aclose()

12. app.state 与全局单例：客户端为什么必须复用 ​

这是 AI 后端最常见的性能问题来源——每次请求都新建 HTTP 客户端。

python

    async with httpx.AsyncClient() as client:        # 每次都重新 TCP + TLS 握手
        r = await client.post(LLM_URL, json=...)
    return r.json()
# 代价：每次多 1 次 TCP 三次握手 + 1 次 TLS 握手（约 50~200ms），
#       高并发下还会耗尽本机端口，出现 TIME_WAIT 堆积

# ✅ 正确写法：lifespan 建一次，依赖注入取出来复用
from fastapi import Request

async def get_http(request: Request) -> httpx.AsyncClient:
    return request.app.state.http

@app.post("/chat")
async def chat(
    req: ChatRequest,
    client: Annotated[httpx.AsyncClient, Depends(get_http)],
):
    r = await client.post(LLM_URL, json=req.model_dump())
    return r.json()

方式写法评价
app.state + 依赖读取上面的写法✅ 推荐：可被 dependency_overrides 替换，多 app 实例不冲突
模块级全局变量client = httpx.AsyncClient() 写在模块顶层❌ 在模块导入时就创建，可能绑定到错误的事件循环，测试时尤其容易出问题
functools.lru_cache 包装工厂@lru_cache def get_client()⚠️ 能用，但关闭时机不可控，不会被 lifespan 释放

13. 中间件：能力、代价和那个必须知道的坑 ​

python
import time
from starlette.middleware.base import BaseHTTPMiddleware

class TimingMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        start = time.perf_counter()
        response = await call_next(request)
        cost_ms = (time.perf_counter() - start) * 1000
        response.headers["X-Process-Time"] = f"{cost_ms:.1f}"
        logger.info("%s %s %s %.1fms",
                    request.method, request.url.path, response.status_code, cost_ms)
        return response

app.add_middleware(TimingMiddleware)

执行顺序是洋葱模型，而且注册顺序和执行顺序相反：

中间件能做中间件做不到
改请求头、改响应头不能像依赖那样把值作为参数注入给接口

注入/透传 trace_id不能在测试里被 dependency_overrides 替换
统一捕获未处理异常不能按单个路由精确开关（只能按路径前缀自己判断）

⚠️ BaseHTTPMiddleware 会破坏流式响应。它的实现是把下游响应包装成一个新的 StreamingResponse，中间经过一层内存队列转发，在某些版本和配置下会导致 SSE 分片被攒着一起发——前端表现为「等了 20 秒，然后一次性蹦出全部文字」，打字机效果完全消失。另外它还会让异常传播路径变复杂，CancelledError 可能被吃掉导致断连检测失效。

两种解法：

15. BackgroundTasks：它不是任务队列 ​

BackgroundTasks 的执行时机是「响应已经写回客户端之后，同一个进程里继续跑」。它既没有持久化，也没有重试，进程一重启任务就彻底消失。

python
from fastapi import BackgroundTasks, FastAPI

app = FastAPI()

def write_audit_log(trace_id: str, user_id: str, tokens: int) -> None:
    # 这里是同步函数 → FastAPI 会丢到线程池执行，不会阻塞事件循环
    db.audit.insert({"trace_id": trace_id, "user_id": user_id, "tokens": tokens})

@app.post("/chat")
async def chat(body: ChatIn, bg: BackgroundTasks):
    answer, tokens = await llm.complete(body.messages)
    # 响应先返回，日志后落库：用户感知不到这 20ms
    bg.add_task(write_audit_log, body.trace_id, body.user_id, tokens)
    return {"answer": answer}
维度BackgroundTasksCelery / RQ / arq
运行位置当前 Web 进程，占用同一份 CPU 和线程池独立 worker 进程／独立机器
持久化❌ 无，进程退出即丢✅ 任务存在 Redis / RabbitMQ
重试❌ 自己写 try✅ 内置 retry、退避策略
定时／延迟❌ 不支持✅ 支持 ETA、周期任务
可观测性只有自己打的日志✅ Flower 等面板、任务状态查询
适用任务时长毫秒到几百毫秒秒级到小时级
典型用途审计日志、埋点上报、发一条通知文档切片向量化、批量导出、模型离线评测
python
# ❌ 错误用法：把 3 分钟的向量化任务塞进 BackgroundTasks
@app.post("/documents")

    bg.add_task(embed_whole_document, file)   # 滚动发布时这个任务直接被 kill
    return {"status": "processing"}

# ✅ 正确用法：投递到真正的队列，接口只负责返回任务 ID
@app.post("/documents")

    task = embed_document.delay(await file.read())   # Celery
    return {"task_id": task.id, "status": "queued"}

⚠️ BackgroundTasks 里不要再读请求体。Request 对象在响应发出后其底层连接可能已关闭，需要的数据必须在请求处理阶段就取出来、以值的形式传进后台函数。

面试加分表述：BackgroundTasks 本质是挂在响应对象上的回调列表，在 ASGI http.response.body 发完之后由同一个事件循环执行。所以它的定位是「不想让用户等的收尾动作」，而不是「异步任务系统」。判断标准很简单：这个任务丢了能不能接受？不能接受就必须上队列。

16. 异常处理体系：从 HTTPException 到统一响应体 ​

FastAPI 的异常处理有三层，搞清楚各自的拦截范围，才不会出现「业务异常被 500吞掉」。

text
请求进入
  │
  ├─ 参数校验失败 ────────→ RequestValidationError ──→ 422（可覆盖）
  │
  ├─ 业务主动 raise ──────→ HTTPException          ──→ 指定状态码
  │                        自定义异常 + handler    ──→ 自定义响应体
  │
  └─ 没人接的异常 ────────→ Exception handler      ──→ 500（必须兜底，别泄栈）
python
from fastapi import FastAPI, HTTPException, Request, status
from fastapi.responses import JSONResponse

app = FastAPI()

# 1）定义业务异常基类，携带业务码与 HTTP 码
class BizError(Exception):
    def __init__(self, code: str, message: str, http_status: int = 400) -> None:
        self.code = code
        self.message = message
        self.http_status = http_status

class QuotaExceeded(BizError):
    def __init__(self, used: int, limit: int) -> None:
        super().__init__(
            code="QUOTA_EXCEEDED",
            message=f"本月额度已用完（{used}/{limit}）",
            http_status=status.HTTP_429_TOO_MANY_REQUESTS,
        )

# 2）统一响应体：成功和失败结构一致，前端只认 code
def envelope(code: str, message: str, data=None, trace_id: str = "") -> dict:
    return {"code": code, "message": message, "data": data, "trace_id": trace_id}

@app.exception_handler(BizError)
async def biz_error_handler(request: Request, exc: BizError) -> JSONResponse:
    trace_id = getattr(request.state, "trace_id", "")
    logger.warning("biz_error code=%s msg=%s trace_id=%s", exc.code, exc.message, trace_id)
    return JSONResponse(
        status_code=exc.http_status,
        content=envelope(exc.code, exc.message, trace_id=trace_id),
    )

# 3）兜底：任何没被接住的异常都不能把堆栈返回给客户端
@app.exception_handler(Exception)
async def unhandled_handler(request: Request, exc: Exception) -> JSONResponse:
    trace_id = getattr(request.state, "trace_id", "")
    logger.exception("unhandled error trace_id=%s", trace_id)   # 栈只进日志
    return JSONResponse(
        status_code=500,
        content=envelope("INTERNAL_ERROR", "服务内部错误，请稍后重试", trace_id=trace_id),
    )
异常类型谁抛的默认状态码要不要自定义
RequestValidationErrorFastAPI 参数校验422建议改成统一响应体，并把字段路径拼成人类可读的 message
HTTPException业务代码 / 依赖自己指定简单场景直接用即可
自定义 BizError业务代码自己指定推荐，业务码与 HTTP 码解耦
Exception任何地方500必须兜底，否则默认返回纯文本并可能泄露栈信息
HTTPException in yield 依赖的 finally 之后清理代码—此时响应已发出，异常只能进日志

⚠️ 流式接口的异常处理是完全不同的路线。StreamingResponse 一旦开始发送数据，状态码和响应头就已经定稿，之后 raise HTTPException 不会变成 500，异常处理器也不会被触发。正确做法是在 SSE 数据流里推一条 event: error 的消息，让前端在流内部感知错误。

面试加分表述：我们团队的规范是「HTTP 状态码表达传输语义，业务码表达业务语义」。限流用 429、鉴权失败用 401/403、上游超时用 504，但响应体里一律带 code 字段，前端只根据 code 做文案和重试决策，这样新增业务错误不需要前端改状态码判断逻辑。

场景workers 建议理由
纯 IO 密集（调 LLM、查 DB）2 ~ 4，再靠协程扛并发瓶颈在上游 RT，不在 CPU；进程多了只是多占内存
有 CPU 密集计算（本地分词、向量运算）CPU 核数（或核数 + 1）必须靠多进程绕开 GIL
K8s 容器内建议 --workers 1，用副本数扩容让 HPA 按 Pod 粒度伸缩，指标更准、滚更新更可控
带内存缓存／本地状态1多 worker 之间内存不共享，缓存命中率会被打散
SSE 长连接为主按「并发连接数 ÷ 单进程可承载连接数」估算每条 SSE 都占一个连接，注意文件描述符上限

⚠️ --reload 绝不能上生产：它会起一个文件监听进程，内存占用翻倍，且任何文件系统抖动都可能触发重启，直接掐断在途的流式请求。

⚠️ 多 worker 下进程内状态全部失效：内存限流计数器、本地缓存、全局字典，4 个 worker 就是 4 份。需要共享状态时一律用 Redis。

面试加分表述：GIL 限制的是「同一进程内同一时刻只有一个线程执行 Python 字节码」，它不影响等待 IO 的协程——因为等待时根本不需要执行字节码。所以 IO 密集服务靠 async 就能把并发拉上去，workers 只需要够用；只有真正的 CPU 密集计算才需要多进程，或者干脆把计算挪到独立的 worker 服务里。

21. 异步数据库集成：SQLAlchemy 2.0 async、连接池与事务边界 ​

FastAPI 项目里数据库是最容易「写得能跑、但一上量就崩」的一块。核心原因是：驱动必须是异步的、会话必须是请求级的、连接池必须按进程数反推，这三件事任意一件错了，表现都是「本地没问题，线上连接数爆了」。

python
# app/db.py —— 引擎与会话工厂：进程级单例，整个应用只建一次
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker, AsyncSession

engine = create_async_engine(
    "postgresql+asyncpg://user:pwd@host:5432/db",   # ⚠️ 驱动必须是 asyncpg / aiomysql
    pool_size=10,            # 常驻连接数
    max_overflow=5,          # 峰值可临时多开的连接数
    pool_timeout=5,          # 等不到连接时的排队上限，宁可快速失败也别无限等
    pool_recycle=1800,       # 主动回收，躲开 DB / 中间件的空闲连接回收
    pool_pre_ping=True,      # 取连接前先 ping，避免拿到已被服务端关掉的死连接
    echo=False,
)

SessionLocal = async_sessionmaker(
    engine,
    expire_on_commit=False,  # ⚠️ 关键：commit 后不过期对象，否则再读属性会触发新 IO
    autoflush=False,
)
python
# app/deps.py —— 会话依赖：请求级，事务边界显式写在依赖里
async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async with SessionLocal() as session:
        try:
            yield session
            await session.commit()        # 请求正常结束才提交
        except Exception:
            await session.rollback()      # 任何异常全量回滚
            raise
        # async with 退出时自动 close，连接归还池子

事务边界放哪，是最常被问的设计题：

方案适用场景风险
依赖里统一 commit（上面的写法）大多数 CRUD 接口，一个请求 = 一个事务长事务：请求里夹了 LLM 调用会把事务拖到几十秒，连接被长期占用
Service 层自己 async with session.begin()一个请求里有多个独立事务，或需要「先落库再调外部」需要团队约定清楚，否则出现嵌套事务混乱
IO 前先提交，拆成两段事务接口里要调 LLM / 第三方需要补偿逻辑：第二段失败要能标记状态为 failed

⚠️ 长事务是 LLM 类接口的头号杀手。一次生成要 30 秒，如果整个请求包在一个事务里，10 个并发就占满了 pool_size=10 的连接池，第 11 个请求直接在 pool_timeout 上超时。正确做法是：先写入一条 status=pending 的记录并立即提交，再去调模型，拿到结果后开新事务更新状态。

# ✅ 正确写法：预加载，一次查完

    select(User)
    .where(User.id == uid)

from sqlalchemy.ext.asyncio import async_engine_from_config

def do_run_migrations(connection):
    context.configure(connection=connection, target_metadata=target_metadata)
    with context.begin_transaction():
        context.run_migrations()

async def run_async_migrations():
    connectable = async_engine_from_config(config.get_section(config.config_ini_section))
    async with connectable.connect() as conn:
        await conn.run_sync(do_run_migrations)   # ⚠️ 迁移逻辑本身是同步的，用 run_sync 桥接
    await connectable.dispose()

⚠️ 迁移不要放在应用启动时自动执行。多副本部署下 N 个 Pod 会同时跑迁移，轻则锁等待，重则表结构被改坏。迁移应该是独立的一步（K8s 的 initContainer 或 CI 流水线里的单独 job）。

面试加分表述：异步数据库这块我会主动讲三个坑。第一是 expire_on_commit 必须关，否则 commit 之后读任何属性都会触发一次新的 IO，在 async 下还可能直接报 MissingGreenlet。第二是 懒加载在异步下完全不可用，所以我们在模型上统一配 lazy="raise"，把 N+1 从「线上慢查询」变成「开发期报错」。第三是连接池是乘法：pool_size × workers × 副本数，这个数必须小于 DB 的 max_connections，我们就是在一次扩容后把 DB 连接打满才补上这个计算的。

1. SSE 协议细节：一个空行决定成败 ​

SSE（Server-Sent Events）是建立在 HTTP 之上的单向文本流协议，报文格式极其简单，但有几个硬性要求，错一个前端就收不到数据。

text
HTTP/1.1 200 OK
Content-Type: text/event-stream; charset=utf-8    ← 必须是这个 MIME

SSE_HEADERS = {
    "Cache-Control": "no-cache",
    "Connection": "keep-alive",
    "X-Accel-Buffering": "no",      # Nginx 专用：关闭该响应的 proxy_buffering
}

def sse_pack(data: str, event: str | None = None, retry: int | None = None) -> str:
    chunk = ""
    if event:
        chunk += f"event: {event}\n"
    if retry:
        chunk += f"retry: {retry}\n"
    # ⚠️ data 内部不能有裸换行，多行要拆成多个 data: 行
    for line in data.split("\n"):
        chunk += f"data: {line}\n"
    return chunk + "\n"             # 结尾空行是事件分隔符

    async def gen():

        async for delta in llm.stream(body.messages):
            yield sse_pack(json.dumps({"delta": delta}, ensure_ascii=False))
        yield sse_pack("[DONE]", event="done")
    return StreamingResponse(gen(), media_type="text/event-stream", headers=SSE_HEADERS)

data:事件数据，可出现多行，前端收到时用 \n 拼接JSON 必须压成单行，ensure_ascii=False 保留中文
event:事件名用来区分 delta / done / error，前端分别监听
id:事件 ID浏览器断线重连时会带 Last-Event-ID 请求头，可用于续传
retry:重连间隔（毫秒）默认约 3 秒，想抑制频繁重连就调大

面试加分表述：SSE 的三个必备条件我会一次说清——text/event-stream 的 MIME、每个事件以空行结尾、全链路禁用缓冲。前两个是协议要求，第三个是部署要求：Nginx 默认 proxy_buffering on，会把流式响应攒满缓冲区才下发，表现就是「后端日志在逐字输出，前端却等了 30 秒一次性全出来」。

7. 并发控制：用 Semaphore 保护上游配额 ​

限流保护的是「自己」，并发控制保护的是「上游」。LLM 厂商按并发数和 TPM 计费限额，超了直接 429，必须在网关侧主动压住。

python
import asyncio
from contextlib import asynccontextmanager

class LLMGate:
    def __init__(self, max_concurrency: int, max_queue: int) -> None:
        self._sem = asyncio.Semaphore(max_concurrency)
        self._max_queue = max_queue
        self.waiting = 0            # 当前排队人数，暴露给监控

    @asynccontextmanager
    async def acquire(self, wait_timeout: float = 10.0):
        # ⚠️ 必须给排队设上限，否则请求无限堆积，内存和延迟一起崩
        if self.waiting >= self._max_queue:
            raise BizError("SERVICE_BUSY", "服务繁忙，请稍后重试", http_status=503)
        self.waiting += 1
        try:
            # 排队也要有超时：等 10 秒还轮不到，不如让用户早点重试
            async with asyncio.timeout(wait_timeout):
                await self._sem.acquire()
        except TimeoutError:
            raise BizError("QUEUE_TIMEOUT", "当前排队过长，请稍后重试", http_status=503)
        finally:
            self.waiting -= 1
        try:
            yield
        finally:
            self._sem.release()     # ⚠️ 必须在 finally 释放，异常路径也要还回令牌

对比项并发控制（Semaphore）限流（Rate Limit）
保护对象上游（模型配额、DB 连接数）自己（防刷、防单用户打满）
判断依据同时在途的请求数单位时间内的请求次数
超限行为排队等待，等不到才拒绝直接拒绝 429
作用域进程内（多 worker 要除以 worker 数）通常全局（Redis）
典型配置max_concurrency=20、max_queue=100单用户 20 次/分钟

⚠️ 多 worker 部署时，Semaphore 是进程内的。4 个 worker × max_concurrency=20 = 实际 80 并发打到上游。配置时必须按 worker 数折算，或者改用 Redis 实现分布式信号量。

面试加分表述：并发控制和限流经常被混为一谈，但它们保护的方向相反。我的做法是两层叠加：外层限流按用户维度防刷，内层信号量按全局维度护上游配额，中间留一个有界队列吸收瞬时毛刺。关键是队列必须有界并且带等待超时——无界队列只是把「立刻失败」变成「超慢成功」，用户体验更差。

  return {0, math.ceil(earliest[2] + window - now)}    -- 返回还要等几秒
end
redis.call('ZADD', key, now, member)
redis.call('EXPIRE', key, window + 1)                  -- ⚠️ 必须设过期，否则 key 永久堆积
return {1, 0}
"""

class RateLimiter:
    def __init__(self, redis: Redis, limit: int, window: int) -> None:
        self._script = redis.register_script(SLIDING_WINDOW_LUA)
        self.limit, self.window = limit, window

    async def check(self, scope: str) -> None:
        allowed, retry_after = await self._script(
            keys=[f"rl:{scope}"],
            args=[time.time(), self.window, self.limit, uuid.uuid4().hex],
        )
        if not allowed:
            raise HTTPException(
                status_code=429,
                detail=f"请求过于频繁，请 {retry_after} 秒后重试",
                headers={"Retry-After": str(retry_after)},   # 标准头，客户端可自动退避
            )

算法优点缺点适用
固定窗口实现最简单，一个 INCR + EXPIRE窗口边界可放过 2 倍流量粗粒度兜底
滑动窗口（ZSET）精确，任意窗口都不超限内存随请求数增长用户维度限流首选
令牌桶允许可控突发，平滑实现略复杂需要容忍突发的场景

面试加分表述：我们线上是三层限流——网关层按 IP 做粗粒度防刷，应用层按用户 ID 做滑动窗口，再叠一层按租户的 token 日配额。返回 429 时一定带 Retry-After 头，因为我们的 SDK 会读这个头做指数退避重试，不带的话客户端只会立刻重试，把问题放大。

# app/middleware.py —— 纯 ASGI 中间件，不破坏流式响应
import uuid
from app.context import trace_id_var

class TraceMiddleware:
    def __init__(self, app) -> None:
        self.app = app

    async def __call__(self, scope, receive, send):
        if scope["type"] != "http":
            return await self.app(scope, receive, send)

        headers = dict(scope["headers"])
        incoming = headers.get(b"x-trace-id", b"").decode()
        trace_id = incoming or uuid.uuid4().hex          # 上游传了就复用，没传就生成
        token = trace_id_var.set(trace_id)

        async def send_wrapper(message):
            if message["type"] == "http.response.start":
                message.setdefault("headers", []).append(
                    (b"x-trace-id", trace_id.encode())    # 回写响应头，前端报错时能带回来
                )
            await send(message)

        try:
            await self.app(scope, receive, send_wrapper)
        finally:
            trace_id_var.reset(token)                     # ⚠️ 必须 reset，防止上下文泄漏

11. Pydantic v2 高级用法：把校验逻辑收进模型 ​

python
from typing import Annotated, Literal, Self
from pydantic import BaseModel, Field, field_validator, model_validator, computed_field

# 用 Annotated 定义可复用的「语义类型」，一处定义处处使用
Temperature = Annotated[float, Field(ge=0, le=2, description="采样温度")]
NonEmptyStr = Annotated[str, Field(min_length=1, max_length=8000, strip_whitespace=True)]

class Message(BaseModel):
    role: Literal["system", "user", "assistant"]
    content: NonEmptyStr

class ChatIn(BaseModel):
    messages: list[Message] = Field(min_length=1, max_length=50)
    temperature: Temperature = 0.7
    max_tokens: int = Field(default=1024, ge=1, le=8192)
    stream: bool = False

    # 单字段校验：mode="before" 在类型转换之前跑，可以做清洗
    @field_validator("messages", mode="after")
    @classmethod
    def no_consecutive_user(cls, v: list[Message]) -> list[Message]:
        for prev, cur in zip(v, v[1:]):
            if prev.role == cur.role == "user":
                raise ValueError("不允许连续两条 user 消息")
        return v

    # 跨字段校验：必须用 model_validator，field_validator 看不到别的字段
    @model_validator(mode="after")
    def check_budget(self) -> Self:
        total = sum(len(m.content) for m in self.messages)
        if total + self.max_tokens * 4 > 120_000:
            raise ValueError("上下文与 max_tokens 之和超出模型窗口")
        return self

class ChatOut(BaseModel):
    answer: str
    prompt_tokens: int
    completion_tokens: int

    # 派生字段：自动进入序列化结果和 OpenAPI schema
    @computed_field
    @property
    def total_tokens(self) -> int:
        return self.prompt_tokens + self.completion_tokens

field_validator(mode="after")类型转换后已转好类型的该字段业务规则校验

Annotated 别名定义期—复用约束，避免复制粘贴

13. WebSocket：心跳、广播与断线重连 ​

python
from fastapi import WebSocket, WebSocketDisconnect, status

class ConnectionManager:
    def __init__(self) -> None:
        self.rooms: dict[str, set[WebSocket]] = {}

    async def connect(self, room: str, ws: WebSocket) -> None:
        await ws.accept()
        self.rooms.setdefault(room, set()).add(ws)

    def disconnect(self, room: str, ws: WebSocket) -> None:
        self.rooms.get(room, set()).discard(ws)

    async def broadcast(self, room: str, payload: dict) -> None:
        dead = []
        for ws in list(self.rooms.get(room, set())):
            try:
                await ws.send_json(payload)
            except Exception:
                dead.append(ws)        # ⚠️ 发送失败说明连接已死，必须剔除，否则集合无限膨胀
        for ws in dead:
            self.disconnect(room, ws)

manager = ConnectionManager()

@app.websocket("/ws/chat/{room}")
async def ws_chat(ws: WebSocket, room: str, token: str = Query(...)):
    # ⚠️ 鉴权要在 accept 之前做，失败就直接 close，别让非法连接进来
    user = await verify_ws_token(token)
    if user is None:
        return await ws.close(code=status.WS_1008_POLICY_VIOLATION)

    await manager.connect(room, ws)
    try:
        while True:
            # 用超时实现服务端心跳：30 秒没消息就主动 ping 一下探活
            try:
                async with asyncio.timeout(30):
                    data = await ws.receive_json()
            except TimeoutError:
                await ws.send_json({"type": "ping"})
                continue
            await manager.broadcast(room, {"type": "message", "from": user.id, **data})
    except WebSocketDisconnect:
        manager.disconnect(room, ws)    # 正常断开，不算异常
    except Exception:
        logger.exception("ws error room=%s user=%s", room, user.id)
        manager.disconnect(room, ws)
        await ws.close(code=status.WS_1011_INTERNAL_ERROR)
坑现象解法
连接集合只增不减内存持续上涨，广播越来越慢finally 里必须移除，广播失败也要剔除
没有心跳代理按空闲超时静默断连，双方都不知道服务端定时 ping，客户端定时 pong
多 worker 下广播只覆盖本进程用户 A 发消息，用户 B 收不到用 Redis Pub/Sub 做跨进程广播
accept() 之后才鉴权非法连接已经建立，浪费资源鉴权在 accept() 之前，失败直接 close
客户端不重连网络抖动一次就彻底掉线前端实现指数退避重连 + 断线期间消息补偿

⚠️ WebSocket 路由不走 HTTP 中间件（scope["type"] == "websocket"）。限流、trace_id、鉴权这些逻辑如果写在 HTTP 中间件里，WS 连接是完全绕过的，必须单独处理。

面试加分表述：WebSocket 的工程复杂度不在协议本身，而在「状态管理」。HTTP 是无状态的，连接集合、房间关系、未读消息全在内存里，一旦多实例部署就需要 Redis 做共享。所以我的原则是：能用 SSE 解决的单向推送就不上 WebSocket，真要上就从第一天起把跨进程广播设计进去。

⚠️ 需要「给某个接口打标记」时（比如「这个接口跳过限流」），正确做法是用 APIRoute 的 openapi_extra 或自定义 APIRoute 子类，而不是在中间件里硬编码路径列表——路径列表是典型的「改了代码忘了改配置」型故障源。

面试加分表述：我的判断口诀是「跨路由的横切关注点用中间件，和业务语义相关的前置逻辑用依赖」。鉴权、限流、参数预处理这些需要知道「这是哪个接口、谁在调」的逻辑，统统用依赖；CORS、trace_id、全局耗时统计这些与业务无关的，用中间件。还有一条硬约束：有流式接口的项目里，BaseHTTPMiddleware 一律不用。

17. 部署超时链路：任何一环都能掐断 SSE ​

浏览器 ──→ CDN/LB ──→ Nginx ──→ gunicorn ──→ uvicorn ──→ httpx ──→ 上游模型

⚠️ gunicorn 的 --timeout 对同步 worker 是「请求处理总时长」，超时会直接杀掉 worker 进程——所有在途的流式请求一起断。用 UvicornWorker 时它的语义变成心跳检测，但保守起见仍应调大。

⚠️ 心跳是对抗「空闲超时」的终极手段。每 15 秒发一个 : keepalive\n\n 注释行，让链路上每一跳都认为连接是活跃的，很多中间设备的 idle timeout 就不会触发。

面试加分表述：排查「本地好、线上断」这类流式问题，我的顺序是固定的：先看是不是整体缓冲（说明 proxy_buffering 没关），再看断在第几秒（60 秒就是某层默认 idle timeout，30 秒就看 gunicorn timeout）。断点时间往往能直接定位到是哪一层的默认值在作祟，比翻日志快得多。

18. 优雅退出：发版不该掐断在途的流式请求 ​

text
K8s 滚动更新时的正确时序：
  1) Pod 标记 Terminating，从 Service Endpoints 摘除
  2) preStop sleep 5s ──→ 等待 kube-proxy/ingress 规则同步完成
  3) 发送 SIGTERM
  4) uvicorn 停止接受新连接，等在途请求跑完
  5) lifespan 的 shutdown 阶段执行：关 httpx、关连接池、flush 日志
  6) 超过 terminationGracePeriodSeconds 才发 SIGKILL

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.http_client = build_client(get_settings())
    app.state.ready = True
    yield
    # ---- 以下是 shutdown 阶段 ----
    app.state.ready = False          # 先让 readiness 探针失败，停止接新流量
    await asyncio.sleep(1)           # 给探针一个周期去感知
    await app.state.http_client.aclose()
    await app.state.redis.aclose()
    logger.info("shutdown complete")

@app.get("/healthz/live")            # ⚠️ liveness 只判断进程活着，绝不做下游检查
async def live():
    return {"status": "ok"}

@app.get("/healthz/ready")           # readiness 判断是否该接流量
async def ready(request: Request):
    if not getattr(request.app.state, "ready", False):
        raise HTTPException(503, "shutting down")
    return {"status": "ready"}
坑后果解法
terminationGracePeriodSeconds 用默认 30 秒跑 60 秒的流式请求被 SIGKILL 掐断调成 120 秒以上
没有 preStop sleep发版期间偶发 502加 5 秒 sleep 等规则同步
liveness 探针里查数据库DB 抖一下，所有 Pod 被判定不健康一起重启liveness 只返回常量，依赖检查放 readiness
shutdown 里不关客户端连接泄漏，日志丢失lifespan 的 yield 之后统一清理
readiness 和 liveness 用同一个接口丧失「摘流量但不重启」的能力必须拆成两个端点

面试加分表述：优雅退出要同时满足两件事——「不再接新请求」和「已接的请求跑完」。前者靠 readiness 探针失败 + preStop 等待摘流量，后者靠足够长的 grace period。流式服务的特殊性在于单个请求可能持续一两分钟，默认 30 秒的 grace period 完全不够，这是我们踩过的真实线上问题：每次发版都有用户的回答被截断在一半。

        self.inner = GZipMiddleware(app, minimum_size=1024)
        self.app = app

题 1：FastAPI 和 Flask / Django 的本质区别是什么？ ​

精简口述答案（90 秒版）

区别在三层。第一层是协议：Flask 是 WSGI，一个请求占一个线程直到处理完；FastAPI 是 ASGI，基于事件循环，一个线程能并发处理成百上千个等待 IO 的请求。这决定了流式输出和 WebSocket 在 Flask 上要么做不了、要么很别扭。第二层是类型系统：FastAPI 把 Python 类型注解当成运行时契约，Pydantic 负责校验和序列化，OpenAPI 文档是自动产物；Flask 需要额外接 marshmallow 之类的库，还得手写文档。第三层是依赖注入：Depends 提供了请求级的资源管理和可覆盖的依赖容器，测试时能整体替换外部依赖。至于 Django，它是全栈框架，自带 ORM、Admin、模板，适合内容型业务；FastAPI 是纯 API 框架，更适合做前后端分离的接口服务和 AI 网关。

连环追问链

追问答题要点
ASGI 比 WSGI 快在哪？不是单请求更快，而是并发模型不同。WSGI 下线程等 IO 时被占着，ASGI 下协程等 IO 时让出控制权，所以 IO 密集场景吞吐差一个量级；纯 CPU 任务两者没区别
Flask 2.x 支持 async def 了，还有差别吗？有。Flask 的 async 是在 WSGI 之上为每个请求起一个临时事件循环跑完再回到同步模型，拿不到真正的全局事件循环，流式和 WebSocket 依然受限
什么情况下你会选 Django？需要 Admin 后台、成熟 ORM、模板渲染，团队熟悉 Django 生态，且业务是传统 CRUD + 内容管理
FastAPI 有什么劣势？生态比 Django 薄（没有官方 ORM、Admin）；异步编程心智负担高，一个同步阻塞调用就能毁掉性能；异步 ORM 成熟度不如同步版本
老 Flask 项目要迁吗？不整体迁。只把需要流式输出、高 IO 并发的新接口用 FastAPI 做成独立服务，通过网关分流，避免大重构风险
FastAPI 和 Starlette 是什么关系？Starlette 提供路由、中间件、响应、WebSocket 等 ASGI 基础设施，FastAPI 在它之上加了 Pydantic 校验、依赖注入和 OpenAPI 生成

✅ 项目关联话术

我们的 AI 网关最初是跟着老项目用 Flask 写的，上流式输出时发现两个硬问题：一是 BaseHTTPMiddleware 式的 WSGI 中间件会把响应攒完再发，流式体验完全出不来；二是单个 LLM 请求要等 30 秒以上，WSGI 下每个请求占一个线程，几十并发就把线程池打满了。迁到 FastAPI 之后，单进程轻松支撑数百条并发 SSE 连接，内存占用反而下降了，因为不再需要开大量线程。

题 2：Pydantic 在 FastAPI 里解决什么问题？v1 和 v2 有什么差别？ ​

精简口述答案（90 秒版）

Pydantic 解决的是「HTTP 世界的无类型数据」到「Python 世界的有类型对象」之间的转换和校验。它一次性承担四个职责：类型转换（query 里的 "30" 自动变成 int）、约束校验（ge、max_length、枚举）、出参序列化（response_model 过滤字段）、文档生成（模型直接编译成 OpenAPI schema）。所以接口函数体里不需要再写任何 if not xxx: raise，所有结构性约束都在模型上声明。v2 最大的变化是核心校验器用 Rust 重写成 pydantic-core，性能有数倍提升。API 层面主要是：@validator 改成 @field_validator 并且必须加 @classmethod、@root_validator 改成 @model_validator、class Config 改成 model_config 字典、.dict() / .json() 改成 .model_dump() / .model_dump_json()、parse_obj 改成 model_validate，约束参数从 conint(ge=0) 风格统一到 Annotated[int, Field(ge=0)]。

连环追问链

追问答题要点
field_validator 和 model_validator 怎么选？单字段校验用前者；需要看到其他字段（跨字段一致性）必须用后者，因为 field_validator 拿不到兄弟字段
mode="before" 和 mode="after" 的区别？before 在类型转换前，拿到原始值，适合做清洗和兼容老格式；after 在转换后，拿到已定型的值，适合做业务规则校验
校验失败为什么是 422 不是 400？400 表示请求格式本身错误（比如 JSON 语法错），422 表示语法正确但语义不符合约束。FastAPI 遵循这个区分，也可以自己覆盖成 400
怎么自定义校验错误的响应格式？注册 @app.exception_handler(RequestValidationError)，从 exc.errors() 里取出 loc、msg、type，拼成统一响应体
response_model 和返回类型注解哪个优先？显式的 response_model 优先。只有没写它时，FastAPI 才用返回值注解当出参模型
v2 有什么坑？extra 默认是 ignore（多余字段静默丢弃），想严格就设 forbid；严格模式下字符串不再自动转数字，老代码可能依赖这个隐式转换

✅ 项目关联话术

我们迁 v2 的直接动机是性能：网关的入参是一个带几十条消息的嵌套列表，v1 的校验在 P99 上能占到几十毫秒。迁完之后校验耗时基本从火焰图里消失了。迁移过程中最大的收获反而是意外的——extra="forbid" 一开，立刻暴露出好几个前端传了拼写错误字段、后端一直在用默认值的隐藏 bug，这些字段在 v1 的 ignore 模式下被静默丢弃了快半年。

题 3：Depends 的原理是什么？yield 依赖的清理代码什么时候执行？ ​

精简口述答案（90 秒版）

Depends 接受任何可调用对象。FastAPI 在启动时解析依赖函数的签名，递归构建出一棵依赖树，并把叶子节点的参数（query、path、header、body）一起合并进接口的 OpenAPI schema。请求进来时按拓扑序求解这棵树，同一个请求内相同依赖只执行一次（按「函数对象 + 参数」做 key 缓存），想关掉就用 Depends(f, use_cache=False)。yield 依赖把函数变成请求级的上下文管理器：yield 之前的代码在进入接口前执行、yield 的值注入参数、yield 之后的代码在响应发送完成之后执行。注意这个时机——它晚于 return、也晚于异常处理器，所以清理代码里 raise 已经无法改变响应了，只能记日志。多个 yield 依赖的清理顺序是逆序的，像栈一样后进先出。

连环追问链

追问答题要点
为什么清理代码在响应发送之后？因为流式响应需要在生成期间持续持有资源（比如 DB 连接），如果 return 时就释放，生成器后续读数据就会拿到已关闭的连接
依赖里抛异常会怎样？走正常的异常处理流程，接口函数根本不会执行。这是实现鉴权、限流的标准方式
怎么做带参数的依赖？用「依赖工厂」：外层普通函数接参数，内层返回真正的依赖函数，形成闭包，比如 Depends(rate_limit(20, 60))
dependencies=[...] 和签名里的 Depends 有什么区别？前者只执行、不要返回值，适合鉴权限流这类副作用型依赖；后者的返回值会注入参数，适合取当前用户、取连接
依赖缓存的 key 是什么？依赖的可调用对象加上它自身的参数值。所以同一个请求里两处注入 current_user 只会查一次库
类作为依赖怎么用？Depends(MyDep) 时 FastAPI 解析 __init__ 签名；如果类实现了 __call__，则 Depends(instance) 解析 __call__ 签名，适合做可配置的依赖实例

✅ 项目关联话术

我们踩过一个很典型的坑：最早用 yield 依赖提供 DB 会话，接口里起了 asyncio.create_task 做异步落库，结果任务跑到一半会话就被关了，报「连接已关闭」。原因就是 yield 之后的清理在响应发完就执行了，而那个后台任务还活着。后来改成在后台任务内部自己开一个独立会话——核心认知是：请求级资源的生命周期不能超出请求本身，想跨出去就必须自己管。

题 4：接口写 def 还是 async def？写错会怎样？ ​

精简口述答案（90 秒版）

判断标准只有一条：函数体里的 IO 是不是 await 的。如果用的是 httpx.AsyncClient、异步 ORM、异步 Redis，就写 async def；如果用的是 requests、同步 ORM、或者某个没有异步版本的 SDK，就写 def——FastAPI 会自动把 def 接口丢到线程池执行，不会阻塞事件循环。最危险的组合是 async def 里调同步阻塞代码：此时没有任何人帮你切换，整个事件循环被这一个请求卡住，所有其他请求一起排队，并发度直接退化到 1。反过来，在 def 接口里调异步代码也不行，你拿到的是一个没有被 await 的协程对象。如果确实需要在 async def 里调用阻塞函数，用 await asyncio.to_thread(...) 显式丢到线程池。

连环追问链

追问答题要点
def 接口的线程池有多大？anyio 默认 40 个线程，全进程共享。同步接口多了会排队，可以通过 current_default_thread_limiter().total_tokens 调整
为什么「全异步」反而可能比混用慢？如果异步接口里混进了阻塞调用，它会卡住整个循环，比老老实实写 def 用线程池更糟
怎么发现代码里有这个问题？现象是 CPU 很低但 QPS 上不去、延迟呈阶梯式恶化；工具上用 ruff 的 ASYNC 规则族在 CI 拦截，或开 asyncio debug 模式看慢回调告警
CPU 密集任务怎么办？线程池解决不了（GIL），要用 ProcessPoolExecutor 配 run_in_executor，或者彻底拆成独立的计算服务
依赖函数也分 def / async def 吗？是的，规则完全一样。同步依赖同样走线程池，一个慢的同步依赖会占着线程池名额
time.sleep 和 asyncio.sleep 在 async def 里的区别？time.sleep 阻塞整个事件循环；asyncio.sleep 让出控制权。这是最小的复现案例，面试常被要求现场说清楚

✅ 项目关联话术

我们线上出过一次很有代表性的事故：有同学在一个 async def 接口里用了同步的 Redis 客户端查限流计数。功能完全正常，测试全绿，灰度也没问题，一上全量 QPS 就死活上不去，但 CPU 只有 10%。排查了半天才定位到是事件循环被阻塞。修完之后我们做了两件事：换成 redis.asyncio，以及在 CI 里开了 ruff 的 ASYNC 规则，把这类问题拦在合并之前。

题 5：SSE 的原理是什么？为什么 LLM 流式输出选它而不是 WebSocket？ ​

精简口述答案（90 秒版）

SSE 本质就是一个不结束的 HTTP 响应：服务端返回 Content-Type: text/event-stream，然后用 chunked 编码持续往下写文本，每个事件由 data: 行组成、以一个空行作为结束标记。浏览器端用 EventSource 或 fetch 流式读取，边收边渲染。它还支持 event: 指定事件名、id: 配合断线重连的 Last-Event-ID 做续传、retry: 指定重连间隔，以及用 : 开头的注释行做心跳。

选 SSE 而不是 WebSocket，核心理由是「LLM 对话只需要单向推送，而 SSE 能完整复用现有 HTTP 基础设施」——鉴权中间件、限流、access log、链路追踪、灰度路由全都不用改一行。WebSocket 是独立协议，需要 101 Upgrade，网关、监控、鉴权都得重建一套，为一个用不到的双向能力付这个成本不划算。另外 SSE 的断线自动重连是浏览器内置的，WebSocket 要自己写。

连环追问链

追问答题要点
为什么线上会出现「前端等很久一次性收到全部」？链路上有缓冲。常见两处：BaseHTTPMiddleware 会收集完整响应体、Nginx 的 proxy_buffering 默认开启。解法是换纯 ASGI 中间件 + 响应头加 X-Accel-Buffering: no
为什么要发心跳？对抗链路上各级代理的空闲超时。每 15 秒发一个 : keepalive\n\n 注释行，前端会忽略但连接保持活跃
为什么要约定 [DONE] 标记？流式响应无法用状态码表达「正常结束」。有了显式结束标记，前端才能区分「生成完了」和「连接意外断了」
浏览器 EventSource 有什么限制？只支持 GET、不能自定义请求头。要 POST 传 body 或带 Authorization，必须改用 fetch + ReadableStream 自己解析
HTTP/1.1 下 SSE 有什么坑？同域名并发连接数约 6，每条 SSE 占一条，开多了会卡住其他请求。上 HTTP/2 多路复用可解
中途出错怎么通知前端？首字节已发出，状态码改不了。必须在流里推一条 event: error 的消息，前端在流内部处理

✅ 项目关联话术

我们的流式接口上线时踩了完整的一套坑：本地跑得很好，上测试环境变成「等 20 秒一次性全出来」，是 Nginx 的 proxy_buffering；关掉之后又发现偶发在 60 秒断开，是云 LB 的 idle timeout；加了 15 秒心跳解决。最后定下来的协议是三件套：event: delta 推分片、event: error 推流内错误、event: done 加 data: [DONE] 标记结束。这个约定让前端能明确区分三种状态，异常重试的逻辑一下就清晰了。

题 6：流式接口中用户关掉页面，后端怎么感知并及时回收资源？ ​

精简口述答案（90 秒版）

两条互补的机制。一是主动轮询：在生成器的每次循环里调 await request.is_disconnected()，它读的是 ASGI 的 http.disconnect 事件，发现断连就 break。二是被动捕获取消：ASGI 服务器检测到连接关闭后会 cancel 掉这个响应任务，表现为 asyncio.CancelledError 或 anyio 的取消异常，要单独捕获、记日志、然后必须重新 raise，不能吞掉，否则任务树的取消状态会错乱。

真正省钱的那一步是在 finally 里调上游流的 aclose()，把到模型厂商的那条连接也关掉——否则后端虽然不往前端写了，却还在继续从模型拉数据，token 照烧。另外已经消耗的 token 仍然要入账计费，否则会被「发起请求立刻断开」反复白嫖。

连环追问链

追问答题要点
is_disconnected() 有什么局限？它只在你调用的那一刻检查。如果模型卡住十几秒不吐字，循环不转，感知就会滞后。所以需要配合取消异常捕获
为什么必须重新抛出 CancelledError？它是协作式取消的信号。吞掉它意味着告诉上层「我不打算被取消」，会导致 shutdown 时任务挂住、超时机制失效
finally 里能不能再 yield？不能。连接可能已经关了，写入会抛新异常并覆盖原始的取消语义。finally 只做资源释放和日志
怎么验证资源真的回收了？压测时主动断开一批连接，观察在途连接数 Gauge 是否回落、上游的并发计数是否下降、连接池是否有泄漏
「停止生成」按钮怎么实现？前端 AbortController.abort() 直接断开 fetch 连接，后端通过上述机制感知即可，不需要额外的取消接口
取消率应该关注多少？我们把它当体验指标：持续高于 20% 基本说明 TTFT 太慢，用户等不下去就走了

✅ 项目关联话术

我们上线后统计发现「生成中途离开」的比例接近 15%，而最初的实现完全没有断连检测，这些请求全都白跑完整个回答。补上 is_disconnected 检查加上游 aclose() 之后，这部分成本直接省掉了。有一个反直觉的设计决定值得一提：已产生的 token 仍然计费。最初我们想「用户都走了就不收了」，后来意识到这会被滥用——只要不停发起请求再立刻断开就能白嫖算力。

题 7：on_event 和 lifespan 有什么区别？启动时应该初始化什么？ ​

精简口述答案（90 秒版）

@app.on_event("startup"/"shutdown") 是旧 API，已经被官方标记废弃。lifespan 用一个异步上下文管理器把启动和关闭写在同一个函数里：yield 之前是启动、yield 之后是关闭。好处有三个：启动和清理的代码物理相邻，不容易出现「创建了没关闭」；可以用局部变量在两个阶段之间传递状态，不需要全局变量；异常语义更清晰，启动失败直接让进程起不来。

启动阶段该做的是「创建需要复用的长生命周期资源」——httpx 客户端、DB 连接池、Redis 连接池、加载配置和模型元信息、设置线程池大小、注册监控。关闭阶段做对称的清理：先把 readiness 标记置成不可用停止接新流量，再依次关客户端和连接池，最后 flush 日志。关键是：异步客户端必须在 lifespan 里创建，不能在模块导入时创建，否则会绑定到错误的事件循环，报 Event loop is closed。

连环追问链

追问答题要点
为什么 TestClient 必须用 with？lifespan 只在进入上下文时触发。不用 with 的话 app.state.http_client 根本不存在，接口会报 AttributeError
启动阶段不该做什么？不该做耗时很久的操作（拖慢发布、探针超时），不该做「失败了也要继续」的操作——那应该是懒加载
启动时要不要检查下游健康？轻量探测可以，但不要让下游不可用阻塞启动。否则 Redis 抖一下，全部 Pod 都起不来，故障被放大
多 worker 下 lifespan 执行几次？每个 worker 进程各执行一次。所以「只该做一次」的操作（比如 DB migration）不能放这里，要放独立的 init job
lifespan 里能访问 app 吗？能，它的入参就是 app，常见做法是把资源挂到 app.state 上
关闭阶段的顺序有讲究吗？有。先停止接流量（readiness 置 false），等一个探针周期，再关客户端和连接池，最后 flush 日志

✅ 项目关联话术

我们最早是在模块顶层创建 httpx.AsyncClient 的，本地单进程跑完全正常，上 gunicorn 多 worker 之后开始偶发 Event loop is closed。原因是客户端在导入时就绑定了一个事件循环，而 worker fork 之后实际运行在另一个循环上。挪到 lifespan 里创建之后问题彻底消失。还有一个连带的坑：测试用 TestClient 时没加 with，app.state.http_client 不存在，报的是 AttributeError，完全看不出和 lifespan 有关系。

题 8：中间件和依赖怎么选？为什么说中间件会破坏流式响应？ ​

精简口述答案（90 秒版）

判断口诀是「跨路由的横切关注点用中间件，和业务语义相关的前置逻辑用依赖」。中间件在路由匹配之前执行，拿不到路径参数、拿不到已校验的 Body、也进不了 OpenAPI 文档，适合 CORS、trace_id 注入、全局耗时统计这类与业务无关的逻辑。依赖能精确挂到单接口或整组路由，返回值可以直接注入参数，鉴权方案还会自动出现在 Swagger 的 Authorize 按钮里，所以鉴权、限流、资源获取都该用依赖。

至于「破坏流式」说的是 Starlette 的 BaseHTTPMiddleware：它的 dispatch 方法拿到的是一个完整的 Response 对象，实现上会把下游响应体收集完再往外发，StreamingResponse 的逐片输出就被压成了一次性返回。解法是改用纯 ASGI 中间件——直接操作 scope、receive、send 三个原语，send 每收到一个 http.response.body 消息就立刻转发，不做任何聚合。

连环追问链

追问答题要点
纯 ASGI 中间件怎么写？实现 __call__(self, scope, receive, send)，用 send_wrapper 包一层拦截 http.response.start 加响应头，body 消息原样透传
中间件的执行顺序？洋葱模型。add_middleware 后注册的在更外层，所以 CORS 要最后注册才能包住异常响应
中间件能拿到路由信息吗？不能。scope["route"] 在中间件执行时还没填充，只能拿到原始 path。靠 path 字符串匹配做鉴权是典型的故障源
为什么用中间件做鉴权不好？只能按路径前缀判断，新增接口忘记加白名单就会裸奔；而且不会出现在 API 文档里，调用方不知道要带什么凭证

题 9：FastAPI 里鉴权和限流怎么做？流式接口有什么特殊处理？ ​

精简口述答案（90 秒版）

鉴权用依赖实现。OAuth2PasswordBearer 负责从 Authorization: Bearer 头提取 token 并把安全方案写进 OpenAPI，然后在依赖里解 JWT、查用户、校验状态。权限校验用「依赖工厂」require_roles("admin") 生成，挂到 router 的 dependencies 上整组生效。两个细节：解 JWT 必须显式指定 algorithms 白名单，否则攻击者把 alg 改成 none 就能伪造身份；未登录返回 401 且必须带 WWW-Authenticate 头，已登录但权限不足返回 403。

限流用 Redis 滑动窗口，ZSET 存请求时间戳，判断逻辑必须写成 Lua 脚本保证原子性——先 ZCARD 再 ZADD 分两次往返，高并发下必然超发。拒绝时返回 429 并带 Retry-After 头，客户端 SDK 读这个头做指数退避。

流式接口的特殊处理是鉴权凭证的位置：浏览器原生 EventSource 不能自定义请求头，很多人就把 token 塞进 query string，结果被 access log、Referer、代理日志全部记录。正确做法是前端改用 fetch 流式读取（可以带头），或者签发一个只能用一次、几十秒过期的短 token。

连环追问链

追问答题要点
JWT 怎么实现「立刻踢人」？JWT 无状态，天生做不到。折中方案是 access token 只给 15 分钟，配 refresh token 续期，再在 Redis 维护一个很小的黑名单处理强制下线
固定窗口限流有什么问题？窗口边界可以放过 2 倍流量：59 秒打满 + 61 秒再打满，2 秒内实际通过了两个窗口的额度
限流 key 应该用什么维度？分层：网关按 IP 防粗粒度刷量，应用按用户 ID 防单用户打满，再叠一层按租户的配额。LLM 场景还要按 token 量而不只是请求数
多 worker 下内存限流为什么不行？计数器在进程内，4 个 worker 就是 4 份独立计数，实际放过 4 倍流量。共享状态必须用 Redis
限流和并发控制有什么区别？限流保护自己（单位时间请求次数，超了直接拒），并发控制保护上游（同时在途数，超了排队等待）。两者方向相反，通常叠加使用
为什么无权访问要返回 404 而不是 403？403 等于确认「这个 ID 确实存在」，攻击者可以靠它枚举有效 ID。统一返回 404 能消除这个信息泄露面

✅ 项目关联话术

我们的限流是三层叠加：Nginx 按 IP 做粗粒度防刷，应用层用 Redis 滑动窗口按用户 ID 限 20 次/分钟，再按租户做 token 日配额。最早用的是固定窗口的 INCR，上线后发现有脚本专门卡在整分钟边界刷量，换成 ZSET 滑动窗口才彻底堵住。另外 429 一定要带 Retry-After——我们自己的 SDK 会读它做退避，不带的话客户端只会立刻重试，把问题放大成雪崩。

题 10：FastAPI 怎么部署？workers 数量怎么定？和 GIL 什么关系？ ​

精简口述答案（90 秒版）

生产形态是 uvicorn --workers N，或者 gunicorn -k uvicorn.workers.UvicornWorker -w N 让 gunicorn 做进程管理，前面再挂 Nginx 做 TLS 卸载和静态资源。两个维度要分清：进程数解决 CPU 并行（绕开 GIL），协程解决 IO 并发（单进程内上千连接）。

workers 的取值看瓶颈在哪。纯 IO 密集（调 LLM、查 DB）给 2 到 4 个就够，再往上只是多占内存，并发靠协程扛；有 CPU 密集计算才按核数配。如果跑在 K8s 里，我更推荐 --workers 1 配副本数扩容——让 HPA 按 Pod 粒度伸缩，CPU 指标更准确，滚动更新也更可控。

GIL 限制的是「同一进程内同一时刻只有一个线程执行 Python 字节码」，但它不影响等待 IO 的协程——等待时根本不需要执行字节码。所以 IO 密集服务靠 async 就能把并发拉上去。另外多 worker 下进程内状态全部失效：内存缓存、内存限流计数器、WebSocket 连接集合，4 个 worker 就是 4 份，需要共享就得上 Redis。

连环追问链

追问答题要点
--reload 能上生产吗？绝对不行。它会起文件监听进程、内存翻倍，任何文件系统抖动都可能触发重启，直接掐断在途的流式请求
gunicorn 的 --timeout 要注意什么？默认 30 秒。对同步 worker 它是请求总时长，超时会直接杀掉 worker 进程，所有在途流式请求一起断。流式服务必须调大
为什么 K8s 里推荐单 worker？容器的 CPU limit 通常不是整核，多 worker 会互相争抢；而且 HPA 按 Pod 的 CPU 使用率伸缩，单 worker 的指标才有意义
SSE 场景怎么估容量？按「峰值并发连接数 ÷ 单进程可承载连接数」算，还要检查文件描述符上限（ulimit -n）和 LB 的连接数配额
uvloop 要手动开吗？Linux 下 uvicorn 检测到已安装会自动启用，不需要手动配置。Windows 不支持
--max-requests 有什么用？让 worker 处理一定请求数后主动重启，用来兜底内存泄漏。配 --max-requests-jitter 避免所有 worker 同时重启

✅ 项目关联话术

我们一开始在 K8s 里按「CPU 核数」配了 4 个 worker，结果容器 CPU limit 只给了 2 核，4 个进程互相争抢，P99 反而比单 worker 更差；而且 HPA 看到的 CPU 使用率失真，扩容判断总是慢半拍。改成单 worker + 副本数扩容之后，指标清晰了，滚动更新也更平滑。另外 gunicorn 的 --timeout 30 这个默认值坑过我们一次：流式请求跑到 30 秒整被杀，日志里只有一行 worker timeout，排查了很久。

题 11：FastAPI 项目怎么测试？流式接口怎么测？ ​

精简口述答案（90 秒版）

核心工具是 TestClient（基于 httpx，直接走 ASGI 不经网络）和 dependency_overrides。后者是 FastAPI 可测性的关键：因为所有外部依赖都通过 Depends 声明进来，测试时在依赖容器层整体替换掉就行，不需要 monkeypatch 任何模块级变量。写法是 app.dependency_overrides[get_llm_client] = lambda: FakeLLM(...)，用完必须 clear()，否则跨用例污染。

两个硬性注意点：TestClient 必须用 with 才会触发 lifespan，不然 app.state 上的资源根本不存在；需要测真异步行为（并发、取消、超时）时改用 httpx.AsyncClient + ASGITransport 配 pytest-asyncio。

测 SSE 用 client.stream("POST", ...)，然后 iter_lines() 逐行解析，断言三件事：Content-Type 是 text/event-stream、分片内容正确、最后一条是 [DONE]。其中「分片是逐条到达的」这条断言特别有价值，它能直接拦住「新加了个中间件把流缓冲掉了」这类回归。

连环追问链

追问答题要点
为什么不用 monkeypatch 替换？monkeypatch 要知道被 patch 对象的导入路径，改个 import 方式就失效；dependency_overrides 作用在容器层，与模块组织无关
怎么测限流和并发控制？用 ASGITransport + asyncio.gather 真并发打一批请求，断言有部分被拒成 429/503，而不是全部超慢成功
要不要 mock Pydantic 模型？不要。校验逻辑本身就是业务约束的一部分，mock 掉等于把校验测试全废了。应该传真实 dict 走完整校验流程
想测真实的上游响应解析怎么办？用 respx 或 httpx.MockTransport 拦截 HTTP 层，这样业务代码里的解析、错误处理逻辑都会被真实执行到

我们的测试套件里有一条看起来很奇怪的用例：断言 SSE 的分片是多条而不是一条。起因就是前面说的中间件缓冲事故——功能断言全都能过，因为内容最终是对的，只有「是不是流式」这件事测不出来。补上这条用例之后，任何引入缓冲的改动在 CI 阶段就会被拦住。另外 TestClient 不加 with 导致 lifespan 不执行这个坑，我们是写进新人文档的，因为报错信息（AttributeError: state has no attribute http_client）完全看不出根因。

题 12：让你设计一个 LLM 网关接口，你会怎么做？ ​

精简口述答案（90 秒版）

我会分六层说。入参层：Pydantic 模型做结构校验，限制消息条数、单条长度、max_tokens 上限，并预估 token 总量防止超窗口。鉴权与配额层：Depends 做 JWT 校验，叠加 Redis 滑动窗口限流（用户维度）和 token 日配额（租户维度）。并发保护层：全局 Semaphore 压住打到上游的并发数，配一个有界队列和排队超时，满了返回 503 而不是无限堆积。调用层：复用在 lifespan 里创建的 httpx.AsyncClient，四段超时分别配置，read 超时按分片间隔设 60 秒，业务层再加一个总时长上限兜底；失败按状态码区分处理——429 退避重试、5xx 切备用模型、4xx 直接返回不重试。输出层：非流式走 response_model 过滤字段；流式用 StreamingResponse 推 SSE，带心跳、[DONE] 标记、流内 event: error、断连检测和上游 aclose()。可观测层：trace_id 全链路透传并回写响应头，指标盯 TTFT、在途连接数、取消率、token 消耗和按上游状态码拆分的错误率。

连环追问链

追问答题要点
上游超时了怎么办？分阶段：首字节前超时可以安全重试（幂等）；已经开始输出后不能重试（会重复内容），只能推 event: error 让用户自己决定
怎么做多模型降级？配置一个优先级列表，主模型连续失败触发熔断后自动切备用。关键是降级要告知用户用了哪个模型，避免质量差异引发投诉
相同问题能不能缓存？能，key 用「模型 + 参数 + 消息内容的 hash」。但要注意带随机性的高 temperature 请求缓存意义不大，而且要尊重用户的「重新生成」意图
怎么防成本型攻击？这是 LLM 接口特有的风险：攻击者不需要打垮服务，持续刷长文生成就能让账单爆掉。必须有 token 配额限流，不只是请求数限流
怎么支持「重新生成」和「继续」？会话状态存 Redis（带 TTL），前端传 session_id + message_id，后端按 ID 回溯上下文重新发起，而不是让前端把全部历史再传一遍
整体可用性怎么保障？熔断（上游连续失败快速失败）+ 降级（切备用模型）+ 限流（保护自己）+ 超时（防止堆积）+ 优雅退出（发版不断流），这五件事缺一不可

✅ 项目关联话术

我们的网关现在日调用量在百万级，最终沉淀下来的核心设计就是「三道闸门 + 两个标记」。三道闸门是：入参校验拦住异常请求、限流配额拦住滥用、并发信号量护住上游配额。两个标记是：trace_id 保证任何一次调用都能追查，以及流式协议里显式的 [DONE] / event: error 让前端能准确区分三种结束状态。最贵的两次教训都在流式上——中间件把流缓冲掉，以及发版时 grace period 太短把在途回答截断，这两个问题现在都有对应的 CI 用例和部署检查项在守着。

题 13：FastAPI 里异步数据库怎么用？连接池参数怎么定？ ​

精简口述答案（90 秒版）

三件事必须同时做对。驱动：必须是异步驱动（asyncpg / aiomysql），用 create_async_engine + async_sessionmaker，并且 expire_on_commit=False，否则 commit 之后读任何属性都会触发新 IO。会话生命周期：会话是请求级的，用 yield 依赖提供，正常结束 commit、异常 rollback、退出时自动归还连接；绝不能做成全局单例，AsyncSession 不是线程/任务安全的。连接池：pool_size + max_overflow 决定单进程上限，但真正要算的是乘法——(pool_size + max_overflow) × worker 数 × 副本数 必须小于 DB 的 max_connections，再配 pool_pre_ping=True 和小于服务端 idle timeout 的 pool_recycle 防死连接。另外异步下懒加载完全不可用，关联数据必须 selectinload / joinedload 预加载，我们还会在模型上配 lazy="raise"，把 N+1 从线上慢查询变成开发期报错。

连环追问链

追问答题要点
为什么 expire_on_commit 要设 False？默认 True 时 commit 会让所有 ORM 对象过期，下次访问属性要重新查库。同步下只是多一次查询，异步下还可能直接抛 MissingGreenlet，因为属性访问是同步调用，没法 await
事务边界放在哪一层？简单 CRUD 放依赖里统一 commit；接口里要调 LLM / 第三方时必须拆：先落 pending 记录并提交，再做 IO，最后开新事务更新状态
为什么不能把 IO 包在事务里？长事务会长期占用连接。一次生成 30秒，pool_size=10 时 10 个并发就把池子占满，第 11 个请求在 pool_timeout 上超时，表现为「DB 没压力但接口全挂」
QueuePool limit reached 怎么排查？先确认是「连接泄漏」还是「真不够用」：查是否有绕过 yield 依赖手动创建的会话、是否有长事务；确实不够再调大，但要重新算那个乘法
连接数算出来超过 DB 上限怎么办？优先调小单进程 pool_size 并减少 worker（IO 型服务靠协程而不是进程扛并发）；规模再大就在 DB 前加 PgBouncer 做连接复用
迁移脚本放在哪执行？独立一步执行（CI job 或 initContainer），绝不能放在应用启动时，多副本会同时跑迁移导致锁等待甚至结构损坏
后台任务里能用请求的会话吗？不能。yield 依赖的清理在响应发出后就执行了，后台任务拿到的是已关闭的连接，必须自己开独立会话

✅ 项目关联话术

我们在一次扩容后踩过连接池的坑：副本从 2 扩到 6，DB 立刻报 too many connections，但 CPU 和慢查询都很正常。原因就是没算那个乘法——(10+5) × 4 workers × 6 副本 = 360，而 PG 的 max_connections 是 100。修复分两步：先把 worker 降到 1、靠副本数扩容（容器里本来就该这么配），再把 pool_size 调到 8，总数压到 54。后来我们把这个计算写进了上线检查项。另一个长期收益大的改动是在所有模型关系上配 lazy="raise"，上线前一次性暴露出七八处忘了预加载的 N+1，这些在之前都是靠线上慢查询日志才能发现的。

from pydantic import BaseModel, Field, field_validator, model_validator, computed_field

Content = Annotated[str, Field(min_length=1, max_length=8000)]

class Message(BaseModel):
    role: Literal["system", "user", "assistant"]
    content: Content

class ChatIn(BaseModel):
    model_config = {"extra": "forbid"}          # 多余字段直接报错，暴露前端拼写问题

    messages: list[Message] = Field(min_length=1, max_length=50)
    model: Literal["gpt-4o-mini", "gpt-4o", "qwen-max"] = "gpt-4o-mini"
    temperature: float = Field(default=0.7, ge=0, le=2)
    max_tokens: int = Field(default=1024, ge=1, le=8192)

    @field_validator("messages", mode="after")
    @classmethod
    def last_must_be_user(cls, v: list[Message]) -> list[Message]:
        if v[-1].role != "user":
            raise ValueError("最后一条消息必须是 user")
        return v

    @model_validator(mode="after")
    def check_context_budget(self) -> Self:
        # 粗略按 1 token ≈ 2 个中文字符预估，防止打到上游才报超窗口
        est = sum(len(m.content) for m in self.messages) // 2 + self.max_tokens
        if est > 100_000:
            raise ValueError(f"预估 token 约 {est}，超出模型上下文窗口")
        return self

    completion_tokens: int

    @property

    def __init__(self, client: httpx.AsyncClient) -> None:
        self.client = client

    async def complete(self, **payload) -> "LLMResult":
        try:
            resp = await self.client.post("/chat/completions", json=payload)
        except httpx.ConnectError as exc:
            raise BizError("UPSTREAM_UNREACHABLE", "模型服务不可达", 502) from exc
        except httpx.ReadTimeout as exc:
            raise BizError("UPSTREAM_TIMEOUT", "模型响应超时，请重试", 504) from exc

        if resp.status_code == 429:
            raise BizError("UPSTREAM_RATE_LIMITED", "模型服务繁忙，请稍后重试", 429)
        if resp.status_code >= 500:
            raise BizError("UPSTREAM_ERROR", "模型服务异常", 502)

            logger.error("upstream 4xx body=%s", resp.text[:500])
            raise BizError("BAD_UPSTREAM_REQUEST", "请求参数不被模型接受", 400)

        data = resp.json()
        usage = data["usage"]
        return LLMResult(
            text=data["choices"][0]["message"]["content"],
            prompt_tokens=usage["prompt_tokens"],
            completion_tokens=usage["completion_tokens"],

# app/sse.py —— SSE 打包工具，统一出口避免格式错误
import json

SSE_HEADERS = {
    "Cache-Control": "no-cache",
    "Connection": "keep-alive",
    "X-Accel-Buffering": "no",          # 关键：让 Nginx 不缓冲这个响应
}

def sse_pack(data: str, event: str | None = None, retry: int | None = None) -> str:
    buf = ""
    if event:
        buf += f"event: {event}\n"
    if retry:
        buf += f"retry: {retry}\n"
    for line in data.split("\n"):       # data 内不能有裸换行，多行拆成多个 data:
        buf += f"data: {line}\n"
    return buf + "\n"                   # 结尾空行是事件分隔符，少了前端收不到

def sse_json(payload: dict, event: str | None = None) -> str:
    return sse_pack(json.dumps(payload, ensure_ascii=False), event=event)

def sse_comment(text: str = "keepalive") -> str:
    return f": {text}\n\n"              # 注释行，前端忽略，仅用于保活

# app/api/stream.py
import asyncio, time
import anyio
from fastapi import APIRouter, Depends, Request
from fastapi.responses import StreamingResponse

router = APIRouter(prefix="/api/v1/chat", tags=["对话"])

HEARTBEAT_INTERVAL = 15.0        # 心跳间隔，要小于链路上最短的 idle timeout
TOTAL_DEADLINE = 300.0           # 单次生成的总时长硬上限

@router.post("/stream")
async def chat_stream(
    request: Request,
    body: ChatIn,
    user: User = Depends(current_user),
    _: None = Depends(rate_limit(20, 60)),
    llm: "LLMService" = Depends(get_llm),
):
    trace_id = trace_id_var.get()
    gate: LLMGate = request.app.state.llm_gate

    async def generator():
        start = time.perf_counter()
        first_at: float | None = None
        tokens, status = 0, "ok"
        queue: asyncio.Queue[str | None] = asyncio.Queue(maxsize=256)

        async def produce() -> None:
            """拉上游分片塞进队列，结束时放一个 None 作为哨兵。"""
            stream = llm.stream(body)
            try:
                async for delta in stream:
                    await queue.put(sse_json({"delta": delta}, event="delta"))
            finally:
                await stream.aclose()         # 真正省钱的一步：关掉上游连接
                await queue.put(None)

        INFLIGHT.inc()
        try:
            # 并发控制要覆盖整个生成期间，所以放在生成器内部
            async with gate.acquire():
                yield sse_pack("", retry=3000)            # 告知浏览器重连间隔
                yield sse_json({"trace_id": trace_id}, event="meta")

                async with asyncio.timeout(TOTAL_DEADLINE):
                    producer = asyncio.create_task(produce())
                    try:
                        while True:
                            # 心跳：队列等待超时就发一个注释行保活
                            try:
                                chunk = await asyncio.wait_for(
                                    queue.get(), timeout=HEARTBEAT_INTERVAL
                                )
                            except asyncio.TimeoutError:
                                yield sse_comment()
                                continue

                            if chunk is None:             # 哨兵：上游已结束
                                break
                            if first_at is None:
                                first_at = time.perf_counter()
                                TTFT.labels(body.model).observe(first_at - start)
                            tokens += 1
                            yield chunk

                            # 断连检测：客户端已走就立刻停，别再烧 token
                            if await request.is_disconnected():
                                status = "disconnected"
                                break
                    finally:
                        producer.cancel()                 # 无论如何都要收掉生产者
                        with anyio.CancelScope(shield=True):
                            await asyncio.gather(producer, return_exceptions=True)

                if status == "ok":
                    yield sse_json({"tokens": tokens}, event="usage")
                    yield sse_pack("[DONE]", event="done")

        except asyncio.TimeoutError:
            status = "deadline"
            yield sse_json({"code": "DEADLINE_EXCEEDED", "message": "生成超时"}, event="error")
        except anyio.get_cancelled_exc_class():
            status = "cancelled"
            raise                                         # 取消异常必须重新抛出
        except BizError as exc:
            status = "biz_error"
            yield sse_json({"code": exc.code, "message": exc.message}, event="error")
        except Exception:
            status = "error"
            logger.exception("stream failed trace_id=%s", trace_id)
            yield sse_json({"code": "INTERNAL_ERROR", "message": "生成中断，请重试"}, event="error")
        finally:
            INFLIGHT.dec()
            elapsed = time.perf_counter() - start
            TOTAL.labels(body.model).observe(elapsed)
            REQUESTS.labels("/chat/stream", status, body.model).inc()
            # 已产生的 token 一律入账，否则「发起即断开」可以白嫖
            await usage_repo.record_stream(user.id, body.model, tokens, status)
            logger.info(
                "stream done status=%s ttft=%.3f total=%.3f tokens=%d trace_id=%s",
                status, (first_at - start) if first_at else -1, elapsed, tokens, trace_id,
            )

    return StreamingResponse(
        generator(),
        media_type="text/event-stream",
        headers={**SSE_HEADERS, "X-Trace-Id": trace_id},
    )

import asyncio, logging

import anyio.to_thread
import httpx
from fastapi import FastAPI

logger = logging.getLogger(__name__)

@asynccontextmanager
async def lifespan(app: FastAPI):
    settings = get_settings()

    # ---------- 启动阶段 ----------
    # 1）线程池容量：同步依赖较多时适当调大
    anyio.to_thread.current_default_thread_limiter().total_tokens = 64

    # 2）HTTP 客户端：必须在这里创建，绑定正确的事件循环
    app.state.http_client = httpx.AsyncClient(
        base_url=settings.openai_base_url,
        headers={"Authorization": f"Bearer {settings.openai_api_key}"},
        timeout=httpx.Timeout(connect=5.0, read=90.0, write=10.0, pool=5.0),
        limits=httpx.Limits(max_connections=100, max_keepalive_connections=20),
        http2=True,
        follow_redirects=False,
    )

    # 3）Redis 连接池
    app.state.redis_pool = ConnectionPool.from_url(
        settings.redis_url, max_connections=50, decode_responses=True
    )
    app.state.redis = Redis(connection_pool=app.state.redis_pool)

    # 4）业务服务与并发闸门
    app.state.llm = LLMService(app.state.http_client)
    app.state.llm_gate = LLMGate(
        max_concurrency=settings.max_concurrency, max_queue=200
    )

    # 5）轻量探测下游：失败只告警，不阻塞启动（否则 Redis 抖一下全部 Pod 起不来）
    try:
        async with asyncio.timeout(3):
            await app.state.redis.ping()
    except Exception:
        logger.warning("redis ping failed on startup, continue anyway")

    app.state.ready = True
    logger.info("startup complete env=%s concurrency=%s",
                settings.env, settings.max_concurrency)

    yield                                  # ← 应用在此期间对外服务

    # ---------- 关闭阶段（顺序很重要）----------
    app.state.ready = False                # ① 先让 readiness 失败，停止接新流量
    await asyncio.sleep(1.5)               # ② 给 K8s 探针一个周期去感知
    await app.state.http_client.aclose()   # ③ 关 HTTP 客户端
    await app.state.redis.aclose()         # ④ 关 Redis
    await app.state.redis_pool.disconnect()
    logger.info("shutdown complete")
    logging.shutdown()                     # ⑤ flush 日志，别丢最后几行

# app/limiter.py
import time, uuid
from dataclasses import dataclass
from fastapi import Depends, HTTPException, Request, status
from redis.asyncio import Redis

# 一次 EVAL 完成「清理过期 + 计数 + 写入」，保证原子性
SLIDING_WINDOW_LUA = """
local key    = KEYS[1]
local now    = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit  = tonumber(ARGV[3])
local member = ARGV[4]
local cost   = tonumber(ARGV[5])

redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local used = 0
local scores = redis.call('ZRANGE', key, 0, -1, 'WITHSCORES')
-- member 形如 "uuid:cost"，用后缀累加权重，支持「一次请求算 N 次」
for i = 1, #scores, 2 do
  local m = scores[i]
  local c = tonumber(string.match(m, ':(%d+)$')) or 1
  used = used + c
end

if used + cost > limit then
  local earliest = redis.call('ZRANGE', key, 0, 0, 'WITHSCORES')
  local retry = 1
  if earliest[2] then
    retry = math.ceil(tonumber(earliest[2]) + window - now)
    if retry < 1 then retry = 1 end
  end
  return {0, used, retry}
end

redis.call('ZADD', key, now, member .. ':' .. cost)
redis.call('EXPIRE', key, window + 1)       -- 必须设过期，否则 key 永久堆积
return {1, used + cost, 0}
"""

@dataclass
class Rule:
    name: str          # 维度名，用于日志和响应头
    limit: int
    window: int

class SlidingWindowLimiter:
    def __init__(self, redis: Redis) -> None:
        self._script = redis.register_script(SLIDING_WINDOW_LUA)

    async def check(self, scope: str, rule: Rule, cost: int = 1) -> tuple[int, int]:
        allowed, used, retry = await self._script(
            keys=[f"rl:{rule.name}:{scope}"],
            args=[time.time(), rule.window, rule.limit, uuid.uuid4().hex, cost],
        )
        if not allowed:
            raise HTTPException(
                status_code=status.HTTP_429_TOO_MANY_REQUESTS,
                detail={
                    "code": "RATE_LIMITED",
                    "message": f"触发{rule.name}限流，请 {retry} 秒后重试",
                    "scope": rule.name,
                },
                headers={
                    "Retry-After": str(retry),                  # 标准头，SDK 读它退避
                    "X-RateLimit-Limit": str(rule.limit),
                    "X-RateLimit-Remaining": "0",
                },
            )
        return int(used), max(rule.limit - int(used), 0)

def parse_sse(lines) -> list[tuple[str, str]]:
    """把原始行解析成 [(event, data), ...]，注释行单独标记为 comment。"""
    events, event = [], None
    for line in lines:
        if line.startswith(":"):
            events.append(("comment", line[1:].strip()))
        elif line.startswith("event: "):
            event = line[7:]
        elif line.startswith("data: "):
            events.append((event or "message", line[6:]))
            event = None
    return events
