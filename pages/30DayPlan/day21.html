基础原理 ​

1. Day21 的定位：Python 不是「换个语法的 Java」，而是另一套运行模型 ​

Java 技术栈切到 Python，最大的认知陷阱是把 Python 当成「语法更短的 Java」。这会导致两类线上事故：

  • 以为 Thread 能利用多核 → 写了一个多线程 CPU 密集任务，8 核机器只跑满 1 核；
  • 以为 async def 加上就是异步 → 里面调了一个同步的 requests.get()，整个事件循环被一个请求卡死，并发从 100 掉到 1。

这两个坑的根源是同一件事：Python 的并发模型由 GIL 决定，而 GIL 是解释器层面的设计，不是语言语法层面的。

⚠️ AI 工程为什么必须吃透这一天：LLM 应用的典型负载是「大量 IO 等待 + 少量 CPU 计算」——一次 LLM 调用要等 2~30 秒，而本地做的事只是拼 prompt 和解析 JSON。这种负载的最优解是 asyncio 协程，不是多线程、更不是多进程。而 RAG 里的向量计算、文本切分、本地 embedding 又是 CPU 密集的，这部分要丢到进程池。一个 AI 服务里两种模型会同时存在，选错一边就是吞吐差 10 倍。

面试加分表述：「我们的 AI 网关是 FastAPI + asyncio，LLM 调用、向量库查询、Redis 这些纯 IO 走协程；文档解析和本地 reranker 这类 CPU 密集的活用 run_in_executor 丢进程池，不让它们占住事件循环。单机从原来 Flask 多线程的 30 QPS 提到 400 QPS，机器数反而少了。」

2. 对象模型：变量是「名字」，不是「盒子」 ​

这是理解后面所有坑（可变对象、默认参数、深浅拷贝、闭包）的唯一前提。Python 里 a = 1 的语义不是「把 1 放进 a 这块内存」，而是「让名字 a 指向对象 1」。

text
a = [1, 2, 3]
b = a            # 不是拷贝！只是多贴一张便利贴

   名字空间                      堆内存里的对象
  ┌───────┐
  │   a   │ ──────┐
  └───────┘       ├──────▶  ┌──────────────┐
  ┌───────┐       │         │ list [1,2,3] │  id=0x7f...a0
  │   b   │ ──────┘         │ 引用计数 = 2  │
  └───────┘                 └──────────────┘

b.append(4)   →  对象被原地改了，a 看到的也是 [1,2,3,4]
b = [9]       →  只是把 b 这张便利贴撕下来贴到新对象上，a 不变

三个必须分清的操作：

写法语义对原对象的影响
b = a名字绑定（rebind）无影响，两个名字指同一对象
b.append(4)原地变更（in-place mutate）原对象被改，所有指向它的名字都受影响
b = b + [4]新建对象后重新绑定原对象不变，b 指向新 list
b += [4]对 list 等价于 extend，是原地变更原对象被改（和上一行结果完全不同）
python
# ✅ 正确理解：+= 对可变对象是原地变更，对不可变对象是重新绑定
a = [1, 2]
b = a
b += [3]          # 原地 extend
print(a)          # [1, 2, 3]  ← a 也变了

a = [1, 2]
b = a
b = b + [3]       # 新建 list 再绑定
print(a)          # [1, 2]     ← a 没变

t = (1, 2)
s = t
s += (3,)         # tuple 不可变，只能新建对象
print(t)          # (1, 2)     ← t 没变

判断「是不是同一个对象」用 is（比较 id），判断「值是否相等」用 ==：

python
a = [1, 2]
b = [1, 2]
print(a == b)     # True   值相等
print(a is b)     # False  不是同一个对象
print(id(a), id(b))

# ⚠️ 小整数池与字符串驻留会让 is 的结果「看起来很诡异」，别依赖它
x = 256; y = 256
print(x is y)     # True   小整数 -5~256 被缓存复用
x = 257; y = 257
print(x is y)     # 交互式下可能 False，脚本里因常量折叠可能 True

⚠️ 永远不要用 is 比较数值和字符串。is 只用于和 None、True、False 这三个单例比较（if x is None）。小整数池、字符串驻留、常量折叠这些优化会让 is 的结果随 Python 版本和执行方式变化，写进业务逻辑就是定时炸弹。

3. 可变对象与不可变对象：到底「不可变」的是什么 ​

很多人把「不可变」理解成「值不能改」，这是错的。不可变指的是「对象创建后，它内部的数据不能被原地修改」；而「名字能不能换指向」是另一回事，任何名字都能随时重新绑定。

类别类型修改时发生什么能否作为 dict 的 key
不可变int、float、bool、str、bytes、tuple、frozenset新建对象，id 变化✅ 可以（__hash__ 稳定）
可变list、dict、set、bytearray、自定义类实例（默认）原地修改，id 不变❌ 不行（list / dict / set 不可哈希）
python
# ✅ 不可变对象：str 的「修改」其实是新建
s = "abc"
print(id(s))
s += "d"          # 等价于 s = s + "d"，新建了一个 str
print(id(s))      # id 变了，原来的 "abc" 等着被回收

# ✅ 可变对象：list 的修改是原地的
lst = [1, 2]
print(id(lst))
lst.append(3)
print(id(lst))    # id 没变

关键边界：不可变容器里可以装可变对象。tuple 不可变，指的是「它的槽位里存的那几个引用不能换」，不是「它装的东西不能变」：

python
t = (1, [2, 3])
# t[1] = [9]      # ❌ TypeError：不能换槽位里的引用
t[1].append(4)    # ✅ 合法！list 自己是可变的
print(t)          # (1, [2, 3, 4])

# 所以这个 tuple 不可哈希，不能当 dict 的 key
# hash(t)         # ❌ TypeError: unhashable type: 'list'
hash((1, (2, 3))) # ✅ 全是不可变元素才能哈希

最高频的线上坑：函数默认参数用可变对象。默认参数在函数定义时求值一次，之后所有调用共用同一个对象：

python
# ❌ 错误写法：所有调用共用同一个 list / dict
def add_msg(msg, history=[]):
    history.append(msg)
    return history

print(add_msg("第一轮"))   # ['第一轮']
print(add_msg("第二轮"))   # ['第一轮', '第二轮']  ← 上一次的脏数据还在！

def build_req(prompt, extra={}):
    extra["prompt"] = prompt
    return extra

print(build_req("A"))     # {'prompt': 'A'}
print(build_req("B"))     # {'prompt': 'B'}  ← extra 始终是同一个 dict
                          #   上一次写入的 user_id 会被带到这一次
python
# ✅ 正确写法：默认值写 None，函数内部新建
def add_msg(msg, history=None):
    if history is None:
        history = []
    history.append(msg)
    return history

print(add_msg("第一轮"))   # ['第一轮']
print(add_msg("第二轮"))   # ['第二轮']  ← 互不干扰

# 验证一下默认参数确实只求值一次
def f(x=[]):
    pass
print(f.__defaults__)     # ([],)  ← 这个 list 挂在函数对象上，终身只有一个

⚠️ 这个坑在 AI 工程里特别危险。多轮对话的 messages=[]、工具调用的 tools=[]、请求头 headers={} 全是高危位置——一旦用了可变默认值，A 用户的对话历史会漏到 B 用户的 prompt 里，这是数据越权，不只是 bug。Day21 的 Code Review 第一条就是搜 def .*=[] 和 def .*={} 这两种写法。

面试加分表述：「默认参数是在函数定义时求值并存到 func.__defaults__ 上的，所以可变默认值相当于一个函数级别的全局状态。我们在 CI 里加了 ruff 的 B006 规则（flake8-bugbear），这类写法直接卡住不让合。」

4. 深浅拷贝：三层语义必须分清 ​

拷贝问题之所以难，是因为它有三层而不是两层，面试时只答「浅拷贝拷一层、深拷贝拷全部」会被追问到卡住。

text
原数据： data = {"name": "张三", "tags": ["AI", "后端"]}

① b = data（直接赋值 / 名字绑定）
   b ──┐
       ├──▶ 同一个 dict  ──▶ 同一个 list
   data┘
   改 b["name"]、b["tags"].append() → data 全都变

② b = copy.copy(data)（浅拷贝）
   b    ──▶ 新 dict ──┐
                      ├──▶ 同一个 list（只拷了引用）
   data ──▶ 旧 dict ──┘
   改 b["name"]          → data 不变 ✅
   改 b["tags"].append() → data 也变 ❌

③ b = copy.deepcopy(data)（深拷贝）
   b    ──▶ 新 dict ──▶ 新 list
   data ──▶ 旧 dict ──▶ 旧 list
   改任何层级 → data 都不变 ✅
python
import copy

data = {"name": "张三", "tags": ["AI", "后端"], "age": 28}

# ① 赋值：同一个对象
b1 = data
b1["name"] = "李四"
print(data["name"])        # 李四       ← 被改了

data = {"name": "张三", "tags": ["AI", "后端"], "age": 28}

# ② 浅拷贝：第一层独立，嵌套层共享
b2 = copy.copy(data)       # 等价写法：data.copy() / dict(data) / {**data}
b2["name"] = "李四"
b2["tags"].append("算法")
print(data["name"])        # 张三                    ← 第一层没被影响 ✅
print(data["tags"])        # ['AI', '后端', '算法']   ← 嵌套层被影响 ❌

data = {"name": "张三", "tags": ["AI", "后端"], "age": 28}

# ③ 深拷贝：递归全部独立
b3 = copy.deepcopy(data)
b3["tags"].append("算法")
print(data["tags"])        # ['AI', '后端']           ← 完全隔离 ✅

常见的「伪浅拷贝」写法，全都等价于 copy.copy()：

对象浅拷贝写法说明
listlst[:]、list(lst)、lst.copy()、[*lst]四种完全等价
dictd.copy()、dict(d)、{**d}{**d} 只展开一层
sets.copy()、set(s)元素必须不可变，所以浅拷贝通常够用
嵌套结构只能 copy.deepcopy()手写递归容易漏掉循环引用

深拷贝的三个必须知道的细节（面试追问重灾区）：

  1. 循环引用能正确处理。deepcopy 内部维护一个 memo 字典（id(原对象) → 新对象），遇到已拷过的对象直接复用，所以 a.append(a) 这种自引用结构不会死循环。
  2. 不可变对象不会真拷。deepcopy(1)、deepcopy("abc")、deepcopy((1, 2)) 会直接返回原对象（全不可变的 tuple 也走这个优化），因为没有被改坏的风险。
  3. 可以用 __deepcopy__ / __copy__ 自定义行为。数据库连接、线程锁、文件句柄这些不该被拷贝的资源必须自定义，否则 deepcopy 会抛 TypeError: cannot pickle ... 或拷出一个废掉的连接。
python
import copy

# ① 循环引用：deepcopy 靠 memo 表安全处理
a = [1, 2]
a.append(a)                 # 自引用
b = copy.deepcopy(a)
print(b[2] is b)            # True   ← 新结构里也是自引用，没死循环

# ② 不可变对象直接返回原对象
t = (1, 2, 3)
print(copy.deepcopy(t) is t)   # True

# ③ 自定义：不该被拷的资源要显式排除
class LLMClient:
    def __init__(self, api_key, session):
        self.api_key = api_key
        self.session = session        # 假设是 aiohttp 连接池，不能拷

    def __deepcopy__(self, memo):
        new = LLMClient(copy.deepcopy(self.api_key, memo), self.session)
        return new                     # session 共享，不深拷

⚠️ AI 工程里 deepcopy 是性能杀手。RAG 场景一个 chunk 列表可能有几万个 dict，deepcopy 要递归遍历所有对象、维护 memo 表，比浅拷贝慢 1~2 个数量级。实践原则：能不改原数据就别拷；必须隔离时优先用「不可变数据 + 重建」而不是 deepcopy（比如 new_msgs = [*msgs, new_one]）。

面试加分表述：「我们规定对话上下文 messages 在链路里只读，任何需要改写的地方都返回新列表，不做深拷贝也不原地改。这样既避免了 deepcopy 的开销，又天然规避了多轮对话串数据的问题。」

5. GIL 全局解释器锁：它到底锁住了什么 ​

GIL（Global Interpreter Lock）是CPython 解释器的一把进程级互斥锁。一句话定义：同一个进程内，任意时刻只有一个线程能持有 GIL 并执行 Python 字节码。

先把容易混淆的边界拆清楚，这是面试区分度最高的地方：

说法对不对真实情况
「GIL 是 Python 语言的特性」❌是 CPython 实现的特性。Jython、IronPython 没有 GIL；PyPy 有；3.13 起 CPython 提供可选的 no-GIL 构建
「有 GIL 所以 Python 没有真线程」❌线程是真的 OS 线程，能被操作系统调度，只是执行字节码要抢 GIL
「有 GIL 所以多线程完全没用」❌IO 密集场景非常有用，等 IO 时 GIL 会被释放
「有 GIL 所以多线程天然线程安全」❌最危险的误解。GIL 保证的是字节码级别的原子性，不是业务操作级别的
「GIL 让 CPU 密集型多线程跑不满多核」✅这才是 GIL 真正的限制
text

GIL 在什么时候会被释放（这是「IO 密集型适合多线程」的技术根据）：

  1. 执行阻塞式 IO 时：socket.recv、file.read、time.sleep、数据库驱动等待响应——CPython 在调用系统调用前后包了一对 Py_BEGIN_ALLOW_THREADS / Py_END_ALLOW_THREADS；
  2. 执行时间超过切换间隔（默认 5ms，sys.getswitchinterval()）时被强制让出；
  3. 进入释放了 GIL 的 C 扩展时：NumPy 的大矩阵运算、hashlib、部分压缩/加解密库，底层循环里会主动放开 GIL；
  4. 线程结束时。

import sys, time, threading
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

    for i in range(n):
        s += i
    return s

def io_task():                      # IO 密集：模拟网络等待

t0 = time.perf_counter()
with ProcessPoolExecutor(4) as ex:
    list(ex.map(cpu_task, [10_000_000] * 4))
print(f"CPU 密集 + 4 进程：{time.perf_counter() - t0:.2f}s")   # ≈ 串行 / 核数

# ✅ IO 密集用多线程：4 个 1 秒的任务总共约 1 秒
t0 = time.perf_counter()
with ThreadPoolExecutor(4) as ex:
    list(ex.map(lambda _: io_task(), range(4)))
print(f"IO 密集 + 4 线程：{time.perf_counter() - t0:.2f}s")    # ≈ 1.0s

⚠️ 「GIL 能不能去掉」的标准答法不是「不能」，而是「代价在哪」。阻碍主要有三点：① 海量 C 扩展（NumPy、Pandas、各种数据库驱动）的 API 假设了 GIL 存在，去掉要全部改造；② 去掉 GIL 要给每个对象加细粒度锁或改引用计数为原子操作，单线程性能会下降（早期尝试慢了 30%~40%）；③ 引用计数本身是非线程安全的，要换成带偏向/原子的方案。CPython 3.13 通过 PEP 703 提供了 --disable-gil 的自由线程（free-threaded）构建，3.13/3.14 仍是实验/逐步成熟阶段，生态适配还在进行中。

import asyncio, time
from concurrent.futures import ProcessPoolExecutor

# 场景：AI 服务里 CPU 密集 + IO 密集混合，一个请求要做两件事
def split_document(text: str) -> list[str]:
    """CPU 密集：文本切分 + 本地分词，纯计算"""
    time.sleep(0.5)                      # 用 sleep 模拟 CPU 耗时
    return [text[i:i + 100] for i in range(0, len(text), 100)]

async def call_embedding(chunk: str) -> list[float]:
    """IO 密集：调远端 embedding 接口"""
    await asyncio.sleep(0.3)
    return [0.1] * 1536

# ✅ 正确组合：CPU 的活丢进程池，IO 的活用协程并发
async def ingest(text: str, pool: ProcessPoolExecutor):
    loop = asyncio.get_running_loop()
    chunks = await loop.run_in_executor(pool, split_document, text)   # 不占事件循环
    vectors = await asyncio.gather(*(call_embedding(c) for c in chunks))
    return len(vectors)

async def main():
    with ProcessPoolExecutor(max_workers=4) as pool:
        texts = ["x" * 1000 for _ in range(4)]
        t0 = time.perf_counter()
        res = await asyncio.gather(*(ingest(t, pool) for t in texts))
        print(res, f"{time.perf_counter() - t0:.2f}s")

asyncio.run(main())

⚠️ 进程池的 max_workers 不要照搬线程池的经验值。线程池可以开几十上百，进程池超过 CPU 核数后只会增加上下文切换和内存，吞吐不升反降。而且每次 run_in_executor 传给进程池的参数都要序列化（pickle），大对象（比如几十 MB 的 DataFrame、模型对象）走进程池反而比串行慢——这种情况要么用共享内存，要么改成在子进程里重新加载。

7. 函数是一等公民：闭包与 LEGB 作用域 ​

装饰器能存在的前提是「函数可以被当成值传递和返回」。这一节是装饰器的地基。

python
def outer(prefix):
    count = 0                      # 自由变量，被内层函数捕获

    def inner(msg):
        nonlocal count             # 声明要修改外层函数的变量
        count += 1
        return f"[{prefix}#{count}] {msg}"

    return inner                   # 返回函数对象本身，不加括号

log = outer("LLM")
print(log("第一次调用"))            # [LLM#1] 第一次调用
print(log("第二次调用"))            # [LLM#2] 第二次调用  ← 状态被闭包保住了

# 闭包捕获的变量存在 __closure__ 里
print(log.__closure__)                                  # (cell, cell)
print([c.cell_contents for c in log.__closure__])       # [2, 'LLM']
print(log.__code__.co_freevars)                         # ('count', 'prefix')

LEGB 查找顺序：Python 查一个名字时按 Local → Enclosing → Global → Builtin 依次找，找到就停。

写操作的默认行为：写入 Local，除非用 global / nonlocal 声明

nonlocal x读写都指向最近的外层函数的变量闭包里累加计数、缓存状态

闭包最经典的坑：延迟绑定（late binding）。闭包捕获的是变量本身，不是定义时刻的值：

python
# ❌ 错误：三个函数共享同一个 i，循环结束后 i == 2
funcs = []
for i in range(3):
    funcs.append(lambda: i)
print([f() for f in funcs])        # [2, 2, 2]  ← 不是 [0, 1, 2]！

# ✅ 解法一：用默认参数在定义时「快照」当前值
funcs = []
for i in range(3):
    funcs.append(lambda i=i: i)
print([f() for f in funcs])        # [0, 1, 2]

# ✅ 解法二：用 functools.partial 绑定
from functools import partial
funcs = [partial(lambda x: x, i) for i in range(3)]
print([f() for f in funcs])        # [0, 1, 2]

# ✅ 解法三：多包一层工厂函数，让每个 i 落在独立作用域
def make(i):
    return lambda: i
funcs = [make(i) for i in range(3)]
print([f() for f in funcs])        # [0, 1, 2]

⚠️ 延迟绑定在 AI 工程里的真实事故：批量注册 Function Calling 工具时，用 for tool in tools: register(name, lambda args: call(tool, args)) 注册了 20 个工具，结果每个工具调用的都是最后那一个。排查了半天才发现是闭包捕获了循环变量。标准写法是 lambda args, tool=tool: call(tool, args)。

面试加分表述：「闭包的本质是函数对象上挂了 __closure__ 这组 cell，捕获的是变量的 cell 而不是值。所以循环里造闭包必须用默认参数或 partial 做值快照——我们注册 LLM 工具函数时就踩过这个坑，现在 code review 看到循环体里出现 lambda 都会多看一眼。」

8. 装饰器 Decorator：原理、执行时机与 wraps ​

装饰器就是一个接收函数、返回函数的高阶函数，@ 只是语法糖。它解决的是 Java 里 AOP 解决的问题：在不改原函数源码的前提下横向加能力（计时、日志、重试、限流、鉴权、缓存）。

python
from functools import wraps
import time

def timer(func):                       # ① 装饰器本体，入参是被装饰的函数
    @wraps(func)                       # ③ 拷贝元信息
    def wrapper(*args, **kwargs):      # ② 包装函数，签名要能接住任意参数
        start = time.perf_counter()
        try:
            return func(*args, **kwargs)
        finally:
            cost = time.perf_counter() - start
            print(f"{func.__qualname__} 耗时 {cost * 1000:.1f}ms")
    return wrapper

@timer
def llm_call(prompt: str) -> str:
    """调用大模型"""
    time.sleep(1)
    return f"回答：{prompt}"

# @timer 完全等价于： llm_call = timer(llm_call)
print(llm_call("你好"))

functools.wraps 到底做了什么：装饰后 foo 这个名字指向的是 wrapper，所以 __name__、__doc__ 等元信息全变成 wrapper 的。wraps 就是把原函数的元信息拷到 wrapper 上，并把原函数挂在 __wrapped__。

python
from functools import wraps

def no_wraps(func):
    def wrapper(*a, **kw):
        return func(*a, **kw)
    return wrapper

def with_wraps(func):
    @wraps(func)
    def wrapper(*a, **kw):
        return func(*a, **kw)
    return wrapper

@no_wraps
def a(x: int) -> str:
    """原始文档"""

@with_wraps
def b(x: int) -> str:
    """原始文档"""

# ❌ 不加 wraps：元信息全丢
print(a.__name__, a.__doc__)        # wrapper None
# ✅ 加了 wraps：元信息保留，还能通过 __wrapped__ 拿到原函数
print(b.__name__, b.__doc__)        # b 原始文档
print(b.__wrapped__)                # <function b at 0x...>

import inspect
print(inspect.signature(a))         # (*a, **kw)       ← 签名坏了
print(inspect.signature(b))         # (x: int) -> str  ← 签名正确

属性作用丢了会怎样
__name__ / __qualname__函数名日志、监控埋点里全是 wrapper，无法定位
__doc__文档字符串Swagger / FastAPI 自动文档变空
__module__所属模块异常栈、反射定位失效
__dict__自定义属性其他框架挂在函数上的标记丢失

⚠️ 不加 wraps 在 FastAPI 项目里是致命的。FastAPI 靠 __annotations__ 和签名做依赖注入与参数校验，装饰器一旦吞掉注解，接口会表现为「参数永远收不到」或启动直接报错。同理，Celery、Click、pytest 的 fixture 都依赖函数元信息。写装饰器时 @wraps 不是可选项，是必写项。

9. 生成器 Generator：yield 的惰性求值 ​

只要函数体里出现 yield，这个函数就不再是普通函数，调用它不执行任何代码，而是返回一个生成器对象。真正的执行发生在每次 next() 时，执行到 yield 就暂停并交出一个值。

python
def gen():
    print("开始")
    yield 1
    print("中间")
    yield 2
    print("结束")

g = gen()                 # ← 什么都没打印！只创建了生成器对象
print(type(g))            # <class 'generator'>

print(next(g))            # 打印「开始」，返回 1，函数暂停在第一个 yield
print(next(g))            # 打印「中间」，返回 2
# print(next(g))          # 打印「结束」，然后抛 StopIteration

生成器的状态机

  created ──next()──▶ running ──遇到 yield──▶ suspended
                         ▲                        │
                         └──────── next() ────────┘
                                                  │
                         函数 return / 执行完 ─────▶ closed
                                                  │
                                            抛 StopIteration

惰性求值的价值：内存从 O(n) 降到 O(1)。这是读取超大文件、流式处理的唯一正确方式：

python
import sys

# ❌ 一次性加载：10GB 文件直接把内存打爆
def read_all_bad(path):
    with open(path, encoding="utf-8") as f:
        return f.readlines()          # 整个文件进内存

# ✅ 生成器逐行：内存只占一行
def read_lines(path):
    with open(path, encoding="utf-8") as f:
        for line in f:                # 文件对象本身就是迭代器
            line = line.strip()
            if line:                  # 顺手过滤空行
                yield line

# 内存对比：列表推导 vs 生成器表达式
lst = [i * i for i in range(1_000_000)]      # 列表推导：立刻算完
genexp = (i * i for i in range(1_000_000))   # 生成器表达式：只存状态
print(sys.getsizeof(lst))        # 约 8 MB
print(sys.getsizeof(genexp))     # 约 200 字节  ← 差 4 万倍

方法作用典型用途

# send：yield 既是出口也是入口
def accumulator():
    total = 0
    while True:
        x = yield total        # yield 出 total，同时接收 send 进来的 x
        if x is None:
            break
        total += x

acc = accumulator()
print(next(acc))               # 0     ← 必须先启动到第一个 yield
print(acc.send(10))            # 10
print(acc.send(5))             # 15

# close + finally：流式输出提前中断时的资源清理
def stream_tokens(prompt):
    conn = f"连接已建立({prompt})"
    print(conn)
    try:
        for i in range(1000):
            yield f"token{i}"
    except GeneratorExit:
        print("消费方提前断开，走清理分支")
        raise
    finally:
        print("连接已关闭")     # ✅ 无论正常结束还是提前中断都会执行

s = stream_tokens("你好")
print(next(s), next(s))
s.close()                      # 打印「消费方提前断开」+「连接已关闭」

return 在生成器里的含义：return value 不是返回值，而是结束迭代并把 value 塞进 StopIteration.value：

    yield 2
    return "统计结果"           # 不会被 for 循环看到

⚠️ 生成器只能消费一次。遍历完就是 closed 状态，再 for 一遍什么都没有。这个坑在 RAG 流水线里非常常见：chunks = split(doc) 返回生成器，第一处用来算 token 数、第二处用来存库，结果存进去的是空的。判断准则：如果同一份数据要用两次，就在拿到的地方立刻 list(...) 物化，或者改成每次重新调用生成器函数。

面试加分表述：「我们 LLM 流式输出整条链路都是生成器/异步生成器：模型 SSE → 解析 → 敏感词过滤 → 下发前端，每层都是 yield，内存里只有当前这个 token。而且在 finally 里关连接，用户中途关页面时 GeneratorExit 会一路传上去，模型侧的连接能及时释放，不会泄漏。」

手写一个迭代器类，用来理解协议（实际项目优先用生成器，代码少 80%）：

# 写法一：实现迭代器协议（啰嗦，但能看清协议要求）
class Countdown:
    def __init__(self, n):
        self.n = n

    def __iter__(self):
        return self                   # 自己就是迭代器

    def __next__(self):
        if self.n <= 0:
            raise StopIteration       # ✅ 必须抛这个异常来终止
        self.n -= 1
        return self.n + 1

print(list(Countdown(3)))             # [3, 2, 1]

# 写法二：可迭代对象 + 独立迭代器（支持重复遍历，推荐给需要多次遍历的数据源）
class ChunkStore:
    def __init__(self, path):
        self.path = path

    def __iter__(self):                # 每次 for 都新开一个生成器
        with open(self.path, encoding="utf-8") as f:
            for line in f:
                yield line.strip()

# print(sum(1 for _ in store))        # ✅ 可以遍历多次

⚠️ 「生成器只能遍历一次」的最佳工程解法不是 list()，而是把它包成可迭代对象（上面的写法二）。list() 会把惰性优势全部抵消；而实现 __iter__ 返回生成器的类，既能重复遍历，又每次都是惰性的。RAG 的 chunk 数据源、日志回放、训练样本加载都适合这个模式。

11. asyncio 异步协程：事件循环是怎么跑起来的 ​

asyncio 的全部能力建立在一个简单机制上：单线程里有一个事件循环，它不停地从就绪队列里取任务执行；任务一旦要等 IO，就把自己挂起并把控制权交回循环，循环立刻去跑下一个任务。

text
事件循环（Event Loop）的一轮迭代

┌───────────────────────────────────────────────────────────┐
│  ① 取出 ready 队列里的所有回调，依次执行                      │
│       协程跑到 await 且要等 IO → 注册到 selector，挂起        │
│       协程跑到 await 但结果已就绪 → 直接继续往下跑             │
│  ② 计算最近的定时器到期时间 timeout                           │
│  ③ selector.select(timeout)  ← 唯一「真正阻塞」的地方          │
│       操作系统通知哪些 fd 可读/可写                            │
│  ④ 把就绪 fd 对应的回调塞进 ready 队列                        │
│  ⑤ 把到期的 call_later 定时器回调塞进 ready 队列               │
└───────────────────────────────────────────────────────────┘
          ▲                                       │
          └───────────────── 下一轮 ───────────────┘

★ 关键推论：如果 ① 里某个协程在做同步阻塞操作（time.sleep、requests.get），

13. 并发原语：gather / as_completed / wait / Semaphore / TaskGroup ​

并发怎么组织，直接决定了 AI 服务的吞吐和故障表现。这是 Day21 在项目里用得最多的一节。

API返回顺序异常行为典型场景
asyncio.gather(*aws)与入参顺序一致默认第一个异常立刻抛出，其余任务继续跑但结果丢弃结果要按序拼装（多路召回合并）
gather(*aws, return_exceptions=True)同上异常作为结果值返回，不中断部分失败可降级（多模型并发，谁活用谁）
asyncio.as_completed(aws)谁先完成谁先出每个 await 单独抛要边出边处理（首个可用答案、流式聚合）
asyncio.wait(tasks, return_when=...)返回 (done, pending) 两个集合不抛，异常留在 Task 里需要精细控制（FIRST_COMPLETED 抢答）
asyncio.wait_for(aw, timeout)单个超时抛 TimeoutError 并取消内部任务给单次 LLM 调用加超时
asyncio.timeout(sec)（3.11+）上下文管理器同上，可包一段代码给「检索 + 生成」整段加预算
asyncio.TaskGroup（3.11+）无返回，靠变量收集任一失败则取消全部兄弟任务，抛 ExceptionGroup要求「要么都成功，要么都别干」
asyncio.Semaphore(n)无无并发度限流，保护下游不被打爆
python
import asyncio, random

async def call_model(name, delay, fail=False):
    await asyncio.sleep(delay)
    if fail:
        raise RuntimeError(f"{name} 调用失败")
    return f"{name} 的回答"

# ① gather：结果按入参顺序，一个失败整体抛
async def demo_gather():
    try:
        res = await asyncio.gather(
            call_model("GPT", 0.3),
            call_model("Claude", 0.1, fail=True),
            call_model("Qwen", 0.2),
        )
    except RuntimeError as e:
        print("gather 直接抛：", e)      # Claude 调用失败

# ② gather + return_exceptions：部分失败可降级（AI 多模型兜底最常用）
async def demo_gather_tolerant():
    res = await asyncio.gather(
        call_model("GPT", 0.3),
        call_model("Claude", 0.1, fail=True),
        call_model("Qwen", 0.2),
        return_exceptions=True,
    )
    ok = [r for r in res if not isinstance(r, Exception)]
    bad = [r for r in res if isinstance(r, Exception)]
    print(f"成功 {len(ok)} 个，失败 {len(bad)} 个：{ok}")

# ③ as_completed：谁先回谁先处理，适合「要首个可用答案」
async def demo_as_completed():
    aws = [call_model("GPT", 0.3), call_model("Claude", 0.1), call_model("Qwen", 0.2)]
    for fut in asyncio.as_completed(aws):
        r = await fut
        print("先到先处理：", r)         # Claude → Qwen → GPT

# ④ wait + FIRST_COMPLETED：抢答模式，拿到第一个就取消其余
async def demo_race():
    tasks = {asyncio.create_task(call_model(n, random.uniform(0.1, 0.5)))
             for n in ("GPT", "Claude", "Qwen")}
    done, pending = await asyncio.wait(tasks, return_when=asyncio.FIRST_COMPLETED)
    for t in pending:
        t.cancel()                      # ✅ 必须显式取消，否则任务继续烧 token
    await asyncio.gather(*pending, return_exceptions=True)   # 等取消落地
    print("抢答结果：", done.pop().result())

asyncio.run(demo_gather_tolerant())

import asyncio

async def demo_taskgroup():
    results = {}
    try:
        async with asyncio.TaskGroup() as tg:
            t1 = tg.create_task(call_model("检索", 0.2))
            t2 = tg.create_task(call_model("重排", 0.1))

        results["检索"] = t1.result()    # 离开 with 时任务一定完成了
        results["重排"] = t2.result()
    except* RuntimeError as eg:          # except* 处理 ExceptionGroup
        print("子任务异常：", eg.exceptions)
    return results
选择准则用哪个
要全部结果、按序、允许部分失败gather(return_exceptions=True)
要全部结果、任一失败就整体放弃TaskGroup（3.11+）或 gather 默认行为
只要最快的那个答案wait(FIRST_COMPLETED) + 取消 pending
结果要边出边流给前端as_completed 或异步生成器
任何时候下游有 QPS/并发上限一定叠加 Semaphore

⚠️ gather 默认行为的坑：第一个异常抛出后，其余任务并没有被取消，它们还在后台跑、还在消耗 token 和下游配额，只是结果没人要了。如果要「失败就全停」，必须用 TaskGroup，或者自己 except 之后遍历 task.cancel()。

14. 上下文管理器 with：__enter__ / __exit__ 与 contextlib ​

with 是 Python 版的 try-with-resources，解决的是「无论正常结束还是抛异常，收尾代码一定要执行」。

text
with expr as var:
    body

实际等价于：

  mgr = expr
  var = mgr.__enter__()          ← 进入：拿到资源
  try:
      body
  except BaseException as e:
      if not mgr.__exit__(type(e), e, e.__traceback__):
          raise                  ← __exit__ 返回假值 → 异常继续往外抛
  else:
      mgr.__exit__(None, None, None)   ← 正常退出，三个参数都是 None
python
import time

class LLMSession:
    def __init__(self, model):
        self.model = model

    def __enter__(self):
        self.t0 = time.perf_counter()
        print(f"建立 {self.model} 连接")
        return self                    # ✅ 返回值赋给 as 后面的变量

    def __exit__(self, exc_type, exc_val, exc_tb):
        cost = (time.perf_counter() - self.t0) * 1000
        print(f"释放连接，耗时 {cost:.1f}ms")
        if exc_type is not None:
            print(f"捕获到异常：{exc_type.__name__}: {exc_val}")
        return False                   # ✅ 返回 False：异常继续往外传播
                                       # ⚠️ 返回 True：异常被「吞掉」，调用方感知不到

with LLMSession("gpt-4") as s:
    print(f"用 {s.model} 回答问题")

16. 协程的本质：生成器 + 事件循环的两层拼装 ​

async def 不是黑魔法。协程对象和生成器共用同一套底层机制——可暂停、可恢复的栈帧。CPython 里 coroutine 和 generator 的实现几乎一致，只是前者多了 __await__、少了 __iter__。

三层结构，从下往上

第三层  事件循环 EventLoop
        ├─ ready 队列：马上能跑的回调
        ├─ selector：epoll/kqueue/IOCP，监听 fd 就绪
        └─ 定时器堆：call_later / sleep

第二层  Task（Future 的子类）

第一层  coroutine（可暂停的栈帧）

  → Task 收到 Future，给它 add_done_callback(自己继续跑)

  → 1 秒后定时器到期 → Future.set_result() → 回调入 ready 队列

17. yield from 旧式协程 vs async/await 原生协程 ​

Python 的协程演进了三代，面试里问「yield from 和 await 什么关系」就是在考这段历史。

阶段版本写法问题
第一代2.5+生成器 + send() 手写调度全靠手工，没有标准库支撑
第二代3.3~3.4yield from + @asyncio.coroutine协程和生成器写法混淆，for 能迭代一个「协程」，语义混乱
第三代3.5+async def + await✅ 语法层面彻底区分，是现在的唯一选择

yield from 并没有被淘汰，它在「生成器委托」这个场景里仍然是最简洁的写法：

# yield from 的真实用途：把子生成器的所有产出透传出去
def read_file(path):
    yield f"--- {path} ---"
    # yield from 等价于 for line in inner(): yield line，但还透传 send/throw/返回值
    yield from ("第 %d 行" % i for i in range(3))

def read_all(paths):
    for p in paths:
        yield from read_file(p)       # 委托给子生成器

print(list(read_all(["a.txt", "b.txt"])))
关键词用在哪语义
yield生成器函数内产出一个值并暂停
yield from生成器函数内把子生成器完全代理（含 send / throw / return 值）
await协程函数内挂起当前协程，等待可等待对象完成

⚠️ 别在 async def 里写 yield from，这是语法错误。async def 里的 yield 表示异步生成器（见 #24），语义完全不同。另外，async def 里既有 yield 又有 return value 也是语法错误。

面试加分表述：「我会直接点明：await 在字节码层面做的事和 yield from 高度相似（都是把子任务的暂停透传给上层驱动者），但 async def 把『协程』和『迭代器』在语法层面分开了，这才是 3.5 那次改动的核心价值——此前一个对象既能 for 又能当协程，可读性和出错率都很糟。」

18. GIL 的切换机制：从字节码计数到时间片 ​

GIL 的切换策略在 Python 3.2 发生过一次重要变更，这是深挖 GIL 时的加分点。

版本切换触发问题
≤ 3.1每执行 100 条字节码检查一次一条字节码耗时差异巨大（a+b 和 big_list.sort() 都算一条），导致切换时机极不均匀；IO 线程响应延迟高
≥ 3.2时间片，默认 5ms（sys.setswitchinterval）更公平，但「GIL 护航」问题（convoy effect）仍存在

GIL 的「护航效应」（convoy effect）

IO 线程被唤醒后想拿 GIL，但 CPU 线程正好持有且没到 5ms：
  CPU线程 │█████████│         █████████│
  IO线程  │  ↑想拿  ░░░░░░░░░ │  ↑拿到  │
            被迫等到时间片用完，延迟被放大

★ 结论：一个进程里同时跑「CPU 密集线程」和「IO 密集线程」是最差组合。
  CPU 线程会持续抢占 GIL，把 IO 线程的响应延迟拖到几十毫秒。
  正确做法：CPU 任务放到独立进程，IO 任务留在主进程的事件循环里。

⚠️ 这解释了一个真实现象：FastAPI 服务里只要有一个接口在做同步的 CPU 密集活（比如用 pandas 处理大表），整个服务所有接口的 P99 都会恶化，不只是那个接口慢。因为它既占着 GIL，又占着事件循环。监控上的表现是「P50 正常、P99 爆炸」。

面试加分表述：「GIL 的切换从 3.2 开始由字节码计数改成 5ms 时间片，可以用 sys.getswitchinterval() 看。更值得说的是『护航效应』——CPU 线程和 IO 线程混在一个进程里时，IO 线程的延迟会被放大到时间片级别。我们线上就因为一个接口里用 pandas 处理大表，把整个服务的 P99 从 200ms 拖到 3 秒，后来把它整体挪到进程池解决。」

import asyncio, contextvars
from concurrent.futures import ThreadPoolExecutor

trace_id = contextvars.ContextVar("trace_id", default="-")

def sync_work():
    return f"子线程看到的 traceId = {trace_id.get()}"

POOL = ThreadPoolExecutor(4)

async def main():
    trace_id.set("abc-123")

    # ✅ to_thread 自动复制 context（3.9+）
    print(await asyncio.to_thread(sync_work))          # abc-123

    # ❌ run_in_executor 默认丢 context
    loop = asyncio.get_running_loop()
    print(await loop.run_in_executor(POOL, sync_work))  # -

    # ✅ 手动复制 context 再跑
    ctx = contextvars.copy_context()
    print(await loop.run_in_executor(POOL, lambda: ctx.run(sync_work)))  # abc-123

asyncio.run(main())

⚠️ 线程池大小不是越大越好。线程池是用来「兜住同步阻塞」的，不是用来提升吞吐的。配置准则：线程数 ≈ 目标并发 × 单次阻塞时长 / 可接受延迟，并且一定要配上队列上限和拒绝策略——否则下游变慢时任务会在队列里无限堆积，表现为「接口全部超时但 CPU 和内存都正常」。

21. asyncio 的异常处理：为什么异常会「凭空消失」 ​

这是 asyncio 最容易踩的坑，也是区分「会用」和「懂」的分水岭。

核心机制：Task 捕获协程抛出的异常后存在自己身上，不会往上冒泡。只有当有人 await task 或 task.result() 时才会重新抛出。没人取 → 异常被静默吞掉，直到 Task 被 GC 时打一条 Task exception was never retrieved 日志。

python
import asyncio

async def boom():
    raise ValueError("出错了")

# ❌ 错误写法：fire-and-forget，异常被吞
async def bad():
    asyncio.create_task(boom())        # 没 await，没回调
    await asyncio.sleep(1)
    print("主流程以为一切正常")          # 照常打印，故障被隐藏

# ✅ 正确写法 1：显式 await
async def good_1():
    task = asyncio.create_task(boom())
    try:
        await task
    except ValueError as e:
        print("捕获到：", e)

# ✅ 正确写法 2：真的要后台跑，就挂 done_callback + 持引用
BACKGROUND: set[asyncio.Task] = set()

def _on_done(t: asyncio.Task):
    BACKGROUND.discard(t)
    if t.cancelled():
        return
    if exc := t.exception():
        print("后台任务异常：", repr(exc))   # 这里应该打日志 / 上报告警

def spawn(coro) -> asyncio.Task:
    t = asyncio.create_task(coro)
    BACKGROUND.add(t)                       # ⚠️ 必须持强引用，否则 Task 可能被 GC
    t.add_done_callback(_on_done)
    return t

⚠️ create_task 返回的 Task 必须被引用住。事件循环只持弱引用，如果你不存起来，Task 可能在执行到一半时被垃圾回收掉，表现为「任务莫名其妙不执行了」且没有任何报错。官方文档对此有明确警告。

22. 取消与超时：CancelledError 为什么不能被 except Exception 吞掉 ​

取消的本质：task.cancel() 并不会「杀死」协程，它只是在协程下一次 await 挂起点往里面扔一个 CancelledError。如果协程永远不 await（比如在跑一个死循环的纯计算），取消就永远不生效。

import functools, time

def retry(times: int = 3, delay: float = 0.5, exceptions=(Exception,)):
    def decorator(fn):                      # 第二层：真正的装饰器
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):       # 第三层：替换函数
            last = None
            for i in range(times):
                try:
                    return fn(*args, **kwargs)
                except exceptions as e:
                    last = e
                    if i < times - 1:
                        time.sleep(delay * (2 ** i))   # 指数退避
            raise last
        return wrapper
    return decorator                        # 第一层：返回装饰器

import functools

class CallCounter:                     # 用类做装饰器：天然带状态
    def __init__(self, fn):
        functools.update_wrapper(self, fn)   # 相当于 wraps 的类版本
        self.fn, self.count = fn, 0
    def __call__(self, *a, **kw):
        self.count += 1
        return self.fn(*a, **kw)

@CallCounter
def ping(): return "pong"

def singleton(cls):                    # 装饰「类」：返回同一实例
    inst = {}
    @functools.wraps(cls)
    def getter(*a, **kw):
        if cls not in inst:
            inst[cls] = cls(*a, **kw)
        return inst[cls]
    return getter

@singleton
class ModelClient:
    def __init__(self): print("加载模型（只应出现一次）")

import sys

class WithDict:                       # 默认每个实例带一个 __dict__
    def __init__(self, x, y): self.x, self.y = x, y

class WithSlots:
    __slots__ = ("x", "y")            # 固定字段，不生成 __dict__
    def __init__(self, x, y): self.x, self.y = x, y

a, b = WithDict(1, 2), WithSlots(1, 2)
print(sys.getsizeof(a) + sys.getsizeof(a.__dict__))   # ≈ 48 + 104 = 152 字节
print(sys.getsizeof(b))                                # ≈ 48 字节

import asyncio, random, time
from dataclasses import dataclass, field

# ---------- ① 并发 + ② 限流（RPM 令牌桶） ----------
class RateLimiter:
    """按「每分钟请求数」平滑放行，不是粗暴的整分钟重置。"""
    def __init__(self, rpm: int):
        self.interval = 60.0 / rpm
        self._lock = asyncio.Lock()          # ⚠️ 跨 await 的临界区必须加锁
        self._next = 0.0

    async def acquire(self) -> None:
        async with self._lock:
            now = time.monotonic()
            wait = max(0.0, self._next - now)
            self._next = max(now, self._next) + self.interval
        if wait:
            await asyncio.sleep(wait)        # 锁外 sleep，避免持锁等待

# ---------- ⑤ 熔断 ----------
@dataclass
class CircuitBreaker:
    fail_threshold: int = 5
    cooldown: float = 30.0
    _fails: int = 0
    _open_until: float = 0.0

    def allow(self) -> bool:
        return time.monotonic() >= self._open_until

    def on_success(self) -> None:
        self._fails = 0

    def on_failure(self) -> None:
        self._fails += 1
        if self._fails >= self.fail_threshold:
            self._open_until = time.monotonic() + self.cooldown
            self._fails = 0

class CircuitOpen(RuntimeError): ...

# ---------- 组装 ----------
RETRYABLE = (asyncio.TimeoutError, ConnectionError)

class LLMClient:
    def __init__(self, rpm: int = 60, concurrency: int = 10):
        self.sem = asyncio.Semaphore(concurrency)
        self.limiter = RateLimiter(rpm)
        self.breaker = CircuitBreaker()

    async def chat(self, prompt: str, *, deadline: float | None = None,
                   retries: int = 3) -> str:
        if not self.breaker.allow():
            raise CircuitOpen("LLM 熔断中，直接走降级")

        last: BaseException | None = None
        for attempt in range(retries):
            try:
                async with self.sem:                     # ① 并发闸门
                    await self.limiter.acquire()         # ② 限流闸门
                    budget = 10.0 if deadline is None else deadline - time.monotonic()
                    if budget <= 0:
                        raise asyncio.TimeoutError("预算已耗尽")
                    async with asyncio.timeout(budget):  # ③ 超时闸门
                        res = await self._raw_call(prompt)
                self.breaker.on_success()
                return res
            except asyncio.CancelledError:
                raise                                    # ⚠️ 取消必须放行，不能当失败重试
            except RETRYABLE as e:                       # ④ 只重试可重试错误
                last = e
                self.breaker.on_failure()
                if attempt < retries - 1:
                    # 指数退避 + 抖动：避免所有失败请求同一时刻重试造成尖峰
                    backoff = min(8.0, 0.5 * 2 ** attempt) * (0.5 + random.random())
                    await asyncio.sleep(backoff)
            except Exception as e:                       # 4xx 这类不可重试，直接失败
                self.breaker.on_failure()
                raise
        raise last                                        # type: ignore[misc]

    async def _raw_call(self, prompt: str) -> str:
        await asyncio.sleep(0.2)
        return f"answer({prompt})"

# ---------- 批量调用：保持顺序 + 部分失败可降级 ----------
async def batch_chat(client: LLMClient, prompts: list[str]) -> list[str | None]:
    deadline = time.monotonic() + 30.0      # 整批共享总预算
    results = await asyncio.gather(
        *(client.chat(p, deadline=deadline) for p in prompts),
        return_exceptions=True,             # ⚠️ 不让单个失败炸掉整批
    )
    out: list[str | None] = []
    for p, r in zip(prompts, results):
        if isinstance(r, BaseException):
            print(f"降级：{p[:20]} → {r!r}")
            out.append(None)                # 这里可以换成缓存结果 / 小模型兜底
        else:
            out.append(r)
    return out                              # ✅ gather 保证顺序与输入一致
实战经验说明
并发不是越高越好LLM 厂商侧有配额，超了只会换成 429 + 退避，净吞吐反而下降
重试必须带抖动否则 N 个失败请求同时退避、同时重试，形成周期性尖峰
区分可重试错误429/5xx/超时可重试；400 参数错、401 鉴权错重试纯属浪费钱
流式请求重试要谨慎已输出部分 token 再重试会重复内容，需按「是否已输出」决定
Token 预算要前置估算用 tiktoken 预估，超限先截断上下文，而不是等厂商报错
必须埋点每次调用记录：模型、输入/输出 token、耗时、重试次数、是否命中缓存

⚠️ 幂等性：重试写操作前必须确认下游幂等。LLM 调用本身无副作用可以放心重试，但「调完就扣费 / 写库 / 发消息」的链路一定要带幂等键，否则重试会导致重复扣费。

29. 异常模型与错误分类：重试策略的地基 ​

ExceptionGroup 与 except*（3.11+）：TaskGroup 的配套设施

TaskGroup 里可能同时有多个子任务失败，单个异常装不下，所以 3.11 引入了 ExceptionGroup。except* 的语义和 except 完全不同：它会把组里匹配的异常挑出来处理，剩下的继续往上抛，而且多个 except* 分支可以同时命中。

python
import asyncio

async def main(prompts: list[str]):
    try:
        async with asyncio.TaskGroup() as tg:
            for p in prompts:
                tg.create_task(call_llm(p))
    except* TimeoutError as eg:
        # eg 是 ExceptionGroup，eg.exceptions 是本次匹配到的所有超时异常
        log.warning("超时 %d 个，准备降级", len(eg.exceptions))
    except* ValueError as eg:
        log.error("参数错误 %d 个，不重试", len(eg.exceptions))
    # 没被任何 except* 匹配的异常会原样继续抛出，不会被静默

# 想按条件切分一个 ExceptionGroup，用 .split() / .subgroup()
def is_retryable(exc: BaseException) -> bool:
    return isinstance(exc, (TimeoutError, ConnectionError))

retryable, fatal = eg.split(is_retryable)   # 返回两个 ExceptionGroup 或 None

⚠️ except 和 except* 不能在同一个 try 里混用，语法层面就禁止。另外 except* 的分支里不能用 break / continue / return 跳出。

AI 工程落地：把下游错误分成三类，驱动重试策略

python
class AppError(Exception):
    """所有自定义异常的基类，便于中间件统一兜底。"""
    retryable = False
    http_status = 500

class RetryableError(AppError):      # 下游抖动：超时、429、5xx、连接重置
    retryable = True
    http_status = 503

class FatalError(AppError):          # 自己的 bug：参数非法、prompt 模板错
    retryable = False
    http_status = 400

class DegradableError(AppError):     # 可降级：rerank 挂了就用原始召回顺序
    retryable = False
    http_status = 200


def classify(exc: BaseException) -> type[AppError]:
    """把第三方 SDK 五花八门的异常，归一成自己的三类语义。"""
    if isinstance(exc, (TimeoutError, ConnectionError)):
        return RetryableError
    status = getattr(exc, "status_code", None)
    if status == 429 or (isinstance(status, int) and status >= 500):
        return RetryableError
    if status in (400, 401, 403):
        return FatalError           # 重试只会浪费配额和时间
    return FatalError

⚠️ 重试前必须先分类。LLM 网关最常见的浪费是「把 400 参数错误也重试 3 次」——不仅不会成功，还把错误放大 3 倍打到下游，429 的时候更会直接雪崩。重试的前提是「这次失败是瞬时的」。

面试加分表述：「我们在 clients/ 层把各家 LLM SDK 的异常统一翻译成 RetryableError / FatalError / DegradableError 三类，重试装饰器只认 RetryableError，所以 400 这种参数错误会立刻失败并告警，而 429 和 5xx 走退避重试。异常全部用 raise ... from e 保留原始栈，对外响应时再 from None 掉内部细节。用了 TaskGroup 之后批量任务的异常是 ExceptionGroup，我们用 except* 分别处理超时和参数错误——这比以前 gather 拿一个 list 回来自己 isinstance 判断清楚太多了。」

④ 并发度怎么断言：计数器比耗时更可靠

题 3 的信号量限流只看总耗时是测不准的（CI 机器负载会让耗时忽上忽下）。正确做法是直接数同时在飞的任务数：

async def test_concurrency_never_exceeds_limit():
    inflight = 0
    peak = 0

    async def fake_call(prompt: str) -> str:
        nonlocal inflight, peak
        inflight += 1
        peak = max(peak, inflight)
        await asyncio.sleep(0)      # 交出控制权，制造真实的交错时机
        inflight -= 1
        return prompt.upper()

    with patch("app.llm.call_one", fake_call):
        results = await batch_call([f"p{i}" for i in range(50)], limit=5)

    assert len(results) == 50                         # 不丢任务
    assert results[0] == "P0" and results[-1] == "P49"  # ✅ 顺序与入参一致

题 1：GIL 是什么？为什么有它？能不能去掉？ ​

精简口述答案（90 秒版）

「GIL 是 CPython 解释器级别的一把互斥锁，保证同一时刻只有一个线程在执行 Python 字节码。它存在的根本原因是 CPython 的内存管理基于引用计数，而引用计数的加减不是原子操作——没有 GIL 的话，两个线程同时改一个对象的 refcount 会导致计数错乱，对象被提前释放或永久泄漏。GIL 是最简单有效的保护方式，代价是多线程无法利用多核做 CPU 密集计算。

要特别区分三点：第一，GIL 是 CPython 的实现细节，不是 Python 语言规范，Jython、IronPython 就没有；第二，GIL 不影响 IO 密集场景，因为线程在等 IO 时会主动释放 GIL，所以多线程爬虫、多线程调接口依然有效；第三，GIL 不等于线程安全，count += 1 会被编译成多条字节码，中间可能被切换，所以共享变量依然要加锁。

能不能去掉？Python 3.13 通过 PEP 703 提供了实验性的 free-threaded 构建，可以真正关掉 GIL，3.14 转为正式支持。代价是单线程性能有几个点的损耗、大量 C 扩展需要重新适配，而且原先靠 GIL『偷来』的原子性全部失效，并发代码必须显式加锁。」

追问答题要点
GIL 什么时候会被释放？① 执行 IO 时主动释放；② 时间片到（默认 5ms，sys.getswitchinterval()）；③ 调用 time.sleep；④ C 扩展显式 Py_BEGIN_ALLOW_THREADS（numpy 大矩阵运算就是这么做的）
有 GIL 为什么还要加锁？GIL 只保证「单条字节码」不被打断。count += 1 是 LOAD/ADD/STORE 多条字节码，可以用 dis.dis 展示，中间切换就会丢更新
多线程在 Python 里还有用吗？有。IO 密集完全有效；另外调用释放了 GIL 的 C 扩展（numpy、部分加解密库）时也能真并行
GIL 切换机制有变化过吗？3.2 之前是每 100 条字节码检查一次，之后改为 5ms 时间片。更值得说的是「护航效应」：CPU 线程和 IO 线程混在一个进程时，IO 线程延迟被放大
去掉 GIL 后有什么新风险？真实的 data race 出现。以前多线程 list.append 还算安全，no-GIL 下必须加锁；单线程性能有损耗；C 扩展兼容性是最大阻力
实际项目中怎么绕开 GIL？CPU 密集走多进程 / 进程池；向量化计算交给 numpy 等会释放 GIL 的库；更重的任务直接下沉到 C++/Rust 扩展或独立服务

✅ 项目关联话术：「我们的 AI 服务一开始是用多线程做批量文档解析，8 核机器 CPU 只跑到 110%，这就是典型的 GIL 卡点。改成『解析走 ProcessPoolExecutor、IO 走 asyncio』的混合模型后，吞吐提升了大约 5 倍。还有个更隐蔽的问题：有个接口在同步代码里用 pandas 处理大表，既占 GIL 又堵事件循环，导致整个服务的 P99 从 200ms 恶化到 3 秒，监控上表现为 P50 正常、P99 爆炸——定位到之后我们把这类计算全部挪进进程池隔离。」

题 2：进程、线程、协程在 Python 里怎么选？ ​

精简口述答案（90 秒版）

「一句话决策：CPU 密集用多进程，IO 密集用协程，必须兼容老同步库时用线程池兜底。

原因是三者的开销和并行能力完全不同。进程有独立的解释器和 GIL，能真正吃多核，但启动开销在百毫秒级，参数要 pickle 序列化，内存也会翻倍。线程共享内存、切换成本中等，但受 GIL 限制，只在 IO 等待或调用释放 GIL 的 C 扩展时才有收益。协程是单线程内的用户态切换，一个协程只占几 KB 栈空间，切换开销是纳秒级，单机轻松撑几万并发，但它有个硬前提——全链路必须是非阻塞的，一旦中间有一个同步阻塞调用，整个事件循环就被卡死。

实际项目基本都是混合模型：外层 asyncio 做 IO 编排（调 LLM、查向量库、读 Redis），CPU 密集部分丢给 run_in_executor + 进程池，遗留的同步 SDK 丢给 asyncio.to_thread 的线程池。这样既吃满多核，又保持高并发。

我自己的判断流程是三问：这个任务在等 CPU 还是等 IO？用的库有没有异步版本？并发量级是几十还是几万？」

追问答题要点
协程为什么比线程轻？线程栈默认 MB 级且由内核调度（切换需陷入内核态、保存寄存器上下文），协程只保存少量帧对象在堆上，用户态切换，无系统调用
一个 asyncio 服务能开多少并发？受限于 fd 上限、内存、下游承载能力，而非协程本身。几万协程很常见，但一定要用 Semaphore 限制对下游的实际并发
既然协程好，为什么还要线程池？生态里大量库只有同步版本（老 ORM、厂商 SDK、OCR 库），没法重写时只能用线程池隔离阻塞
多进程为什么不是免费的？三笔账：启动开销（spawn 百毫秒级）、pickle 序列化开销、内存翻倍。传大 DataFrame 时可能 80% 时间花在搬数据上
线程池大小怎么定？不是越大越好。公式思路：线程数 ≈ 目标并发 × 阻塞时长 / 可接受延迟；且必须按下游隔离成多个池 + 配队列上限和拒绝策略
怎么验证自己选对了？压测看指标：CPU 跑不满 → GIL 或阻塞问题；CPU 满但 QPS 低 → 真 CPU 瓶颈；内存暴涨 → 并发无限流

✅ 项目关联话术：「我们 RAG 服务的最终形态是三层：最外层 asyncio 并发调用检索和 LLM；文档切分、向量归一化这类 CPU 活走全局 ProcessPoolExecutor，启动时建一次、关闭时 shutdown，绝不每次请求新建；老的 OCR SDK 只有同步版本，我们给它单独配了一个 8 线程的池，和老数据库 SDK 的池完全隔离，谁慢谁自己排队、不会互相传染。另外 traceId 这类 contextvars 在 run_in_executor 里会丢，我们封了一个 run_sync() 内部用 copy_context().run() 透传，保证日志链路不断。」

题 3：Python 的可变对象和不可变对象有什么区别？函数默认参数为什么不能用可变对象？ ​

精简口述答案（90 秒版）

「首先要纠正一个心智模型：Python 里变量是贴在对象上的名字，不是装东西的盒子。赋值永远是「让名字指向另一个对象」，不是「把值搬进变量」。

在这个前提下，可变对象（list、dict、set、自定义类实例）支持原地修改，id 不变；不可变对象（int、str、tuple、frozenset）任何「修改」都是创建新对象。最典型的对比是 b = b + [4] 和 b += [4]：前者创建新 list 并让 b 指向它，原对象不受影响；后者等价于 b.extend([4])，是原地修改，所有指向这个 list 的名字都会看到变化。

默认参数的坑在于：默认值对象在函数定义时只创建一次，之后所有调用共享它。所以 def f(items=[]) 里的那个空列表是函数对象的一部分，存在 f.__defaults__ 里，第一次调用往里 append，第二次调用就不是空列表了。正确写法是默认值用 None，在函数体里判空再创建。ruff 的 B006 规则可以静态拦住这类代码，建议直接配进 CI。

补充一个容易混的点：不可变容器装可变对象，内部依然可变。t = (1, [2, 3]) 这个 tuple 不可变指的是「它的元素引用不能换」，但 t[1].append(4) 完全合法——所以这种 tuple 不可哈希，不能做字典键。」

连环追问链

追问答题要点
is 和 == 的区别？is 比 id（是否同一对象），== 比值（调 __eq__）。小整数缓存（-5~256）和字符串驻留会让 is 偶然为 True，所以只有和 None/单例比较才用 is
a += b 和 a = a + b 对 list 有区别吗？有。+= 调 __iadd__ 原地扩展，共享该对象的其他名字都会看到；a + b 产生新对象。对 tuple/str 则没区别（都只能新建）
为什么可变默认参数的问题这么隐蔽？单次调用、单元测试都正常，只有在「被多次调用」时才暴露，表现为数据莫名叠加。而且常见于「缓存历史消息」这类 AI 场景
哪些对象可以做字典键？可哈希的（实现 __hash__ 且不可变）。装了 list 的 tuple 不可哈希；自定义类默认按 id 哈希，重写 __eq__ 必须同时重写 __hash__
函数参数传递是值传递还是引用传递？都不是，是「对象引用的传值」（call by object reference）。重新赋值不影响调用方，原地修改会影响
工程上怎么系统性避免？① 默认值一律 None；② ruff 开 B006/B008；③ 配置类用 frozen=True 的 dataclass 或 pydantic 的不可变模型；④ 跨边界传数据时明确「谁拥有这份数据」

✅ 项目关联话术：「这个坑我们在 Agent 的会话管理上真踩过：def chat(msg, history=[]) 想让 history 默认空列表，结果所有用户共用了同一个 list——A 用户的对话被追加到了 B 用户的上下文里，既串了数据又把 prompt 撑爆导致 token 超限报错。改成 history=None + 函数内 history = history or [] 之后立刻就好了，同时在 CI 的 ruff 配置里打开了 B006，彻底杜绝同类问题。另外我们所有配置对象都用不可变模型，避免某个模块偷偷改了全局配置导致别的模块行为异常。」

题 4：深拷贝和浅拷贝的区别？循环引用怎么处理？ ​

精简口述答案（90 秒版）

「有三个层次，必须区分清楚：

赋值 b = a 完全不拷贝，只是多一个名字指向同一对象，b is a 为 True。

浅拷贝 copy.copy(a) 或 a[:] / list(a) / dict(a)，创建新的外层容器，但内部元素仍是原来的引用。所以改嵌套层会互相影响。

深拷贝 copy.deepcopy(a) 递归复制整棵对象树，新旧完全独立。

循环引用是深拷贝必须解决的问题：如果 a 里引用了 b，b 里又引用 a，朴素递归会无限栈溢出。deepcopy 内部维护一个 memo 字典，键是原对象的 id，值是已经创建的副本——每次递归前先查 memo，命中就直接返回已有副本，这样环就被正确地复制成环而不是无限展开。

工程上要特别注意 deepcopy 是性能杀手：它要遍历整棵对象树，还要维护 memo，对大配置对象、大 DataFrame、带模型句柄的对象可能慢几个数量级，甚至因为复制了不该复制的东西（socket、锁、线程池）直接报错。更好的做法是让对象不可变、或者只拷贝真正需要隔离的那一层。需要自定义拷贝行为时可以实现 __deepcopy__ 和 __copy__。」

连环追问链

追问答题要点
浅拷贝有哪几种写法？copy.copy(x)、切片 x[:]、list(x)/dict(x)/set(x)、x.copy()。效果一致，都只复制一层
不可变对象 deepcopy 会怎样？直接返回原对象（没必要复制），这是 deepcopy 的优化之一。所以 deepcopy(("a", 1)) is ("a", 1) 可能为 True
怎么自定义拷贝行为？实现 __copy__(self) 和 __deepcopy__(self, memo)。典型用途：让对象在 deepcopy 时复用模型句柄/连接池而不是复制
deepcopy 会调 __init__ 吗？不会。默认走 __reduce_ex__，直接创建对象并填充 __dict__，所以 __init__ 里的副作用不会重放
什么时候必须深拷贝？要把一份数据交给可能修改它的下游，且不能影响原始数据时。比如把 base prompt 模板交给多个 Agent 各自改写
有没有更轻的替代方案？① 用不可变数据结构（frozen dataclass、tuple）；② 只手动拷贝需要隔离的字段；③ 用 model_copy(deep=True) 这类框架提供的精确拷贝；④ 用 JSON 序列化反序列化（仅限纯数据）

✅ 项目关联话术：「我们做多 Agent 编排时，每个 Agent 要基于同一份基础上下文做自己的改写。最初直接传引用，结果 A Agent 改了消息列表，B Agent 看到的上下文就被污染了，输出完全乱掉。改成深拷贝后正确了，但性能又出问题——上下文里挂着检索到的文档全文，一次 deepcopy 要几十毫秒，QPS 上来之后 CPU 直接打满。最终方案是把上下文拆成『不可变的共享部分（文档、系统 prompt）』和『每个 Agent 独立的可变部分（消息列表）』，只拷贝后者，耗时降到微秒级。」

题 5：装饰器的原理是什么？为什么要用 functools.wraps？ ​

精简口述答案（90 秒版）

「装饰器的本质就一行等价代码：@deco 加在 def f 上，等于 f = deco(f)。它利用了 Python 里函数是一等公民这个特性——函数可以作为参数传入、作为返回值返回、还能通过闭包携带状态。

有三个关键点：

第一，装饰器在函数定义时就执行了，不是调用时。模块一 import，装饰器外层代码就跑了一遍。所以装饰器里不要放耗时操作或有副作用的初始化。这也是 @app.get("/x") 这类注册型装饰器能工作的原理——import 阶段就把路由注册进去了。

第二，不加 functools.wraps 会丢元信息。包装后的函数实际是 wrapper，它的 __name__ 是 'wrapper'、__doc__ 是 None、__annotations__ 是空的、__wrapped__ 也没有。日志里全是 wrapper 很难排查，更致命的是像 FastAPI、pydantic、Celery 这些依赖类型注解做运行时反射的框架会直接失效——FastAPI 拿不到注解就没法做参数校验和生成 OpenAPI 文档。

第三，带参装饰器是三层函数：最外层接装饰器参数返回真正的装饰器，中间层接被装饰函数返回 wrapper，最内层才是运行时逻辑。所以 @retry 和 @retry() 不是一回事，前者会把函数本身当成第一个参数传进去。」

连环追问链

追问答题要点
functools.wraps 具体拷了什么？拷 __module__、__name__、__qualname__、__doc__、__annotations__，更新 __dict__，并设置 __wrapped__ 指向原函数（inspect.signature 靠它拿到真实签名）
多个装饰器叠放的顺序？由下往上包装，由上往下执行。@a @b def f 等于 f = a(b(f))。工程规范：注册在最上，限流次之，重试再次，缓存最靠近业务函数——否则重试会穿透缓存反复打下游
怎么写同时支持同步和异步的装饰器？用 inspect.iscoroutinefunction(fn) 分支，返回 async def 或 def 两个不同的 wrapper。不判断的话同步 wrapper 包异步函数会返回未 await 的协程对象，计时恒为 0 并抛 coroutine was never awaited
类装饰器和装饰类有什么区别？类装饰器是用类的 __call__ 当装饰器（天然带状态，用 functools.update_wrapper）；装饰类是装饰器参数是 class，常用于单例、自动注册
怎么给装饰器加「可开关」能力？wrapper 里读配置/环境变量决定是否走增强逻辑；或在 __wrapped__ 上暴露原函数，让测试可以绕过装饰器
装饰器会影响性能吗？每层增加一次函数调用开销（几百纳秒级）。热点路径上叠 5 层以上要注意；更大的风险是装饰器里误放了同步 IO 或 deepcopy

✅ 项目关联话术：「我们所有 LLM 调用都通过一个 @llm_call 装饰器统一接管：计时、token 统计、重试退避、异常上报、traceId 透传。两个踩坑换来的经验：一是最初没加 functools.wraps，FastAPI 拿不到被装饰函数的类型注解，接口参数校验直接失效、OpenAPI 文档里参数全空，排查了小半天；二是装饰器栈顺序排错了——缓存装在重试外面，导致重试直接穿透缓存反复打 LLM，当天的 token 成本翻了一倍。现在我们把顺序写进了规范：路由注册最外、限流、重试、缓存最里。」

题 6：生成器和迭代器有什么区别？yield 的作用是什么？ ​

精简口述答案（90 秒版）

「先理清三个概念的包含关系：可迭代对象 ⊃ 迭代器 ⊃ 生成器。

可迭代对象只需要实现 __iter__，比如 list；迭代器要同时实现 __iter__ 和 __next__，并且耗尽后不能重来；生成器是 Python 帮你自动生成的迭代器——函数体里只要出现 yield，调用它就不执行函数体，而是返回一个生成器对象。

yield 的核心作用是暂停并保存执行状态。执行到 yield 时，把值交出去，同时把局部变量、指令指针完整保留在生成器的栈帧里；下次 next() 从暂停处继续。这就是协程的底层基础。

生成器最大的价值是惰性求值：内存占用是 O(1) 而不是 O(n)。读 10GB 日志文件，用 readlines() 会直接 OOM，用生成器逐行 yield 则常驻内存只有几 KB。

还有个容易被忽略的双向通信能力：gen.send(value) 可以把值送进生成器，让 yield 表达式求值为这个值；gen.throw(exc) 往里面抛异常；gen.close() 在暂停点注入 GeneratorExit。生成器里 return value 不会作为迭代项产出，而是塞进 StopIteration.value，yield from 会把它作为表达式的值。

最后一个常见坑：生成器只能消费一次，第二次遍历得到空。需要多次遍历就得用 list 物化，或者写成一个每次返回新生成器的函数。」

连环追问链

追问答题要点
可迭代对象和迭代器怎么区分？iter(x) is x 为 True 就是迭代器。list 是可迭代但不是迭代器（每次 iter() 给一个新迭代器，所以能重复遍历）
for 循环底层做了什么？it = iter(obj) → 反复 next(it) → 捕获 StopIteration 退出。这就是为什么在业务代码里不要吞掉 StopIteration
生成器表达式和列表推导的区别？(x for x in ...) 惰性、内存 O(1)、只能消费一次；[x for x in ...] 立刻物化。处理大数据流一律用前者
生成器怎么做管道？多个生成器串联：read() → parse() → filter() → batch()，每层只做一件事，整条链保持惰性，内存恒定。这是 ETL / 向量化入库的标准写法
yield from 有什么用？委托给子生成器，并透传 send/throw/返回值。扁平化嵌套结构和「旧式协程」都靠它，3.5 之后协程场景已被 async/await 取代
生成器怎么保证资源释放？用 try/finally 包住，close() 或 GC 时 GeneratorExit 会触发 finally；更稳妥的是消费方用 contextlib.closing/aclosing，防止提前 break 导致迟迟不清理

✅ 项目关联话术：「我们做知识库入库时，单个 PDF 解析出来有几十万个文本块。最初一次性 load 成 list 再切分，8G 内存的容器直接 OOM。重构成生成器管道：读取 → 清洗 → 切块 → 按 batch 聚合 → 调 Embedding → 写向量库，每层都是生成器，常驻内存稳定在 200MB 以内，还能边读边入库，首批数据可用时间从 20 分钟降到 30 秒。有个细节值得一提：中间加了一个 batched() 生成器把单条聚成 64 条一批，因为 Embedding 接口按批调用吞吐高得多——这个函数 3.12 的 itertools.batched 已经内置了。」

题 7：asyncio 的事件循环是怎么跑起来的？协程为什么比线程轻？ ​

精简口述答案（90 秒版）

「事件循环本质是一个 while True 的调度器，一轮迭代做四件事：

第一，从 ready 队列取出所有就绪的回调并执行到下一个挂起点；第二，计算最近的定时器到期时间，作为 IO 多路复用的超时参数；第三，调用 select/epoll/kqueue 等待 IO 事件，有事件就把对应回调放回 ready 队列；第四，处理到期的定时器。然后进入下一轮。

关键在于：协程执行到 await 一个未完成的 awaitable 时会把控制权交回事件循环，并登记「我在等什么」。事件循环趁这个空档去跑别的协程，等 IO 就绪再回来恢复它。所以并发的来源是「等待时间重叠」，而不是「同时执行」——它始终是单线程。

协程比线程轻主要是三点：第一，栈空间，线程栈默认 MB 级别，协程只是堆上的几个帧对象，几 KB；第二，切换成本，线程切换由内核调度，要陷入内核态、保存恢复寄存器上下文，微秒级，协程是用户态的函数调用返回，纳秒级；第三，无锁，协程切换点是确定的（只在 await 处），同一个事件循环内不会出现线程那种任意指令间的抢占，大部分共享状态读写天然安全。

但要注意最后这点有边界：跨 await 的临界区仍然需要 asyncio.Lock，因为中间会让出控制权，别的协程可能插进来改状态。」

追问答题要点

题 8：在协程里调用一个同步阻塞函数会发生什么？怎么解决？ ​

精简口述答案（90 秒版）

「会卡死整个事件循环。因为事件循环是单线程的，同步阻塞函数不会把控制权交回去，这段时间内所有协程都停摆——不只是当前这个请求慢，是整个服务的所有请求一起卡住。

最典型的就是在 async def 里写了 time.sleep(1)。看起来只是慢了 1 秒，但实际上这 1 秒内服务处理不了任何其他请求。换成 await asyncio.sleep(1) 才是真正的让出控制权。同类的还有 requests.get、同步的 pymysql、open().read() 读大文件、同步 Redis 客户端，以及 CPU 密集的计算。

解决方案有三个层次，优先级从高到低：

第一，换原生异步库——requests 换 httpx/aiohttp，pymysql 换 asyncmy/asyncpg，redis 换 redis.asyncio。这是最彻底的。

第二，丢线程池——await asyncio.to_thread(fn, *args)，适合没有异步版本的阻塞 IO。注意默认 executor 的线程数是 min(32, cpu_count+4) 且全局共享，关键路径最好用 run_in_executor 配独立线程池做隔离。

第三，丢进程池——loop.run_in_executor(process_pool, fn, ...)，这是 CPU 密集任务的唯一正解，线程池对 CPU 密集没用，因为还是被 GIL 卡着。

另外推荐在 CI 里开 ruff 的 ASYNC 规则组，它能静态查出异步函数里的 time.sleep、requests.get、open() 这类调用。」

题 9：gather、as_completed、wait、TaskGroup 有什么区别？异常怎么处理？ ​

精简口述答案（90 秒版）

「按『结果顺序』和『异常语义』两个维度区分：

gather 最常用，返回结果列表且顺序与传入顺序一致（不是完成顺序）。默认第一个异常会立刻向上抛，但其余任务不会被取消，仍在后台跑，它们的结果就丢了。加 return_exceptions=True 后异常会作为结果项返回，整批不中断——批量调 LLM 这种允许部分失败的场景基本都用这个。

as_completed 返回一个迭代器，谁先完成先 yield，适合流式处理、首个结果优先返回的场景。但它丢失了与输入的对应关系，想知道「这是哪个任务的结果」得自己包装；而且每个 await 都要单独 try。

wait 更底层，返回 (done, pending) 两个 Task 集合，支持 FIRST_COMPLETED / FIRST_EXCEPTION / ALL_COMPLETED 三种返回条件。它不会抛异常，异常留在 Task 里要自己取；pending 的任务也要自己决定取消还是继续。「谁先回用谁、其余取消」的竞速场景用它最合适。

TaskGroup（3.11+）是现在推荐的默认选择：async with 结构化并发，退出时等全部完成，任一失败自动取消所有兄弟任务并抛 ExceptionGroup，用 except* 按类型分别处理。它从根本上杜绝了任务泄漏。

另外两个配套工具：asyncio.Semaphore 控并发上限，asyncio.timeout / wait_for 控超时。」

连环追问链

追问答题要点
gather 默认抛异常后，其他任务怎么样了？仍在后台运行，不会被取消，结果被丢弃。这是常见的资源泄漏点。需要取消就改用 TaskGroup
gather 的结果顺序是完成顺序吗？不是，是传入顺序。这点很关键，批量处理时可以直接 zip(inputs, results) 对应
return_exceptions=True 有什么副作用？CancelledError 也会被当成结果返回，可能掩盖取消语义。处理结果时要用 isinstance(r, BaseException) 判断并单独识别取消
as_completed 怎么知道结果属于哪个输入？把任务包成 async def wrap(i, coro): return i, await coro，或直接 for fut in as_completed(tasks) 配合 Task 到输入的映射字典
怎么实现「取最快的一个，其余取消」？done, pending = await asyncio.wait(tasks, return_when=FIRST_COMPLETED)，然后对 pending 逐个 cancel() 并 await gather(*pending, return_exceptions=True) 等清理完成
为什么推荐 TaskGroup？结构化并发：作用域结束前所有子任务必定终结，没有「忘了 await 的孤儿 Task」；失败自动扇出取消；ExceptionGroup 保留所有异常而非只有第一个

✅ 项目关联话术：「我们批量调 LLM 用的是 gather(..., return_exceptions=True) 加 Semaphore(10) 限流：拿到完整的成功结果加失败清单，失败的走小模型兜底降级，整体可用性从 97% 提到 99.9%，而且 gather 保证顺序和输入一致，后续 zip 对齐很方便。检索侧用的是 as_completed，向量库和 ES 并发查，谁先回就先把结果推给前端，首屏时间减少约 40%。多路模型竞速的场景用 wait(FIRST_COMPLETED)，拿到最快的那个之后记得把 pending 全部 cancel 掉，不然会白白烧 token。新代码我们统一改用 TaskGroup，因为它能保证不漏任务。」

题 10：协程的取消是怎么实现的？CancelledError 有什么特殊性？ ​

精简口述答案（90 秒版）

「task.cancel() 不会立刻杀死协程，它只是打一个标记，等协程执行到下一个 await 挂起点时，事件循环往里面抛一个 CancelledError。异常逐层向上传播，沿途的 finally 和 __aexit__ 会依次执行，给你清理资源的机会，最后 Task 状态变为 cancelled。

由此推出两个重要结论：

第一，纯 CPU 死循环的协程取消不掉，因为它永远到不了 await 点。需要在循环里插 await asyncio.sleep(0) 主动让出。

第二，如果协程把 CancelledError 吞掉且不重新抛出，取消就失败了。这会导致服务无法优雅关闭、超时控制失效。所以 Python 3.8 把 asyncio.CancelledError 的基类从 Exception 改成了 BaseException，专门防止被业务代码的 except Exception 误伤。但 except BaseException、裸 except:、以及 gather(return_exceptions=True) 仍然能拦住它，写通用重试/兜底逻辑时必须显式 except asyncio.CancelledError: raise 放行。

正确姿势是：捕获它只为了做清理（回滚事务、关连接、记录已消耗的 token），清理完一定要 raise。

超时本质上就是「定时取消」。3.11 之前用 wait_for，3.11 之后推荐 async with asyncio.timeout(n)，能包住一整段流程；timeout_at 接受绝对截止时间，适合跨多层透传同一个 deadline，避免每层各写 3 秒最后累加成 9 秒。如果有一段副作用绝对不能半途而废（比如扣费），用 asyncio.shield 保护起来。」

连环追问链

追问答题要点
为什么 3.8 要把它改成 BaseException？避免业务的 except Exception 误吞取消信号，导致服务无法优雅关闭、超时失效
finally 里能不能再 await？可以，但要小心：清理期间如果再次被取消会更麻烦。关键清理用 asyncio.shield 包住，或者给清理设独立的短超时
shield 的真实语义？外层取消时，被 shield 的内部任务继续运行，只是外层的 await 立刻抛 CancelledError。适合扣费、幂等写入这类必须完成的副作用，滥用会导致资源迟迟不释放
服务优雅关闭怎么做？捕获 SIGTERM → 停止接收新请求 → 给在途任务一个宽限期 → 超时后统一 cancel() 并 gather(..., return_exceptions=True) 等清理 → 关闭连接池
wait_for 超时后任务一定停了吗？不一定，它只是发起取消，协程可能还在跑 finally 清理。超时后不要立刻复用它持有的连接等资源
取消和超时在链路上怎么统一？入口算出绝对 deadline，用 timeout_at 向下透传；每层只检查剩余预算，不再各自设固定超时

✅ 项目关联话术：「我们 LLM 流式接口里，客户端断开会让 FastAPI 取消这个协程，异步生成器收到 CancelledError。我们必须在这里关掉上游的流式连接、并且按已经产出的 token 做计费，所以在 finally 里补了这两段逻辑——之前没做，既漏计费又泄漏了上游连接。另一个坑是我们的通用重试装饰器最初写的是 except Exception，Python 3.8 之后虽然抓不到取消了，但 gather(return_exceptions=True) 那层还是把它当普通失败重试，导致服务 SIGTERM 之后迟迟退不掉、K8s 直接 SIGKILL。现在统一在重试逻辑最前面显式 except asyncio.CancelledError: raise。」

题 11：上下文管理器的原理是什么？__exit__ 返回值有什么讲究？ ​

精简口述答案（90 秒版）

「with 语句依赖的是上下文管理器协议：__enter__ 和 __exit__。

with obj as x: 等价于：调用 obj.__enter__() 把返回值赋给 x，然后在 try/finally 里执行代码块，无论正常结束还是抛异常，都会调用 obj.__exit__(exc_type, exc_val, tb)。它的核心价值是把「获取-释放」成对的逻辑收敛到一处，彻底避免忘记释放。

__exit__ 的返回值是个高频考点：返回 True 表示异常已被处理、吞掉不再向外抛；返回 False 或 None（默认）表示异常继续传播。注意 Python 里不写 return 就是返回 None，所以默认行为是传播异常——这通常是对的。不小心写成 return True 会把所有异常静默吞掉，是非常危险的 bug。

写法上有两种：实现类的双下方法，或者用 @contextlib.contextmanager 装饰一个生成器——yield 之前是 __enter__，yield 之后是 __exit__，要捕获异常就用 try/except/finally 包住 yield。后者更简洁，但每次只能用一次（生成器会耗尽）。

异步版本是 __aenter__ / __aexit__，配 async with，用 @asynccontextmanager 写生成器版本。FastAPI 的 lifespan 就是这么管理连接池的。

标准库里还有几个很实用的：contextlib.suppress 忽略指定异常、closing 给只有 close() 的对象补协议、ExitStack 动态管理数量不定的资源、nullcontext 做「可选的 with」。」

连环追问链

追问答题要点
__exit__ 的三个参数是什么？exc_type、exc_val、exc_tb。正常退出时都是 None。可以据此区分「成功提交」还是「异常回滚」
@contextmanager 里怎么捕获异常？try: yield resource except Exception: rollback(); raise finally: close()。注意不 raise 就相当于返回 True 吞掉异常
with 里 return / break 会执行 __exit__ 吗？会。它等价于 try/finally，任何退出路径都触发
管理数量不定的资源怎么办？with ExitStack() as stack: files = [stack.enter_context(open(f)) for f in paths]，退出时逆序全部关闭
同一个上下文管理器能嵌套/重入吗？类实现的可以设计成可重入；@contextmanager 生成的不可重用，因为生成器只能跑一次。需要复用就把它包成工厂函数
异步版本要注意什么？__aexit__ 里的清理如果再被取消会很麻烦，关键清理要 shield；异步生成器配 contextlib.aclosing，防止消费方 break 后迟迟不释放

✅ 项目关联话术：「我们用 @asynccontextmanager 封了一个 llm_session()：进入时申请 Semaphore 配额、记录开始时间、绑定 traceId，退出时统计 token 消耗、上报耗时指标、释放配额。这样所有调用点都是三行代码，不会有人忘记释放配额——之前手写 acquire/release 时，异常路径上漏了 release，跑几个小时后 Semaphore 配额被耗尽，服务直接全部卡死在等信号量。还有个坑是有同事在 __exit__ 里写了 return True，把下游的超时异常全吞了，表现为接口返回空结果但没有任何错误日志，排查了很久——现在 code review 会专门盯这一行。」

题 12：什么是闭包？LEGB 规则是什么？循环里创建闭包为什么会出问题？ ​

精简口述答案（90 秒版）

「闭包是「函数 + 它捕获的外层作用域变量」。内层函数引用了外层函数的局部变量，外层函数返回后这些变量依然存活，被保存在函数对象的 __closure__ 里。

名字查找遵循 LEGB 顺序：Local 局部 → Enclosing 外层函数 → Global 模块全局 → Builtin 内置。要注意赋值会创建局部变量，所以想改外层函数的变量要用 nonlocal，想改模块全局变量要用 global，否则会报 UnboundLocalError——这个报错特别反直觉：明明外面有这个变量，但因为函数体里有赋值语句，整个函数里它就被认定为局部变量了。

循环里创建闭包的经典坑是延迟绑定：闭包捕获的是变量本身，不是创建时的值。所以 [lambda: i for i in range(3)] 里三个 lambda 全都返回 2，因为它们共享同一个 i，而循环结束时 i 已经是 2 了。

三种解法：第一，用默认参数在定义时固定值 lambda i=i: i；第二，用 functools.partial(fn, i)；第三，外面再包一层函数制造独立作用域。

这个坑在 AI 工程里有个很典型的触发场景：批量注册 Function Calling 的工具函数时用循环创建 handler，结果所有工具名都指向最后一个，调用任何工具都执行同一个函数。」

追问答题要点
怎么看一个函数捕获了什么？fn.__closure__ 是 cell 对象元组，fn.__code__.co_freevars 是被捕获的变量名。配合看最直观
nonlocal 和 global 的区别？nonlocal 绑定到最近的外层函数作用域（不能是全局）；global 绑定到模块级。都只是声明「这个名字不是局部的」
为什么会 UnboundLocalError？函数体内任何位置有赋值，该名字整个函数内都是局部的。读在赋值之前就会报错。解法是 nonlocal/global，或换个名字
类里的推导式为什么访问不到类属性？推导式有自己的作用域且不包含类作用域（3.12 对此有改动但原则仍在）。解法是在推导式外先存成局部变量
闭包会造成内存泄漏吗？会。闭包持有外层变量的强引用，如果捕获了大对象（整个 DataFrame、模型实例），这些对象就一直不释放。只捕获真正需要的小参数
闭包和类谁更合适？状态少、逻辑单一用闭包更轻；状态多、需要多个方法操作同一状态用类更清晰。装饰器通常用闭包，带复杂状态的装饰器可以用类

✅ 项目关联话术：「我们注册 Agent 工具时踩过延迟绑定的坑：用 for cfg in tool_configs 循环创建 handler 闭包，结果所有工具注册上去都指向最后一个配置，模型调『查天气』实际执行的是『查库存』，而且没有任何报错，纯靠用户反馈才发现。改成 lambda cfg=cfg: ... 固定默认参数后解决。后来我们干脆规范成用 functools.partial 显式传参，可读性更好也不容易被 review 漏掉。还有一次是闭包捕获了整个检索结果列表，几百个注册的 handler 把几百份文档全留在内存里，常驻内存涨了 2G——定位之后只捕获文档 ID，内存立刻降下来了。」

题 1：实现「计时 + 日志 + 重试」三合一带参装饰器（同步 / 异步双兼容） ​

这是 AI 工程里最高频的一道手撕题。调 LLM、调向量库、调下游 HTTP，全都需要「超时重试 + 耗时埋点」，而业务里同步函数和协程函数混用，装饰器必须两种都能包。

核心实现

python
import asyncio
import functools
import inspect
import logging
import random
import time
from typing import Callable, TypeVar, Any

logger = logging.getLogger(__name__)
F = TypeVar("F", bound=Callable[..., Any])


def traced_retry(
    *,
    retries: int = 3,
    base_delay: float = 0.5,
    max_delay: float = 8.0,
    jitter: bool = True,
    exceptions: tuple[type[BaseException], ...] = (Exception,),
    name: str | None = None,
) -> Callable[[F], F]:
    """带参装饰器：三层结构 = 配置层 -> 装饰层 -> 执行层。

    - 自动识别被装饰对象是协程函数还是普通函数，分别返回 async / sync 包装
    - 指数退避 + 随机抖动，避免重试风暴
    - 只重试 exceptions 里声明的异常；CancelledError 永不重试
    """

    def _sleep_seconds(attempt: int) -> float:
        delay = min(base_delay * (2 ** attempt), max_delay)
        if jitter:
            # full jitter：在 [0, delay] 之间随机，彻底打散同时重试的请求
            delay = random.uniform(0, delay)
        return delay

    def decorator(func: F) -> F:
        label = name or func.__qualname__

        if inspect.iscoroutinefunction(func):

            @functools.wraps(func)
            async def async_wrapper(*args, **kwargs):
                started = time.perf_counter()
                last_exc: BaseException | None = None
                for attempt in range(retries + 1):
                    try:
                        result = await func(*args, **kwargs)
                    except asyncio.CancelledError:
                        # 取消是协作信号，不是失败，必须原样向上抛
                        logger.info("%s cancelled after %.3fs", label,
                                    time.perf_counter() - started)
                        raise
                    except exceptions as exc:
                        last_exc = exc
                        if attempt >= retries:
                            break
                        wait = _sleep_seconds(attempt)
                        logger.warning(
                            "%s failed (%s), retry %d/%d in %.2fs",
                            label, exc.__class__.__name__,
                            attempt + 1, retries, wait,
                        )
                        await asyncio.sleep(wait)
                    else:
                        logger.info("%s ok in %.3fs (attempt=%d)", label,
                                    time.perf_counter() - started, attempt + 1)
                        return result
                logger.error("%s give up after %d attempts, %.3fs", label,
                             retries + 1, time.perf_counter() - started)
                raise last_exc  # type: ignore[misc]

            return async_wrapper  # type: ignore[return-value]

        @functools.wraps(func)
        def sync_wrapper(*args, **kwargs):
            started = time.perf_counter()
            last_exc: BaseException | None = None
            for attempt in range(retries + 1):
                try:
                    result = func(*args, **kwargs)
                except exceptions as exc:
                    last_exc = exc
                    if attempt >= retries:
                        break
                    wait = _sleep_seconds(attempt)
                    logger.warning(
                        "%s failed (%s), retry %d/%d in %.2fs",
                        label, exc.__class__.__name__,
                        attempt + 1, retries, wait,
                    )
                    time.sleep(wait)
                else:
                    logger.info("%s ok in %.3fs (attempt=%d)", label,
                                time.perf_counter() - started, attempt + 1)
                    return result
            logger.error("%s give up after %d attempts, %.3fs", label,
                         retries + 1, time.perf_counter() - started)
            raise last_exc  # type: ignore[misc]

        return sync_wrapper  # type: ignore[return-value]

    return decorator

题 2：用生成器流式读取超大文件，并按 token 预算分批喂给 Embedding ​

场景：一个 4GB 的 JSONL 知识库要灌进向量库。不能 read() 全量进内存，也不能一条一条调 Embedding（QPS 打满、成本爆炸），必须「流式读 → 清洗 → 按预算攒批 → 批量调用」，全程内存恒定。

核心实现

python
import json
from collections.abc import Iterable, Iterator
from dataclasses import dataclass


@dataclass(slots=True)
class Chunk:
    doc_id: str
    text: str
    tokens: int


def read_jsonl(path: str, encoding: str = "utf-8") -> Iterator[dict]:
    """逐行惰性读取：文件句柄由 with 托管，内存里始终只有一行。"""
    with open(path, "r", encoding=encoding) as f:
        for lineno, line in enumerate(f, 1):
            line = line.strip()
            if not line:
                continue
            try:
                yield json.loads(line)
            except json.JSONDecodeError:
                # 脏数据跳过而不是中断整个灌库任务
                print(f"[skip] bad json at line {lineno}")
                continue


def to_chunks(rows: Iterable[dict], max_tokens: int = 500) -> Iterator[Chunk]:
    """清洗 + 切片：生成器管道的中间一级，不缓存任何中间列表。"""
    for row in rows:
        doc_id = row.get("id")
        text = (row.get("content") or "").strip()
        if not doc_id or not text:
            continue
        # 这里用「4 字符 ≈ 1 token」粗估，生产应换成 tiktoken
        for i in range(0, len(text), max_tokens * 4):
            piece = text[i: i + max_tokens * 4]
            yield Chunk(doc_id=doc_id, text=piece, tokens=len(piece) // 4 + 1)


def batch_by_budget(
    chunks: Iterable[Chunk],
    max_items: int = 64,
    max_tokens: int = 8000,
) -> Iterator[list[Chunk]]:
    """双预算攒批：条数和 token 数任一达标就出批。

    关键点：单条就超预算时也必须单独成批，否则会死循环或永远攒不出来。
    """
    buf: list[Chunk] = []
    buf_tokens = 0
    for c in chunks:
        if buf and (len(buf) >= max_items or buf_tokens + c.tokens > max_tokens):
            yield buf
            buf, buf_tokens = [], 0
        buf.append(c)
        buf_tokens += c.tokens
        if buf_tokens >= max_tokens:
            yield buf
            buf, buf_tokens = [], 0
    if buf:  # 收尾：最后一批一定不能漏
        yield buf


def ingest(path: str) -> int:
    total = 0
    pipeline = batch_by_budget(to_chunks(read_jsonl(path)))
    for batch in pipeline:
        vectors = embed([c.text for c in batch])   # 一次网络调用处理一批
        save_vectors(batch, vectors)
        total += len(batch)
    return total

面试加分表述：「read_jsonl → to_chunks → batch_by_budget 是三级生成器管道，上游不会因为下游慢而堆积数据，整个链路的内存占用是 O(一批) 而不是 O(文件)。我们灌 4GB 知识库时常驻内存只有 200MB 左右，而且因为是惰性的，中途失败可以记录 lineno 断点续传。」

题 3：asyncio 并发调用 LLM —— 限流 + 超时 + 重试 + 结果顺序保持 + 部分失败可降级 ​

这题几乎是 AI 工程岗的必考题。要求：输入 200 个 prompt，最多 8 并发，单请求 20s 超时，失败重试 2 次，返回结果顺序必须和输入一致，个别失败不能让整批崩掉，并且要能被外部整体取消。

核心实现

python
import asyncio
from dataclasses import dataclass
from typing import Sequence


@dataclass(slots=True)
class LLMResult:
    index: int
    prompt: str
    text: str | None = None
    error: str | None = None

    @property
    def ok(self) -> bool:
        return self.error is None


async def _call_one(
    index: int,
    prompt: str,
    sem: asyncio.Semaphore,
    *,
    timeout: float = 20.0,
    retries: int = 2,
) -> LLMResult:
    """单个请求：信号量在最内层，确保「排队等额度」不占用并发额度。"""
    last_err = "unknown"
    for attempt in range(retries + 1):
        try:
            async with sem:                      # 闸门一：并发上限
                async with asyncio.timeout(timeout):   # 闸门二：单请求超时
                    text = await llm.acreate(prompt)
            return LLMResult(index=index, prompt=prompt, text=text)
        except asyncio.CancelledError:
            # 外部整体取消：立刻放弃，绝不重试
            raise
        except TimeoutError:
            last_err = f"timeout>{timeout}s"
        except Exception as exc:                 # noqa: BLE001
            last_err = f"{exc.__class__.__name__}: {exc}"
        if attempt < retries:
            await asyncio.sleep(min(0.5 * 2 ** attempt, 4.0))
    return LLMResult(index=index, prompt=prompt, error=last_err)


async def batch_call(
    prompts: Sequence[str],
    concurrency: int = 8,
    timeout: float = 20.0,
    retries: int = 2,
) -> list[LLMResult]:
    """并发调用并保持顺序。

    顺序保持的三种做法：
      1. gather 天然按入参顺序返回（本实现采用，最简单）
      2. 自己带 index，as_completed 拿到后按 index 排序（可做流式进度）
      3. 预分配结果数组，task 完成后写回 results[index]
    """
    if not prompts:
        return []
    sem = asyncio.Semaphore(concurrency)
    tasks = [
        asyncio.create_task(
            _call_one(i, p, sem, timeout=timeout, retries=retries),
            name=f"llm-{i}",
        )
        for i, p in enumerate(prompts)
    ]
    try:
        # return_exceptions=True：个别任务抛异常不会让整批立刻失败
        raw = await asyncio.gather(*tasks, return_exceptions=True)
    except asyncio.CancelledError:
        for t in tasks:
            t.cancel()
        # 等取消真正落地，避免 "Task was destroyed but it is pending"
        await asyncio.gather(*tasks, return_exceptions=True)
        raise

    results: list[LLMResult] = []
    for i, item in enumerate(raw):
        if isinstance(item, BaseException):
            results.append(LLMResult(index=i, prompt=prompts[i],
                                     error=repr(item)))
        else:
            results.append(item)
    return results

python
async def batch_call_stream(prompts, concurrency=8):
    sem = asyncio.Semaphore(concurrency)
    tasks = [asyncio.create_task(_call_one(i, p, sem))
             for i, p in enumerate(prompts)]
    done_count = 0
    try:
        for fut in asyncio.as_completed(tasks):
            res = await fut
            done_count += 1
            yield done_count, res          # 谁先完成先吐，顺序由调用方按 index 还原
    finally:
        for t in tasks:
            t.cancel()
        await asyncio.gather(*tasks, return_exceptions=True)

⚠️ 四个高频踩坑：① async with sem 写在 for attempt 循环外面，重试期间一直占着并发额度，实际并发远低于设定值；② 只 await asyncio.sleep 不加抖动，8 个请求同时失败后又同时重试，形成周期性尖峰；③ gather 不传 return_exceptions=True，一个请求挂掉剩下 199 个的结果全部丢失（任务其实还在后台跑完才被 GC）；④ 不保存 tasks 强引用，create_task 的返回值被 GC 后任务「神秘消失」。

题 4：手写同步 / 异步双版本上下文管理器（资源保障 + 异常分类 + 耗时埋点） ​

要求：实现一个 span 上下文管理器，进入时记录开始时间与 trace 上下文，退出时打点；异常时标记失败但不吞异常；同时提供 with 和 async with 两种用法；再实现一个真正会「吞掉特定异常」的 suppress_and_log，讲清 __exit__ 返回值的含义。

核心实现（类写法，把协议写全）

python
import time
import types
import contextvars
from contextlib import contextmanager, asynccontextmanager

current_span = contextvars.ContextVar[str]("current_span", default="root")


class Span:
    """同时实现同步与异步上下文管理器协议的类。"""

    __slots__ = ("name", "_t0", "_token", "elapsed", "failed")

    def __init__(self, name: str) -> None:
        self.name = name
        self._t0 = 0.0
        self._token: contextvars.Token | None = None
        self.elapsed = 0.0
        self.failed = False

    # ---------- 公共逻辑 ----------
    def _enter(self) -> "Span":
        self._t0 = time.perf_counter()
        parent = current_span.get()
        self._token = current_span.set(f"{parent}/{self.name}")
        return self

    def _exit(self, exc_type) -> bool:
        self.elapsed = time.perf_counter() - self._t0
        self.failed = exc_type is not None
        if self._token is not None:
            current_span.reset(self._token)   # 必须 reset，否则污染后续调用
        status = "ERR" if self.failed else "OK"
        print(f"[span] {self.name} {status} {self.elapsed * 1000:.1f}ms")
        return False      # 返回 False/None = 不吞异常，原样向上抛

    # ---------- 同步协议 ----------
    def __enter__(self) -> "Span":
        return self._enter()

    def __exit__(
        self,
        exc_type: type[BaseException] | None,
        exc: BaseException | None,
        tb: types.TracebackType | None,
    ) -> bool:
        return self._exit(exc_type)

    # ---------- 异步协议 ----------

class suppress_and_log:
    """只吞掉指定异常并记日志，其余原样抛出。"""

    def __init__(self, *exceptions: type[BaseException], tag: str = "") -> None:
        self.exceptions = exceptions or (Exception,)
        self.tag = tag

    def __enter__(self) -> "suppress_and_log":
        return self

        if exc_type is None:

        return False

题 5：手写带 TTL 的 LRU 缓存装饰器（支持异步 + 线程安全 + 防缓存惊群） ​

场景：同一个 prompt 在 5 分钟内重复问，直接走缓存省钱省时延。要求：容量上限 LRU 淘汰、每条带 TTL 过期、同步异步双支持、线程安全、并且同一 key 的并发穿透只打一次下游（防惊群 / dog-pile）。

核心实现

python
import asyncio
import functools
import inspect
import threading
import time
from collections import OrderedDict
from typing import Any, Callable, Hashable


class _Entry:
    __slots__ = ("value", "expire_at")

    def __init__(self, value: Any, expire_at: float) -> None:
        self.value = value
        self.expire_at = expire_at


def make_key(args: tuple, kwargs: dict) -> Hashable:
    """稳定 key：kwargs 排序，保证 f(a=1,b=2) 与 f(b=2,a=1) 命中同一条。"""
    return (args, tuple(sorted(kwargs.items())))


def ttl_lru_cache(maxsize: int = 128, ttl: float = 300.0):
    def decorator(func: Callable):
        store: OrderedDict[Hashable, _Entry] = OrderedDict()
        lock = threading.Lock()                       # 同步版：保护 dict
        inflight: dict[Hashable, asyncio.Future] = {}  # 异步版：防惊群
        stats = {"hit": 0, "miss": 0, "expired": 0}

        def _get(key: Hashable) -> tuple[bool, Any]:
            now = time.monotonic()
            entry = store.get(key)
            if entry is None:
                stats["miss"] += 1
                return False, None
            if entry.expire_at <= now:                 # 先判过期再判命中
                del store[key]
                stats["expired"] += 1
                stats["miss"] += 1
                return False, None
            store.move_to_end(key)                     # LRU：命中即刷新热度
            stats["hit"] += 1
            return True, entry.value

        def _set(key: Hashable, value: Any) -> None:
            store[key] = _Entry(value, time.monotonic() + ttl)
            store.move_to_end(key)
            while len(store) > maxsize:
                store.popitem(last=False)              # 淘汰最久未使用

        if inspect.iscoroutinefunction(func):

            @functools.wraps(func)
            async def async_wrapper(*args, **kwargs):
                key = make_key(args, kwargs)
                hit, value = _get(key)
                if hit:
                    return value
                # 防惊群：同一 key 并发只放一个请求打下游，其余等同一个 Future
                fut = inflight.get(key)
                if fut is not None:
                    return await asyncio.shield(fut)
                loop = asyncio.get_running_loop()
                fut = loop.create_future()
                inflight[key] = fut
                try:
                    result = await func(*args, **kwargs)
                except BaseException as exc:
                    if not fut.done():
                        fut.set_exception(exc)
                    raise
                else:
                    _set(key, result)
                    if not fut.done():
                        fut.set_result(result)
                    return result
                finally:
                    inflight.pop(key, None)

            async_wrapper.cache_info = lambda: dict(stats, size=len(store))  # type: ignore[attr-defined]
            async_wrapper.cache_clear = lambda: (store.clear(), stats.update(hit=0, miss=0, expired=0))  # type: ignore[attr-defined]
            return async_wrapper

        @functools.wraps(func)
        def sync_wrapper(*args, **kwargs):
            key = make_key(args, kwargs)
            with lock:
                hit, value = _get(key)
            if hit:
                return value
            result = func(*args, **kwargs)   # 锁外执行，避免长时间持锁
            with lock:
                _set(key, result)
            return result

        sync_wrapper.cache_info = lambda: dict(stats, size=len(store))  # type: ignore[attr-defined]
        sync_wrapper.cache_clear = lambda: (store.clear(), stats.update(hit=0, miss=0, expired=0))  # type: ignore[attr-defined]
        return sync_wrapper

    return decorator
