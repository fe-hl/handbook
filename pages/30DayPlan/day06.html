Day6 React 核心：Fiber、Diff 算法、Hooks 原理 ​

📖 基础知识讲解【基础原理 + 高级深挖知识点】 ​

基础原理 ​

1. JSX 到真实 DOM 的完整链路 ​

JSX 不是浏览器能识别的语法，它是 React.createElement 的语法糖，由 Babel 在编译期转换：

jsx
// 你写的 JSX
const el = (
  <div className="box" onClick={handleClick}>
    <span>hello</span>
    {count}
  </div>
);

// React 17 之前：Babel 编译产物
const el = React.createElement(
  "div",
  { className: "box", onClick: handleClick },
  React.createElement("span", null, "hello"),
  count
);

// React 17+ 新 JSX 转换（自动引入，不用再 import React）
import { jsx as _jsx, jsxs as _jsxs } from "react/jsx-runtime";
const el = _jsxs("div", {
  className: "box",
  onClick: handleClick,
  children: [_jsx("span", { children: "hello" }), count],
});

createElement 返回的就是 ReactElement（虚拟 DOM）：

js
{
  $$typeof: Symbol(react.element), // 防 XSS，JSON 无法伪造 Symbol
  type: 'div',                     // 字符串=原生标签，函数/类=组件
  key: null,
  ref: null,
  props: { className: 'box', onClick: f, children: [...] },
  _owner: FiberNode               // 创建它的那个组件 Fiber
}

真实 DOM
概念是什么关键区别
ReactElementcreateElement 的返回值不可变，每次 render 都新建；只描述 UI 结构
Fiber真实的工作单元节点可变，尽量复用；带 stateNode、memoizedState、flags
DOM浏览器真实节点挂在 Fiber 的 stateNode 上

为什么要虚拟 DOM？ 不是因为「虚拟 DOM 比直接操作 DOM 快」—— 手写最优的原生 DOM 操作一定比虚拟 DOM 快。虚拟 DOM 的真正价值是：① 提供声明式编程模型，让你只关心状态不关心 DOM 操作；② 用可接受的性能换来跨平台能力（ReactDOM / ReactNative / 自定义渲染器）；③ 批量 diff 后一次性提交，避免手写代码里常见的多次回流重绘。

2. React Diff 的三大原则 ​

React 把 O(n³) 的树 diff 问题，通过三条启发式假设降到了 O(n)：

原则具体做法带来的代价
① 同层级比较（Tree Diff）只比较同一父节点下的同层节点，不做跨层级移动节点跨层级移动会被「删除 + 重建」，状态和 DOM 全丢
② 类型不同直接销毁重建（Component Diff）type 不同（div→p、A→B）就卸载整棵子树重建即使子树内容完全一样也会重建
③ key 作为同层唯一标识（Element Diff）同层列表用 key 判断是否可复用key 不稳定（如 index）会导致大量无效重建

单节点 diff 的判断流程：

新旧节点对比
   │
   ├─ key 不同？ ────────────► 直接标记删除旧节点，创建新节点
   │
   └─ key 相同
        │
        ├─ type 不同？ ──────► 删除旧节点（及整棵子树），创建新节点
        │
        └─ type 相同  ──────► ✅ 复用 Fiber，只更新 props，继续 diff children

多节点（列表）diff —— 两轮遍历：

第一轮：从左到右逐个比对（处理「更新」这种最常见的情况）
  旧: A B C D
  新: A B C E
       ✓ ✓ ✓ ✗ ← key 或 type 不匹配，立即跳出第一轮

第二轮：把剩余旧节点存进 Map（key → fiber），再遍历剩余新节点
  existingChildren = { D: fiber }
  新节点 E：Map 里找不到 → 新建
  遍历结束，Map 里剩下的 D → 标记删除

移动判断：用 lastPlacedIndex 记录「上一个可复用节点在旧列表中的位置」
  若 oldIndex < lastPlacedIndex → 标记 Placement（需要右移）
  若 oldIndex >= lastPlacedIndex → 不动，更新 lastPlacedIndex = oldIndex

React 的 diff 只做「向右移动」，不做向左移动。所以把最后一个元素移到最前面（ABCD → DABC），React 需要移动 A、B、C 三个节点；而移到最后（ABCD → BCDA）只需移动 A 一个。这是 React diff 相比 Vue3 最长递增子序列算法的一个短板，面试讲出来很加分。

3. 为什么不能用 index 作为 key ​

jsx
// ❌ 用 index：在头部插入一条数据
// 旧: [{id:1,'A'}, {id:2,'B'}]  →  key: 0, 1
// 新: [{id:3,'C'}, {id:1,'A'}, {id:2,'B'}]  →  key: 0, 1, 2
//
// React 认为：key=0 的节点内容从 A 变成了 C → 更新
//            key=1 的节点内容从 B 变成了 A → 更新
//            key=2 是新增 → 创建
// 结果：3 个节点全部重新渲染，而实际只需要插入 1 个！
{
  list.map((item, index) => <Item key={index} {...item} />);
}

// ✅ 用业务唯一 id
{
  list.map((item) => <Item key={item.id} {...item} />);
}
// React 认为：id=3 是新节点 → 插入；id=1、id=2 原样复用
危害表现
性能下降本可复用的节点被判定为「内容变化」，触发大面积更新
非受控组件状态错乱<input> 的值、<video> 播放进度、CSS 动画状态跟着「位置」而不是「数据」走
组件内部 state 串位子组件自己的 useState 被错误复用到了另一条数据上
动画异常过渡动画作用在错误的元素上

什么时候 index 当 key 是安全的？ 同时满足三个条件：① 列表是纯静态的，不会增删改排序；② 列表项没有内部 state、没有非受控输入；③ 列表项不是可拖拽的。实际业务里很难同时满足，所以默认就该用业务 id。

另一个常见错误是用 Math.random() 当 key —— 每次 render 都生成新 key，等于告诉 React「所有节点都是全新的」，整个列表每次都销毁重建，比 index 还糟糕。

Hooks 的两条铁律：

jsx
// ❌ 条件调用：Hook 数量/顺序在不同渲染间不一致
function Bad({ show }) {
  const [a, setA] = useState(0);
  if (show) {
    const [b, setB] = useState(1); // 报错：Rendered fewer hooks than expected
  }
  useEffect(() => {}, []); // 这个 Hook 在两次渲染中对应到了不同的链表位置
}

// ✅ 正确：Hook 永远在顶层，条件写在 Hook 内部
function Good({ show }) {
  const [a, setA] = useState(0);
  const [b, setB] = useState(1);
  useEffect(() => {
    if (!show) return; // 条件判断放进去
    doSomething();
  }, [show]);
}
规则原因
只能在函数组件顶层调用Hook 用单向链表 + 顺序定位，不能有 if/for/return 之后的调用
只能在函数组件或自定义 Hook 中调用Hook 依赖全局 currentlyRenderingFiber，普通函数里调用取不到对应 Fiber

唯一的例外：React 19 的 use。 它可以写在 if 里、也可以提前 return，因为它不占用 Hook 链表的槽位——use(promise) 的实现是「读 promise 的状态，pending 就 throw 出去交给 Suspense」，状态挂在 promise 对象自身而不是 fiber 的 hook 链表上。除此之外的所有 Hook 仍然必须无条件顶层调用。

强烈建议开启 eslint-plugin-react-hooks，rules-of-hooks 和 exhaustive-deps 两条规则能在编译期拦掉 90% 的 Hooks 问题。

1. Fiber 架构：React 16 为什么要重写 ​

React 15（Stack Reconciler）的痛点：

递归遍历虚拟 DOM 树（函数调用栈），一旦开始无法中断
 │
 ├─ 组件树很深 / 节点很多 → 单次调和耗时 100ms+
 │
 └─ 期间主线程被完全占满
      ├─ 用户点击/输入无响应
      ├─ 动画掉帧
      └─ 浏览器无法绘制 → 页面「卡死」

浏览器一帧约 16.6ms（60fps），留给 JS 的时间只有几毫秒。React 15 的递归调和没有「暂停点」，因为函数调用栈一旦展开，中断就意味着丢失执行上下文。

Fiber 的解法：把递归改成「可中断的链表遍历」

Fiber 节点本质是一个虚拟的调用栈帧，用对象的属性保存了原本在函数调用栈里的信息，所以可以随时存盘、随时恢复：

js
function FiberNode(tag, pendingProps, key) {
  // ===== 1. 节点自身属性 =====
  this.tag = tag; // 类型：FunctionComponent=0 / ClassComponent=1 / HostComponent=5
  this.key = key;
  this.type = null; // 函数组件就是函数本身，原生标签是 'div'
  this.stateNode = null; // 对应的真实 DOM 实例 / 类组件实例

  // ===== 2. 链表指针（取代递归调用栈）=====
  this.return = null; // 父 Fiber（为什么叫 return？因为它是"归还/返回"的目标）
  this.child = null; // 第一个子 Fiber
  this.sibling = null; // 下一个兄弟 Fiber
  this.index = 0;

  // ===== 3. 工作单元数据 =====
  this.pendingProps = pendingProps; // 新的 props
  this.memoizedProps = null; // 上次渲染的 props
  this.memoizedState = null; // 上次渲染的 state（函数组件里是 Hook 链表头！）
  this.updateQueue = null; // 更新队列（环状链表）

  // ===== 4. 副作用 =====
  this.flags = NoFlags; // 自身副作用标记：Placement/Update/Deletion...
  this.subtreeFlags = NoFlags; // 子树是否有副作用（用于快速跳过整棵子树）
  this.deletions = null;

  // ===== 5. 优先级（并发特性的基础）=====
  this.lanes = NoLanes; // 本节点待处理更新的优先级
  this.childLanes = NoLanes;

  // ===== 6. 双缓存 =====
  this.alternate = null; // 指向另一棵树的对应节点
}

遍历顺序：深度优先 + 「归」阶段（这是 Fiber 最精髓的设计）

        App
       /   \
      A     B
     / \
    C   D

遍历路径（递 → 归）：
  beginWork  (递):  App → A → C
  completeWork(归):  C 没有 child → 完成 C → 找 sibling D
  beginWork  (递):  D
  completeWork(归):  完成 D → 没有 sibling → 回到 return A → 完成 A
                    → A 的 sibling 是 B → beginWork(B)
  completeWork(归):  完成 B → 回到 App → 完成 App → 结束

实际顺序：App↓ A↓ C↓ C↑ D↓ D↑ A↑ B↓ B↑ App↑
阶段函数干了什么
递（beginWork）自顶向下根据新 Element 创建/复用子 Fiber，调用组件函数拿到 children，diff 打 flags
归（completeWork）自底向上创建离屏 DOM 节点、设置属性、把子树的 flags 冒泡到父节点（subtreeFlags）

关键：每处理完一个 Fiber，React 都会检查 shouldYield() —— 如果当前时间切片（5ms）用完了，就保存 workInProgress 指针并 return，把主线程交还给浏览器；下一次调度再从断点继续。这就是「时间切片」。

2. 两大阶段：Render（可中断） vs Commit（不可中断） ​

┌──────────── Render / Reconciliation 阶段（可中断、可重做、可丢弃）────────────┐
│                                                                          │
│  performConcurrentWorkOnRoot                                                 │
│    └─ workLoopConcurrent:  while (workInProgress && !shouldYield())          │
│         ├─ beginWork(fiber)      ← 创建/复用子 Fiber，执行组件函数            │
│         └─ completeWork(fiber)   ← 创建离屏 DOM，冒泡 flags                   │
│                                                                              │
│  ⚠️ 这里不能有副作用！因为可能被中断后重新执行多次                              │
└──────────────────────────────────────────────────────────────────────────────┘
                                   │ 构建完成，得到带 flags 的 workInProgress 树
                                   ▼
┌──────────── Commit 阶段（同步执行，不可中断）──────────────────────────────────┐
│                                                                              │
│  ① before mutation：getSnapshotBeforeUpdate / 调度 useEffect（异步）           │
│  ② mutation       ：真正操作 DOM（插入/更新/删除）                             │
│       └─ 中间切换指针：root.current = finishedWork  ⭐ 双缓存切换点             │
│  ③ layout         ：componentDidMount/Update、useLayoutEffect 回调（同步）     │
│                                                                              │
│  浏览器绘制 ──► 之后异步执行 useEffect 回调                                     │
└──────────────────────────────────────────────────────────────────────────────┘
维度Render 阶段Commit 阶段
能否中断✅ 可中断、可丢弃重做❌ 必须一次性完成
为什么工作在内存中进行，用户看不到操作真实 DOM，中断会让用户看到不完整的 UI
执行什么beginWork / completeWork、组件函数、diffDOM 增删改、生命周期、ref 挂载、effect 调度
副作用限制必须纯净（可能执行多次）可以有副作用
对应钩子render、getDerivedStateFromProps、函数组件体componentDidMount/Update、useLayoutEffect、useEffect

为什么 React 18 的严格模式（StrictMode）会故意把函数组件执行两次？ 就是为了帮你发现「Render 阶段不纯净」的 bug —— 如果你在组件体里改了外部变量、发了请求、操作了 DOM，两次执行会暴露出不一致。因为并发模式下 Render 阶段真的可能被执行多次。

3. 双缓存 Fiber 树：指针切换一步到位 ​

React 同时维护两棵 Fiber 树，通过 alternate 互相指向：

          ┌──────────────┐
          │  FiberRoot   │ (整个应用唯一)
          └──────┬───────┘
                 │ current  ← 指向当前屏幕上的那棵树
                 ▼
   ┌─────────────────────┐  alternate   ┌──────────────────────────┐
   │   current 树         │ ◄──────────► │  workInProgress 树        │
   │  （屏幕上正在显示）    │              │ （内存中正在构建的新 UI）    │
   │                     │              │                          │
   │   HostRoot          │              │   HostRoot'              │
   │     └─ App          │              │     └─ App'              │
   │          └─ ...     │              │          └─ ...          │
   └─────────────────────┘              └──────────────────────────┘

构建完成后，在 commit 的 mutation 阶段结束时：
   root.current = workInProgressTree;   ← ⭐ 一行代码切换整棵树
原来的 current 树变成下次更新的 workInProgress（复用对象，避免反复 new）
好处说明
避免 UI 闪烁 / 撕裂新树在内存里构建，没构建完屏幕上一直是旧 UI；切换是原子操作
可以随时丢弃高优先级任务插队时，直接扔掉半成品 workInProgress 树重新构建，current 树毫发无损
对象复用，减少 GC两棵树的 Fiber 节点通过 alternate 来回复用，不用每次都新建一整棵树
便于对比fiber.alternate 就是上一次的自己，memoizedProps vs pendingProps 直接比

面试加分： 双缓存这个思路和图形渲染里的 double buffering 完全一致 —— 后台缓冲区画好了再 swap 到前台，避免看到绘制过程。

4. Hooks 底层：挂在 Fiber 上的单向链表 ​

Hooks 的数据不存在组件里，而是存在当前组件对应的 FiberNode 上：

js

9. setState 之后发生了什么：更新队列与 bailout ​

前面讲了 Fiber、双缓存、Hooks 链表，但「setState 到底怎么把新值塞进去的」这段还缺一块：更新队列（update queue）。

(1) 每次 setState 都生成一个 update 对象，挂进环形链表

js
// 简化版 dispatchSetState
function dispatchSetState(fiber, queue, action) {
  const update = {
    lane: requestUpdateLane(fiber), // 本次更新的优先级
    action, // 值 或 (prev) => next
    hasEagerState: false,
    eagerState: null,
    next: null, // 构成环形链表
  };

  // pending 始终指向【最后一个】update，pending.next 是【第一个】
  const pending = queue.pending;
  if (pending === null) {
    update.next = update; // 自己指向自己，形成单元素环
  } else {
    update.next = pending.next;
    pending.next = update;
  }
  queue.pending = update;

  scheduleUpdateOnFiber(fiber, update.lane); // 进入调度
}
为什么用【环形链表】而不是数组或普通链表？
  ① 只存一个 pending 指针，就能 O(1) 拿到首个（pending.next）和末个（pending）
  ② O(1) 插入新 update，不用遍历到尾部
  ③ 高优先级更新插队后，被跳过的低优先级 update 还留在环里，
     下一轮渲染能从环的头部重新完整遍历一遍 —— 这是并发可中断的前提

链表形态：pending ──► u3 ──► u1 ──► u2 ──┐
                      ▲                 │
                      └─────────────────┘
          遍历顺序：u1 → u2 → u3（从 pending.next 开始）

(2) 渲染时按优先级依次计算：updateReducer

js
// 简化：遍历环形链表，跳过优先级不够的 update
let newState = current.baseState;
let update = first;
do {
  if (isSubsetOfLanes(renderLanes, update.lane)) {
    // 优先级够：参与计算
    newState =
      typeof update.action === "function"
        ? update.action(newState) // 函数式更新：基于上一个结果
        : update.action; // 直接赋值
  } else {
    // 优先级不够：跳过，但要存进 baseQueue 留给下一轮
    markSkippedUpdateLanes(update.lane);
  }
  update = update.next;
} while (update !== first);

这段代码直接解释了两个经典现象：setCount(count + 1) 连写三次只加 1（三个 action 都是同一个闭包里的常量值，后者覆盖前者），而 setCount(c => c + 1) 连写三次加 3（每个函数都基于上一个计算结果）。

(3) 两级「短路」优化：eagerState 与 bailout

优化发生时机做了什么
eagerStatedispatch 调用的那一刻如果当前 fiber 没有任何待处理更新，就提前算一遍新 state，和旧值 Object.is 相等时直接 return，连调度都不发起
bailout（复用）beginWork 开始时props 全等 + 无 lanes + context 没变 → 直接复用上一轮的 fiber 子树（bailoutOnAlreadyFinishedWork），不执行组件函数

11. Context 原理与「Provider 一变，全家重渲染」 ​

(1) Context 不走 props，走的是「栈 + 订阅」

  push(context, v) —— 把 value 压入该 context 的全局栈，并记录在 fiber 上

  ① 读取栈顶 value
  ② 把当前 fiber 加进 Ctx 的依赖列表（fiber.dependencies 链表）
      ↓
Provider 的 value 变化（Object.is 比较）时：
  不是「让子树重渲染」，而是 propagateContextChange：
  从 Provider 向下深度遍历，找到所有 dependencies 里含该 Ctx 的 fiber，
  给它们打上 lanes 标记 —— 这样即使中间组件命中了 bailout，
  消费者本身也因为有 lanes 而被强制更新

关键结论： React.memo / bailout 挡不住 Context 更新，因为 Context 是「穿透式」地给消费者打标记的。所以「用 memo 包一层就能避免 context 导致的渲染」是错的。

React.lazy 的本质：一个带状态机的 thenable 包装。

js
function lazy(ctor) {
  const payload = { status: -1, result: ctor }; // -1 未初始化
  return {
    $$typeof: Symbol.for('react.lazy'),
    _payload: payload,
    _init(payload) {
      if (payload.status === -1) {
        const thenable = payload.result();
        thenable.then(
          (m) => { payload.status = 1; payload.result = m.default; },
          (e) => { payload.status = 2; payload.result = e; }
        );
        payload.status = 0; // pending
        payload.result = thenable;
      }
      if (payload.status === 1) return payload.result; // 直接返回组件
      throw payload.result; // pending 抛 promise / rejected 抛 error
    },
  };
}

所以 lazy 既能被 Suspense 接住（pending 抛 Promise），也能被错误边界接住（加载失败抛 Error）—— 这就是为什么动态加载的组件同时需要这两层包裹。

错误边界：只能用类组件写。

jsx
class ErrorBoundary extends React.Component {
  state = { error: null };
  // 1. Render 阶段调用，纯函数，用来更新 state 渲染降级 UI
  static getDerivedStateFromError(error) {
    return { error };
  }
  // 2. Commit 阶段调用，可以有副作用，用来上报
  componentDidCatch(error, info) {
    reportError(error, info.componentStack);
  }
  render() {
    if (this.state.error) return this.props.fallback;
    return this.props.children;
  }
}

为什么没有 useErrorBoundary Hook？ 官方的说法是还没想好 API 形态：错误边界需要「在 Render 阶段同步拿到错误并立即返回降级 UI」，这与 Hook 「先执行完整个函数体再决定返回值」的模型不匹配。目前只能用类组件，或者用 react-error-boundary 这个库（它内部也是类组件）。

  • 过渡态保留旧 UI：被 startTransition 包裹的更新触发 Suspense 时，React 不再立刻把已有内容换成 fallback，而是继续显示旧 UI直到新内容就绪，配合 useTransition 的 isPending 做 loading 态，避免了 17 时代「点一下整块内容闪成骨架屏」的体验问题。

  • 配合 use（19）：use(promise) 内部就是 pending 时 throw，让 Suspense 接管，这是 React 官方认可的「组件内直接 await」写法。

题 1：React Diff 算法的原理是什么？为什么不要用 index 作为 key？ ​

精简口述答案：

完整的树 diff 是 O(n³)，React 基于三个假设把它降到了 O(n)：第一，不同类型的元素产生不同的树，type 变了就整棵子树删除重建；第二，只做同层比较，不做跨层级移动；第三，用 key 标识同层节点，帮助复用。列表 diff 分两轮：第一轮从左往右按位置比对，key 相同就复用、不同就跳出；第二轮把剩下的旧节点放进一个 key → fiber 的 Map，再遍历新节点去 Map 里找复用，用 lastPlacedIndex 判断是否需要向右移动，最后删掉 Map 里剩下的节点。index 作为 key 的问题在于它跟数据本身没有绑定关系：列表头部插入或排序后，同一个 index 对应的数据变了，React 会认为这是「同一个节点内容变了」，于是复用了旧 Fiber 和旧 DOM，导致非受控组件的输入框内容、CSS 动画状态、组件内部 state 全部错位，而且本该是移动的操作变成了大量属性更新，性能反而更差。

连环追问链：

  1. 追问：key 的最佳实践是什么？
    • 答：优先用业务唯一且稳定的 id（后端主键）；没有 id 时可以用能唯一标识该条数据的字段组合；只有当列表是纯静态展示、不增删不排序、无内部状态时才可以用 index。绝对不能用 Math.random()，那样每次渲染 key 都变，所有节点全部卸载重建，等于关掉了 diff。
  2. 追问：key 只需要在兄弟节点间唯一还是全局唯一？
    • 答：只需要在同一个父节点的兄弟之间唯一即可，因为 diff 是同层进行的，React 用的是一个局部的 Map。
  3. 追问：节点跨层级移动 React 怎么处理？
    • 答：React 不处理，直接把原位置的子树删除、在新位置重新创建。所以要避免设计出会导致 DOM 层级变化的结构，比如用条件渲染包裹一层 div 把子树整体挪走，应改成用 CSS 控制或者保持层级不变。
  4. 追问：React 和 Vue3 的列表 diff 有什么区别？
    • 答：Vue3 是双端 + 最长递增子序列（LIS）。先处理头尾相同的部分，中间乱序部分建立 key 索引表，求出 LIS，不在 LIS 里的节点才移动，移动次数是理论最优。React 只有一轮从左到右的遍历，用 lastPlacedIndex 单调判断，只能向右移动，所以把最后一个元素移到第一个这种场景，React 会移动前面所有元素，而 Vue3 只移动一个。
  5. 追问：不写 key 会怎样？
    • 答：React 会用 index 兜底并在控制台告警，行为等价于 key={index}，同样有上面说的错位风险。

✅ 项目关联话术（按真实经历替换）：

题 2：Fiber 架构解决了什么痛点？Render 和 Commit 阶段有什么区别？ ​

精简口述答案：

React 15 的 Stack Reconciler 是递归遍历虚拟 DOM 树，一旦开始就无法中断，组件树一深，单次更新占用主线程几百毫秒，用户输入和动画全部卡死。Fiber 做了两件事：一是把树形递归改成了链表结构的循环，每个 FiberNode 有 return、child、sibling 三个指针，可以把「下一个要处理的节点」保存在 workInProgress 变量里，随时中断随时恢复；二是配合 Scheduler 做时间切片，每处理完一个 Fiber 就调用 shouldYield() 检查这一帧的 5ms 时间片有没有用完，用完就把控制权还给浏览器。整个更新分两个阶段：Render 阶段做 diff、打 flags、构建 workInProgress 树，它是纯计算、不碰真实 DOM，所以可中断、可丢弃、可重做；Commit 阶段遍历 effectList 真正操作 DOM，分 before mutation、mutation、layout 三个子阶段，这个阶段同步不可中断，否则用户会看到渲染到一半的界面。

连环追问链：

  1. 追问：双缓存 Fiber 树的作用是什么？
    • 答：内存中同时存在 current 树（屏幕上的）和 workInProgress 树（正在构建的），两棵树通过 alternate 互相指向。新树在内存里慢慢构建，构建失败可以直接丢弃，不影响屏幕；构建完成后 Commit 阶段只需要一句 root.current = workInProgress 完成切换，避免了用户看到中间态。跟图形学的 double buffering 是一个思路。
  2. 追问：为什么 Commit 阶段不能中断？
    • 答：Commit 阶段在真实操作 DOM，如果中断，用户会看到一部分旧 UI 一部分新 UI 的撕裂画面；而且 getSnapshotBeforeUpdate、componentDidMount、useLayoutEffect 都要求在同一帧内、DOM 更新后绘制前同步完成，中断会破坏这个语义。
  3. 追问：Render 阶段可能被重复执行，有什么实际影响？
    • 答：这就是为什么 Render 阶段必须是纯函数：不能有副作用、不能直接 setState、不能直接 mutate。React 18 的 StrictMode 在开发环境故意把渲染和 effect 执行两次，就是为了提前把不纯的代码暴露出来。
  4. 追问：Fiber 如何实现中断后恢复？
    • 答：全局变量 workInProgress 保存当前处理到的 Fiber 节点，中断时只是退出 workLoop 循环，恢复时从这个变量继续 performUnitOfWork。遍历用的是深度优先的「递」beginWork 和「归」completeWork，沿着 child → sibling → return 走，是纯指针跳转，不依赖调用栈。
  5. 追问：优先级是怎么表达的？
    • 答：React 17 之前用 expirationTime 过期时间，18 换成了 Lane 模型 —— 31 位二进制位，位越低优先级越高，可以用位运算同时表示一批优先级，便于做批量判断和解决低优先级任务饥饿的问题。

✅ 项目关联话术（按真实经历替换）：

题 3：为什么 Hooks 不能写在条件语句、循环里？ ​

精简口述答案：

因为 Hook 的数据是以单向链表的形式挂在组件对应的 FiberNode 的 memoizedState 上的，链表节点之间只有 next 指针，没有任何名字或 key 来标识身份。首次渲染时 React 按调用顺序依次创建 Hook 节点并串成链表；更新渲染时 React 只是顺着链表按顺序往下取，取第几个完全依赖调用顺序。如果 Hook 写在 if 里，某次渲染这个 Hook 没执行，后面所有 Hook 的取值就整体错位一位，拿到的就是别人的 state，表现出来可能是报错 "Rendered fewer hooks than expected"，也可能是更隐蔽的数据串位。

连环追问链：

  1. 追问：为什么类组件没有这个限制？
    • 答：类组件的 state 是一个对象，this.state.count 是按 key 取值的，跟声明顺序无关；Hook 是链表 + 隐式下标，只能靠顺序对齐。
  2. 追问：React 是怎么检测到这个错误的？
    • 答：更新阶段 updateWorkInProgressHook 发现要取下一个 Hook 但链表已经走到 null，就会抛 "Rendered more hooks than during the previous render"；反之渲染结束后发现链表还有剩余，就提示 fewer hooks。另外 eslint-plugin-react-hooks 的 rules-of-hooks 会在编译期静态检查出条件调用。
  3. 追问：那我确实需要条件性的逻辑怎么办？
    • 答：把条件移到 Hook 内部，而不是包在外面。比如 useEffect(() => { if (!show) return; ... }, [show])；或者把这部分逻辑抽成一个独立子组件，用条件渲染控制子组件的挂载。
  4. 追问：自定义 Hook 里的 state 在多个组件间是共享的吗？
    • 答：不共享。自定义 Hook 只是函数复用，调用它时 Hook 节点是挂在调用方组件的 Fiber 上的，每个组件实例各有一份独立状态。要共享必须靠 Context、状态管理库，或者把 state 提到共同的父组件。
  5. 追问：同一个组件里调用两次同一个自定义 Hook 会冲突吗？
    • 答：不会，它们在链表上是两段独立的 Hook 节点，互不影响 —— 这也正说明了「顺序即身份」。

✅ 项目关联话术（按真实经历替换）：

我们有个表单组件早期为了「省性能」，把 useMemo 写在了 if (isEdit) 里，结果编辑态和新增态来回切换时报了 hooks 数量不一致的错。排查完之后我们在项目里强制开启了 eslint-plugin-react-hooks，并把 rules-of-hooks 设为 error 接入 CI 的 lint 卡点，之后这类问题就彻底拦在提交前了。

题 4：useMemo / useCallback 一定能优化性能吗？闭包陷阱怎么解决？ ​

精简口述答案：

不一定，用错了反而是负优化。它们本质就是把 [值, 依赖数组] 存在 Hook 链表上，每次渲染都要做一次依赖的浅比较，这个比较本身和额外的内存占用都是成本。只有三种情况值得用：一是计算确实昂贵；二是结果作为 props 传给了 React.memo 包裹的子组件，需要保持引用稳定；三是这个值本身要作为其他 Hook 的依赖项。如果子组件没包 memo，父组件重渲染时子组件照样重渲染，缓存引用毫无意义。闭包陷阱是另一个常见坑：函数组件每次渲染都会生成一个全新的作用域，如果 effect 或回调的依赖数组是空的，它捕获的就永远是首次渲染那一刻的 state。解法有三种：优先用函数式更新 setX(prev => ...)，彻底不依赖外部变量；需要读多个最新值时用 useRef 在每次渲染同步最新值；或者干脆补全依赖让 effect 重建，代价是副作用会反复创建销毁。

连环追问链：

  1. 追问：React.memo 的比较规则是什么？能自定义吗？
    • 答：默认对 props 做浅比较（Object.is 逐个比较第一层）。可以传第二个参数 areEqual(prevProps, nextProps) 自定义，返回 true 表示相等、跳过渲染 —— 注意它的返回值语义和 shouldComponentUpdate 是相反的。
  2. 追问：依赖数组漏写会有什么后果？不写依赖数组呢？
    • 答：漏写会读到过期的变量（stale closure），表现为「点了没反应」或者拿到旧值；完全不写依赖数组则每次渲染后都执行，如果里面还 setState 就会死循环。
  3. 追问：依赖里是对象或数组，每次都是新引用怎么办？
    • 答：三种办法：把依赖拆成用到的原始值（[obj.id, obj.name]）；把对象本身也用 useMemo 缓存；或者在 effect 内部做深比较/用 JSON.stringify 后的字符串作为依赖（仅限小对象）。
  4. 追问：怎么拿到「引用稳定但总是最新」的回调？
    • 答：用 useRef 存最新的函数，再用 useCallback 返回一个只调用 ref.current(...) 的稳定包装（也就是社区的 useEvent / useLatest 方案）。React 官方的 useEffectEvent 提案就是它的标准化版本。
  5. 追问：React 19 的编译器会改变这些吗？
    • 答：会。React Compiler 会在编译期自动插入等价的 memo 逻辑，手写 useMemo / useCallback 的必要性会大幅降低，但理解依赖和闭包的原理依然必要，因为编译器也依赖你的代码是纯的。

✅ 项目关联话术（按真实经历替换）：

我接手的一个页面几乎每个变量都包了 useMemo，但子组件一个 memo 都没加，profiler 上看渲染耗时没有任何改善，反而多了一堆依赖比较。我的做法是：先用 React DevTools Profiler 定位真正的渲染热点，只给确认是瓶颈的长列表子组件加 React.memo，再给传给它的回调和对象加 useCallback / useMemo，其余全部删掉。最终列表区域的重渲染次数从每次输入 1 次全量变成了 0 次，代码也简洁了很多。

题 5：useEffect 和 useLayoutEffect 的区别？什么时候必须用后者？ ​

精简口述答案：

两者的 API 和依赖规则完全一样，区别只在执行时机。useLayoutEffect 在 Commit 阶段的 layout 子阶段同步执行，此时真实 DOM 已经更新但浏览器还没绘制，所以在里面读 DOM 尺寸、再同步修改样式，用户看不到中间状态；代价是它会阻塞绘制，里面放耗时逻辑会直接掉帧。useEffect 是在浏览器完成绘制之后异步执行的，不阻塞渲染，适合请求数据、订阅事件、埋点这类不影响布局的副作用。判断标准很简单：如果副作用会改变布局且用户可能看到闪烁，就用 useLayoutEffect，比如 Tooltip 根据目标元素位置定位、滚动容器恢复 scrollTop；其他情况默认用 useEffect。另外 useLayoutEffect 在 SSR 下不执行并会告警，需要降级处理。

连环追问链：

  1. 追问：清理函数（return 的函数）什么时候执行？
    • 答：两个时机 —— 下一次该 effect 执行之前（先清理旧的再执行新的），以及组件卸载时。所以定时器、事件监听、AbortController、WebSocket 都必须在清理函数里释放。
  2. 追问：StrictMode 下 effect 执行两次是 bug 吗？
    • 答：不是，是 React 18 开发环境故意的「挂载 → 卸载 → 再挂载」，用来检验你的 effect 是否可重复执行、清理函数是否写全。生产环境只执行一次。如果执行两次出问题，说明代码本身有副作用泄漏。
  3. 追问：在 useEffect 里 setState 会不会死循环？
    • 答：如果没有依赖数组，或者依赖项每次渲染都是新引用（对象/数组字面量），就会「渲染 → effect → setState → 渲染」无限循环。正确做法是补全并收窄依赖，或者加 if (next !== cur) return; 这样的短路判断。
  4. 追问：如何在 effect 里安全地发请求？
    • 答：用 AbortController 在清理函数里 abort，或者用一个 let cancelled = false 的闭包标记，在 then 回调里判断后再 setState，避免竞态（后发的请求先返回导致数据错乱）和卸载后 setState。
  5. 追问：SSR 里怎么处理？
    • 答：服务端不存在布局，React 不会执行 useLayoutEffect 并会在控制台告警。常见做法是封装 useIsomorphicLayoutEffect，根据 typeof window 判断选择 useLayoutEffect 还是 useEffect。

✅ 项目关联话术（按真实经历替换）：

我们做了个气泡提示组件，需要读取触发元素的 getBoundingClientRect() 再计算气泡位置。最初用 useEffect，气泡会先在左上角 (0,0) 闪一下再跳到正确位置。换成 useLayoutEffect 之后定位在绘制前就完成了，闪烁彻底消失。同时因为项目有 SSR，我们封装了一个同构版本的 hook 来消除服务端的告警。

题 6：调用 setState 之后 React 内部发生了什么？ ​

精简口述答案：

setState（函数组件里是 dispatchSetState）并不会立刻改 state，它做的是三件事：第一，创建一个 update 对象，里面记着这次的 action 和本次更新的 lane 优先级；第二，把这个 update 挂到当前 Hook 的 queue.pending 这条环形链表上；第三，调用 scheduleUpdateOnFiber 从当前节点沿 return 一路把 lane 冒泡到根，然后向 Scheduler 注册一个渲染任务。真正计算新值发生在下一次渲染时的 updateReducer 里 —— 它从链表头开始遍历，优先级够的就执行 reducer 累积计算，不够的留在队列里等下一轮。所以 state 的更新是「先排队、后批量结算」。另外在入队之前 React 还会做一次 eagerState 优化：如果队列本来是空的，就提前算一次结果，和当前值用 Object.is 比较，相同就直接 return，连渲染都不调度。

连环追问链：

  1. 追问：为什么更新队列要设计成环形链表？
    • 答：三个好处。一是用一个 pending 指针同时拿到头和尾 —— pending 指向最后一个节点，pending.next 就是第一个，插入新节点是 O(1)，不需要再存一个 tail；二是遍历时天然能判断「回到起点就结束」，不用额外的 null 哨兵；三是高优先级任务插队后，被跳过的低优先级 update 还留在环上，下一轮还能被重新遍历到，不会丢更新。
  2. 追问：eagerState 和 bailout 有什么区别？
    • 答：两级短路，层级完全不同。eagerState 在 setState 调用时生效，命中后连渲染都不调度，最省；但它只在队列为空（没有待处理更新）时才敢提前计算。bailout 在组件渲染时生效，React 发现 props 浅比较相等、state 没变、context 没变、lanes 为空，就复用上一次的 Fiber 子树直接返回，省掉子树的重渲染。简单说：eagerState 省掉整次渲染，bailout 省掉子树遍历。
  3. 追问：为什么 setCount(count + 1) 连写三次只加 1，setCount(c => c + 1) 就能加 3？
    • 答：因为前者入队的 action 是一个已经算好的常量值，三次都是闭包里那个旧 count 加 1，结算时后面的覆盖前面的；后者入队的是函数，updateReducer 遍历链表时会把上一个的结果作为参数传给下一个，三次累积。这也是为什么「新值依赖旧值」时必须用函数式更新。
  4. 追问：React 18 的自动批处理和 17 有什么不同？flushSync 什么时候用？
    • 答：17 只在 React 合成事件的回调里批处理，setTimeout、Promise.then、原生事件监听里的多次 setState 会各自触发一次渲染；18 用 createRoot 后，所有场景都默认批处理（基于 lane 而不是基于「是否在事件中」）。需要绕过批处理、立刻拿到更新后的 DOM 时才用 flushSync，典型场景是 setState 之后马上要读 scrollHeight 做滚动定位 —— 但它会强制同步渲染，属于性能逃生舱，不能滥用。
  5. 追问：这次更新的优先级（lane）是从哪来的？
    • 答：来自 requestUpdateLane，它优先读当前的执行上下文：如果在 startTransition 里就拿 TransitionLane；否则读 Scheduler 当前的优先级，而这个优先级在事件系统分发时就根据事件类型设置好了（click 是离散事件 → SyncLane，scroll/mousemove 是连续事件 → ContinuousLane）。所以「点击比滚动优先」这件事是在事件层就决定的。

✅ 项目关联话术（按真实经历替换）：

我们有个批量勾选的表格，早期代码写的是 setSelected(selected.concat(id))，在一个循环里连续调用，结果只有最后一条被选中。排查清楚是闭包里的 selected 始终是旧值之后，我们统一把项目里所有「新值依赖旧值」的场景都改成函数式更新，并在 code review checklist 里加了这一条。后来做一个「setState 后立即滚动到新增行」的需求时，又遇到读到旧 DOM 高度的问题，用 flushSync 包住那次 setState 解决，同时在注释里写清了为什么这里必须同步。

题 7：React 的事件系统是怎么实现的？onClick 和原生 onclick 有什么区别？ ​

精简口述答案：

React 的 onClick 不会真的绑到那个 DOM 上，它是事件委托 + 合成事件。createRoot 的时候 React 就在根容器上把所有支持的事件类型各注册了一遍（捕获和冒泡两个阶段）。真实点击发生时，浏览器原生冒泡到根容器，React 的统一监听器被触发，它通过 DOM 节点上的 __reactFiber$xxx 属性找到对应的 Fiber，然后沿着 return 指针一路向上，把路径上所有同类型的回调收集成一个数组，再构造一个符合 W3C 标准的 SyntheticEvent 对象，最后模拟执行：捕获阶段倒序执行、冒泡阶段正序执行。这样做有三个收益：一是不管多少元素都只有根容器上的少量监听器，内存开销小；二是抹平了各浏览器的事件差异，e.target、e.stopPropagation() 行为完全一致；三是 React 可以在分发时根据事件类型给这次更新打上优先级 lane。

连环追问链：

  1. 追问：React 17 为什么把委托位置从 document 移到了根容器？
    • 答：为了支持多版本共存和微前端。委托在 document 时，页面上同时跑两个 React 版本（比如主应用 17、子应用 16）会互相干扰，一个 e.stopPropagation() 可能把另一个的事件也掐断；移到各自的根容器后，每个 React 实例的事件只在自己的子树内传播，天然隔离。顺带也解决了「React 事件和外层原生 jQuery 事件执行顺序反直觉」的问题。
  2. 追问：在 React 的 onClick 里调 e.stopPropagation()，能阻止外层 document 上的原生监听吗？
    • 答：不能。你的回调是在原生事件已经冒泡到根容器之后才被 React 模拟执行的，此时如果 document 上也有监听，它的执行顺序取决于它在根容器之上还是之下。e.stopPropagation() 只能阻断 React 自己收集的那条回调链。要真的阻止原生监听，得用 e.nativeEvent.stopImmediatePropagation()。
  3. 追问：React 事件和原生事件在同一个元素上的执行顺序？
    • 答：给同一个元素同时用 addEventListener 和 onClick，原生监听先执行（它在目标元素上，而 React 的监听在根容器上，要等冒泡上来）。所以「原生捕获 → 原生冒泡 → React 捕获 → React 冒泡」是常见的实际顺序。
  4. 追问：所有事件都是委托的吗？
    • 答：不是。scroll、load、error、abort、媒体类事件不冒泡，React 只能直接绑在目标元素上；selectionchange 这类也是特殊处理。所以不要假设「React 的所有事件都在根容器上」。
  5. 追问：事件池（event pooling）现在还有吗？
    • 答：React 16 为了减少 GC 会复用 SyntheticEvent 对象，回调执行完属性就被清空，异步里访问要先 e.persist()。React 17 已经移除了事件池，现在可以在 setTimeout 里安全访问 e.target。但面试里被问到老项目兼容时，要说清 e.persist() 的来历。

✅ 项目关联话术（按真实经历替换）：

我们做过一个「点击外部关闭下拉面板」的组件，在 document 上监听 click 做关闭，同时在触发按钮的 React onClick 里 e.stopPropagation() 想拦住它，结果面板点开就立刻关了。定位到是 React 的回调执行时原生事件已经到了 document 这一层，stopPropagation 根本来不及。最后的方案是不再依赖阻止冒泡，而是在 document 的处理函数里用 panelRef.current.contains(e.target) 做包含判断，顺带把这个逻辑抽成了 useClickOutside 在项目里复用。

题 1：实现简易版 useState（Hook 链表版） ​

核心实现：

// ============ 模拟 Fiber 与调度 ============
const fiber = {
  memoizedState: null, // Hook 链表头
  stateNode: null, // 组件函数
};
let workInProgressHook = null; // 当前正在处理的 Hook
let isMount = true; // 是否首次挂载

// 取出（或创建）当前这个 Hook —— 顺序即身份
function getHook() {
  if (isMount) {
    const hook = {
      memoizedState: null,
      queue: { pending: null }, // 环状更新链表
      next: null,
    };
    if (fiber.memoizedState === null) {
      fiber.memoizedState = hook; // 链表头
    } else {
      workInProgressHook.next = hook; // 串到尾部
    }
    workInProgressHook = hook;
    return hook;
  }
  // 更新阶段：按顺序往下取
  const hook =
    workInProgressHook === null ? fiber.memoizedState : workInProgressHook.next;
  workInProgressHook = hook;
  return hook;
}

// ============ useState ============
function useState(initialState) {
  const hook = getHook();

  if (isMount) {
    // 惰性初始化：支持传函数
    hook.memoizedState =
      typeof initialState === "function" ? initialState() : initialState;
  } else {
    // 消费更新队列
    let newState = hook.memoizedState;
    const pending = hook.queue.pending;
    if (pending !== null) {
      let update = pending.next; // 环状链表的第一个
      do {
        const action = update.action;
        // 支持函数式更新 setState(prev => next)
        newState = typeof action === "function" ? action(newState) : action;
        update = update.next;
      } while (update !== pending.next);
      hook.queue.pending = null; // 清空队列
    }
    hook.memoizedState = newState;
  }

  return [hook.memoizedState, dispatchAction.bind(null, hook.queue)];
}

function dispatchAction(queue, action) {
  const update = { action, next: null };
  // 维护成环状链表，pending 指向最后一个
  if (queue.pending === null) {
    update.next = update;
  } else {
    update.next = queue.pending.next;
    queue.pending.next = update;
  }
  queue.pending = update;

  schedule(); // 触发重新渲染
}

// ============ 渲染入口 ============
function schedule() {
  workInProgressHook = null; // 关键：每次渲染前重置指针
  const app = fiber.stateNode();
  isMount = false;
  return app;
}

// ============ 使用 ============
function App() {
  const [count, setCount] = useState(0);
  const [text, setText] = useState(() => "hi"); // 惰性初始化
  console.log("render:", count, text);
  return {
    add: () => setCount((c) => c + 1),
    setText: (v) => setText(v),
  };
}
fiber.stateNode = App;
let app = schedule(); // render: 0 hi
app.add(); // render: 1 hi

✅ 边界 Case 自测：

  • 一个组件里调用多个 useState，更新其中一个，其余状态是否保持正确？
  • useState(() => expensive()) 惰性初始化：初始函数是否只在 mount 执行一次？
  • setCount(5) 直接传值 与 setCount(c => c + 1) 函数式更新都要支持。
  • 同一次事件中连续调用三次 setCount(c => c + 1)，结果应是 +3 而不是 +1（环状队列按序消费）。
  • 新旧 state 用 Object.is 判断相等时应跳过本次渲染（eagerState 优化）。
  • 每次渲染前必须把 workInProgressHook 重置为 null，否则第二次渲染会从链表尾部继续取，直接取到 null。
  • 在条件语句里调用会导致链表错位 —— 可以手动验证一下报错现象。
  • 组件卸载后调用 setState 应被忽略，不应报错或内存泄漏。

function useReducer(reducer, initialArg, init) {
  const hook = getHook();

    hook.memoizedState = init ? init(initialArg) : initialArg;

题 2：实现简易版 useRef / useMemo / useCallback / useEffect ​

核心实现：

// 复用题 1 的 getHook()、isMount

// ============ 依赖浅比较 ============
function areDepsEqual(nextDeps, prevDeps) {
  if (prevDeps === null || nextDeps === null) return false;
  if (nextDeps.length !== prevDeps.length) return false;
  for (let i = 0; i < nextDeps.length; i++) {
    if (!Object.is(nextDeps[i], prevDeps[i])) return false; // 注意是浅比较
  }
  return true;
}

// ============ useRef ============
function useRef(initialValue) {
  const hook = getHook();
  if (isMount) {
    hook.memoizedState = { current: initialValue }; // 只创建一次
  }
  return hook.memoizedState; // 每次返回【同一个】对象引用
}

// ============ useMemo ============
function useMemo(create, deps) {
  const hook = getHook();
  const nextDeps = deps === undefined ? null : deps;

  if (!isMount) {
    const prev = hook.memoizedState; // [value, deps]
    if (prev !== null && nextDeps !== null && areDepsEqual(nextDeps, prev[1])) {
      return prev[0]; // 命中缓存
    }
  }
  const nextValue = create(); // 未命中 or 首次：重新计算
  hook.memoizedState = [nextValue, nextDeps];
  return nextValue;
}

// ============ useCallback：只是不执行 create ============
function useCallback(callback, deps) {
  const hook = getHook();
  const nextDeps = deps === undefined ? null : deps;

  if (!isMount) {
    const prev = hook.memoizedState;
    if (prev !== null && nextDeps !== null && areDepsEqual(nextDeps, prev[1])) {
      return prev[0];
    }
  }
  hook.memoizedState = [callback, nextDeps];
  return callback;
}

// ============ useEffect：收集 effect，渲染后统一执行 ============
const effectQueue = [];

function useEffect(create, deps) {
  const hook = getHook();
  const nextDeps = deps === undefined ? null : deps;
  const prev = hook.memoizedState; // { create, destroy, deps }

  if (!isMount && prev !== null && areDepsEqual(nextDeps, prev.deps)) {
    hook.memoizedState = { ...prev, deps: nextDeps }; // 依赖未变，跳过
    return;
  }

  const effect = {
    create,
    destroy: prev ? prev.destroy : undefined,
    deps: nextDeps,
  };
  hook.memoizedState = effect;
  effectQueue.push(effect); // 本次需要执行
}

// 渲染提交后调用：先清理上一次，再执行本次
function flushEffects() {
  effectQueue.forEach((effect) => {
    if (typeof effect.destroy === "function") effect.destroy();
    effect.destroy = effect.create(); // 返回值作为下次的清理函数
  });
  effectQueue.length = 0;
}

✅ 边界 Case 自测：

  • deps 传 undefined（不传）→ 每次渲染都重新计算 / 每次都执行 effect。
  • deps 传 [] → 只在首次计算一次，之后永远命中缓存。
  • deps 长度变化（如从 [a] 变成 [a, b]）→ 应判定为不相等并重算。
  • 依赖项是 NaN → 必须用 Object.is 而不是 ===，否则 NaN !== NaN 导致缓存永久失效。
  • 依赖项是对象字面量 → 每次都是新引用，缓存必然失效，需要提醒使用者。
  • useRef 返回的对象在多次渲染间必须是同一引用；修改 .current 不应触发渲染。
  • useEffect 的清理函数要在下次执行前和卸载时都被调用，且只调用一次。
  • useCallback 不应执行传入的函数，只缓存引用。

// 变种 1：手写 React.memo 的浅比较
function shallowEqual(objA, objB) {
  if (Object.is(objA, objB)) return true;
  if (typeof objA !== "object" || objA === null) return false;
  if (typeof objB !== "object" || objB === null) return false;

  const keysA = Object.keys(objA);
  const keysB = Object.keys(objB);
  if (keysA.length !== keysB.length) return false;

  return keysA.every(
    (key) =>
      Object.prototype.hasOwnProperty.call(objB, key) &&
      Object.is(objA[key], objB[key])
  );
}

function memo(Component, areEqual = shallowEqual) {
  let prevProps = null;
  let prevResult = null;
  return function MemoComponent(props) {
    if (prevProps !== null && areEqual(prevProps, props)) {
      return prevResult; // 命中：复用上次的渲染结果
    }
    prevProps = props;
    prevResult = Component(props);
    return prevResult;
  };
}

// 变种 2：usePrevious / useLatest / useDebounce
function usePrevious(value) {
  const ref = useRef();
  useEffect(() => {
    ref.current = value;
  }); // 渲染后才赋值，所以渲染中读到的是上一次的值
  return ref.current;
}

function useLatest(value) {
  const ref = useRef(value);
  ref.current = value; // 每次渲染同步，专治闭包陷阱
  return ref;
}

function useDebounce(fn, delay) {
  const fnRef = useLatest(fn);
  const timer = useRef(null);
  useEffect(() => () => clearTimeout(timer.current), []); // 卸载清理
  return useCallback(
    (...args) => {
      clearTimeout(timer.current);
      timer.current = setTimeout(() => fnRef.current(...args), delay);
    },
    [delay]
  ); // 引用稳定，但永远调用最新的 fn
}

function shouldYield() {
  return performance.now() >= deadline; // 时间片用尽就让出主线程
}

function performUnitOfWork(work) {
  work.doWork(); // 执行一个最小工作单元（对应一个 Fiber 的 beginWork）
  return work.next; // 返回下一个单元；返回 null 表示整棵树处理完
}

  while (nextUnitOfWork !== null && !shouldYield()) {
    nextUnitOfWork = performUnitOfWork(nextUnitOfWork);
  }
  if (nextUnitOfWork !== null) {
    schedulePerformWork(); // 还没做完 → 下一帧继续（恢复）

  }
}

  workLoop();
};

  port.postMessage(null); // 作为宏任务排到下一轮，浏览器有机会绘制与响应输入
}

function commitRoot() {
  console.log("commit: 同步操作 DOM，不可中断");
}

  • 单个工作单元本身超过 5ms（如一次 50ms 的计算）→ 时间切片无法拆分单个任务，仍会掉帧，这正是 Fiber 要求把工作拆到足够细的原因。
  • 中断后恢复时，nextUnitOfWork 必须准确指向上次的断点，不能重复执行也不能漏掉。
  • 高优先级任务插入时，应能打断当前低优先级循环（可扩展一个按 priority 排序的小顶堆任务队列）。
  • commitRoot 期间不应检查 shouldYield，必须一次性同步做完。

题 4：手写 Fiber 树的可中断深度优先遍历 ​

题目： 给定一棵由 { type, props, child, sibling, return } 构成的 Fiber 树，实现 beginWork / completeWork 两阶段遍历，要求可中断可恢复（配合题 3 的时间切片）。

核心实现：

js
// ---------- 1. Fiber 节点 ----------
function FiberNode(type, props) {
  this.type = type;
  this.props = props;
  this.child = null;    // 第一个子节点
  this.sibling = null;  // 下一个兄弟节点
  this.return = null;   // 父节点（不叫 parent，强调「归」的去向）
  this.memoizedState = null;
  this.flags = 0;       // 副作用标记
}

// ---------- 2. 全局指针：中断/恢复的关键 ----------
let workInProgress = null;   // 当前正在处理的 Fiber
let workInProgressRoot = null;
const logs = [];             // 仅用于观察遍历顺序

function prepareFreshStack(root) {
  workInProgressRoot = root;
  workInProgress = root;
  logs.length = 0;
}

// ---------- 3. 「递」：处理当前节点，返回下一个要处理的子节点 ----------
function beginWork(fiber) {
  logs.push(`begin:${fiber.type}`);
  // 真实 React 在这里：计算 state、调用函数组件、reconcileChildren 生成子 Fiber
  return fiber.child; // 没有子节点返回 null，进入「归」
}

// ---------- 4. 「归」：收集副作用，然后找兄弟或继续向上 ----------
function completeUnitOfWork(fiber) {
  let node = fiber;
  do {
    logs.push(`complete:${node.type}`);
    // 真实 React 在这里：创建/更新 DOM 实例、把 effect 冒泡给父节点
    if (node.sibling !== null) {
      workInProgress = node.sibling; // 有兄弟 → 转去「递」兄弟
      return;
    }
    node = node.return;              // 没兄弟 → 继续向上「归」
    workInProgress = node;
  } while (node !== null);
  // node 为 null 说明已经归到根的上方，整棵树处理完
}

// ---------- 5. 单个工作单元 ----------
function performUnitOfWork(fiber) {
  const next = beginWork(fiber);
  if (next === null) {
    completeUnitOfWork(fiber); // 叶子节点，立刻进入「归」
  } else {
    workInProgress = next;     // 继续向下「递」
  }
}

// ---------- 6. 同步版 workLoop ----------
function workLoopSync() {
  while (workInProgress !== null) {
    performUnitOfWork(workInProgress);
  }
}

// ---------- 7. 可中断版 workLoop ----------
function shouldYield() {
  return performance.now() >= deadline; // deadline 由时间切片调度器给出
}
let deadline = 0;

function workLoopConcurrent() {
  while (workInProgress !== null && !shouldYield()) {
    performUnitOfWork(workInProgress);
  }
  // 退出循环时 workInProgress 已经保存了断点，下次直接继续
  return workInProgress === null ? 'completed' : 'yielded';
}

function renderConcurrent(root, slice = 5) {
  prepareFreshStack(root);
  function tick() {
    deadline = performance.now() + slice;
    if (workLoopConcurrent() === 'yielded') {
      // 让出主线程，下一个宏任务继续（真实 React 用 MessageChannel）
      const mc = new MessageChannel();
      mc.port1.onmessage = tick;
      mc.port2.postMessage(null);
    } else {
      commitRoot(root);
    }
  }
  tick();
}

function commitRoot(root) {
  console.log('commit（不可中断）', root.type);
}

题 5：手写 useSyncExternalStore 与极简外部 store ​

核心实现：

// ---------- 1. 极简 store（zustand 的内核就是这个形状） ----------
function createStore(createState) {
  let state;
  const listeners = new Set();

  const setState = (partial) => {
    const next = typeof partial === 'function' ? partial(state) : partial;
    if (Object.is(next, state)) return;
    const prev = state;
    state = typeof next === 'object' && next !== null ? { ...state, ...next } : next;
    listeners.forEach((l) => l(state, prev));
  };
  const getState = () => state;
  const subscribe = (listener) => {
    listeners.add(listener);
    return () => listeners.delete(listener); // 必须返回取消订阅函数
  };

  state = createState(setState, getState);
  return { setState, getState, subscribe };
}

// ---------- 2. 手写 useSyncExternalStore ----------
function useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot) {
  // SSR 分支：服务端没有订阅，直接取服务端快照
  if (typeof window === 'undefined') {
    return (getServerSnapshot || getSnapshot)();
  }

  // 先同步读一次，保证本次渲染用到的是最新值（避免撕裂）
  const value = getSnapshot();
  const [{ inst }, forceUpdate] = useState({ inst: { value, getSnapshot } });

  // 渲染后校验：渲染期间 store 可能已经变了
  useLayoutEffect(() => {
    inst.value = value;
    inst.getSnapshot = getSnapshot;
    if (checkIfSnapshotChanged(inst)) {
      forceUpdate({ inst }); // 立刻重渲染，在用户看到之前修正
    }
  }, [subscribe, value, getSnapshot]);

  useEffect(() => {
    const handleChange = () => {
      if (checkIfSnapshotChanged(inst)) forceUpdate({ inst });
    };
    handleChange();               // 订阅前先补一次，防止订阅间隙丢更新
    return subscribe(handleChange);
  }, [subscribe]);

  useDebugValue(value);
  return value;
}

function checkIfSnapshotChanged(inst) {
  try {
    return !Object.is(inst.value, inst.getSnapshot());
  } catch {
    return true; // getSnapshot 抛错也当作变化，触发重渲染把错误抛给边界
  }
}

// ---------- 3. 封装带 selector 的 hook ----------
function createHook(store) {
  return function useStore(selector = (s) => s, isEqual = Object.is) {
    // 用 ref 缓存上一次 selector 的结果，实现「值不变就不重渲染」
    const lastRef = useRef();
    const getSnapshot = useCallback(() => {
      const next = selector(store.getState());
      if (lastRef.current !== undefined && isEqual(lastRef.current, next)) {
        return lastRef.current; // 返回同一个引用，useSyncExternalStore 内部 Object.is 判定未变
      }
      lastRef.current = next;
      return next;
    }, [selector, isEqual]);

    return useSyncExternalStore(store.subscribe, getSnapshot, getSnapshot);
  };
}

为什么必须用 useSyncExternalStore 而不是 useState + useEffect 手搓订阅？ 并发渲染下，React 可能中断一次渲染去处理高优先级任务，期间外部 store 变了；恢复渲染时先渲染好的组件用的是旧值、后渲染的用的是新值，同一屏出现两份数据，这就是 tearing（撕裂）。useSyncExternalStore 通过「渲染时同步读 + layout 阶段再校验一次」保证了整屏一致。
