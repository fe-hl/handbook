基础原理 ​

1. 为什么需要 LangGraph：Day27 那个 while 循环到底撑不住什么 ​

Day27 手写的最小 ReAct Agent，本质是这样一段代码：

python
while True:
    resp = llm.invoke(messages)
    if not resp.tool_calls:
        return resp.content
    messages.append(resp)
    for tc in resp.tool_calls:
        messages.append(tool_result(tc))

这段代码能跑通 80% 的 Demo，但一旦进生产就会在五个地方同时崩：

生产诉求裸 while 循环的处境
执行到第 7 步时服务重启全部状态在内存里，重启即丢，用户只能从头再问一遍
第 3 步是转账，要人工审批循环没法"暂停在中间"，只能阻塞住整个线程等输入
同时查 RAG + 查数据库 + 查天气要自己写线程池、自己合并结果、自己处理部分失败
产品要在前端画出"当前执行到哪一步"循环内部没有可观测的节点概念，只能靠日志猜
回滚到第 2 步换个分支重跑不可能，历史状态没有留存

一句话定位： LangGraph 不是"更高级的 Agent"，它是把 Agent 的控制流从 Python 代码里抽出来，变成一张可持久化、可中断、可回放、可并行的状态图。模型还是那个模型，工具还是那些工具，变的是谁来管流程。

和 LangChain 的关系也要说清楚，这是面试第一个送分题也是第一个送命题：

text
LangChain（LCEL Chain）         LangGraph
┌──────────────────────┐      ┌───────────────────────────────┐
│ prompt | llm | parser│      │  START → agent ⇄ tools → END  │
│ 单向、无环、一次走完   │      │  有向图，允许环、分支、并行      │
│ 状态 = 上一步的输出    │      │  状态 = 全局 State，节点共享     │
│ 中间状态不落盘         │      │  每个超步落 Checkpoint          │
│ 想暂停？没有这个概念    │      │  interrupt 原生支持人工介入      │
└──────────────────────┘   └───────────────────────────────┘

容易被问倒的边界：LangGraph 不依赖 LangChain 的 Chain 体系，它只是复用了 langchain-core 的 BaseMessage、BaseChatModel 这些基础抽象。你完全可以用 LangGraph + 裸 OpenAI SDK，不写一行 LCEL。所以"LangGraph 是 LangChain 的升级版"这个说法是错的，准确说法是：LCEL 解决数据流编排，LangGraph 解决控制流编排，二者正交。

2. 核心概念五件套：State、Node、Edge、Conditional Edge、Graph ​

text
                    ┌──────────── State（全局状态，贯穿整张图）────────────┐
                    │  messages / query / retrieved_docs / step_count ... │
                    └─────────────────────────────────────────────────────┘
                          ▲ 读            ▲ 读            ▲ 读
                              │ 写 patch      │ 写 patch      │ 写 patch
   START ──→ ┌──────────┐ ──→ ┌──────────┐ ──→ ┌──────────┐ ──→ END
             │  Node A  │     │  Node B  │     │  Node C  │
             └──────────┘     └──────────┘     └──────────┘
                   │                ▲
                   └── Conditional Edge（读 State 决定下一跳）
概念是什么代码形态最容易搞错的点
State全图共享的一份数据结构TypedDict / Pydantic BaseModel / dataclass它不是"节点间传参"，而是一块带**合并规则（reducer）**的共享内存
Node一个执行单元def node(state) -> dict返回值是增量 patch，不是完整 State
Edge固定跳转add_edge("a", "b")A 到 B 无条件执行；同一节点出多条普通边 = 并行
Conditional Edge动态跳转add_conditional_edges("a", router, {...})路由函数只能读 State，不能改 State
Graph图本身StateGraph(State) → .compile()必须 compile() 才能执行；编译期会校验孤立节点、不可达 END
python
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]   # 带 reducer：追加
    query: str                                 # 不带 reducer：覆盖
    retry: int

builder = StateGraph(AgentState)
builder.add_node("agent", agent_node)
builder.add_node("tools", tool_node)
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", should_continue, {"tools": "tools", "end": END})

graph = builder.compile()

3. State 的本质：带 reducer 的共享内存，不是"传参" ​

这是 LangGraph 最核心、也是新手 90% 的 bug 来源。节点返回的不是新 State，而是一份"写请求"（patch），框架拿 reducer 把它合并进全局 State。

text
节点返回 {"messages": [AIMessage(...)], "retry": 1}
                    │
                    ▼
       ┌──────── 合并阶段 ────────┐
       │ messages: 有 reducer      │ → old + new（追加）
       │           add_messages    │
       │ retry:   无 reducer       │ → 直接覆盖 old
       └──────────────────────────┘
                    ▼
            新的全局 State → 落 Checkpoint
声明方式合并行为适用场景
query: str覆盖（last write wins）单值字段：用户问题、当前意图、最终答案
messages: Annotated[list, add_messages]按 id 追加/更新/删除对话历史，唯一正确写法
docs: Annotated[list, operator.add]列表拼接多路检索结果汇总
logs: Annotated[list, my_merge]自定义函数 (old, new) -> merged去重、排序、取 TopK、RRF 融合

✅ 正确：返回增量

python
def agent_node(state: AgentState):
    resp = llm_with_tools.invoke(state["messages"])
    return {"messages": [resp]}          # 只返回新增的那一条

❌ 错误写法一：返回完整 State

python
def agent_node(state: AgentState):
    resp = llm_with_tools.invoke(state["messages"])
    state["messages"].append(resp)
    return state                          # 看起来"对"，实际埋了两个雷

雷在哪：① 原地 append 直接改了上一个 Checkpoint 的对象引用，时间旅行回放时拿到的是被污染的历史；② 整个 messages 列表又被 add_messages 走一遍合并 —— 这里侥幸不炸，是因为 add_messages 会按 message.id 去重覆盖，但换成 operator.add 的字段就会直接翻倍。

❌ 错误写法二：对无 reducer 的字段期望累加

python
class S(TypedDict):
    count: int                            # 没有 reducer

def n(state: S):
    return {"count": state["count"] + 1}  # ✅ 这样是对的（自己算好再覆盖）

def n_wrong(state: S):
    return {"count": 1}                   # ❌ 以为会累加，实际永远是 1

记住这句话：Annotated[X, reducer] 里的 reducer 是"写冲突裁决规则"。 串行执行时它决定"新旧怎么合"，并行执行时它决定"多个节点同时写同一个 key 怎么合"。没有 reducer 的 key 在并行场景下会直接抛 InvalidUpdateError —— 这是高级深挖第 1 条要展开的内容。

4. 节点函数的四条契约 ​

python
def my_node(state: AgentState, config: RunnableConfig) -> dict:
    ...
    return {"some_key": value}
契约说明违反后果
入参 1 = state框架注入当前全局状态（只读语义）原地修改会污染 Checkpoint 历史
入参 2 = config（可选）拿 thread_id、callbacks、自定义 configurable不透传 config，LLM 的 token 流和 LangSmith 链路就断了
返回值 = dict / Command / Nonedict 是 patch；Command 可同时改状态+跳转；None 表示不改状态返回非法 key 时 TypedDict 不报错但静默丢弃，Pydantic State 会直接抛错
必须幂等节点可能因为重试、中断恢复、超步失败而重复执行扣款类节点重跑 = 重复扣款

同步节点与异步节点不能混搭：图里有 async def 节点，就必须用 await graph.ainvoke(...) / graph.astream(...)；用 graph.invoke() 会直接报错。反之全同步节点用 ainvoke 是允许的（框架丢线程池跑），但同步节点里的阻塞 IO 会卡住事件循环，这就回到 Day21 讲的 asyncio 那套结论。

5. 边的三种形态：固定边、条件边、并行边 ​

python
# ① 固定边：无条件跳转
builder.add_edge("tools", "agent")

# ② 条件边：路由函数返回"键"，映射表决定去哪个节点
def should_continue(state: AgentState) -> str:
    last = state["messages"][-1]
    if getattr(last, "tool_calls", None):
        return "use_tool"
    return "finish"

builder.add_conditional_edges(
    "agent",
    should_continue,
    {"use_tool": "tools", "finish": END},   # ← 映射表，强烈建议显式写
)

# ③ 并行边：同一个源节点挂多条固定边 → fan-out
builder.add_edge("plan", "search_rag")
builder.add_edge("plan", "search_web")
builder.add_edge("plan", "search_db")
builder.add_edge("search_rag", "merge")      # fan-in
builder.add_edge("search_web", "merge")
builder.add_edge("search_db", "merge")

条件边两个高频坑：

❌ 坑✅ 正确做法
路由函数返回了映射表里没有的键要么补全映射表，要么不传映射表（此时返回值必须就是节点名本身）
在路由函数里改 State路由函数的返回值只用于选路，对 State 的修改会被丢弃；要改状态就用 Command

路由函数还可以返回列表，表示同时走多个分支（动态 fan-out）：

python
def dispatch(state) -> list[str]:
    targets = []
    if state["need_rag"]:
        targets.append("search_rag")
    if state["need_web"]:
        targets.append("search_web")
    return targets or ["fallback"]

连完边一定要先自检图结构，再去调 LLM。编译后的图能把自己的拓扑打出来，这是排"为什么它不走我想的那条边"最快的手段：

python
print(graph.get_graph().draw_ascii())        # 终端直接看拓扑
print(graph.get_graph(xray=1).draw_ascii())  # xray=1 展开子图内部节点

自检要看什么说明
条件边有没有连到 END少了这条分支 = 永远循环，直到撞 recursion_limit
有没有不可达节点节点名拼错时 add_edge 不报错，图上会出现一个孤岛
回边方向对不对tools → agent 写反成 agent → tools 会变成两条平行边，直接并行执行
返回 Command 的节点连线必须写 -> Command[Literal["a", "b"]] 注解，框架靠它推断连线，否则图上看不到这条边

6. 执行模型：超步（super-step）与 Pregel BSP ​

LangGraph 的执行引擎抄的是 Google Pregel 的 BSP（Bulk Synchronous Parallel）模型。理解这一点，并行、Checkpoint 时机、部分失败这三个问题就全通了。

text
超步 1                      超步 2                      超步 3
┌──────────────┐           ┌──────────────┐           ┌──────────────┐
│   plan       │           │ search_rag   │  并行      │   merge      │
│              │           │ search_web   │  同一超步  │              │
└──────────────┘           │ search_db    │           └──────────────┘
       │                   └──────────────┘                  │
       ▼                          ▼                          ▼
 ┌─ 屏障 barrier ─┐        ┌─ 屏障 barrier ─┐        ┌─ 屏障 barrier ─┐
 │ 合并所有 patch │        │ 用 reducer 合并 │        │ 合并 patch     │
 │ 落 Checkpoint  │        │ 三份 patch      │        │ 落 Checkpoint  │
 └────────────────┘        │ 落 Checkpoint   │        └────────────────┘
                           └─────────────────┘
结论含义
同一超步内的节点并行执行它们看到的是同一份超步开始时的 State 快照，互相看不到对方的写入
超步结束才合并、才落盘所以 Checkpoint 的粒度是超步，不是节点
超步内任一节点抛异常整个超步的写入不落盘，恢复时该超步的所有节点一起重跑 → 节点必须幂等
节点数 = 执行步数？不是并行的 3 个节点只算 1 步，这直接关系到 recursion_limit 怎么算

面试加分表述：「LangGraph 的并行不是"开线程池跑任务"，而是 BSP 的超步并行 —— 同一超步的节点看不到彼此的中间状态，必须等屏障处用 reducer 统一合并。所以写并行节点时，绝不能假设'另一个分支已经把数据写进去了'，有依赖关系就必须拆成两个超步。」

7. 最小可运行 Graph：把 Day27 的 ReAct 图化 ​

python
from typing import Annotated, TypedDict
from langchain_core.messages import SystemMessage
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode, tools_condition

@tool
def get_weather(city: str) -> str:
    """查询指定城市的实时天气。city 传中文城市名，如 '北京'。"""
    return f"{city} 晴 26℃"

tools = [get_weather]
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0).bind_tools(tools)

class State(TypedDict):
    messages: Annotated[list, add_messages]

SYSTEM = SystemMessage("你是严谨的助手，信息不足时必须调用工具，不要编造。")

def agent(state: State):
    return {"messages": [llm.invoke([SYSTEM] + state["messages"])]}

builder = StateGraph(State)
builder.add_node("agent", agent)
builder.add_node("tools", ToolNode(tools))       # 预制件：自动执行 tool_calls
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", tools_condition)  # 预制件：有 tool_calls 就去 tools
builder.add_edge("tools", "agent")
graph = builder.compile()

out = graph.invoke({"messages": [("user", "北京天气怎么样")]})
print(out["messages"][-1].content)

两个预制件的隐含约定必须记住：

预制件做了什么隐含约定（踩坑点）
ToolNode(tools)读最后一条 AIMessage 的 tool_calls，并发执行所有工具，把结果包成 ToolMessage 返回State 里必须有名为 messages 的键；工具抛异常时默认把错误文本当 ToolMessage 返回给模型（handle_tool_errors）
tools_condition有 tool_calls 返回 "tools"，否则返回 END工具节点必须叫 tools，改名就要自己写映射表 {"tools": "my_tool_node", END: END}

15. Send API：真正的动态 map-reduce ​

class State(TypedDict):
    chapters: list[str]
    summaries: Annotated[list, operator.add]   # ← fan-in 必须有 reducer
    final: str

# map：为每个 chapter 动态生成一个任务
def fan_out(state: State):
    return [Send("summarize_one", {"chapter": c}) for c in state["chapters"]]

# 被 Send 调用的节点，收到的 state 就是 Send 的第二个参数，不是全局 State！
def summarize_one(payload: dict):
    s = llm.invoke(f"总结这一章：{payload['chapter']}").content
    return {"summaries": [s]}                   # 写回全局 State，靠 reducer 合并

# reduce
def reduce_all(state: State):
    return {"final": llm.invoke("合并这些摘要：" + "\n".join(state["summaries"])).content}

builder.add_edge("summarize_one", "reduce_all")
Send 的三个关键语义说明
接收节点拿到的是自定义载荷不是全局 State，所以别在里面写 state["messages"]

N 个 Send = 一个超步不消耗 N 次 recursion_limit

1. reducer 的三类冲突，以及自定义 reducer 的正确写法 ​

reducer 是 LangGraph 里最容易出事的地方，因为它的错误不报异常，只是结果不对。

冲突类型现象根因修法
覆盖冲突并行两个节点写同一个无 reducer 字段默认 reducer 是 last_value，但并行时"谁最后"不确定要么加 reducer，要么拆成两个字段
累加冲突list 字段越跑越长，里面全是重复项用了 operator.add 但节点非幂等、重跑时又追加一遍reducer 里做去重，或改用 dict 按 key 覆盖
类型冲突reducer 收到 None 直接抛 TypeError节点返回了 {"docs": None}reducer 必须自己处理 None 和首次初始化

from typing import Annotated, TypedDict

def merge_docs(left: list | None, right: list | None) -> list:
    """按 doc_id 去重合并，右侧覆盖左侧 —— 幂等、可重跑"""
    left = left or []
    right = right or []
    merged = {d["id"]: d for d in left}
    for d in right:
        merged[d["id"]] = d
    return list(merged.values())

def keep_max_score(left: float | None, right: float | None) -> float:
    return max(left or 0.0, right or 0.0)

class State(TypedDict):
    docs: Annotated[list, merge_docs]      # ✅ 幂等合并
    best: Annotated[float, keep_max_score] # ✅ 并行写也不冲突
    answer: str                            # 只有单一节点写，无需 reducer

判断口诀：一个字段会不会被"两个以上节点"或"同一节点重跑两次"写入？会，就必须给它一个幂等的 reducer。

防误用input_schema 之外的字段传进来会被忽略，不会悄悄污染状态
中间态不落 Checkpoint 外泄私有字段依然会进 checkpoint，但不会出现在返回值里

注意：output_schema 只裁剪返回值，不裁剪 checkpoint。 真正敏感的数据（用户身份证、原始 token）不要放 State，应该放 config["configurable"] 或外部存储，因为 State 是会被完整序列化落盘的。

3. add_messages 的隐藏能力：按 id 覆盖与 RemoveMessage ​

很多人以为 add_messages 就是 list.append，其实它是按 id 的 upsert。

from langchain_core.messages import RemoveMessage, HumanMessage, REMOVE_ALL_MESSAGES

# ① 按 id 覆盖：修正上一条消息而不是追加
def edit_node(state):
    last = state["messages"][-1]
    return {"messages": [HumanMessage(content="改过的问题", id=last.id)]}

# ② 删除指定消息：做上下文裁剪
def trim_node(state):
    old = state["messages"][:-10]
    return {"messages": [RemoveMessage(id=m.id) for m in old]}

# ③ 清空重开（0.3+）
def reset_node(state):
    return {"messages": [RemoveMessage(id=REMOVE_ALL_MESSAGES)]}
行为触发条件
追加新消息没有 id 或 id 不存在
覆盖新消息的 id 与已有消息相同
删除传 RemoveMessage(id=...)

坑：删除 AIMessage(tool_calls=[...]) 时必须连带删掉对应的 ToolMessage，否则下一轮请求会因为"有 tool 响应但找不到对应 tool_call"被 OpenAI 直接 400。裁剪上下文时要以完整的 tool 回合为单位切，不能按条数硬切。

4. 上下文工程：三种裁剪策略挂在图的什么位置 ​

Agent 跑长了必然爆上下文。LangGraph 的做法是把裁剪本身做成一个节点，而不是在调用 LLM 前临时处理。

START → agent ⇄ tools
          ↑
       manage_ctx   ← 每轮进 agent 前先过一遍裁剪节点
策略实现适用
滑动窗口trim_messages(max_tokens=..., strategy="last")客服、闲聊，旧信息无价值
摘要压缩超过阈值时调 LLM 把前 N 条压成一条 SystemMessage，再 RemoveMessage 掉原文长任务、需要记住早期结论
外置检索全量消息写入 Store，每轮只检索相关片段塞进 prompt超长对话、跨会话记忆
python
from langchain_core.messages import trim_messages

def manage_ctx(state):
    msgs = state["messages"]
    if count_tokens(msgs) < 60_000:
        return None                              # ← 返回 None = 不改状态，省一次写盘
    summary = llm.invoke(SUMMARY_PROMPT + render(msgs[:-6])).content
    return {
        "messages": [RemoveMessage(id=m.id) for m in msgs[:-6]]
                    + [SystemMessage(content=f"【历史摘要】{summary}")],
    }

面试加分点： 「裁剪必须做成独立节点而不是在 agent 节点里顺手做，原因是 ① 裁剪结果要落 Checkpoint，否则断点恢复后又得重新压一遍、白花一次 LLM 调用；② 摘要本身是一次 LLM 调用，做成节点才能被 stream 观测到和被重试策略覆盖。」

5. Store：跨 thread 的长期记忆 ​

Checkpointer 存的是单个 thread 的短期状态，换个 thread_id 就什么都不记得了。跨会话记忆要用 Store。

python
from langgraph.store.memory import InMemoryStore
# 生产：from langgraph.store.postgres import PostgresStore

store = InMemoryStore(index={"embed": embeddings, "dims": 1536})

def remember(state, *, store):                      # 节点签名注入 store
    uid = state["user_id"]
    store.put(("memories", uid), key=str(uuid4()), value={"text": state["fact"]})
    return None

def recall(state, *, store):
    uid = state["user_id"]
    hits = store.search(("memories", uid), query=state["question"], limit=3)
    return {"context": [h.value["text"] for h in hits]}

graph = builder.compile(checkpointer=checkpointer, store=store)
维度CheckpointerStore
作用域单 thread_id按 namespace（通常是 (类型, user_id)）跨 thread
内容完整 State 快照 + 执行进度自定义 KV 文档
典型用途断点续跑、时间旅行用户画像、偏好、长期事实

架构话术： 「短期记忆靠 Checkpointer 自动落盘，长期记忆靠 Store 显式读写。写长期记忆有两种时机 —— 热路径（对话中实时抽取，延迟高但即时生效）和后台（会话结束后异步总结，不影响响应速度）。我们选后台，因为用户不会在同一句话里既告诉你偏好又要求你立刻用上。」

6. 并行节点的事务性：超步失败到底回滚了什么 ​

超步 N 开始
  ├─ node_a ✅ 完成 → 写入 pending_writes
  ├─ node_b ✅ 完成 → 写入 pending_writes
  └─ node_c ❌ 抛异常
       ↓
  整个超步不提交 → State 保持超步 N-1 的样子
  但 a/b 的 pending_writes 已落盘
       ↓
  恢复时：a、b 不再重跑（复用 pending_writes），只重跑 c
关键结论工程含义
State 以超步为事务单位提交超步内任一节点失败，这一步的状态更新全部不可见
成功节点的结果存在 pending_writes恢复后不会重复调 LLM，这是省钱的关键机制
但副作用无法回滚node_a 已经扣过款、已经发过邮件，LangGraph 管不了

所以生产里的铁律：有外部副作用的节点必须自带幂等键。 比如下单节点用 f"{thread_id}:{checkpoint_id}:order" 作为幂等 token 传给下游服务，让下游去重，而不是指望框架帮你回滚。

8. Command：一个返回值同时干"改状态"和"跳转"两件事 ​

条件边的问题是：路由决策和状态更新被硬拆成两个地方，路由函数只能读不能写，节点只能写不能决定去哪。Command 把两者合一。

python
from langgraph.types import Command
from typing import Literal

def router_node(state) -> Command[Literal["billing", "tech", "human"]]:
    intent = classify(state["messages"][-1].content)
    return Command(
        update={"intent": intent, "route_log": [intent]},   # 改状态
        goto=intent if intent in ("billing", "tech") else "human",  # 同时决定去哪
    )

builder.add_node("router", router_node)
# 注意：用了 Command 的节点不需要 add_conditional_edges，
# 但要靠返回类型注解 Command[Literal[...]] 让 LangGraph 画出图的连线
用法写法场景
状态 + 跳转Command(update=..., goto=...)路由节点、Agent handoff
跳到父图Command(goto="x", graph=Command.PARENT)子图里决定退出到父图的某个节点
恢复中断Command(resume=人工输入)HITL 续跑
并行 fan-outCommand(goto=[Send(...), Send(...)])动态 map

对比话术： 「条件边适合纯路由（决策不依赖写状态）；Command 适合决策和状态耦合的场景，典型就是多 Agent 的 handoff —— 交接的同时要把任务描述写进共享状态。另外子图想跳回父图的兄弟节点，只有 Command(graph=Command.PARENT) 能做到，条件边做不到。」

9. 多智能体四种拓扑，面试必须能画出来 ​

① Network（全连接）           ② Supervisor（中心调度）
    A ⇄ B                          ┌──→ A ──┐
    ⇅ ╳ ⇅                     Sup ─┼──→ B ──┼─→ 回 Sup
    C ⇄ D                          └──→ C ──┘

③ Hierarchical（分层）        ④ Swarm（去中心交接）
    TopSup                         A ──handoff──→ B
     ├─ SubSup1 ─ A, B                 ↖─────────↙
     └─ SubSup2 ─ C, D             （谁接手就由谁继续对话，直到再交接）
拓扑实现要点优点缺点
Network每个 Agent 都能 goto 任意 Agent最灵活token 爆炸、容易绕圈，几乎不用于生产
SupervisorSupervisor 是唯一的路由节点，子 Agent 做完回边指向它可控、好调试、好限流Supervisor 是单点，prompt 会越来越长
HierarchicalSupervisor 的下级也是 Supervisor（子图）能撑几十个 Agent层级深 → 延迟高
Swarm用 handoff 工具 + Command 把控制权交出去对话连贯、无中心开销全局可观测性差，谁在负责要靠状态记录
python
# Supervisor 的最小实现：结构化输出决定下一个 Agent
class Route(BaseModel):
    next: Literal["researcher", "coder", "FINISH"]

def supervisor(state) -> Command[Literal["researcher", "coder", "__end__"]]:
    r = llm.with_structured_output(Route).invoke(SUP_PROMPT + state["messages"])
    return Command(goto=END if r.next == "FINISH" else r.next)

选型话术： 「两三个角色、流程线性 → 直接子图串起来；角色多但职责清晰、需要集中限流和审计 → Supervisor；强调对话体验、角色之间是"转接客服"关系 → Swarm。我们选 Supervisor，因为它能在一个地方统一做预算控制和越权拦截。」

10. Handoff 的标准实现：让工具返回 Command ​

多 Agent 交接的工业写法不是在 prompt 里写"请把问题转给 X"，而是把交接变成一个工具。

python
from langchain_core.tools import tool, InjectedToolCallId
from langgraph.prebuilt import InjectedState

def make_handoff(agent_name: str):
    @tool(f"transfer_to_{agent_name}", description=f"把任务交接给 {agent_name}")
    def handoff(
        task: str,
        state: Annotated[dict, InjectedState],
        tool_call_id: Annotated[str, InjectedToolCallId],
    ) -> Command:
        tool_msg = ToolMessage(
            content=f"已交接给 {agent_name}", tool_call_id=tool_call_id
        )
        return Command(
            goto=agent_name,
            graph=Command.PARENT,                       # 跳到父图的兄弟 Agent
            update={"messages": state["messages"] + [tool_msg],
                    "task_desc": task},                 # 把任务描述一起带过去
        )
    return handoff
细节为什么不能省
必须返回 ToolMessage不返回就留下一个"悬空的 tool_call"，下一轮 LLM 请求直接 400
必须带 graph=Command.PARENTAgent 自己是子图，目标 Agent 是父图里的兄弟节点，不加就会在子图里找不到目标
必须显式传 task不要让下一个 Agent 从几十条历史里猜任务，显式交接任务描述能明显提升成功率

11. Checkpoint 膨胀：被忽略的存储炸弹 ​

Checkpoint 是每个超步存一份全量 State，不是存 diff。一个 20 轮对话的 Agent 很容易写出几十 MB。

膨胀来源治理手段
每超步一份全量快照生产用 PostgresSaver（大字段走 blob 表、按 channel 版本去重），别用 SqliteSaver 扛并发
State 里塞了检索到的原文只存 doc_id + 摘要，原文留在向量库，节点内按需取
messages 无限增长配裁剪节点（深挖 4），并用 RemoveMessage 真正删掉
历史 thread 永不清理按 thread_id 建定时任务删 N 天前的 checkpoint；或业务结束时主动 delete_thread
调试期开了 stream_mode="debug" 全量落盘生产关掉
python
# 0.6+ 的 durability 三档：用写盘时机换性能
graph.invoke(inputs, config, durability="async")
durability行为取舍
"exit"只在整图结束时写一次最快，中途崩了全丢 —— 只适合纯计算、无 HITL
"async"超步结束后异步写，不阻塞下一步默认推荐，极端情况下可能丢最后一个超步
"sync"超步结束后同步写完才继续最慢但最可靠，HITL / 付费类流程用这个

12. 节点级可靠性：retry_policy 与 cache_policy ​

重试不该写在节点函数里，否则重试次数不会被 Checkpoint 记录，恢复后计数归零。

python
from langgraph.types import RetryPolicy, CachePolicy

builder.add_node(
    "call_llm", call_llm,
    retry=RetryPolicy(
        max_attempts=3,
        initial_interval=0.5,
        backoff_factor=2.0,

        retry_on=lambda e: isinstance(e, (RateLimitError, APITimeoutError)),  # ← 只重试可恢复错误

配置不配会怎样

jitter不开就会出现"多个并行节点同时被限流、同时退避、同时重试"的雷群效应
cache_policy调试时每改一行 prompt 都要把前面所有节点重跑一遍，LLM 账单飞涨

缓存的坑：缓存键由节点输入计算，含时间戳/随机 id 的输入永远不会命中。 想让缓存生效，就别把 datetime.now() 塞进 State。

15. 安全：把图当权限边界用 ​

Agent 的安全问题不是"模型会不会说坏话"，而是它手里的工具权限太大。LangGraph 的图结构正好可以当权限边界。

用户输入
   ↓
[输入校验节点]  ← prompt 注入检测、敏感词、租户归属校验
   ↓
[agent]  ⇄  [只读工具]        ← 低风险，自动执行
   ↓
[风险分级节点] → 高风险？
   ↓ 是                ↓ 否
[interrupt 人工审批]   [写操作工具]
风险图层面的解法
Prompt 注入让 Agent 调危险工具把写操作工具放在审批节点之后，模型根本拿不到它的调用权
工具返回的内容里带指令（间接注入）在 tools 节点后加一个清洗节点，把工具结果标记为"数据而非指令"
越权访问他人数据user_id 从 config["configurable"] 取，绝不从 State / 模型输出取（模型可被诱导改 State）
工具参数被诱导成 rm -rf工具内部做白名单校验，失败就返回错误让模型重试，而不是抛异常中断整图
无限循环烧钱四道闸门（基础 9）+ 按 user_id 的日预算

面试金句： 「身份与权限必须走 config，不能走 State。因为 State 是模型可以写的，而 config 是调用方注入、模型完全看不到也改不了的 —— 这是 LangGraph 里唯一可信的通道。」

17. 性能：延迟都花在哪，以及怎么压 ​

延迟来源优化手段
串行的 ReAct 轮次（最大头）① 支持并行 tool_calls，让一轮调多个工具；② 给模型更好的工具描述减少试错轮次
每超步的 Checkpoint 写盘durability="async"；State 瘦身
首 token 等待stream_mode="messages" 直接把 token 透给前端；路由/分类节点换小模型
子图层级过深层级每多一层就多一次完整的状态序列化，控制在 2 层内
工具自身慢工具内部加缓存 + 超时；用 cache_policy 挡住重复调用

一条反直觉的结论：把并行节点开得越多不一定越快，因为超步有屏障 —— 整个超步的耗时等于最慢那个节点。所以并行分支的耗时要尽量均衡，一个 10s 的节点和四个 1s 的节点并行，总耗时还是 10s。

20. Double-texting：用户没等回答完就又发了一条 ​

这是真实流量里一定会遇到、Demo 里永远遇不到的问题：上一轮还在跑工具，用户又发来一条消息，同一个 thread_id 出现并发写。

t0  用户: "帮我查下 A 的库存"     → 图开始跑，正在调工具
t1  用户: "算了，查 B 的"         → 第二个请求进来，同一个 thread_id

                    两个 run 同时往同一份 checkpoint 写 → 状态错乱

四种处理策略，对应到产品体验上是四种不同的交互：

策略行为适合场景
reject直接拒掉第二条，提示"上一条还在处理"金融、工单类严肃场景，宁可不响应也不能乱
enqueue第二条排队，等第一个 run 结束再跑用户在补充信息（"还有一点..."）
rollback取消第一个 run 并回滚它写过的状态，只跑第二条用户明显在改主意（"算了"）
interrupt中断第一个 run 但保留已完成的部分，再跑第二条通用默认值，体验最自然

python
# ① 同 thread 串行化：Redis 锁，粒度是 thread_id 而不是用户
async def run_locked(thread_id, payload):
    lock = redis.lock(f"lg:{thread_id}", timeout=120)
    if not await lock.acquire(blocking=False):
        raise Busy("上一条还在处理")          # ← reject 策略
    try:
        return await graph.ainvoke(payload, cfg(thread_id))
    finally:
        await lock.release()

# ② 可取消：把 run 的 task 存起来，新请求进来时 cancel 掉旧的（interrupt 策略）
task = asyncio.create_task(graph.ainvoke(payload, cfg(thread_id)))
RUNNING[thread_id] = task
实现要点说明
锁的粒度是 thread_id按用户加锁会导致他开两个会话都被互相阻塞
cancel 之后状态是干净的取消点落在超步边界，上一个超步已提交、当前超步整体不提交
rollback 要能定位回滚点用 get_state_history 找到该 run 开始前的 checkpoint_id，带着它重新 invoke
必须给前端明确信号被 reject / 被 interrupt 都要有独立事件类型，否则前端只能看到"消息发出去没反应"

面试话术： 「我们默认用 interrupt 语义：新消息进来就取消正在跑的 run，但保留它已经完成的超步，所以用户追问时之前检索到的文档不会白跑。写操作类节点我们单独改成 reject，因为那种场景下中途取消的歧义比等一会儿更难解释。」

❓ 高频面试题【基础简答 + 连环追问链 + 精简口述答案 + 项目关联话术】 ​

题 1：LangGraph 是什么？它和 LangChain 是什么关系，为什么不用 LCEL 就够了 ​

精简口述答案（90 秒版）

LangGraph 是 LangChain 团队做的有状态、可循环的 Agent 编排框架，底层是 Pregel 的 BSP 模型。它和 LCEL 不是替代关系而是正交的：LCEL 管的是数据流，把 prompt、model、parser 用管道串成一个 DAG，特点是单向、无环、无状态；LangGraph 管的是控制流，支持循环、分支、并行、中断、恢复，节点内部通常还是用 LCEL 写的。为什么 LCEL 不够？因为 Agent 的本质是循环——"想→做→观察→再想"，DAG 画不出环。那我自己写 while 循环行不行？能跑但撑不住生产，缺五样东西：状态持久化、断点续跑、人工审批、执行过程可观测、多角色协作。LangGraph 正好把这五样做成了基础设施：State 是带 reducer 的共享内存，Checkpointer 每个超步自动落盘，interrupt 能在任意节点暂停等人工，stream 能把每一步的进度推给前端。

追问答题要点
底层为什么选 Pregel？图计算的 BSP 模型天然适配"一批节点并行执行 → 屏障同步 → 合并状态 → 下一轮"，和 Agent 的多步推理同构
节点里还能用 LCEL 吗？能，而且应该。节点内部是 prompt | llm | parser 这样的链，节点之间才是图
什么场景不该上 LangGraph？流程固定、步数 ≤ 3、不需要持久化和人工介入 —— 这时候裸循环或 LCEL 更好维护
和 Dify / Coze 这类低代码编排的区别？低代码是产品，适合固定流程、非开发者配置；LangGraph 是库，适合需要精细控制状态、重试、权限的自研系统

✅ 项目关联话术：我们第一版知识库助手是 Day27 那种裸 while 循环，上线两周踩了两个问题。第一是链路长的任务一旦中途失败就得全量重跑，一次检索 + 两次 LLM 的钱白花；第二是有写操作的工具必须人工确认，但 HTTP 一次请求内没法等人，我们只能把流程硬拆成两个接口、自己把中间上下文塞 Redis，代码很脏。换成 LangGraph 后，前者靠 Checkpoint 的 pending_writes 直接复用成功节点的结果，后者靠 interrupt 一行搞定，我们删掉了大约 200 行自己写的状态管理代码。

题 2：State 和 reducer 讲一下，为什么并行节点写同一个字段会报错 ​

精简口述答案（90 秒版）

State 不是"函数传参"，而是一块所有节点共享的内存，每个字段是一个带 reducer 的通道。节点的返回值不是新 State，而是一个 patch——只写你想改的字段，框架按该字段的 reducer 把 patch 合并进全局 State。reducer 的签名是 (旧值, 新值) -> 合并后的值。不加 Annotated 的字段，默认 reducer 是"直接覆盖"；加了 operator.add 就是追加；messages 一般用 add_messages，它不是简单 append，而是按消息 id 做 upsert，还支持 RemoveMessage 删除。

并行写报 InvalidUpdateError 的原因是：同一个超步里两个节点都给同一字段写了值，默认的覆盖型 reducer 没法决定"谁赢"——如果让它随机覆盖，结果就不确定了，而不确定的状态会让 Checkpoint 恢复也不可复现。所以框架选择直接报错，强迫你显式声明合并语义。修法就是给这个字段加一个幂等的 reducer，或者让两个节点写不同字段。

追问答题要点
节点返回完整 State 会怎样？没写 reducer 的字段被整体覆盖，带 reducer 的字段（如 messages）会被重复追加一遍，上下文翻倍
返回 None 和返回 {} 的区别？效果都是不改状态，但 None 语义更清晰：表示"这一步什么都不用更新"，可以省一次写盘
自定义 reducer 要注意什么？① 必须处理 None（首次初始化）；② 必须幂等（超步会重跑）；③ 不能有副作用；④ 不要在里面调 LLM
add_messages 删消息要注意什么？删 AIMessage(tool_calls=[...]) 必须连带删对应的 ToolMessage，否则下一轮请求 400
State 能放大对象吗？不建议。State 每个超步全量序列化落盘，放检索原文会让 Checkpoint 爆炸，应该只存 doc_id

✅ 项目关联话术：我们做并行检索时踩过一次。两个节点一个查向量库一个查 ES，都往 docs 字段写，本地单测没问题（因为 mock 太快、执行顺序固定），上线后偶发 InvalidUpdateError。排查出来是 docs 没加 reducer。修的时候我们没直接用 operator.add，而是写了个按 doc_id 去重合并的 reducer，因为两个检索源会命中同一篇文档，直接相加会把重复文档塞进上下文，既浪费 token 又让模型答案偏向重复项。

题 3：什么是超步（super-step）？Checkpoint 以超步为粒度会带来什么后果 ​

精简口述答案（90 秒版）

超步是 LangGraph 的执行单位，一个超步 = 一批节点并行执行 + 一次屏障同步 + 一次状态合并提交。流程是：先确定这一轮要激活哪些节点，这些节点并行跑、各自返回 patch，全部跑完才在屏障处按 reducer 合并，然后写一个 Checkpoint，再进入下一个超步。

它带来三个直接后果。第一，recursion_limit 算的是超步不是节点，默认 25，而一轮 ReAct 是 agent + tools 两个超步，所以默认只够跑大约 12 轮工具。第二，超步内任一节点失败，整个超步的状态更新都不提交，恢复时会从这个超步的开头重来——所以节点必须幂等，不能"加一次计数"或"发一次邮件"就留下痕迹。第三，成功节点的结果会存进 pending_writes，恢复时不会重复调 LLM，只重跑失败的那个节点，这是省钱的关键机制，但它救不了副作用，已经扣的款框架回滚不了。

追问答题要点
并行 5 个节点算几步？1 步。所以靠并行能省 recursion_limit 配额
并行开越多越快吗？不是。超步耗时 = 最慢节点的耗时，并行分支耗时要均衡
怎么让节点幂等？不依赖"执行了几次"的隐含状态；计数类改成由 reducer 计算；有外部副作用的带幂等键交给下游去重
durability 三档怎么选？exit 最快但崩了全丢；async 默认推荐；sync 最可靠，HITL 和付费流程用它
怎么确认某个超步真的落盘了？graph.get_state_history(config) 列出所有 checkpoint，看 next 字段和 metadata.step

✅ 项目关联话术：我们吃过一次幂等的亏。有个节点里写了 state["retry"] + 1 然后同时调了外部通知接口，结果上游限流让这个超步失败重跑，用户收到了三条重复的"任务开始"推送。修法是把通知拆成单独节点，并且用 thread_id + checkpoint_id 生成幂等 key 交给推送服务去重。这件事之后我们定了条规范：凡是有外部副作用的操作，必须单独成节点，且必须带幂等键。

题 4：Checkpointer 和 thread_id 是什么？短期记忆和长期记忆怎么分 ​

精简口述答案（90 秒版）

Checkpointer 是 LangGraph 的持久化层，编译时传进去，之后每个超步自动把完整 State 快照 + 执行进度写一份，按 thread_id 组织。thread_id 就是一次会话的主键：同一个 thread_id 再 invoke，框架会自动加载上次的 State，所谓"多轮记忆"不需要你手动拼历史。Checkpoint 里存的不只是 State，还有 next（下一步要跑哪些节点）、pending_writes（本超步已完成节点的结果）、versions_seen（通道版本），正是这些让断点续跑和时间旅行成为可能。

但 Checkpointer 是单 thread 的短期记忆，换 thread_id 就什么都不记得。跨会话的长期记忆要用 Store：它按 namespace（通常是 ("memories", user_id)）存自定义 KV 文档，支持前缀列举和向量语义检索，节点里通过签名注入 store 参数来读写。一句话区分：Checkpointer 存"这次对话到哪了"，Store 存"这个用户是谁"。

追问答题要点
生产用哪个 Saver？PostgresSaver（需 .setup() 建表）；SqliteSaver 只适合单机/本地；MemorySaver 只能测试
不传 thread_id 会怎样？配了 checkpointer 却不传会直接报错；没配 checkpointer 则每次都是全新状态
Checkpoint 会不会越存越大？会，因为是全量快照不是 diff。要靠 State 瘦身 + messages 裁剪 + 定期清理旧 thread
长期记忆什么时候写？热路径（对话中实时抽取，即时但加延迟）或后台（会话结束异步总结，不影响响应）。多数场景选后台
怎么做"多用户隔离"？thread_id 带上 user_id 前缀，且 user_id 必须从 config["configurable"] 取，绝不从 State 取

✅ 项目关联话术：我们一开始把 user_id 放在 State 里，后来做安全评审时被指出这是个越权漏洞——State 是模型能写的，理论上可以通过 prompt 注入诱导 Agent 改掉 user_id 去读别人的数据。现在所有身份和权限信息都走 config["configurable"]，模型完全看不见也改不了。这条我现在会当成红线讲：可信信息走 config，不可信信息走 State。

题 5：Human-in-the-Loop 怎么实现？interrupt 恢复的时候有什么坑 ​

精简口述答案（90 秒版）

两种写法。老的是静态断点：编译时 interrupt_before=["tools"]，图跑到 tools 之前停住返回当前状态，人工看完后用 invoke(None, config) 续跑——优点是不改节点代码，缺点是断点位置固定、拿不到人工的输入内容。新的是动态中断：在节点里调 value = interrupt({"要确认的内容": ...})，它会抛出一个特殊异常把图挂起，恢复时用 invoke(Command(resume=人工输入), config)，interrupt() 就返回这个输入，执行继续。动态中断能带数据、能有条件触发（比如只有金额超过 1000 才中断），是现在的推荐写法。

最大的坑是：恢复时不是从 interrupt 那一行继续，而是整个节点从头重跑。因为 Checkpoint 粒度是超步，框架没有保存函数内部的执行位置。所以 interrupt 之前的代码会再跑一遍——如果你在 interrupt 之前发了短信、扣了款、写了库，就会执行两次。正确做法是把所有副作用放在 interrupt 之后，interrupt 之前只做纯计算。

追问答题要点
一个节点里能有两个 interrupt 吗？能但强烈不建议，重跑时顺序和返回值匹配极易出错，应该拆成两个节点
HITL 有哪几种模式？Approve/Reject（批或驳）、Edit State（人工改状态再续）、Review Tool Call（改模型生成的工具参数）、Time Travel（回到第 N 步换分支）
必须配 checkpointer 吗？必须。中断的本质是"把状态存下来然后退出"，没有持久化层就没法恢复
中断信息怎么给前端？invoke 返回值里会有 __interrupt__ 字段，里面是你传给 interrupt() 的 payload
用户一直不审批怎么办？中断态会一直留在 checkpoint 里。需要自己加超时清理任务，并在恢复时校验业务数据是否已过期

✅ 项目关联话术：我们的退款 Agent 要求金额超过阈值必须人工确认。第一版就踩了重跑的坑——我们在 interrupt 之前写了一条"待审批"的业务流水，审批通过恢复后流水又插了一条，对账时发现重复。定位过程挺折磨的，因为本地测试是一路跑通的，只有真正中断再恢复才复现。现在我们的规范是：interrupt 必须是节点的第一行副作用边界，它上面只允许有纯函数和读操作。

题 6：条件边和 Command 都能决定下一步，什么时候用哪个 ​

精简口述答案（90 秒版）

条件边是"节点写状态、路由函数读状态决定去哪"，职责分离：路由函数只能读 State 返回一个键，映射表把键翻译成目标节点。Command 是"节点自己同时干两件事"：Command(update={...}, goto="x") 一个返回值既改状态又指定跳转。

选择标准是决策和状态更新是否耦合。纯路由场景用条件边更清晰，比如"看 messages 最后一条有没有 tool_calls 决定去 tools 还是 END"，这个判断不需要写状态。但多 Agent 的 handoff 必须用 Command——交接的时候要把任务描述一起写进共享状态，拆成"先写状态再路由"会多一个超步且容易漏。另外有两件事只有 Command 能做：一是 Command(graph=Command.PARENT) 从子图跳到父图的兄弟节点，条件边做不到跨图；二是 Command(resume=...) 恢复中断。

追问答题要点
用了 Command 还要 add_conditional_edges 吗？不要。但要写返回类型注解 Command[Literal["a","b"]]，框架靠它画出连线做可视化和校验
条件边为什么要写第三个参数（目标列表/映射）？让编译期就知道可能的目标，能画图、能在节点名拼错时提前报错；不写则运行时才炸
路由函数能返回列表吗？能，返回节点名列表就是动态 fan-out；返回 Send 列表就是 map-reduce
路由函数里能调 LLM 吗？技术上能，但不该。路由函数不落 Checkpoint、不被 stream 观测、不走重试策略，有 LLM 调用就该做成节点
条件边最常见的两个坑？① 路由函数返回的键不在映射表里 → KeyError；② 忘了把 END 作为一个可能分支 → 死循环

✅ 项目关联话术：我们的客服主图里两种都在用。入口的意图分类用 Command，因为分类结果本身要写进 State 给后面的节点看，同时决定去账单/技术/人工三个分支，一个节点一个超步就搞定。而 ReAct 子图里"要不要继续调工具"用条件边，因为这个判断纯粹是读 messages 最后一条，不产生任何状态变更，用 Command 反而要多写一层包装。我面试时就是这么讲的：看决策要不要落状态。

题 7：运行时才知道要并行跑 N 个任务，怎么做？fan-in 怎么汇总 ​

精简口述答案（90 秒版）

条件边只能在编译期已声明的节点之间选路，解决不了"运行时才知道要跑 10 份还是 100 份"。这时要用 Send：路由函数返回一个 Send 列表，每个 Send("节点名", 自定义载荷) 动态生成一个任务实例，框架把它们放在同一个超步里并行执行。

两个关键语义容易答错。第一，被 Send 调用的节点收到的参数是载荷本身，不是全局 State，所以别在里面写 state["messages"]。第二，这些节点的返回值仍然走全局 State 的 reducer 合并，所以汇总字段必须带 reducer（比如 Annotated[list, operator.add]），否则 N 个并发写同一字段直接 InvalidUpdateError。fan-in 就是在 Send 的目标节点后面挂一条普通边指向汇总节点——因为超步有屏障，所有并行任务跑完才会进汇总节点，不需要你手动等。

追问答题要点
N 个 Send 消耗几次 recursion_limit？1 次，它们属于同一个超步
其中一个 Send 任务失败会怎样？整个超步不提交，但成功的任务结果进 pending_writes，恢复时只重跑失败的那个
怎么限制并发数？invoke(..., {"max_concurrency": 8})，或者自己分批 Send，否则几百个任务同时打 LLM 会被限流
和"同一节点挂多条固定边"的区别？固定边的分支数在编译期固定；Send 的任务数运行时决定，且能携带不同载荷
汇总节点怎么保证顺序？并行结果的到达顺序不保证。要有序就在载荷里带 index，汇总时按 index 排序

✅ 项目关联话术：我们做长文档总结用的就是这个结构：切章节 → Send 到每章的总结节点 → 汇总节点合并。踩过两个坑。一是最初 summaries 字段忘了加 reducer，本地测两章没事，线上一篇 30 章的文档直接 InvalidUpdateError。二是没限并发，30 个 Send 同时打模型被限流，一半失败。现在固定 max_concurrency=8，并且给每个载荷带上章节序号，汇总时按序号排序，避免摘要顺序乱掉。

题 8：Agent 无限循环怎么防？recursion_limit 设大点不就行了 ​

精简口述答案（90 秒版）

不行，recursion_limit 只是最后一道保险丝，而且它抛 GraphRecursionError、没有降级答案，直接扔给用户就是 500。要四道闸门一起上。

第一道是模型自然收尾，模型不再返回 tool_calls 就走向 END，这是正常路径。第二道是 recursion_limit，注意它算的是超步不是节点，默认 25，一轮 ReAct 两个超步，所以默认只够约 12 轮。第三道是业务预算，在 State 里记 token、费用、调用次数、耗时，超了就路由到一个"强制收尾"节点——用 tool_choice="none" 再请求一次，让模型用已有信息作答，这样用户拿到的是降级答案而不是报错。第四道是重复动作检测，把"工具名 + 规范化后的参数"做成指纹存进 State，发现重复就把这次调用拦掉、回一条"这个查询你已经做过了，结果是 X，请换个思路"的 ToolMessage——大多数绕圈不是 bug 而是模型拿着同一个参数反复查。

追问答题要点
为什么说调大 recursion_limit 是错的？它不治病，只是把烧钱时间拉长；真正的病因通常是条件边写反或工具描述太差导致模型反复试错
怎么捕获并降级？try/except GraphRecursionError 里用 get_state(config) 拿到当前状态，拼一个降级回复
重复检测的指纹怎么算？工具名 + 参数 JSON 按 key 排序后序列化再 hash；时间戳之类的易变字段要剔除
怎么区分"合理重试"和"绕圈"？合理重试通常参数会变（换关键词、换页码）；参数完全相同的重复就是绕圈
预算怎么记才不出错？记在 State 里并给个幂等的 reducer（取 max 或由节点算绝对值），不要写 +1，因为超步会重跑

✅ 项目关联话术：我们灰度期真出过一次。模型拿着同一个报销单号连查了十几次审批流，每次都觉得结果"不够详细"要再查一次，一个会话烧了几千 token。加了重复指纹检测之后，第二次重复调用直接被拦下并回提示，模型立刻换了思路去查制度文档。现在我们的 force_answer 降级节点也是标配——宁可给用户一个"基于已查到的信息，我判断是 X，但建议人工复核"，也不要给 500。

题 9：图太大怎么拆子图？父子 State 怎么对接 ​

精简口述答案（90 秒版）

超过 15 个节点就该拆。拆子图有两种挂法，区别全在状态怎么对接。

第一种是直接把编译后的子图当节点挂上去：parent.add_node("research", sub_graph)。前提是父子 State 有同名 key，同名字段自动透传进去、写回时按父图的 reducer 合并。好处是子图有独立的 checkpoint_ns，父图 stream(..., subgraphs=True) 能看到子图内部每一步，子图里的 interrupt 也能穿透到最外层。第二种是包装成普通函数：自己写 sub_graph.invoke(映射后的输入) 再把输出映射回父 State。好处是映射完全可控、父子 schema 可以完全不同；代价是子图被当成一次黑盒调用，内部的中断和流式事件穿不出来，中间态也不落父图的 Checkpoint。

选择标准：子流程需不需要被观测、中断、恢复。需要就直接挂图，不需要就包成函数。

追问答题要点
子图写了父图没有的 key 会怎样？被静默丢弃，不报错 —— 这是最难查的一类 bug，要用 stream(..., subgraphs=True) 对照子图 updates
子图能单独做时间旅行吗？能，直接挂图的方式下子图有自己的 checkpoint_ns，可以定位到子图内部的 checkpoint
子图层级能嵌多深？技术上无限，但每多一层就多一次完整状态序列化，建议控制在 2 层内
子图要不要单独传 checkpointer？不要。编译子图时不传，它会复用父图的 checkpointer；传了反而容易出现两套持久化
子图和"把流程做成工具"有什么区别？工具是模型决定调不调；子图是你用图结构硬编码的流程，确定性更高

✅ 项目关联话术：我们主图里的检索流程（改写 query → 多路检索 → 重排 → 压缩）拆成了子图，用的是直接挂图的方式。关键收益是排障：以前检索效果差只能看最终答案猜，现在 stream(subgraphs=True) 能看到改写后的 query 长什么样、每一路召回了几篇、重排后留了哪几篇。另外踩过一次静默丢弃的坑——子图里新加了个 rerank_score 字段忘了同步到父 State，父图拿到的结果里一直没有分数，也不报错，查了半天。

题 10：多智能体有哪几种拓扑？你们怎么选的，handoff 怎么实现 ​

精简口述答案（90 秒版）

四种。Network 是全连接，每个 Agent 都能跳到任意 Agent，最灵活但 token 爆炸、容易绕圈，基本不用于生产。Supervisor 是中心调度，一个 Supervisor 用结构化输出决定下一个 Agent，子 Agent 做完回边指向它——可控、好调试、能在一个地方统一做预算和权限控制，缺点是 Supervisor 是单点、prompt 会越来越长。Hierarchical 是分层，Supervisor 的下级也是 Supervisor，能撑几十个 Agent，代价是层级深、延迟高。Swarm 是去中心交接，谁接手就由谁一直对话直到再交接，对话体验最连贯、没有中心开销，但全局可观测性差。

handoff 的工业写法不是在 prompt 里写"请转给 X"，而是把交接做成一个工具，工具返回 Command：Command(goto="目标Agent", graph=Command.PARENT, update={...})。三个细节不能省：必须返回一条 ToolMessage 否则留下悬空 tool_call 导致下一轮 400；必须带 graph=Command.PARENT 因为 Agent 自己是子图、目标是父图的兄弟节点；必须显式传任务描述，不要让下一个 Agent 从几十条历史里猜任务。

追问答题要点
Supervisor 怎么保证输出合法的目标名？with_structured_output 配 Literal 枚举，而不是让它自由输出字符串再做匹配
多 Agent 的历史消息要不要全共享？不建议全共享。常见做法是只共享"结论类"消息，各 Agent 的中间推理留在自己的子图 State 里，否则上下文爆炸
多 Agent 比单 Agent 一定好吗？不一定。角色一多、交接一多，错误传播和延迟都放大。工具超过 15 个、职责明显互斥时才值得拆
怎么防止两个 Agent 来回踢皮球？State 里记交接链，同一对 Agent 交接超过 N 次就强制路由到人工或收尾节点
Supervisor 的 prompt 越来越长怎么办？升级成 Hierarchical，按业务域分组，每个 Supervisor 只认自己域里的三五个 Agent

✅ 项目关联话术：我们选的是 Supervisor。原因很具体：一是要集中做预算控制和越权拦截，中心节点最容易埋这些检查；二是运维要看"当前在哪个 Agent"，Supervisor 结构下这个信息天然在 State 里。踩过的坑是来回踢皮球——账单 Agent 觉得是技术问题、技术 Agent 觉得是账单问题，互相交接了五六轮。现在 State 里记了 handoff_chain，同一对 Agent 交接超过两次就直接转人工。

题 11：LangGraph 的流式输出怎么对接前端？几种 stream_mode 分别干什么 ​

精简口述答案（90 秒版）

前端要的"打字机效果"和"执行进度条"是两种完全不同的流，混淆是对接时最常见的事故。stream_mode 有五种：values 吐每个超步后的完整 State，适合调试；updates 吐每个节点返回的 patch，形如"节点名 → 增量"，这是做执行进度条用的；messages 吐 (token, metadata) 二元组，是 LLM token 级的，metadata 里有 langgraph_node 可以按节点过滤，这是做打字机用的；custom 是节点里用 get_stream_writer() 主动推的任意数据，适合推工具执行进度比如"正在检索第 3/5 篇"；debug 吐任务开始结束和 Checkpoint 细节，只用于排障。

实际对接一般同时订阅多个：stream_mode=["updates", "messages"]，这时 chunk 变成 (mode, data) 二元组，按 mode 分发成不同的 SSE 事件类型。

追问答题要点
messages 模式捕获不到 token，为什么？① 节点里绕过 LangChain 直接用厂商 SDK 裸调，框架看不见；② Python < 3.11 异步环境下 config 没透传给 ainvoke
怎么只把主 Agent 的 token 推给用户？用 metadata 里的 langgraph_node 过滤，把路由/摘要等内部节点的 token 丢掉
子图内部的流式事件怎么拿？stream(..., subgraphs=True)，chunk 会带上 namespace 路径
中断发生时流会怎样？流正常结束，最后能拿到 __interrupt__ 的 payload，前端据此渲染审批弹窗
工具执行很慢，前端一直空白怎么办？用 custom 模式在工具内部推进度，而不是让用户干等

✅ 项目关联话术：我们的 SSE 接口定了三种事件：step（来自 updates，渲染"正在检索 → 正在生成"的步骤条）、token（来自 messages，只放行 langgraph_node == "agent" 的）、progress（来自 custom，工具里推的细粒度进度）。踩过一个坑是最初没按节点过滤 token，结果意图分类节点和摘要节点的输出也被当成答案打到了屏幕上，用户看到一串莫名其妙的 JSON。

题 12：为什么说 LangGraph 的节点必须幂等？有副作用的操作该怎么处理 ​

精简口述答案（90 秒版）

因为 LangGraph 的事务单位是超步，不是节点。超步内任一节点失败，这一步的状态更新全部不提交，恢复时从超步开头重来；interrupt 恢复时也不是从 interrupt 那一行继续，而是整个节点从头重跑。这两件事合起来意味着：任何节点都可能被执行多次，而框架只能回滚 State，回滚不了你发出去的短信和扣掉的钱。

处理副作用有三条规矩。第一，有副作用的操作必须单独成节点，不要和纯计算混在一起，否则重跑时计算和副作用一起重来。第二，必须带幂等键交给下游去重，比如用 thread_id + checkpoint_id + 业务动作 生成 token，让支付/推送服务自己判重——这是唯一可靠的办法，因为分布式下你没法做真正的回滚。第三，副作用必须放在 interrupt 之后，interrupt 之前只允许纯函数和读操作。另外计数类状态不要在节点里写 x + 1，要么让 reducer 去算，要么由节点算出绝对值，否则重跑就多加一次。

追问答题要点
pending_writes 是干什么的？存本超步已成功节点的结果，恢复时直接复用、不重复调 LLM —— 这是省钱的关键，但它救不了副作用
节点里重试和 retry_policy 有什么区别？自己写的重试次数不进 Checkpoint，恢复后计数归零；retry_policy 由框架管，还能配退避和 retry_on 白名单
cache_policy 为什么经常不命中？缓存键由节点输入算，输入里有 datetime.now() 或随机 id 就永远不会命中
怎么测幂等性？集成测试里显式制造一次中断/异常再恢复，断言外部调用只发生一次（用 mock 记调用次数）
reducer 也要幂等吗？要。超步重跑会重新合并，operator.add 配非幂等节点就会出现重复项，所以列表类 reducer 最好带去重

✅ 项目关联话术：这条是我们血的教训攒出来的规范。前面说的重复推送和重复流水两次事故，根因都是同一个：把副作用和纯计算写在了一个节点里，还假设节点只会执行一次。现在我们 code review 有一条硬性检查项——节点里有没有外部写操作，有的话有没有幂等键、是不是单独成节点、是不是在 interrupt 之后。我面试讲这段的时候，面试官追问过"为什么不用事务回滚"，我的回答是：调用的是第三方 HTTP 接口，根本没有分布式事务可用，幂等键 + 下游去重是成本最低且真正可靠的方案。

题 13：用户上一条还在生成就又发了一条，你们怎么处理（double-texting） ​

精简口述答案（90 秒版）

这是真实流量里一定会遇到、Demo 里永远遇不到的问题：同一个 thread_id 出现两个并发 run，两个 run 同时往同一份 checkpoint 写，状态必然错乱。处理方式有四种语义：reject 直接拒掉第二条并提示"上一条还在处理"；enqueue 让第二条排队，等第一个 run 跑完再接着跑；rollback 取消第一个 run 并回滚它写过的状态，只认第二条；interrupt 中断第一个 run 但保留它已完成的超步，再跑第二条。

选型看产品语义：用户在补充信息就用 enqueue，用户明显在改主意（"算了，换成 B"）就用 rollback 或 interrupt，严肃的写操作场景宁可 reject。实现上，如果用 LangGraph Server 这就是一个 multitask_strategy 参数；自己包 FastAPI 的话要手动做两件事：按 thread_id 加分布式锁做串行化，以及把运行中的 task 存起来以便取消。关键是取消点一定落在超步边界上，所以取消后的状态是干净的——上一个超步已提交，当前超步整体不提交。

追问答题要点
锁为什么按 thread_id 而不是按用户？按用户加锁会导致同一个人开两个会话互相阻塞
rollback 怎么定位回滚点？get_state_history 找到该 run 开始前的 checkpoint_id，带着它重新 invoke
取消一个跑到一半的 run 会不会留脏状态？State 不会脏（超步未提交），但已经发出去的副作用回滚不了，所以写操作节点要么幂等要么走 reject
用户点"停止生成"是同一套机制吗？是。取消任务即可，checkpoint 停在上一个超步，下次 invoke(None, config) 能续上
前端怎么感知被拒/被中断？必须是独立的 SSE 事件类型，否则用户只看到"发出去没反应"

✅ 项目关联话术：我们默认用 interrupt 语义——新消息进来取消正在跑的 run，但保留已完成的超步，用户追问时之前检索到的文档不会白跑。写操作类的流程单独改成 reject，因为那种场景下"中途取消了但钱扣了没扣"的歧义比让用户等一会儿更难解释。最早我们完全没管这事，线上出现过用户连点三次发送、三个 run 抢同一个 thread，最后 messages 里工具消息和 AI 消息交错错位，直接 400。

题 14：LangGraph 写完的图怎么上线？多副本部署要注意什么 ​

精简口述答案（90 秒版）

compile() 出来的只是一个进程内对象，上线有三条路。第一条是自己包一层 Web 框架，FastAPI 里 await graph.ainvoke，流式就转发 astream——好处是复用现有网关、鉴权、日志体系，代价是 thread 生命周期、并发控制、SSE 协议全要自己写。第二条是自托管 LangGraph Server，写一个 langgraph.json 声明图入口，langgraph dev 本地起、打镜像上线，白捡 HTTP API、流式、HITL 和定时任务，还有 Assistant 这种"同一张图 + 不同配置 = 不同实例"的配置化能力，代价是多一个服务要运维，依赖 Postgres 和 Redis。第三条是托管平台，适合快速验证，但数据出域要先过合规。

多副本部署的关键是：状态全在 Postgres，所以副本本身是无状态的，可以随意水平扩。要注意四件事：PostgresSaver 首次必须跑 .setup() 建表和迁移；连接池要给够，因为每个超步都要读写 checkpoint，池子小了表现就是"延迟莫名翻倍"；异步服务必须用 AsyncPostgresSaver，混用同步 Saver 会阻塞事件循环；同一个 thread_id 的并发请求要做串行化，这就回到 double-texting 那套锁。

追问答题要点
为什么副本可以无状态？所有状态落在 checkpointer 后端，副本只负责执行超步，不持有会话内存
需要做 thread 粘性（session affinity）吗？不需要粘性，但需要同 thread 串行化；两者是不同的问题

题 1：用 LangGraph 手写带四道闸门的 ReAct 图 ​

要求

  1. 不用 create_react_agent，手写 agent / tools 两个节点和回边。
  2. 条件边必须覆盖三条出路：继续调工具、强制收尾、自然结束。
  3. State 里记账 token 与迭代次数，预算超了路由到 force_answer 降级节点。
  4. 工具抛异常不能让图崩，要把错误作为 ToolMessage 回传给模型。
  5. 配 checkpointer，支持同一 thread_id 的多轮对话。
python
import json, operator
from typing import Annotated, TypedDict, Literal
from langchain_core.messages import AIMessage, ToolMessage, SystemMessage
from langgraph.graph import StateGraph, START, END, add_messages
from langgraph.checkpoint.memory import MemorySaver


class AgentState(TypedDict):
    messages: Annotated[list, add_messages]
    iters: Annotated[int, operator.add]      # reducer 累加，节点只返回增量 1
    used_tokens: Annotated[int, operator.add]
    fingerprints: Annotated[list, operator.add]


MAX_ITERS, MAX_TOKENS = 6, 40_000


def build_agent(llm, tool_map, system_prompt):
    bound = llm.bind_tools(list(tool_map.values()))

    # ---------- 节点 1：模型决策 ----------
    def agent_node(state: AgentState):
        msgs = [SystemMessage(content=system_prompt)] + state["messages"]
        ai: AIMessage = bound.invoke(msgs)
        usage = (ai.usage_metadata or {}).get("total_tokens", 0)
        return {"messages": [ai], "iters": 1, "used_tokens": usage}

    # ---------- 节点 2：执行工具（并行 + 异常隔离 + 重复检测）----------
    def tools_node(state: AgentState):
        ai = state["messages"][-1]
        seen = set(state["fingerprints"])
        out, new_fp = [], []
        for call in ai.tool_calls:
            fp = call["name"] + "|" + json.dumps(call["args"], sort_keys=True,
                                                 ensure_ascii=False)
            if fp in seen:                              # ← 闸门 4：重复动作
                out.append(ToolMessage(
                    content="该查询你已执行过，结果未变，请换思路或直接作答",
                    tool_call_id=call["id"], name=call["name"]))
                continue
            new_fp.append(fp)
            fn = tool_map.get(call["name"])
            if fn is None:
                text = f"工具 {call['name']} 不存在，可用工具：{list(tool_map)}"
            else:
                try:
                    text = str(fn.invoke(call["args"]))
                except Exception as e:                   # ← 单点失败不炸整图
                    text = f"工具执行失败：{type(e).__name__}: {e}"
            out.append(ToolMessage(content=text[:2000],
                                   tool_call_id=call["id"], name=call["name"]))
        return {"messages": out, "fingerprints": new_fp}

    # ---------- 节点 3：强制收尾（降级答案，不抛异常）----------
    def force_answer(state: AgentState):
        msgs = ([SystemMessage(content="已达上限，请基于已有信息直接作答，"
                                       "并说明哪些部分未能核实")]
                + state["messages"])
        return {"messages": [llm.invoke(msgs)]}          # 不 bind_tools = 不可能再调工具

    # ---------- 条件边：三条出路 ----------
    def route(state: AgentState) -> Literal["tools", "force_answer", "__end__"]:
        if state["iters"] >= MAX_ITERS or state["used_tokens"] >= MAX_TOKENS:
            return "force_answer"                        # ← 闸门 3：业务预算
        last = state["messages"][-1]
        if getattr(last, "tool_calls", None):
            return "tools"
        return END                                       # ← 闸门 1：模型自然收尾

    b = StateGraph(AgentState)
    b.add_node("agent", agent_node)
    b.add_node("tools", tools_node)
    b.add_node("force_answer", force_answer)
    b.add_edge(START, "agent")
    b.add_conditional_edges("agent", route, ["tools", "force_answer", END])
    b.add_edge("tools", "agent")                         # 回边 → 形成循环
    b.add_edge("force_answer", END)
    return b.compile(checkpointer=MemorySaver())

题 2：手写一个支持并行写入的幂等 reducer 集合 ​

要求

  1. 实现 merge_docs：按 id 去重合并，右侧覆盖左侧，必须处理 None。
  2. 实现 keep_best：并行多路打分只保留最高分及其来源。
  3. 实现 dedup_append：列表追加但自动去重，保持首次出现顺序。
  4. 实现 counter_max：计数类字段用"取最大值"语义，保证超步重跑不虚增。
  5. 全部 reducer 必须满足：幂等（同一 patch 合并两次结果不变）、无副作用、可交换顺序不敏感（或明确说明不满足）。
python
from typing import Annotated, TypedDict, Any


def merge_docs(left: list | None, right: list | None) -> list:
    """按 doc id 去重合并；右侧同 id 覆盖左侧。幂等。"""
    merged: dict[str, dict] = {d["id"]: d for d in (left or [])}
    for d in (right or []):
        merged[d["id"]] = d
    return list(merged.values())


def keep_best(left: dict | None, right: dict | None) -> dict:
    """保留 score 最高的那条；并行写入顺序无关。"""
    cands = [x for x in (left, right) if x]
    if not cands:
        return {}
    return max(cands, key=lambda x: x.get("score", float("-inf")))


def dedup_append(left: list | None, right: list | None) -> list:
    """追加去重，保持首次出现顺序。幂等。"""
    seen, out = set(), []
    for item in (left or []) + (right or []):
        key = item if isinstance(item, (str, int)) else repr(item)
        if key not in seen:
            seen.add(key)
            out.append(item)
    return out


def counter_max(left: int | None, right: int | None) -> int:
    """计数取最大值：节点返回绝对值，超步重跑不会虚增。"""
    return max(left or 0, right or 0)


class State(TypedDict):
    docs: Annotated[list, merge_docs]
    best: Annotated[dict, keep_best]
    visited: Annotated[list, dedup_append]
    depth: Annotated[int, counter_max]
    answer: str                        # 单一节点写，无需 reducer

WRITE_TOOLS = {"refund", "create_order", "send_sms"}
AMOUNT_THRESHOLD = 1000


def approval_tools_node(state, config):
    ai = state["messages"][-1]
    out = []
    for call in ai.tool_calls:
        name, args = call["name"], dict(call["args"])

        # ===== interrupt 之前：只做纯计算，重跑无副作用 =====
        need_review = name in WRITE_TOOLS and args.get("amount", 0) >= AMOUNT_THRESHOLD

        if need_review:
            decision = interrupt({                      # ← 图在此挂起并落盘
                "type": "tool_approval",
                "tool": name,
                "args": args,
                "risk": "high",
                "hint": f"将执行 {name}，金额 {args.get('amount')} 元，请确认",
            })
            action = decision.get("action")
            if action == "reject":
                out.append(ToolMessage(
                    content=f"人工驳回：{decision.get('reason', '未说明原因')}。"
                            f"请不要重试该操作，改为向用户解释。",
                    tool_call_id=call["id"], name=name))
                continue
            if action == "edit":
                args = decision.get("args", args)       # 人工修正后的参数

            text = str(result)
        except Exception as e:
            text = f"执行失败：{type(e).__name__}: {e}"
        out.append(ToolMessage(content=text, tool_call_id=call["id"], name=name))

    return {"messages": out}

题 4：用 Send 实现长文档的 map-reduce 摘要 ​

要求

  1. 运行时根据章节数动态 fan-out，不能在编译期固定分支数。
  2. 每个 map 任务只拿自己那一章（自定义载荷），不拿全局 State。
  3. fan-in 字段必须有幂等 reducer，且结果要能按原章节顺序还原。
  4. 限制并发，避免几十个任务同时打模型被限流。
  5. 单个章节失败不能让整篇失败，要降级为占位摘要。
python
import operator
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Send


def merge_by_index(left: list | None, right: list | None) -> list:
    """按 index 去重合并，天然幂等；汇总时再排序。"""
    m = {x["index"]: x for x in (left or [])}
    for x in (right or []):
        m[x["index"]] = x
    return list(m.values())


class State(TypedDict):
    doc: str
    chapters: list[str]
    parts: Annotated[list, merge_by_index]
    final: str


def split_node(state: State):
    chapters = [c.strip() for c in state["doc"].split("\n## ") if c.strip()]
    return {"chapters": chapters}


# ---------- map：动态 fan-out ----------
def fan_out(state: State):
    return [
        Send("summarize_one", {"index": i, "chapter": c})
        for i, c in enumerate(state["chapters"])
    ]


# ---------- 注意：payload 不是全局 State ----------
def summarize_one(payload: dict):
    try:
        text = llm.invoke(f"用 3 句话总结：\n{payload['chapter'][:4000]}").content
    except Exception as e:
        text = f"[该章摘要生成失败：{type(e).__name__}]"      # 降级占位，不炸整篇
    return {"parts": [{"index": payload["index"], "text": text}]}


# ---------- reduce：屏障保证所有 map 跑完才进来 ----------
def reduce_all(state: State):
    ordered = sorted(state["parts"], key=lambda x: x["index"])
    joined = "\n".join(f"{i+1}. {p['text']}" for i, p in enumerate(ordered))
    return {"final": llm.invoke(f"把以下分章摘要合并成一篇连贯综述：\n{joined}").content}


b = StateGraph(State)
b.add_node("split", split_node)
b.add_node("summarize_one", summarize_one)
b.add_node("reduce", reduce_all)
b.add_edge(START, "split")
b.add_conditional_edges("split", fan_out, ["summarize_one"])   # ← 声明可能目标
b.add_edge("summarize_one", "reduce")
b.add_edge("reduce", END)
graph = b.compile()

graph.invoke({"doc": long_text}, {"max_concurrency": 8})        # ← 限并发

        update={"task_desc": r.task, "handoffs": [f"sup>{r.next}"]},
    )


def _ping_pong(chain: list[str], limit: int) -> bool:
    """检测 A>B、B>A 反复出现"""
    pairs = [tuple(sorted(h.split(">"))) for h in chain if ">" in h]
    return any(pairs.count(p) > limit * 2 for p in set(pairs))


# ---------- handoff 工具：让 Agent 直接交接 ----------
def make_handoff(target: str, source: str):
    @tool(f"transfer_to_{target}", description=f"把任务交接给 {target}")
    def _handoff(
        task: str,
        state: Annotated[dict, InjectedState],
        tool_call_id: Annotated[str, InjectedToolCallId],
    ) -> Command:
        return Command(
            goto=target,
            graph=Command.PARENT,                       # ← 跳到父图的兄弟 Agent
            update={
                # 必须补 ToolMessage，否则悬空 tool_call 导致下一轮 400
                "messages": [ToolMessage(content=f"已交接给 {target}",
                                         tool_call_id=tool_call_id)],
                "task_desc": task,                  # 显式交接任务，别让它猜
                "handoffs": [f"{source}>{target}"],  # source 要传进来，否则链路记不准
            },
        )
    return _handoff


# ---------- 子 Agent：子图，做完回 Supervisor ----------
def make_agent(name: str, tools: list):
    sub = build_react_subgraph(llm, tools + [make_handoff(t, name) for t in AGENTS
                                             if t != name])

    def node(state: SupState) -> Command:
        out = sub.invoke({"messages": state["messages"],
                          "task_desc": state["task_desc"]})
        return Command(
            goto="supervisor",                          # 回边
            update={"messages": [AIMessage(content=out["messages"][-1].content,
                                           name=name)],
                    "tokens": out.get("tokens", 0)},
        )
    return node
