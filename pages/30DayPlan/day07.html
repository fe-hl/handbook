1. Webpack 五大核心概念 ​

概念作用常见配置

// webpack.config.js 最小可用骨架
const path = require("path");
const HtmlWebpackPlugin = require("html-webpack-plugin");

module.exports = {
  mode: "production",
  entry: "./src/index.js",
  output: {
    path: path.resolve(__dirname, "dist"),
    filename: "js/[name].[contenthash:8].js",
    clean: true, // webpack5 内置，替代 clean-webpack-plugin
  },
  module: {
    rules: [
      {
        test: /\.jsx?$/,
        exclude: /node_modules/, // ⚠️ 必须排除，否则构建速度灾难
        use: "babel-loader",
      },
      {
        test: /\.s?css$/,
        // ⚠️ loader 执行顺序：从右到左、从下到上

      {
        test: /\.(png|jpe?g|svg)$/,
        type: "asset", // webpack5 内置资源模块，替代 url-loader/file-loader

    ],
  },

};

3. HMR 热更新 vs Live Reload ​

维度Live ReloadHMR (Hot Module Replacement)
粒度整个页面刷新单个模块替换
页面状态❌ 全部丢失（表单、路由、弹窗）✅ 保留
速度和首次加载一样慢毫秒级
失败兜底—自动降级为整页刷新
js
// HMR 的用户侧 API（框架脚手架已帮你接好，手写需要自己 accept）
if (module.hot) {
  // webpack
  module.hot.accept("./render", () => {
    render(); // 接受 ./render 模块的更新，手动重新执行
  });
  module.hot.dispose((data) => {
    clearInterval(timer); // 旧模块销毁前清理副作用，否则定时器会叠加
  });
}

if (import.meta.hot) {
  // vite（原生 ESM 规范）
  import.meta.hot.accept((newModule) => {
    newModule?.render();
  });
  import.meta.hot.dispose(() => clearInterval(timer));
}

注意： React 的 react-refresh、Vue 的 @vitejs/plugin-vue 内部都已经调用了 accept，并且能保留组件 state —— 这是框架插件的能力，不是 HMR 协议本身自带的。

4. Tree-Shaking：摇掉没用到的代码 ​

js
// utils.js
export function used() {
  return 1;
}
export function unused() {
  return 2;
} // ✅ 会被摇掉

// index.js
import { used } from "./utils";
console.log(used());

生效的三个必要条件：

条件说明
ESM 静态语法必须是 import / export，import 只能在顶层、路径必须是字面量，才能在编译期确定依赖关系
不能被 Babel 转成 CJS@babel/preset-env 的 modules 必须设为 false，否则 ESM 被降级成 require，静态分析能力丢失
开启压缩Webpack 只做「标记」（usedExports），真正删除代码靠 Terser；mode: 'production' 才默认开启
js
// ❌ CommonJS 无法 Tree-Shaking：require 是运行时的，路径可以是变量
const utils = require("./utils");
const name = Math.random() > 0.5 ? "used" : "unused";
utils[name](); // 打包工具无法在编译期知道用了哪个

// ❌ 整体导入命名空间也会让摇树变困难
import * as utils from "./utils";

// ✅ 具名导入，可静态分析
import { used } from "./utils";
对比项ES ModuleCommonJS
加载时机编译期（静态）运行时（动态）
导出值值的引用（动态绑定）值的拷贝
能否条件导入❌（import() 除外）✅

1. Webpack 完整构建流程（必背） ​

① 初始化参数
   读取 webpack.config.js + CLI 参数 → 合并出最终 options
        │
        ▼
② 创建 Compiler 对象
   Compiler 是全局唯一的「大管家」，持有完整配置与所有钩子
   遍历 plugins 调用 plugin.apply(compiler) 注册钩子
        │
        ▼
③ 开始编译 run / watch
   触发 compile 钩子 → 创建 Compilation（一次编译的上下文）
        │
        ▼
④ 从 Entry 出发确定入口
   addEntry → NormalModuleFactory 创建 Module
        │
        ▼
⑤ 编译模块 buildModule
   ├─ 用 loader 链处理源码（从右到左）→ 得到标准 JS
   └─ 用 acorn 解析成 AST → 收集 import / require 依赖
        │
        ▼
⑥ 递归处理依赖
   对每个依赖重复 ⑤，直到所有模块处理完 → 形成【依赖图 Module Graph】
        │
        ▼
⑦ seal 封装：生成 Chunk
   按 entry / 动态 import / splitChunks 规则把 Module 分组成 Chunk
   Tree-Shaking 标记、作用域提升、代码压缩都在这个阶段
        │
        ▼
⑧ 输出资源 emit
   Chunk → Asset（最终文件内容），emit 是【最后能修改产物的时机】
   写入 output.path，触发 done 钩子
核心对象职责生命周期
Compiler全局唯一，持有配置与全部钩子，控制启动/监听整个 webpack 进程
Compilation一次具体编译的上下文，持有本次所有 module/chunk/asset每次编译（watch 下多次）
Module一个文件对应一个模块可跨 compilation 缓存
Chunk若干 Module 的集合，最终对应一个输出文件seal 阶段生成

面试加分： Webpack 的插件体系基于 Tapable，提供同步钩子（SyncHook、SyncBailHook）和异步钩子（AsyncSeriesHook、AsyncParallelHook），对应 tap / tapAsync / tapPromise 三种注册方式。理解这点，写插件就不会踩「异步钩子忘了调 callback 导致构建卡死」的坑。

📢 口述版：

Webpack 底层基于 Tapable 实现发布订阅的钩子机制。

启动的时候先读取合并配置，然后 new 一个 Compiler 对象，它是全局唯一的打包大管家。紧接着遍历所有 plugin，调用每个插件的 .apply(compiler)，让插件去 tap 注册各个生命周期钩子。

之后调用 compiler.run() 正式开始打包。走到 make 钩子的时候，会创建 Compilation 对象，代表这一次编译的上下文；从 entry 入口开始递归扫描，把每一个文件都当成一个 module（模块），收集所有依赖、构建依赖图；每个 module 会经过对应的 Loader 做转换；整个过程中之前注册好的插件钩子会不断触发，做各种处理；等所有模块处理完之后，Webpack 会把多个 module 合并成一个或多个 chunk（代码块），再做代码分割、压缩这些优化；走到 emit 钩子的时候就是马上要输出了；最后把 chunk 输出成最终的 bundle（打包产物文件）；如果是 webpack-dev-server 就放在内存，不写到磁盘。

顺便区分一下：

  • Compiler：全局唯一；
  • Compilation：每次编译都会新建；
  • module：就是单个源文件；
  • chunk：打包过程中的中间代码块；
  • bundle：最后输出的文件；
  • Loader 只转换单个模块；Plugin 通过钩子干预整个流程。

2. Tree-Shaking 失效场景与 sideEffects ​

失效场景原因解法
使用 CommonJS 导出require 是运行时动态行为，无法静态分析让库提供 ESM 产物（module / exports.import 字段）
Babel 把 ESM 转成了 CJSpreset-env 默认 modules: 'auto'配置 modules: false，把模块处理交给 webpack
模块有副作用删掉可能改变程序行为，打包器不敢删package.json 的 sideEffects 标记
函数调用有潜在副作用如 IIFE、类的 static 属性赋值用 /*#__PURE__*/ 注释声明可安全删除
只用了导出对象的某个属性导出的是一个大对象而非多个具名导出拆成具名导出，避免 export default { a, b, c }
没开压缩webpack 只做标记，删除靠 Tersermode: 'production' 或显式配 optimization.minimize
json
// package.json —— 二者取其一
{
  "sideEffects": false,
  "sideEffects": ["*.css", "*.scss", "./src/polyfill.js"]
}
js
// ⚠️ 典型副作用：只 import 不使用，但必须保留
import "./reset.css"; // 没标 sideEffects 的话会被摇掉 → 样式全丢
import "core-js/stable"; // polyfill 同理

// ✅ PURE 注释：告诉 Terser 这个调用没有副作用
const instance = /*#__PURE__*/ createInstance();

// ❌ 反例：default 导出一个大对象，用不到的也会被打进去
export default { formatDate, formatMoney, deepClone };

// ✅ 正例：具名导出，可按需摇树
export { formatDate, formatMoney, deepClone };

验证手段： 配 optimization: { usedExports: true } 且 mode: 'development'，产物里会出现 /* unused harmony export xxx */ 注释；或直接用 webpack-bundle-analyzer 看体积构成。

3. splitChunks 代码分割 ​

js
module.exports = {
  optimization: {
    runtimeChunk: "single", // runtime 单独抽出，避免它变动影响所有 chunk 的 hash
    splitChunks: {
      chunks: "all", // 同步 + 异步模块都参与分割（默认只处理 async）
      minSize: 20000, // 小于 20kb 不单独拆，避免请求数爆炸
      maxAsyncRequests: 30, // 并发请求数上限
      cacheGroups: {
        // 体积大、更新频率低的库单独拆，长期命中强缓存
        react: {
          test: /[\\/]node_modules[\\/](react|react-dom|react-router)[\\/]/,
          name: "vendor-react",
          priority: 20, // priority 越大越优先匹配
        },
        vendors: {
          test: /[\\/]node_modules[\\/]/,
          name: "vendors",
          priority: 10,
        },
        common: {
          minChunks: 2, // 被 2 个以上 chunk 引用才抽取
          name: "common",
          priority: 5,
          reuseExistingChunk: true, // 复用已拆出的 chunk，避免重复打包
        },
      },
    },
  },
};
分割方式写法适用场景
入口分割多 entry多页应用
动态导入import('./Modal')路由懒加载、大组件按需加载
splitChunks配置 cacheGroups抽离第三方库与公共模块

真正的收益点： 业务代码每天在变，react/lodash 几个月才升级一次。拆开之后用户只需重新下载几十 KB 的业务 chunk，几百 KB 的 vendor 直接走浏览器缓存 —— 这才是代码分割的价值，而不是单纯「文件变小」。

4. Vite 依赖预构建原理 ​

启动 vite dev
    │
    ├─ 扫描 index.html 与源码中的 import，找出所有裸模块（bare import）
    │     import { debounce } from 'lodash-es'   ← 裸模块，需要预构建
    │     import App from './App.vue'            ← 相对路径，不预构建
    │
    ├─ ESBuild 把这些依赖各自打包成单个 ESM 文件
    │     输出到 node_modules/.vite/deps/
    │
    └─ 请求重写：'lodash-es' → '/node_modules/.vite/deps/lodash-es.js'

为什么必须预构建（三个原因缺一不可）：

问题不预构建会怎样预构建如何解决
格式兼容很多 npm 包只有 CJS 产物，浏览器原生 ESM 不认识 require / module.exportsESBuild 统一转成 ESM
请求瀑布流lodash-es 内部有 600+ 个模块，浏览器会发 600+ 个请求，页面直接卡住打包成 1 个文件，1 个请求搞定
路径解析浏览器不认识 import 'vue' 这种裸模块说明符重写为合法的相对/绝对路径
js
// vite.config.js
export default {
  optimizeDeps: {
    include: ["lodash-es", "some-cjs-pkg"], // 强制预构建（如被动态 import 的依赖）
    exclude: ["my-local-link-pkg"], // 排除（如本地 link 的包，希望改动实时生效）
    force: true, // 忽略缓存，强制重新预构建
  },
};

缓存机制： 预构建产物缓存在 node_modules/.vite，Vite 用 package.json 的依赖声明、锁文件、optimizeDeps 配置等生成 hash 做校验。如果手动改了 node_modules 里的代码（patch），hash 不会变，需要删掉 .vite 目录或执行 vite --force。

5. HMR 完整链路：Webpack vs Vite ​

【Webpack HMR】
  文件变更
     │
     ▼
  webpack watch 监听到变化 → 增量重新编译受影响的模块
     │
     ▼
  生成两个产物：
     ① [hash].hot-update.json  —— 描述哪些 chunk 变了
     ② [chunkId].[hash].hot-update.js —— 变更模块的新代码
     │
     ▼
  webpack-dev-server 通过 WebSocket 向客户端推送新的 hash
     │
     ▼
  客户端 HMR Runtime 收到 hash，发起 ajax 拉取 json 清单
     │
     ▼
  再用 JSONP 拉取 hot-update.js（JSONP 可以直接执行代码并回调）
     │
     ▼
  沿着模块依赖图向上冒泡查找 accept 回调：
     ├─ 找到 → 删除旧模块缓存，执行 dispose 清理，执行 accept 回调 ✅
     └─ 冒泡到入口仍没有 → 降级 location.reload() 整页刷新 ⚠️

【Vite HMR】
  文件变更
     │
     ▼
  Vite 基于模块图（Module Graph）精准定位该文件及其「HMR 边界」
     │
     ▼
  使该模块缓存失效，通过 WebSocket 推送一条 update 消息（含模块 url + 时间戳）
     │
     ▼
  客户端用 import(`/src/App.vue?t=1699999999`) 重新拉取【单个模块】
     │
     ▼
  执行 import.meta.hot.accept 回调完成替换
维度Webpack HMRVite HMR
是否需要重新编译✅ 需要增量打包，项目越大越慢❌ 只转换单个文件
更新粒度chunk 级模块级
更新耗时随项目规模增长基本恒定（毫秒级）
传输方式WebSocket 通知 + ajax/JSONP 拉取WebSocket 通知 + 原生 import() 拉取
失效 URL 技巧hash 文件名query 加时间戳 ?t=

关键概念 HMR 边界： accept 的位置决定了更新会冒泡到哪一层。Vue SFC、React 组件之所以能「改哪个组件只更新哪个组件」，是因为框架插件在每个组件文件里自动注入了 accept，让每个组件都成为一个边界。而修改一个被全局引用的 utils.js，往往就只能一路冒泡到入口 → 整页刷新。

6. 长缓存优化：三种 hash 的区别 ​

hash 类型变化时机问题适用
[hash]整个项目任意文件变化就变改一行业务代码，所有文件 hash 全变，缓存全失效❌ 不要用
[chunkhash]所在 chunk 的内容变化才变JS 和它 import 的 CSS 属于同一 chunk，改 JS 会导致 CSS 的 hash 也变JS 可用
[contenthash]单个文件内容变化才变—✅ 推荐，JS/CSS 都用
js
module.exports = {
  output: {
    filename: "js/[name].[contenthash:8].js",
    chunkFilename: "js/[name].[contenthash:8].chunk.js", // 异步 chunk
    assetModuleFilename: "assets/[name].[contenthash:8][ext]",
  },
  plugins: [
    new MiniCssExtractPlugin({ filename: "css/[name].[contenthash:8].css" }),
  ],
  optimization: {
    runtimeChunk: "single", // ⚠️ 不抽 runtime，模块 id 变化会污染所有 chunk 的 hash
    moduleIds: "deterministic", // 模块 id 稳定，避免新增文件导致 id 重排、hash 全变
  },
};

配套的 HTTP 缓存策略：

nginx
# 带 contenthash 的静态资源：永久强缓存，内容变了文件名就变
location ~* \.(js|css|png|jpg|woff2)$ {
  add_header Cache-Control "public, max-age=31536000, immutable";
}

# index.html：绝不能强缓存，否则永远加载不到新的资源文件名
location = /index.html {
  add_header Cache-Control "no-cache";
}

完整闭环： contenthash 保证文件名随内容变化 → index.html 不缓存保证每次拿到最新的文件名列表 → 静态资源永久强缓存。少了任何一环，要么用户加载不到新代码，要么缓存命中率极低。

8. Rollup / ESBuild / Webpack / Vite 工具选型 ​

工具语言定位优势劣势
WebpackJS应用打包生态最全、配置最灵活、对非 JS 资源支持最好慢、配置复杂
RollupJS库打包Tree-Shaking 最彻底、产物干净、ESM 原生对 CJS、代码分割支持不如 webpack
ESBuildGo转换 / 压缩快 10~100 倍（Go 原生 + 多线程并行 + 零中间 AST 转换）不支持降级到 ES5 的部分语法、插件能力弱、无类型检查
ViteJS开发服务 + 应用打包dev 极快、开箱即用开发与生产工具链不同，存在行为差异风险
Rspack / TurbopackRustWebpack 替代兼容 webpack 生态且快数倍生态仍在完善

ESBuild 为什么快（面试高频）： ① Go 编写、编译为机器码，无需 JS 的 JIT 预热；② 充分利用多核并行，JS 单线程做不到；③ 从头设计，解析/链接/生成共用同一套数据结构，避免 AST 在不同工具间反复序列化；④ 内存高效，尽量避免对象分配。

为什么 Vite 生产环境不用 ESBuild： ESBuild 的代码分割（code splitting）和 CSS 处理能力尚不成熟，而生产产物的质量（分包策略、兼容性、CSS 提取）比构建速度更重要。Vite 4+ 已在探索 Rolldown（Rust 版 Rollup）来统一两端。

9. Source Map：产物如何映射回源码 ​

本质： 一份独立的 JSON，记录「产物的某一行某一列」对应「哪个源文件的哪一行哪一列」。

json
{
  "version": 3,
  "file": "bundle.js",
  "sourceRoot": "",
  "sources": ["src/a.js", "src/b.js"],
  "sourcesContent": ["源码内容（可选，有它才能在 DevTools 里直接看源码）"],
  "names": ["fn", "count"],
  "mappings": "AAAA,SAASA,GAAT;AACA..."
}

mappings 是整个 Source Map 的核心，用 Base64 VLQ 编码压缩：

text
mappings 结构：   行与行用 ;  分隔，同一行的多个片段用 , 分隔
每个片段最多 5 个字段（全部是「相对上一个片段的差值」，所以才这么短）：
  ┌─────────────────────────────────────────────┐
  │ ① 产物列号                                   │
  │ ② sources 数组下标（哪个源文件）              │
  │ ③ 源文件行号                                 │
  │ ④ 源文件列号                                 │
  │ ⑤ names 数组下标（变量名，可选）              │
  └─────────────────────────────────────────────┘
只有 ① 一个字段 → 这段代码只知道位置，关联不到源码（比如注入的运行时）

用差值 + VLQ 变长编码，是因为行列号大多是小幅递增，差值绝大多数只占 1 个字符。这也是为什么 .map 文件虽然大，但远小于「逐字符记录绝对坐标」的朴素方案。

浏览器怎么找到它： 产物末尾的注释或 HTTP 响应头。

js
//# sourceMappingURL=bundle.js.map        // 外链（最常用）
//# sourceMappingURL=data:application/json;base64,xxx   // inline，体积翻倍
// 或响应头：SourceMap: /path/bundle.js.map  （产物里不留痕迹，最安全）

devtool 的关键字是「组合语法」，不是 20 个独立枚举：

关键字含义影响
eval每个模块用 eval() 包裹，sourceURL 标注文件名构建/重建最快，但没有列信息
source-map生成完整的独立 .map 文件最慢、最准
inline-把 map 以 base64 内联进产物不产生额外文件，产物体积暴涨
hidden-生成 .map 但不写 sourceMappingURL上传给监控平台专用，用户拿不到
nosources-map 里不含 sourcesContent能看到堆栈行号，看不到源码
cheap-只映射行不映射列快很多，报错定位到行足够用
module-应用 loader 自己产出的 sourcemap不加的话看到的是 babel 转换后的代码

选型结论（直接背）：

js
// 开发环境：要快 + 要能定位到源码的行
devtool: 'eval-cheap-module-source-map';

// 生产环境（要接错误监控）：产物干净，map 只上传给平台
devtool: 'hidden-source-map';

// 生产环境（不想泄露源码但要行号）：
devtool: 'nosources-source-map';

// 生产环境（完全不需要）：
devtool: false;
js
// Vite 对应配置
export default {
  build: {
    sourcemap: true,     // true | false | 'inline' | 'hidden'
  },
};

几个容易答错的点：

  • .map 文件不会被用户自动下载。只有打开 DevTools 时浏览器才会去请求它，所以它不影响线上首屏性能，但一旦被人扒走就等于源码泄露 —— 这才是生产环境不能直接挂 source-map 的真正原因。
  • CI 里的正确做法：构建产出 .map → 上传到 Sentry / 自建平台 → 在部署前把 .map 从产物目录删掉（或用 nginx 规则禁止访问 *.map）。
  • 压缩工具必须也支持 sourcemap 链式传递。Terser、ESBuild 都会基于输入的 map 生成新 map，如果中间某个环节丢了（典型是自己写的 loader 没用 this.callback 把 sourceMap 透传），后面全部错位。
  • 堆栈行号对不上，先怀疑三件事：少了 module- 前缀（看到的是转换后代码）、用了 cheap-（只有行没有列，压缩成一行后就全是第 1 行）、产物与 .map 版本不匹配（发版后 map 没同步更新）。

10. Babel：它到底做了什么，polyfill 又是怎么回事 ​

三阶段（和所有编译器一样）：

text
源码字符串
   │  @babel/parser（基于 acorn 魔改）
   ▼
AST  ──────────────────────────────────────────┐
   │  @babel/traverse 深度遍历，各 plugin 在     │  这一步才是「转换」
   │  visitor 上注册 enter/exit 钩子改写节点     │  plugin 只改 AST，不碰字符串
   ▼                                           │
新 AST ────────────────────────────────────────┘
   │  @babel/generator
   ▼
新代码字符串 + sourcemap

关键认知：Babel 本身什么都不做。@babel/core 只负责搭流水线，所有语法转换能力都来自 plugin。preset 只是「plugin 的有序集合」。

插件执行顺序（面试高频）：

js
module.exports = {
  // ① plugins 永远先于 presets 执行
  plugins: ['a', 'b', 'c'],      // 正序：a → b → c
  // ② presets 倒序执行
  presets: ['x', 'y', 'z'],      // 倒序：z → y → x
};

记法：plugins 正序、presets 倒序。这是约定，目的是让 preset-env（放第一个）最后兜底处理剩余语法。

语法转换 ≠ API 补齐，这是 polyfill 存在的唯一原因：

类型例子Babel 能否单独搞定
语法（syntax）箭头函数、class、可选链 ?.、解构✅ 纯 AST 改写即可
API（built-ins）Promise、Array.prototype.includes、Object.entries❌ 必须注入运行时实现
js
// 语法：Babel 直接改写
const f = (a) => a + 1;        →  var f = function (a) { return a + 1; };

// API：改写不了，ES5 引擎里就是没有这个方法
[1, 2].includes(1);            →  [1, 2].includes(1);   // 原样输出，到低版本浏览器就报错

三种 polyfill 方案的区别（必须讲清）：

js
// 方案一：useBuiltIns: 'entry' —— 入口全量按目标浏览器引入
// babel.config.js
presets: [['@babel/preset-env', { useBuiltIns: 'entry', corejs: 3 }]];
// src/main.js 顶部必须手写一行：
import 'core-js/stable';
// Babel 会把这一行「展开」成目标浏览器缺失的那批 core-js 模块
// 优点：第三方依赖里用到的 API 也被兜住
// 缺点：引入了你根本没用到的 polyfill，体积偏大

// 方案二：useBuiltIns: 'usage' —— 按实际用到的 API 自动引入（推荐，业务项目默认）
presets: [['@babel/preset-env', { useBuiltIns: 'usage', corejs: 3 }]];
// 不需要手写 import，Babel 扫到 [].includes 才注入对应模块
// 缺点：只扫你的源码；node_modules 默认被 exclude，第三方依赖里的新 API 不会被补

// 方案三：@babel/plugin-transform-runtime —— 不污染全局（写库必用）
plugins: [['@babel/plugin-transform-runtime', { corejs: 3 }]];
// 把 Promise 改写成 import _Promise from '@babel/runtime-corejs3/core-js/promise'
// 优点：不修改 window.Promise / Array.prototype，不会和宿主环境打架
// 缺点：同一份 helper 在每个模块里以模块引用形式存在，体积略大于全局方案

modules 配置决定 Tree-Shaking 能不能生效：

js
presets: [
  ['@babel/preset-env', {
    modules: false,   // 关键！保留 ESM，交给 webpack/rollup 做静态分析
                      // 默认值'auto' 在没有 caller 信息时会转成 CJS，Tree-Shaking 直接失效
  }],
];

目标浏览器由 browserslist 决定，不是由 Babel 决定：

json
// package.json
{
  "browserslist": ["> 1%", "last 2 versions", "not dead", "not ie 11"]
}

preset-env 读这份配置，查 compat-table 得出「哪些语法/API 需要转换」。同一份 Babel 配置在不同 browserslist 下产物完全不同 —— 排查「为什么我的箭头函数没被转换」时，第一步就该看 browserslist，而不是看 Babel 配置。

同一份 browserslist 还会被 Autoprefixer、postcss-preset-env 读取，所以改它会同时影响 JS 和 CSS 产物，别随手往里塞古董浏览器。

11. Vite / Rollup 插件钩子体系 ​

一句话区分角色： webpack 里 loader 管「单个文件的字符串转换」，plugin 管「生命周期事件」；Rollup/Vite 把二者合并了 —— 一切皆插件，靠不同钩子分别承担 loader 和 plugin 的职责。

text
Rollup 钩子分两类：
  ① Build 钩子（构建阶段，串行/并行可控）
     options → buildStart → resolveId → load → transform → moduleParsed
     → buildEnd → （generateBundle /writeBundle 属于输出阶段）
  ② Output 钩子（产物生成阶段）

关键三个位点，正好对应「找文件 / 读文件 / 改文件」：
  resolveId(source, importer)  → 决定 import 'x' 解析到哪个文件（返回 null 表示交回默认逻辑）
  load(id)                     → 拿到 id 后，自己决定文件内容是什么（虚拟模块就在这里造）
  transform(code, id)          → 内容已就绪，做代码改写（等价于 webpack loader）
js
// 最小可用插件：给所有 .js 注入一个全局变量
function injectVersion(version) {
  return {
    name: 'inject-version',
    // 排序控制（Vite 特有，Rollup 没有）
    enforce: 'pre',          // 'pre' 在 Vite 核心插件之前 | 'post' 之后 | 不写=正常
    apply: 'build',          // 'serve' 只在 dev 生效 | 'build' 只在构建生效，返回函数也可以

    transform(code, id) {
      if (!id.endsWith('.js')) return null;   // 返回 null = 不处理，交回流水线
      return { code: `const __VERSION__=${JSON.stringify(version)};\n${code}`, map: null };
    },
  };
}

enforce 的顺序不是装饰：pre → Vite 核心插件 → 普通插件 → post。写一个要抢在 vite:import-analysis 之前改写 import 的插件，不写 enforce: 'pre' 就一定失败。

Vite 独有的钩子（面试考点，Rollup 没有）：

const virtualId = 'virtual:app-info';

12. ESM / CJS 互操作与 package.json 入口字段 ​

两套模块系统的根本差异（不是语法糖的区别）：

维度CommonJSES Module
加载时机运行时，require() 执行到才加载编译期静态分析，import 提升到顶部
导出值值的拷贝（导出后原值改变，引用方拿不到）值的引用（live binding，原值变了跟着变）
路径可以是变量 require(a ? 'x' : 'y')必须是字符串字面量（动态要用 import()）
顶层 await❌✅
Tree-Shaking❌ 做不了✅ 静态结构可分析
js
// live binding 实证
// counter.js
export let count = 0;
export const inc = () => count++;
// main.js
import { count, inc } from './counter.js';
inc();
console.log(count); // 1  ← ESM 是引用；换成 CJS 这里会是 0

__esModule 是怎么回事（互操作的核心）：

js
// 源码
export default function foo() {}

// Babel 转成 CJS 后
exports.__esModule = true;   // 打标记：我原本是 ESM
exports.default = foo;

// 另一个文件 import foo from './foo'  →  转换后：
var _foo = _interopRequireDefault(require('./foo'));
function _interopRequireDefault(obj) {
  // 有标记 → 直接用；没标记（纯 CJS 模块）→ 把 module.exports 整体当作 default
  return obj && obj.__esModule ? obj : { default: obj };
}
_foo.default();

这就是「import xxx from 'cjs-pkg' 有时拿到的是 { default: ... }」的根源：打包器加了 interop 垫片，而 Node 原生 ESM 的 interop 规则又略有不同，两边行为对不上时就会出现 xxx is not a function。

package.json 入口字段的优先级：

json
{
  "main": "dist/index.cjs.js",      // ① 最老的字段，CJS 入口，Node 默认读它
  "module": "dist/index.esm.js",    // ② 社区约定（非官方），打包器优先读它以启用 Tree-Shaking
  "browser": "dist/index.browser.js", // ③ 浏览器专用产物，可替换掉 Node 内置模块
  "types": "dist/index.d.ts",
  "sideEffects": false,             // 配合 ② 才真正 Tree-Shaking 得干净
  "exports": {                      // ④ 现代方案，优先级最高，且会「封死」未声明的路径
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.esm.js",
      "require": "./dist/index.cjs.js",
      "default": "./dist/index.esm.js"
    },
    "./styles.css": "./dist/styles.css"
  }
}

exports 的两个副作用，升级依赖时经常被它坑：

  1. 一旦声明 exports，没列进去的子路径一律不可 import。老代码里的 import 'pkg/lib/utils' 会直接报 ERR_PACKAGE_PATH_NOT_EXPORTED。
  2. 条件顺序是从上到下匹配的，types 必须写在最前、default 必须写在最后，顺序写反会导致类型丢失或解析到错误产物。

双包危险（dual package hazard）：

text
同一个库同时提供 ESM 和 CJS 两份产物时：
  应用 A ──import──> pkg/esm/index.js   ┐
                                        ├─ 两份实例，模块内的单例状态各一份！
  依赖 B ──require──> pkg/cjs/index.js  ┘

症状：instanceof 判断失败、单例 store 数据对不上、Context 取不到值（React 多实例的经典原因）
解法：① 只发 ESM；② CJS 产物做成 ESM 的薄包装；③ 用 peerDependencies + 构建时 alias 强制归一

这也是 Vite 必须做依赖预构建的原因：浏览器原生 ESM 不认 CJS，而 npm 上仍有大量 CJS-only 包，必须先用 ESBuild 把它们转成 ESM 并合并成单文件，否则既跑不起来，也会因为「一个包几百个子模块」把浏览器请求数打爆。

13. Module Federation：构建层视角 ​

微前端的完整方案（qiankun、沙箱隔离、路由分发等）见 micro.md，这里只讲 webpack 构建层 需要理解的部分。

它解决的是什么： 传统拆包是「构建时」把代码切成 chunk，所有 chunk 仍属于同一次构建；MF 让两次独立的构建产物在运行时互相 import。

js
// 远程应用 remote：暴露模块
new ModuleFederationPlugin({
  name: 'remoteApp',
  filename: 'remoteEntry.js',          // 清单文件，宿主靠它知道有哪些模块
  exposes: {
    './Button': './src/components/Button',
  },
  shared: {
    react: { singleton: true, requiredVersion: '^18.0.0' },
    'react-dom': { singleton: true, requiredVersion: '^18.0.0' },
  },
});

// 宿主应用 host：消费模块
new ModuleFederationPlugin({
  name: 'hostApp',
  remotes: {
    remoteApp: 'remoteApp@https://cdn.xx.com/remoteEntry.js',
  },
  shared: { react: { singleton: true }, 'react-dom': { singleton: true } },
});

// 使用（必须异步，因为要先下载 remoteEntry）
const Button = React.lazy(() => import('remoteApp/Button'));

三个必须讲清的点：

  • shared 不是「共用」而是「协商」：运行时各方把自己的版本注册到共享作用域，由 webpack 运行时挑一个满足所有 requiredVersion 的最高版本加载。满足不了就各加载各的 —— 于是 React 出现两个实例，Hooks 直接报错。
  • singleton: true 是 React/Vue 这类有内部状态的库的强制项，并且要配 strictVersion 决定「版本不匹配时是警告还是直接报错」。
  • 入口必须异步化：host 的 index.js 通常只写 import('./bootstrap')，因为共享模块的协商发生在异步 chunk 加载时，同步入口会在协商完成前就执行代码。

和 Vite 的关系：Vite 本身无此能力，社区方案是 @originjs/vite-plugin-federation，原理相同但 dev 下行为差异较大，生产环境使用前务必实测。

题 1：Webpack 和 Vite 的核心差异？Vite 开发环境为什么启动更快？ ​

精简口述答案：

最本质的差异是开发环境要不要打包。Webpack 是 bundle 架构，启动开发服务前必须把整个项目的模块全部解析、转换、打包成 bundle，所以启动时间和项目规模成正比，大项目几十秒到几分钟。Vite 是 no-bundle 架构，启动时只做一件事 —— 用 ESBuild 把 node_modules 里的第三方依赖预构建成 ESM，然后直接启动静态服务；业务代码完全不打包，浏览器通过原生 <script type="module"> 按需请求，Vite 收到请求才实时转换这一个文件。所以启动时间几乎和项目体积无关。生产环境 Vite 则换成 Rollup 打包，因为生产要的是产物质量而不是速度。另外 ESBuild 之所以快，是因为它用 Go 编写、编译成机器码、充分利用多核并行，而且内部各阶段共用数据结构，避免了 AST 的反复序列化。

连环追问链：

  1. 追问：Vite 开发环境有什么缺点？
    • 答：主要三点。一是首次打开页面时请求数很多，弱网或模块特别多的页面会有明显的瀑布流延迟（不过有浏览器缓存，二次就快了）；二是开发用 ESBuild、生产用 Rollup，两套工具链可能产生行为差异，出现「开发正常、上线白屏」的情况，所以上线前必须跑一遍 vite build && vite preview；三是对只有 CJS 产物的老旧依赖兼容性依赖预构建，偶尔需要手动配 optimizeDeps。
  2. 追问：为什么 Vite 生产环境不继续用 ESBuild？
    • 答：ESBuild 的代码分割和 CSS 处理能力还不成熟，而生产环境更关心分包策略、Tree-Shaking 彻底性、浏览器兼容性，这些 Rollup 更可靠。社区正在做 Rolldown（Rust 版 Rollup）来统一开发和生产。
  3. 追问：既然 Vite 这么快，Webpack 还有必要吗？
    • 答：有。Webpack 生态最全，对微前端（Module Federation）、复杂的多页/库构建、各种非标准资源处理支持更好，老项目迁移成本也要考虑。追求速度又不想丢生态，现在更推荐 Rspack（Rust 实现、兼容 webpack 配置）。
  4. 追问：Vite 为什么要做依赖预构建，不做会怎样？
    • 答：三个原因 —— 很多包只有 CJS 产物浏览器不认；像 lodash-es 这种内部有几百个模块的包不打包会产生几百个请求；浏览器也不认识 import 'vue' 这种裸模块路径。预构建用 ESBuild 一次性解决格式转换 + 合并请求 + 路径重写。
  5. 追问：预构建的缓存在哪里，什么时候会失效？
    • 答：缓存在 node_modules/.vite，Vite 根据 package.json 依赖、锁文件、optimizeDeps 配置算 hash 来判断是否复用。手动 patch 了 node_modules 代码时 hash 不变，需要删 .vite 或用 vite --force。

✅ 项目关联话术（按真实经历替换）：

我们一个有 2000 多个模块的中后台项目，Webpack 冷启动要 45 秒，改一行代码热更新要 6 到 8 秒，开发体验很差。迁移到 Vite 后启动稳定在 3 秒以内，热更新基本是毫秒级。迁移时主要处理了三件事：require 改成 import，process.env 换成 import.meta.env，以及几个只有 CJS 产物的内部包加到了 optimizeDeps.include 里。另外我们在 CI 里加了 vite build 的卡点，避免开发环境正常但生产构建失败。

题 2：Tree-Shaking 的原理是什么？哪些场景会失效？ ​

精简口述答案：

Tree-Shaking 依赖 ES Module 的静态特性 —— import/export 必须写在顶层、路径必须是字符串字面量，所以打包工具在编译期就能构建出完整的导入导出关系图，标记出哪些导出从未被引用，再交给 Terser 这类压缩器把死代码真正删掉。注意 webpack 本身只负责「标记」（usedExports），删除是压缩阶段做的，所以不开 production 模式是看不到效果的。失效场景主要有：使用 CommonJS 导出，因为 require 是运行时的、路径还能是变量，没法静态分析；Babel 的 preset-env 把 ESM 转成了 CJS，这是最隐蔽的一种，要把 modules 设为 false；模块存在副作用，比如 import './reset.css' 这种只导入不使用的，打包器不敢删，需要用 package.json 的 sideEffects 字段声明哪些文件是无副作用的；还有导出一个大对象而不是具名导出，以及函数调用本身可能有副作用的情况，后者可以用 /*#__PURE__*/ 注释标注。

连环追问链：

  1. 追问：sideEffects 和 usedExports 有什么区别？
    • 答：这是 webpack 的两种 Tree-Shaking。usedExports 是粒度细的「导出级」摇树，分析某个导出有没有被用到；sideEffects 是粒度粗的「文件级」摇树，如果一个文件被标记无副作用且它的导出完全没被用到，整个文件连解析都跳过，效率更高。两者配合使用。
  2. 追问：为什么 import './reset.css' 会被摇掉？
    • 答：因为这条 import 没有绑定任何变量，在 webpack 看来「导入了但没使用」。如果 sideEffects: false 就会被当成死代码删除，导致样式全丢。正确做法是 sideEffects: ["*.css", "*.scss"] 把样式文件列入白名单。
  3. 追问：lodash 和 lodash-es 有什么区别？该怎么按需引入？
    • 答：lodash 是 CJS 产物，无法 Tree-Shaking，import { debounce } from 'lodash' 会把整个 70KB 的库打进去；lodash-es 是 ESM 产物，可以正常摇树。如果必须用 lodash，可以单文件引入 import debounce from 'lodash/debounce'，或者用 babel-plugin-lodash 自动改写。
  4. 追问：类的方法能被 Tree-Shaking 吗？
    • 答：很难。因为类的方法挂在 prototype 上，可能通过 this[methodName]() 这种动态方式调用，压缩器无法确定安全性。所以工具库更推荐导出独立的纯函数而不是一个大类，这也是 lodash、date-fns 的设计思路。
  5. 追问：怎么验证 Tree-Shaking 到底生效了？
    • 答：开发模式配 usedExports: true 看产物里的 /* unused harmony export */ 注释；或者用 webpack-bundle-analyzer / rollup-plugin-visualizer 对比优化前后体积；也可以直接搜产物里有没有残留某个本应被删掉的函数名。

✅ 项目关联话术（按真实经历替换）：

我们内部的 UI 组件库最初只打了一份 UMD 产物，业务方 import { Button } 时整个 800KB 的库都会进包。我做的改造是：Rollup 同时输出 ESM、CJS、UMD 三份产物，在 package.json 里用 module 字段指向 ESM、main 指向 CJS、exports 字段做条件导出；Babel 配置 modules: false 保留 ESM 语法；sideEffects 设为 ["*.css"] 保护样式文件。改完之后业务方首屏 JS 体积减少了约 40%，接入 webpack-bundle-analyzer 看确认未使用的组件已经完全不在产物里了。

题 3：HMR 的原理是什么？和 Live Reload 有什么区别？ ​

精简口述答案：

【30 秒口述版 · 以 Vite 为例】 浏览器本身是不支持热更的。拿 Vite 举例，npm run dev 的时候它会启动开发服务，本地监听文件变化，同时往浏览器注入一段 runtime。一旦文件改动，服务端通过 WebSocket 发消息告诉浏览器哪个模块 ID 变了。浏览器里那个 runtime 收到通知后，会带时间戳动态 import 拉取新版模块；然后去查这个模块有没有注册 accept 回调。如果有就执行 accept 做局部更新；如果没有就往父模块冒泡去找，一直冒泡到顶层都没有的话，就整页刷新。

【完整版】 Live Reload 是整页刷新，页面所有 JS 重新执行，路由、表单、组件 state 全部丢失。HMR 是模块级替换，只把变更的那个模块的新代码换进运行时，页面不刷新，其他模块的状态都保留。实现上需要三方配合：构建工具监听文件变化并算出哪些模块受影响；通过 WebSocket 把变更通知推给浏览器；浏览器端的 HMR runtime 拉取新模块代码，然后沿着模块依赖图向上冒泡寻找最近的一个声明了 module.hot.accept 的父模块（这个点叫 HMR 边界），在那里执行替换和回调；如果一路冒泡到入口都没有边界，就只能降级成整页刷新。Webpack 的做法是服务端生成新的 hash，浏览器先拉一个 json 清单知道哪些 chunk 变了，再用 JSONP 拉对应的 hot-update.js；Vite 更轻，因为本来就是 no-bundle，服务端在模块图上找到失效模块后直接推路径，浏览器用 import('/src/App.vue?t=时间戳') 重新请求单个文件，不需要任何打包，所以热更新速度和项目体积无关。

连环追问链：

  1. 追问：为什么 React 组件更新后 state 还能保留？
    • 答：这是 react-refresh（Fast Refresh）做的。它在编译时给每个组件注册一个稳定的签名，HMR 发生时只替换组件的渲染函数，Fiber 树上的 hooks state 保持不动。但有限制：只有导出的是函数组件时才有效；如果修改了 hooks 的调用顺序或数量，签名校验失败就会强制重新挂载并丢失 state；文件里混了非组件的导出也可能导致降级。
  2. 追问：为什么我改一个 utils 文件，整个页面刷新了？
    • 答：因为从 utils 到入口的链路上没有任何模块声明 HMR 边界，冒泡到顶就只能整页刷新。这也是合理的 —— 一个被几十处引用的纯函数模块，框架无法知道怎么安全地把老的引用替换掉。框架插件（vue-loader、react-refresh）只会给组件文件自动注入边界。
  3. 追问：HMR 替换掉的旧模块留下的副作用怎么清理？
    • 答：要用 module.hot.dispose（Vite 里是 import.meta.hot.dispose）注册清理函数，在旧模块被卸载前执行，用来清定时器、解绑事件、关闭 WebSocket。不清理就会出现「改一次代码多一个定时器」的内存泄漏，表现为热更新几次后页面卡死。
  4. 追问：import.meta.hot 在生产环境会报错吗？
    • 答：不会，但必须写成 if (import.meta.hot) { ... }。Vite 生产构建时 import.meta.hot 会被静态替换成 undefined，整个 if 块会被 Tree-Shaking 掉。如果不加判断直接 import.meta.hot.accept(...)，生产环境就是读 undefined 的属性报错。
  5. 追问：HMR 的 WebSocket 断了怎么办？
    • 答：客户端 runtime 有重连机制，并会在重连成功后判断是否需要整页刷新来追平状态。常见踩坑是通过 nginx / 内网穿透代理开发服务时没配 WebSocket 升级头（Upgrade / Connection），导致连接建不起来、HMR 静默失效，这时要配 server.hmr.clientPort 或 protocol。

✅ 项目关联话术（按真实经历替换）：

我们项目里有个全局的 WebSocket 推送模块，早期每次热更新都会新建一个连接，开发半小时后浏览器就会堆几十个连接、页面明显卡顿。定位到是 HMR 替换旧模块时没做清理，后来在这个模块里加了 import.meta.hot.dispose(() => ws.close())，问题就解决了。另外我们把一个 1000 多行的「万能 utils」按领域拆成了多个小文件，因为之前改任何一个工具函数都会触发全页刷新，拆分后热更新影响面小了很多。

题 4：Loader 和 Plugin 的区别？简述 Webpack 的构建流程 ​

精简口述答案：

Loader 是文件转换器，本质是一个函数，输入源码字符串、输出 JS 字符串，职责单一，作用在单个模块上，比如 babel-loader 转 ES6、css-loader 处理 @import。Plugin 是功能扩展器，本质是一个带 apply(compiler) 方法的类，通过 Tapable 往 webpack 生命周期的几十个钩子上挂回调，能力覆盖整个构建流程，比如 HtmlWebpackPlugin 在 emit 阶段生成 html。一句话：Loader 是翻译官，Plugin 是监工。

构建流程大致八步：读取配置合并 CLI 参数初始化 Compiler；注册所有 Plugin；从 Entry 开始编译；用 Loader 把模块转成 JS 并用 AST 解析出它的依赖；递归处理所有依赖，构建完整的依赖图；根据入口和动态导入把模块组装成 Chunk；每个 Chunk 生成对应的 Asset 代码；最后 emit 阶段写入磁盘。整个过程中 Plugin 在各个钩子上插入自己的逻辑。

连环追问链：

  1. 追问：Loader 的执行顺序是怎样的？为什么是从右到左？
    • 答：use 数组的执行顺序是从右到左、从下到上，因为它是函数组合的语义：style(css(sass(source)))。但 loader 实际有两个阶段 —— 先从左到右执行所有 loader 的 pitch 方法，再从右到左执行 normal 方法。如果某个 pitch 返回了值，就会熔断，直接跳过它右边所有 loader 并往左回溯，style-loader 就是用这个机制接管后续处理的。
  2. 追问：Compiler 和 Compilation 有什么区别？
    • 答：Compiler 是全局唯一的编译器实例，持有完整配置，生命周期贯穿整个 webpack 进程；Compilation 代表一次具体的构建，包含这次构建的所有 modules、chunks、assets。watch 模式下每次文件变化都会创建一个新的 Compilation，但 Compiler 始终只有一个。
  3. 追问：Tapable 的钩子有哪几种类型？
    • 答：按执行方式分同步（SyncHook）和异步（AsyncSeriesHook 串行、AsyncParallelHook 并行）；按返回值处理分普通、Bail（有返回值就熔断）、Waterfall（上一个的返回值作为下一个的入参）、Loop（返回非 undefined 就重新循环）。写插件时根据钩子类型选 tap / tapAsync / tapPromise。
  4. 追问：Module 和 Chunk 是什么关系？
    • 答：Module 是一个文件对应的模块单元，Chunk 是打包输出的代码块。多个 Module 按入口、动态导入、splitChunks 规则被组装成 Chunk，一个 Chunk 最终输出一个或多个 Asset（比如 js + source-map）。
  5. 追问：说一个你了解原理的常用插件？
    • 答：比如 MiniCssExtractPlugin，它的 loader 在处理 CSS 时不像 style-loader 那样返回注入 DOM 的 JS，而是把 CSS 内容存到 Chunk 上，再由插件在 renderManifest / emit 阶段把这些内容抽成独立的 .css 文件，并让 HtmlWebpackPlugin 注入 <link>。这样 CSS 可以并行下载、独立缓存，也避免了 FOUC。

✅ 项目关联话术（按真实经历替换）：

我写过两个内部插件。一个是构建产物体积卡口插件，在 emit 钩子里遍历 compilation.assets，如果单个 JS 超过 500KB 就往 compilation.warnings 推警告、超过 1MB 直接 push 到 errors 让 CI 失败，防止有人无意间把大依赖带进主包。另一个是国际化文案校验 loader，在编译阶段扫描源码里的 t('key') 调用，和语言包比对，缺失的 key 直接在编译期报错，不用等到线上才发现文案显示成 key。

题 5：项目构建速度慢、首屏包体积大，你会怎么优化？ ​

精简口述答案：

我会分成「构建速度」和「产物体积」两条线，而且先测量再优化。构建速度先用 speed-measure-webpack-plugin 看是哪个 loader / plugin 耗时，常见手段是：开启 webpack5 的 filesystem 持久化缓存（收益最大，二次构建能快 80% 以上）、给 loader 加 exclude: /node_modules/ 和 include 缩小范围、用 thread-loader 对耗时的 babel 做多进程、把稳定的大依赖用 DllPlugin 或 externals + CDN 移出构建、开发环境把 source-map 降到 eval-cheap-module-source-map、resolve.extensions 收窄减少文件探测。产物体积先用 webpack-bundle-analyzer 看谁最大，手段是：确保 Tree-Shaking 真的生效、按路由做动态 import() 分割、用 splitChunks 把 node_modules 和公共模块抽出来、moment 这类带全量语言包的库用 IgnorePlugin 裁剪或换 dayjs、图片走压缩和 CDN、开 gzip/brotli。最后配 contenthash + 长缓存，让没变的 chunk 不重复下载。

连环追问链：

  1. 追问：怎么定位构建瓶颈？
    • 答：时间维度用 speed-measure-webpack-plugin 或 webpack5 的 stats: 'normal' + --profile；体积维度用 webpack-bundle-analyzer（Vite 用 rollup-plugin-visualizer）。没有数据就优化，很容易花大力气优化了只占 3% 耗时的环节。
  2. 追问：thread-loader 什么情况下反而会变慢？
    • 答：它每个 worker 都要启动一个 Node 进程并做进程间通信，启动开销大约几百毫秒。小项目或者单个 loader 本身耗时很短时，开销大于收益。所以只建议用在耗时明显的 babel-loader / ts-loader 上，并且放在 loader 链的最前面（最先执行的位置）。
  3. 追问：splitChunks 你是怎么配的？为什么这么配？
    • 答：至少分三组 —— vendors 把 node_modules 抽出来（变动频率低、缓存命中率高）；common 把被两个以上 chunk 引用的业务模块抽出来（minChunks: 2）；再把 React/Vue 这类超大且几乎不升级的框架单独抽一组，设更高的 priority。不能无脑全抽，chunk 太碎会导致 HTTP 请求数暴涨，首屏反而变慢，要结合 maxInitialRequests 和 minSize 控制。
  4. 追问：contenthash 配了为什么缓存还是经常全部失效？
    • 答：通常是两个原因。一是没抽 runtimeChunk，webpack 的运行时代码里记录了所有 chunk 的 hash 映射，任何一个 chunk 变了都会让包含运行时的入口文件 hash 变；二是模块 ID 用了自增数字，新增一个文件会让后面所有模块 ID 偏移，配 optimization.moduleIds: 'deterministic' 让 ID 基于路径生成即可。
  5. 追问：首屏优化除了打包，还能做什么？
    • 答：路由级懒加载 + 组件级 React.lazy；关键资源 preload、次要域名 dns-prefetch；非首屏 JS 加 defer；大列表虚拟滚动；骨架屏改善体感；真正要命的首屏可以上 SSR 或预渲染。打包优化只是其中一环，要结合 Lighthouse 和真实用户的 LCP 数据看。

✅ 项目关联话术（按真实经历替换）：

我们一个 Webpack 项目构建从 4 分钟优化到了 50 秒左右，关键的三步是：开 webpack5 filesystem 缓存（二次构建直接降到 40 秒）、babel-loader 加 exclude 并挂 thread-loader、把 echarts 和地图相关的大依赖改成 CDN externals。产物侧首屏 JS 从 2.3MB 降到 780KB，主要靠路由级动态 import、echarts 按需引入、moment 换 dayjs。最后配了 contenthash + runtimeChunk + moduleIds: 'deterministic'，nginx 上对带 hash 的静态资源设一年强缓存、index.html 设 no-cache，灰度期间统计到静态资源缓存命中率提升了一倍多。

题 6：Source Map 是怎么工作的？生产环境你会怎么配？ ​

精简口述答案：

Source Map 本质是一份独立的 JSON，核心字段是 mappings，它用 Base64 VLQ 编码记录「产物的第几行第几列」对应「哪个源文件的第几行第几列」，并且存的是相对上一个片段的差值，所以文件体积能压得很小。浏览器通过产物末尾的 //# sourceMappingURL= 注释或者 HTTP 响应头里的 SourceMap 字段找到它，而且只有打开 DevTools 时才会去下载，所以它不影响线上用户的首屏性能，真正的风险是源码泄露。webpack 的 devtool 不是一堆独立枚举，而是关键字组合：eval 最快但没列信息，cheap 只映射行不映射列，module 决定是否应用 loader 自己产出的 map（不加就只能看到 Babel 转换后的代码），inline 内联进产物，hidden 生成 map 但不写注释，nosources 不带源码内容。我的配置是开发用 eval-cheap-module-source-map，兼顾重建速度和定位能力；生产如果接了错误监控就用 hidden-source-map，构建后把 map 上传到监控平台，再从部署产物里删掉，这样既能还原线上堆栈又不泄露源码。

连环追问链：

  1. 追问：生产环境开 source-map 会不会拖慢用户访问？
    • 答：不会拖慢加载，因为 map 文件只在 DevTools 打开时才请求。但它会拖慢构建（完整 map 是最慢的 devtool），而且会把源码暴露给任何人 —— 这才是不能直接用的原因。所以要么 hidden-source-map 配合 nginx 禁止访问 *.map，要么构建完就把 map 移出部署目录。
  2. 追问：hidden-source-map 和 nosources-source-map 该选哪个？
    • 答：看是否有错误监控平台。有平台就用 hidden-source-map，map 完整上传给平台，平台能还原出完整源码级堆栈，用户侧完全拿不到 map。没有平台、需要自己偶尔在浏览器里看堆栈，就用 nosources-source-map，这样 DevTools 能显示正确的文件名和行号，但点进去看不到源码内容。
  3. 追问：为什么线上报错堆栈还原出来的行号是错的？
    • 答：常见三个原因。一是 devtool 少了 module 前缀，映射到的是 Babel 转换后的中间代码；二是用了 cheap，只有行映射没有列映射，而生产代码压缩成一行后所有位置都落到第 1 行；三是产物和 map 版本不一致，比如重新构建后 map 没同步上传，哪怕只差一次构建，hash 和行列都会错位。
  4. 追问：自己写 loader 时需要注意 sourcemap 吗？
    • 答：需要。loader 链是串起来的，每个 loader 都应该把上游传入的 map 继续往下传，正确做法是用 this.callback(null, code, map) 而不是直接 return code。一旦某个环节把 map 丢了，整条链后面的映射全部失效，排查时很容易误以为是 devtool 配错了。
  5. 追问：Vite 怎么配？和 webpack 有什么不一样？
    • 答：Vite 用 build.sourcemap，取值 true | false | 'inline' | 'hidden'，语义和 webpack 的对应前缀一致。开发环境 Vite 默认就有 sourcemap 且基本不需要调，因为它本来就是按需转换单个文件，没有打包过程带来的层层映射；这也是 Vite 开发时报错定位天然更准的原因之一。

我们线上接的是 Sentry。构建配 hidden-source-map，CI 流程是：build 之后用 sentry-cli releases files upload-sourcemaps 把 map 和产物一起上传，并用 git commit id 作为 release 版本号，上传成功后在部署步骤前把 dist 里的 *.map 全部移到一个临时目录，确保 CDN 上不存在 map 文件。之前排查过一次「堆栈还原后行号偏移几十行」的问题，最后发现是有人为了加快构建把 devtool 改成了 cheap-source-map，丢了列信息，压缩后全部指向第一行，改回完整 map 后就正常了。

题 7：Babel 的工作流程是什么？polyfill 有哪几种方案？ ​

精简口述答案：

Babel 是「parse → transform → generate」三段式：@babel/parser 把源码转成 AST，@babel/traverse 深度遍历 AST，各个 plugin 在 visitor 上注册节点钩子改写 AST，最后 @babel/generator 把 AST 还原成代码并产出 sourcemap。要强调的是 Babel 内核本身不做任何转换，所有能力都来自 plugin，preset 只是 plugin 的有序集合；执行顺序是 plugins 先于 presets，plugins 正序、presets 倒序。然后是最关键的认知：语法转换和 API 补齐是两件事。箭头函数、class、可选链这些是语法，Babel 改写 AST 就能搞定；但 Promise、Array.prototype.includes 这些是 API，低版本引擎里根本不存在这个方法，必须注入运行时实现，这就是 polyfill。方案有三种：useBuiltIns: 'entry' 在入口按目标浏览器全量引入，能兜住第三方依赖但体积偏大；useBuiltIns: 'usage' 按源码实际用到的 API 自动引入，体积最小，但默认不扫 node_modules；@babel/plugin-transform-runtime 把 API 改写成模块引用，不污染全局原型，写库必须用这个。另外要补一点：到底哪些需要转换不是 Babel 决定的，是 browserslist 决定的。

连环追问链：

  1. 追问：useBuiltIns: 'usage' 和 'entry' 到底该怎么选？
    • 答：业务应用默认选 usage，因为按需引入体积最优，而且不用在入口手写 import 'core-js/stable'。但 usage 只扫描你自己的源码，如果某个第三方依赖内部用了 Object.fromEntries 而没自己带 polyfill，线上低版本浏览器就会挂 —— 这种情况要么改用 entry 全量兜底，要么把那个包加到 babel-loader 的 include 里一起编译。
  2. 追问：transform-runtime 和 preset-env 的 polyfill 冲突吗？
    • 答：职责有重叠，所以一般不同时开 useBuiltIns 和 transform-runtime 的 corejs。库作者选 transform-runtime，因为它不改全局环境，不会和使用方的运行时打架；应用作者选 useBuiltIns: 'usage'，因为应用是最终产物，直接改全局更省体积。另外 transform-runtime 还有个独立价值：把 _classCallCheck 这类 helper 函数抽成模块引用，避免每个文件里重复一份。
  3. 追问：为什么我的箭头函数没被转换成 function？
    • 答：第一反应应该查 browserslist，而不是查 Babel 配置。preset-env 会把 browserslist 和 compat-table 比对，如果你的目标浏览器全都原生支持箭头函数，它就故意不转换 —— 这是正确行为。另一个常见原因是文件在 exclude: /node_modules/ 范围内，babel-loader 根本没处理它。
  4. 追问：modules: false 不配会有什么后果？
    • 答：preset-env 的 modules 默认是 'auto'，在拿不到 caller 信息（比如自己跑 babel CLI、或者用了非标准集成）时会把 ESM 转成 CommonJS，而 CJS 是运行时模块系统、无法静态分析，Tree-Shaking 直接彻底失效。这是「配置看着都对但产物就是摇不干净」最隐蔽的一个原因。
  5. 追问：既然 ESBuild/SWC 这么快，还需要 Babel 吗？
    • 答：需要，但场景在收缩。ESBuild 和 SWC 在语法转换上快一到两个数量级，日常转译完全可以替代；但 Babel 的优势是插件生态和 AST 操作能力，像自定义 AST 转换、按需引入改写、国际化文案提取、代码埋点注入这类需求，Babel 插件写起来最成熟。另外 ESBuild 不提供 polyfill 注入能力，需要兼容低版本浏览器时仍然要靠 core-js 配合（Vite 里对应 @vitejs/plugin-legacy，它内部就是用 Babel 做的）。

// FileListPlugin.js
class FileListPlugin {
  constructor(options = {}) {
    this.filename = options.filename || "FILELIST.md";
  }

  // webpack 会调用 apply，并把 compiler 实例传进来
  apply(compiler) {
    const pluginName = FileListPlugin.name;

    // emit：产物已生成、尚未写入磁盘，是修改/新增 assets 的最佳时机
    compiler.hooks.emit.tapAsync(pluginName, (compilation, callback) => {
      const assets = compilation.assets;
      const names = Object.keys(assets);

      let content = `# 本次构建共产出 ${names.length} 个文件\n\n`;
      content += "| 文件 | 体积(KB) |\n| --- | --- |\n";

      names
        .map((name) => ({ name, size: assets[name].size() }))
        .sort((a, b) => b.size - a.size)
        .forEach(({ name, size }) => {
          content += `| ${name} | ${(size / 1024).toFixed(2)} |\n`;
        });

      // 往产物里新增一个文件：必须提供 source() 和 size()
      compilation.assets[this.filename] = {
        source: () => content,
        size: () => content.length,
      };

      // 异步钩子必须调用 callback，否则构建卡死
      callback();
    });

    // 同步钩子用 tap，没有 callback
    compiler.hooks.done.tap(pluginName, (stats) => {
      console.log(
        `[FileListPlugin] 构建耗时 ${stats.endTime - stats.startTime}ms`
      );
    });
  }
}

module.exports = FileListPlugin;

三个必须记住的点： ① Plugin 是一个类，核心是 apply(compiler)；② 根据钩子类型选 tap（同步）/ tapAsync（回调）/ tapPromise（Promise），用错会直接卡住或报错；③ 新增 asset 的对象必须同时有 source() 和 size() 两个方法。webpack 5 更推荐用 compilation.hooks.processAssets 并指定 stage。

✅ 边界 Case 自测：

  • apply 里直接执行耗时逻辑 → 应该只注册钩子，真正的工作放在回调里
  • tapAsync 忘记调 callback() → 构建永久挂起，没有任何报错，极难排查
  • 选错钩子时机：afterEmit 之后改 assets 不会被写盘，compile 阶段又还没有 assets
  • 插件内抛异常未捕获 → 整个构建崩溃，应该 push 到 compilation.errors / warnings
  • 多次构建（watch 模式）时在 apply 里累积数组 → 数据会越积越多，状态要放在 compilation 维度
  • compilation.assets 的 key 带了 publicPath 前缀 → 实际 key 是相对 output 的路径，不要手动拼

  // ESM 转 CJS，产物里才能用我们自己实现的 require
  const { code } = babel.transformFromAstSync(ast, content, {
    presets: [["@babel/preset-env", { targets: { node: "current" } }]],
  });

  return { id: ID++, filename, dependencies, code, mapping: {} };
}

// 2. 从入口开始广度遍历，构建完整依赖图
function createGraph(entry) {
  const mainAsset = createAsset(entry);
  const queue = [mainAsset];

  for (const asset of queue) {
    const dirname = path.dirname(asset.filename);
    asset.dependencies.forEach((relativePath) => {
      const absolutePath = path.resolve(dirname, relativePath);
      const child = createAsset(absolutePath);
      // 记录「相对路径 -> 模块 id」的映射，供运行时 require 查找
      asset.mapping[relativePath] = child.id;
      queue.push(child);
    });
  }
  return queue;
}

// 3. 生成 bundle：IIFE + 模块映射表 + 自实现 require
function bundle(graph) {
  let modules = "";
  graph.forEach((mod) => {
    modules += `${mod.id}: [
      function (require, module, exports) { ${mod.code} },
      ${JSON.stringify(mod.mapping)}
    ],`;
  });

  return `(function (modules) {
    const cache = {};
    function require(id) {
      if (cache[id]) return cache[id].exports;      // 循环依赖 & 单例的关键
      const [fn, mapping] = modules[id];
      const module = { exports: {} };
      cache[id] = module;
      // 把模块内的相对路径翻译成数字 id
      fn(function localRequire(rel) { return require(mapping[rel]); }, module, module.exports);
      return module.exports;
    }
    require(0);
  })({ ${modules} });`;
}

fs.writeFileSync("./dist/bundle.js", bundle(createGraph("./src/index.js")));

这道题考的不是 API，而是对「模块化」的理解： 打包器做的就是把「文件路径的依赖关系」在编译期翻译成「数字 id 的映射表」，再用一个自己实现的 require + 闭包模拟出模块作用域。理解了这个，webpack 产物里那一大坨 __webpack_require__ 就不神秘了。

✅ 边界 Case 自测：

  • 循环依赖：A 引 B、B 又引 A → 靠 cache[id] 先占位再执行解决，否则无限递归爆栈；注意此时拿到的可能是「未完成的 exports」
  • 重复依赖：同一个文件被多处引用 → 上面的实现会重复 createAsset，应该用 absolutePath -> asset 的 Map 去重
  • 没有扩展名的引入 ./utils → 需要实现 resolve 逻辑依次尝试 .js / .json / /index.js
  • 引入 node_modules 裸模块 import vue from 'vue' → 需要逐级向上查找 node_modules
  • 动态 import() → 上面的实现不支持，真实打包器要在这里切分 chunk 并生成异步加载的运行时
  • 非 JS 资源（css / 图片）→ 需要 loader 机制先转成 JS 字符串
  • 模块内 this 指向 → CJS 里顶层 this 应等于 module.exports，示例未处理

      return modules; // 返回原数组 = 走默认逻辑

// babel-plugin-console-with-loc.js
module.exports = function ({ types: t }) {
  return {
    name: 'console-with-loc',
    // 只在函数作用域内访问，避免重复处理
    visitor: {
      CallExpression(path, state) {
        const { node } = path;
        // ① 只处理 console.xxx(...) 这种成员调用
        if (!t.isMemberExpression(node.callee)) return;
        if (!t.isIdentifier(node.callee.object, { name: 'console' })) return;
        // ② 已经加工过就跳过（插件可能被多次执行）
        const firstArg = node.arguments[0];
        if (
          t.isStringLiteral(firstArg) &&
          /^\[\d+:\d+\]/.test(firstArg.value)
        ) return;

        // ③ 拿位置信息：node.loc 由 parser 生成，插件里可直接用
        const loc = node.loc;
        if (!loc) return;
        const fileName = state.filename
          ? state.filename.split(/[\\/]/).pop()
          : 'unknown';

        node.arguments.unshift(
          t.stringLiteral(`[${fileName}:${loc.start.line}:${loc.start.column}]`)
        );
      },
    },
  };
};

  return {
    visitor: {
      ImportDeclaration(path, state) {
        const { node } = path;
        if (node.source.value !== state.opts.libraryName) return;

        const specs = node.specifiers;
        if (!specs.length) return;

✅ 边界 Case 自测：

  • 是否处理了 local 与 imported 不同名的情形（import { Button as Btn }），改写后必须保留本地名
  • 是否处理了 default / namespace 导入（import UI from 'ui'）——通常应跳过而不是硬改写
  • 是否处理了 多个 specifier 共用一个 import（import { Button, Table } from 'ui'），要拆成多条
  • 是否处理了 CSS 副作用导入的顺序问题，样式必须在组件导入之后
  • console 被局部变量遮蔽（const console = xxx）时是否误伤 —— 严格实现应检查 path.scope.hasBinding('console')
  • node.loc 为 null（代码由其他插件动态生成、无原始位置）时是否会崩
  • replaceWithMultiple 后没有重新遍历新节点，导致链式插件处理不到 —— 必要时用 path.scope.crawl()
  • 传参给 t.stringLiteral 时文件名含反斜杠（Windows 路径），字符串要经过 JSON.stringify 或转义
  • 插件是否被重复执行（preset 和 plugins 里都配了），用打标记或幂等判断兜住

❌ instanceof 失败 / Context 取不到值 / 单例状态对不上✅ 双包危险，ESM 和 CJS 两份产物被同时加载产生双实例，用 alias 或 peerDependencies 强制归一

❌ 写 Vite 插件时 generateBundle 在 dev 下完全不触发✅ 开发期不打包，没有输出阶段；兼容 dev/build 的逻辑必须写在 transform / load 里
❌ Vite 插件改写 import 不生效✅ 顺序问题，需加 enforce: 'pre' 抢在 vite:import-analysis 之前执行
❌ 虚拟模块报 ENOENT 找不到文件✅ resolveId 返回的 id 要加 \0 前缀，告知其他插件这不是真实文件路径
❌ resolveId / transform 不匹配时乱返回值导致构建崩✅ 不处理时必须返回 null，返回 false 会被当成 external，返回空字符串直接报错
❌ Vite 插件 transform 注入代码后把 CSS / SVG 也改坏✅ 必须同时过滤 id.includes('node_modules') 和文件扩展名
❌ handleHotUpdate 里返回 undefined 想阻止刷新但没效果✅ 返回 [] 才是阻止传播，返回 undefined 是走默认逻辑
❌ Babel 插件改写 console 时误伤了局部变量✅ 用 path.scope.hasBinding('console') 判断是否被遮蔽，再决定是否处理
❌ Babel 插件被重复执行，注入内容叠加两遍✅ preset 和 plugins 里重复配置了，或缺少幂等判断，处理前先检查是否已打过标记
❌ 用正则改写 import 实现按需引入，偶发把注释/字符串改坏✅ 必须走 AST（@babel/parser 或 es-module-lexer），正则无法区分代码与文本
❌ Module Federation 下 React 报 Hooks 错误✅ shared 没配 singleton: true，版本协商失败后各加载一份 React，产生双实例
❌ Module Federation 宿主同步入口拿不到远程模块✅ 共享作用域协商发生在异步阶段，入口要改成 import('./bootstrap') 异步化
