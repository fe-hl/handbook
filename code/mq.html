1. 如何保证消息不丢失？ ​

核心思路 ​

从生产者、Broker、消费者三个环节保证可靠性，并用重试、告警和补偿机制兜底。

环节措施注意事项
生产者开启发布确认（Publisher Confirm）确认 Broker 是否承担消息责任，不代表消费成功；超时结果未知，重试需幂等
消息路由开启 mandatory，并处理退回通知（Return）Confirm 成功不代表消息一定进入目标队列；无法路由的消息需要单独处理
Broker交换机、队列持久化，消息设置为持久化队列持久化不等于消息持久化；关键业务还需结合仲裁队列和发布确认
消费者业务处理成功后再确认消息（ACK）失败时有限重试，超过次数转入异常队列并告警，避免无限重入队

消费者确认的区别：

  • Spring AMQP 的 AUTO 模式：监听方法正常返回后，由容器确认；抛出异常后的处理取决于重试、拒绝和重新入队配置。
  • MANUAL 模式：业务代码在处理成功后主动确认，适合需要精细控制的场景。
  • Spring AMQP 的 AUTO 不等于 RabbitMQ 原生的自动确认。原生自动确认在消息交付后即视为已确认，业务处理失败可能丢失消息。
  • 如果采用异步处理，不能在异步业务尚未完成时就确认消息。

业务补充：

  • 数据库提交和发送消息不是一个原子操作。关键场景可以使用本地消息表，将业务数据和待发送记录放在同一数据库事务中，再由后台可靠投递。
  • 使用 RabbitMQ 同步 MySQL 与 Redis 时，通常实现的是最终一致性，还需要重试、幂等和对账补偿。
  • 重试次数如“3 次”属于项目配置；耗尽重试后进入异常队列，不代表业务已经处理成功。

面试口述版 ​

我会从三个环节保证消息可靠性：生产者开启发布确认，同时处理无法路由的消息；Broker 对交换机、队列和消息做持久化，关键业务采用仲裁队列；消费者在业务成功后再确认，失败时有限重试，最终转入异常队列并告警。如果还涉及数据库更新和发送消息的一致性，会结合本地消息表和补偿机制。消息重投可能造成重复消费，因此消费者也要保证幂等。

2. 如何解决消息重复消费？ ​

为什么会重复？ ​

  • 消费者已经完成业务处理，但确认消息前宕机，Broker 会重新投递未确认的消息。
  • 生产者发送成功，但没有收到确认，重试后也可能产生重复消息。
  • 因此不能只依赖 MQ 去重，需要保证业务幂等，即重复执行不产生额外业务影响。

常见方案 ​

  1. 业务唯一标识＋数据库唯一约束（优先考虑）
    • 按业务操作选择稳定标识，例如支付流水号，或“订单号＋事件类型＋业务版本”；同一订单的创建、支付、退款不能共用一个去重标识。生产者重试应保持事件 ID 不变。
    • 多个服务共用消费记录表时，唯一键还应包含消费者业务标识，避免一个服务的消费记录误拦截另一个服务。
    • 在数据库中建立唯一约束，防止并发插入重复记录。
    • 如果使用独立消费记录表，消费记录和业务更新应放在同一事务中，避免“已标记消费但业务未完成”。
    • 重复请求应识别为已处理，不再重复执行扣款、发券等操作。
  2. 状态机或条件更新
    • 例如只允许订单从“待支付”更新为“已支付”，通过更新条件和受影响行数判断是否首次处理。
    • 状态变更和相关业务副作用需要保持一致，不能仅靠状态判断忽略其他操作。同库更新应放在同一事务；外部扣款、发短信等不受本地事务保护，还需下游幂等键、可靠任务或消息投递及结果核实，超时不能直接视为失败。
  3. Redis 辅助去重或分布式锁
    • 可用于削减重复请求或控制并发，但需要考虑过期、宕机以及标记和业务操作无法原子提交的问题。
    • 分布式锁本身不等于幂等；锁释放后，重复消息仍可能再次执行，关键业务仍应有数据库兜底。

**常见误区：**只做“先查询，不存在再插入”不安全。两个消费者可能同时查询到不存在，需要唯一约束或原子条件更新保证并发正确性。

面试口述版 ​

重复消费通常发生在业务处理完成、但还没来得及确认消息时服务宕机，或者生产者因确认超时而重发。我的处理方式是让消费者保证幂等：按业务操作选取稳定的事件标识，例如支付流水号或订单号加事件类型、版本，通过数据库唯一约束或状态条件更新防止重复执行。如果使用消费记录表，会让消费记录和业务操作在同一事务中提交；Redis 锁可以辅助控制并发，但不能单独保证幂等。

3. 死信交换机和延迟队列是什么？ ​

死信交换机（DLX） ​

消息在以下情况下可能成为死信：

  • 被消费者拒绝，且不重新入队。
  • 消息 TTL 到期。
  • 队列达到长度限制，且溢出策略会淘汰消息；并非所有溢出策略都会产生死信。
  • 仲裁队列中的消息超过投递次数限制。

在原队列上配置死信交换机和可选的死信路由键，消息成为死信后会被重新发布到该交换机，再路由到绑定的队列。

**注意：**死信交换机不是特殊类型的交换机，而是承担死信路由用途的普通交换机。默认死信转发不能无条件视为可靠；支持该能力的仲裁队列可配置至少一次死信转发，并满足溢出策略等前提。仍需确保目标交换机、队列和绑定正确，并处理重复投递。

TTL 到期不代表业务会准时执行：过期消息的移除、死信转发、业务队列积压都会带来延迟。重要超时任务应记录业务截止时间，消费时校验，并通过定期扫描补偿遗漏。

延迟队列的两种实现 ​

方案实现流程注意事项
TTL ＋死信交换机消息进入无消费者的等待队列 → TTL 到期成为死信 → 转发到业务队列 → 消费者处理同一队列混用不同消息 TTL 可能发生队头阻塞；常按延迟档位拆分等待队列
延迟消息插件安装并启用延迟消息插件 → 声明延迟交换机 → 发送消息时指定延迟时间是延迟消息插件，不是“死信插件”；需确认与 RabbitMQ 版本兼容，不能简单等同于仲裁队列的可靠性

**典型场景：**订单超时关闭、延迟检查支付状态、定时重试。

订单超时关闭时，消费者仍需重新检查订单是否已支付，并用条件更新防止误关单；不能仅凭延迟消息到达就直接关闭订单。

面试口述版 ​

死信交换机负责接收原队列中的死信，例如消息过期或被拒绝且不重新入队。延迟队列可以用 TTL 加死信交换机实现：先把消息放到不消费的等待队列，过期后转发到业务队列进行处理。也可以使用延迟消息插件，在发送时指定延迟时间。TTL 方案要注意不同过期时间混用时的队头阻塞，业务侧还要校验当前状态，比如关闭订单前确认订单仍未支付。

4. 如果有 100 万条消息堆积，如何处理？ ​

先定位原因 ​

  • 观察消息进入速率、消费速率、待消费数量和未确认数量，判断是生产突增、消费者故障还是处理速度变慢。
  • 检查消费耗时、错误率、重试次数，以及数据库、下游接口和线程池是否出现瓶颈。
  • 结合磁盘、内存和告警判断容量风险，避免盲目扩容消费者压垮下游。
  • 粗估清空时间：积压量 ÷（有效消费速率－进入速率）。只有有效消费速率高于进入速率，积压才会下降；例如积压 100 万条、每秒消费 2000 条、新增 1000 条，约需 1000 秒清空，实际还要考虑重试和流量波动。

再按瓶颈处理 ​

  1. 恢复故障消费者：排查连接、异常和配置，阻止失败消息无限重新入队。
  2. 提高消费能力：优化慢 SQL、远程调用和不必要的串行操作；在下游容量允许时增加消费者实例或消费并发。
  3. 合理设置预取数量：结合消息大小、处理耗时和并发调整，避免单个消费者持有过多未确认消息。
  4. 控制生产速率：必要时限流、削峰，优先处理核心业务。
  5. 规划容量与隔离：评估磁盘空间，必要时按业务分片或拆分队列；严格顺序消费的场景不能随意增加并发。
  6. 积压恢复后复盘：补充监控、告警和容量预估，确认延迟消息的业务时效性。

关于惰性队列：

  • 旧版本经典队列支持惰性队列模式，主要将消息放到磁盘，减少大量积压时的内存压力。
  • RabbitMQ 3.12 起经典队列不再支持旧的惰性模式，相关配置会被忽略，磁盘与内存管理采用新的实现。
  • 扩大容量只能缓解存储压力，不能解决消费吞吐不足，也不能据此承诺任意规模的积压都能安全保存。

面试口述版 ​

我会先看生产和消费速率、待消费和未确认数量，判断是流量突增、消费者故障还是数据库和下游变慢。然后先恢复故障、优化耗时操作，再根据下游承载能力增加消费者和并发，合理调整预取数量。必要时对生产端限流并做队列隔离，同时检查磁盘容量。扩大队列容量只是缓解措施，真正消除积压还是要提高有效消费速度或降低进入速度，并注意顺序要求。

5. RabbitMQ 如何保证高可用？ ​

普通集群与队列复制 ​

  • 普通集群会共享交换机、队列定义等元数据，但不代表每个队列的消息自动复制到所有节点。
  • 队列是否具备副本容灾能力，取决于队列类型和相应配置。

镜像队列与仲裁队列 ​

对比项镜像队列仲裁队列（Quorum Queue）
定位经典队列的历史高可用方案新项目通常优先考虑的复制队列方案
同步机制主节点向镜像节点复制基于 Raft，在副本组内进行复制和选举
故障处理故障提升策略和副本同步状态影响可用性与数据安全多数副本存活且能通信时，可选举新的领导者并继续服务
版本情况已弃用，RabbitMQ 4.0 中移除现代 RabbitMQ 的主要高可用队列方案

仲裁队列的关键点 ​

  • 通常采用 3 个副本，分布在不同节点或故障域，可容忍其中 1 个副本不可用。
  • 发布确认在消息复制并持久化到多数副本后返回，不代表消费者已经处理成功。仲裁队列会持久化消息，不依赖消息的持久化标记；生产者仍建议设置持久化标记，以兼容经典持久化队列。
  • 多数副本不可用时，队列停止服务，而不是牺牲一致性继续写入；同时仍需考虑磁盘损坏等故障边界。
  • 只声明仲裁队列并不等于部署完成，还需要多节点集群、副本分布、容量规划和监控。
  • 客户端应配置连接恢复、多个连接地址或负载均衡，并处理重连后的消息重试和幂等。

面试口述版 ​

RabbitMQ 普通集群只共享元数据，并不会自动复制所有队列的消息。旧方案是镜像队列，但它已经弃用，并在 RabbitMQ 4.0 中移除。现在通常采用仲裁队列，基于 Raft 进行复制和选举，比如在三个节点上部署三个副本，只要多数副本存活且能通信，就可以继续服务。它提高了已确认消息的可靠性，但仍需要合理部署副本、开启发布确认，并做好客户端重连、重试和幂等。

6. 下单后要通知库存、积分和短信服务，为什么使用 MQ？ ​

处理思路 ​

  • 异步：将允许稍后完成的操作移出下单主链路，减少接口等待时间。
  • 解耦：订单服务发布业务事件，各下游服务通过自己的队列订阅，减少直接调用依赖。
  • 削峰：突发请求先进入队列，下游按承载能力消费，但要有容量上限、限流和积压告警。
  • 代价：引入最终一致性、重复消息、失败补偿、消息延迟和运维复杂度。
  • 业务边界：不能把所有操作都异步化。若“下单成功”必须代表库存已锁定，就应同步完成锁库存或采用明确的预占流程；积分、短信通常更适合异步处理。

面试口述版 ​

MQ 主要用于异步、解耦和削峰。比如订单创建后，积分和短信服务可以独立订阅事件，不阻塞下单接口。但不能为了异步牺牲业务正确性：如果下单成功必须保证库存锁定，就要先完成库存预占。使用 MQ 后还需要接受最终一致性，并做好可靠投递、幂等、重试和补偿。

7. 订单已经写入数据库，但消息发送失败怎么办？ ​

处理思路 ​

  1. 本地事务写两份数据：在同一数据库事务中写入订单和待发送消息记录，保证同时成功或同时回滚。
  2. 后台可靠投递：任务扫描待发送记录，发送消息并等待发布确认，同时处理无法路由的退回消息。
  3. 确认后更新状态：按消息关联发布确认与退回结果，只有确认成功且没有路由失败才标记发送完成。mandatory 只能发现完全无法路由，不能保证所有预期订阅队列都存在；队列和绑定需提前部署并校验。失败或超时则退避重试，记录次数和错误原因。
  4. 消费者幂等：发送成功但更新发送状态前宕机，会导致再次投递，因此不能假设消息只发送一次。
  5. 监控与补偿：对长期未发送记录告警，支持人工重放和定期对账；消息记录按保留策略归档。

**常见追问：**先发消息再提交订单，也不可靠，因为消息可能已消费而订单事务随后回滚；只在事务提交后发送，仍存在提交成功后进程宕机的窗口。重试任务也需要并发控制，避免多个任务争抢同一条记录。

面试口述版 ​

我会使用本地消息表，让订单和待发送消息记录在同一个数据库事务里提交。后台任务负责发送，收到发布确认且没有路由失败后更新发送状态，失败则重试。发送成功后如果进程宕机，消息可能再次发送，所以消费者必须幂等。再通过积压告警、对账和人工补偿保证异常可恢复，这通常实现的是最终一致性。

8. 同一订单的创建、支付、退款消息乱序怎么办？ ​

处理思路 ​

  • 明确顺序范围：通常只要求同一订单有序，不要求全部订单全局有序。
  • 生产端保证业务顺序：由统一的事件生成流程维护订单事件顺序或业务版本；多个生产者并发发送不能天然保证业务先后。
  • 按订单分片：以订单标识固定路由到同一队列，不同订单可分布到多个队列。调整分片数量时需要处理历史消息与新消息的衔接。
  • 消费端串行：每个分片使用单个活动消费者并串行执行业务；可以设置预取数量为 1，减少多条在途消息，但预取配置本身不是顺序保证。
  • 业务层兜底：通过状态机、事件 ID 和版本校验去重、识别过期事件；缺少前序事件时暂存、有限重试或补偿，不能盲目应用后续事件。
  • 权衡吞吐：严格有序与高并发存在冲突；失败消息是否阻塞后续消息，需要根据业务决定。

面试口述版 ​

我会先明确只保证同一订单有序。生产端按业务顺序生成事件，再按订单标识固定路由到同一个队列，消费端采用单活动消费者串行处理，不同订单通过分片并行。由于多生产者、重试和重新投递都可能影响顺序，业务还要结合状态机和版本校验；前序事件缺失时先暂存或补偿，不能让退款消息直接越过支付流程。

9. 订单超时关闭与用户支付同时发生怎么办？ ​

处理思路 ​

  1. 以数据库状态为准：支付回调和关单操作都通过条件更新竞争“待支付”状态，防止双方覆盖彼此结果。
  2. 关单前核实支付：检查本地支付记录，必要时查询支付渠道；查询成功仍不等于消除了后续支付的竞态。
  3. 协调渠道关单：根据支付渠道能力关闭支付单，并处理“关单时已经支付”等返回结果；本地更新与渠道操作无法简单放在一个事务中。
  4. 处理迟到支付：如果订单已关闭但渠道确实扣款，按照业务规则进入退款或人工补偿，不能直接忽略回调。
  5. 资源释放幂等：库存释放、退款等使用唯一业务标识和状态校验，避免重复释放、重复退款；通过对账发现遗漏。

面试口述版 ​

延迟消息只是触发检查，不是直接关单的依据。支付和关单都要用数据库条件更新竞争订单状态，同时核实渠道支付结果并协调关闭支付单。如果订单已关闭但用户实际扣款，就走幂等退款或补偿流程。库存释放也要幂等，并通过支付对账兜底，不能认为加一把锁就能让数据库和支付渠道保持原子一致。

10. 某条消息一直失败，影响正常消费怎么办？ ​

处理思路 ​

  • 区分错误类型：网络超时、下游短暂不可用可重试；格式错误、缺少必填字段等永久错误通常应直接隔离。
  • 有限退避重试：设置重试次数和间隔，可采用延迟重试队列，避免立即重新入队形成忙循环。
  • 失败隔离：耗尽重试后进入异常队列，记录消息标识、错误原因、失败次数并告警。
  • 可靠交接：如果应用主动转发到重试或异常队列，应确认转发可靠完成后再确认原消息，并接受交接窗口可能导致重复。
  • 修复后重放：提供受控重放流程，保持业务标识不变，并验证幂等，避免批量重放压垮下游。
  • 顺序取舍：独立消息可以隔离后继续消费；严格有序业务不能直接跳过前序失败事件，应暂停对应分片或业务键并补偿。

面试口述版 ​

我不会让失败消息无限重新入队。先区分临时故障和永久错误，临时故障做有限次数的退避重试，永久错误或重试耗尽后进入异常队列并告警。转发重试消息时也要保证可靠交接，修复后再受控重放。如果同一业务要求严格顺序，还要明确失败事件是否允许跳过，不能为了吞吐破坏业务顺序。

11. 多个服务都需要收到消息，可以共用一个队列吗？ ​

处理思路 ​

  • 同一队列多个消费者是竞争消费：一次投递由其中一个消费者处理，不代表每个服务都能收到。
  • 各服务独立队列：库存、积分、短信分别创建队列，绑定同一个业务交换机，实现各自订阅。
  • 按路由需求选交换机：广播可使用 fanout；需要按事件类别筛选时可使用 topic 或 direct。
  • 服务内部扩容：同一服务的多个实例消费该服务自己的队列，实现负载分担。
  • 独立失败处理：各队列独立配置重试、异常处理和告警，一个服务失败不应直接阻塞其他服务。
  • 订阅时机：普通队列绑定前发布的消息不会自动补发；需要可靠接收时，应先完成持久化队列和绑定部署。

面试口述版 ​

不能让库存、积分和短信共用一个队列，因为那是竞争消费，不是广播。我会给每个服务建独立队列，绑定同一个交换机，让它们各自收到需要的事件。某个服务内部可以用多个实例消费自己的队列来扩容，失败重试也独立管理。还要提前部署队列和绑定，不能期待新订阅者自动拿到历史消息。

12. 秒杀请求进入 MQ，就代表抢购成功了吗？ ​

处理思路 ​

  1. 入口限流与资格校验：防刷、限制重复请求，控制进入系统的流量。
  2. 原子预扣库存：可以使用 Redis 原子操作或脚本完成库存判断、预扣和用户去重，但要考虑 Redis 的持久性和故障边界。
  3. 可靠受理：预扣与发送 MQ 不是一个原子操作；必须设计可恢复的受理记录、投递重试和对账，不能只在发送异常时简单加回库存。
  4. 异步创建订单：消费者幂等落单，数据库唯一约束保证业务去重；结合库存扣减或预占记录，确保库存账正确。
  5. 失败回补：根据请求最终状态进行幂等回补。发布确认超时不等于消息未发送，要先核实或补偿，避免订单成功又回补库存。
  6. 明确结果状态：接口返回“已受理/排队中”，用户通过查询或通知获知最终结果；超时待处理也需明确反馈。

面试口述版 ​

进入 MQ 只代表请求被受理，不代表抢购成功。入口先限流和校验资格，再原子预扣库存，并解决预扣与消息投递之间的可靠性问题。消费者异步幂等落单，失败时按最终状态回补库存，用户通过结果查询获取成功或失败。确认超时时不能立即回补，因为消息可能已经送达，需要核实和对账，避免超卖或库存不一致。

13. 消费者处理很慢，可以先确认消息再处理吗？ ​

处理思路 ​

  • 不能直接提前确认：确认后进程宕机，Broker 不再负责重投，尚未完成的业务可能丢失。
  • 先定位慢的原因：优化慢 SQL、远程调用和串行操作，设置超时，并按下游容量增加实例或并发。
  • 合理控制在途消息：调整预取数量、线程池和消费并发，关注未确认数量及消费者确认超时配置。
  • 需要异步交接时先可靠落地：将消息转换为持久化任务，事务提交成功后再确认原消息；后台任务具备领取、执行、重试和故障恢复能力。
  • 交接仍需幂等：任务已经落库但原消息尚未确认时宕机，会重复投递，因此任务表应有唯一约束；任务完成和业务更新也要保证一致性。

面试口述版 ​

我不会收到消息后就立即确认，因为后续进程宕机会丢失业务处理机会。优先优化耗时、合理设置预取和并发。如果确实需要异步处理，会先把任务可靠写入数据库，提交成功后再确认消息，之后由可恢复的任务执行器处理。这个方案只是转移了可靠性责任，仍需要任务去重、重试、状态管理和补偿。

场景题通用答题框架 ​

  1. 业务目标：为什么使用 MQ？成功的业务定义是什么？
  2. 故障点：数据库提交、发送、确认、消费分别在哪些窗口可能失败？
  3. 处理方案：如何可靠投递、控制顺序、重试和隔离异常？
  4. 幂等与补偿：重复消息如何处理？长期失败如何恢复和对账？
  5. 性能取舍：吞吐、延迟、顺序、一致性和下游容量如何平衡？

场景题不只回答“开启某个配置”，还要说明业务边界、失败后的恢复方式，以及方案的代价。
